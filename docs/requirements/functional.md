## 0. AI-first parity

- **FR-0.0 [MVP]** Scope of AI-first: kora's MCP server and skills serve the **user's own coding-agent session** (the engineer's Claude Code or Codex replacing manual actions). Agent nodes inside a graph have no access to kora's MCP server or API; they only receive typed inputs and produce typed outputs.
- **FR-0.1 [MVP]** kora exposes its own **MCP server** (as a `kora mcp` stdio process and as an HTTP MCP endpoint on the API server) with curated, task-shaped tools (an authoring server and an operating server, sixteen tools in the complete inventory; the first slice exposes ten stdio tools under [ADR-0002](../decisions/0002-ai-first-api-and-thin-clients.md); tools that start work return its outcome at once, and waiting for a run is a bounded option of reading it; skills stay files in each harness's own format and are not duplicated over MCP) that together cover every operation available through the CLI and HTTP API: authoring help (DSL reference, presets catalogue), `compile`, `validate` (structured errors with source locations), `deploy`, `trigger` with parameters, list and inspect runs, nodes, attempts, logs, artifacts and cost, `approve`/`reject` with typed input, `retry`, `cancel`, manage presets and namespaces. The MCP server acts with the user's token and has exactly the user's permissions.
- **FR-0.2 [MVP]** kora ships **skills** for the supported harnesses (Claude Code skill, Codex equivalent) that teach an agent how to author, validate, deploy and operate graphs through the MCP server, including the artifact and error schemas.
- **FR-0.3 [MVP]** Parity is enforced structurally: the HTTP API is the only implementation of operations; CLI, MCP tools, skills and the web frontend are thin clients of it (the frontend through a TypeScript client generated from OpenAPI). A coverage test verifies that every API operation is reachable through the CLI and through at least one MCP tool; a capability added to one surface without the others fails the release checklist.
- **FR-0.4 [MVP]** All errors (compile, validate, API, runtime) are structured objects with a stable code, a message, and a location (file:line for DSL, YAML path for IR, ids for runtime), consumable by agents without parsing prose.

## 1. Graph definition

- **FR-1.1 [MVP]** Graphs are defined in Python using decorators and the `>>` dependency operator in the style of Airflow TaskFlow (`@graph`, `@node`-style decorators; `a >> b >> [c, d]`). Passing a node's output as another node's keyword argument also creates a dependency; node inputs are keyword-only.
- **FR-1.2 [MVP]** Every graph compiles to a **YAML intermediate representation (IR)**. The scheduler consumes only the IR; it never imports user Python at run time. The IR carries a root `ir_version` field (the format version, distinct from the graph's own `graph.version`) and is validated against a published JSON Schema.
- **FR-1.3 [MVP]** The IR separates three concerns into distinct sections: (a) graph topology and node definitions, (b) graph-level runtime and policy configuration, (c) references to secrets (never secret values).
- **FR-1.4 [MVP]** `kora compile` produces the IR from Python; `kora validate` checks an IR against the schema and semantic rules (acyclicity, resolvable references, artifact type compatibility on edges, one branch owner per direct target and its explicit control edge). Compiled IR is a committed, machine-generated file that is never hand-edited (precedent: gh-aw `.lock.yml`, Windmill `flow.yaml`).
- **FR-1.5 [post-MVP]** Other language SDKs and a UI editor produce the same IR. Design rule: stable string node ids and expression references, not positional edges; lenient on unknown top-level keys, strict inside typed sub-objects.
- **FR-1.6 [MVP]** Dependency trigger rules per node, Airflow-style: `all_success` (default), `all_done`, `one_success`, `one_failed`, `none_failed`, `none_failed_min_one_success`, `all_skipped`. When an upstream node is retried and succeeds, downstream nodes whose rules are now satisfied start automatically.
- **FR-1.7 [MVP]** Graph versioning: each run records the graph version it ran with and keeps it until it ends; a manual retry (FR-6.8) stays within that version. Running an existing run again is a new run linked to the original, on the original's graph version unless explicitly told to use the latest or a named one (amended 2026-10-16, requirements decision 25).

## 2. Node kinds

- **FR-2.1 [MVP] Agent node.** Runs one full coding-agent session on a harness. Harness is a protocol; MVP implements **Claude Code** through the Claude Agent SDK and **Codex** through its app-server JSON-RPC protocol (the Codex SDK exists only for TypeScript). **[post-MVP]** A third adapter speaking the Agent Client Protocol (ACP) covers OpenCode, Pi, Gemini CLI and other ACP-capable agents. kora enforces event, budget and stall limits itself from the event stream regardless of adapter.
- **FR-2.2 [MVP] Human-input node (approval gate).** Pauses the run and waits for a typed response through an approval channel (section 7). Has a form schema, a timeout, a default/expiry behaviour (`fail` | `skip` | `default_value`) and records approver identity. It holds no worker slot while waiting.
- **FR-2.3 [MVP] Wait-for-event / sensor node.** Blocks until an external condition holds: webhook received, CI status on a PR, PR merged, HTTP poll with a CEL predicate, or a custom sensor. Sensors are a protocol (section 8a) with built-in implementations for change-request status, CI status and HTTP. Has a poll interval and a timeout. Holds no worker slot while waiting.
- **FR-2.4 [MVP] Timer node.** Durable delay ("wait 24 h, then continue").
- **FR-2.5 [MVP] Branch node.** Deterministic routing on an upstream artifact's fields with a CEL (Common Expression Language) expression (e.g. `inputs.review.verdict == "approved" && inputs.bench.cpu < inputs.baseline.cpu * 0.85`, with `cpu` declared a `number`). CEL is the expression language everywhere in the IR (branch conditions, retry predicates, sensor predicates, event filters). No LLM in the routing decision. Each direct target has one owning branch in MVP, lowered to an explicit control dependency. Its current persisted selection gates every target readiness evaluation, including after target-only retry; permissive trigger rules cannot bypass routing. Untargeted joins retain ordinary trigger semantics (ADR-0006).
- **FR-2.6 [MVP] Fan-out.** A list-typed artifact expands into N parallel instances of a sub-graph (`expand`-style mapping; a single node is wrapped by the compiler); the fan-out node itself produces the list artifact of the instances' outputs. Supports a parallelism cap and `skip_failures` semantics for the collection.
- **FR-2.7 [MVP] Sub-graph node.** A graph invoked as a node of another graph. Has its own retry policy, timeout and budget applied to the sub-graph as a unit; a sub-graph retry re-runs the whole sub-graph and marks its intermediate artifacts as superseded (they stay retained per FR-4.5). kora does **not** touch VCS side effects of failed attempts (branches, change requests stay as they are); cleaning them up is the graph author's responsibility, e.g. via a `CommandNode`. Sub-graphs are reusable across graphs and in fan-out.
- **FR-2.7a [MVP] Iteration semantics (the feedback loop).** The graph stays acyclic; a loop is expressed as a sub-graph retry. Rules:
  - An attempt ends in `success`, or in `failed(reason, artifacts)`; a node inside the sub-graph can end the attempt explicitly (`fail_attempt(reason=...)`, e.g. the review node when the verdict is "changes requested").
  - Attempt N+1 receives the sub-graph's original inputs plus a `previous_attempt` input: the failure reason and the artifacts of attempt N (for the SQL optimisation case: `VcsRef` of the candidate branch, the review verdict with comments, gate results). Nodes declare whether they consume `previous_attempt`.
  - The sub-graph's `max_attempts`, timeout and budget span all attempts; the per-node limits apply per attempt.
  - Everything inside the sub-graph re-runs; nothing is memoised across attempts unless a node declares its output as attempt-invariant, in which case it is reused. In MVP `attempt_invariant` is forbidden on branch nodes and their direct targets named by any case or `else`; those nodes participate in each new iteration's routing (ADR-0006).
  - Artifacts of all attempts are retained with attempt lineage (FR-4.5).
- **FR-2.8 [MVP] Command node.** Runs a command (argv, no shell) deterministically in an isolated workspace (same VCS checkout semantics as an agent node, same runtime protocol). Output artifact: exit code, captured stdout/stderr (truncated, full output stored as a reference), optional JSON parsed from a declared output file into a `StructuredOutput` or a declared custom artifact type. A graph or node may declare **protected paths** (gate scripts, build files, test directories): the tool policy forbids agent nodes of the graph from editing them, and before a command gate runs the worker verifies their digests against the base commit, failing the attempt with class `protected_path_modified` on mismatch. Intended for cheap mechanical gates outside the agent loop: build, tests, benchmarks, linters, VCS cleanup. Follows the pattern of the published case studies (Dropbox: "not every step belongs inside the agent loop"). Measurements may also come from an agent session through domain MCP tools and skills; a command node is the choice when the author wants them outside any session. Not a general-purpose Python task runner: no user Python executed by the scheduler.

## 3. Node configuration and inheritance

- **FR-3.1 [MVP]** Agent-node configuration vocabulary: harness (`claude` | `codex`; `acp:<agent>` after MVP), model, tool-call policy reference (FR-8b), system prompt (append), prompt template, skills, subagents, hooks, MCP servers, permission mode, sandbox mode, workspace reference, output artifact schema, retry policy, timeouts, event-count limit, soft budget, runtime override, network policy field, `trust_repo_config` flag (FR-3.4), environment variables and secret references. The vocabulary is a superset modelled on Claude Code subagent frontmatter and mapped per harness. Harness versions are not a node setting: they are fixed per kora installation (images or installed binaries) and recorded on the `AgentSession` artifact.
- **FR-3.2 [MVP]** Layered inheritance with named presets: **global → graph → preset → node**. Each field has a documented merge rule (scalars override, lists such as skills/MCP servers append-and-dedupe, maps deep-merge), modelled on gh-aw `imports` and Airflow `client_defaults` precedence. The resolved per-node configuration is materialised in the IR so the scheduler never re-resolves it.
- **FR-3.3 [MVP]** Per-harness mapping: the harness adapter translates the resolved node config into the options of the harness's interface (Claude Agent SDK: settings, agents, MCP servers, output schema, budget, `setting_sources=[]`; Codex app-server: config overrides, output schema, sandbox mode; after MVP, ACP: the protocol's session and permission messages). Fields that no harness can honour uniformly (event limits, mid-session budget stops, stall detection) are enforced by kora's session runner from the normalised event stream rather than promised as harness features; native limits (Agent SDK `max_turns`, Codex token budget) are applied in addition where they exist. Fields a harness cannot honour produce a validation warning at compile time.
- **FR-3.4 [MVP]** The target repository's own harness configuration (`CLAUDE.md`, `AGENTS.md`, `.claude/` settings, hooks, subagents, `.mcp.json`, `.codex/`) is **not** loaded by default: nodes run hermetically (Agent SDK `setting_sources=[]` or the harness equivalent) and receive only what the resolved node config specifies. A node-config field `trust_repo_config` (default `false`, inheritable through the global → graph → preset → node layers) enables loading of the repository's harness configuration, including its instruction files. Rationale: hooks and MCP servers from a checked-out branch are executable code; the harness docs warn that non-hermetic headless runs execute them even in untrusted folders.

## 4. Artifacts

- **FR-4.1 [MVP]** Every edge carries a typed artifact. A base `Artifact` type defines: id, type name, JSON-Schema of the payload, producer (run, node, attempt), lineage (input artifact ids), created-at, storage reference.
- **FR-4.2 [MVP]** Built-in artifact types:
  - `StructuredOutput` — JSON validated against a Pydantic/JSON Schema declared on the node; produced via the harness's structured-output feature.
  - `VcsRef` — immutable publication facts: repository, branch, exact commit and base revision, changed paths and diff summary, the pushing principal, and optional change-request, commit and comparison URLs with the change-request opening principal. Current change-request status and branch head are observed separately. Revision 1 and its immutable behavior descriptors are defined in the [built-in artifact contract](../../knowledge/specs/artifacts/README.md).
  - `AgentSession` — harness name and version, session id (resumable handle), transcript reference, token usage per model, cost estimate with cost basis and billing class, turn count, duration, tool-permission denials, stop reason.
  - `CommandResult` — exit code, captured output reference, optional parsed JSON (FR-2.8).
  - `ReviewBundle` — the evidence package for the single human touchpoint, split into two parts. **Facts**, populated by kora from its own records and read-only to agents: the `VcsRef` under review (pinned to a commit), gate results taken from `CommandResult` rows with the protected paths in force and the verification result, metrics with the provenance of each number (measured by a command node or reported by an agent session), the diff reference, attempt history, the aggregated cost of all attempts, and provenance of each fact. **Narrative**, written by an agent node: selection rationale and summary. Approvals bind to the digests of the facts; the frontend and the change-request comment render facts and narrative visibly apart. The human-input node accepts a `ReviewBundle` as input; the VCS approval channel publishes it as a change-request comment.
- **FR-4.3 [MVP]** Users define custom artifact types by subclassing the base type with their own schema; custom types are usable on edges, in fan-out and in branch conditions. Authoritative compiled type contracts and their schema/parent/behavior closure are fixed on deployment and used by all consumers, including scheduler-only nodes; registry changes never reinterpret an existing graph version (ADR-0018).
- **FR-4.4 [MVP]** Artifact storage is a protocol; artifact metadata lives in the metadata DB; MVP ships two payload stores: local disk (standalone and development) and S3-compatible object storage (docker-compose and organisation deployments; decided 2026-10-16, requirements decision 23). Large payloads are referenced by digest, not inlined.
- **FR-4.5 [MVP]** Artifacts are per attempt: a retried node produces a new artifact version; previous attempts' artifacts are retained for inspection (retry diffs). Every artifact version and usage record carries provenance: the attempt, the uploading worker and the runtime image digest that produced it. Retention is a graph-level setting with a namespace default; defaults: run metadata and usage records forever, session transcripts 30 days, artifact payloads 30 days, reference-only artifacts (VcsRef) forever; cleanup deletes payloads, never metadata. Every physical attempt also owns immutable input bindings and a nonsecret execution request saved before the first preparation/execution effect, independently of outputs. Rendered text/feedback and content-bearing derived results are retained payloads; historical reads and retry diffs report unavailable content explicitly. Secret values and secret-derived hashes are excluded (ADR-0018).
- **FR-4.6 [MVP]** Node outputs (edge payloads) are distinct from node scratch state. Scratch state (e.g. a resumable session id used by a `resume` retry) survives retries; outputs do not.

## 5. Workspace and VCS

- **FR-5.1 [MVP]** Each agent node runs on an **isolated workspace**: a fresh checkout of the repository at a declared revision; the node's result is a branch/commit expressed as a `VcsRef` artifact. Nodes never share a working directory.
- **FR-5.2 [MVP]** VCS operations are a protocol: typed checkout and publication plans, change requests, branch head and CI status. The runtime supervisor executes preparation and prepares/inspects an immutable publication input in fresh metadata; late `finalize` publishes exactly that revision to a trusted destination. MVP git preserves candidate commits and adds one commit for uncommitted changes, then pushes the platform attempt branch and opens a change request through the configured code-host API. Scan all newly published reachable content/history, not only the final diff, and block leaks with `secret_leak`. Independent non-git VCS plans remain provider-defined (ADR-0005, ADR-0016). Code-host credentials are acquired per purpose (`checkout`, `publish`, `api`) by trusted code at the moment they are needed; each backend reports the scope, operations, expiry, replacement, revocation and stable principal it actually enforces, and nothing falls back to a broader credential. MVP backends: the GitHub App (issued in the control plane), explicitly configured static service credentials, GitLab project or group tokens, and adopter-supplied integrations (ADR-0023).
- **FR-5.3 [MVP]** The VCS implementation is chosen per graph (graph-level config), overridable per node.

## 6. Execution, scheduling and retries

- **FR-6.1 [MVP]** Control plane from day one: scheduler, metadata database, HTTP API, workers/runtime adapters. Run state lives only in the metadata DB; a scheduler restart resumes in-flight runs (adopting running sessions through the runtime protocol).
- **FR-6.1a [MVP] At-most-once submission.** Before calling the runtime, the scheduler persists the attempt; its id is the submission key. `submit(workload)` must be idempotent in every runtime (a second call for the same attempt id returns the existing handle), and `lookup(attempt_id)` recovers the handle after a crash between submit and handle persistence. Adoption after restart is by attempt id, not by handle. Before granting dispatch authority, persist the original non-reused execution domain and every worker incarnation/lease generation. Lease expiry or missing registry/handle preserves execution uncertainty; replacement requires affirmative runtime termination and closure of all old dispatch/publication authority (ADR-0017).
- **FR-6.1b [MVP] Side-effect boundary.** kora guarantees at-most-once submission per attempt, performs its own publications idempotently on their natural keys (the branch; the head and base of a change request) and records every VCS side effect it performs through the VCS protocol. Side effects made inside a session (pushes, change requests, MCP calls) are not transactional and are never rolled back; kora records what the harness reports (`VcsRef`, tool calls in the transcript) and exposes the attempt history so a human or a `CommandNode` can clean up. Retrying a node or sub-graph never deletes anything outside kora's own state. Unknown kora-managed publication retains the replacement barrier; an API epoch cannot revoke an already issued external operation. Already-issued agent/MCP effects can outlive runtime execution, with no generic exactly-once guarantee (ADR-0017).
- **FR-6.2 [MVP]** Triggers: manual (`kora trigger <graph> --param k=v`, API), cron schedule, webhook/event (HTTP endpoint authenticated by HMAC signature or by bearer token with timestamp and nonce replay protection; payload parameters are schema-typed and never templated into commands or revisions; webhook-triggered graphs default to `overlap: queue`), "triggered by another graph", and sensor-driven start (poll predicate). All starts use bounded canonical acceptance: persist a pending run or a deduplicated overlap-skip outcome before success, never an uncounted pending trigger event. Full outstanding quota is a structured retryable refusal; internal scheduled/event occurrences record explicit rejection without hidden catch-up. Accepted replay returns its original outcome before current-version validation or quotas (ADR-0020).
- **FR-6.3 [MVP]** Retry policy per node and per sub-graph: `max_attempts`, `initial_interval`, `backoff_coefficient`, `max_interval`, `retry_on` (error classes: harness error, timeout, budget exhausted, artifact validation failed, custom predicate on the artifact), `non_retryable` classes.
- **FR-6.4 [MVP]** Agent-node retry **strategy** is chosen by the graph author per node:
  - `fresh` — new session, clean workspace, same inputs;
  - `resume` — resume the same harness session with a feedback message (uses the `AgentSession` handle; available only when the runtime declares `supports_resume`);
  - `fresh_with_feedback` — new session that receives the previous attempt's artifacts and failure reason as additional input.

  The documented default pattern for "reviewer rejected with comments" is `fresh_with_feedback`: a new session on a workspace checked out from the attempt's branch, with the `VcsRef` and the review comments as inputs. `resume` is documented as an optimisation for runtimes that can keep the session's environment; a `resume` whose session is no longer available, or whose installed harness version changed, falls back to `fresh_with_feedback` and records that on the attempt.
- **FR-6.5 [MVP]** Timeouts: per physical node attempt, per subgraph instance across iterations, per run and per human-input/sensor wait. Managed preparation/execution/publication inherit the earliest configured execution deadline and apply local interruption/escalation without control-plane connectivity. Run time starts at promotion, subgraph time at first activation and attempt time at first executing claim before preparation; existing clocks survive retry/adoption. The nominal 30-second grace follows the deadline and never restarts on recovery; physical termination remains evidenced, with explicit clock/failure assumptions (ADR-0022). Wait expiry keeps its configured behaviour.
- **FR-6.6 [MVP]** Event-count limit per agent node (`max_events`: turns, tool calls and tool results counted by kora's session runner from the normalised event stream) with a classified error (`events_exhausted`) usable in `retry_on`. kora enforces it itself by interrupting and then terminating the session; harness-native limits are applied in addition where they exist (Agent SDK `max_turns`).
- **FR-6.7 [MVP]** Cancellation of a run or a node with a grace period; runtime adapters must establish termination before release. Cancellation revokes current-result authority immediately but retains unresolved attempts, capacity and acquired target holds until execution and dispatch/publication closure is established; recovery-only claims remain available after run cancellation (ADR-0017).
- **FR-6.8 [MVP]** Manual retry of a failed node (and everything downstream via trigger rules) from the CLI/API without restarting the run; record clear/cancel intent immediately, but admit no new attempt in the affected run while any old execution/publication recovery remains unresolved. A linked rerun is refused while the original has any replacement-blocking condition; cancellation never becomes infrastructure retry (ADR-0017). Retry requires the sources needed by the selected new attempt to be available; missing/expired required content is a structured conflict before new effects. Potential future retry does not extend payload retention indefinitely (ADR-0018). Retrying a settled failed run reacquires outstanding acceptance capacity before any clear/downstream mutation; a full quota refuses it without effects, while an already outstanding run takes no second credit (ADR-0020).
  Manual retry preserves existing run/subgraph clocks and checks the target wrapper and ancestors before quota/clear mutations. An expired persistent scope is refused with `API002`, reason `deadline_expired`, and rerun guidance; a new physical attempt may get a fresh node clock (ADR-0022).

- **FR-6.8a [MVP] Artifact versions and downstream invalidation.** Manual retry or a new subgraph iteration invalidates the affected current dependency closure atomically, including dependents that never consumed an artifact. Fully cleared nodes return to pending and reevaluate their trigger, input and routing rules; current/staged outputs become historical, open waits are cancelled, pending approvals invalidated and running attempts cancelled without losing history or usage. Retrying one body child recollects enclosing exports and fan-out lists while retaining unaffected siblings; retrying the wrapper or invalidating its inputs/control dependencies resets its current body. `independent_of` names inputs and may preserve only an already successful result; another affected input or control dependency still invalidates it. Inherited deadlines and the run target never reset (ADR-0007).
- **FR-6.9 [MVP]** A daily soft cost limit per namespace: when the day's estimated spend exceeds the namespace policy value, no new attempts are admitted until the next day (running attempts finish); exposed in the API and metrics. **[post-MVP]** finer quotas (per graph, per week, hard limits).
- **FR-6.10 [MVP]** Concurrency controls: global, per-graph and per-runtime parallelism limits; fan-out parallelism cap over unfinished body instances, retained through waits. Graph `max_running_runs` counts distinct runs with any non-terminal physical attempt, across graph versions; all attempt reservations survive until confirmed closure. No-attempt waits consume no execution-run slot. Namespace `max_pending_runs` separately bounds outstanding accepted runs, including active/waiting runs and retained recovery/holds, with a positive finite default of 1000. Graph concurrency caps are live policy from the highest-numbered active version, falling back to the newest deployed version when none is active; execution semantics remain pinned. Admission scans eligible instances in stable FIFO order, skipping blocked work; effective counts, scopes, limits, cap provenance and next action are public (ADR-0020).
- **FR-6.11 [MVP] Target identity.** A run may carry an optional target key with namespace scope, bound from a valid present run parameter or on successful atomic acceptance of the complete result of the declared top-level output source. Once bound, the key never changes or clears, even after hold release or retry. Same-key rediscovery is accepted; a different key rejects the entire source result with non-retryable `config_error`, without exposing any companion output as current. The first binding and its compact source evidence survive payload expiry; a different target requires a new run (ADR-0019). The graph declares what a new run does while another run holds the same target: `allow` (the default) or `defer` (wait at admission until the holder leaves `running` and all blocking execution/publication recovery is settled), applied as one admission scope beside the limits of FR-6.10; it never cancels a run or closes a change request. Without physical attempts, target deferral reserves no execution capacity and does not stop eligible independent-target work; real occupied capacity, the bounded shared outstanding quota and graph-wide `overlap` still apply (ADR-0020). Acquired target holds survive execution-slot release, including review/soak waits. Incoming `allow` can create several holders, and `defer` waits for every other holder. The target's history (its runs, their approval requests, the change they bound and the accepted one) is a read projection over stored data, exposed in the API, the CLI and an MCP tool. **[post-MVP]** `supersede` and `join` policies, a caller-supplied target key in the trigger request, a stable mapping key inside a fan-out.
- **FR-6.12 [MVP] Execution reconciliation.** The public API accepts idempotent `observe` and `stop` intents for worker recovery and an explicit operator `confirm_stopped` attestation of actual termination/decommissioning and closure of every old dispatcher/publication authority, with reason and evidence reference, expected recovery version/domain and namespace plus `platform` checks. No force-overlap action exists. The shared CLI client and existing `kora_admin` tool expose the operation; reads/events/metrics and console show unknown execution, evidence provenance, retained scopes and permitted actions, including terminal runs (ADR-0017).

## 7. Approvals (human input)

- **FR-7.1 [MVP]** The approval channel is a protocol: `request(form_schema, context) → request_id`, `poll/notify(request_id) → response | pending`, `cancel(request_id)`. Responses are typed data validated against the form schema; approver identity and timestamp are recorded.
- **FR-7.2 [MVP]** Built-in channels: **CLI/API** (`kora approve <approval-id> --input ...`, REST endpoint; requires a token with the `approve` flag, FR-12.4) and **VCS change request** (approval = change request approved by a reviewer who is neither its author nor kora's own bot identity and, when the namespace sets an approver allowlist, is on it; "merged" is a separate opt-in signal; rejection = closed or "changes requested"; review comments from collaborators with write access are captured with author and association as the response payload so the next attempt can receive them, by default through `fresh_with_feedback`, optionally through `resume`; see FR-6.4).
- **FR-7.2a [MVP] Approval is bound to content, not to a URL.** An approval request records the exact commit SHA and the digests of the `ReviewBundle` facts it covers. A VCS approval is accepted only if the change request's head SHA equals the recorded one; a new push invalidates the pending request and fails the node with `candidate_moved`; a new request is produced only for a new commit, by retrying the producing node. The approval record stores approver identity, timestamp, SHA and digests.
- **FR-7.3 [MVP]** A **web console** (`kora web`, production stack from the start) held to the user-experience bar of NFR-13.1. MVP scope: approvals (pending approvals, the review bundle with facts and narrative rendered apart, the form and the decision); runs (list with filters, a run page with the live graph, node states and timeline); the attempts of a node with their artifacts and the diff between attempts; session logs followed live; cost per run, node and attempt; graphs and their versions. Editing graphs in the console stays post-MVP (FR-1.5). Amended 2026-10-16 ([ADR-0015](../decisions/0015-web-console-design.md)): the console's sections are Graphs (the entry), Targets, Approvals, Cost and System; its actions in MVP are the approval response, triggering a run with parameters, retrying a node and cancelling a run or node; its design is [console.md](../console.md).
- **FR-7.4 [post-MVP]** Chat approval channels (approving or rejecting from Slack or Telegram) and enterprise approval systems implemented against the same protocol.
- **FR-7.5 [MVP]** Gate state is stored as data, never as serialised callables.
- **FR-7.6 [MVP]** Notifications tell people when an approval is needed, when an outstanding approval becomes invalid or expires, and when a run fails or needs intervention: the `vcs` channel requests configured reviewers on the change request, and per-namespace subscriptions deliver selected event kinds as signed JSON webhooks or one-way Slack and Telegram messages, at least once, with links to the console and the change request. A notification never approves and never carries secret values, transcripts or artifact payloads (ADR-0025).

## 8. Runtimes

- **FR-8.1 [MVP]** Runtime is a protocol: idempotent `submit(workload)` keyed by attempt id, `lookup`, `adopt`, `status`, resumable `events`, `heartbeat`, late `finalize(handle, authorization)`, `cancel`, domain-bound `recovery`, monotonic `record_dispatcher_quiescence`, durable `retire(attempt_id, grace)` and `release`. Retirement serializes with delayed submission/finalization, returns affirmative termination evidence only, and retains its fence beyond release (ADR-0017). Workloads carry resolved config, workspace target, VCS plans and secret/artifact references. The supervisor hosts the harness adapter and enforces event, soft-budget and stall limits; candidate processes run through its runtime launcher. Capabilities include resume, network enforcement, credential proxy, plan executors and protected execution (ADR-0016).
- **FR-8.2 [MVP]** Built-in runtimes: **local process** for trusted development/tests on Linux and macOS, without sandboxing or extra trust opt-in; **Docker** with a candidate container and separate trusted publication environment under one logical attempt handle. Local does not claim isolation from hostile same-user code. An installation requiring protected execution rejects an incapable runtime (ADR-0016).
- **FR-8.3 [post-MVP]** Cloud sandbox runtime (one of E2B / Daytona / Modal class, with pause/snapshot) as the second wave; **Kubernetes** (one Job/Pod or `agent-sandbox` per session) as the third wave or community-contributed.
- **FR-8.4 [MVP]** Runtime is selected at graph level and overridable per node (precedent: Airflow `executor=` per task).
- **FR-8.5 [MVP]** Secrets reach the runtime only through the secrets protocol (section 10); the runtime adapter decides the injection method (env var, file, proxy).
- **FR-8.6 [MVP]** Network policy is a field of the node config (egress allowlist) on agent and command nodes and on MCP-server entries; runtimes that cannot enforce it report that through capability flags and compile-time warnings. An agent node or MCP server holding secrets fails validation without enforced egress and tool-secret isolation, unless the namespace allows it explicitly; on unenforcing runtimes such a run starts only with an explicit recorded option (ADR-0009, amended 2026-10-18).
- **FR-8.7** Adopters implement enterprise runtimes (for example an in-house CI and execution platform) against the same protocol; kora ships a conformance test suite for runtime implementations.
- **FR-8.8 [MVP]** The runtime names the workspace and supplies trusted lifecycle/control storage. Runtime and VCS negotiate plan placement (`runner`, preferred, or `worker_host`). Worker-host publication receives sealed bytes in private storage, never executes against candidate metadata, and uses the same late-finalization contract. Independent runtime/VCS composition needs no shared worker filesystem. Harness API keys remain environment variables in MVP; the per-attempt proxy stays post-MVP. Publication credentials arrive only after inspection; parent credentials remain outside candidate execution (ADR-0016).
- **FR-8.9 [MVP]** Workers authenticate to the control plane with a service principal bound to a runtime and to a namespace list, limited to claiming attempts of that runtime in those namespaces and to heartbeat, upload and state transitions on attempts they hold a lease on; every worker write carries a lease epoch and stale writes are rejected. Each process registers a fresh incarnation and the runtime domain; every dispatch grant is durable before return. Recovery-only claims permit observation, retirement and historical reporting for cancelled/superseded attempts, including terminal runs, without new submission/publication authority. Every by-id API route is scoped to the namespace in the path.

## 8a. Sensors

- **FR-8a.1 [MVP]** Sensors are a protocol (`poll(context) → satisfied | pending`, poll interval, timeout, capability flags) discovered through entry points; built-in sensors: change-request status, CI status, HTTP poll with a CEL predicate over the response. Adopters add their own (e.g. "slow query appeared in the top list").

## 8b. Tool-call policy

- **FR-8b.1 [MVP]** Tool policy is a protocol (decision point for tool calls: `decide(principal, tool, arguments, context) → allow | deny`) invoked through the harness's pre-tool-use hook mechanism (Claude Code hooks, the Codex equivalent, and after MVP ACP's permission request). The node configuration carries one `tool_policy` with `allow` and `deny` lists (this replaces separate allowed/disallowed tool fields) inherited through the layers; the namespace-level policy set by the platform team is evaluated as its own layer, so a deny in either layer wins and every layer with a non-empty allow list must match (amended 2026-10-21). MVP implementation: allow/deny lists by tool name and argument patterns with argv-level matching under which a call with shell chaining or `-c`/`--exec`-style indirection matches every `Bash(...)` deny and no allow pattern (amended 2026-10-21); a conformance test verifies, for every call kind an adapter declares covered and under every permission mode, that a deny reaches every tool call the harness does not reject itself (amended 2026-10-19, [ADR-0009](../decisions/0009-target-repository-trust-boundary.md)). Denials, including calls a harness permission rule denied, are recorded as session events on the `AgentSession` artifact; a call a built-in tool's own input validation rejects is a failed tool call, not a denial. Cedar/OPA evaluators as plugins later (additive IR change).

## 9. Cost accounting and limits

- **FR-9.1 [MVP]** Unit of record is **tokens per model per node attempt** (input, cached input, output, reasoning; cache creation where reported), read from the harness result (Claude Code `usage`/`modelUsage`, the Codex app-server's turn-completion usage report). Each usage record carries a completeness state: `complete` (final result received), `partial` (summed from streamed per-turn events after a crash or kill; Codex reports usage only when a turn completes, so a killed turn is unaccounted), `unavailable`. For `resume` retries, where the harness reports whole-session totals, the attempt's usage is the delta between the totals after and before the resume.
- **FR-9.2 [MVP]** A **pluggable price table** converts tokens to a USD-equivalent estimate; kora ships a default list-price table and allows overriding it (corporate contract, gateway prices). When the harness reports its own cost with a trustworthy basis (Claude Code `costBasis` in `list` | `managed`), that figure is used.
- **FR-9.3 [MVP]** Each `AgentSession` artifact records a **billing class** (`api_key` | `subscription` | `gateway` | `managed`) so estimates can be interpreted correctly; subscription-based runs are labelled "not billable in USD".
- **FR-9.4 [MVP]** **Hard limits** enforced by kora: inherited node/subgraph/run timeout policy and `max_events` (FR-6.6). Timeout means fixed local interruption/escalation thresholds under ADR-0022, not instantaneous physical stopping, remote-effect rollback or capacity release. **Soft limit**: USD-equivalent budget per node and per run; for Claude Code it is also propagated to the Agent SDK's `max_budget_usd`, for Codex kora computes spend from the token stream and terminates the session when exceeded. All USD figures are labelled as estimates.
- **FR-9.5 [MVP]** Run and node views show tokens, estimated cost and cost per attempt; fan-out views aggregate across instances.
- **FR-9.6 [post-MVP]** Reconciliation against vendor Admin usage/cost APIs and gateway spend; period quotas (FR-6.9).

## 10. Secrets

- **FR-10.1 [MVP]** Secrets provider is a protocol: `resolve(reference) → value` with references like `secret://<provider>/<name>`. MVP implements environment variables and a local file; Vault, Kubernetes Secrets and enterprise providers post-MVP or by adopters.
- **FR-10.2 [MVP]** Secret values never appear in the IR, artifacts, logs or transcripts; kora redacts known secret values from captured output. Redaction and the publication secret scan cover literal values and common key patterns, not encoded or transformed values; the full statement of what MVP secret handling guarantees and does not is in ADR-0009 (amended 2026-10-18).

## 11. Observability

- **FR-11.1 [MVP]** Run and node status, timeline and failure reason via CLI (`kora runs`, `kora run <id>`, `kora logs <run> <node> --follow`) and HTTP API.
- **FR-11.2 [MVP]** The normalised session event stream is captured per attempt as segments in artifact storage (readable live by `kora logs --follow`) and the raw harness transcript is stored as the transcript reference of the `AgentSession` artifact; both are retained per attempt.
- **FR-11.3 [MVP]** Observability exporter is a protocol (a single `on_event` over the append-only event timeline, so exporters are replayable; exporters run in the control plane only) with one **opt-in** reference implementation in MVP: **OpenTelemetry** over OTLP (GenAI semantic conventions: `invoke_workflow` span per run, `invoke_agent` span per attempt built from the session event segments, inference and tool spans, `gen_ai.usage.*` attributes, harness session id as `gen_ai.conversation.id`). Langfuse and Datadog LLM Observability ingest OTLP and are configured as OTLP endpoints; custom exporters (for example to an in-house monitoring system) implement the protocol. **[post-MVP]** vendor-native exporters where OTLP is insufficient.
- **FR-11.4 [MVP]** Audit log: approval decisions with approver identity, tool-permission denials from the harness, run → node → attempt → session → VcsRef linkage.
- **FR-11.5 [MVP]** Graph visualisation, run inspection and retry diffs are views of the web console (FR-7.3). Attempt inspection/diff reads saved per-attempt inputs, requests, policy and observed execution facts; content expiry and unknown observations are explicit. Prompt/feedback and equivalent content projections require namespace `transcripts` access on every surface (ADR-0018).

## 12. Control plane, CLI and deployment

- **FR-12.1 [MVP]** Components: scheduler, metadata DB (PostgreSQL; SQLite for standalone/dev), HTTP API, runtime workers/adapters, web console (FR-7.3).
- **FR-12.2 [MVP]** CLI: `kora compile`, `kora validate`, `kora plan` (materialised execution plan), `kora deploy <ir>` (register a graph), `kora trigger` (with `--dry-run` on the fake runtime and harness), `kora graphs`, `kora runs`, `kora run`, `kora node`, `kora events`, `kora logs`, `kora diff` (between attempts), `kora cost` (per run, or daily per namespace), `kora approve` / `kora reject`, `kora retry <run> <node>`, `kora cancel`, `kora reconcile` (versioned/domain-bound `observe`, `stop` and evidenced `confirm_stopped`, requiring namespace access plus `platform`), `kora presets pull`, `kora plugins list`, `kora conformance`, `kora doctor` (installation health check incl. harness version ranges), `kora db upgrade`, `kora standalone` (single process with SQLite for development), `kora open` (opens the web console signed in through a one-time link).
- **FR-12.3 [MVP]** Deployment: `docker-compose` (Postgres + an S3-compatible object store + scheduler + API + local/Docker runtime) and `kora standalone`. Helm chart for the control plane post-MVP, together with the Kubernetes runtime.
- **FR-12.4 [MVP]** Namespaces/projects group graphs, secret references, presets, tool policies and quotas. Tokens are **personal** from MVP: each token is bound to a person (or a service identity for workers), to a namespace list, and to two optional flags: `approve` (may respond to approvals) and `platform` (may publish presets, namespace policies and tool policies). The MCP server's default token carries no `approve`. No roles or groups: RBAC and credential management arrive through the authentication protocol post-MVP.
- **FR-12.5 [MVP]** Graph registration is versioned: deployment identity binds the canonical IR and resolved execution contract; an identical complete deployment returns the same graph version and a changed contract cannot silently reuse it. Running runs keep their version and contract (ADR-0018).
