### Local mutation audit

Install locked build backends before the optional source-built tooling:

```sh
uv sync --locked --group build --no-build --no-install-project
uv sync --locked --group mutation --group build --no-build-isolation
```

From the tooling checkout, run:

```sh
uv run --no-sync python -B -m scripts.ci.mutation_audit \
  --source-revision "$(git rev-parse origin/master)"
```

The executor audits a disposable copy of the recorded master revision. Source and tooling revisions are recorded separately; the primary checkout is not mutated. Initial scope is pricing arithmetic and CEL-path behavior. Reports in `mutation-report/` contain native inventory, baseline JUnit, normalized outcomes and pending work. The admission budget includes preparation and baseline time; an exhausted budget is a partial result. See the [scope, limits and evidence record](../knowledge/research/mutation-testing-2026-10-30.md).

Ordinary CI verifies the tooling on small owned fixtures on Linux/macOS. Those regressions do not audit PR source or impose a mutation-score requirement. Daily master scheduling, trusted artifact continuation and agent triage activate under #455 after the local foundation.

Install the pinned uv with its versioned installer, following the [official installation instructions](https://docs.astral.sh/uv/getting-started/installation/) to make it available in your shell:

```sh
curl -LsSf https://astral.sh/uv/0.13.1/install.sh | sh
```

Install the Node release recorded in the version file using a version manager or the official binary. With Node available, install the pinned pnpm:

```sh
npm install --global pnpm@12.14.0
uv python install
uv --version
node --version
pnpm --version
```

Run the following commands from the repository root in the same shell. Dependency setup may access package registries; retain the uv cache, pnpm store and temporary build constraints for the subsequent offline distribution build. The setup commands preserve both lockfiles:

```sh
uv sync --locked --no-build --group build --extra postgres --extra cel --no-install-project
KORA_BUILD_CONSTRAINT_DIR="$(mktemp -d)"
uv export --locked --only-group build --no-emit-project \
  --format requirements.txt \
  --output-file "$KORA_BUILD_CONSTRAINT_DIR/constraints.txt"
uv pip install --python "$PWD/.venv/bin/python" \
  --target "$KORA_BUILD_CONSTRAINT_DIR/backend" \
  --require-hashes \
  --requirements "$KORA_BUILD_CONSTRAINT_DIR/constraints.txt"
uv pip install --python "$PWD/.venv/bin/python" --no-deps \
  --build-constraints "$KORA_BUILD_CONSTRAINT_DIR/constraints.txt" \
  --require-build-hashes \
  --editable .
pnpm --dir web install --frozen-lockfile
```

The disposable target primes registry metadata for the isolated build resolver using the locked build requirements and their hashes. Locked sync installs cached artifacts without necessarily populating that metadata, so it is insufficient on a fresh cache. The target is separate from the project environment and is not used by the build itself.

## Source checks and distributions

Ordinary CI and security workflows run when a pull request opens, changes its source revision or reopens, including while it is a draft. Marking the same revision ready for review does not start another CI or security execution. Failed or cancelled required results remain unresolved until the normal correction or explicitly justified recovery process supplies passing final-revision evidence.

Run every source check, then build the sdist and build a wheel from that sdist under isolated, hash-constrained build requirements:

```sh
uv lock --check
uv run --no-sync ruff format --check .
uv run --no-sync ruff check --ignore-noqa .
uv run --no-sync pyright
uv run --no-sync pytest -q
pnpm --dir web run typecheck
pnpm --dir web run lint
pnpm --dir web run build

KORA_BUILD_OFFLINE=1 uv build --offline \
  --python "$PWD/.venv/bin/python" \
  --build-constraints "$KORA_BUILD_CONSTRAINT_DIR/constraints.txt" \
  --require-hashes --clear

uv sync --locked --no-build --group build --extra postgres --extra cel
git diff --exit-code -- pyproject.toml uv.lock web/package.json \
  web/pnpm-lock.yaml web/pnpm-workspace.yaml
```

`--no-build` refuses to compile a dependency from source, so a platform or interpreter without a published wheel for a native package fails at setup instead of building on the machine; `--extra postgres` installs the PostgreSQL driver on every platform, because the dialect is registered whether or not a PostgreSQL test runs. `--extra cel` installs the `common-expression-language` binding, which the CEL tests load; it has no source build in kora's setup, so setup fails on a platform without its wheel, such as Python 3.15 on macOS. The lock constrains `wcwidth`, which the binding's command-line dependencies import, to its last pure-Python release. An install outside kora's lock, such as `pip install kora[cel]`, never gets that constraint, and gets the wheel-only rule only with `--only-binary common-expression-language`. kora loads the binding only when the files of its `cel` package, bytecode caches excepted, match its RECORD and the package contains no symbolic links, so an install in uv's symbolic-link mode is refused. `test_cel_bundled_crate_lock_covers_installed_wheel` in `tests/cel_eval/test_cel_bundled_crates.py` knows the wheels of the CI platforms and Linux aarch64 only, and fails with the unknown wheel tag elsewhere.

The default test run needs a reachable Docker daemon: `tests/conftest.py` runs every database test on SQLite and on PostgreSQL, and the PostgreSQL parameter starts one container per session from the image pinned by digest in `tests/support/databases.py`, migrates a template database once and clones it for each test. `KORA_TEST_DATABASES` selects the parameters as a comma-separated subset of `sqlite` and `postgresql`; the selection is printed in the pytest header, an unknown name is a usage error, and a selected PostgreSQL without a daemon is an error, never a skip. The macOS lanes and a machine without Docker run:

```sh
KORA_TEST_DATABASES=sqlite uv run --no-sync pytest -q
```

The container runs without the reaper container that `testcontainers` starts by default, because the session fixture removes the database container itself on every exit path, readiness failure included; the fixture disables the reaper through the library's configuration when `TESTCONTAINERS_RYUK_DISABLED` is unset, CI sets the variable explicitly, and an explicit `false` re-enables the reaper, which mounts the Docker socket. Readiness is checked from the host with a content-free deadline, never through the library's `psql` probe, so no error carries the password. The container publishes a random port on every network interface of the host for the duration of the run, protected by a password generated for the session; a daemon configured with `"ip": "127.0.0.1"` keeps it on the loopback interface locally.

The default run also excludes the `host_fixture` marker: those tests need host paths that `scripts/ci/prepare-local-runtime-fixtures.sh` prepares with `sudo` under `/opt/kora-local-runtime` (a directory owned by `nobody`, a setuid sleep helper, a 16 MiB `tmpfs` or RAM disk, and on Linux a loopback NFS export through the distribution's `nfs-kernel-server` package and permission for unprivileged user namespaces, reverted at teardown), and without them they fail with a named error, never skip. Every process leg of the local runtime lives under `tests/plugins/runtime/local` and runs in the `local-runtime` lane of each scaffold matrix entry, which prepares the fixtures, runs `uv run --no-sync pytest -q -m "not measurement" tests/plugins/runtime/local` once, requires its host-fixture and contract tests among the executed JUnit identities, and then removes the fixtures; teardown acts only on a fixture directory that the same script's preparation created. The lock-contention and runner-spawn diagnostics in `tests/measurements/test_local_runtime_cost.py` run in separate bounded optional jobs and upload `local-runtime-diagnostics-<os>-<python>` outside mandatory dependencies. The other lanes ignore the local-runtime path; the evidence join requires actual successful general, storage and local-runtime JUnit identities to partition the single complete `-m "not measurement"` collection exactly.

On macOS, host-fixture preparation additionally requires the system C toolchain exposed through `/usr/bin/cc`. It builds the bounded helper in `scripts/ci/setuid-sleep.c` in a temporary directory, removes that build directory on exit and installs the helper as `nobody` with mode `4755`. Linux continues to use a copy of its system `sleep`. The compiler is a test-preparation prerequisite only; running kora needs no C compiler. See the [fixture evidence](../knowledge/research/local-runtime-attestation-probe-2026-10-30.md) for the relocated system-binary failure that this avoids.

## Daily master mutation audit

The `Mutation audit` workflow runs once daily, with a manual recovery trigger, and admits only the native `refs/heads/master` event SHA. It has a ten-minute job cap; the admission budget includes setup and baseline and stops early enough for bounded cleanup and publication. Hosted scheduling is best effort. New commits wait for the next campaign. See the [workflow](../.github/workflows/mutation.yml) and [scope/limits record](../knowledge/research/mutation-testing-2026-10-30.md).

For planning or requested triage, locate the latest applicable successful run on master and read its summary plus `report.json` artifact. Verify the source SHA, declared scopes, continuation status and whether entries were executed, reused, inconclusive or pending. A green job means successful execution/reporting; it does not mean every mutation was detected or every repository component was audited. Missing, expired, failed or partial evidence stays explicit.

Agents compare each relevant finding with the contract, then classify it as a real test gap, demonstrated product defect, explained equivalent/low-value change or tooling/inconclusive. A report group is a triage starting point and may contain several distinct gaps. Search existing issues by behavior, component and finding ID before creating work. Repeated findings update existing work; record new, repeated, resolved and inconclusive states with the original run link. Test-only improvements normally use `type:enhancement`; use `type:bug` for a demonstrated defect in implemented behavior or an established contract.

Fixes use the normal issue, approved implementation plan, focused regression and PR process. A test must express the contract rather than reproduce the current implementation. The next master audit supplies mutation confirmation; ordinary PR checks alone do not establish it. There is no PR mutation campaign, score threshold, required audit status, stale-report hold or autonomous model-provider service. No issues or messages are sent by the scheduled workflow itself.
