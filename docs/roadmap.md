## Where the project stands

- Positioning, requirements and the design are written, went through two design-review cycles, and on 2026-10-16 the project owner reviewed every statement in `docs/`; that review established the initial design baseline. Open design corrections are tracked in GitHub issues; ADR-0016 records the publication-boundary correction and ADR-0017 preserves execution uncertainty through recovery. Deferred work is tagged `[post-MVP]` in the requirements or written up in [proposals/](proposals/README.md).
- The repository scaffold contains a typed Python package, a minimal React shell, a wheel frontend-build hook and a Linux/macOS CI matrix. [Development instructions](development.md) describe setup and verification. Logging, metadata tables/migrations and database reads, CEL parser/binding/evaluator foundations, the first IR models, provider loading and protocol/conformance foundations are implemented with their component checks. The API, scheduler, worker, executor/runtime and real harness integrations are still to build; these foundations are not a runnable end-to-end slice.
- The web console is designed ([console.md](console.md), [ADR-0015](decisions/0015-web-console-design.md)); the implemented frontend is a minimal shell, with the product screens still to build.
- The scope of the first implementation slice is decided in the [ADR-0001 amendments of 2026-10-19 and 2026-10-21](decisions/0001-own-control-plane.md) and the boundary amendment of 2026-10-23, with the exact [capability/refusal matrix](../knowledge/specs/first-slice.md); its defaults are recorded in [DD-36](../knowledge/reviews/design-decisions-2026-10-15.md): `kora standalone` on SQLite as the only deployment it ships, exactly one sequential agent → command gate → human-input approval chain, with the agent selectable between the Claude Agent SDK and Codex app-server, a manual trigger, a local bare Git `VcsRef` publication and approval through the CLI. Wider/parallel topology and unsupported fields/defaults are refused; complete IR/CEL representation remains broader. Both harnesses are required: acceptance runs the same minimal topology independently with each adapter. Every integration test of the slice that touches the metadata database runs on PostgreSQL and on SQLite, under the testing and platform rules of [AGENTS.md](../AGENTS.md#testing). A restarted worker adopts a live session ([issue #123](https://github.com/realkarych/kora/issues/123)). The slice ships full API, CLI and MCP parity: every API operation it adds meets the parity rule of [ADR-0002](decisions/0002-ai-first-api-and-thin-clients.md), checked by the parity coverage test, and a long MCP operation it adds, such as `kora_trigger` for the manual trigger, follows the MCP contract as changed under [issue #124](https://github.com/realkarych/kora/issues/124).

## What the documents cannot settle

These are the assumptions that only code can confirm, in the order they should be tested:

1. **Protected lifecycle and harness SDK behaviour.** ADR-0016 separates the supervisor-side SDK/client from candidate processes through a runtime launcher, then seals input and publishes in a separate authority. The first local slice proves lifecycle behaviour, delayed-dispatch retirement fences, partition recovery without replacement, retained reservations and evidenced reconciliation in a trusted environment; it does not prove OS isolation. Docker process/descendant, journal and transfer conformance on Linux, plus independent-provider evidence, are required before a protected runtime ships. **Harness SDK behaviour.** The adapters ([ADR-0004](decisions/0004-harness-adapters-over-vendor-sdks.md)) and the trust boundary ([ADR-0009](decisions/0009-target-repository-trust-boundary.md)) rely on documented but untested behaviour: the Claude Agent SDK with `setting_sources=[]` and the `PreToolUse` hook, and the Codex app-server protocol (the `PreToolUse` command hook installed as a managed hook of the attempt, the turn-completion usage report); the Agent Client Protocol is after MVP. The first slice must drive a real session through each path it claims. The same first slice records one trace per harness of a provider limit and of an internal retry, because the ADR-0024 mapping of `protocols.md` section 14 is taken from SDK types and app-server schemas, not from observed sessions.
2. **CEL consumer integration.** The selected Rust-backed binding, parser, evaluator, compact cost regression and lifetime checks are implemented. Schema-driven checking/projections and integration with real API/scheduler consumers remain to prove. The compact regression is not a throughput, fairness or scheduler-latency result; the [implementation plan](implementation-plan.md) preserves those consumer gates.
3. **The fake harness and the fake runtime.** The testing rules in [AGENTS.md](../AGENTS.md) forbid mocks, so almost every test depends on these two fakes (`NFR-10.1`) passing the same conformance suites as real implementations. Their separate [contract](../knowledge/specs/fakes.md) is accepted; the fake implementations and their integration with the runner still need to land before the real adapters rely on them. The canonical scenario suite of `knowledge/specs/dsl.md` section 4 runs on these fakes, both fake VCS backends and the approval path, so it can be implemented only after the first slice delivers them; until then its six scenario files are validated against their schema only.
4. **Scale.** The scheduler is designed for hundreds of concurrent attempts (`NFR-1`), which is unverified until a load test on PostgreSQL after the scheduler and worker exist as separate processes.
5. **Code-host backend behaviour.** ADR-0023 takes token lifetimes, rotation semantics and principal stability from provider documentation. The slice that implements a code host confirms them for the corresponding backends through the code-host identity contracts of `protocols.md` §13. Slice 1 publishes only to a trusted local bare repository in explicit credential-free mode, with late authorization, a stable local principal and recovery evidence preserved; receiving code-host webhooks instead of polling remains after MVP.
6. **Product hypotheses.** "External demand", "multi-harness value" and "outer-loop value" in [positioning.md](positioning.md) are tested by the pilot on the canonical SQL optimisation graph, not by code.

## How work is done here

- The project owner decides product features and architecture; proposals go to them as options with trade-offs and a recommendation, one question at a time.
- Decisions become records in `decisions/`, deferred changes become `proposals/`, and the specifications in `knowledge/specs/` are updated to match before code follows them.
- The rules in [AGENTS.md](../AGENTS.md) apply to every contributor, human or agent.
