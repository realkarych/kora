## Context

An agent node checks out a repository and lets a coding agent work in it. Left to themselves, Claude Code and Codex load the folder's own `CLAUDE.md`, `AGENTS.md`, `.claude/` settings, hooks, subagents, `.mcp.json` and `.codex/`. Hooks and MCP servers are executable code, and the harness documentation warns that non-hermetic headless runs execute them even in untrusted folders (FR-3.4); on a shared platform the branch may have been written by anyone, including a previous agent attempt. Three threats shaped the decision, the last two identified by the threat model of the [design review of 2026-10-15](../../knowledge/reviews/review-2026-10-15.md) ([protected gate paths](../../knowledge/reviews/review-2026-10-15.md#protected-gate-paths) and [tool deny coverage](../../knowledge/reviews/review-2026-10-15.md#tool-deny-coverage)):

1. **Prompt injection through repository files.** Instruction files on a branch redirect the agent; hook and MCP definitions run the branch author's code with the session's credentials.
2. **An agent editing its own gate.** Command nodes run tests and benchmarks from the same checkout; an agent that edits `Makefile` or `tests/` passes the gate without doing the work.
3. **A deny that does not reach every tool call.** Harness allowlists differ per permission mode and adapter; shell chaining or `bash -c` hides a denied command inside an allowed one.

## First-slice amendment of 2026-10-23

Unsupported security controls fail validation; an uncovered node-only tool-policy kind is `IR028`, while namespace coverage remains `IR019` and malformed policy remains `IR013`. `IR008` is reserved for non-security adapter warnings. This supersedes the earlier node-only warning rule. First-slice installations also refuse nonempty declared hooks, skills, subagents and MCP servers, and `trust_repo_config: true`; the future trusted-repository residual below does not authorize them now.

The existing local agent-secret exception remains narrow: namespace `allow_unenforced_agent_secrets` defaults false and must permit deployment, and trigger `allow_unenforced_secrets` defaults false and must be explicitly true for each start of such a graph. It permits the agent-secret egress policy to remain honestly unenforced and recorded as such on local, without weakening protected-execution/resource, tool-policy, secret-prefix/reserved-environment or command `require_network_enforcement` checks. Outside that exception, explicit unsupported network policy, including an empty egress list, is refused. [First-slice.md](../../knowledge/specs/first-slice.md#refusal-contract) defines the exact empty/absent values and retained seeded-policy tests.

## Decision

**Hermetic by default.** `trust_repo_config` defaults to `false` and is inherited global → graph → preset → node. With `false`, the `claude` adapter runs with `setting_sources=[]` and `strict_mcp_config=True`; in both modes it uses a fresh per-attempt config directory and home created outside the checkout and sets `ENABLE_CLAUDEAI_MCP_SERVERS=false`, so a branch cannot pre-seed the config directory or home, and the invoking account's settings, shell profile and claude.ai MCP connectors stay out of the session (the last two documented, not yet observed; amended 2026-10-19). The `codex` adapter marks the project untrusted and sets `project_doc_max_bytes=0`, and, after MVP, the `acp` adapter applies a hermetic workspace overlay and refuses execution when the agent cannot exclude project config (amended 2026-10-23). `true` requires the namespace policy `allow_trust_repo_config`, else `IR017`. With `true` the repository's configuration is trusted code outside the tool policy: per the Claude Code documentation its hooks can rewrite a tool call's input after the decision, a project setting can disable hooks and may switch off kora's callback (not yet observed), its settings can change the harness's endpoint, proxy or TLS trust, and settings the agent writes during the session are reloaded. Namespace denies are therefore not guaranteed under `true`, while protected paths are still checked at gate time; the namespace accepts that residual with the permission (amended 2026-10-19). A registry preset that raises the flag above the namespace policy fails compilation with `DSL013`. The resolved flag, permission mode and tool policy are auditable parts of the resolved config (NFR-4.2). Harness configuration policy is distinct from runtime authority: [ADR-0016](0016-trusted-execution-and-publication.md) protects lifecycle state and publication on protected runtimes; local remains trusted development/testing without hostile-code isolation.

**Protected paths.** A graph declares `runtime.protected_paths` and a node adds `protected_paths`: gate scripts, build files, test directories, tooling configuration. The tool policy denies every file-edit tool of the harness on them for every agent node of the graph (amended 2026-10-23: the file-edit family of protocols.md section 12), and before a command gate runs the preparation phase of its attempt compares the paths changed between the base commit and the candidate commit (the `changed_paths` capture of the VCS checkout plan, [ADR-0005](0005-eleven-protocols-with-conformance-suites.md) as amended 2026-10-16) with them and fails the attempt with class `protected_path_modified` on any change. There is no second checkout. In-repository tests are evaluated by code the candidate can influence outside the protected paths, so a gate result is a measurement whose shielding is exactly the declared paths, never an attestation by the platform; the `CommandResult` records the paths in force, the base commit and the verification result so that the reviewer sees how far each measurement was shielded (amended 2026-10-16). Gate scripts can instead travel with the graph as command resources (issue #45): pinned by digest, materialised outside the candidate tree, read-only to candidate code on protected runtimes and re-hashed before execution. That protects the scripts' file integrity; it does not make the gate an independently trusted evaluator, because the candidate still controls the code the gate measures.

**One `tool_policy`.** A node carries exactly one tool-permission field, `tool_policy` with `allow` and `deny` patterns; the DSL's `allowed_tools` and `disallowed_tools` compile into it. The namespace's `tool_policy` and the node's are evaluated per layer (amended 2026-10-21, [issue #134](https://github.com/realkarych/kora/issues/134)): a deny in either layer wins, so a namespace deny always wins, and every layer with a non-empty `allow` must match, so a node never widens a namespace allow list; order inside an array has no effect, and `IR013` validates the patterns. The one exception is the harness's own output channel: the `claude` adapter allows its synthetic `StructuredOutput` tool without evaluating either policy, only for a main-session call with exactly that name of a node with an output schema, and `IR013` rejects a pattern with that exact tool name (amended 2026-10-19). The MVP implementation `allow_deny` treats a shell call with a form on the closed indirection list of [protocols.md section 12](../../knowledge/specs/protocols.md#the-allow_deny-policy-issue-233) as matching every governing `Bash` deny of either layer and no allow pattern, so it is denied under a layer with a non-empty allow list (amended 2026-10-23, issue #233; extended 2026-10-24 to the forms that re-run an argument, including a command substitution however its characters are quoted, as listed in that section). The guarantee is that a deny cannot be bypassed through the listed forms; a denied effect reached otherwise, through options before a subcommand, a script, a build tool or a program outside the list that runs an argument as a command, belongs to the runtime and external-permission layers. A denial travels as a `permission_denied` session event on the `AgentSession` artifact and becomes an event row for the audit log (FR-11.4).

**The policy protocol is the decision point, invoked from the harness's `PreToolUse` hook** (amended 2026-10-16). The session runner answers the hook before every tool call the harness routes through it: on `claude` the Agent SDK callback, the only decision point, which per the Claude Code documentation runs in every permission mode before every call the harness does not reject itself, while a call a permission rule denies is blocked without reaching it and is recorded as a denial from the harness's report, and a call a built-in tool's own input validation rejects never runs and is an ordinary failed tool result, not a denial (amended 2026-10-19); on `codex` a command hook that kora installs as a managed hook of the attempt, with `allow_managed_hooks_only = true` so that repository hooks never load, and that denies by exit code; on ACP (after MVP) `session/request_permission`, whose coverage is declared per agent. Approval requests are not the decision point: Codex raises them only when the agent leaves its sandbox. Each adapter declares the call kinds its hook intercepts (shell command, file edit, MCP tool call, call inside a subagent, hosted tool); a `tool_policy` pattern from the namespace on a kind the adapter does not intercept fails validation (`IR019`), the same pattern from the node alone fails with `IR028` (amended 2026-10-23). Codex hosted web search is the one uncovered kind in MVP and is disabled through the harness configuration. The hook is one of three layers, and the runtime guarantees it actually declares and external-service permissions remain independent of it; local declares no hostile-code isolation (ADR-0016). The decision is local to the session; the agent never reaches kora. The policy conformance suite requires that a deny reaches every call kind the adapter declares covered, under every permission mode, for every call the harness does not reject itself, never reaches the tool, and that a protected path cannot be edited; the harness conformance suite includes a repository hook that must not run.

**Control state and publication.** [ADR-0016](0016-trusted-execution-and-publication.md) places the authoritative journal, plans and publisher metadata outside candidate authority, stops the candidate domain before sealing, inspects an immutable native result and only then authorizes publication. Candidate Git configuration and descendants never execute in a protected publisher. Existing candidate commits are preserved; uncommitted changes become one additional prepared commit. Local follows the structure without OS security claims or extra opt-in.

**Secrets in agent sessions** (amended 2026-10-18, issue #42). Injected instructions reach an agent through repository files, through data it reads (query text, table comments, other tool output) and through review comments carried in `Feedback`, so a secret in the agent's environment can be sent anywhere its network allows.

- **Fail closed.** An agent node with `secret_env` is a validation error (`IR015`) unless it sets a non-empty `network_policy` and its runtime declares `enforces_network_policy: true`. Only the namespace policy `allow_unenforced_agent_secrets` lifts the rule. Command nodes keep the earlier opt-in rule.
- **Secrets for tools, not for the agent.** An MCP server entry may declare its own `secret_env`; one that does must also declare a non-empty `network_policy`, and its runtime must declare both `isolates_tool_secrets` and `enforces_network_policy`, or validation fails under the same rule. A runtime declaring `isolates_tool_secrets` runs every such server outside the agent's process tree and filesystem. The reference `docker` runtime runs it in a sidecar container of the attempt on the attempt's private network and exposes it to the harness over MCP's HTTP transport. The agent calls its tools but cannot read its environment. Only the namespace policy `allow_unenforced_agent_secrets` lifts it.
- **Enforced egress on `docker`.** The candidate container joins a network without a direct route out, and its traffic leaves through an egress proxy that allows only the listed domains.
- **Model hosts from configuration.** A harness adapter declares the hosts its deployment configuration needs (the model API or gateway base URL), and the runtime adds them to the allowlist. A graph lists only its domain hosts, and the resolved configuration shows the final list.
- **Unenforcing runtimes.** On `local` and `kora standalone`, an agent with secrets runs only with the explicit run option `allow_unenforced_secrets`, which is recorded on the run and shown in the console. The same rule applies in every deployment shape.

What MVP guarantees and what it does not:

| | guaranteed in MVP | not guaranteed in MVP |
|---|---|---|
| agent with `secret_env` | refused unless egress is enforced, or run with an explicit recorded option | that an allowed host is not an exfiltration channel |
| MCP-server secrets | absent from the agent's environment, files and processes, and the server's egress limited to its own allowlist, on runtimes declaring `isolates_tool_secrets` and `enforces_network_policy` | anything on runtimes without them (`local`) |
| model API key | redacted from logs, transcripts and results | absence from the agent's environment: the harness needs it until a credential proxy exists (DD-30) |
| redaction and secret scan | literal values and common key patterns | encoded, split or transformed values |
| rights of a secret | none: kora passes what the secrets provider holds | that a token is read-only; least privilege is the operator's configuration, and a secret handed to an agent's tools should be read-only unless the node's purpose needs more |

An ACL-enforced broker that issues scoped, short-lived credentials to an agent on request is deferred work, recorded in [proposal 0002](../proposals/0002-scoped-credential-broker.md). It adds nothing to MVP scope or acceptance.

## Alternatives considered

- **Trusting repository configuration by default, as the harnesses do.** Rejected (requirements decision 4): on a shared platform the repository is the agent's output, not the platform's configuration; instruction files fall under the same flag because they steer the agent as much as hooks do.
- **Relying on the harness sandbox alone.** Rejected: the `sandbox` field maps differently per harness and only warns on ACP, does not see MCP tool calls and does not know which paths are gates; it stays as a second layer.
- **Harness-native allowlists only.** Rejected by the [design review of 2026-10-15](../../knowledge/reviews/review-2026-10-15.md#central-tool-call-policy): no central decision point, no audit trail.
- **Approval requests as the decision point** (Codex `approval_policy = on-request` with `item/permissions/requestApproval`), the mechanism this record named until 2026-10-16. Replaced: the app-server raises approval requests only when the agent leaves its sandbox, never for a command or an edit inside `workspace-write`, `approval_policy = untrusted` is no longer supported, and `item/permissions/requestApproval` belongs to the `request_permissions` tool; the Codex `PreToolUse` hook covers the calls the policy names ([harness policy hooks](../../knowledge/research/harness-policy-hooks.md)).
- **One claim for all adapters** ("a deny reaches every tool call under every permission mode and adapter"). Replaced by declared coverage per adapter with fail-closed validation: a mechanism verified on one harness proves nothing about another.
- **A second clean checkout for gates.** Rejected by DD-34: digest verification against the base commit is sufficient and cheaper.
- **A separately hosted trusted evaluator**, which fixes the evaluator version, the measurement inputs, how the candidate is started and the channel the result returns through, outside the candidate's reach. Deferred after MVP on 2026-10-16: in the canonical scenario the measurement comes from the warehouse through an in-house command, not from the candidate, and the facts now say how far each gate was shielded.
- **Separate `allowed_tools`, `disallowed_tools` and `policy` fields in the IR.** Collapsed by the [same review](../../knowledge/reviews/review-2026-10-15.md#one-tool-policy-field) into one field.

## Consequences

- Agents do not see the repository's `CLAUDE.md` or `AGENTS.md` unless the node is trusted; authors put project instructions into the node configuration or obtain the namespace permission.
- Gate files must be declared; an undeclared gate file is editable by the agent.
- Digest verification runs at gate time, so an edit that slipped past the tool policy costs the attempt; after MVP, an ACP agent that cannot exclude project configuration is refused under the same fail-closed rule.
- Cedar and OPA evaluators can replace `allow_deny` as plugins without a change to the intermediate representation.
- A policy pattern on a call kind the harness cannot intercept is rejected at validation, except under `trust_repo_config: true`, where the repository's configuration can act around the policy (amended 2026-10-19); the coverage an adapter declares is verified against the harness's real interface before the adapter ships, and the Codex managed-hook flow through the app-server is confirmed with a real binary in the first vertical slice.
- On Codex every tool call spawns the hook process once; the cost is bounded by the session's `max_events`.
