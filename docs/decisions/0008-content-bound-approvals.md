# ADR-0008: Approvals bind to content — commit SHA plus ReviewBundle fact digests — and VCS approvals must come from a real reviewer

## Context

In the owner's model of an agentic pipeline there is one human touchpoint per target: the final change request. Everything before it happens without a person, so that touchpoint must be evidence-backed (requirements decision 7). The human-input node (FR-2.2) pauses the run and waits for a typed response through an approval channel; the built-in channels are the CLI/API and the change request on the version control system (VCS), with a web view in `kora web` (FR-7.2, FR-7.3).

The threat-model lens of the design review of 2026-10-15 (second cycle) raised two findings: an agent could write the evidence it is then judged on, and a change-request author, kora's own bot, or a plain merge could count as the approval. Together with requirements decision 10 (an approval must not silently cover a branch that moved after the reviewer looked), they shaped the decision.

## Decision

- **Binding to content, not to a URL.** An approval request records the exact commit SHA of the `VcsRef` under review and the digests of the `ReviewBundle.facts` it covers (`binds.vcs_ref` and `binds.gate_digests` in the node config; `bound_commit_sha` and `bound_digests` on the `approval_request` row). A response whose observed SHA or digests differ is refused with `API006` and the request stays `pending`; a push to the candidate branch during review invalidates the request and fails the node (amended 2026-10-16, below). Which fields of an artifact enter a digest is declared by its artifact type (`digest_fields`).
- **A push during review fails the node; nothing re-requests on old evidence** (amended 2026-10-16). An approval request covers one immutable revision: the commit, the digests of the facts and the bundle version, which names the input artifact versions and the gate results. A push to the candidate branch while the request is `pending` moves it to `invalidated` and fails the human-input node with error class `candidate_moved`, for every channel: the scheduler observes the branch head through the VCS protocol (`head_sha`), never through the channel. The author retries the producing agent node (a manual retry, with `fresh_with_feedback` to continue from the pushed commit), and the gates, the bundle and a new request are produced for the new commit through the normal downstream path; `candidate_moved` is never retryable, and a manual retry of the approval node itself is refused. A response that arrives after the push, a response and a push that race, and a replayed webhook all resolve against the request's recorded SHA and bundle version: a response to an invalidated request is recorded and ignored, and a webhook for a SHA already recorded is a no-op. Before the approved node's downstream starts, the scheduler checks once more that the approved SHA is still the branch head and fails the node with `candidate_moved` otherwise.
- **`ReviewBundle` is split into facts and narrative** (DD-33). `facts` are written by kora from its own records and are read-only to agents: every input artifact of the bundle node with type, digest and producing attempt; gate results from `CommandResult` rows with exit codes, the protected paths in force, the base commit and the result of the digest check, so that each gate shows as verified against its protected paths or unprotected (amended 2026-10-16, [ADR-0009](0009-target-repository-trust-boundary.md)); metrics, each number labelled with its provenance: measured by a command node, or reported by an agent session through domain MCP tools and skills (amended 2026-10-16, so that graphs which measure inside a session stay honest about it); the diff and commit references of the `VcsRef`; the run's attempt cost; and provenance per item (attempt, worker, image digest). The agent node writes only `narrative`: `summary` and `rationale`. The web view and the change-request comment render the two parts visibly apart.
- **Approval channels are a protocol** (`request`, read-only `lookup`, `poll`, `feedback`, `notify`, `cancel`) with capability flags `push_notifications`, `carries_identity` and `observes_head_sha`. A channel returns what it observed (payload, approver login and permission level, `is_author`, `is_bot`, timestamp, head SHA and digests) and never decides validity; the scheduler compares SHA and digests and applies the rules below.
- **VCS approval rules** (DD-35). An approval from the change-request channel counts only when the approver is not the change-request author, not kora's own bot identity (amended 2026-10-18 by [ADR-0023](0023-code-host-identity-and-purpose-scoped-credentials.md): both are compared by stable host principal, against the recorded publication principals and every automation principal kora has used for the binding) and, when the namespace policy sets `approver_allowlist`, on that list. "Merged" is a separate signal, accepted only when the channel configuration sets `accept_merged_as_approval` (default `false`). Approver login and permission level are recorded. Feedback comments fed into a `fresh_with_feedback` retry carry author and association, filtered to collaborators with write access by default (`feedback_from: collaborators_write`).
- **CLI/API approvals** require a personal token with the `approve` flag; the recorded approver is the token owner ([ADR-0011](0011-namespaces-and-personal-tokens.md)).
- **Cost next to the form.** kora itself attaches the run's aggregated estimated cost to every request; no agent computes it ([ADR-0010](0010-cost-accounting-and-limits.md)).

A VCS-bound request becoming `approved` keeps its original current wait open until a fresh post-approval head observation resolves the gate; approvals without a VCS binding require no head read. Old approved audit rows cannot authorize replacement waits. All external observations and channel effects run outside database transactions and locks. A nonpending request closes further channel interaction without changing its audit decision; uncertain late creation is reconciled on that original request. The exact transport and push-order limits are [ADR-0021](0021-external-observations-outside-transactions.md).

## Alternatives considered

- **Approving a node by name, without binding.** The approver would be saying yes to whatever the branch holds now; a push between review and response, or an upstream retry that regenerated the bundle, would pass unnoticed. Rejected: it breaks the single-touchpoint model.
- **Letting the agent author the whole bundle.** What the first design did, and simpler, but the agent under review would also author the gate results it is judged on. Rejected after the threat-model finding; facts now come from kora's own `CommandResult`, `artifact_version` and `usage_record` rows, and a number that an agent session reported is shown as agent-reported, never as measured.
- **Treating a merge as an approval by default.** A merge can be performed by the author or by automation. Kept only as an explicit opt-in per channel configuration.
- **Re-requesting with the new SHA on the same bundle.** The design until 2026-10-16. Rejected: it lets a reviewer approve commit B on evidence gathered for commit A, and keeping the bundle's SHA instead would leave the request unable to cover B at all.
- **Clearing downstream from the gate nodes on a push.** The push would be treated like an upstream retry and the gates re-run on the new commit automatically. Rejected on 2026-10-16: a push is an external event that no node produced, and clear-downstream would come to depend on the VCS channel; it stays the only invalidation mechanism for artifacts and is started only by a manual retry or a sub-graph attempt ([ADR-0007](0007-attempt-model-and-retries.md)).

## Consequences

- The approval record is an audit entry: approver identity, channel, permission level, timestamp, SHA and digests (FR-11.4); `run_cost` and the bound digests survive payload retention.
- Downstream invalidation ([ADR-0007](0007-attempt-model-and-retries.md)) moves pending requests to `invalidated` and notifies the channel, so an upstream retry can never be approved against stale evidence.
- A push during review ends the approval node with `candidate_moved`; the gates run again on the new commit through the retry of the producing node, never behind a re-request.
- The approval-channel conformance suite checks the round trip, a stale response reported with its observed SHA, and idempotent cancel and notify; chat and enterprise channels plug into the same protocol later (FR-7.4).
- `kora validate` enforces that `binds` paths resolve to a `VcsRef` and to digest-bearing artifacts (`IR005`).
- Platform teams gain settings per namespace and per graph: `approver_allowlist`, `accept_merged_as_approval`, `feedback_from`.
