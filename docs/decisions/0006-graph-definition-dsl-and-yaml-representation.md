## Context

kora orchestrates graphs whose nodes are whole coding-agent sessions. Graph authors are engineers used to Airflow-style Python; a platform team must review, diff and operate hundreds of graphs it did not write. The scheduler is shared by many teams, so it must never execute author code at run time (FR-1.2, FR-7.5), and the definition must stay portable to other SDKs and a UI editor (NFR-6.1). Archon, the primary contrast in the positioning document (requirements decision 13), has authors write YAML by hand.

## Decision

Graphs are authored in Python with decorators and the `>>` operator; `kora compile` lowers them to a YAML intermediate representation (IR), the only thing the scheduler consumes.

- **DSL surface.** `@graph` and `@subgraph` functions declare nodes through `node.*` constructors; keyword arguments carrying other nodes' outputs create data edges, `>>` and `<<` create control edges. Node inputs are keyword-only; a positional argument to a node is compile error `DSL003` (DD-24). The graph function runs once at compile time; no Python runs on the execution path. `@graph(repo=…)` is optional; a node left without any workspace source is `DSL003` (DD-26).
- **Compile step.** `kora compile` imports the module in the author's own process (compilation is client-side and never an API operation, [ADR-0002](0002-ai-first-api-and-thin-clients.md), amended 2026-10-16), resolves the global → graph → preset → node layers, validates with the validator the API uses and emits YAML in schema key order without timestamps; identical sources give byte-identical output (NFR-6.2), checked in CI. The document carries `ir_version` (format, semver) apart from `graph.version` (the author's), validates against the published JSON Schema [ir.schema.json](../../knowledge/specs/ir.schema.json), and separates topology (`graph`), policy (`runtime`) and secret references (`secrets`), with authoritative `type_contracts` for used built-in revisions and custom schemas/behavior, and compiler provenance under `meta` (ADR-0018). The deployment snapshots the resolved contract by value; informational provenance never supplies an execution input.
- **Trigger rules** are a closed enum of seven in IR v1: `all_success`, `all_done`, `one_success`, `one_failed`, `none_failed`, `all_skipped` and `none_failed_min_one_success`, the last borrowed from Archon so that a node after an all-skipped branch stays skipped (DD-1).
- **Branch targets have one owner in MVP.** Each named direct target has exactly one controlling branch in its graph/body scope. The DSL inserts an ordinary direct `depends_on` edge from that branch; semantic validation requires it in supplied IR and checks routing cycles through the ordinary DAG. A node may appear in several cases of the same branch, but two distinct owners are rejected. MVP also rejects `attempt_invariant: true` on every branch and every ordinary direct target named by any case or `else`. Other nodes retain ordinary invariant reuse. Each new body iteration therefore materialises its own route and direct targets instead of reusing a successful target that bypasses the new selection. `$fail_attempt` is an action, not a target node.
- **Branch selection is durable control state.** Publish the compact current selected-target set atomically with branch success. Every target readiness evaluation requires selection by its successful current owner, plus ordinary terminal-upstream, trigger and input checks. Unresolved owner means wait; skipped owner or exclusion means target skipped; failed/upstream-failed owner means target upstream_failed. Cancellation follows ordinary cancellation rules. Target-only clear and payload expiry preserve this decision; clearing the owner revokes it. Input independence cannot waive routing. Untargeted joins retain ordinary trigger semantics; skipping is not recursively applied to all descendants. The owner control edge counts in ordinary trigger aggregation.
- **Expressions are CEL** (Common Expression Language): branch conditions, retry predicates, `approve_when`, event `match` and sensor `until` (DD-3). The DSL takes CEL strings only. Evaluation goes through the Rust-backed `common-expression-language` binding, the `kora[cel]` extra; the binding has no checker and exposes no syntax tree, so kora has its own parser and schema-driven checker (`IR011`), and the CEL conformance suite runs in CI. Amended 2026-10-19 ([ir.md section 7](../../knowledge/specs/ir.md#7-expressions-and-templates)):
  - **Static limits** fixed in the execution semantics `kora.execution.v1`: 4,096 Unicode code points, syntax-tree depth 32, at most four comprehension macros nested at most two deep, and a worst-case cost estimate over bounded data that rejects expensive expressions (`IR027`). The binding compiles only kora's canonical rendering of the checked tree.
  - **Typed data.** Expressions read projections cut from validated payloads by the paths they use, converted to the schema's CEL types; a JSON number without a schema is a `double`.
  - **Initial provisional settings.** Before any deployment stores an estimate, the initial `kora.execution.v1` settings remain provisional. The initial limits are 4,096 canonical JSON bytes and 256 scalar/container values, selected by the [historical conversion collection](../../knowledge/research/cel-cost-calibration-2026-10-22.md#qualified-smaller-bound-result) and checked across referenced roots in both original and converted representations. This exception ends at the first stored estimate; later bound or cost-rule changes require a new execution semantics identity. It does not define a migration mechanism.
  - **Lightweight validation.** A golden corpus pins provisional estimates, and a compact regression checks ten fixed cases through the real evaluator, with one cold and three warm calls each, against an observed 100 ms target. The steps budget is 100,000,000,000,000 logical charge units; the existing weights, regex tables and 16 MiB logical-memory budget remain provisional. This replaces full coefficient fitting and crash-margin calibration as a pre-consumer gate. It establishes no interruption deadline, bound for every admitted expression or RSS envelope. Schema-driven checking/projections, correction of native minimum-int negation and real consumer integration remain required before author expressions execute.
  - **In-process evaluation.** It runs in the API and scheduler inside their transactions, with a per-transaction scheduler allowance of 100,000,000,000,000 logical charge units by default and never less than one expression's budget; no separate evaluator process. The allowance bounds logical work, not transaction duration. The GIL-holding native call cannot be interrupted, so an admitted expression can still stall or crash the shared process; an external supervisor's kill remains the hard limit.
  - **Error meaning per expression kind.**
    - A branch `when` or `reason` error fails the branch with `config_error`, and its direct targets become `upstream_failed`.
    - An `approve_when` error marks the request `failed` and fails the node with `config_error`.
    - A `retry.predicate` error means no retry, and the node keeps its original class.
    - A `match` or `until` error over external data is no match or "not yet".
- **Prompt templates are full Jinja2 in a sandbox** (DD-11): no filesystem loaders, imports or includes, no Python attribute access beyond the bound data; rendered once at attempt start and recorded on the attempt.
- **Fan-out body is always a sub-graph** (DD-9). The compiler wraps a single node; the `fan_out` node itself declares the collected `List[T]` outputs, so there is no fan-in node kind. A body is fed only through the node's `inputs`, with `over` naming the mapped one.
- **Trigger overlap** defaults to `allow` for every trigger kind except webhooks, which default to `queue` so that a burst of events does not start a burst of runs (FR-6.2, aligned on 2026-10-16); `skip` and `queue` are per-graph options in `graph.overlap` (DD-12). [ADR-0020](0020-execution-capacity-and-bounded-run-acceptance.md) makes starts bounded and canonical: `skip` considers accepted `pending` as well as `running` runs; `queue` promotion selects the oldest pending run under the graph scope lock when no run is running. Accepted delivery/skip replay precedes current-version validation and quota checks.
- **Presets live in two places** (DD-25): Python objects in graph code and registry presets published by the platform team. `kora presets pull` fetches the latter into `.kora/presets/` beforehand, so compile stays offline; both kinds are snapshotted under `meta.presets`, and the scheduler reads only each node's resolved `config`.

## Alternatives considered

- **YAML authored by hand**, as Archon does. Rejected: typed artifacts as Pydantic models, presets with merge rules and source locations in compile errors (NFR-10.3) come naturally from a language, and the YAML still exists as the committed, generated output.
- **A Python-only runtime graph with no intermediate document.** Rejected: author code would sit on the scheduler's execution path, portability would be lost, and "what will run" could not be diffed.
- **A restricted, expression-only template language** for prompts, proposed by the simplicity lens of the design review of 2026-10-15 (first cycle). Declined by the owner; the full Jinja2 sandbox was confirmed (DD-11).
- **A Python expression builder** for conditions. Dropped in the same review in favour of CEL strings that land in the IR unchanged.

## Consequences

- Three file classes stay distinct (NFR-6.4): human-authored Python and presets, generated and committed `build/*.ir.yaml` and `.kora/presets/*.json`, and secrets excluded from version control; the IR is never hand-edited.
- Compile and validate errors share one vocabulary of stable codes (`DSLnnn`, `IRnnn`) with locations, so an agent in the user's own coding session can fix graphs without parsing prose (FR-0.4).
- Every feature must be expressible in the IR first; the DSL is a client of it. The closed trigger-rule enum and the absence of a fan-in kind keep IR v1 small; adding either is a minor format bump.
- The CEL checker and the sandboxed Jinja2 renderer are the two places where author-provided text is interpreted, and kora code to maintain and unit-test. The CEL checker includes kora's own parser and cost estimate. Limits and logical estimates reduce exposure without proving API/scheduler responsiveness or a native crash margin. Binding pin changes repeat functional conformance, golden estimates, the compact regression, evaluator lifetime and applicable security checks; newly exposed workload gaps need an explicitly approved measurement method. Consumer fairness, transaction and large-scale integration measurements remain mandatory in their implementing issues.
- Components that evaluate CEL need the `kora[cel]` extra, installed only from binary wheels; `kora compile` does not.
