## Context

The data model stores runs, node instances, attempts and artifacts. Above a run it knows two identities: the delivery, `run.idempotency_key`, unique per graph, which keeps a replayed webhook from starting a second run (NFR-2.2), and the graph, through `graph.overlap`, which decides at trigger time whether a new run may start while another run of the same graph is `running` (FR-6.2, [ADR-0006](0006-graph-definition-dsl-and-yaml-representation.md)). The engineer who owns a target, a query to optimise, a dependency to upgrade, a flaky test, has no object that answers "what is the current state of this target and which change was accepted"; the pilot metrics in [positioning.md](../positioning.md) are per target (accepted useful changes per target, full cost per accepted change) and NFR-8.3 asks for cost per accepted change from stored data.

The canonical graph shows the gap. On day one a trigger for query Q starts a run; the run pushes a branch named after the run id, opens a change request and waits for review, then for rollout and a soak; `running` includes "all remaining nodes are waiting", so the run stays `running` for days. On day two a second, correct trigger for Q arrives: a different delivery, so idempotency does not apply. Under `overlap: allow` a second run opens a second change request for Q and nothing links the two runs; under `skip` the second trigger is dropped, which is right for Q by accident and wrong for a trigger for query R that is dropped with it; under `queue` both wait for days. After the merge nothing records that Q accepted that change in that run, and the next run for Q is unrelated to it. Before this decision both example graph documents set `overlap: skip`, and the canonical one also set `max_running_runs: 2`, which `skip` made unreachable.

The critique proposed, for MVP, an optional stable target key with namespace scope, a per-target concurrency policy with the vocabulary join, new revision, defer and alternative strategy, and a projection of the target's history over runs; no asset catalogue, no campaign framework, three keys kept apart (the delivery, the target, the attempt). The critique's survey of adjacent systems ([finding A14](../../knowledge/reviews/architecture-critique-2026-10-16.md#a14-target-identity)) shows the usefulness of the separation without prescribing kora's model. Issue #23 decided the minimal form below; the console design (roadmap step 2) builds its target page on it.

## Decision

**A run may carry a target key** (FR-6.11). `run.target_key` is an optional, stable, opaque string matching `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,255}$`, written to the run row only and never a template variable, with namespace scope: two graphs of one namespace that bind the same key work on the same target, and the key convention is the namespace's. The three keys stay apart: the delivery (`idempotency_key`), the target (`target_key`) and the execution (the attempt id).

**The key comes from the graph's declaration and binds once** (amended by [ADR-0019](0019-immutable-run-target-identity.md)). `graph.target.key` names a run parameter (`{ param: package }`), bound at creation from valid present `params`, or a field of one top-level node's output (`{ from: find_target, output: target, path: task_id }`), bound when the complete source result is successfully accepted. The declaration is validated (`IR020`, `DSL014`): the parameter, node, output and scalar path must resolve to a string. An absent optional parameter leaves the run unbound; an invalid present value is validation failure. The key never changes or clears after first binding, including after retry or hold release. Same-key rediscovery is accepted; a different valid key rejects the complete source result with non-retryable `config_error`, reason `target_identity_conflict`. All outputs of the declared source remain non-current until one atomic acceptance transaction checks authority, complete valid results and the key, promotes the results and completes the source. The first `run.target_bound` event identifies the parameter or exact accepted artifact/selector; equal-key confirmations emit no second initial-binding event. The trigger request gains no field.

**A run holds its target** from the first attempt admitted under its key. `run.target_held_since` clears only when the run leaves `running` and all blocking execution/publication recovery is settled ([ADR-0017](0017-execution-uncertainty-and-safe-replacement.md)). Cancellation, clear-downstream and lease expiry do not prove termination; a terminal run can retain its acquired hold. A manual retry retains an unresolved hold; after an ordinary settled release it takes the hold again at its next admission, behind any run that took the target meanwhile. No hold or key is invented for an unbound run. Binding acquires no hold; the immutable key survives every settled release. Different targets require different runs (ADR-0019).

**The policy is `graph.target.on_active`: `allow` or `defer`**, default `allow`. The admission pass gains a sixth limit scope after the global, namespace, graph, runtime and fan-out limits of [scheduler.md §6](../../knowledge/specs/scheduler.md): under `defer`, at most one holding run per `(namespace_id, target_key)`. A `ready` instance of a run that does not hold its target, while another run of the namespace holds the key, gets the ordinary `admission` wait row, FIFO by `node_instance.id`, and the event `run.target_deferred {target_key, held_by_run_id}` is written once per run and holder, for the first `admission` wait row the run receives behind that holder, not for every wait row the admission interval re-creates. The count and the hold are taken in one transaction under the target scope lock, so two scheduler replicas never admit two holders. A run with no key is never counted and never waits on this scope. `graph.overlap` keeps its meaning, its defaults and its place: it decides first, at trigger time, per graph; the target scope decides second, at admission, per key. A graph that declares `defer` sets `overlap: allow`, otherwise `skip` and `queue` act first.

**`defer` cancels nothing and closes nothing.** The holder's open change request stays open on the code host ([ADR-0007](0007-attempt-model-and-retries.md)); its pending approval request stays `pending` ([ADR-0008](0008-content-bound-approvals.md)); a deferred run is a row (NFR-1.3) that spends nothing and is cancelled like any run. Runs on other targets are never affected.

**The target's history is a read projection**, computed from existing rows at request time and writing nothing: `GET /namespaces/{ns}/targets` lists the keys of a namespace with the holding runs (one under `defer`, several under `allow`), the deferred runs, the open approval requests, the last `approved` request with its bound `VcsRef` and the last run's status and time; `active=true` keeps the keys with a holding or deferred run and `graph=` the keys bound by runs of that graph. `GET /namespaces/{ns}/targets/{key}`, the key percent-encoded in the path, returns the key's runs newest first with their status, hold, `rerun_of`, approval requests and cost totals. The projection names three facts apart and claims only the first: *accepted* is the latest `approved` request on the key and the `VcsRef` it binds; whether the change was *merged* is known only to a graph that waits for it (the `change_request_status` sensor) and is read from that run; whether the result was *verified* after rollout is a run-level artifact, and the projection links the run instead of claiming it. The first successful binding associates previously unbound run history once; subsequent retries cannot move it. Discovery, failed/rejected proposals and late usage remain attributed to that run and its fixed key. Compact binding origin survives payload expiry. There is no `target` table and no asset catalogue.

**Clients** ([ADR-0002](0002-ai-first-api-and-thin-clients.md)): `kora runs --target`, `kora targets`, `kora target <key>`; the `target` filter of `kora_runs` and one operating tool, `kora_targets`, the fourteenth of fifteen. The run view, the runs list and the approval list carry `target_key`.

**The format has not shipped**, so `graph.target` lands in `ir_version` 1.0, as `candidate_moved` did; the first minor bump waits for the first release (NFR-6.3).

## Alternatives considered

- **Rebinding after output replacement.** Superseded by ADR-0019: a preserved hold cannot authorize another key, and history must not move between keys. A new linked run provides separate attribution without identity epochs.

- **A label without a policy.** Rejected: two correct triggers for one target would still produce two competing change requests, and the critique's acceptance (`test_same_target_triggers_follow_declared_policy`) could not pass.
- **`supersede`**: a new run cancels the holder and takes its target. Deferred after MVP: it needs a decision on the holder's open change request, which ADR-0007 never closes, and a channel notification; it adds to this record without changing it.
- **`join`**: a trigger for a held target attaches to the holder. Deferred after MVP: `POST …/runs` would return a run the caller did not create, a change to the trigger contract, and a key bound from an output cannot join because the work was already spent.
- **A caller-supplied key in the trigger request.** Deferred after MVP: the graph's declaration covers both example graphs, and a supplied key would bypass the declared binding.
- **A `target` table with current pointers** (status, holding run, accepted run). Rejected: a second source of truth against the principles of [data-model.md §1](../../knowledge/specs/data-model.md) (the scheduler is a pure function from rows; append, do not overwrite), one more table a Temporal-backed backend would have to project, and the start of the asset catalogue the critique set aside.
- **A per-target `overlap`.** Rejected: `overlap` decides at trigger time on a run status that includes days of waiting, and `skip` would still drop triggers for unrelated targets; a scope in the admission pass decides per key, reuses the `admission` wait row and never touches `overlap`.
- **A stable mapping key inside a fan-out.** Deferred after MVP: fan-out identity stays positional ([ADR-0006](0006-graph-definition-dsl-and-yaml-representation.md)); the reordered-list clause of the critique's acceptance test is dropped.
- **Deferring target identity after MVP.** Rejected: the pilot metrics are per target and would need a manual join of runs, and the console's target page would have no footing.

## Consequences

- A graph without `graph.target` behaves exactly as before; `allow` is the default, and `graph.overlap` keeps DD-12's semantics.
- A deferred run is `running` (its instance waits on an `admission` row), so it counts toward `runtime.concurrency.max_running_runs`: in the canonical example a holder and a deferred run fill its two slots, and a run on another target then waits on the graph scope, not on the target scope.
- A `failed` holder with settled execution and publication releases its target, so a failed run with an open change request lets a deferred run proceed and the projection may show two requests for one key with their status; unresolved execution retains the hold even after cancellation until closure is established (ADR-0017).
- A key bound from an output costs the producing node before `defer` can act; a graph that wants a free wait binds from a parameter. Pre-binding work and a wrapper body are not retroactively target-gated, and scheduler-only approval paths need not acquire a runtime hold. ADR-0019 prevents rejected exported results from becoming current, not prior external effects or false business-target declarations. A rerun rediscovers independently and does not guarantee the rejected target will be selected.
- Two graphs of one namespace can collide on a key by coincidence and defer each other; the key convention is the namespace's. Scoping the policy per graph is one sentence in [scheduler.md §6](../../knowledge/specs/scheduler.md) if the pilot shows the collision.
- The MCP operating server has fourteen tools of fifteen; the console design decides whether its attention listing is the last tool or an option of `kora_runs`.
- The console design builds the target page on the projection and the attention queue on the events of this record.
