## Context

kora runs graphs whose nodes are whole coding-agent sessions, and the requirements ask for a control plane from day one: scheduler, metadata database, HTTP API, workers (FR-6.1). Writing a scheduler is expensive, and mature engines already provide retries, durable waits, cron and human-in-the-loop steps. The main alternative was "an existing engine plus a session adapter": one coding session as one Temporal activity, Kestra task or Airflow task, with the engine owning retries, waits and approvals. The positioning document recorded this as the hypothesis "own scheduler is necessary" and required a test before scope freeze (requirements decision 6).

The test was a desk analysis of Temporal, Kestra and Airflow against kora's requirements, modelling kora as a thin adapter on each ([verdict](../../knowledge/analysis/own-scheduler-vs-existing-engine/verdict.md)); no prototype was built. The reviewed thin-adapter models for Kestra and Airflow fail the test: both record task-run attempts, but those records do not provide kora's `previous_attempt` artifact inputs and lineage; content-bound approval requires kora-owned validation and authority beyond their task-instance pause/resume operations; neither has a production standalone mode; Airflow's scheduler reads a serialised DAG that a DAG processor parses from Python files, so a YAML graph would have to be lowered into generated Python rather than being what runs, and Kestra's plugins are Java only. Temporal is viable: it provides durable scheduling primitives and its Update validators can express content-bound approvals, but its activities are at-least-once, so a lost completion re-runs the activity and submission to a runtime still needs kora's durable idempotency key and authoritative lookup; it also forces a mandatory deployment with no single-process mode, a second source of truth beside kora's database and a determinism discipline on kora's interpreter. Every engine leaves the same engine-neutral work: DSL and IR, artifact model with lineage, harness adapters, protocols, cost ledger. The hypothesis was partly confirmed: an own scheduler is not strictly necessary, but no engine removes kora's state model.

## First-slice amendment of 2026-10-23

The first slice accepts exactly one sequential agent → command gate → human-input approval chain, with a manual start and the local runtime. Acceptance exercises the same topology independently with both Claude and Codex. Wider or parallel graphs are refused for execution; the IR schema and CEL checker still represent and check the complete language and all its examples. [The first-slice matrix](../../knowledge/specs/first-slice.md) is the canonical capability/refusal and test-activation contract.

The shared installation-aware validator refuses unsupported fields before side effects with `IR028` and their original YAML path, identically for validate and deploy. The installed capability inventory is trusted configuration, never author input. Syntax/type errors and more specific security errors retain their existing codes. Startup/default validation and trigger/admission/dispatch compatibility checks prevent omitted defaults or later installation changes from activating unsupported behavior; saved execution contracts and recovery obligations remain binding.

Refused execution includes branch, fan-out, subgraph, wait-event and timer nodes; nonmanual triggers; `graph.target`; nonempty `graph.subgraphs`; retry `max_attempts > 1`; all automatic infrastructure/provider retries and provider pauses; manual retry/rerun; `runtime.limits.budget_usd`, node/subgraph `limits.budget_usd`, `runtime.budget_headroom_pct` and namespace `daily_budget_usd`; nonempty node `skills`, `subagents`, `hooks` or `mcp_servers`; and `trust_repo_config: true`. This applies to resolved defaults and provider/standalone configuration as well as submitted IR. Exact no-op values are listed in the matrix; budget zero is not omission. No automatic failure creates another attempt. Lease expiry remains uncertainty; adoption of the same live attempt and bounded transport retries remain required. Only proved loss after closure fails the node.

Usage records, completeness and approval `run_cost` remain required despite budget refusal. Missing prices, unknown usage and subscription billing never become a fabricated zero; #142 owns those contracts. Supported namespace tool policy, protected paths, secret-prefix checks, effective-policy history and admission limits remain required. Trusted startup provisioning obeys the normal policy revision and lock rules while public namespace-management routes are deferred. Unsupported security controls are errors, with the sole existing local agent-secret exception of ADR-0009 requiring both the explicit namespace permission at deploy and the separate explicit option on each start; neither defaults true.

Finite retention and abandoned-upload cleanup, `kora doctor`, provider listing/conformance commands and an isolated built-and-installed external provider fixture are required before readiness. Implementation owners are [#216](https://github.com/realkarych/kora/issues/216), [#214](https://github.com/realkarych/kora/issues/214) and [#215](https://github.com/realkarych/kora/issues/215). Immutable history and unresolved recovery remain retained. Graph-version retirement, attempt diff, S3, external exporters, product console journeys, DSL/scenarios/dry-run, product harness skills, remote code-host/credential issuance and the other matrix rows activate with their named implementations; existing executable gates remain active.

Local bare Git publication is explicitly credential-free only under a saved trusted binding, and retains late authorization, a stable `local_service` principal, digest/destination matching, closure and durable provenance (ADR-0023). It creates no change request. The included API operations have complete CLI/MCP coverage: ten stdio tools, including a distinct compiled-IR `kora_validate`. The complete future inventory becomes sixteen under ADR-0002. Probe exclusions apply to exactly `GET /healthz`, `GET /readyz` and `GET /metrics`, with no authentication exemption.

Every affected test keeps its required legs; only legs needing an excluded feature wait for that feature's implementation. [The named test matrix](../../knowledge/specs/first-slice.md#required-and-pending-test-cases) and implementation plan record these splits. Both real harness policy/launcher gates, local publication/recovery checks and resource-lifetime methods remain first-slice obligations. This amendment defines scope, not implemented runtime behavior.

## Decision

kora keeps its own control plane for the MVP (requirements decision 12): a scheduler that is a stateless loop over the metadata database, an HTTP API, and workers per runtime (ADR-0003).

The run-state model is designed so that a Temporal-backed execution backend stays possible (NFR-5.5). "Run state as interpretable data with explicit attempts" means:

- Every `run`, `node_instance`, `attempt` and `wait` row is plain JSON-compatible data: no pickled objects, no callables. The scheduler is a pure function from rows to actions and keeps no in-memory state between passes (NFR-1.2).
- Each runtime submission is an explicit `attempt` row with its own status, lease, counters, artifact versions and usage records (ADR-0007), the object no engine owns.
- Timers, approvals, event subscriptions, polls, retry back-off and admission back-pressure are `wait` rows with a `wake_at` or a subscription; nothing holds a worker.
- The backend boundary is prose. Only the shared transition functions move the four execution tables between states. The API calls them for the requests it receives: starts, direct approval responses, cancellation, manual retry, reconciliation requests and worker reports, and deadline expiry it observes while handling them. A namespace policy write is a scope-only engine write that changes no run. The scheduler calls them for its passes, its own starts, the results it observes itself (channel and sensor observations, head reads, push handling and event matching), and deadline and lease-expiry recovery. The entry points are start a run, deliver a signal (approval response, inbound event, cancel, manual retry, reconciliation, worker report) and tick. The design review of 2026-10-15 ([record](../../knowledge/reviews/review-2026-10-15.md)) found that an `ExecutionBackend` Python interface with one implementation adds nothing, so none exists (DD-7).

Amendment of 2026-10-19 ([issue #103](https://github.com/realkarych/kora/issues/103)). The earlier wording said that the scheduling passes are the only code that moves the four tables. The specifications already have the API apply worker reports, manual retry and canonical start itself, and the scheduler apply transitions that are not passes. The bullet above records the actual assignment, with one set of shared transition functions in `kora.engine` ([ADR-0026](0026-package-layers.md)) and the caller table of [scheduler.md section 12](../../knowledge/specs/scheduler.md#12-execution-backend-boundary-nfr-55). A different backend replaces the callers, not the rows. The API contract is backend-neutral: the API validates a signal and applies it durably before it responds; for an inbound event the durable application is persisting it, and matching it to waits stays with the scheduler. A Temporal-backed backend would therefore need a synchronous, validated Update whose result is projected into kora's tables before the response, not an asynchronous Signal.

The Temporal backend is prototyped after MVP, by demand (DD-7). A generic interpreter workflow would then replace the scheduler's passes behind the same synchronous signal entry point and project its transitions into the same four tables, while artifacts, lineage, approval requests, usage records, session segments, events and the registry stay in kora's database, written through the same code as today: `approval_request` and `artifact_version` writes are `kora.engine` functions like those of the four execution tables, and `kora.db` holds the table definitions and read functions; readers always read kora's tables. Two rules keep the door open: no table stores backend-specific handles except `attempt.handle` and `attempt.lease_*`, and the scheduler never relies on in-memory state.

Kestra and Airflow become integration targets only: they start kora runs through the webhook trigger, and a kora command node can call their APIs. A dedicated Airflow operator or Kestra task can follow after MVP.

## Alternatives considered

- **Temporal as the core from the start.** Rejected for MVP: a mandatory cluster or Temporal Cloud bill, no standalone mode (NFR-7.1, NFR-0.1), run state split across two stores. Kept as an alternative backend; the later DBOS assessment remains subject to the scheduler-prototype gate.
- **Kestra or Airflow as the core.** Rejected for MVP: the reviewed thin-adapter models still require kora-owned attempt lineage, content-bound approval authority and IR lowering; the result is an orchestrator inside an orchestrator, not elimination of that work.
- **DBOS as an embedded durability library.** Not in the original analysis; assessed on 2026-10-16 ([DBOS evidence](../../knowledge/analysis/own-scheduler-vs-existing-engine/verdict.md#dbos)). Not adopted before the scheduler-prototype milestone; re-evaluated with that milestone's data.
- **A coded `ExecutionBackend` interface now.** Rejected as an abstraction with one implementation.
- **Worker reports and retries as recorded intents that a pass applies** (considered 2026-10-19, issue #103). Rejected: the API must answer them synchronously, with refusals and results, and the specifications already apply them in the request.

## Consequences

- kora owns scheduling, leases, adoption after crash, stall detection and scale, responsibilities an alternative engine could share, with adapter and operational costs still to prove.
- Standalone mode on SQLite keeps the same schema and queries as PostgreSQL (NFR-0.1).
- A future backend inherits the data model unchanged. The API's synchronous contract stays the same whichever backend performs transitions; the backend must offer a synchronous, validated entry point for signals.
