# ADR-0007: Explicit attempts with lineage, sub-graph iteration semantics, at-most-once submission and retention

- Status: accepted, 2026-10-15; amended 2026-10-16 (result authority revoked by clear-downstream; [architecture critique of 2026-10-16, finding A06](../../knowledge/reviews/architecture-critique-2026-10-16.md#a06-result-authority), issue #13); amended 2026-10-16 (publication is idempotent on natural keys; [architecture critique of 2026-10-16, finding A08](../../knowledge/reviews/architecture-critique-2026-10-16.md#a08-durable-intent), issue #21); amended 2026-10-16 (a run's graph version is immutable and running again is a new linked run; [finding A09](../../knowledge/reviews/architecture-critique-2026-10-16.md#a09-graph-version-retry), issue #18); amended 2026-10-16 (the `local` and `docker` runtimes declare `supports_resume = False` and `fresh_with_feedback` is the strategy that works on every runtime; [finding A10](../../knowledge/reviews/architecture-critique-2026-10-16.md#a10-session-checkpoint), issue #19)

## Context

A coding-agent session is non-deterministic and expensive. A run that retries a node or re-iterates a sub-graph produces several candidates for the same output, each with its own cost, transcript and branch. The canonical graph loops (implement, measure, check equivalence, review) and a rejected attempt must pass its comments and branch to the next one; the graph stays acyclic, so a loop is a retry with memory.

The desk analysis of existing engines found that they record attempts but none makes a previous attempt addressable as an input with its own artifacts and lineage (ADR-0001). Session side effects are not transactional, and a crash between submit and handle persistence must not start a second session (NFR-2.1). The design review of 2026-10-15 ([record](../../knowledge/reviews/review-2026-10-15.md)) simplified the first drafts: "attempt" no longer also means a sub-graph iteration, a transactional clear-downstream replaces generation counters and a dirty set, and retention leaves the scheduling loop.

## Decision

**Every execution is an attempt row.** An `attempt` is exactly one runtime submission and the unit of cost. It records status, handle, lease, counters, `strategy` and `strategy_fallback`, and snapshots `price_table_id`, `image_digest` and `harness_version`. `artifact_lineage` rows link its `artifact_version` outputs to the versions the node instance consumed when it became ready (`consumed`, `reused_invariant`, `previous_attempt`). Earlier versions become `superseded`; scheduling never deletes them.

**Retry strategies** (FR-6.4): `fresh` (new workspace from the declared revision), `resume` (the previous attempt's session handle; needs the runtime capability `supports_resume`) and `fresh_with_feedback` (new workspace from the previous attempt's `VcsRef`, plus a `Feedback` DTO with the review comments, author and association). `fresh_with_feedback` is the documented default after reviewer rejection (requirements decision 2) because it works on every runtime; `resume` falls back to it (recording `strategy_fallback`) when the handle is gone or the installed harness version changed. In MVP the `local` and `docker` runtimes declare `supports_resume = False` (amended 2026-10-16): `release` frees the workspace that holds the harness checkpoint and their handles are bound to one host, so no later attempt can reach the previous session, and a `resume` retry on them always falls back with `strategy_fallback` recorded and visible on the attempt. `fresh_with_feedback` is therefore the only strategy that continues a previous attempt's work on every runtime: the published `VcsRef` and the `Feedback` are what is preserved. A runtime declares `supports_resume` only when its harness checkpoint outlives `release` and is readable from wherever the next attempt runs.

**Sub-graph iteration** (FR-2.7a, requirements decision 8). A sub-graph attempt is the integer `subgraph_attempt` on node instances, never an `attempt` row. A body node ends the iteration through a branch to `$fail_attempt`; the instance fails with class `attempt_failed`. Iteration N+1 re-materialises the body and receives `$previous_attempt`, a `PreviousAttempt` artifact `{subgraph_attempt, reason, error_class, artifacts}` stored as an ordinary artifact version; a node gets it only by declaring an input `from: $previous_attempt`. Nodes marked `attempt_invariant` are not re-run. The sub-graph's `max_attempts`, timeout and budget span all iterations.

**Side effects are never rolled back** (requirements decisions 3 and 9, FR-6.1b). kora never deletes or closes branches or change requests created by failed attempts; cleanup is the author's job, for example through a command node. Submission is at most once: the attempt row is committed before `runtime.submit`, the submission is keyed by the attempt id (runtimes dedupe on it) and `lookup(attempt_id)` recovers a handle after a crash.

**Publication is idempotent on a prepared result and natural keys** (amended 2026-10-17 by [ADR-0016](0016-trusted-execution-and-publication.md)). Before late authorization, the runtime durably records the sealed input, exact prepared revision and trusted deterministic destination. Repeated `finalize` serializes on that operation and reconciles the same revision: equal remote revision is success, authoritative absence permits the same push, and unexpected remote content fails without overwrite. Recovery never repeats collection against a mutable workspace or creates another commit. `open_change_request` remains idempotent on `(head, base)` by search before create. The persisted attempt and runtime phase checkpoint are the durable intent without a database outbox. Lost sealed/prepared state is infrastructure failure; an existing branch stays discoverable and is never adopted by another attempt. A lease change does not settle an earlier external request. ADR-0017 requires every prior dispatcher and unresolved platform publication to be closed before replacement or new platform writes; runtime retirement fences delayed starts and retains evidence beyond release. The future conformance contracts cover response loss and concurrent repetitions.

**Clear downstream** (requirements decision 10, FR-6.8a). Only a manual retry and the start of sub-graph attempt N+1 invalidate downstream results, in one transaction under the run lock: the downstream closure through `consumed_versions` and `depends_on` (minus consumers listing the input in `independent_of`) returns to `pending` with its `current_attempt_id` cleared, its `current` versions become `superseded`, open waits are cancelled, pending approval requests become `invalidated`, non-terminal attempts get `desired_state = cancel`. Readiness is then an ordinary query, but ADR-0017 blocks all new runtime admissions in the run until old execution and publication recovery is settled; cancellation does not release those reservations. The same commit revokes the cancelled attempts' result authority: an upload or a `finishing` transition is accepted as current only from an attempt with `desired_state = run` that is still its instance's current attempt, so a write that lands between the commit and the attempt's next heartbeat is stored as historical; usage records and segments are accepted regardless, so no cost is lost. The lease epoch fences a previous lease holder, not the attempt's own late writes.

**A run's graph version is immutable; running again is a new run** (amended 2026-10-16, FR-1.7). `run.graph_version_id` is set when the run is created and never changes; a manual retry is the clear-downstream transaction inside that version, so a graph version that adds a required node, removes one or changes an artifact type never meets an existing run. Running an existing run again is a **rerun**: `POST …/runs/{run}/rerun` creates a new run of the same graph with `rerun_of_run_id` pointing at the original, on the pinned version by default or on the latest or a named one, with the original's parameters unless overridden. A linked rerun is refused with `API002` while the original has any replacement-blocking condition (ADR-0017). The rerun consumes none of the original's artifact versions and leaves the original untouched; the parameters are the only thing that passes between the two runs. The configuration any attempt ran with is reconstructible from the pinned document, the preset snapshot under `meta.presets`, the run parameters and the consumed artifact versions, and `resolved_config_digest` verifies the reconstruction. In the clients a rerun is `kora rerun` and the `rerun_of` option of `kora_trigger`.

**Retention** (DD-4). A graph-level setting with a namespace default: run, node instance, attempt, event and usage records forever; session transcripts and segments 30 days after the run finished; artifact payloads 30 days (both lowered from 90 and 180 days on 2026-10-16); reference-only artifacts such as `VcsRef` forever. Only payloads are deleted; rows keep digest, lineage and `payload_state = expired`. Deletion is a separate low-priority batched task: candidates are marked `expiring`, a blob is deleted only when no other `present` or `expiring` version references its `storage_ref`, then rows become `expired`.

## Alternatives considered

- **Attempt as iteration too.** Rejected: one word, one meaning.
- **`resume` as the default after rejection.** Rejected: it depends on a runtime capability and a surviving handle.
- **Keeping the workspace and container alive until the retry decision so that `resume` works on the reference runtimes.** Rejected ([finding A10](../../knowledge/reviews/architecture-critique-2026-10-16.md#a10-session-checkpoint)): it holds a workspace and a container per failed attempt through back-off and approval waits, binds the next attempt to that host, and a worker loss still destroys the checkpoint.
- **Cleaning up branches of failed attempts.** Rejected: session side effects are not transactional, and failed attempts are evidence.
- **Generation counters and a dirty set.** Rejected for the transactional clear-downstream.
- **Retention inside the scheduling loop.** Rejected: it deleted shared blobs.
- **An outbox or operation log for publications.** Rejected on 2026-10-16: the code host identifies branches and change requests by their natural keys. ADR-0016 additionally requires a durable runtime checkpoint for the immutable prepared result; no separate metadata-database outbox is introduced. Conformance cases are future implementation gates, not tests already run.
- **Re-pinning a running run to a newer graph version** (a boolean on the retry route, the design until 2026-10-16). Rejected ([finding A09](../../knowledge/reviews/architecture-critique-2026-10-16.md#a09-graph-version-retry)): nobody materialised the nodes the new version added, so a retry could bypass a gate added in it; removed and renamed nodes and artifacts produced under the old schema had no defined reading under the new one; and the run's history mixed two definitions. In-place migration needs the admissible topology changes, remapping rules, an immutable execution definition per attempt, schema compatibility and atomic invalidation defined first, and it does not return as a retry flag.

## Consequences

- Cost per accepted change, failed attempts and fan-out losers included, is derivable offline from `artifact_lineage` and `usage_record` (NFR-8.3).
- Authors must plan VCS cleanup explicitly.
- "Attempt" and "sub-graph attempt" stay distinct terms everywhere.
- Comparing a run with its rerun compares two runs linked through `rerun_of_run_id`, never two definitions inside one run; the attempt diff compares attempts of one node within one graph version.
- On the MVP runtimes `strategy: resume` is never honoured: validation warns `IR009` and every retry records `strategy_fallback`. Resuming across `release` needs the harness checkpoint exported before release as an artifact version with its own retention and the compatible harness version recorded, readable by the worker that runs the next attempt; that is the post-MVP design, not an MVP promise.
