## Context

A run of a kora graph can hold many agent sessions, retries and fan-out losers, each consuming model tokens on an organisation's account. The platform team needs to know what a run cost, stop runaway spend, and later derive cost per accepted change (NFR-8.3). The harnesses make this hard: Claude Code reports per-model usage with a cost basis on its final result; Codex reports usage separately from turn completion, and a killed turn can leave an unreported interval; a subscription session has no USD price at all. Prices and gateway contracts differ per organisation and change over time. The production-readiness lens of the design review of 2026-10-15 (first cycle) found no spend guard above the per-run budget and no way to attribute a mid-run price change to the attempts it affected.

## Decision

- **Unit of record: tokens per model per attempt.** One `usage_record` per `(attempt, model)` with `input_tokens`, `cached_input_tokens`, `cache_creation_tokens`, `output_tokens` and `reasoning_tokens`, normalized from harness observations (Claude Code per-call stream and final per-model results, Codex app-server token-usage notifications). Input is uncached, cache reads and writes are separate, and output includes reasoning. Presence metadata distinguishes unknown dimensions from zero. Each record carries `completeness`: complete only with usable final evidence and no retained gap, partial for known interrupted observations, unavailable without usable usage. Attempt-level coverage also represents absent reports and attribution/observation gaps without inventing a model row. For `resume` retries the record stores the delta of whole-session totals (`delta_of_session_totals`). Run and node totals are sums over rows, never stored, and carry the weakest completeness of their parts.
- **Price table as a pluggable source.** The API process imports trusted default or namespace revisions through the engine. The engine pins an immutable multi-model revision atomically at attempt creation; a namespace revision replaces the whole default map, including missing models. Claim, saved request and checkpoint carry the same id and values to the runner, which needs no price service. The API invokes the engine to derive `usd_estimate` at acceptance: validated normalized per-model harness amounts for `harness_list` or `harness_managed`, otherwise the pinned table for `price_table` or `gateway`. Rates are total prices; output reasoning and cache input are never charged twice. Equal-rate buckets can be combined when their split is unknown; otherwise required missing data leaves USD null. The exact decimal arithmetic, transport and bounds are in [data-model section 7](../../knowledge/specs/data-model.md#7-usage-records-and-completeness-fr-91). Cross-grant token/completeness evidence cannot regress; one supported interim-table to final-harness correction may lower the estimate without changing billing class or earlier approvals. Every record carries `billing_class` (`api_key`, `subscription`, `gateway`, `managed`); subscription USD remains null even when the harness supplies a numeric list amount. All USD figures are estimates with their basis, completeness and source-observation time.
- **USD limits are soft.** `budget_usd` exists at agent node, sub-graph and run level. The agent node's budget is enforced by the session runner inside the runtime from streamed usage: it tolerates the overshoot in `runtime.budget_headroom_pct`, then terminates the session (interrupt, 30 s grace, kill) with error class `budget_exhausted`. Native budgets are set in addition where they exist (Claude Code `max_budget_usd`). The sub-graph and run budgets are enforced by the scheduler, because no single session can see the others: it sums the usage records of finished attempts and the live counters of running ones per scope and admits no further attempt in a scope over its budget plus headroom; a ready node in that scope fails with the same error class, while running attempts finish and keep their outputs, the rule the daily namespace budget already follows. Sub-graph budgets span all sub-graph attempts.
- **Hard limits are only timeouts and event counts.** `timeout` at node, sub-graph and run level uses the earliest inherited immutable deadline, enforced by the runtime/common executor through preparation, execution and publication even when the control plane is unreachable (ADR-0022). Interruption and forced-stop escalation have nominal thresholds at that deadline and 30 seconds later; scheduling/termination latency and already-authorized remote effects are not a hard-real-time bound. The scheduler/API own durable timeout and result authority; time alone never releases reservations; `max_events` counts turns, tool calls and tool results in the SDK event stream and is enforced by the session runner (`events_exhausted`); `stall_after` is likewise hard. None depends on price data or harness-reported usage.
- **Daily soft cost limit per namespace** (DD-31). One policy field, `daily_budget_usd`. When the namespace's estimated spend for the current day (sum of `usage_record.usd_estimate` over attempts started that day, in the namespace's timezone) exceeds it, the admission pass admits no new attempts and running ones finish. The state is exposed in `/metrics` (`kora_namespace_daily_spend_usd`, `kora_namespace_budget_blocked`) and on `GET /namespaces/{ns}/cost/daily`.
- **Cost on approval requests** is a write-once snapshot of persisted usage from every attempt of the run, including failed, superseded and fan-out attempts, saved atomically with the request under the run lock. No live-counter substitution, current-price lookup, lineage walk or agent calculation participates. Missing reports, unknown prices and subscription usage retain explicit nulls, known subtotals and coverage; only a genuinely empty cost-producing ledger is known zero. Every approval surface and channel forwards the same saved value next to the form. Late reports and delivery retries never rewrite it. If the bounded snapshot cannot represent the aggregate, the approval node fails `config_error` with `approval_cost_too_large`, creates no request and preserves the ledger; it never truncates the sum or kills running agents.

These ownership and arithmetic changes are forward contracts. [Issue #213](https://github.com/realkarych/kora/issues/213) owns shared models and the migration from the existing database shape; engine, runner and adapter behavior remains pending their implementing work items. [Issue #140](https://github.com/realkarych/kora/issues/140) owns budget activation and unsupported-configuration refusal. Usage and approval cost remain required in the first slice; no hard USD limit is introduced.

## Alternatives considered

- **Hard USD kill switches.** Rejected: a USD figure is an estimate that depends on a price table, a billing class and a harness that may report nothing for a killed turn; a hard stop would turn accounting gaps into failed runs.
- **No cost accounting, relying on vendor dashboards.** Rejected: dashboards cannot attribute spend to a run, node, attempt or fan-out instance, and cannot feed an admission decision or an approval request. Reconciliation against vendor usage APIs is post-MVP (FR-9.6).
- **A fixed built-in price table.** Rejected: list prices change and organisations pay contract or gateway prices; the shipped table is only the default.
- **Walking artifact lineage for the cost shown on an approval.** Dropped as a special case by the simplicity lens of the design review of 2026-10-15 (first cycle); the plain run sum replaced it.

## Consequences

- Cost per accepted change, including failed attempts, retries and fan-out losers, is derivable offline from `artifact_lineage` and `usage_record` (NFR-8.3); usage records are retained forever by default.
- Run and node views (CLI, API, the `kora_cost` MCP tool) show tokens, estimated cost and completeness per attempt; fan-out views aggregate across instances (FR-9.5).
- A session can overshoot a soft budget by the headroom plus whatever the harness spends before the stream reports it; with healthy reporting a run or sub-graph can overshoot by that amount per running session plus one heartbeat interval. During a partition, reporting staleness is unbounded and displayed spend is last-known/partial with its observation time (ADR-0017); the documentation must say so (NFR-8.2).
- The cost formula and the limit arithmetic are among the few places where unit tests are warranted in this project.
