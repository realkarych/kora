# Installed execution selection provenance

The project owner approved this specification architecture under [#1640](https://github.com/realkarych/kora/issues/1640#issuecomment-7082305733) at [SHA-256 `a0e7d6373cae86a2495f87902eb532a4924346a9ac5f3b69e8ace6bed5327383`](https://github.com/realkarych/kora/issues/1640#issuecomment-7082135036). [#1774](https://github.com/realkarych/kora/issues/1774) records the contract. Implementation and activation are separate. The first consumer is the [authenticated execution-request upload](execution-request.md#4-original-handoff-and-recovery).

The [original first-Claim basis](data-model.md#original-first-claim-basis), [original metadata Writer](execution-custody-native.md#3-original-metadata-commit-protocol) and [physical qualification](execution-custody-native.md#6-qualification-method-and-activation-evidence) retain their existing contracts. [ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md) governs Worker access to the control plane. [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md) governs the cooperative local trust boundary.

## Ownership, keys and lifetime

The existing ordinary SQLite API composition owns the catalog in its metadata database. An operator-provisioned release installs entries through a private administrative path while affected processes are drained. Application callers get typed reads. Worker registration, Claim, upload and replay cannot provision or update catalog rows. The first slice admits one explicitly provisioned execution domain, one current generation and one live verified Worker binding for one credential-free local command and local Git configuration. Ordinary Worker operations retain their existing scope.

| Logical relation | Natural key and immutable data |
| --- | --- |
| Provider selection revision | `(role, selection_id, selection_revision)`, where role is runtime, vcs or harness, ID is a canonical configured ULID and revision is positive signed-64. The row binds exactly one execution domain, approved provider name and implementation version, canonical behavior descriptor and its SHA-256. The owner assigns the ID once to one role/domain configuration lineage. For that lineage, a behavior change strictly increases the revision, including when restoring previously used provider bytes. A retired key remains resolvable and is never rebound or reactivated for a new selection. |
| Renderer behavior | Raw 32-byte domain-separated SHA-256 of the canonical renderer descriptor defined below. Use a single immutable descriptor for each digest. A different descriptor under an existing digest refuses provisioning. |
| Current installation selection | One row keyed by the configured execution domain ULID. It binds the trusted native host and the anchored state-root directory identity (device, inode and owner UID), a positive non-reused signed-64 generation, the exact role revision keys and the renderer digest. Runtime and VCS are present. Harness may be absent for a command-only installation. The operator changes this row only in a drained cutover. One transaction inserts any new immutable descriptors and switches the full generation together. |
| Verified Worker launch | `(worker_id, incarnation_id)`, the existing retained dispatcher selectors. Immutable token ID, execution domain and catalog generation, the original native SQLite metadata installation as observed by the trusted launch owner, plus the trusted native Worker process identity (host, boot, PID and checked start identity, including platform namespace evidence as applicable). Only the trusted launch owner may append a binding after observing the original process. Neither registering an incarnation nor replaying a Claim creates or changes this row. Replacement uses a new incarnation and cannot inherit the old binding. |

An identical provisioning retry has no new effect. Generation changes compare the exact previous generation, advance once and refuse overflow. Restore retains historical identities under the existing compatible-backup rules. The surviving launch owner must independently match the API's actual anchored original SQLite main file, domain and live process. A copied or replaced database, or loss of that owner, supplies no continuation of original launch proof. Match the actual acquired native SQLite main file for Claim, comparison and ready. A pathname stat or schema stamp alone cannot prove that identity. A restored installation needs fresh trusted binding and ordinary original-grant authority for new effects. Historical keys are never repointed. The first delivery keeps all admitted history, including inactive entries, with no online pruning or recycling. Database-total catalog ceilings are 256 provider descriptors and 64 renderer descriptors, each at most 16 KiB of canonical data, plus 256 trusted launch records with at most 2 KiB each of encoded identity data. That caps descriptor content at 5 MiB and launch identity content at 512 KiB before row and index overhead. Count only new keys under the same provisioning serialization and exact previous-generation check. Exact retry uses zero additional capacity. Capacity exhaustion refuses provisioning and leaves the current generation intact. Reuse existing validated identity, provider-name and version domains and use explicit bounded native widths for scalar fields and per-record encoded/decoded allocation in the implementation plan. The catalog confers no policy, credential, grant or storage authority.

## Canonical nonsecret fingerprint

Use closed version-one records. Apply the canonical UTF-8 JSON encoding already specified for v1 execution requests to the catalog descriptor only. Encode digests as lower-case 64-digit hex, use exact JSON integer kinds, reject duplicate or unknown members, malformed Unicode and NUL, and include effective defaults explicitly. Unit-bearing configuration uses the corresponding integer field and unit. Preserve behavior-significant sequence order. Sort artifact inventory entries by their canonical package-relative path and tool entries by fixed role. Hash `UTF8("kora.installed-selection/1")`, one zero byte, and the canonical descriptor bytes with SHA-256. Provider descriptors include their role. Renderer records include role `renderer` and profile `kora.jinja2.v1`. Persist the raw 32-byte digest. Exclude display labels, process IDs, bearer and credential values, secret references (including hashes of them), raw `runner.json`, inherited environment, credential-bearing URIs and mutable repository/workload inputs. Include configured Git commit author name/email from `GitConfiguration.identity`. The committed revision and mutable repository state remain pinned source facts.

| Descriptor | Required observed facts |
| --- | --- |
| Runtime | Registered protocol identity and implementation version, exact verified distribution/release and the behavior-bearing manifest digest, effective `LocalRuntimeConfiguration` and capabilities, selected Python/runner entry and resolved launch dependencies. The stable root/domain identity belongs to the current installation binding. `LocalRuntime` has no installed runtime registration today. Positive admission requires a separately approved real identity/version source. |
| VCS | Exact installed `git` provider identity and release manifest digest, normalized effective `GitConfiguration` for the selected repositories and bindings, and the resolved executable identities actually used by `GitVcs`. Bind the selected bare repository's `RemotePin` (device and inode) with its exact credential-free binding and its binding revision; the same path under a replaced directory fails. For Git and applicable helpers bind their versions when defined and exact file size and SHA-256. A version string or PATH match alone supplies no content proof. Mutable checkout contents are covered by pinned source authority. |
| Harness | Required exactly for agents. For `claude` bind the installed adapter and SDK manifest digests, verified CLI version, byte size and SHA-256, and the complete effective nonsecret deployment settings, including quota, retry and telemetry settings. Agent admission remains pending an approved harness credential-source/policy compatibility check. Those sources and values stay outside the descriptor. Compare actual binary bytes to the approved original record, including when a substituted binary and its current SDK RECORD agree with each other. |
| Renderer | Exact package releases and the actual behavior-bearing package/dependency manifest digests, and the closed Jinja sandbox configuration used by the admitted producer and verifier. That includes fixed allowed options, filters, globals and tests, unavailable loaders, normalization and output rules, and the semantic version of the renderer configuration. The renderer implementation and its admission remain a prerequisite. |

A release manifest is the canonical ordered list of role-approved package-relative names, byte sizes and SHA-256 values for behavior-bearing files. Its digest hashes `UTF8("kora.installed-artifacts/1")`, one zero byte and the canonical manifest bytes. A descriptor stores this digest, with distribution name and version, in place of repeating the inventory. The verifier checks the approved immutable manifest independently against the actual files and resolved tools, with admitted bytes/work and actual closure. A mutable self-declared RECORD is insufficient. The exact allowlists and release manifests, including applicable launcher/loader dependencies and typed configuration projections, are implementation-plan inputs. Unrecognized, incomplete or oversized configuration keeps provenance unavailable. Catalogue diagnostics carry fixed reasons and counts only.

## Bind the actual Worker and the original Claim

Use the existing authenticated Worker ID, token binding, incarnation, runtime, namespace and execution-domain predicates. A positive check compares the actual selected runtime and VCS names with the pinned node overrides or pinned graph defaults, resolves the pinned repository through that exact verified VCS configuration, and compares the pinned harness name for an agent. A profile default cannot substitute for a missing or unsupported pinned binding. Defaults present in the pinned graph still participate in its normal role selection. A positive selection additionally needs the trusted installation launch owner to supply an observed, live binding for the actual local Worker process.

The [isolated first sealed test agent](execution-request.md#isolated-first-sealed-test-agent) specifies the single test-only harness comparison for its exact checked graph and original attested testing launch. It preserves the original Claim and private-peer predicates. The initial installed command-only delivery and ordinary name comparison retain their existing scope.

Deliver the existing scoped service credential exclusively to that launched Worker under the trusted launch owner. Store only its existing token ID. The Worker keeps its existing token-ID binding. A new incarnation of the same Worker receives that credential only after the original process and owned connections actually close. Never rebind the old incarnation. Keep its credential identity, Worker identity/incarnation, host/boot/process-start observation, anchored root, selected generation and immutable constructor inputs in the private launch binding. The trusted operator's local launch owner, whose lifetime is independent of the API process, owns the exact interpreter, runtime root, runner command, provider constructors and relevant environment for the real Worker. Both API processes must obtain the binding from that trusted owner while the original Worker stays live. The Worker consumes those same pinned inputs on the actual runtime/provider path, under the existing cooperative installation trust. Compare artifact bytes inertly against the operator-approved release before importing an entry point or running a tool probe. Require one frozen verified launch image and preserve its identity into the actual constructors, renderer and runner launch. Reopen only under the corresponding verified anchor and recheck the selected artifact/configuration immediately before use. If the runtime would resolve an unverified path or reread mutable configuration, refuse positive provenance. No PATH, inherited config, alternate Python or state-root fallback may replace a verified input.

The positive provenance path uses an API-owned private Unix-domain connection to the same Worker operation handlers. For the exact accepted socket, capture `PeerSource.stamp()` at or immediately before accept, then attest the kernel peer and native start identity with the existing `kora.runner.peers` primitives. An absent timestamp on a fallback that requires it supplies no proof. On a credential/start-time fallback, the trusted launcher must also hold the original child continuously from before connect through useful admission and exclude PID reuse by retaining its unreaped child ownership until the exchange closes. The launcher must observe the original child still live at the guard. Accept-time PID/start equality alone cannot exclude reuse during a queued connection. Where the original continuity cannot be established, positive admission refuses. Bind that observation to the exact server exchange. For its one request, recheck the full live peer identity against the independently observed launch row and existing bearer/registration binding. Require host, boot, PID and start equality, with namespace and process-group fields according to the existing native identity contract. The attending Worker and server own the original connection without delegation, aliasing or inheritance. Refuse if that ownership or identity cannot be established or maintained. The trusted configured Worker may not proxy or pass its attested connection. An ordinary TCP loopback request, matching registration DTOs, provider names, a caller-supplied PID or a copied bearer supply no positive provenance.

The private endpoint is a second HTTP listening path under the same original foreground serving owner. Only a trusted, explicitly provisioned installation with separate activation approval and verified startup may bind the private endpoint. The trusted Worker connects to the installation-configured anchored local socket for its private exchange. The existing URL-based client destination and bearer policy still governs ordinary HTTP. The API retains the exact accepted connection through the exchange and retires only its own actual socket and path. The composition root injects a narrow API-owned proof capability under ADR-0026; API and engine do not import runner internals. The installed serving integration must provide the trusted accepted-socket binding before the private path can activate. The [ADR-0029 amendment](../../docs/decisions/0029-installed-api-serving-stack.md#private-unix-http-for-installed-selection-evidence) governs this future endpoint. Its implementation and activation require separate approval. #1772 owns its existing ordinary TCP operations.

Admit at most one private exchange and one peer observation job before native reads or body delivery, with the configured kernel backlog set to one, no application wait queue and finite pre-header, request and stop deadlines. Run native peer work outside the selector loop and metadata checkout. Reuse the original Claim slot across both paths. Return exchange/job capacity only after actual task, socket and native handle closure. At ready recheck the same live exchange witness and compact launch/generation under the original authority guard.

A single installation verification owner, with no wait queue or work inside the #1772 Claim slot, verifies the active descriptor set and actual artifacts before granting positive provenance. Give its implementation plan separate aggregate limits for installed file count, native/wire bytes, paths, parsed/configuration and intermediate copies, tool probes and deadline, plus stop and actual join/descriptor closure on success, failure, cancellation or shutdown. Do not read a changed file to EOF or release a stopped subprocess on timeout alone. Claim and replay perform no artifact/Jinja work. A missing verified generation keeps the provenance path closed instead of waiting on a request. Pin the verified selection and launch binding for the process lifetime. Configuration or files that can change outside the verified binding make it unavailable. Drain before operator replacement. Outside metadata ownership perform artifact, config and package work. At the original first `execute` Claim, recheck current generation and exact binding against the verified set, using bounded scalar admission in the existing grant transaction. For the initially supported command, populate the existing `0033` companion with the renderer digest and runtime/VCS pairs. A command keeps both harness fields NULL. An agent can later enter the same format only with the full harness pair and real agent verification. A command with a declared or materialized input remains outside the accepted v1 command scope. If original positive verification is unavailable, ordinary Claim writes the current stall-only basis with all seven selection fields NULL. It never writes partial provenance.

After API restart independently observe actual current artifacts/configuration and the same still-live original Worker through the trusted launch owner. Resolve the original Claim keys and require exact current keys, original and observed descriptors, renderer digest and the retained launch's original generation and live process binding to agree. Resolve the launch with the worker/incarnation from the original retained dispatcher, then verify the attested peer on this exchange before allowing a new upload.

Do not enumerate history. Admit indexed reads for one current binding, one original launch and at most three provider rows plus one renderer row. Check storage class and encoded lengths before handing bytes to the driver, giving at most 64 KiB descriptor bytes for the full role set or 48 KiB for the first command, before scalar, detached decoded and independently observed copies. Acquire comparator capacity for the raw projections, driver/native and retained copies, fixed scalars, and detached decode and comparison state before checkout, including the launch projection of at most 2 KiB. Retain that capacity until the checkout and every charged comparison buffer and task have actually settled. Close the native checkout before decode, hashing or artifact/config work.

Reuse the verified startup set for Claim and read only compact indexed identities under the grant transaction. Account for new compact current and launch lookups in the existing Claim admission before checkout. Preserve the #1772 Claim slot, producer ceilings, wire caps and already charged 428-byte modeled basis row. If the matched profile cannot admit the new complete projection within those limits, return for a separately approved budget design. For upload, keep the detached comparison tied to the observed generation; a compact current-generation and authority recheck at ready fences work admitted earlier, including a selection that changed and was restored.

Legacy and stall-only receipts, wrong role/mode/domain, missing or corrupt records, stale authority, ambiguous launch, unsupported defaults and same-name version, binary or config drift refuse new upload before payload receive or allocation. Authorize the live open original first grant independently from replay, which can retain a closed dispatcher. Claim replay stays read-only, keeps its original fields and uses current unsealed policy. It never fills older rows. If an ordinary authorized TCP Claim wins first, its stall-only basis stays stall-only even when retried on the attested path. Existing sealed and ready recovery predicates retain their separate contracts.

## Schema and upgrade

Allocate the next available additive migration when a plan is approved. Preserve the `0033` row shape and existing history. Create the empty catalog without backfill and verify native type, indexes, bounds and table ownership under the installed startup/acquisition fence for the exact new schema. Pin that proof for the admitted database lifetime and re-establish it at the next schema-maintenance boundary. Keep the existing approved basis checks and add no request-time schema scans. Teach the new Claim reader the verified `0032` legacy case, exact `0033` predecessor with its existing basis, and the exact new schema. On SQLite, a current stamp with missing or damaged catalog relations refuses Claim even with positive provenance disabled, and the installed admission check refuses the damaged schema before bind. It cannot masquerade as a predecessor. An empty correctly migrated catalog permits ordinary stall-only Claim.

Fence and drain incompatible Claim acquisition before moving the database stamp. The current reader only recognizes `0032` and `0033`. Keep the installed launcher exact-head guard and database → scheduler → API → Worker order. Finish verified provisioning and recheck live bindings before emitting the first populated companion. Existing workers keep the ordinary wire contract. Recovery to an earlier schema uses a compatible backup with the matching catalog/installation facts, not conversion of issued evidence. The common migration stamp also advances on the other ordinary metadata backend, with no catalog DDL there. Its new stamp is accepted only with the exact unchanged basis schema and absent SQLite-only catalog. It keeps the same ordinary stall-only Claim and replay. Existing two-database regressions remain required.

## Smallest independently verifiable delivery and checks

Deliver one real first `execute` Claim on installed SQLite after #1772. One normally scoped local command with no declared inputs receives a basis containing the verified runtime/VCS/renderer keys. Lose the response, restart the API against the same database with the original owned Worker still alive, and recover the same grant through the unchanged wire response. Resolve the complete original evidence through the internal authority comparison and verify it against the actual installed selection without replay writes. A supported harness descriptor covers the agent row shape and must eventually exercise a real installed agent path before positive agent admission. The initial delivery supplies the Claim producer and the exact read-only comparison the upload owner will use. The real before-payload transport proof belongs to the first upload consumer. Stage selection and payload reading must follow the native exchange and metadata checks, including when meta and payload arrive together.

| Check | Required observation |
| --- | --- |
| Original producer and restart | Real installed server, private native peer admission using the production Claim route, real registered Worker and native SQLite. Confirm one fully populated command basis in the original first-grant commit, historic keys resolve after restart, replay writes nothing, request loss and cancellation retain original outcome, and changed current policy leaves original provenance intact. Verify the agent-only pair and refusal of partial/contradictory rows. |
| Live source and same-name drift | Trusted current launch must match after restart. Swap a same-version executable or effective config, break the interpreter/root/domain or substitute a renderer setting. With the actual Worker still live, exercise a second process holding the same bearer and correct request selectors. It cannot write positive provenance from either transport. If its ordinary TCP request wins first, the later attested replay must keep the same stall-only grant and show no upgrade. Also reject wrong peers on the same domain, copied or unverified process claims, unbound/default Worker, wrong service/incarnation, incorrect repository or pinned role, legacy/absent/partial evidence and missing historical keys. Keep ordinary Claim replay, with no new positive basis for it. |
| Atomic switch and migration | Exercise exact 0033 → new schema, no backfill, legacy replay, malformed native catalog/schema and compatible backup rules. Reject conflicting retries and unknown cutover outcomes. With a deterministic barrier, change selection/authority after detached comparison and require refusal at the final guard, including A→B→A. Lose the launch owner and reuse a PID or incarnation hint to prove no reconstruction. Replace the SQLite file at the same path with a valid copy while Worker and launch owner stay live, and require refusal of positive proof from the acquired native database. Test exact record/byte capacity and one over, no key scans, an existing maximum applicable Claim with the new compact admission, and zero catalog decode/file work on ordinary replay, and actual checkout release before artifact/config work. Hold one native exchange before headers or payload, refuse a competitor without another peer job or body admission, keep applicable ordinary control progressing, and verify actual release on stop, timeout and disconnect before accepting a new private exchange. |
| Consumer and remaining witnesses | On the later real multipart route, observe zero payload reads/stage/provider calls on every pre-byte refusal. On the positive path exercise original ready commit, recovery and cleanup under their existing gates. #1772 owns installed registration/ordinary Claim; #197's local/2 proof remains isolated and supplies no installation selection or upload authority. Existing physical qualification remains separate. |

Implementation plans must approve the exact catalog persistence, trusted launch evidence and matched native inputs. The existing #1640 gate disposition and operational activation retain separate approvals.
