# kora MVP design — scheduler

Status: design draft for owner review (2026-10-15, revised after the design review, see [review-2026-10-15.md](../reviews/review-2026-10-15.md)). Scope: FR-6.1–6.10, FR-1.6, NFR-1, NFR-2, NFR-3, NFR-7. The scheduler is a stateless loop over the tables in [data-model.md](data-model.md); workers submit work through the runtime protocol in [protocols.md](protocols.md). Owner decisions on design choices are referenced as **DD-n** ("design decision n") and recorded in [design-decisions.md](../reviews/design-decisions-2026-10-15.md).

## 1. Components and processes

| process | role | MVP deployment |
|---|---|---|
| `kora api` | HTTP API, webhook endpoints, worker endpoints, MCP endpoints, the static files of the `kora web` console | 1..n replicas, stateless |
| `kora scheduler` | the passes below plus bounded external observation/delivery dispatch: triggers, readiness, admission, waits, timeouts, completion, clear-downstream | 1 replica in MVP; designed for n with per-row claims and a per-run lock |
| `kora worker` | one per runtime: claims attempts, prepares workspaces, submits, tails the session's normalised event stream and relays the runner's counters, uploads segments and artifacts, finalises | 1..n per runtime name, registered in the `worker` table; a worker has **one path to the control plane, the HTTP API**, with a service token bound to a namespace list (design review finding [namespace-scoped principals](../reviews/review-2026-10-15.md#namespace-scoped-principals)), outbound only (DD-13); it may run inside an adopter's network; it never enforces limits (design review finding [one enforcement point](../reviews/review-2026-10-15.md#one-enforcement-point)) |
| retention task | section 13 | a low-priority coroutine inside the scheduler process, batch-paced; not a process of its own |
| `kora standalone` | api + scheduler + worker(local) in one process on SQLite; the worker uses the same API client over an in-process ASGI transport | development |

The split between scheduler and worker is a decision (DD-13) and follows the Airflow executor model: the scheduler decides and persists; workers perform the runtime calls and report through the API. There is no direct-SQL path for workers.

## 2. The scheduling loop

The scheduler runs the following passes continuously; each database phase is a short transaction that claims rows, decides, and writes rows. External observations and channel effects use separate claim, unlocked call and compare/apply phases (section 16, ADR-0021); no transaction, connection or run/scope lock spans provider hooks, network/storage I/O or secret resolution. Disposable bounded tasks carry no authoritative run state between passes (NFR-1.2). Passes 2 to 8 operate per run under the **run lock** (a transaction-scoped advisory lock on `run.id` on PostgreSQL, the single writer on SQLite), so two scheduler replicas never evaluate the same run concurrently (design review finding [per-run lock](../reviews/review-2026-10-15.md#per-run-lock)); triggers and timeouts stay per row.

1. **Triggers.** Apply current start-sensor observations and fire due cron bindings and graph-triggered occurrences through the canonical start-run transition below, with derived idempotency keys. Webhook start acceptance already committed its pending run or no-run skip receipt in the API; this pass never converts an acknowledged trigger event into another run. Wait-directed inbound events remain wake-ups. Target policy decides at physical admission, per key (section 6), after graph overlap decided at acceptance/promotion.
2. **Materialise.** Promote an accepted `pending` run under its run lock and ordered scopes, including the graph lock. A queued-overlap run promotes only when no graph run is `running` and it is the oldest pending run by ID; other explicitly allowed starts retain their policy. Save write-once `started_at`/`run.started` on promotion and create top-level instances from the pinned IR; subgraph bodies and fan-out instances are materialised lazily when the containing node becomes `ready` (NFR-3.3). Fan-out body activation obeys its existing max_parallel body-instance cap under the relevant ordered scopes, including scheduler-only bodies; it does not reserve a graph execution-run slot without a physical attempt.
3. **Readiness.** Only accepted `current` artifacts are resolvable; staged target-source results and rejected history are never fallback inputs (ADR-0019). Readiness is a query over node state, distinct from the durable run-level discovery marker: `pending` instances of the run whose upstream instances are all terminal under the trigger rule (design review finding [one downstream clear instead of generation counters](../reviews/review-2026-10-15.md#one-downstream-clear)). For each direct branch target, first check the concrete owner's retained selection (data-model section 5.1): unresolved owner waits, exclusion/skipped owner skips the target, failed/upstream-failed owner yields `upstream_failed`, and cancellation follows existing rules. Selection cannot bypass ordinary trigger/input checks, and permissive triggers or `independent_of` cannot bypass selection. For each eligible instance: resolve inputs to `current` artifact versions, write `consumed_versions`, move to `ready` or `skipped`/`upstream_failed`. Ordinary run candidates come from durable `run.needs_scheduling`, without a timestamp cutoff (section 8). Evaluate indexed pending/changed dependency work within those runs, preserving NFR-3.3 incrementality; the marker is not a reason to rescan every node and edge.
4. **Branch and collection.** `ready` branch instances evaluate their CEL expression over consumed artifacts using the saved graph-version contract and stored summaries/projections, never current registry/plugin behavior (ADR-0018), and atomically persist compact selection with branch success. Every later target readiness rechecks that selection; a one-time write of `skipped` is insufficient after target-only clear. Only direct targets are routed, not all descendants. IR010 forbids invariant branches and direct targets, so a new body iteration materialises them and evaluates its own route; ordinary invariant nodes keep their existing reuse rules. A fan-out instance whose body instances are all terminal collects their `collect` outputs into its `List` artifact versions and completes (there is no fan-in node). A declared target-source wrapper/collector accepts its complete exported result and key atomically under the source rule below; child outputs are not renamed or invalidated.
5. **Admission.** `ready` instances that need a runtime (`agent`, `command`) become `queued` with an `attempt` row (`created`) and an immutable copy of exact input bindings (ADR-0018), subject to concurrency limits and the namespace's daily soft cost limit (section 6); an instance held back gets an `admission` wait row rather than a field of its own, whose `reason` names the limit that held it (`concurrency_limit` with its scope, `daily_budget`, `target_held` with all other holding runs, or `execution_recovery` with blocking attempt ids; [ADR-0015](../../docs/decisions/0015-web-console-design.md)). Waiting kinds (`human_input`, `wait_event`, `timer`) become `waiting` with a `wait` row and, for approvals, an `approval_request` row (section 5).
6. **Wake-ups.** Scheduler-only target sources route their output/success through the same atomic acceptance below, after validating the current wait/request. `wait` rows with `wake_at <= now`, a matching `inbound_event`, or a current prepared observation are evaluated; the owning instance returns to `running`, `ready` (retry back-off), completes (timer/valid wait), or expires. Sensor `until` uses a prepared current observation; polling and backoff use separate due times and do not move the expiry clock.
7. **Timeouts and liveness** (section 4).
8. **Completion.** Attempts in `finishing` whose runtime/dispatcher/publication closure is established and declared outputs are schema-validated and complete move their instance to `succeeded`, otherwise `failed` with `artifact_invalid`. Ordinary outputs are `current`; every output of the declared target source remains `staged` until its complete result and key are accepted together ([data-model.md section 12](data-model.md#12-immutable-run-target-identity-adr-0019), ADR-0019). A valid different key fails that source with `config_error` / `target_identity_conflict`, without promoting any companion result. Retry policy applies to ordinary failures; target identity conflict is never automatically retried, including by a source wrapper's own retry/skip-failures behavior. A sub-graph whose body failed and may retry runs **clear downstream** for its body and re-materialises it with `subgraph_attempt + 1` (data-model.md section 6); the run completes when no instance is non-terminal (DD-36 finalisation ownership).

A manual retry from the API is the same clear-downstream transaction on the chosen node, followed by the ordinary passes. When an approval request is created (pass 5), the scheduler sums the run's usage records into `run_cost` on the request (DD-8).

**Canonical start acceptance** (FR-6.2, [ADR-0020](../../docs/decisions/0020-execution-capacity-and-bounded-run-acceptance.md)). API starts and scheduler occurrences use the shared start-run entry point of section 12; there is one implementation. Authenticate and validate the envelope first, then resolve accepted run/skip replay by original request digest before current graph/schema/target checks. For a new start, preallocate its run ID and take that run lock before ordered global, namespace and graph scope locks; no existing other run lock is acquired under those scopes. Recheck deduplication, resolve/validate the requested version and params, decide overlap, check namespace outstanding usage and commit the pinned pending run plus its durable receipt/event together. A skip commits a deduplicated no-run receipt/event. The complete identity/outcome rules are [data-model section 13](data-model.md#13-run-acceptance-and-execution-capacity-adr-0020).

`graph.overlap` defaults to queue for webhook-fired starts and allow for others (ADR-0006). Allow imposes no graph lifecycle exclusion; skip considers all accepted pending/running graph runs, closing the pre-materialisation burst window; queue accepts bounded pending work and serializes promotion as above. Save the resolved policy on the run. Manual retry remains a same-run operation, not a new overlap decision. A graph using target defer declares overlap allow for independent targets to progress.

Full outstanding quota returns retryable HTTP 409/API002 with `reason=run_backlog_full`, scope, limit and used count, with no run, accepted receipt or unprocessed trigger event. Do not poison the retry key/24-hour response cache. Matching accepted replay still succeeds when the quota is full, after a deployment or after response loss. Cron/start-sensor/graph-triggered saturation instead records explicit `trigger.rejected` and advances the occurrence cursor atomically; skip records `trigger.skipped`. No hidden occurrence queue or catch-up is added. Existing trigger reads show the latest outcome/reason/time; wait-directed events retain ordinary wake processing.

Workers run a separate loop: claim `created` attempts of their runtime through the API (section 3), prepare the workspace, submit, stream, enforce, finalise.

## 3. Submission, execution uncertainty and recovery

[ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md) amends lease recovery. Lease defaults remain 120 s, renewed every 15 s; workers poll claims every 1 s. A lease is API ownership, not a physical execution lease.

1. The scheduler commits `attempt(status=created, execution_state=not_started)`, reserving capacity before any runtime effects. The worker registers its stable host name, fresh process incarnation and non-reused runtime `execution_domain_id`.
2. Before returning a self-contained claim, the API persists the attempt's original domain, increments `lease_epoch`, inserts an `attempt_dispatcher` grant binding incarnation, generation and mode, and records conservative `execution_state=unknown`. The first executing claim sets `attempt.started_at` and saves its inherited deadline under the run lock before granting effects; recovery never resets either (section 17). The claim includes that timing binding, attempt, domain, dispatcher id, mode, lease, run parameters, resolved node config/inputs/outputs/limits and secret aliases. No preparation or submission happens before this commit. A stable host id is not a domain identity.
3. Every API heartbeat, upload and transition carries the current epoch; stale calls fail `API008`. Runtime effect calls use the claim's opaque dispatcher id and authenticated control channel (protocols.md section 2), not the API epoch as an external fence. On rejection/expiry or cancellation the worker atomically closes its local dispatch gate, settles/fences in-flight calls and records its closure acknowledgement in the original runtime registry. It never dispatches another effect under that grant. A paused worker that has not acknowledged remains unresolved.
4. Before its first workspace allocation/preparation effect, an executing claim saves the nonsecret execution request and effective execution policy through the API (data-model.md section 11). The conditional write checks current namespace policy revision, capabilities, execute/result authority and write-once identity; a stale revision refreshes only an unsealed request. The worker derives its workload and session spec from these saved values, then prepares and calls idempotent `submit(workload)`; the runtime checks the original domain, dispatcher gate and durable retirement fence. The worker persists the handle and observation through the API. Heartbeats return desired state, lease expiry, recovery mode and permitted actions. Current-result writes additionally require unchanged result authority (data-model.md section 3).
5. On lease expiry the scheduler records `execution_state=unknown`, reason and last observation and makes the original attempt reclaimable for recovery. It does not release reservations, increment retry counts or mark `lost` after another lease period. The scheduler calls neither runtime nor worker. Missing registry, wrong domain, unreachable host and `lookup(None)` do not prove that an earlier authorized dispatcher cannot still submit.
6. A fresh claim for recovery reads `Runtime.recovery(attempt_id)` and uses lookup/status/adoption in the original domain. A live current attempt continues under the same id and resumes the supervisor journal/checkpoint from its recorded offset. Recovery loads the saved request and policy and never re-renders config, replaces input bindings or resolves a new branch head/feedback under that id. Dispatcher and secret authorization remain current and outside semantic hashing; observations cannot authorize effects (ADR-0018). Until every earlier dispatcher closes, adoption is observational: no worker-dispatched submission, finalization or change-request write is permitted. A claim for a current attempt with `desired_state=run`, no stop intent and an eligible unchanged deadline/expiry guard has `mode=execute`, but initially permits observation only. It can resume writes and clear `recovery_required` once the original domain confirms either the same live execution or an authoritative retained immutable prepared/completed checkpoint, and every earlier grant/operation is closed. Only while its unchanged deadline and sticky-expiry guards remain eligible may a non-retired current attempt finish that original stored publication operation, including `open_change_request` after a completed push, without restarting the agent or recollecting mutable input. Expired attempts remain observation/stop-only; a checkpoint cannot renew authority (ADR-0022). Retired, cancelled/superseded and stop-requested attempts remain read-only/stop-only. Cancelled/superseded or stop-requested work has `mode=recover` and never gains effect rights under that grant. Closing its gate still permits read-only evidence/retirement control calls. A non-portable runtime requires a worker with access to the original domain (normally the same host); a portable runtime lets another authorized worker reach that domain and all its recovery state. A new host or empty registry cannot reuse its identity.
7. If execution cannot continue, or cancellation/supersession ordered it to stop, a recovery worker closes its execution dispatch gate and calls `Runtime.retire(attempt_id, grace)`, even when no handle was stored. Retirement serializes with submit/finalize and retains a tombstone after release. Only an affirmative original-domain `TerminationReceipt` establishes runtime quiescence. An unreachable or inconclusive answer stays unknown and is retried as observation/retirement, never as a new session. Retirement does not attest to the old worker's independent operations: closure of **every** recorded dispatcher grant and resolution/fencing of each in-flight platform publication are separately required.
8. Cancelled/superseded attempts remain claimable in `recover` mode even when the run is terminal or `current_attempt_id` was cleared. Namespace/runtime token restrictions remain enforced. Such a claim can observe, stop, settle existing operations read-only and relay historical diagnostics/usage/evidence, but cannot submit, begin publication, open a change request or restore current outputs. A normal executing claim remains excluded for cancelled runs and `desired_state=cancel`.
9. When runtime termination and all dispatcher/publication closure are established, a cancelled attempt becomes `cancelled`; a disappeared execution with no recoverable result becomes `lost` (`infrastructure`). Only then may the existing infrastructure retry policy admit a new attempt; it consumes no agent retry count. A never-dispatched `created` attempt can be cancelled from durable metadata alone because no grant ever existed. Normal completed attempts also close runtime and dispatch/publication authority before terminal status. The affected run's admission barrier clears only when all its blocking attempts are settled.

**Publication recovery.** Adoption after candidate exit uses the immutable checkpoint of [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md); it never re-collects mutable files or regenerates a commit. Before a first or repeated `finalize`, close all earlier dispatchers and settle/fence their operations, then check current desired state and the unchanged deadline/expiry guard by heartbeat and obtain fresh authorization bound to the stored revision/destination. `runner` and `worker_host` have the same barrier. A completed operation returns its recorded `VcsRef` read-only. An unknown remote outcome remains a barrier while an earlier call can still take effect: equality with the exact prepared revision reconciles content, but an inconclusive/point-in-time absent branch cannot close an in-flight request. Once prior dispatch is closed and the unchanged deadline/expiry guard remains eligible, authoritative absence permits repeating the same non-retired operation; unexpected content conflicts without overwrite. Repeated change-request creation searches head/base after the same closure and deadline/expiry checks. Retired or expired operations return recorded results/read-only reconciliation only and never create effects. Missing private state is an infrastructure error but cannot terminalize the attempt until execution and dispatch closure are proven. New attempts keep distinct branches; old effects are never overwritten or rolled back.

**Operator reconciliation.** The public operation in [api-and-agent-surface.md](api-and-agent-surface.md) section 2 records `observe`, `stop` or evidenced `confirm_stopped` against the expected recovery version/domain. The first two persist intent for a worker without external calls in the API transaction. An operator with `platform` may attest that a permanently lost domain was actually terminated/decommissioned and every old dispatch/publication authority closed, naming reason and evidence. This does not mean "assume stopped" and there is no force-overlap action. Terminal run status does not exclude this recovery path.

## 4. Heartbeats, stall detection and timeouts

Two liveness signals are kept apart (NFR-2.3):

- **Runtime liveness**: the API lease (`lease_until`) and worker observations of `runtime.heartbeat(handle)` are separate facts. Lease expiry means ownership expired, not that the worker or session stopped. It records execution uncertainty and enables recovery in the original domain (section 3); time alone never permits replacement.
- **Agent-loop liveness**: `last_event_at`, advanced by every normalised event and relayed in `counters`. A session whose SDK event stream has been silent for `stall_after` is classified `stalled` by the **session runner**, the only enforcer of `max_events`, the soft budget and `stall_after` (design review finding [one enforcement point](../reviews/review-2026-10-15.md#one-enforcement-point)): it terminates the session (interrupt, 30 s grace, kill), the attempt fails with class `stalled`, and the node's retry policy decides (design review finding [`stalled` in node policy](../reviews/review-2026-10-15.md#stalled-in-node-policy)). `stall_after` comes from the node's `limits.stall_after`, else the graph's `runtime.stall_after`, else the runtime's `default_stall_after` (15 minutes in the reference runtimes; DD-15). The window is **extended while the last event is an unanswered tool call** (a long dev-run inside one `Bash` call is not a stall) up to the inherited execution deadline; it applies in full only when the harness is between tool calls (design review finding [stall detection and orphaned processes](../reviews/review-2026-10-15.md#stall-detection-and-orphans)).
- **Provider retries** (ADR-0024): `provider_retrying` events advance `last_event_at` like any normalised event, so a harness visibly retrying a provider limit is not `stalled`; the harness's own retry ceiling, set by the adapter, bounds them, and the session runner stops a session reporting a rejected limit whose reset lies beyond `stall_after`.

The supervisor's normalised stream is recorded in its control journal outside the candidate root, one line per `{i, at, kind, data}` event. Worker adoption resumes its stored offset; only supervisor-generated phase results establish preparation and publication facts (ADR-0016). Local uses separate directories and process-group cleanup for trusted development/tests, without claiming that those mechanisms stop hostile same-user code. Protected runtimes enforce control authority and whole-domain termination independently of harness parent exit.

Timeouts (FR-6.5, ADR-0022): use the immutable earliest node-attempt, enclosing-subgraph and run deadline, fixed before preparation. The runtime/common executor applies nominal local interruption at `D` and forced-stop escalation at `D + 30s` without API connectivity, including `worker_host` preparation/publication. Clock assumptions, phase ownership and fixed grace are in section 17; there is no exact physical-stop guarantee. The scheduler/API persist timeout/cancel intent and refuse new/current-result authority independently of timeout-pass latency. Terminal attempts, reservations and replacement still require affirmative execution/dispatcher/publication closure. Wait expiry remains `wait.wake_at` with its existing `on_expiry`; parent scope clocks include waits and are never reset by retries. The existing `test_runtime_enforces_deadline_during_control_plane_partition` conformance scenario now includes inherited deadlines; the named #57 contracts are in data-model section 15.3.

**Aggregate budgets** (FR-6.6, ADR-0010; [architecture critique of 2026-10-16, finding A11](../reviews/architecture-critique-2026-10-16.md#a11-aggregate-budget)). The session runner enforces only the attempt's own `budget_usd`; it cannot see the other sessions of a run. The same timeout pass therefore sums, for marked runs and their affected subgraph scopes, with counter/usage changes marking the run transactionally (section 8), `usage_record.usd_estimate` of finished attempts plus `attempt.counters.usd` of non-terminal ones, which the runner relays with every heartbeat, so the figure is at most one heartbeat interval stale while observations are healthy; during a partition it is last-known/partial with its observation time, not a bounded-staleness or complete-spend claim; previous sub-graph attempts are included (data-model.md section 5) and `resume` attempts count their delta only. When the sum exceeds the scope's `budget_usd` plus `budget_headroom_pct`, the scope is budget-exhausted, with the same rule as the namespace daily budget (section 6): the admission pass admits no further attempt in it, and a `ready` instance in that scope fails with class `budget_exhausted` instead of waiting, so the run ends deterministically; running attempts are not cancelled, they finish and keep their outputs, because killing a nearly finished session over an aggregate costs more than the overshoot of what is already running. The limit stays soft: a scope can overshoot by what its running sessions spend until they finish, plus reporting staleness, which is unbounded during an observation gap (NFR-8.2). Tests: `test_parallel_attempts_share_run_budget` (two sessions at 6 under a run budget of 10 both finish, and the third ready node of the run fails with `budget_exhausted` instead of starting), `test_subgraph_budget_includes_previous_iterations`, `test_resumed_session_does_not_double_count_usage`; each drives controlled usage events and checks the documented action at the threshold, with `partial` and `unavailable` records included at their recorded value.

Grace handling (FR-6.7): `cancel(handle, grace)` requests interruption then kill, but a successful request is not a termination receipt. Recovery uses `retire` to prove quiescence and close dispatch/publication authority before terminalizing or releasing capacity. Partial artifacts/usage and logs can be collected under a fresh recovery lease without restoring result authority. Cleanup releases bulky storage only after recovery is settled and preserves retirement fences/evidence (protocols.md section 2).

## 5. Waits hold no worker (NFR-1.3)

Admission to `human_input`, `wait_event` and `timer` creates a `wait` row and, for approval, an `approval_request` plus durable delivery intent. There is no held worker/container/lease or persistent coroutine per wait. Bounded external tasks exist only while making a call; all ownership and due work live in rows (section 16).

- **Time:** `wait.wake_at` is the timer/backoff wake or approval/sensor expiry, scanned directly. Poll due times never extend an expiry.
- **Event:** existing inbound-event matching and transition functions resolve exact current open waits; this change does not introduce another matcher. Relevant push recipients are fixed durably when selected before asynchronous handling (data-model section 14).
- **Poll:** the bounded dispatcher claims due sensor/channel/head work, commits, calls outside all DB transactions/locks, and conditionally applies the current result. Negative evidence schedules the next poll without completing the wait. Push-capable sensors/channels use the same existing inbound-event path.

Approval responses from API/channel use one shared transition under the run lock: verify the exact current open wait and pending request, immutable response SHA/digests and current approver rules. Polled completion additionally compares its observation token; an authenticated direct API response keeps its existing request body and needs no observation-token field. A request outside that authority records `approval.responded {applied: false}` and changes nothing (`API006` through the API). Response processing fences pending reads. An approval with a bound `VcsRef` leaves its original wait open and schedules a new `approved_head` claim after approval; without a VCS binding, saved-contract validation and current-wait checks suffice to complete through the existing wake transition.

**A push during review** (ADR-0008, ADR-0021). Requests bind immutable commit, fact digests and context artifact versions. Pending `head_sha` reads use the VCS protocol for every channel; a valid changed-head result invalidates the exact pending request, records `observed_head_sha`, cancels its wait, fails its node with `candidate_moved` and commits channel-closure intent. External notification/closure happens after commit. Nothing re-requests on that old evidence. The author retries the producing node with `fresh_with_feedback`; manual retry of the moved approval node remains refused (`API002`).

Authenticated unordered ref pushes are conservative negative evidence for their durably fixed local recipients. A remotely old event first arriving during a newer request can consequently cause conservative failure; no local token or arbitrary timestamp proves remote order. A queued event bound to an old wait cannot attach itself to its replacement. A new equal-head push changes no approval decision but revokes outstanding read authority; deduplicated replay adds no event/notification. A relevant push while an approved gate awaits verification fences its check and schedules a fresh one. Request audit approval is never rebound or erased.

**The re-check before downstream.** Wake-up completion of a VCS-bound approved gate requires a newly claimed head read issued after approval, with the exact approved request still owning the same open wait. Neither a pending-watch read nor channel-reported SHA qualifies. Equal head satisfies the wait and succeeds the node; changed head fails it with `candidate_moved` and `node.failed {reason: candidate_moved, approved_sha, head_sha}`, leaving the request approved as audit. Retryable unavailable evidence leaves the gate unresolved with backoff and its original expiry. A successful read is a point-in-time sample: downstream remains pinned to the approved immutable revision, including if the branch moves between sampling and database apply. No cross-system atomic fence is claimed.

`test_push_cannot_rebind_old_evidence` fixes the lifecycle on the fake VCS and the fake approval channel, on PostgreSQL and SQLite: commit A passes the gate and a request binds A, the head moves to a commit B that breaks the gate, and an authorised reviewer approves after the push: the request is `invalidated`, the node failed with `candidate_moved`, the response recorded with `applied: false`, no downstream instance becomes ready, and after a manual retry of the producing node with `fresh_with_feedback` the gate runs on B and fails, so no request exists for B; a push and a response applied concurrently, in both orders under the run lock, open no downstream either, the response-first order through the re-check; a replayed push webhook, with the same delivery key and with a fresh key for the same SHA, writes no second event and notifies the channel no second time; a response delayed past the invalidation is recorded with `applied: false` and leaves the row `invalidated` and the node failed.

## 6. Concurrency limits (FR-6.10)

There are three independent facts: namespace outstanding acceptance, graph execution-run occupancy and acquired target ownership ([ADR-0020](../../docs/decisions/0020-execution-capacity-and-bounded-run-acceptance.md)). Their exact predicates and state-by-limit table are in [data-model section 13](data-model.md#13-run-acceptance-and-execution-capacity-adr-0020). Never infer capacity from run/instance status or an admission wait's reason.

**Limits and live cap source.** Check global `max_running_attempts` (deployment config), namespace attempt concurrency, graph `runtime.concurrency.max_running_nodes`/`max_running_runs`, runtime capability/configured concurrency, fan-out `max_parallel` and target eligibility. Global/namespace attempt limits, graph max_running_nodes and runtime limits count non-terminal physical attempts; graph `max_running_runs` counts distinct run IDs with any such attempt, across all versions of the graph. Fan-out max_parallel retains its different unit: admitted unfinished body instances, one per body rather than per attempt. A body keeps its unit through no-attempt waits and until it ends with every old descendant physical attempt settled; two parallel nodes inside that body add no second body unit. Body activation, not just runtime admission, checks this cap. A proposed parallel attempt of an already counted run adds zero run slots, while still adding its physical attempt reservations; it adds a fan-out body unit only when entering a body not already counted. An admission blocked at any scope creates no attempt or hold. Namespace `max_pending_runs` is the separate start/settled-failed-retry check, counting outstanding runs, default 1000, positive finite only.

**Provider pause** (ADR-0024). The pause is applied when the limit is **observed**, not when the attempt terminates. When the API accepts, from a worker holding the current lease epoch, a `provider_limited` event in a segment upload or heartbeat, it upserts in a short transaction the `provider_pause` rows for `(quota resource, quota group)`. It maps the vendor group named by the event through the binding's `quota.vendor_groups` and pauses the whole resource when the event names no group or a group the binding does not map. `until` is set to `retry_after`, or the next back-off step when none was reported. The update is monotonic: a later `until` replaces an earlier one, never the reverse. Collection, runtime and dispatcher closure and publication reconciliation of that attempt proceed unchanged, and its execution reservations and closure barriers are not affected. Admission refuses an attempt when any paused group of its binding's quota resource covers the attempt's model, using the binding's `quota.groups` patterns, and gives it an ordinary `admission` wait with reason `provider_pause`. In the same transaction it sets the instance's `provider_wait_deadline` if none is set (section 7) and gives the wait the earlier of the pause's `until` and that deadline as its `wake_at`, so the deadline wakes the instance even while other attempts keep extending the pause. **Release is paced**: once a pause expires, admission admits at most `quota.release_batch` attempts (default 1) on that quota resource per `quota.release_interval` (default 10 seconds), oldest first. This applies to waiters whose wakes were jittered, to overdue waiters found after a restart or a delayed tick, and to never-attempted instances held back by the pause. Expired rows are inert and removed by the retention task.

The highest-numbered active graph version supplies live graph concurrency caps; when none is active, the highest-numbered deployed version remains the source. An absent cap adds no graph restriction. Deploy/retire, namespace policy changes and admission use compatible scope locks, and reads expose the cap-source version. These are current operational admission limits; graph execution semantics and each run's other pinned IR values remain unchanged. Lowering a limit cancels nothing and blocks only positive additions until usage permits them. A new branch of an already execution-reserving run still obeys all attempt caps.

**Reservation and release.** Every physical attempt reserves from `created` through `claimed`, `submitted`, `running`, `finishing`, including historical/superseded attempts and unknown work after cancellation/clear (ADR-0017). Insert and count commit together. The first attempt of a run adds one execution-run slot; terminalizing its last attempt releases one. Replayed terminal transitions release nothing twice. All ordinary terminal transitions require runtime and every dispatcher/publication closure; never-dispatched created cancellation retains its existing metadata-only exception. A no-attempt approval/sensor/timer/retry/target/budget wait reserves no execution slot; another live parallel branch retains the run slot. Target holds can persist with no execution slot, and an approval wake competes for admission normally.

**Locks and visibility.** Take the candidate run lock first; then on PostgreSQL take global, namespace, graph, runtime, fan-out and bound-target scope locks in that fixed order. Sort identifiers within a scope category when several are affected. Counts/policies are read after locks using fresh READ COMMITTED statements or explicit serializable retries; SQLite uses its existing single writer. All reservation-affecting inserts/releases, target changes, fan-out body activation/release and policy writes follow compatible locking. Never acquire another holder's run lock under a target lock. Target/recovery reason priority need not match scope lock order: among recovery/target/concurrency reasons, report recovery first, then target blockers, then concurrency scopes in their listed order, while committing neither a hold nor an attempt until every check passes. Budget-check ordering remains section 4's contract, not redesigned here.

**Eligible ordering.** In the single-scheduler MVP, visit ready candidates FIFO by stable `node_instance.id`, skip blocked candidates and continue scanning; an old Q target waiter cannot stop eligible R. A blocked instance receives an admission wait with `wake_at = now + admission_interval`; a due wake or relevant state change rechecks its authoritative eligibility. Recreated wait rows do not reset age. Do not hold a positive reservation for a candidate that failed admission. Shared locks preserve capacity under concurrent participants; strict cross-scheduler FIFO, starvation freedom, holder priority and weighted fairness are not promised. A full outstanding namespace quota or genuine physical occupancy can still delay/refuse an independent target.

Future reservation cases include `test_last_slot_reserved_once`, `test_created_attempt_reserves_capacity` and `test_capacity_released_once`, plus the complete PostgreSQL/SQLite matrix in data-model section 13.4. These are implementation gates, not runtime tests executed by documentation validation.

**Run recovery barrier** (ADR-0017). Before admitting any new runtime attempt, check every attempt of the run, including historical/superseded ones. Any `recovery_required` execution or publication condition produces `admission.reason={kind: execution_recovery, attempt_ids: [...]}`. Healthy live attempts and their current grants do not create this run-wide recovery barrier; normal parallel admissions continue under ordinary concurrency limits. Already-running work may finish; unrelated runs remain subject to ordinary limits and target policy. No unknown attempt releases its global, namespace, graph, runtime or fan-out reservation just because its instance/run is cancelled or cleared.

**Target-source acceptance** ([ADR-0019](../../docs/decisions/0019-immutable-run-target-identity.md)). The run key binds once at valid parameter creation or successful complete-result acceptance, never first upload or first hold. All source mutations, clear/cancel, recovery/claim authority changes and acceptance acquire the run lock before state/authority reads; do not acquire it after an attempt-row lock in the opposite order. Under that lock the current authoritative production must have complete valid results and normal closure. Extract one valid string; bind a null key or require exact equality; commit first-binding evidence, whole-set promotion and source success atomically. Different valid key is the non-retryable asynchronous conflict, missing/malformed/incomplete data is ordinary invalid output. Cancel-first prevents acceptance; accept-first preserves the key even if outputs are then superseded. Replays and terminal late writes cannot reopen a production.

A wake, approval, exported subgraph or fan-out source performs the same decision without an attempt. If it prepares bytes outside the transaction, recheck the exact current wait/request, iteration, consumed bindings and child versions inside it. Export rows belong to the wrapper and reference body versions through lineage; rejecting them does not mutate body history. Staging gates exported results, not body work already executed. A control-only failure handler may proceed but cannot consume rejected results. Future cases, including every upload order and scheduler source, are in data-model section 12.5.

**Lock visibility.** On PostgreSQL acquire the run lock before relevant state reads and read admission counts after the ordered scope locks, using READ COMMITTED or explicit serializable retries. A snapshot taken before waiting on an advisory lock must not supply stale counts. SQLite retains its existing single-writer discipline. Binding itself acquires no shared target hold/lock; hold acquisition/release retain their existing scope locks. Never acquire a different holder's run lock under a target scope lock.

**Target hold** (FR-6.11, [ADR-0014](../../docs/decisions/0014-target-identity.md)). A run holds its target from the first attempt admitted under its key until it leaves `running` **and** all blocking execution/publication recovery is settled: the admission pass sets `run.target_held_since` when it admits an attempt of a run whose `target_key` is bound and the field is null, and the transition to `succeeded`, `failed` or `cancelled` clears it only when recovery is settled; otherwise it remains held and is cleared by recovery completion under the same scope locks; a `retry node` after a settled release leaves it null; an unresolved hold is retained. After settled release the retry takes the hold again at its next admission, behind any run that took the target meanwhile. The hold is set whatever the graph's policy. Under `on_active: defer`, a `ready` instance of a run that does not hold its target, while any other runs of the namespace hold the same key, gets an `admission` wait row naming all those holders. Each blocker must release before defer becomes eligible; scanning continues for independent candidates; the first `admission` wait row a run receives behind a given holder writes `run.target_deferred {target_key, held_by_run_id}`, once per run and holder, not once per wait row the admission interval re-creates. A run with no key is never counted and never waits on this scope; a run of a graph with `on_active: allow` never waits but holds its target for the benefit of another graph's `defer`. The count and the setting of `target_held_since` run in one transaction under the target scope lock, taken after the fan-out scope in the fixed order above, so two concurrent defer contenders cannot both acquire a previously free key; incoming allow may still create several holders. The policy decides at admission and per key, after `graph.overlap` decided at trigger time and per graph (section 2): a graph that declares `defer` sets `overlap: allow`, otherwise `skip` and `queue` act first. `defer` cancels nothing and closes nothing: the holder's open change request stays open on the code host (ADR-0007), its pending approval request stays `pending` (ADR-0008), and a deferred run is a row (NFR-1.3) that spends nothing and is cancelled like any run. Tests: `test_same_target_triggers_follow_declared_policy` (two runs for one key under `defer`, with a parameter-bound and with an output-bound key: the second run's first admission under the key waits with an `admission` wait row and the `run.target_deferred` event, exactly one approval request in the target-dependent runtime path of this fixture is open at any time, a run on another key proceeds, and the second run is admitted when the first ends by `succeeded`, `failed` and `cancelled` in turn with execution/publication settled; under `allow` both run and the projection lists both; on PostgreSQL and SQLite), `test_target_hold_taken_once` (two admission participants on PostgreSQL, two runs on one key, exactly one defer contender sets `target_held_since` and creates its attempt), `test_target_bound_from_artifact_version` (late binding, its event, whole-result first binding and immutable origin, same-key rediscovery, different-key rejection even before first hold or after release, no binding from staged/invalid/superseded versions), `test_failed_run_releases_target` (a failed holder with settled execution/publication releases; its retry waits behind a run that took the target meanwhile), `test_target_projection_names_accepted_change` (after approval the projection of [api-and-agent-surface.md](api-and-agent-surface.md) section 2 points at the `approved` request and its `VcsRef`; an invalidated request is listed with its status).

The hold never unfreezes the key: retry after settled release reacquires the same key, and source acceptance never transfers Q to R. Output discovery, already admitted unbound work and internal wrapper work are not retroactively protected; target-dependent runtime work must depend on the source for its admission to see the key. Scheduler-only approval paths need not acquire a runtime hold, and incoming `allow` remains unchanged. No-attempt target deferral consumes no execution-run slot under ADR-0020, but physical reservations, bounded outstanding acceptance and graph overlap still apply.

**Daily soft cost limit** (DD-31): `namespace.policy.daily_budget_usd`. When the namespace's estimated spend for the current day (sum of `usage_record.usd_estimate` over attempts started today, in the namespace's timezone) exceeds it, no new attempts are admitted; running ones finish. The state is visible in `/metrics` (`kora_namespace_daily_spend_usd`, `kora_namespace_budget_blocked`) and on `GET /namespaces/{ns}/cost/daily`.

## 7. Retry handling

On attempt failure with class `c`: if `c` is in `non_retryable` or not in `retry_on`, or `attempt_count >= max_attempts`, or `predicate` evaluates false, the instance fails. Otherwise a `wait` row of kind `retry_backoff` is created with `wake_at = now + min(initial_interval × backoff^(n−1), max_interval)`; on wake the instance becomes `ready` again and the next attempt is created with the chosen strategy: `fresh` (new workspace from the declared revision), `fresh_with_feedback` (new workspace checked out from the branch of the previous attempt's `VcsRef` when present, at the branch's current head rather than the recorded commit, so that after `candidate_moved` the attempt continues from the pushed commit, section 5; `Feedback` DTO passed to `build_session_spec`, carrying review comments with author and association per DD-35, the comments of an invalidated request included), `resume` (previous attempt's `scratch.session_handle`; falls back to `fresh_with_feedback` with `strategy_fallback` set when the runtime lacks `supports_resume`, when the handle is gone, or when the installed harness version differs from the one recorded on the previous attempt, design review finding [per-attempt version snapshots](../reviews/review-2026-10-15.md#per-attempt-version-snapshots)). Sub-graph attempts follow the retry policy of the sub-graph with clear-downstream and body re-materialisation instead of a new runtime attempt.

**Provider limits** (ADR-0024). An attempt that fails with `provider_limited` never consumes the node's agent attempts and ignores `retry_on`. The scheduler persists `provider_wait_deadline` at the first of two events for the node instance: its first provider limit, at the limit's observation time, or its first admission refusal with reason `provider_pause` (section 6), at the refusal time. The second event covers an instance that has never executed and is held back by a limit another attempt observed on a shared quota. The deadline is that time plus `runtime.provider_retry.max_wait` (default 6 hours, namespace default when absent), and it never moves while set. The deadline is an ordinary indexed `wake_at`, so it is discoverable without any other wake: every `retry_backoff` or `provider_pause` admission wait of the instance wakes at the earlier of its own reason and the deadline. It covers all time until the node next succeeds or is cleared: provider retry waits, `admission` waits with reason `provider_pause`, and attempts in between. The node's `retry_backoff` wait wakes at the earlier of the deadline and either `retry_after` plus jitter (up to 10 % of the remaining wait, at most 5 minutes) or, without `retry_after`, exponential back-off from 1 minute doubling to 30 minutes with the same jitter. A node that reaches the deadline while still limited or paused fails with `provider_limited`, so a seven-day reset with a six-hour budget fails at six hours. Extending a shared pause cannot extend a node's deadline. The waits count towards the run's and sub-graph's inherited deadlines (ADR-0022); a deadline that passes first fails the node with `timeout`. The next attempt uses the node's strategy; with `fresh_with_feedback` it starts from the `VcsRef` the interrupted session published.

In MVP the `local` and `docker` runtimes declare `supports_resume = False`, because `release` frees the workspace that holds the harness checkpoint and their handles are bound to one host (protocols.md section 2, [architecture critique of 2026-10-16, finding A10](../reviews/architecture-critique-2026-10-16.md#a10-session-checkpoint)); on them every `resume` retry takes the fallback, and the attempt carries `strategy = resume` with `strategy_fallback = fresh_with_feedback`, shown in the node view and the console. `fresh_with_feedback` is the strategy that works on every runtime and the documented default where the next attempt needs the previous attempt's work: it checks out the `VcsRef` the previous attempt published and passes the `Feedback`; nothing that existed only in the released workspace or checkpoint is promised. A fallback attempt starts a new harness session, so its usage records are whole figures, never deltas (data-model.md section 7).

`test_resume_after_original_environment_removal` fixes this: a node with `strategy: resume` runs on the `docker` runtime; attempt 1 publishes its branch and fails with a retryable class; after collection its container and workspace are released and its worker is stopped; attempt 2 is claimed by another worker of the runtime and runs with `strategy = resume` and `strategy_fallback = fresh_with_feedback` in a new workspace checked out from attempt 1's `VcsRef`, with the committed changes present and a `Feedback` carrying attempt 1's failure; the node view shows the fallback; attempt 2's usage records are whole figures, and the run's cost is the sum of the two attempts. The same scenario on the fake runtime declaring `supports_resume = True` with a changed `harness_version` records the fallback too. On PostgreSQL and SQLite.

Manual retry records clear/cancel intent but creates no replacement while any execution/publication barrier in its run remains. `POST …/runs/{run}/rerun` is refused with `API002` and blocking attempt ids while the original has any replacement-blocking condition; there is no exception for a new version, different parameters or target policy. A separately triggered graph run still follows ordinary target policy. Cancellation is not converted into an infrastructure retry.

Manual retry (FR-6.8) first checks availability of required input/feedback sources for the selected strategy under the saved contract. Missing/expired required sources return `API002` with `reason = execution_inputs_unavailable`, IDs and states before retry effects; internal execution reports `config_error` before dispatch. A historical request payload is not itself required when the selected fresh retry needs no value from it. The accepted operation atomically reacquires outstanding capacity for a settled failed run before the clear-downstream transaction (data-model.md sections 6 and 13). A full quota returns retryable API002/run_backlog_full without clear effects; an already outstanding run needs no second credit. The clear closure uses declared concrete-instance data/control dependencies even for unbound inputs, and composition exports/collectors, as specified in data-model section 6. A child-only retry rearms enclosing wrappers for recollection without rematerialising unaffected siblings; a full wrapper/input/control clear retains its separate body-reset semantics. Readiness reevaluates trigger/input/routing rules and ordinary physical admission does the rest. It stays within the run's pinned graph version: `run.graph_version_id` never changes after creation, so a graph version that adds a required node, removes one or changes an artifact type never meets an existing run (FR-1.7, ADR-0007, [architecture critique of 2026-10-16, finding A09](../reviews/architecture-critique-2026-10-16.md#a09-graph-version-retry)). Running again on another version is a **rerun**: `POST …/runs/{run}/rerun` creates a new run of the same graph with `rerun_of_run_id` pointing at the original, on the pinned version by default or on the latest or a named one, with the original's parameters unless overridden; it uses canonical bounded start acceptance like any manually triggered run, consumes none of the original's artifact versions and leaves the original untouched (api-and-agent-surface.md section 2). Each attempt snapshots `price_table_id` and records actual runtime `image_digest` and installed `harness_version` when observed, with unknown values explicit. Its own saved request contains exact retained nonsecret configuration/feedback and binds `resolved_config_digest`; graph contracts and policy values are independently pinned. Current pointers and informational preset provenance are not reconstruction sources (ADR-0018, data-model.md section 11).

`test_latest_graph_creates_explicit_new_execution` fixes this: version 1 of a graph is `build → approve`; version 2 adds a mandatory gate before `approve`, removes a node and changes the type of an output. A run pinned to version 1 fails in `build`; a manual retry of `build` keeps running version 1 and never materialises the gate. A rerun with `graph_version: latest` creates a new run with `rerun_of_run_id` set, materialises the gate so that `approve` is unreachable without it, and consumes no artifact version of the original run, so no artifact of the removed node or of the old type is read under the new type. The original run's attempts still resolve to version 1, and reading their own retained configuration verifies `resolved_config_digest`; expired content is explicit, not recomputed from current pointers. On PostgreSQL and SQLite.

## 8. Restart and multi-scheduler safety

- Per-row passes (triggers, timeouts) claim rows with `UPDATE … WHERE status = … AND (lease_until IS NULL OR lease_until < now)`; per-run passes take the run lock first.
- **Pending promotion candidates** (ADR-0020): every tick queries the oldest pending run of each graph independently of `needs_scheduling` and attempts promotion under its own run lock and ordered scopes. Recheck graph lifecycle/queue eligibility under the graph lock. A blocked pending run needs no node wait or timestamp update to be revisited when its predecessor ends, including after restart. Notifications may accelerate the loop; the ordinary one-second tick remains the fallback.
- **Observation/delivery discovery** (ADR-0021): every tick scans due/expired observation claims and pending delivery records directly, independently of `needs_scheduling`. Restart supersedes expired read authority and reconciles delivery on original identities; stale tokens never reopen state. In-memory task credits are not durable workflow state; MVP has one scheduler, and any HA aggregate budget must be designed explicitly.
- **Durable candidate discovery** (ADR-0003): query indexed `needs_scheduling = true` rows with no `updated_at`/sequence cutoff. Process finite rotating batches, with a fixed upper ID ceiling for each sweep and wrap after reaching it. New arrivals cannot extend the sweep forever, and rows marked behind its cursor are included on a later sweep. Never restart every page at the first persistently marked rows. The cursor/ceiling are disposable scheduling optimizations; after restart a fresh sweep reads the same durable predicate. Blocked pending/settled runs may acknowledge no local work without suppressing independent scans.
- **Tick semantics** (DD-36, amended by ADR-0003): for each candidate, passes 2 to 8 repeat until a fixed point, capped at 10 rounds per run per tick. Every graph-relevant write, including writes by these passes, sets the marker as specified in data-model section 2.1. Acknowledge only under the run lock after a fresh read/check that no local transition is currently actionable; this check and setting `needs_scheduling = false` are one transaction. An earlier round's cached no-change result is insufficient. If work remains at the cap, leave the marker true for the next sweep. Releasing the lock between rounds is permitted, never between the final check and acknowledgement. A concurrent producer takes the same lock: either its change participates in that check or it commits the marker true afterwards. Every table still carries `created_at` and `updated_at` for inspection.
- **Independent progress sources**: timed waits, admission rechecks, pending promotion, due observations/delivery, deadline enforcement and execution recovery are queried by their own durable predicates each tick, without requiring a marked or running run. Apply graph-relevant results with the marker in the same locked transaction. The marker may be cleared while waiting for a future timer, admission recheck or an external observation only when that durable independent source remains discoverable. Terminal-run recovery and delivery never disappear behind the ordinary run filter.
- Actions are idempotent on `(run id, node path, attempt id)` (NFR-2.2): re-running a pass after a crash re-derives the same decisions from rows; side effects are guarded by the attempt id as submission key, `approval_request.id`, `inbound_event` idempotency per `(namespace, name)` and the `idempotency_record` table.
- On restart the scheduler performs a **recovery pass** first: expired leases on `claimed`/`submitted`/`running`/`finishing` attempts are marked reclaimable under the domain rule of section 3; lookup and adoption are performed by the workers that claim them. Then ordinary marked-run discovery resumes from a fresh sweep alongside all independent due-work scans; neither pre-crash timestamps nor in-memory notifications are needed.

## 9. Scheduling latency (NFR-3.1)

Passes run every 1 s when idle and immediately after any transition (a lightweight in-process notification, or Postgres `LISTEN/NOTIFY`, wakes the loop; SQLite polls). The under-5-second admission target at MVP scale includes complete candidate discovery (including cursor wrap), all required bounded local processing and the worker claim interval. Verify it with notifications disabled; a one-second tick alone is not a latency proof. Candidate batching must keep NFR-3.3 incremental behavior on a 1,000-node graph. This does not add a starvation-free or bounded-latency guarantee under overload. Runtime start-up latency (container start, checkout) is measured separately between `submitted` and the first event and exposed as a metric and on the attempt (`startup_ms`).

## 10. Standalone (SQLite) versus Postgres

| concern | Postgres | SQLite (standalone) |
|---|---|---|
| row claims | `SELECT … FOR UPDATE SKIP LOCKED` | single-writer connection with `BEGIN IMMEDIATE`; one process owns all loops, so claims are plain updates |
| run lock | `pg_advisory_xact_lock(hash(run.id))` | implicit: one writer |
| admission scope locks | `pg_advisory_xact_lock` per limit scope in the fixed order of section 6 | implicit: one writer |
| connection | pool | one connection, WAL mode, `busy_timeout` 5 s, one `asyncio` lock per transaction |
| wake-up | `LISTEN/NOTIFY` plus 1 s poll | in-process event plus 1 s poll |
| JSON columns | `jsonb`, indexed on `consumed_versions` keys | `json` text, no partial indexes; sufficient at standalone scale |
| concurrency | n api replicas, n workers | all coroutines in one process; local runtime only by default (Docker allowed) |
| migrations | `kora db upgrade`, online (NFR-7.2) | same migration files |

The schema and all queries are shared; the repository layer has exactly two dialect-specific statements (claim and notify). Anything that works only on SQLite or only on Postgres is a bug by NFR-0.1.

**Standalone bootstrap** (DD-36): `kora standalone` reads `kora.toml` (or defaults), creates the namespace `default` and the data directory `./.kora-data/{kora.db,artifacts,workspaces}`, prints a personal user token once (with `approve` and `platform` set, namespace `default`, transcripts readable) and mints an internal service token for the in-process worker; the CLI and the MCP servers read `KORA_URL` and `KORA_TOKEN`.

## 11. Metrics and health (NFR-7.3)

`/metrics` exposes: queue depth per runtime (`created` + `queued`), age of the oldest `created` attempt, failed-to-submit count per runtime (design review finding [missing metric and native limit](../reviews/review-2026-10-15.md#missing-metric-and-native-limit)), running attempts, waiting instances by kind, scheduling latency histogram (ready → submitted), startup latency, stalled and confirmed-lost counts, unknown execution count/oldest age by runtime and namespace, retained reservation counts by scope, distinct execution-run usage and effective graph caps/source version, outstanding namespace usage/limit, rejected-start count and last trigger outcome, retained target holds (including terminal runs), unresolved dispatcher/publication counts, last successful recovery observation, worker liveness (registered workers by runtime and seconds since last seen), webhook authentication failures, retention last success timestamp and backlog, pending approval age, daily spend and budget-blocked flag per namespace, exporter drops. `/readyz` fails when the DB is unreachable or the recovery pass has not completed.

### Diagnostic output health

Scheduler and worker diagnostics follow [the shared logging contract](observability.md), including standalone logical-component context. Expose diagnostic loss by fixed component/level/reason, queue records/bytes and sink failure/recovery independently of the output sink through existing health/metrics surfaces. Preserve this specification's bounded namespace/runtime/resource/scope dimensions; never label diagnostic metrics by run/request/attempt/session. Output saturation is visible degradation and does not change core database readiness, transition authority or durable events.

For diagnosis, first inspect component/instance and safe correlation IDs, then the authoritative run/attempt/event state. Check loss/queue/sink health before interpreting absence of a log. Use scoped DEBUG configuration at process startup without weakening content protection, and restore the intended level after investigation. Do not copy raw session content into operator logs. A stalled collector or closed pipe must not hold a scheduler transaction, delay provider cancellation or postpone inherited-deadline stop escalation; the bounded output/shutdown tests activate with each owning component.

## 12. Execution backend boundary (NFR-5.5)

The shared start-run transition and passes in section 2 own `run`, `node_instance`, `attempt` and `wait` rows between states, and the API reaches them through three entry points: start a run, deliver a signal (approval response, inbound event, cancel, manual retry) and tick. Canonical start commits bounded acceptance and receipt/skip replay through this shared entry, including webhook calls in the API; the scheduler owns later promotion/materialisation and physical admission. It does not convert acknowledged trigger receipts into new runs (ADR-0020). That boundary is documented in prose rather than as a Python interface with one implementation (DD-7, design review finding [speculative mechanisms](../reviews/review-2026-10-15.md#speculative-mechanisms)): when the Temporal-backed backend is prototyped after MVP, the generic interpreter workflow replaces the passes and projects transitions into the same rows (data-model.md section 9); readers always read kora's tables.

## 13. Retention task (DD-4)

Retention runs as a separate low-priority task in the scheduler process, paced in small batches with a sleep between them, never inside a scheduling pass. Each batch: select up to N payload owners past their retention, mark `expiring`, delete content only when no unexpired owner outside the batch or required active/recovery hold references it, mark `expired`, write content-free `retention.expired` events. The task also covers saved request/derived-result descriptors and inline copies (ADR-0018, data-model.md section 11). It checks all unexpired owners and explicit active-execution/recovery holds, not only artifact-version references. A terminal run's possible future retry holds nothing; unresolved recovery holds only the bytes required by its original operation. Deletion of inline content uses the same expiring/expired protocol, without copying it into permanent events. The task records its last successful completion for the metric and is safe to re-run at any point (data-model.md section 10).

## 14. Migrations (NFR-7.2)

Alembic migrations are **additive only within a minor version**: columns are added nullable or with defaults, nothing is dropped or renamed until the next minor, and every release runs against the previous schema (N−1 compatibility) so components can be upgraded one at a time. Index creation on PostgreSQL uses `CREATE INDEX CONCURRENTLY` outside a transaction; every DDL statement sets `lock_timeout` so a migration fails fast rather than blocking the scheduler. Upgrade order: database → scheduler → API → workers; a worker on the previous version keeps working because the API accepts the previous request shapes. ADR-0018 additionally requires compatibility with active execution-record formats, saved type/behavior contracts and execution semantics. A compatible release retains required implementations/readers; missing behavior is an explicit pre-effect incompatibility, never a schema alias or plugin substitution. Historical reads use stored results without executing old plugins. SQL compatibility alone does not satisfy this gate.

## 15. Operability runbook

- **Workers**: `GET /workers` lists the registry (runtime, version, capacity, last seen from claims and attempt heartbeats); a worker that stops claiming is visible before any attempt stalls. A worker refuses to start, and `kora doctor` reports, when an installed harness lies outside the version range its adapter declares as tested (design review finding [harness version health check](../reviews/review-2026-10-15.md#harness-version-health-check)).
- **Execution recovery**: inspect the attempt's original domain, last observation, unclosed dispatcher grants, pending publication, retained scopes and permitted actions through `kora node`/`kora run`. Request `kora reconcile … --action observe` or `stop` with the expected version/domain. For a permanently lost host, establish actual decommissioning/termination and closure of all dispatch and publication authority before recording `confirm_stopped` with evidence. No elapsed-time or force-retry shortcut exists; stale requests reload the version (`API002`). Cost remains last-known and partial until observation recovers.
- **Storage consistency**: `kora db verify-storage` walks artifact/segment/request/derived-result references and required active/recovery holds against the blob store and reports missing or orphaned blobs (ADR-0018).
- **Backup and restore**: back up the metadata database first, then the blob store; on restore apply in the same order. Blobs are immutable and content-addressed, so the blob store is backed up by copying new objects: the `artifacts/` directory for `local`, bucket replication or versioning of the S3-compatible service (or a copy with its own tooling) for `s3`. Rows whose referenced bytes are physically missing are marked `missing` by `verify-storage --repair`, distinct from intentional retention expiry; neither state can be silently replaced with current data (ADR-0018). Approval channels search for an existing comment carrying the request id before posting, to reconcile existing comments; search-before-create alone is not exactly-once publication, and terminal recovery uses read-only lookup/closure (section 16); the publish plan and `open_change_request` are idempotent on their natural keys (protocols.md section 4), so an attempt finalised again after a restore returns the same branch and change request; triggers replay from `trigger_binding.last_fired_key`, so a restored cron does not double-fire.
- **VCS polling**: the approval channel and the built-in sensors poll with exponential back-off and respect the code host's rate-limit headers; results and worker logs are redacted of push URLs and tokens (credential helpers, never URL-embedded secrets).

## 16. External observation dispatch (ADR-0021)

### 16.1 Claim, call, compare and apply

The dispatcher is an async component inside the existing single MVP scheduler, including standalone. It calls sensors, approval channels, VCS reads and their declared secret/storage dependencies; it calls no runtime and uses no worker service token. Control-plane placement must reach each configured integration; worker-only network access supplies no route. Provider installation/hooks are trusted bounded cooperative code, not graph-author Python or a hard isolation boundary (protocols section 1).

1. Reserve all immediately available local invocation/resource/namespace credits together; create no task queue proportional to due rows and hold no partial credit set while waiting. Scan finite batches, rotating across resources/namespaces and skipping saturated ones. Under the existing owner/run locks, check due/current state and persist a fresh token/purpose/deadline and snapshot descriptor (data-model section 14). Failed claims return the credits without external work.
2. Commit and release all DB transactions, connections, run/scope locks and the SQLite writer. Only then load retained content, resolve current authorized credentials, call the provider once and prepare/validate its bounded result against saved semantics. Previously validated immutable local metadata supplies capabilities/contracts inside transactions; invoking provider/type hooks or external storage there is forbidden.
3. In a short transaction, take the original run lock and any required ordered scopes, read fresh state, and compare token/deadline, exact current open wait/request/iteration, input/contract/configuration bindings and relevant current authority. A stale success or error is discarded. Apply through the existing shared transition/source-acceptance function and consume the token with outcomes/events atomically. A state-changing current apply also sets the owning `run.needs_scheduling = true` in that transaction so ordinary incremental readiness/completion sees it; notification only accelerates the next tick and is not required for recovery. Do not turn old negative evidence into a failure of new work.

Start-sensor apply uses prospective run lock → global/namespace/graph scopes → binding row/CAS, with enabled/revision/token/cursor validation after locking. Canonical acceptance commits one accepted/skipped/saturation-rejected outcome and cursor together; no intermediate start or cursor commit. Pause/resume, deployment and binding changes use compatible scope-before-binding order. Claim-only binding transactions never acquire scopes/run locks afterwards. Matching and transition ownership remain the existing shared functions.

Each wait has one current read slot. Approval polling and pending head watches choose earliest due purpose with a stable rotating tie-break; neither can starve the other. Approval transition fences pending reads and makes `approved_head` newly due, without another pending poll. Clear/cancel/expiry revokes the exact wait authority; expiry follows its existing `wake_at`/policy, independently of stuck observations. Without a VCS binding, approval completion requires no fabricated head read.

### 16.2 Finite budgets and cooperative lifetime

Defaults are installation configuration, finite positive and not graph-author overrides:

| setting | default | accounting |
|---|---|---|
| active invocations | 16 | one scheduler installation in MVP; not an implied fleet-wide semaphore |
| active invocations per integration resource | 4 | actual configured backend/account shared by aliases and declared nested dependencies |
| active invocations per namespace | 4 | all observation and channel-delivery purposes |
| operation deadline | 10 s | includes content/credential resolution, provider work, pagination/decoding and prepared validation |
| cancellation grace | 1 s | after deadline, initiate cancel and observe settlement asynchronously; no inline wait blocks scheduling |
| local backoff ceiling | 5 min | exponential with injected jitter; respect sensor minimum interval and any later backend retry time |
| payload/body/result bound | 1 MiB | per call, encoded and decoded HTTP bytes/result envelope; reject excess, never truncate into success |

Bound scan batch size, strings/collections/nesting, pagination/request counts, redirects and diagnostic buffers in installation config too. Reference providers use streaming body limits and serial pagination; one composite invocation has at most one outbound request active at a time. Declare the complete dependency-resource set before dispatch, including VCS/secret/storage resources; charge all together, without nested reacquisition or hidden parallel backend calls. Undeclared dynamic dependencies violate the protocol. Call limits bound local conforming work, not remote operations continuing after a response timeout. Resource identity binds trusted endpoint/account and implementation/config revision separately from an author-visible alias.

Observation/create deadlines are no later than their owner's remaining lifetime; terminal cleanup gets its own finite call deadline after wait expiry. At deadline, reject the result and initiate cancellation; do not use `wait_for` completion as proof of a hard stop. Physical credits release exactly once when the task settles. A task surviving grace keeps credits, degrades its integration and requires provider repair/restart; no unlimited replacement tasks or detached-task replenishment. Cooperative reference providers keep event-loop synchronous work bounded and propagate cancellation. Arbitrary blocking/cancellation-resistant installed code is outside this MVP guarantee, including standalone. Multiple future schedulers must state aggregate budgets; logical CAS safety alone does not establish physical concurrency bounds.

### 16.3 Error and recovery policy

Every failure is a bounded redacted structured integration diagnostic (`code`, `message`, `retryable`, `details`, purpose/resource/time/recovery hint), not a placeholder observation. Only a current claim may change its owner's failure state.

| result | decision |
|---|---|
| Explicit negative/false or `poll(None)` | Successful observation; consume token, retain unresolved wait, schedule next due purpose |
| Timeout, connection failure, retryable backend error | Record unavailable evidence and back off; no success, agent-attempt retry charge or expiry extension |
| Rate limit | Same, plus shared resource cooldown; honor a later valid server retry time even beyond local backoff ceiling |
| No credits | Local dispatch deferral; no provider call, failure or attempt created; scan other eligible resources |
| Permanent config/access/credential failure, unavailable saved semantics, invalid/oversized result | Fail the current waiting operation with `config_error` and specific integration code; close its wait and commit closure for any pending request, preserving an already approved audit row. A start binding stays blocked with no consumed occurrence |
| Unexpected provider exception | Explicit provider fault, bounded backoff; after three consecutive failures mark degraded and allow one probe at a time at capped backoff; no swallowed failure or fabricated value |
| Obsolete owner/token | Discard both success/error; cancel active work where possible; no retry for that owner |

Credential/access failures allow capped probes that recheck authorization and resolve current values even under unchanged references. A local policy denial permits no external call; periodically recheck local policy for repair. Successful probe clears integration/start-binding degradation and schedules a fresh authorized observation; it does not resurrect failed nodes. They use ordinary manual retry after repair. Binding changes and existing pause/resume also schedule recheck. Truly invalid configuration/protocol contracts require relevant repair rather than blind repeated effects. A backend cooldown applies to all aliases of that resource, not every integration.

### 16.4 Recoverable approval effects and visibility

`request`, `notify` and transport `cancel` are effects. Their durable authorization/desired revision and result reconciliation are data-model section 14.3 and protocols section 5, not the discardable read rule. Pending creation always reconciles its stable marker first. A terminal transition stops new create authorizations; an already authorized call may still send after that transition. Record every late learned id on the original request and close each. Terminal lookup never creates. No timeout, missing response or empty lookup proves that an old effect cannot appear.

Discover pending delivery independently of `needs_scheduling`, including approved/rejected and terminal runs. After create becomes forbidden, release delivery payload holds and retain compact original-resource identity/progress only. Continue bounded read-only reconciliation without abandonment or reservation/recovery barriers; old-resource authorization failures remain visible. Exact current gate/audit status lives in the API; terminal messages may duplicate or reorder and never authorize downstream.

Existing node/approval/trigger reads and their CLI/MCP projections show purpose, configured integration, current deadline, last successful observation/time, structured error, retry/cooldown, dispatch deferral and delivery uncertainty. Terminal delivery rows stay discoverable. Metrics add in-flight/limits, due age, call duration/outcomes, timeout/stale-discard counts, cooldown and pending/unknown delivery age, with bounded resource/purpose/outcome labels and no secrets, payloads, URLs or run ids. External outages degrade integrations rather than core DB readiness. The future PostgreSQL/SQLite acceptance matrix is [data-model section 14.4](data-model.md#144-future-acceptance-contracts); documentation checks do not execute it.

## 17. Inherited deadline enforcement (ADR-0022)

The decision is [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md); scope fields/binding and future cases are [data-model section 15](data-model.md#15-inherited-execution-deadlines-adr-0022). This section changes eligibility and local timing, not the matching engine or broader pass/lock ordering in issue #48.

1. Promotion writes the run clock once. First subgraph activation to `ready` writes its clock before body materialization; own iterations and clear preserve it. First executing claim fixes the physical attempt's start and earliest configured scope deadline before any allocation/preparation. No parent deadline may already be expired/latched. An absent overall deadline stays null. An expired unclaimed scope is still discovered; missing attempt start does not hide its parent.
2. Before every useful admission/activation, first request sealing, execute/publication authorization and current-result/success transition, use the same run lock and fresh time/authority reads to compare applicable deadlines and latches. Include scheduler-only completion and exact equality. Authentication and saved-descriptor read-only replay keep their existing order; replay never renews authority. An expiry transition commits timeout/cancel and `run.needs_scheduling = true` together. Manual retry checks the target persistent wrapper and ancestors before quota/clear; a prior physical node timeout alone does not prohibit a new eligible attempt.
3. Each tick discovers due run/subgraph/attempt deadlines directly, independently of `needs_scheduling`, including runs with only waits or unclaimed attempts. Parent expiry records its sticky latch, fails the scope with `timeout` and orders cancellation of active descendants. Child retries cannot reopen it. Node-attempt expiry follows existing node retry policy only after ordinary closure, while all enclosing scopes remain eligible. Timeout intent does not terminalize an unresolved physical attempt or release its reservations.
4. Before pre-submit work the existing authenticated protocol context/common executor receives the saved binding and records it in the original runtime registry/checkpoint. Each placement has local timers and cancellable, finitely bounded operations. Plan steps and network/secret/input-transfer work use the lesser of their own bound and remaining scope time; no phase adds another full duration. `Workload` and finalization refer to the same binding. Runtime placement, not the VCS backend, owns local process control. Stall extension never exceeds the inherited cutoff.
5. On the conservative interruption threshold, close the local execution gate durably and interrupt active managed work. Start no new effectful phase or publication. Escalate from the fixed absolute `D + 30s`; a late claim/adoption beyond it forces immediately. Earlier cancellation/retirement can shorten stopping, never extend it. Candidate effects may continue during grace and an already-authorized external call may send/settle later. A closed gate is not a remote send fence.
6. Continue only bounded historical collection, observation, retirement, dispatcher/publication reconciliation and cleanup under existing recovery claims. Their finite configured operation/decoding/output bounds and bounded batches never block escalation; optional diagnostics yield partial/unavailable at their bound. Required unresolved closure may survive indefinitely. Recovery may return a completed operation read-only but cannot use remote absence or a prepared checkpoint to launch a new push/change request after expiry. Keep ADR-0017/ADR-0020 barriers and target holds until affirmative closure.

### Clock conversion and fault model

Persist UTC `D`, the determining concrete scope and the saved finite nonnegative `clock_uncertainty`; persist expiry/closed state, not cross-host monotonic timestamps. The uncertainty covers UTC error against the authority, conversion sampling and elapsed-time underestimation over the supported horizon. A supported installation states that bound; it is not a synchronization service or a bound on OS scheduling latency.

For a paired local sample `(w0, m0)`, schedule interruption at `m0 + max(0, D - w0 - clock_uncertainty)` and escalation at `m0 + max(0, D + 30s - w0 - clock_uncertainty)`. A new sample may only shorten an installed threshold. UTC guards at useful-phase/authority boundaries also observe forward adjustment. A backward adjustment cannot extend a live monotonic timer or reopen latched expiry. Restart reconstructs thresholds from the same saved values; changed installation policy cannot weaken the original contract.

`D` and `D + 30s` are nominal local action thresholds, with scheduling/runtime-control latency rather than a hard-real-time dispatch or physical-termination guarantee. Control-plane partition tolerance assumes the local supervisor remains runnable, local runtime control works and the clock assumption holds. Host suspension, paused/crashed supervisor, lost registry, inaccessible daemon or known unsupported clocks do not prove stopping. Deny new execution when a known condition violates the model; run overdue stop actions when local control returns and keep recovery uncertain until evidence arrives. Real local/Docker evidence is separate from fake protocol decisions and metadata transitions.
