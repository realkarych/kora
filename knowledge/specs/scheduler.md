# kora MVP design — scheduler

Status: design draft for owner review (2026-10-15, revised after the design review, see [review-2026-10-15.md](../reviews/review-2026-10-15.md)). Scope: FR-6.1–6.10, FR-1.6, NFR-1, NFR-2, NFR-3, NFR-7. The scheduler is a stateless loop over the tables in [data-model.md](data-model.md); workers submit work through the runtime protocol in [protocols.md](protocols.md). Owner decisions on design choices are referenced as **DD-n** ("design decision n") and recorded in [design-decisions.md](../reviews/design-decisions-2026-10-15.md).

## 1. Components and processes

| process | role | MVP deployment |
|---|---|---|
| `kora api` | HTTP API, webhook endpoints, worker endpoints, MCP endpoints, the static files of the `kora web` console | 1..n replicas, stateless |
| `kora scheduler` | the passes below: triggers, readiness, admission, waits, timeouts, completion, clear-downstream | 1 replica in MVP; designed for n with per-row claims and a per-run lock |
| `kora worker` | one per runtime: claims attempts, prepares workspaces, submits, tails the session's normalised event stream and relays the runner's counters, uploads segments and artifacts, finalises | 1..n per runtime name, registered in the `worker` table; a worker has **one path to the control plane, the HTTP API**, with a service token bound to a namespace list (design review finding [namespace-scoped principals](../reviews/review-2026-10-15.md#namespace-scoped-principals)), outbound only (DD-13); it may run inside an adopter's network; it never enforces limits (design review finding [one enforcement point](../reviews/review-2026-10-15.md#one-enforcement-point)) |
| retention task | section 13 | a low-priority coroutine inside the scheduler process, batch-paced; not a process of its own |
| `kora standalone` | api + scheduler + worker(local) in one process on SQLite; the worker uses the same API client over an in-process ASGI transport | development |

The split between scheduler and worker is a decision (DD-13) and follows the Airflow executor model: the scheduler decides and persists; workers perform the runtime calls and report through the API. There is no direct-SQL path for workers.

## 2. The scheduling loop

The scheduler runs the following passes continuously; each pass is a short transaction that claims rows, decides, and writes rows. No pass holds state in memory between passes (NFR-1.2). Passes 2 to 8 operate per run under the **run lock** (a transaction-scoped advisory lock on `run.id` on PostgreSQL, the single writer on SQLite), so two scheduler replicas never evaluate the same run concurrently (design review finding [per-run lock](../reviews/review-2026-10-15.md#per-run-lock)); triggers and timeouts stay per row.

1. **Triggers.** Fire due `trigger_binding` rows (cron `next_fire_at <= now`, sensor polls due through the sensor protocol); create `run` rows with derived idempotency keys; apply the graph's `overlap` (`allow`: always start; `skip`: no run if one is `running` for the graph; `queue`: create `pending` and start later; DD-12). When the graph sets no `overlap`, runs fired by a webhook use `queue`, so that a burst of events does not start a burst of runs, and runs from every other trigger kind use `allow` (FR-6.2, ADR-0006). Webhooks are authenticated by the API (HMAC or bearer per trigger, DD-17) and turned into `inbound_event` rows; the trigger pass converts those addressed to a trigger binding into runs and those addressed to waits into wake-ups. A graph's per-target policy (`graph.target.on_active`, FR-6.11) is not applied here: it decides at admission, per target (section 6).
2. **Materialise.** A `pending` run gets its top-level node instances created from the pinned graph version's IR; subgraph bodies and fan-out instances are materialised lazily when the containing node becomes `ready` (NFR-3.3).
3. **Readiness.** A query, not a dirty set: `pending` instances of the run whose upstream instances are all terminal under the trigger rule (design review finding [one downstream clear instead of generation counters](../reviews/review-2026-10-15.md#one-downstream-clear)). For each: resolve inputs to `current` artifact versions, write `consumed_versions`, move to `ready` or `skipped`/`upstream_failed`. Only runs touched since the last pass (`run.updated_at`) are visited, which keeps the pass incremental (NFR-3.3).
4. **Branch and collection.** `ready` branch instances evaluate their CEL expression over consumed artifacts using the saved graph-version contract and stored summaries/projections, never current registry/plugin behavior (ADR-0018), and mark non-chosen targets `skipped`; a fan-out instance whose body instances are all terminal collects their `collect` outputs into its `List` artifact versions and completes (there is no fan-in node).
5. **Admission.** `ready` instances that need a runtime (`agent`, `command`) become `queued` with an `attempt` row (`created`) and an immutable copy of exact input bindings (ADR-0018), subject to concurrency limits and the namespace's daily soft cost limit (section 6); an instance held back gets an `admission` wait row rather than a field of its own, whose `reason` names the limit that held it (`concurrency_limit` with its scope, `daily_budget`, `target_held` with the holding run, or `execution_recovery` with blocking attempt ids; [ADR-0015](../../docs/decisions/0015-web-console-design.md)). Waiting kinds (`human_input`, `wait_event`, `timer`) become `waiting` with a `wait` row and, for approvals, an `approval_request` row (section 5).
6. **Wake-ups.** `wait` rows with `wake_at <= now` or a matching `inbound_event` are resolved; the owning instance returns to `running` (sensor: evaluate `until`, else reschedule), `ready` (retry back-off) or completes (timer).
7. **Timeouts and liveness** (section 4).
8. **Completion.** Attempts in `finishing` whose runtime/dispatcher/publication closure is established and declared outputs all have a `current`, schema-validated version (the API validated them at upload) move their instance to `succeeded`, otherwise `failed` with `artifact_invalid`; retry policy is applied (new `queued` attempt with back-off wait, or terminal failure); a sub-graph instance whose sub-graph attempt failed and may retry runs **clear downstream** for its body and re-materialises it with `subgraph_attempt + 1` (data-model.md section 6); the run completes when no instance is non-terminal (DD-36 finalisation ownership). When the version that becomes current is the output named by `graph.target.key`, the pass binds `run.target_key` from it and writes `run.target_bound` ([data-model.md](data-model.md) section 3, ADR-0014).

A manual retry from the API is the same clear-downstream transaction on the chosen node, followed by the ordinary passes. When an approval request is created (pass 5), the scheduler sums the run's usage records into `run_cost` on the request (DD-8).

Workers run a separate loop: claim `created` attempts of their runtime through the API (section 3), prepare the workspace, submit, stream, enforce, finalise.

## 3. Submission, execution uncertainty and recovery

[ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md) amends lease recovery. Lease defaults remain 120 s, renewed every 15 s; workers poll claims every 1 s. A lease is API ownership, not a physical execution lease.

1. The scheduler commits `attempt(status=created, execution_state=not_started)`, reserving capacity before any runtime effects. The worker registers its stable host name, fresh process incarnation and non-reused runtime `execution_domain_id`.
2. Before returning a self-contained claim, the API persists the attempt's original domain, increments `lease_epoch`, inserts an `attempt_dispatcher` grant binding incarnation, generation and mode, and records conservative `execution_state=unknown`. The claim includes the attempt, domain, dispatcher id, mode, lease, run parameters, resolved node config/inputs/outputs/limits and secret aliases. No preparation or submission happens before this commit. A stable host id is not a domain identity.
3. Every API heartbeat, upload and transition carries the current epoch; stale calls fail `API008`. Runtime effect calls use the claim's opaque dispatcher id and authenticated control channel (protocols.md section 2), not the API epoch as an external fence. On rejection/expiry or cancellation the worker atomically closes its local dispatch gate, settles/fences in-flight calls and records its closure acknowledgement in the original runtime registry. It never dispatches another effect under that grant. A paused worker that has not acknowledged remains unresolved.
4. Before its first workspace allocation/preparation effect, an executing claim saves the nonsecret execution request and effective execution policy through the API (data-model.md section 11). The conditional write checks current namespace policy revision, capabilities, execute/result authority and write-once identity; a stale revision refreshes only an unsealed request. The worker derives its workload and session spec from these saved values, then prepares and calls idempotent `submit(workload)`; the runtime checks the original domain, dispatcher gate and durable retirement fence. The worker persists the handle and observation through the API. Heartbeats return desired state, lease expiry, recovery mode and permitted actions. Current-result writes additionally require unchanged result authority (data-model.md section 3).
5. On lease expiry the scheduler records `execution_state=unknown`, reason and last observation and makes the original attempt reclaimable for recovery. It does not release reservations, increment retry counts or mark `lost` after another lease period. The scheduler calls neither runtime nor worker. Missing registry, wrong domain, unreachable host and `lookup(None)` do not prove that an earlier authorized dispatcher cannot still submit.
6. A fresh claim for recovery reads `Runtime.recovery(attempt_id)` and uses lookup/status/adoption in the original domain. A live current attempt continues under the same id and resumes the supervisor journal/checkpoint from its recorded offset. Recovery loads the saved request and policy and never re-renders config, replaces input bindings or resolves a new branch head/feedback under that id. Dispatcher and secret authorization remain current and outside semantic hashing; observations cannot authorize effects (ADR-0018). Until every earlier dispatcher closes, adoption is observational: no worker-dispatched submission, finalization or change-request write is permitted. A claim for a current attempt with `desired_state=run` and no stop intent has `mode=execute`, but initially permits observation only. It can resume writes and clear `recovery_required` once the original domain confirms either the same live execution or an authoritative retained immutable prepared/completed checkpoint, and every earlier grant/operation is closed. A non-retired current attempt may finish only that original stored publication operation, including `open_change_request` after a completed push, without restarting the agent or recollecting mutable input. Retired, cancelled/superseded and stop-requested attempts remain read-only/stop-only. Cancelled/superseded or stop-requested work has `mode=recover` and never gains effect rights under that grant. Closing its gate still permits read-only evidence/retirement control calls. A non-portable runtime requires a worker with access to the original domain (normally the same host); a portable runtime lets another authorized worker reach that domain and all its recovery state. A new host or empty registry cannot reuse its identity.
7. If execution cannot continue, or cancellation/supersession ordered it to stop, a recovery worker closes its execution dispatch gate and calls `Runtime.retire(attempt_id, grace)`, even when no handle was stored. Retirement serializes with submit/finalize and retains a tombstone after release. Only an affirmative original-domain `TerminationReceipt` establishes runtime quiescence. An unreachable or inconclusive answer stays unknown and is retried as observation/retirement, never as a new session. Retirement does not attest to the old worker's independent operations: closure of **every** recorded dispatcher grant and resolution/fencing of each in-flight platform publication are separately required.
8. Cancelled/superseded attempts remain claimable in `recover` mode even when the run is terminal or `current_attempt_id` was cleared. Namespace/runtime token restrictions remain enforced. Such a claim can observe, stop, settle existing operations read-only and relay historical diagnostics/usage/evidence, but cannot submit, begin publication, open a change request or restore current outputs. A normal executing claim remains excluded for cancelled runs and `desired_state=cancel`.
9. When runtime termination and all dispatcher/publication closure are established, a cancelled attempt becomes `cancelled`; a disappeared execution with no recoverable result becomes `lost` (`infrastructure`). Only then may the existing infrastructure retry policy admit a new attempt; it consumes no agent retry count. A never-dispatched `created` attempt can be cancelled from durable metadata alone because no grant ever existed. Normal completed attempts also close runtime and dispatch/publication authority before terminal status. The affected run's admission barrier clears only when all its blocking attempts are settled.

**Publication recovery.** Adoption after candidate exit uses the immutable checkpoint of [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md); it never re-collects mutable files or regenerates a commit. Before a first or repeated `finalize`, close all earlier dispatchers and settle/fence their operations, then check current desired state by heartbeat and obtain fresh authorization bound to the stored revision/destination. `runner` and `worker_host` have the same barrier. A completed operation returns its recorded `VcsRef` read-only. An unknown remote outcome remains a barrier while an earlier call can still take effect: equality with the exact prepared revision reconciles content, but an inconclusive/point-in-time absent branch cannot close an in-flight request. Once prior dispatch is closed, authoritative absence permits repeating the same non-retired operation; unexpected content conflicts without overwrite. Repeated change-request creation searches head/base after the same closure check. Retired operations return recorded results only and never create effects. Missing private state is an infrastructure error but cannot terminalize the attempt until execution and dispatch closure are proven. New attempts keep distinct branches; old effects are never overwritten or rolled back.

**Operator reconciliation.** The public operation in [api-and-agent-surface.md](api-and-agent-surface.md) section 2 records `observe`, `stop` or evidenced `confirm_stopped` against the expected recovery version/domain. The first two persist intent for a worker without external calls in the API transaction. An operator with `platform` may attest that a permanently lost domain was actually terminated/decommissioned and every old dispatch/publication authority closed, naming reason and evidence. This does not mean "assume stopped" and there is no force-overlap action. Terminal run status does not exclude this recovery path.

## 4. Heartbeats, stall detection and timeouts

Two liveness signals are kept apart (NFR-2.3):

- **Runtime liveness**: the API lease (`lease_until`) and worker observations of `runtime.heartbeat(handle)` are separate facts. Lease expiry means ownership expired, not that the worker or session stopped. It records execution uncertainty and enables recovery in the original domain (section 3); time alone never permits replacement.
- **Agent-loop liveness**: `last_event_at`, advanced by every normalised event and relayed in `counters`. A session whose SDK event stream has been silent for `stall_after` is classified `stalled` by the **session runner**, the only enforcer of `max_events`, the soft budget and `stall_after` (design review finding [one enforcement point](../reviews/review-2026-10-15.md#one-enforcement-point)): it terminates the session (interrupt, 30 s grace, kill), the attempt fails with class `stalled`, and the node's retry policy decides (design review finding [`stalled` in node policy](../reviews/review-2026-10-15.md#stalled-in-node-policy)). `stall_after` comes from the node's `limits.stall_after`, else the graph's `runtime.stall_after`, else the runtime's `default_stall_after` (15 minutes in the reference runtimes; DD-15). The window is **extended while the last event is an unanswered tool call** (a long dev-run inside one `Bash` call is not a stall) up to the node timeout; it applies in full only when the harness is between tool calls (design review finding [stall detection and orphaned processes](../reviews/review-2026-10-15.md#stall-detection-and-orphans)).

The supervisor's normalised stream is recorded in its control journal outside the candidate root, one line per `{i, at, kind, data}` event. Worker adoption resumes its stored offset; only supervisor-generated phase results establish preparation and publication facts (ADR-0016). Local uses separate directories and process-group cleanup for trusted development/tests, without claiming that those mechanisms stop hostile same-user code. Protected runtimes enforce control authority and whole-domain termination independently of harness parent exit.

Timeouts (FR-6.5): the scheduler's timeout pass compares `attempt.started_at + limits.timeout` and `run.started_at + runtime.limits.timeout` with `now`; breaches cancel with grace and fail with class `timeout`. The node timeout also travels to the runner as an absolute deadline in `Workload.limits`, and the runner terminates the session at that deadline itself (interrupt, 30 s grace, kill) when the control plane is unreachable, so the runtime enforces the deadline independently during a partition. The scheduler records timeout/cancel intent, but terminal attempt status, reservation release and replacement still wait for affirmative termination and dispatcher/publication closure; a promised deadline is not observed evidence (`test_runtime_enforces_deadline_during_control_plane_partition`). Every wait expiry, timers, approvals and sensors alike, is the `wake_at` of its `wait` row (design review finding [one clock for approvals](../reviews/review-2026-10-15.md#one-approval-clock)); expiry applies `on_expiry` (NFR-2.5). Subgraph timeouts are checked against the subgraph instance across attempts (data-model.md section 5).

**Aggregate budgets** (FR-6.6, ADR-0010; [architecture critique of 2026-10-16, finding A11](../reviews/architecture-critique-2026-10-16.md#a11-aggregate-budget)). The session runner enforces only the attempt's own `budget_usd`; it cannot see the other sessions of a run. The same timeout pass therefore sums, for every run and every sub-graph instance touched since the last tick, `usage_record.usd_estimate` of finished attempts plus `attempt.counters.usd` of non-terminal ones, which the runner relays with every heartbeat, so the figure is at most one heartbeat interval stale while observations are healthy; during a partition it is last-known/partial with its observation time, not a bounded-staleness or complete-spend claim; previous sub-graph attempts are included (data-model.md section 5) and `resume` attempts count their delta only. When the sum exceeds the scope's `budget_usd` plus `budget_headroom_pct`, the scope is budget-exhausted, with the same rule as the namespace daily budget (section 6): the admission pass admits no further attempt in it, and a `ready` instance in that scope fails with class `budget_exhausted` instead of waiting, so the run ends deterministically; running attempts are not cancelled, they finish and keep their outputs, because killing a nearly finished session over an aggregate costs more than the overshoot of what is already running. The limit stays soft: a scope can overshoot by what its running sessions spend until they finish, plus reporting staleness, which is unbounded during an observation gap (NFR-8.2). Tests: `test_parallel_attempts_share_run_budget` (two sessions at 6 under a run budget of 10 both finish, and the third ready node of the run fails with `budget_exhausted` instead of starting), `test_subgraph_budget_includes_previous_iterations`, `test_resumed_session_does_not_double_count_usage`; each drives controlled usage events and checks the documented action at the threshold, with `partial` and `unavailable` records included at their recorded value.

Grace handling (FR-6.7): `cancel(handle, grace)` requests interruption then kill, but a successful request is not a termination receipt. Recovery uses `retire` to prove quiescence and close dispatch/publication authority before terminalizing or releasing capacity. Partial artifacts/usage and logs can be collected under a fresh recovery lease without restoring result authority. Cleanup releases bulky storage only after recovery is settled and preserves retirement fences/evidence (protocols.md section 2).

## 5. Waits hold no worker (NFR-1.3)

A waiting instance is one `wait` row and, for approvals, one `approval_request` row. Nothing else exists: no coroutine, no container, no lease. Three resolution paths:

- **Time**: `wake_at` scanned by the wake-up pass; timers and retry back-off.
- **Event**: the API writes an `inbound_event`; the wake-up pass matches it against open `wait.subscription` rows (`name` equality, then the `match` expression over payload and inputs), marks the wait `satisfied`, records `consumed_by`.
- **Poll**: sensors are polled by the scheduler at `interval` through the sensor protocol (`observe` returns an observation the node's `until` CEL expression is evaluated on); the `vcs` approval channel is polled through the approval protocol. A poll is a short call, not a held slot. Sensors that declare `supports_push` and chat channels with push notifications (post-MVP) deliver through the same `inbound_event` path.

An approval response from any channel is applied through one function: load the request, check that it is still `pending`, compare `(commit_sha, digests)` with the bound values, then transition. The channel is only a transport (FR-7.2a).

**A push during review** ([architecture critique of 2026-10-16, finding A03](../reviews/architecture-critique-2026-10-16.md#a03-review-revision); ADR-0008 as amended on 2026-10-16). An approval request covers one immutable revision: `bound_commit_sha`, `bound_digests` and `context_artifact_version_id`, which names the input artifact versions and the gate results with their provenance; a push changes none of them, and nothing ever re-requests on that bundle. For every `pending` request that binds a `VcsRef`, the wake-up pass observes the head of the bound branch through the VCS protocol's `head_sha`, at the VCS polling interval of section 15, for every channel alike; a VCS with `head_sha_watch` delivers the same observation earlier as an `inbound_event` (protocols.md section 4). A head observation is applied through a second function next to the response one, under the run lock: load the request; a request that is not `pending` means nothing to do; an observed head equal to `bound_commit_sha` means nothing to do; otherwise the request becomes `invalidated` with `observed_head_sha` recorded, the channel is notified, the `wait` row is cancelled and the human-input instance fails with class `candidate_moved`. Because both functions run under the run lock, a push and a response that race are serialised, and the one applied second finds the row no longer `pending`: a response to a request that is not `pending` is recorded as an `approval.responded` event with `applied: false` and changes nothing (`API006` through the API); a replayed push webhook is deduplicated by `inbound_event.idempotency_key`, and a delivery that gets through finds the request no longer `pending`. `candidate_moved` is never retryable (ir.md section 6): the author retries the node whose attempt produced the bound `VcsRef` (FR-6.8), with `fresh_with_feedback` to continue from the pushed commit (section 7), and the gates, the bundle and a new request follow through the normal downstream path; a manual retry of the human-input node itself is refused with `API002`, because it would request again on the bundle built for the old commit.

**The re-check before downstream.** The wake-up pass completes `human_input` instances (DD-36). Before it moves an instance whose request is `approved` to `succeeded`, it calls `head_sha` for the bound `VcsRef` once more: when the head equals `bound_commit_sha` the instance succeeds and readiness opens the downstream; otherwise the instance fails with `candidate_moved` and the event `node.failed {reason: candidate_moved, approved_sha, head_sha}` is written, while the request row stays `approved` as the audit entry of what the reviewer approved, the failed node being what shows that it authorised nothing. A `KoraProtocolError(retryable=True)` from `head_sha` leaves the instance waiting until the next tick; the node never completes on an unverified head. `test_push_cannot_rebind_old_evidence` fixes the lifecycle on the fake VCS and the fake approval channel, on PostgreSQL and SQLite: commit A passes the gate and a request binds A, the head moves to a commit B that breaks the gate, and an authorised reviewer approves after the push: the request is `invalidated`, the node failed with `candidate_moved`, the response recorded with `applied: false`, no downstream instance becomes ready, and after a manual retry of the producing node with `fresh_with_feedback` the gate runs on B and fails, so no request exists for B; a push and a response applied concurrently, in both orders under the run lock, open no downstream either, the response-first order through the re-check; a replayed push webhook, with the same delivery key and with a fresh key for the same SHA, writes no second event and notifies the channel no second time; a response delayed past the invalidation is recorded with `applied: false` and leaves the row `invalidated` and the node failed.

## 6. Concurrency limits (FR-6.10)

Limits are evaluated in the admission pass, in this order, each as a count over rows: global `max_running_attempts` (deployment config), per namespace (`namespace.policy.concurrency`, and `max_pending_runs` checked at trigger time, design review finding [namespace-scoped principals](../reviews/review-2026-10-15.md#namespace-scoped-principals)), per graph (`runtime.concurrency.max_running_nodes`, `max_running_runs`), per runtime (`RuntimeCapabilities.max_concurrent` and NFR-7.4 configured limit), per fan-out (`max_parallel`, counted over body instances of the same fan-out instance), per target (`graph.target.on_active: defer`: at most one holding run per `(namespace_id, target_key)`, below). A `ready` instance that fails any check gets an `admission` wait row with `wake_at = now + admission_interval`; the oldest ready instance wins (FIFO by `node_instance.id`). Limits live in rows and config reloaded every pass, so they change without restart (NFR-7.4).

**Reservation** ([architecture critique of 2026-10-16, finding A12](../reviews/architecture-critique-2026-10-16.md#a12-capacity-reservations)). Capacity is occupied by every non-terminal attempt, including unknown execution after run cancellation or clear-downstream, from `created` through `claimed`, `submitted`, `running` and `finishing`: an attempt reserves its slot when its row is inserted and releases it when it reaches a terminal state, which happens exactly once because terminal transitions are idempotent. The count and the insert run in one transaction under a lock per limit scope: on PostgreSQL the admission pass takes `pg_advisory_xact_lock` on the global scope, then the namespace, the graph, the runtime, the fan-out instance and the target, always in that order, so two scheduler replicas holding different run locks serialise on the shared scope and never admit over a limit; on SQLite the single writer serialises. Tests: `test_last_slot_reserved_once` (two admission participants on PostgreSQL, one free global slot, one attempt created), `test_created_attempt_reserves_capacity` (a `created` attempt not yet claimed counts), `test_capacity_released_once` (a terminal transition frees one slot and a repeated terminal transition changes nothing); SQLite is checked for the same observable outcome.

**Run recovery barrier** (ADR-0017). Before admitting any new runtime attempt, check every attempt of the run, including historical/superseded ones. Any `recovery_required` execution or publication condition produces `admission.reason={kind: execution_recovery, attempt_ids: [...]}`. Healthy live attempts and their current grants do not create this run-wide recovery barrier; normal parallel admissions continue under ordinary concurrency limits. Already-running work may finish; unrelated runs remain subject to ordinary limits and target policy. No unknown attempt releases its global, namespace, graph, runtime or fan-out reservation just because its instance/run is cancelled or cleared.

**Target hold** (FR-6.11, [ADR-0014](../../docs/decisions/0014-target-identity.md)). A run holds its target from the first attempt admitted under its key until it leaves `running` **and** all blocking execution/publication recovery is settled: the admission pass sets `run.target_held_since` when it admits an attempt of a run whose `target_key` is bound and the field is null, and the transition to `succeeded`, `failed` or `cancelled` clears it only when recovery is settled; otherwise it remains held and is cleared by recovery completion under the same scope locks; a `retry node` after a settled release leaves it null; an unresolved hold is retained. After settled release the retry takes the hold again at its next admission, behind any run that took the target meanwhile. The hold is set whatever the graph's policy. Under `on_active: defer`, a `ready` instance of a run that does not hold its target, while another run of the namespace holds the same key, gets an `admission` wait row like any other held-back instance, FIFO by `node_instance.id`; the first `admission` wait row a run receives behind a given holder writes `run.target_deferred {target_key, held_by_run_id}`, once per run and holder, not once per wait row the admission interval re-creates. A run with no key is never counted and never waits on this scope; a run of a graph with `on_active: allow` never waits but holds its target for the benefit of another graph's `defer`. The count and the setting of `target_held_since` run in one transaction under the target scope lock, taken after the fan-out scope in the fixed order above, so two scheduler replicas never admit two holders. The policy decides at admission and per key, after `graph.overlap` decided at trigger time and per graph (section 2): a graph that declares `defer` sets `overlap: allow`, otherwise `skip` and `queue` act first. `defer` cancels nothing and closes nothing: the holder's open change request stays open on the code host (ADR-0007), its pending approval request stays `pending` (ADR-0008), and a deferred run is a row (NFR-1.3) that spends nothing and is cancelled like any run. Tests: `test_same_target_triggers_follow_declared_policy` (two runs for one key under `defer`, with a parameter-bound and with an output-bound key: the second run's first admission under the key waits with an `admission` wait row and the `run.target_deferred` event, exactly one approval request for the key is open at any time, a run on another key proceeds, and the second run is admitted when the first ends by `succeeded`, `failed` and `cancelled` in turn with execution/publication settled; under `allow` both run and the projection lists both; on PostgreSQL and SQLite), `test_target_hold_taken_once` (two admission participants on PostgreSQL, two runs on one key, exactly one `target_held_since` set), `test_target_bound_from_artifact_version` (late binding, its event, the rebinding after a manual retry of the producing node, no binding from a `superseded` version), `test_failed_run_releases_target` (a failed holder with settled execution/publication releases; its retry waits behind a run that took the target meanwhile), `test_target_projection_names_accepted_change` (after approval the projection of [api-and-agent-surface.md](api-and-agent-surface.md) section 2 points at the `approved` request and its `VcsRef`; an invalidated request is listed with its status).

**Daily soft cost limit** (DD-31): `namespace.policy.daily_budget_usd`. When the namespace's estimated spend for the current day (sum of `usage_record.usd_estimate` over attempts started today, in the namespace's timezone) exceeds it, no new attempts are admitted; running ones finish. The state is visible in `/metrics` (`kora_namespace_daily_spend_usd`, `kora_namespace_budget_blocked`) and on `GET /namespaces/{ns}/cost/daily`.

## 7. Retry handling

On attempt failure with class `c`: if `c` is in `non_retryable` or not in `retry_on`, or `attempt_count >= max_attempts`, or `predicate` evaluates false, the instance fails. Otherwise a `wait` row of kind `retry_backoff` is created with `wake_at = now + min(initial_interval × backoff^(n−1), max_interval)`; on wake the instance becomes `ready` again and the next attempt is created with the chosen strategy: `fresh` (new workspace from the declared revision), `fresh_with_feedback` (new workspace checked out from the branch of the previous attempt's `VcsRef` when present, at the branch's current head rather than the recorded commit, so that after `candidate_moved` the attempt continues from the pushed commit, section 5; `Feedback` DTO passed to `build_session_spec`, carrying review comments with author and association per DD-35, the comments of an invalidated request included), `resume` (previous attempt's `scratch.session_handle`; falls back to `fresh_with_feedback` with `strategy_fallback` set when the runtime lacks `supports_resume`, when the handle is gone, or when the installed harness version differs from the one recorded on the previous attempt, design review finding [per-attempt version snapshots](../reviews/review-2026-10-15.md#per-attempt-version-snapshots)). Sub-graph attempts follow the retry policy of the sub-graph with clear-downstream and body re-materialisation instead of a new runtime attempt.

In MVP the `local` and `docker` runtimes declare `supports_resume = False`, because `release` frees the workspace that holds the harness checkpoint and their handles are bound to one host (protocols.md section 2, [architecture critique of 2026-10-16, finding A10](../reviews/architecture-critique-2026-10-16.md#a10-session-checkpoint)); on them every `resume` retry takes the fallback, and the attempt carries `strategy = resume` with `strategy_fallback = fresh_with_feedback`, shown in the node view and the console. `fresh_with_feedback` is the strategy that works on every runtime and the documented default where the next attempt needs the previous attempt's work: it checks out the `VcsRef` the previous attempt published and passes the `Feedback`; nothing that existed only in the released workspace or checkpoint is promised. A fallback attempt starts a new harness session, so its usage records are whole figures, never deltas (data-model.md section 7).

`test_resume_after_original_environment_removal` fixes this: a node with `strategy: resume` runs on the `docker` runtime; attempt 1 publishes its branch and fails with a retryable class; after collection its container and workspace are released and its worker is stopped; attempt 2 is claimed by another worker of the runtime and runs with `strategy = resume` and `strategy_fallback = fresh_with_feedback` in a new workspace checked out from attempt 1's `VcsRef`, with the committed changes present and a `Feedback` carrying attempt 1's failure; the node view shows the fallback; attempt 2's usage records are whole figures, and the run's cost is the sum of the two attempts. The same scenario on the fake runtime declaring `supports_resume = True` with a changed `harness_version` records the fallback too. On PostgreSQL and SQLite.

Manual retry records clear/cancel intent but creates no replacement while any execution/publication barrier in its run remains. `POST …/runs/{run}/rerun` is refused with `API002` and blocking attempt ids while the original has any replacement-blocking condition; there is no exception for a new version, different parameters or target policy. A separately triggered graph run still follows ordinary target policy. Cancellation is not converted into an infrastructure retry.

Manual retry (FR-6.8) first checks availability of required input/feedback sources for the selected strategy under the saved contract. Missing/expired required sources return `API002` with `reason = execution_inputs_unavailable`, IDs and states before retry effects; internal execution reports `config_error` before dispatch. A historical request payload is not itself required when the selected fresh retry needs no value from it. The accepted operation is the clear-downstream transaction started by the API (data-model.md section 6); readiness does the rest. It stays within the run's pinned graph version: `run.graph_version_id` never changes after creation, so a graph version that adds a required node, removes one or changes an artifact type never meets an existing run (FR-1.7, ADR-0007, [architecture critique of 2026-10-16, finding A09](../reviews/architecture-critique-2026-10-16.md#a09-graph-version-retry)). Running again on another version is a **rerun**: `POST …/runs/{run}/rerun` creates a new run of the same graph with `rerun_of_run_id` pointing at the original, on the pinned version by default or on the latest or a named one, with the original's parameters unless overridden; it enters the trigger pass like any manually triggered run, consumes none of the original's artifact versions and leaves the original untouched (api-and-agent-surface.md section 2). Each attempt snapshots `price_table_id` and records actual runtime `image_digest` and installed `harness_version` when observed, with unknown values explicit. Its own saved request contains exact retained nonsecret configuration/feedback and binds `resolved_config_digest`; graph contracts and policy values are independently pinned. Current pointers and informational preset provenance are not reconstruction sources (ADR-0018, data-model.md section 11).

`test_latest_graph_creates_explicit_new_execution` fixes this: version 1 of a graph is `build → approve`; version 2 adds a mandatory gate before `approve`, removes a node and changes the type of an output. A run pinned to version 1 fails in `build`; a manual retry of `build` keeps running version 1 and never materialises the gate. A rerun with `graph_version: latest` creates a new run with `rerun_of_run_id` set, materialises the gate so that `approve` is unreachable without it, and consumes no artifact version of the original run, so no artifact of the removed node or of the old type is read under the new type. The original run's attempts still resolve to version 1, and reading their own retained configuration verifies `resolved_config_digest`; expired content is explicit, not recomputed from current pointers. On PostgreSQL and SQLite.

## 8. Restart and multi-scheduler safety

- Per-row passes (triggers, timeouts) claim rows with `UPDATE … WHERE status = … AND (lease_until IS NULL OR lease_until < now)`; per-run passes take the run lock first.
- **Tick semantics** (DD-36): for each run touched since the last tick, passes 2 to 8 repeat until no row changes, capped at 10 rounds per run per tick; every table carries `created_at` and `updated_at`. MVP runs one scheduler but the statements are already claim-based (NFR-1.2 HA path).
- Actions are idempotent on `(run id, node path, attempt id)` (NFR-2.2): re-running a pass after a crash re-derives the same decisions from rows; side effects are guarded by the attempt id as submission key, `approval_request.id`, `inbound_event` idempotency per `(namespace, name)` and the `idempotency_record` table.
- On restart the scheduler performs a **recovery pass** first: expired leases on `claimed`/`submitted`/`running`/`finishing` attempts are marked reclaimable under the domain rule of section 3; lookup and adoption are performed by the workers that claim them. Nothing else needs rebuilding because readiness is a query.

## 9. Scheduling latency (NFR-3.1)

Passes run every 1 s when idle and immediately after any transition (a lightweight in-process notification, or Postgres `LISTEN/NOTIFY`, wakes the loop; SQLite polls). Admission to `runtime.submit` is therefore bounded by one pass plus the worker claim interval, under 5 s at MVP scale. Runtime start-up latency (container start, checkout) is measured separately between `submitted` and the first event and exposed as a metric and on the attempt (`startup_ms`).

## 10. Standalone (SQLite) versus Postgres

| concern | Postgres | SQLite (standalone) |
|---|---|---|
| row claims | `SELECT … FOR UPDATE SKIP LOCKED` | single-writer connection with `BEGIN IMMEDIATE`; one process owns all loops, so claims are plain updates |
| run lock | `pg_advisory_xact_lock(hash(run.id))` | implicit: one writer |
| admission scope locks | `pg_advisory_xact_lock` per limit scope in the fixed order of section 6 | implicit: one writer |
| connection | pool | one connection, WAL mode, `busy_timeout` 5 s, one `asyncio` lock per transaction |
| wake-up | `LISTEN/NOTIFY` plus 1 s poll | in-process event plus 1 s poll |
| JSON columns | `jsonb`, indexed on `consumed_versions` keys | `json` text, no partial indexes; sufficient at standalone scale |
| concurrency | n api replicas, n workers | all coroutines in one process; local runtime only by default (Docker allowed) |
| migrations | `kora db upgrade`, online (NFR-7.2) | same migration files |

The schema and all queries are shared; the repository layer has exactly two dialect-specific statements (claim and notify). Anything that works only on SQLite or only on Postgres is a bug by NFR-0.1.

**Standalone bootstrap** (DD-36): `kora standalone` reads `kora.toml` (or defaults), creates the namespace `default` and the data directory `./.kora-data/{kora.db,artifacts,workspaces}`, prints a personal user token once (with `approve` and `platform` set, namespace `default`, transcripts readable) and mints an internal service token for the in-process worker; the CLI and the MCP servers read `KORA_URL` and `KORA_TOKEN`.

## 11. Metrics and health (NFR-7.3)

`/metrics` exposes: queue depth per runtime (`created` + `queued`), age of the oldest `created` attempt, failed-to-submit count per runtime (design review finding [missing metric and native limit](../reviews/review-2026-10-15.md#missing-metric-and-native-limit)), running attempts, waiting instances by kind, scheduling latency histogram (ready → submitted), startup latency, stalled and confirmed-lost counts, unknown execution count/oldest age by runtime and namespace, retained reservation counts by scope, retained target holds (including terminal runs), unresolved dispatcher/publication counts, last successful recovery observation, worker liveness (registered workers by runtime and seconds since last seen), webhook authentication failures, retention last success timestamp and backlog, pending approval age, daily spend and budget-blocked flag per namespace, exporter drops. `/readyz` fails when the DB is unreachable or the recovery pass has not completed.

## 12. Execution backend boundary (NFR-5.5)

The passes in section 2 are the only code that moves `run`, `node_instance`, `attempt` and `wait` rows between states, and the API reaches them through three entry points: start a run, deliver a signal (approval response, inbound event, cancel, manual retry) and tick. That boundary is documented in prose rather than as a Python interface with one implementation (DD-7, design review finding [speculative mechanisms](../reviews/review-2026-10-15.md#speculative-mechanisms)): when the Temporal-backed backend is prototyped after MVP, the generic interpreter workflow replaces the passes and projects transitions into the same rows (data-model.md section 9); readers always read kora's tables.

## 13. Retention task (DD-4)

Retention runs as a separate low-priority task in the scheduler process, paced in small batches with a sleep between them, never inside a scheduling pass. Each batch: select up to N payload owners past their retention, mark `expiring`, delete content only when no unexpired owner outside the batch or required active/recovery hold references it, mark `expired`, write content-free `retention.expired` events. The task also covers saved request/derived-result descriptors and inline copies (ADR-0018, data-model.md section 11). It checks all unexpired owners and explicit active-execution/recovery holds, not only artifact-version references. A terminal run's possible future retry holds nothing; unresolved recovery holds only the bytes required by its original operation. Deletion of inline content uses the same expiring/expired protocol, without copying it into permanent events. The task records its last successful completion for the metric and is safe to re-run at any point (data-model.md section 10).

## 14. Migrations (NFR-7.2)

Alembic migrations are **additive only within a minor version**: columns are added nullable or with defaults, nothing is dropped or renamed until the next minor, and every release runs against the previous schema (N−1 compatibility) so components can be upgraded one at a time. Index creation on PostgreSQL uses `CREATE INDEX CONCURRENTLY` outside a transaction; every DDL statement sets `lock_timeout` so a migration fails fast rather than blocking the scheduler. Upgrade order: database → scheduler → API → workers; a worker on the previous version keeps working because the API accepts the previous request shapes. ADR-0018 additionally requires compatibility with active execution-record formats, saved type/behavior contracts and execution semantics. A compatible release retains required implementations/readers; missing behavior is an explicit pre-effect incompatibility, never a schema alias or plugin substitution. Historical reads use stored results without executing old plugins. SQL compatibility alone does not satisfy this gate.

## 15. Operability runbook

- **Workers**: `GET /workers` lists the registry (runtime, version, capacity, last seen from claims and attempt heartbeats); a worker that stops claiming is visible before any attempt stalls. A worker refuses to start, and `kora doctor` reports, when an installed harness lies outside the version range its adapter declares as tested (design review finding [harness version health check](../reviews/review-2026-10-15.md#harness-version-health-check)).
- **Execution recovery**: inspect the attempt's original domain, last observation, unclosed dispatcher grants, pending publication, retained scopes and permitted actions through `kora node`/`kora run`. Request `kora reconcile … --action observe` or `stop` with the expected version/domain. For a permanently lost host, establish actual decommissioning/termination and closure of all dispatch and publication authority before recording `confirm_stopped` with evidence. No elapsed-time or force-retry shortcut exists; stale requests reload the version (`API002`). Cost remains last-known and partial until observation recovers.
- **Storage consistency**: `kora db verify-storage` walks artifact/segment/request/derived-result references and required active/recovery holds against the blob store and reports missing or orphaned blobs (ADR-0018).
- **Backup and restore**: back up the metadata database first, then the blob store; on restore apply in the same order. Blobs are immutable and content-addressed, so the blob store is backed up by copying new objects: the `artifacts/` directory for `local`, bucket replication or versioning of the S3-compatible service (or a copy with its own tooling) for `s3`. Rows whose referenced bytes are physically missing are marked `missing` by `verify-storage --repair`, distinct from intentional retention expiry; neither state can be silently replaced with current data (ADR-0018). Approval channels search for an existing comment carrying the request id before posting, so a restore does not duplicate change-request comments; the publish plan and `open_change_request` are idempotent on their natural keys (protocols.md section 4), so an attempt finalised again after a restore returns the same branch and change request; triggers replay from `trigger_binding.last_fired_key`, so a restored cron does not double-fire.
- **VCS polling**: the approval channel and the built-in sensors poll with exponential back-off and respect the code host's rate-limit headers; results and worker logs are redacted of push URLs and tokens (credential helpers, never URL-embedded secrets).
