# Pi execution profile

[ADR-0030](../../docs/decisions/0030-pi-sdk-candidate-process.md) selects a direct `pi` adapter for MVP under [ADR-0004](../../docs/decisions/0004-harness-adapters-over-vendor-sdks.md). This profile defines its trusted local installation, minimum coding capabilities and qualification. The [upstream source record](../research/pi-sdk-profile-2026-11-27.md) identifies the pinned SDK used to establish feasibility. The private launch and Bash witnesses cover the first executable deliveries. Ordinary installed activation remains pending.

The existing [harness and runner contracts](protocols.md#3-harness-adapter-fr-21-fr-33-fr-66-fr-91-dd-27) govern session requests, events, limits and finalization. [ADR-0009](../../docs/decisions/0009-target-repository-trust-boundary.md), [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md) and [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) govern trust, placement, unresolved work and deadlines. The version-one [execution request](execution-request.md) remains the source of sealed workload inputs. Operators select a trusted Pi profile at installation. Authors use the existing `harness` and `model` fields. Without a registered Pi adapter the current unknown-harness refusal (`IR018`) applies. The shared validator and runner require the same qualified selection, and independently check their own trust boundaries before authorizing their operations.

## Installation and private launch

- One selected installation fixes the candidate platform, exact Node runtime, locked official Pi Coding Agent SDK and dependency closure, packaged bridge, and trusted launch configuration. `kora doctor` and worker startup check version and identity. The launcher independently checks the actual executable, SDK/bridge installation inputs and reviewed role recipe before starting the attempt process. Pinning a version label without checking the installed bytes is insufficient. The candidate checkout cannot resolve or substitute any of these inputs.
- The local runtime binds the session child and any managed shell execution to the exact prepared checkout, attempt, selected roles and verified placements. The existing runtime launcher and fence own dispatch and stopping. The SDK child has a one-shot start. Each shell call has separate per-call admission under the same attempt owner after its own matched Policy decision. The bridge has no authority to supply an executable, choose its role, acquire other credentials, publish Git refs, decide Policy, or report trusted closure. Launch refuses cross-attempt, role, checkout or selected-installation substitution before credential delivery.
- Construct each role's environment and descriptors explicitly. The Pi child receives only its owned control pipes and the intended standard error drain. The shell role receives a separate constructed environment and ordinary command I/O. Neither inherits a supervisor environment, API/provider/publication credentials from other roles, unrelated descriptors, or access furnished by the launcher to trusted control state.
- The launch and validation owners use the same definitions for applicable fields and reserved environment names. Reject collisions and authored overrides of the adapter, runtime and secret owners, including applicable Pi, Node, loader, shell startup, HOME, temporary directory, proxy, CA and TLS controls, even if intentionally unset. The native declaration uses [the reservation grammar](validation-facts.md#6-native-candidate-environment-reservations) with required case spellings. Configuration, environment or placement refusal precedes secret resolution or release to the child.

The initial binding uses one installed physical Anthropic model and its pinned HTTPS model endpoint. The owned model route validates the destination before each credential-bearing request and refuses redirects without forwarding either key or prompt. Reject OAuth-shaped credentials that would select the SDK's bearer path, as well as model fallbacks, virtual routing, ambient credentials and authored endpoint overrides. A response reporting a different model cannot establish success for the configured model. The test-owned scripted loopback binding is available only in qualification. These controls apply to the SDK model route independently of [local runtime capabilities](protocols.md#2-runtime-fr-81). Processes run under the local trust assumptions in ADR-0016, including the same-user residual.

### Credential handoff and prompt admission

Use the installed reference through the [file secret provider](protocols.md#6-secrets-fr-101) with the original sealed request and active attempt authority. After exec and verification of placement and live registration, resolve the key once for the attempt and admit it to the attempt's masking scope before reveal. The runtime owns an authenticated one-use handoff over the private channel bound to the exact attempt, SDK role and verified child registration. The recipient accepts only the complete bounded credential frame for that registration and installs the key in memory. Keys stay out of argv, environment, files, prompts and shell inputs.

The owner fences reveal and delivery with the same stop and cutoff authority as the launch. Check the original binding, current execution authority, expiry and stop before and after each wait, including provider resolution or writable readiness, and serialize every nonblocking write with the stop fence. An incomplete frame grants no credential or prompt authority. On loss, cancellation, expiry or an abandoned partial transfer, discard any unsent credential bytes, revoke the channel and stop the original process under the existing termination rules. A complete handoff delivered before stop cannot be rolled back. Prompt dispatch requires its own one-use admission under the same authority and cutoff after readiness and credential handoff. It rechecks the fence before and after waits and at each write. Replayed handoffs or confirmations convey no authority to send a new prompt.

Keep the existing lease and attempt recovery rules, process ownership and charged resources through physical stop or unresolved closure. Retain masking through dependent output drain and sanitization. Recovery joins the same owned attempt where authorized and never persists, re-resolves or resends the key on handoff replay. These are profile-specific obligations of the existing launcher and runner.

## Session inputs and owned tools

Construct the SDK session with explicit cwd and agent placement, in-memory settings, credentials and session, an explicit physical model, and a resource loader with no ambient sources. Use the rendered and sealed prompt literally, and append any admitted `system_prompt_append` to the installation's fixed instructions. Omitted `model` selects the fixed installed physical model. An explicit value must match that binding exactly. Disable ambient project or home instructions and settings, extensions, skills, prompt expansion, package discovery, project migrations, catalog refresh, telemetry, cache warming and any other background model calls. The production profile excludes MCP, hosted tools, subagents and native resume. The initial registered production inventory contains read, edit, write and shell. Ready verification checks its actual model-visible, registered and callable inventories, including inactive or indirectly callable entries and the owned definitions and callbacks. A mismatch prevents prompting.

The sealed workload, shared validation and [first-slice refusals](first-slice.md#refusal-contract) still apply. The profile admits an absent `permission_mode` or exactly `dont_ask`, with the fixed runner Policy path for every tool effect in both cases. Only an absent `sandbox` is admitted. It uses the existing local runtime controls and asserts no native sandbox. Refuse all other explicit permission modes and any explicit sandbox value with `IR028`, including values supplied by trusted defaults. Preserve the shared first-slice default and no-op rules. `resume` remains unsupported for this profile. A fresh attempt starts an empty SDK session, while worker adoption reconnects to the original runtime attempt only under the shared adoption rules. The scoped, masked [AgentSession](artifacts/AgentSession.md) follows kora's retained history contract. It contains no native session authority for loading or replaying an SDK session.

### Required tool policy

The installed SDK supplies the invocation id and schema-checked arguments to an owned callback. The callback prepares a bounded typed action. A one-use positive Policy response for that exact attempt, session, request and action is required before execution. The runner dispatches existing `Policy.decide` with both policy layers and required protected-path checks. A new request, changed arguments or an expired or stopped attempt cannot use an earlier decision. Explicit deny, malformed data, loss of the channel, unavailable decision, timeout or cancellation preserves refusal. An absent or late allow never authorizes a tool. Unexpected tool, alternate command or child-context routes and any effect without a matched decision fail the session through the existing enforcement and first-cause boundary. The runner owns safe `permission_denied` observations and the existing failure dispositions.

| SDK tool | Policy tool and extracted input | Effect and qualification |
| --- | --- | --- |
| `read` | `Read` | The bounded path binds the action. This adds no Policy pattern extractor or complete `other_tool` coverage. |
| `edit` | `Edit`, admitted lexical workspace pathname in `file_path` | Apply the shared path condition and bind the admitted target to the edit. |
| `write` | `Write`, admitted lexical workspace pathname in `file_path` | Apply the shared path condition and bind the admitted target to the creation or write. |
| `bash` | `Bash`, exact `command` | Existing shell and shell-indirection rules apply before the runtime launches its verified shell. Pi's native detached Bash and spill path are excluded. |

The Policy request uses `harness: pi` and the runner's trusted workspace. For edit and write, send the admitted lexical workspace pathname as `file_path`. Under the [shared path condition](protocols.md#the-allow_deny-policy-issue-233), Policy compares the lexical and kernel-resolved paths when protected paths are set or a policy layer has a pattern governing that tool. Denies and protected paths match either form under the shared rules. Bind the resolved pathname actually used for Policy matching together with the physical target identity and verify that pair across the actual open and effect. For a new destination, bind the resolved destination pathname to the physical parent directory identity and leaf name. Refuse when the bound target differs or the match cannot be proved. If the path condition is false, apply the required one-use Policy decision with no pathname check and have the owned opener independently verify and bind the target, using the same parent and leaf binding for creation. Read retains its admitted target binding and existing pattern semantics. Refuse ambiguity, escapes and changed bindings before any file effect. No second SDK expansion runs at the open. [Owner decision](https://github.com/realkarych/kora/issues/1930#issuecomment-7205411558)

Qualify a successful edit and a successful creation when the path condition is false. For a deny or protected-path match on either lexical or resolved aliases, confirm unchanged targets. Exercise a symlink swap confined to Policy's resolution, the same object under a changed resolved pathname, and a changed parent directory identity for file creation. Verify refusal before effect when the checked pair differs or its match cannot be proved. Also exercise hard-link refusal, relative-path escapes and SDK spellings involving `@`, `~` or Unicode whitespace.

Shell executes the exact admitted command with the bound working directory and constructed environment in the candidate domain. Shell, pipes, spill storage and descendants remain owned by the runtime through actual closure. An allowed command can still do what its operating-system and external permissions allow. Policy and a working-directory check alone do not establish hostile-code containment.

A separate effect-free fact may discharge only subagent context under [configured coverage](validation-facts.md#selected-pi-admission). Qualification proves the exact installation cannot create a child agent even through indirect producer routes. Primary coverage remains independent and is declared only after exact verified coverage in every selected branch. The production profile admits no hosted or MCP coverage and therefore cannot satisfy a nonempty allow array or another requirement for all primary kinds. A real controlled MCP check crosses the same before-effect boundary via a test-owned tool. That configuration cannot be selected for ordinary execution and contributes no production coverage.

## Observation, bounds and release

Frames are private, strictly typed and correlated. The runner and child bound frame size, sequence tracking, concurrent or pending calls, cumulative native context and response bytes, adopted state, output and each queue or native accumulator before retaining resources. Ownership begins before launch and includes output draining and resource retention while settlement is unknown. The implementation assigns fixed admissible bounds and demonstrates them against the pinned SDK for finite output, oversized or malformed frames and slow or closed peers. Limits and stop control remain usable when event, usage or diagnostic output is pressured or drops. Overflow uses the existing bounded refusal and stop behavior.

Normalise SDK events, confirmed tool completion and output candidates into the shared runner contracts. Match terminal evidence to the exact run after the SDK has settled. Prompt acceptance, interim agent-end events, loss of a reply or exit alone do not establish success or an accepted artifact. For a selected [StructuredOutput producer](artifacts/StructuredOutput.md#35-producer-boundaries), use only the bounded text blocks of the completed terminal assistant message from the exact settled successful run. Concatenate those blocks in their original order without adding text. The complete text must be exactly one strict JSON value. Earlier tool-turn messages and partial deltas supply no fallback. Refuse prose, fences, trailing documents, duplicate keys and nonfinite numbers. Stop flags, missing text and absent native values cannot supply a JSON null, while the literal JSON text `null` remains governed by the saved schema. Missing, oversized or invalid required output follows the existing `artifact_invalid` path. The result is only a candidate for the saved effective schema and existing acceptance and publication owners. This text path adds no synthetic tool or Policy exception. Lost tool or terminal replies preserve uncertainty about effects. They cannot authorize redispatch of the call or replacement of the attempt.

Carry confirmed token observations per observed model from bounded SDK message evidence. Preserve deduplication, the installed price snapshot if present, known gaps and the shared `complete`, `partial` and `unavailable` semantics. A result or aggregate usage count alone cannot demonstrate completeness or zero cost. Preserved provider-limit and internal-retry observations follow [ADR-0024](../../docs/decisions/0024-provider-limits-as-non-agent-failures.md) and the [usage contract](data-model.md#7-usage-records-and-completeness-fr-91). Native retries belong to the reviewed installation, are bounded by the inherited attempt, and cannot supply silent retries, new retry policy or a renewed deadline.

The runner owns stop latching, deadlines and the first cause. SDK abort and disposal are cooperative. The runtime interrupts, escalates and reaps the child and every owned shell process or descendant under the existing stop boundary. Retain attempt and capacity ownership on unresolved closure. Lost results, cancellation, worker adoption and orderly shutdown never synthesize accepted outputs, publication or physical release. Duplicate and delayed observations keep the existing replay and uncertainty rules.

Trusted runner diagnostics carry only approved identifiers, safe states and bounded counters. The host owns launch/refusal, missing-decision, usage-gap and release diagnostics. Runner bindings use the existing `runner.agent` and adapter diagnostics ownership. Raw model messages, credential values, arguments, file paths and untrusted stderr stay out of logs at every level. Drain untrusted output with fixed bounds, retaining masks through dependent sanitization. The [observability contract](observability.md#7-component-coverage-and-activation) governs fields, masking, output loss and stream separation.

The implementation records the selected input bytes and revisions, supported Linux/macOS provider configurations under the repository's platform rules, exact observing component and result for each case below. Recorded streams exercise normalization. Live routing and release require the real interface. Ordinary graph execution also needs installed selection and the existing shared producers.

| Evidence boundary | Required checks before its activation |
| --- | --- |
| Pinned SDK and owned runtime launch | Start the real pinned SDK and bridge with the scripted loopback model. Prove exact profile and tool inventory, placement and target binding, refusal of substituted inputs before key delivery, stop between verified placement and disclosure, stop or expiry during a partial frame, separate prompt refusal when stopped after key delivery, rejection of OAuth-shaped credentials, and no ambient files/resources/credentials or background calls. Exercise a trusted origin that redirects and assert zero key or prompt at the target. Verify safe diagnostic channels and rejection of a provider-reported model mismatch. Qualify claimed platforms without inheriting the deferred broad macOS runtime campaign. |

Exercise malformed, stale, missing and late replies, and a cancelled decision. Exercise a real test-owned MCP tool and verify the separate production inventory. Both validate and deploy must reject unsupported coverage, permission modes and sandbox settings with the same code and safe field path before effects. Exercise omitted permission mode and explicit `dont_ask` through the same Policy gate. |
| Runner, results and capacity | Prove `max_events` and deadline enforcement, strict terminal JSON selection and saved candidate validation. Prove that valid JSON in an earlier assistant message cannot satisfy missing or invalid terminal output. Also verify observed complete and incomplete usage, provider-limit and internal-retry traces, bounded streaming and native state, and abort/escalation with real shell-descendant and pipe release. Through ordinary deploy/trigger and the existing HTTP, CLI and MCP operations, independently qualify the local Git agent → command gate → CLI approval flow. Observe the accepted commit and matching gate input, bound approval, same-run output/usage history, and exact release and adoption. Run the separate documented operator compatibility probe against the pinned production Anthropic binding outside deterministic CI. Metadata integration keeps both database legs under the repository's existing rules. |

Pi owns its SDK bridge, adapter, exact native evidence and provider conformance. The common runner and Policy path (#199 and #233), trusted validation facts (#549), sealing and custody (#1453 and #1640), Scheduler and terminal acceptance (#1448 and #1472), and existing public surfaces retain their authority. Ship independently usable deliveries in the approved [implementation order](../../docs/implementation-plan.md#pi-mvp-deliveries). ### Tools-disabled launch witness

The [test-owned stage](../../docs/development.md#local-pi-sdk-launch-qualification) compiles the bridge and binds the locked installation to an inventory produced before the witness. The launch checks the inventory against actual bytes and rechecks identities before activation and fixture key delivery. It uses the existing gated process, the anchored checkout, an exact invocation, constructed environment and borrowed stdio. The runner sends the complete command data before it sends a separate activation with a one-use challenge. The bridge acts only on activated data. Each reply must carry the challenge of its initiating command. Before accepting the reply, the runner rechecks the anchored checkout and original process registration. The witness verifies that the real SDK sends a single request to its reserved loopback origin with the selected model and an empty tool list. It refuses ambient resources, stale or unmatched control frames, altered installation inputs, redirects and responses exceeding the fixture limit. The process owner establishes physical reap and output settlement after a positive, failed, lost or interrupted SDK reply. The fixture checks its owned checkout, home and temporary paths after normal and abrupt process exit.

The fixture admits one prompt of at most 32 KiB, one pending control transition, 64 KiB private frames and at most 256 KiB decoded model response before the SSE decoder. These bounds qualify the scripted witness. Ordinary Pi selection and the remaining tool, usage, managed model, shared workflow and full native-accumulation evidence remain at their respective activation boundaries above.

### Private Bash qualification

[Issue #1938](https://github.com/realkarych/kora/issues/1938) adds a separate test-owned selection with one SDK custom tool, `bash`. The ready check binds its definition, callback, active SDK wrapper and schema. The bridge admits only the selected model and requires the complete original tool-use event sequence through response EOF before comparing the exact native ID and string command with the SDK callback. The test-owned runner calls the existing Policy provider with both policy layers and the bound checkout. It consumes one matching decision through the scoped shell admission. The bridge and shell keep their own registrations and waits under the same adopted-child reaper. Revoking the channel starts settlement of the original bridge independently of shell settlement.

The one pending request binds the original registration, prompt challenge, native call ID, fresh call challenge and command. The socket receive path accounts for delivered bytes and closure before the sole reader resumes. While the call is pending, any bytes beyond the accepted call revoke authority, including bytes delivered with that call. Loss, denial, expiry and cancellation also revoke pending authority. Stopping a call after activation retains the original owner through physical process and pipe settlement. The SDK receives the masked, JSON-encoded exit code and stdout for the original request after settlement. A separate continuation activation supplies a fresh challenge for the terminal reply, whose consumption rechecks the original binding and deadline. The command data occupies at most 32 KiB and each private frame remains limited to 64 KiB. The existing 8 KiB raw and encoded shell bounds apply.

The bridge checks each physical Messages request body within 256 KiB before network transfer. It verifies the selected endpoint, method and model, refuses redirects and excludes the key from decoded body content, including tool history. Immediately before each Bash-profile request submission, it checks the native cutoff conservatively translated from the inherited runner deadline. One continuation may carry the original call and exact settled result. Both responses share a 256 KiB limit before decoding and the terminal response requires its own complete ordered, model-matched assistant message with an `end_turn` stop. The independent terminal witness also applies to the single-request text profile.
