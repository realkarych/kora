# Pi execution profile

[ADR-0030](../../docs/decisions/0030-pi-sdk-candidate-process.md) selects a direct `pi` adapter for MVP under [ADR-0004](../../docs/decisions/0004-harness-adapters-over-vendor-sdks.md). This profile defines its trusted local installation, minimum coding capabilities and qualification. The [upstream source record](../research/pi-sdk-profile-2026-11-27.md) identifies the pinned SDK used to establish feasibility. Executable qualification and installed activation remain pending.

The existing [harness and runner contracts](protocols.md#3-harness-adapter-fr-21-fr-33-fr-66-fr-91-dd-27) govern session requests, events, limits and finalization. [ADR-0009](../../docs/decisions/0009-target-repository-trust-boundary.md), [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md) and [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) govern trust, placement, unresolved work and deadlines. The version-one [execution request](execution-request.md) remains the source of sealed workload inputs. Operators select a trusted Pi profile at installation. Authors use the existing `harness` and `model` fields. Without a registered Pi adapter the current unknown-harness refusal (`IR018`) applies. The shared validator and runner require the same qualified selection, and independently check their own trust boundaries before authorizing their operations.

## Installation and private launch

- One selected installation fixes the candidate platform, exact Node runtime, locked official Pi Coding Agent SDK and dependency closure, packaged bridge, and trusted launch configuration. `kora doctor` and worker startup check version and identity. The launcher independently checks the actual executable, SDK/bridge installation inputs and reviewed role recipe before starting the attempt process. Pinning a version label without checking the installed bytes is insufficient. The candidate checkout cannot resolve or substitute any of these inputs.
- The local runtime binds the session child and any managed shell execution to the exact prepared checkout, attempt, selected roles and verified placements. The existing runtime launcher and fence own dispatch and stopping. The bridge has no authority to supply an executable, choose its role, acquire other credentials, publish Git refs, decide Policy, or report trusted closure. Launch refuses cross-attempt, role, checkout or selected-installation substitution before credential delivery.
- Construct each role's environment and descriptors explicitly. The Pi child receives only its owned control pipes and the intended standard error drain. The shell role receives a separate constructed environment and ordinary command I/O. Neither inherits a supervisor environment, API/provider/publication credentials from other roles, unrelated descriptors, or access furnished by the launcher to trusted control state.
- The launch and validation owners use the same definitions for applicable fields and reserved environment names. Reject collisions and authored overrides of the adapter, runtime and secret owners, including applicable Pi, Node, loader, shell startup, HOME, temporary directory, proxy, CA and TLS controls, even if intentionally unset. The native declaration uses [the reservation grammar](validation-facts.md#6-native-candidate-environment-reservations) with required case spellings. Configuration, environment or placement refusal precedes secret resolution or release to the child.

The initial binding uses one installed physical Anthropic model and its pinned catalog endpoint. A dedicated API key comes from the existing [file secret provider](protocols.md#6-secrets-fr-101). The runner checks the selected placement and registers the secret for masking before delivery only to the selected child's model runtime in memory. Keys stay out of argv, environment, files, prompts and shell inputs. Model fallbacks, virtual routing, OAuth, ambient credentials and authored endpoint overrides are refused. The test-owned scripted loopback binding is available only in qualification. [Local runtime capabilities](protocols.md#2-runtime-fr-81) govern filesystem and network claims. Processes run under the local trust assumptions in ADR-0016, including the same-user residual.

## Session inputs and owned tools

Construct the SDK session with explicit cwd and agent placement, in-memory settings, credentials and session, an explicit physical model, and a resource loader with no ambient sources. Use the rendered and sealed prompt literally, and append any admitted `system_prompt_append` to the installation's fixed instructions. Check the exact proposed `model` against the installed binding. Disable ambient project or home instructions and settings, extensions, skills, prompt expansion, package discovery, project migrations, catalog refresh, telemetry, cache warming and any other background model calls. The production profile excludes MCP, hosted tools, subagents and native resume. The initial registered production inventory contains read, edit, write and shell. Ready verification checks its actual model-visible, registered and callable inventories, including inactive or indirectly callable entries and the owned definitions and callbacks. A mismatch prevents prompting.

The sealed workload, shared validation, existing permission and sandbox contracts, and [first-slice refusals](first-slice.md#refusal-contract) still apply. Refuse unsupported controls and authored configuration instead of substituting an unprotected mode. `resume` remains unsupported for this profile. A fresh attempt starts an empty SDK session, while worker adoption reconnects to the original runtime attempt only under the shared adoption rules. The scoped, masked [AgentSession](artifacts/AgentSession.md) follows kora's retained history contract. It contains no native session authority for loading or replaying an SDK session.

### Required tool policy

The installed SDK supplies the invocation id and schema-checked arguments to an owned callback. The callback prepares a bounded typed action. A one-use positive Policy response for that exact attempt, session, request and action is required before execution. The runner dispatches existing `Policy.decide` with both policy layers and required protected-path checks. A new request, changed arguments or an expired or stopped attempt cannot use an earlier decision. Explicit deny, malformed data, loss of the channel, unavailable decision, timeout or cancellation preserves refusal. An absent or late allow never authorizes a tool. Unexpected tool, alternate command or child-context routes and any effect without a matched decision fail the session through the existing enforcement and first-cause boundary. The runner owns safe `permission_denied` observations and the existing failure dispositions.

| SDK tool | Policy tool and extracted input | Effect and qualification |
| --- | --- | --- |
| `read` | `Read`, runner-local bounded path | A read through the owned callback. An exposed read does not by itself qualify the complete `other_tool` class. |
| `edit` | `Edit`, `file_path` from the SDK's `path` | The file-edit family and protected-path checks apply to the target actually edited. |
| `write` | `Write`, `file_path` from the SDK's `path` | The same checks apply to the target actually created or written. |
| `bash` | `Bash`, exact `command` | Existing shell and shell-indirection rules apply before the runtime launches its verified shell. Pi's native detached Bash and spill path are excluded. |

The Policy request uses `harness: pi` and the runner's trusted workspace. File paths are resolved to the exact admitted workspace targets before evaluation. Use the same targets for effect, with no second SDK expansion, and refuse ambiguity, escapes or changed binding before mutation. Qualification checks aliases, including symlinks or hard links that could change the affected object, relative-path escapes, and SDK spellings involving `@`, `~` or Unicode whitespace. Shell executes the exact admitted command with the bound working directory and constructed environment in the candidate domain. Shell, pipes, spill storage and descendants remain owned by the runtime through actual closure. An allowed command can still do what its operating-system and external permissions allow. Policy and a working-directory check alone do not establish hostile-code containment.

A separate effect-free fact may discharge only subagent context under [configured coverage](validation-facts.md#selected-pi-admission). Qualification proves the exact installation cannot create a child agent even through indirect producer routes. Primary coverage remains independent and is declared only after exact verified coverage in every selected branch. The production profile admits no hosted or MCP coverage and therefore cannot satisfy a nonempty allow array or another requirement for all primary kinds. A real controlled MCP check crosses the same before-effect boundary via a test-owned tool. That configuration cannot be selected for ordinary execution and contributes no production coverage.

## Observation, bounds and release

Frames are private, strictly typed and correlated. The runner and child bound frame size, sequence tracking, concurrent or pending calls, cumulative native context and response bytes, adopted state, output and each queue or native accumulator before retaining resources. Ownership begins before launch and includes output draining and resource retention while settlement is unknown. The implementation assigns fixed admissible bounds and demonstrates them against the pinned SDK for finite output, oversized or malformed frames and slow or closed peers. Limits and stop control remain usable when event, usage or diagnostic output is pressured or drops. Overflow uses the existing bounded refusal and stop behavior.

Normalise SDK events, confirmed tool completion and output candidates into the shared runner contracts. Match terminal evidence to the exact run after the SDK has settled. Prompt acceptance, interim agent-end events, loss of a reply or exit alone do not establish success or an accepted artifact. A qualified terminal result yields only the relevant output candidate for the existing schema and publication/acceptance owners. Lost tool or terminal replies preserve uncertainty about effects. They cannot authorize redispatch of the call or replacement of the attempt.

Carry confirmed token observations per observed model from bounded SDK message evidence. Preserve deduplication, the installed price snapshot if present, known gaps and the shared `complete`, `partial` and `unavailable` semantics. A result or aggregate usage count alone cannot demonstrate completeness or zero cost. Preserved provider-limit and internal-retry observations follow [ADR-0024](../../docs/decisions/0024-provider-limits-as-non-agent-failures.md) and the [usage contract](data-model.md#7-usage-records-and-completeness-fr-91). Native retries belong to the reviewed installation, are bounded by the inherited attempt, and cannot supply silent retries, new retry policy or a renewed deadline.

The runner owns stop latching, deadlines and the first cause. SDK abort and disposal are cooperative. The runtime interrupts, escalates and reaps the child and every owned shell process or descendant under the existing stop boundary. Retain attempt and capacity ownership on unresolved closure. Lost results, cancellation, worker adoption and orderly shutdown never synthesize accepted outputs, publication or physical release. Duplicate and delayed observations keep the existing replay and uncertainty rules.

Trusted runner diagnostics carry only approved identifiers, safe states and bounded counters. The host owns launch/refusal, missing-decision, usage-gap and release diagnostics. Runner bindings use the existing `runner.agent` and adapter diagnostics ownership. Raw model messages, credential values, arguments, file paths and untrusted stderr stay out of logs at every level. Drain untrusted output with fixed bounds, retaining masks through dependent sanitization. The [observability contract](observability.md#7-component-coverage-and-activation) governs fields, masking, output loss and stream separation.

## Qualification and activation

The implementation records the selected input bytes and revisions, supported Linux/macOS provider configurations under the repository's platform rules, exact observing component and result for each case below. Recorded streams exercise normalization. Live routing and release require the real interface. Ordinary graph execution also needs installed selection and the existing shared producers.

| Evidence boundary | Required checks before its activation |
| --- | --- |
| Pinned SDK and owned runtime launch | Start the real pinned SDK and bridge with the scripted loopback model. Prove exact profile and tool inventory, placement and target binding, refusal of substituted inputs before key delivery, no ambient files/resources/credentials or background calls, and safe diagnostic channels. Qualify claimed platforms without inheriting the deferred broad macOS runtime campaign. |
| Policy and effects | In the exact profile exercise qualified tool kinds and modes, namespace deny precedence, allowed shell and file effects, unchanged denied targets, alias/rebinding cases, malformed, stale, missing and late replies, and a cancelled decision. Exercise a real test-owned MCP tool and verify the separate production inventory. Both validate and deploy must reject unsupported coverage with the same code and safe field path before effects. |
| Runner, results and capacity | Prove `max_events` and deadline enforcement, proper output candidate validation, observed complete and incomplete usage, provider-limit and internal-retry traces, bounded streaming and native state, and abort/escalation with real shell-descendant and pipe release. Lose a tool reply after a possible admitted effect and lose a terminal SDK reply separately. Check that ownership holds without duplicate dispatch or premature replacement or release. Exercise startup failure, cancellation, shutdown, truthful uncertain cleanup and same-attempt adoption. |
| Ordinary installed workflow | Check installed selection and doctor with exact compatible and incompatible inputs. Through ordinary deploy/trigger and the existing HTTP, CLI and MCP operations, independently qualify the local Git agent → command gate → CLI approval flow. Observe the accepted commit and matching gate input, bound approval, same-run output/usage history, and exact release and adoption. Run the separate documented operator compatibility probe against the pinned production Anthropic binding outside deterministic CI. Metadata integration keeps both database legs under the repository's existing rules. |

Pi owns its SDK bridge, adapter, exact native evidence and provider conformance. The common runner and Policy path (#199 and #233), trusted validation facts (#549), sealing and custody (#1453 and #1640), Scheduler and terminal acceptance (#1448 and #1472), and existing public surfaces retain their authority. Ship independently usable deliveries in the approved [implementation order](../../docs/implementation-plan.md#pi-mvp-deliveries). [Issue #1933](https://github.com/realkarych/kora/issues/1933) owns the first tools-disabled launch witness. Ordinary profile activation consumes the required evidence and shared producers when they exist. Full MVP Pi acceptance is separate from baseline first-slice readiness under [ADR-0001](../../docs/decisions/0001-own-control-plane.md#pi-mvp-qualification-amendment-of-2026-11-27).
