# First-slice capability and refusal contract

This is the first-slice contract adopted by [ADR-0001](../../docs/decisions/0001-own-control-plane.md), amended on 2026-10-23 under [#140](https://github.com/realkarych/kora/issues/140) and on 2026-11-11 under [#1357](https://github.com/realkarych/kora/issues/1357). [Implementation-plan work items](../../docs/implementation-plan.md#6-work-items) own its implementation. The full IR and protocol specifications continue to describe the complete language and future operations; this document determines what the first installation may execute. A contract requirement is not evidence of implemented behavior.

## Walking skeleton and narrowed depth

The [walking-skeleton amendment of ADR-0001](../../docs/decisions/0001-own-control-plane.md#walking-skeleton-amendment-of-2026-11-11), decided by the project owner on 2026-11-11 under [#1356](https://github.com/realkarych/kora/issues/1356) and [#1357](https://github.com/realkarych/kora/issues/1357), adds an intermediate milestone and narrows the slice.

### The skeleton is not first-slice-ready

The walking skeleton runs one graph end to end through the public surfaces on SQLite, with deliberately simple implementations. [The implementation plan](../../docs/implementation-plan.md#walking-skeleton) lists its steps. Every requirement of this contract that the narrowing below does not change applies when the skeleton's path is extended to slice acceptance. No existing test is skipped, deleted or weakened, and every integration test that touches the metadata database still runs on PostgreSQL and SQLite.

The architecture stays as designed. The worker reaches the metadata database only through the HTTP API, the agent session runs in its own runner on the local runtime, and the CLI and the stdio MCP server are thin clients over the shared API client. Under the [fakes contract](fakes.md), the fake harness runs only in the testing runner composed by `kora.testing`, so the skeleton's end-to-end run in CI uses the testing composition; `kora standalone` never imports it.

### Skeleton depth

The project owner fixed the following depth on 2026-11-11 ([graph and startup answers on #1357](https://github.com/realkarych/kora/issues/1357), [deploy answers on #1369](https://github.com/realkarych/kora/issues/1369)). Each item is extended to the requirements of this contract at slice acceptance.

- **Graph.** The fake agent returns a `StructuredOutput` and publishes no commit. The command node runs a fixed check without artifact inputs and produces its `CommandResult`. The human-input node presents the command result for a CLI response. The published `VcsRef`, command inputs and the approval binding to the published change of [the sequential chain](#shared-refusal-rules) are the first extensions toward slice acceptance.
- **Deploy writer.** One writer transaction finds or creates the graph by name, returns the existing version when the deployment digest is equal, and otherwise inserts the next version with the explicit empty saved resource record, the three digests and its read-admission record. The skeleton writer has no durable preparation record, preparation capacity, `Idempotency-Key` receipt, interrupted-request recovery, PostgreSQL migration fence or audit event. The transaction holds the namespace scope lock, so concurrent first deployments of one graph produce one graph row; equal-version reuse matches only an `active` version. The writer stores `deployed_by` as the authenticated owner, `resolved_digests` as the empty object, and `source_digest` as the hexadecimal value of `meta.source_digest` when the document carries one and otherwise the `ir_digest`, since a document without compiler provenance is its own source. Before it writes the read-admission record, the writer compares the stored row with the prepared values through the existing saved-value comparison. The read-admission record stores the exact measured resource transport width; its database input bound is the existing conservative record-and-overflow footprint of the observed layout on SQLite and, on PostgreSQL, the measured uncompressed widths of the IR, execution contract and resource datums plus the two metadata texts and 1,024 bytes for the fixed-width columns ([#1435](https://github.com/realkarych/kora/issues/1435)). The guarded publication writer of [#1369](https://github.com/realkarych/kora/issues/1369) replaces it at slice acceptance, together with the route-activation proofs of [first graph publication](api-and-agent-surface.md#first-graph-publication).
- **Deploy validation.** Deploy runs the existing IR passes, the first-slice configuration check and the CEL verification of execution-contract preparation. A minimal trusted facts producer supplies one fixed selection per installation: the configured harness name and the `local` runtime, with no namespace policy layers. A graph naming another harness or runtime is refused at deploy: an agent `config.harness` other than the configured one is `IR018` at that path, and a graph `runtime.runtime` or node `config.runtime` other than `local` is `IR028` at that path, because the installation does not implement it. The checks run every IR pass and the installation checks on the parsed document and merge their findings into one bounded collection. At skeleton depth, a pass that reports unresolved work while the merged collection holds no error makes the result incomplete, never valid; an unrelated error next to unresolved work yields the ordinary invalid collection, a simplification of the trusted-facts rule of [validation-facts.md section 7](validation-facts.md#7-public-disposition-of-incomplete-trusted-facts) that applies to the IR passes only. Preparation runs only on a valid, complete result, under fixed production budgets: the canonical, ASCII-escaped document is limited to 4 MiB, and a larger one is refused like any request over its byte limit; each declared output reserves the canonical document together with its type contracts against an output inventory budget of 4 MiB, so the four outputs of the skeleton graph admit a canonical document of about 0.8 MB; the CEL inventory admits at most 1,024 declarations, counting the graph root, bodies, nodes and type contracts together, and 64 triggers. A valid document that exceeds a preparation budget is validation that could not complete ([#1435](https://github.com/realkarych/kora/issues/1435)). The complete producers of [#549](https://github.com/realkarych/kora/issues/549) apply at slice acceptance.
- **Deploy route contract.** The request is `{graph, ir, resources}`, with `ir` the compiled graph as a JSON object, canonicalized by the server for the digests, and `resources` empty. A new version returns `201 Created` and an equal version `200 OK`; both bodies are `{graph_version_id, number, ir_digest, execution_contract_digest, deployment_digest, reused, warnings}`. A declared command file is an unavailable installation capability: the shared validator reports `IR028` at the command node's `config.resources` path, including for a single zero-byte file, while an empty `resources` list declares nothing, and deploy returns `API003` with that diagnostic before any write or storage call. Personal-token authentication, namespace authorization and the agreement of the route graph, the request graph, `ir.graph.id` and `ir.graph.namespace` apply as specified; only the route-activation proofs wait for the guarded writer.
- **Client input.** `kora deploy` and `kora_deploy` read the compiled graph as JSON only.
- **MCP dependency.** The stdio MCP server needs a new optional extra, `kora[mcp]`, with the existing `mcp` pin; the `claude` extra includes it. Without the extra, `kora mcp` refuses with a structured error naming the extra.
- **Manual start.** Because manual-start parameter evaluation pauses, the skeleton graph declares no parameters.

### Narrowed first-slice depth

These changes apply to the first slice itself, not only to the skeleton:

- **Adoption.** A restarted worker adopts a live session. This stays required for slice acceptance and is outside the skeleton.
- **Local process identity.** A local process is the original one while its pid is present with the recorded start time, read through the platform's ordinary process information, and a dispatch group has ended when no process remains in its process group. Extended platform process identity, for example the host, boot and PID-namespace binding of an identity and Darwin unique process ids, moves out of the first slice: new consumers in #196, #197 and work item 17 rely only on the process group and start time, and no first-slice work extends the extended facts. Identity checks already implemented in `kora.runner.identity` and their tests stay active. The receipt scopes that state what cleanup observed are unchanged.
- **Isolated crash and diagnostic file I/O and startup durability.** The startup durability contract of [protocols.md](protocols.md#startup-durability-contract-issue-615) and the [startup I/O contract](startup-io.md), whose implementation remains pending under [#616](https://github.com/realkarych/kora/issues/616), move out of the first slice entirely, as the project owner decided on 2026-11-11: a runner registers without the durable `runner.started` record and startup checkpoint, the registry's running state carries no startup reference, and the running-state journal of [#196](https://github.com/realkarych/kora/issues/196) begins with its first running-state record. A runner lost during startup is resolved from the registry and its process identity; where those leave doubt, the attempt stays unresolved under the existing rules. The per-root diagnostic and crash collector of [#700](https://github.com/realkarych/kora/issues/700) and [#701](https://github.com/realkarych/kora/issues/701) and the native filesystem barriers that qualify these mechanisms also move out. The other running-state journal obligations of #196 are unchanged.
- **macOS native qualification of the runner.** macOS stays a supported platform, and the ordinary local-runtime tests keep running on macOS. Native qualification of the runner on macOS moves out of the first slice: blocked-I/O barriers, disk-image pressure fixtures and the macOS evidence of the startup I/O contract.
- **Minimal doctor.** `kora doctor` checks the kora version, that the CEL binding loads, the configured harness binaries and their versions, that the metadata database is reachable and that the state root is writable. Free-space thresholds, full-disk behavior and Linux service-manager diagnostics move out of the first slice and have no first-slice owner; [#214](https://github.com/realkarych/kora/issues/214) records its earlier scope. The doctor does not replace worker or startup refusal, and the runtime's own Linux service-manager startup checks stay active.

Each moved item keeps its specification text as the contract for when its issue resumes.

## Refusal contract

The [same-call trusted validation-facts contract](validation-facts.md) defines the accepted lifetime and ownership of installation-aware input. Missing or inconsistent required protection facts cannot become normal validation success or admission; [section 7](validation-facts.md#7-public-disposition-of-incomplete-trusted-facts) defines their public failure disposition under #628. Concrete producer, normalization and consuming integration prerequisites remain under #549; authored first-slice checks and fake-provider facts do not establish them.

### Graph parameter evaluation support

On 2026-11-08 the project owner selected a bounded first-slice parameter profile under [#1075](https://github.com/realkarych/kora/issues/1075). The profile preserves draft-2020-12 meaning for admitted assertions, including supported object, array, primitive, numerical, equality and Boolean composition rules. It resolves permitted references from the original parameter root and exact saved type/reference closure. Shared bounded IR machinery may implement these rules. The StructuredOutput policy and its artifact-specific constraints carry no parameter authority.

Structural IR continues to represent the full parameter schema. First-slice support excludes executable `pattern`, `patternProperties`, `unevaluatedItems`, `unevaluatedProperties` and cycles in potential validation calls. A complete support check accounts for potentially executable locations, including referenced and alternative branches whose values may never be selected in a particular request. Apply the check to schema operations, leaving literal values and annotations as data. Established unsupported behavior in a well-formed schema is an installation finding under [the HTTP validation envelope](api-and-agent-surface.md#validation-envelopes). Existing more specific authored findings retain precedence.

An incomplete support or value check remains incomplete through negation, conditionals, alternatives and collection matching. Only completed evaluation proves whether submitted values satisfy an admitted schema. The [saved interpretation and resource ownership](data-model.md#graph-parameter-interpretation) and [manual-start envelope](api-and-agent-surface.md#admission-state-and-bounded-starts-adr-0020) govern new effects. [#1075](https://github.com/realkarych/kora/issues/1075) owns the exact keyword, reference, numeric, annotation and capacity tables, the charging schedule, the implementation and executable qualification before activation. The [saved parameter evaluation profile](data-model.md#saved-parameter-evaluation-profile) defines the binding's by-value member and reserved profile identity.

### Shared refusal rules

1. `IR028` is the installation feature-refusal error. #137 owns approval/output rules; #135 and its diagnostic sub-issue #207 own Diagnostic and HTTP mappings.
2. Allowed no-op values are exact: skills/subagents absent or []; hooks/mcp_servers absent or {}; trust_repo_config absent/false; graph.subgraphs absent/{}. Nonempty subgraph definitions are refused even when unused. Absent/empty node tool_policy adds no restriction but never removes the namespace layer; absent/[] node protected_paths never removes runtime paths. Explicit network_policy, including egress:[], remains a request for enforcement, not omission; local cannot promise enforced egress. The sole retained ADR-0009 agent-secret exception permits deployment when the namespace explicitly allows unenforced agent secrets, and permits start only with the separate explicit trigger opt-in. Its policy remains honestly unenforced and recorded through the run opt-in/capability facts. It waives only that agent-secret egress rule, never protected execution/resources, tool policy, secret-prefix/reserved-env checks, command require_network_enforcement or deferred MCP configuration. Outside that documented exception, unsupported explicit network policy is refused. Budgets allow omission only, never numeric zero as a no-op. Wrong types/null retain schema errors. Traverse operational typed fields recursively; informational meta, x- metadata and payload strings grant no feature authority. Omitted retry.max_attempts means one, as does explicit 1; dormant retry predicates still undergo full syntax/type checks. First-slice deployment topology is the minimal sequential chain: one agent, one command gate and one human-input approval, with dependencies/inputs consistent with that order. Refuse wider or parallel topology with `IR028`. The full IR still models arbitrary graphs. A publishing node fed from an earlier VcsRef remains deferred under #159; gate/approval consumption of the newly published VcsRef remains required.
3. A trusted installation feature inventory drives the same shared validator for validate and deploy. It does not come from submitted IR or an arbitrary user override. Startup validates bindings before serving; trigger/admission and worker dispatch re-check compatibility with the saved execution contract after installation changes, without reinterpreting or rewriting pinned work. Unsupported resumption refuses new side effects while existing recovery/closure obligations remain. The full schema continues to represent the full language.
4. Diagnostics identify the unavailable capability and its safe segmented document path through the [shared diagnostic contract](diagnostics.md), preserving its safe-location fallback, source metadata, collection bounds and omitted counts. Validation collects independent diagnostics; a rejected deploy returns API003 with details.errors[] under #135. The shared representation is the only diagnostic model.
5. Validate all defaults from standalone, kora.toml, bindings and namespace configuration as well as explicit fields. Optional no-op values, where allowed, are explicitly listed; no default may enable retries, budgets, notifications or repository configuration behind the slice restriction.
6. Preserve existing specific syntax/type/capability codes. Security fields cannot downgrade to warning merely because a feature is absent: implement and test the control, or refuse it. Use IR013 for malformed patterns and IR019 for unsupported namespace policy as today. A well-formed node-only security rule whose tool kind has no enforceable coverage becomes the new installation-refusal error instead of IR008; retain existing more specific hard-error codes when their conditions apply. IR008 remains only for non-security adapter warnings; optional security capabilities cannot be silently weakened under IR009. The [ADR-0009 amendment](../../docs/decisions/0009-target-repository-trust-boundary.md) supersedes permissive security-warning behavior.
7. Outside IR, reject unsupported trigger/configuration values before accepting a run or starting providers, with safe structured diagnostics. Never resolve secrets or perform publication while deciding support.

For first-slice installations, omitted `runtime.provider_retry`, an empty object and any schema-valid zero `max_wait` resolve to `{max_wait: "0s"}`, the disabled policy. This built-in default is chosen before the enabled-feature namespace/six-hour fallback. An explicit positive value or a positive default in namespace, binding, standalone or `kora.toml` configuration is refused before effects, never silently replaced. Malformed/null values retain schema errors. Save the normalized zero in the graph version's required [`execution_contract.retry_policies` binding](data-model.md#saved-disabled-retry-policies); its contract and deployment digests bind these values so a later installation upgrade cannot reinterpret omission. Numeric budget zero remains refused independently.

For first-slice `runtime.infrastructure_retry`, omission, `{}` and a valid object with omitted or explicit-one `max_attempts` resolve to a saved explicit `max_attempts: 1`: one initial attempt and zero replacements. Select this disabled built-in before enabled-feature fallback. Refuse any explicit or operator-configured count above one, including namespace, runtime/binding, standalone and `kora.toml` defaults, even when an author override, empty retry list or false predicate would hide it. Never clamp an enabling default silently. Preserve schema/type errors and static checking of every dormant field, including CEL predicates, and retain validated authored fields without allowing them to reinterpret the saved disabled policy after restart or feature activation. Store this normalized value with the node's ordinary and provider policies in the [saved disabled binding](data-model.md#saved-disabled-retry-policies). Run, attempt, admission and recovery consumers use that binding, including before the first attempt after an upgrade; missing saved policies fail closed under the graph-contract compatibility rules. No infrastructure predicate, backoff or counter increment can authorize a replacement in this slice.

The [infrastructure predicate static context](ir.md#71-expression-kinds-and-environments) gives every authored and applicable configured infrastructure predicate only the graph's typed `params` variable. Static checking includes configured predicates hidden by an override and preserves their diagnostic ownership.

Ordinary node and body policies use the same disabled binding, with explicit `max_attempts: 1` and exact authored dormant values. Deployment still validates all authored and configured layers, including settings hidden by overrides. Saved policy selection requires complete trusted inputs and preserves the refusal of nonempty subgraph definitions.

The sequential chain uses direct CLI approval bindings, as in [the accepted dependency-upgrade example](examples/dependency-upgrade.ir.yaml): the command consumes the agent's newly published `VcsRef`, and the human-input node consumes that same reference plus the command's `CommandResult`. Its `binds.vcs_ref` names the reference input and `binds.gate_digests` names the gate-result input. The approval covers the exact commit and result digest without synthesizing a ReviewBundle or requiring another agent. `approval_request.run_cost` remains independently attached. Existing artifact/approval reads expose the gate's provenance and protection result; approver authorization, current request/wait, expiry, `API006`, `candidate_moved` and the final fresh-head check remain unchanged.

`test_slice_one_approval_binds_published_change_and_gate` runs this chain on both databases and through CLI and API, checks those bindings and visible gate evidence, accepts only the authorized current matching response, rejects stale/mismatched responses and moved heads, and preserves `run_cost`. Work items 9/18/21 own this future integration evidence; the schema example alone is not a passing runtime test.

`test_slice_one_infrastructure_retry_defaults_are_disabled` covers omitted/empty/omitted-count/explicit-one values, configured defaults and saved normalization across restart/feature activation. `test_slice_one_rejects_infrastructure_retry_configuration` covers enabling explicit/default counts despite dormant lists/predicates and preserves malformed-field errors. The existing failure gate also asserts no infrastructure backoff/replacement/counter increment for failure or proved loss, preserving uncertainty and same-attempt adoption on both databases. Work items 3/11/20 own normalization/refusal, with 9/10/14/17 owning execution consequences.

`test_slice_one_retry_policies_survive_installation_upgrade` deploys omitted, empty and explicit-disabled policies, verifies the complete saved binding and both digests, then enables retry features and changes operator defaults across restart. New runs and attempts of the old version still use disabled policies without backoff, replacement or provider pause; the original IR stays unchanged. Different normalized sections have different deployment digests, and a missing binding refuses new effects rather than importing current defaults. The real deployment/database/scheduler/worker path runs on both databases; work items 3/5/9/10/11/17/20 own this pending gate.

## Included operation and parity contract

Retain every included API operation with one reachable CLI form and MCP selector. Ten slice tools: authoring `kora_reference` (deployed graphs/versions only), `kora_validate`, `kora_deploy`; operating `kora_trigger`, `kora_runs`, `kora_inspect`, `kora_approvals`, `kora_respond`, `kora_cancel`, `kora_admin` (reconcile only).

- Validate compiled IR; deploy graph versions; list/get graphs and versions.
- Trigger; list/get runs, with the existing bounded wait on the single-run read; events.
- Node read; attempts list/read; logs; artifact list/metadata/payload/lineage. Full stdio payload retrieval uses `kora_inspect` with `artifact_id` and explicit local `download_to`, requiring the trusted `kora mcp --download-root` launch directory, streaming the existing API payload into a safely created file within it and verifying full `payload_digest` SHA-256 and size from immutable metadata before publication and a bounded receipt; the trusted transfer budget (default 45s plus at most 10s response/cleanup) is paired with the client's wall timeout, with longer compatible settings required for slower maximum-sized transfers; the process admits at most four downloads with no waiting queue, retaining each slot until its owned resources are settled; small inline inspection is not its only payload path.
- Cancel run/node; approval list with run filter/read/respond; reconcile observe/stop/confirm_stopped.
- Make versions-list, attempts-list, artifact-lineage and approval-read selection explicit using existing commands/tools, without increasing the slice tool count.
- Preserve worker routes as their existing parity exclusion.
- Add exactly GET /healthz, GET /readyz and GET /metrics as infrastructure-probe exclusions. This grants no authentication exemption; #135 owns each authorization row and metrics/readiness exposure.
- Add kora_validate to the complete future inventory as well: the prior fifteen-tool cap becomes sixteen by this explicit amendment; existing compile/test author-side isolation stays unchanged. The first slice exposes only its ten tools.
- Skill-reference topic/example and skill error-table parity gates activate with product harness skills/reference delivery; slice 1 retains structured-error recovery hints and complete operation parity. Compile/test pair-presence assertions activate with those implementations. The ban on server-side Python compilation/scenario execution remains unconditional. Local doctor/plugins/conformance/standalone/db operations keep their documented local status, without inventing remote execution.
- Auth token semantics and error status decisions remain in #135/#141; MCP stdio forwards the configured identity unchanged.

## Local publication

Credential-free local publication preserves late authorization, a stable scoped principal, saved binding identity/revision, destination matching and recovery closure. The exact model, Git destination and authority rules are in [protocols.md](protocols.md#credential-free-local-publication). Only a trusted saved binding explicitly selects `local_credential_free`; missing credentials never do. #156 owns the models/method, #159 the executor/Git implementation, #195–197 the local command lifecycle and work item 17 the worker/API authority and durable provenance. A successful local bare-Git `finalize` supplies the published `VcsRef`; the worker uploads outputs/usage and requests `finishing` without a change-request call. Heartbeats, atomic result acceptance and runtime/dispatcher/publication closure remain required. Remote issuance and code-host operations activate only with the code-host implementation.
