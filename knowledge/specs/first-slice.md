# First-slice capability and refusal contract

This is the first-slice contract adopted by [ADR-0001](../../docs/decisions/0001-own-control-plane.md), amended on 2026-10-23 under [#140](https://github.com/realkarych/kora/issues/140). [Implementation-plan work items](../../docs/implementation-plan.md#6-work-items) own its implementation. The full IR and protocol specifications continue to describe the complete language and future operations; this document determines what the first installation may execute. A contract requirement is not evidence of implemented behavior.

## Refusal contract

1. `IR028` is the installation feature-refusal error. #137 owns approval/output rules; #135 and its diagnostic sub-issue #207 own Diagnostic and HTTP mappings.
2. Allowed no-op values are exact: skills/subagents absent or []; hooks/mcp_servers absent or {}; trust_repo_config absent/false; graph.subgraphs absent/{}. Nonempty subgraph definitions are refused even when unused. Absent/empty node tool_policy adds no restriction but never removes the namespace layer; absent/[] node protected_paths never removes runtime paths. Explicit network_policy, including egress:[], remains a request for enforcement, not omission; local cannot promise enforced egress. The sole retained ADR-0009 agent-secret exception permits deployment when the namespace explicitly allows unenforced agent secrets, and permits start only with the separate explicit trigger opt-in. Its policy remains honestly unenforced and recorded through the run opt-in/capability facts. It waives only that agent-secret egress rule, never protected execution/resources, tool policy, secret-prefix/reserved-env checks, command require_network_enforcement or deferred MCP configuration. Outside that documented exception, unsupported explicit network policy is refused. Budgets allow omission only, never numeric zero as a no-op. Wrong types/null retain schema errors. Traverse operational typed fields recursively; informational meta, x- metadata and payload strings grant no feature authority. Omitted retry.max_attempts means one, as does explicit 1; dormant retry predicates still undergo full syntax/type checks. First-slice deployment topology is the minimal sequential chain: one agent, one command gate and one human-input approval, with dependencies/inputs consistent with that order. Refuse wider or parallel topology with `IR028`. The full IR still models arbitrary graphs. A publishing node fed from an earlier VcsRef remains deferred under #159; gate/approval consumption of the newly published VcsRef remains required.
3. A trusted installation feature inventory drives the same shared validator for validate and deploy. It does not come from submitted IR or an arbitrary user override. Startup validates bindings before serving; trigger/admission and worker dispatch re-check compatibility with the saved execution contract after installation changes, without reinterpreting or rewriting pinned work. Unsupported resumption refuses new side effects while existing recovery/closure obligations remain. The full schema continues to represent the full language.
4. Diagnostics identify the unavailable capability and its safe segmented document path through the [shared diagnostic contract](diagnostics.md), preserving its safe-location fallback, source metadata, collection bounds and omitted counts. Validation collects independent diagnostics; a rejected deploy returns API003 with details.errors[] under #135. The shared representation is the only diagnostic model.
5. Validate all defaults from standalone, kora.toml, bindings and namespace configuration as well as explicit fields. Optional no-op values, where allowed, are explicitly listed; no default may enable retries, budgets, notifications or repository configuration behind the slice restriction.
6. Preserve existing specific syntax/type/capability codes. Security fields cannot downgrade to warning merely because a feature is absent: implement and test the control, or refuse it. Use IR013 for malformed patterns and IR019 for unsupported namespace policy as today. A well-formed node-only security rule whose tool kind has no enforceable coverage becomes the new installation-refusal error instead of IR008; retain existing more specific hard-error codes when their conditions apply. IR008 remains only for non-security adapter warnings; optional security capabilities cannot be silently weakened under IR009. The [ADR-0009 amendment](../../docs/decisions/0009-target-repository-trust-boundary.md) supersedes permissive security-warning behavior.
7. Outside IR, reject unsupported trigger/configuration values before accepting a run or starting providers, with safe structured diagnostics. Never resolve secrets or perform publication while deciding support.

For first-slice installations, omitted `runtime.provider_retry`, an empty object and any schema-valid zero `max_wait` resolve to `{max_wait: "0s"}`, the disabled policy. This built-in default is chosen before the enabled-feature namespace/six-hour fallback. An explicit positive value or a positive default in namespace, binding, standalone or `kora.toml` configuration is refused before effects, never silently replaced. Malformed/null values retain schema errors. Save the normalized zero in the graph version's required `execution_contract.retry_policies` map ([data-model section 11.1](data-model.md#111-graph-version-contract)); its contract and deployment digests bind these values so a later installation upgrade cannot reinterpret omission. Numeric budget zero remains refused independently.

For first-slice `runtime.infrastructure_retry`, omission, `{}` and a valid object with omitted or explicit-one `max_attempts` resolve to a saved explicit `max_attempts: 1`: one initial attempt and zero replacements. Select this disabled built-in before enabled-feature fallback. Refuse any explicit or operator-configured count above one, including namespace, runtime/binding, standalone and `kora.toml` defaults, even when an author override, empty retry list or false predicate would hide it. Never clamp an enabling default silently. Preserve schema/type errors and static checking of every dormant field, including CEL predicates, and retain validated authored fields without allowing them to reinterpret the saved disabled policy after restart or feature activation. Store this complete normalized policy in the same per-node `execution_contract.retry_policies` map. Run, attempt, admission and recovery consumers use that saved map, including before the first attempt after an upgrade; missing saved policies fail closed under the graph-contract compatibility rules. No infrastructure predicate, backoff or counter increment can authorize a replacement in this slice.

The sequential chain uses direct CLI approval bindings, as in [the accepted dependency-upgrade example](examples/dependency-upgrade.ir.yaml): the command consumes the agent's newly published `VcsRef`, and the human-input node consumes that same reference plus the command's `CommandResult`. Its `binds.vcs_ref` names the reference input and `binds.gate_digests` names the gate-result input. The approval covers the exact commit and result digest without synthesizing a ReviewBundle or requiring another agent. `approval_request.run_cost` remains independently attached. Existing artifact/approval reads expose the gate's provenance and protection result; approver authorization, current request/wait, expiry, `API006`, `candidate_moved` and the final fresh-head check remain unchanged.

`test_slice_one_approval_binds_published_change_and_gate` runs this chain on both databases and through CLI and API, checks those bindings and visible gate evidence, accepts only the authorized current matching response, rejects stale/mismatched responses and moved heads, and preserves `run_cost`. Work items 9/18/21 own this future integration evidence; the schema example alone is not a passing runtime test.

`test_slice_one_infrastructure_retry_defaults_are_disabled` covers omitted/empty/omitted-count/explicit-one values, configured defaults and saved normalization across restart/feature activation. `test_slice_one_rejects_infrastructure_retry_configuration` covers enabling explicit/default counts despite dormant lists/predicates and preserves malformed-field errors. The existing failure gate also asserts no infrastructure backoff/replacement/counter increment for failure or proved loss, preserving uncertainty and same-attempt adoption on both databases. Work items 3/11/20 own normalization/refusal, with 9/10/14/17 owning execution consequences.

`test_slice_one_retry_policies_survive_installation_upgrade` deploys omitted, empty and explicit-disabled policies, verifies their saved map and both digests, then enables retry features and changes operator defaults across restart. New runs and attempts of the old version still use disabled policies without backoff, replacement or provider pause; the original IR stays unchanged. Different normalized policy maps have different deployment digests, and a missing map refuses new effects rather than importing current defaults. The real deployment/database/scheduler/worker path runs on both databases; work items 3/5/9/10/11/17/20 own this pending gate.

## Included operation and parity contract

Retain every included API operation with one reachable CLI form and MCP selector. Ten slice tools: authoring `kora_reference` (deployed graphs/versions only), `kora_validate`, `kora_deploy`; operating `kora_trigger`, `kora_runs`, `kora_inspect`, `kora_approvals`, `kora_respond`, `kora_cancel`, `kora_admin` (reconcile only).

- Validate compiled IR; deploy graph versions; list/get graphs and versions.
- Trigger; list/get runs, with the existing bounded wait on the single-run read; events.
- Node read; attempts list/read; logs; artifact list/metadata/payload/lineage. Full stdio payload retrieval uses `kora_inspect` with `artifact_id` and explicit local `download_to`, requiring the trusted `kora mcp --download-root` launch directory, streaming the existing API payload into a safely created file within it and verifying full `payload_digest` SHA-256 and size from immutable metadata before publication and a bounded receipt; the trusted transfer budget (default 45s plus at most 10s response/cleanup) is paired with the client's wall timeout, with longer compatible settings required for slower maximum-sized transfers; the process admits at most four downloads with no waiting queue, retaining each slot until its owned resources are settled; small inline inspection is not its only payload path.
- Cancel run/node; approval list with run filter/read/respond; reconcile observe/stop/confirm_stopped.
- Make versions-list, attempts-list, artifact-lineage and approval-read selection explicit using existing commands/tools, without increasing the slice tool count.
- Preserve worker routes as their existing parity exclusion.
- Add exactly GET /healthz, GET /readyz and GET /metrics as infrastructure-probe exclusions. This grants no authentication exemption; #135 owns each authorization row and metrics/readiness exposure.
- Add kora_validate to the complete future inventory as well: the prior fifteen-tool cap becomes sixteen by this explicit amendment; existing compile/test author-side isolation stays unchanged. The first slice exposes only its ten tools.
- Skill-reference topic/example and skill error-table parity gates activate with product harness skills/reference delivery; slice 1 retains structured-error recovery hints and complete operation parity. Compile/test pair-presence assertions activate with those implementations. The ban on server-side Python compilation/scenario execution remains unconditional. Local doctor/plugins/conformance/standalone/db operations keep their documented local status, without inventing remote execution.
- Auth token semantics and error status decisions remain in #135/#141; MCP stdio forwards the configured identity unchanged.

## Local publication

Credential-free local publication preserves late authorization, a stable scoped principal, saved binding identity/revision, destination matching and recovery closure. The exact model, Git destination and authority rules are in [protocols.md](protocols.md#credential-free-local-publication). Only a trusted saved binding explicitly selects `local_credential_free`; missing credentials never do. #156 owns the models/method, #159 the executor/Git implementation, #195–197 the local command lifecycle and work item 17 the worker/API authority and durable provenance. A successful local bare-Git `finalize` supplies the published `VcsRef`; the worker uploads outputs/usage and requests `finishing` without a change-request call. Heartbeats, atomic result acceptance and runtime/dispatcher/publication closure remain required. Remote issuance and code-host operations activate only with the code-host implementation.

## Retention, tooling and lifecycle evidence

[#214](https://github.com/realkarych/kora/issues/214) owns local doctor integration, [#215](https://github.com/realkarych/kora/issues/215) provider CLI/installed-distribution evidence, and [#216](https://github.com/realkarych/kora/issues/216) retention integration. Each ships its applicable [observability activation](observability.md#7-component-coverage-and-activation), with bounded safe diagnostics on stderr and no configuration/secret values in refusal logs. Existing loader, conformance and database checks remain active; these new integration cases are pending implementation.

`test_installed_provider_supports_local_tooling` builds and installs a locally owned third-party distribution in an isolated environment and exercises production discovery, nonempty valid/invalid configuration, plugin/schema listing and conformance by protocol/name with explicit installed exercise fixtures and bounded fixture data ([command contract](protocols.md#local-conformance-command)), without checkout/core-test imports. Listing may inspect all providers; targeted conformance loads only the selected provider and fixture module. Core retains and invokes the selected factory, supplying its exact returned instance to command cases; the required `kora_conformance_adapter` fixture supplies the named typed preparation/configuration-binding/exercise/cleanup bridge, never replacement providers. The lifetime ABI remains blocked on accepted #231 design before #215 implementation/readiness. Core supplies its retained validated inputs; protocol-specific consumers receive the configuration, and `test_installed_provider_configuration_is_effective` proves two valid settings through observable behavior. The bridge and runtime evidence remain pending #215. Missing fixture/suite, same-name decoy/override and zero-test cases fail; configuration/exercise values stay out of all output, and the parent owns the process group and registers detached fixture domains before they become independently live. Bounded teardown/escalation verifies their closure on success, failure, cancellation and shutdown, even if pytest exits before teardown; unresolved resources fail with evidence. Serving processes never import fakes/testing/conformance modules or install packages automatically.

Retention snapshots finite resolved defaults into the run. Eligible payloads/projections expire without rewriting immutable history; active-version resources, unresolved execution/publication and recovery holds remain retained. With version retirement deferred, active-version resource growth is intentional durable state. `test_retention_lifetime` declares growing-history/shared-owner workloads and measures actual owner lookup/query work, storage calls/bytes, memory, tasks, database connections/cursors/locks, descriptors and staging across success, failure, cancellation, restart and shutdown. Bounded selected rows alone do not prove bounded work. Shared deletion and new owner admission serialize through a durable physical-storage/full-digest fence; a pending generation blocks eligibility, not unrelated digests. Slow deletion holds no database transaction, connection or scope/run lock, and only proved closure permits re-promotion after deletion. Checkpoint release in #159 and work items 14/17 cannot erase durable publication provenance.

Preserve the existing lifecycle method: declared workload/data, explicit cleanup barriers, identical base/head environments, peak/post-quiescence/per-cycle counters and retained samples. Scheduler release includes at least 1,000 cycles per applicable ending path, on both databases. #159 retains real-Git warm-up and 20 cycles per outcome with independent runs and process/descriptor/zombie/memory/storage evidence. #195–197 retain spawn/lock/attestation, journal/transfer/adoption, full-disk/unknown-outcome, stop and whole-command lifetime gates. Work items 19/20 retain bounded-wait cancellation and process-exit cleanup. Only remote issuance/rotation/expiry/re-scan workloads wait for a code host. The existing compact CEL regression and lifetime requirements stay active; this scope introduces no numerical calibration campaign.
