# Live Claude and local Git demo execution profile

[ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md#decision) defines this single-host placement for the [#1919 demonstration](https://github.com/realkarych/kora/issues/1919) alone. The server side of [work item 20](../../docs/implementation-plan.md#6-work-items) owns installed composition, its qualification and the operator invocation. Work item 21 owns the same-run demo witness. [ADR-0001](../../docs/decisions/0001-own-control-plane.md) retains the first-slice `kora standalone` release shape, independent Claude and Codex acceptance and the separate Pi MVP qualification. The installed first-Claim staging profile and isolated Linux ext4 test admission keep their existing scopes.

This design defines future activation conditions. Implementation and activation of the private transport, ordinary request producers, bound opener, public admission and console handoff remain with their respective owners. Existing routes, payloads, credential scopes, settings and persisted formats govern.

## Placement and authority

One host means an independently verified native host and boot with applicable process namespace evidence. The foreground API owns the Scheduler lifetime, the original serving loop and the original qualified SQLite metadata writer shared by API and Scheduler. The storage and custody journal retain their respective native owners. Bind each actual acquired resource to its original installation. A common pathname, host or device cannot establish physical qualification. Apply the [native custody profile](execution-custody-native.md#1-native-ownership-and-installation-binding) and the [installed test-store refusal and actual-close rules](installed-sqlite-driver.md#native-open-and-settlement). The approved guarded wheel and its release evidence establish only their own boundary.

The trusted local launcher has a lifetime independent of the API and owns the original separate Worker through an API restart. It exclusively supplies that Worker with its scoped service credential and the verified original launch inputs. Only the existing token ID belongs in the retained launch binding. Worker and candidate receive no metadata writer or database credential. Personal CLI and console requests keep their own identities and scope under [ADR-0011](../../docs/decisions/0011-namespaces-and-personal-tokens.md).

Positive provenance requires the existing authenticated Worker operations over the API-owned private Unix-domain HTTP listener specified by [ADR-0029](../../docs/decisions/0029-installed-api-serving-stack.md#private-unix-http-for-installed-selection-evidence). On the exact accepted socket apply the [native peer and original Claim checks](installed-execution-selection.md#bind-the-actual-worker-and-the-original-claim), including accept-time observation and launcher-held continuity where the platform requires it. Retain actual ownership of the socket, peer job and exchange from admission through closure, with one request per connection and the existing deadlines and capacity. Disallow proxying, inheritance or handoff of the attested connection. The composition root injects the narrow accepted-socket proof into API operations under [ADR-0026](../../docs/decisions/0026-package-layers.md). Registration, provider names, a bearer, ordinary TCP Claim, mode or flag presence, PID/path match and health carry no positive provenance.

## Threats and diagnostics

The [threat model](../../docs/threat-model.md#threat-scenarios-and-controls) governs the trusted host and cooperative LocalRuntime boundary. This profile retains these controls and assigns their integration evidence to the cases above.

| Threat | Required evidence |
| --- | --- |
| TM-01 and TM-07 · authorization and visibility | The original Worker and authenticated exchange are bound to service scope. Personal console reads keep separate current authorization and protected content boundaries. Exercise copied bearer, wrong peer and denied read, and inspect safe refusal output. |
| TM-08 and TM-11 · gate integrity and artifact identity | Original VcsRef owner, trusted sealed input, actual checkout, accepted CommandResult and bound approval follow the same source through the run. A same-commit different artifact cannot substitute. |
| TM-09 · replay and ownership | Replay keeps the exact original outcome. Wrong or stale launch binding, retained ownership, unresolved native COMMIT and incomplete stop preserve closure obligations without opening a new execution effect. |
| TM-12 · installation proof | Independently verify approved bytes, effective inputs, live Worker, native custody and later read compatibility. Neither staged evidence nor a guard-only release supplies ordinary profile qualification. |
| TM-03, TM-05, TM-06 and TM-10 · inherited controls | Keep selected tool policy, trusted late publication, credential/content protection and bounded exchange and lifetime controls. The installed demo remains on a trusted host, with the existing LocalRuntime same-user residual. |

Work item 20 owns foreground startup, refusal and stop diagnostics. Scheduler, Worker, runtime and custody retain their existing diagnostic ownership. Apply the [structured logging contract](observability.md#5-safe-content-and-trust-boundaries), including DEBUG and unavailable-sink cases. Use bounded, fixed categories for startup qualification, peer or selection refusal and completed or unfinished settlement under existing owning surfaces. Report only admitted safe states, counts and correlation fields. Exclude credentials, input and artifact contents or digests, private paths, raw peer facts and native errors. Diagnostics and health have no admission, replay or closure authority. The activating implementation records the named evidence for safe output and unchanged settlement with blocked or failed diagnostic delivery.
