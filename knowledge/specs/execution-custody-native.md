# Native custody journal and recovery

Status: native design [accepted in #1586](https://github.com/realkarych/kora/pull/1586#issuecomment-6894239462) on 2026-11-15, closing [#1580](https://github.com/realkarych/kora/issues/1580). The owner accepted the original v1 formats, native procedures and qualification method; implementation and qualification remain pending. The [authority mechanism](execution-custody-authority.md) was accepted in [#1575](https://github.com/realkarych/kora/pull/1575#issuecomment-6886916062). This companion preserves its single-host core placement, one local physical storage domain, serialized metadata writes, 64 ordinary participants and reserved recovery owner. The [recovery-priority amendment](execution-custody-recovery-priority.md) specifies native v2 and the qualified PostgreSQL checkout handoff. Custody activation requires implementation and qualification.

The authority specification's governing decisions, uncertainty rules and resource limits apply throughout. [ADR-0026](../../docs/decisions/0026-package-layers.md) additionally governs module ownership. The [dated source inventory and delivery assessment](../research/execution-custody-native-plan-2026-11-15.md) distinguishes existing code, proposed producers and native facts checked against primary documentation. #216 owns integration, #1320 owns deletion custody, and #1581 owns the upload-retirement handoff fields accepted in #1583. This document grants none of their missing runtime capabilities.

## 1. Native ownership and installation binding

The journal lives in one private directory outside the metadata backup/restore set and outside the provider's private control database. The v2 installation's fixed children are `authority.sqlite3`, `lifetime.lock`, `commit.lock`, `recovery.lock` and `journal-order.lock`; SQLite may create its own rollback journal beside the database. The journal uses rollback-journal DELETE mode, synchronous EXTRA, a 4096-byte page size, no attached database, no extension loading and no journal-mode changes after provisioning. EXTRA includes the FULL requirement and adds directory synchronization for rollback-journal removal. On macOS every journal connection also requests and verifies `fullfsync`. Actual native synchronization, including directory operations and fallback refusal, still requires qualification; returned pragma values are not physical evidence.

Provisioning opens the canonical private parent and child directory by native directory handles. It refuses symlinks, unexpected owners/permissions, hard-linked files, an existing nonempty target, and files whose device/inode differs between open and verification. Directory mode is 0700 and regular files are 0600 for the trusted service account. Direct file opens are relative to the anchored directory; SQLite uses its stable canonical private path, as the local provider does. Recheck named entries against retained handles before acquisition and before dispatch. Detected substitution refuses, but this is no race-safe SQLite-open guarantee against a trusted operator replacing files concurrently; live replacement is unsupported. Lock files are never unlinked, truncated or replaced. No path from an API request selects them. Directory and file creation, initial contents and parent-directory entry persistence must complete before provisioning can publish a binding.

The installation binds the journal's random 128-bit identity, the actual host identity, native root/lock/database anchors, one metadata installation, and the provider's complete resolved `StorageIdentity`. Native anchors include filesystem/device identity and inode/file identity, not only a canonical pathname. Copying those values is not an authority transfer. PostgreSQL binding includes the cluster system identifier and database OID obtained from the configured server, plus the pinned connection authority; it is not merely a URL or backend PID. A physical clone may retain a system identifier, so the qualified operator procedure and independent journal remain necessary. Credentials and provider payloads never enter the journal.

Every ordinary issuer holds shared `lifetime.lock` ownership from before registration until actual closure. Generation rotation and offline image replacement require its exclusive form. `commit.lock` has one exclusive owner across metadata checkout, journal preparation, native completion, resource release and journal settlement. `recovery.lock` reserves one exclusive coordinator. The coordinator may coexist with ordinary shared lifetime holders while settling their original records. Exclusive lifetime ownership is for closed-admission procedures such as fresh provisioning, rotation and offline replacement. Shared lifetime ownership supplies no proof that an ordinary issuer stopped. No operation upgrades a held shared lifetime lock in place. A coordinator closes its own shared admission before trying exclusive ownership. Failure keeps useful admission closed.

The [priority contract](execution-custody-recovery-priority.md#one-ordered-recovery-request) governs the latch checks before ordinary allocation, the short journal order lock, the reserved coordinator's priority publication and the permitted native waits. Ordinary commit admission continues to use nonwaiting `flock`. After commit admission, close each short journal phase before metadata checkout or a metadata await. Reads of journal state also acquire `commit.lock` briefly and release it before provider entry. The captured live issuer and registered invocation cover the later interval. The only journal administrative update without commit admission publishes the exact priority hint under the reserved recovery and lifetime leases and short journal exclusion. A stale hint is reconciled only by the natively exclusive successor under the [priority startup and failure rules](execution-custody-recovery-priority.md#native-failure-cancellation-and-fork). Qualified PostgreSQL uses the [same-pool next-checkout handoff](execution-custody-recovery-priority.md#postgresql-admission-and-release), including before any ordinary pool waiter can dispatch.

Descriptors are noninheritable. Forked children close inherited custody descriptors in the native child hook without issuing `LOCK_UN`, which would also unlock the parent's shared open-file description. They cannot use copied issuers: every admission verifies the captured PID and native host/boot/process-start identity, and composition does not fork an active receiver into a serving child. Exec closes descriptors. Neither hook success nor PID disappearance alone proves provider/native work closed. A paused process retaining its shared lock prevents rotation; a dead process frees a lock but may leave a PostgreSQL transaction or provider effect unresolved. These are cooperative controls for trusted core code, not protection against a hostile process with the service account's credentials.

## 2. Native records and versions

Records use native scalar columns with closed versioned data shapes. The v2 installation requires `authority.format_version=2` and the v2 lock binding. The other journal rows and metadata frontier retain `format_version=1`. Unsupported stored versions, enum values or invalid data refuse activation. Strict record decoders reject coercions and enforce the declared domains. Kora trusts the layouts its own migrations create under [data-model principle 7](data-model.md#1-principles): runtime code does not inspect relation layouts, extra columns, indexes, triggers or foreign-key actions. Migration tests establish the declared native constraints. Version/data validation, actual native durability inputs, binding and coherent-image provenance remain separate requirements. A complete encoded row is at most 16 KiB with depth at most 16; native width admission precedes driver materialization. Indexed keys and states are never decoded from documents. Nested values below expand into fixed columns, except the existing canonical bounded `StorageIdentity` encoding.

Common domains: `counter` is a positive signed-64 integer, never wrapped or reused; allocator exhaustion closes new admission. `zero_counter` also permits zero only for the initial frontier or an unused allocator. `id128` is exactly 16 bytes. Digests are exactly 32 bytes. Enums are exact ASCII values. Native integer identifiers that can exceed signed-64, including a PostgreSQL `xid8`, use fixed-width unsigned eight-byte big-endian values, compared bytewise and never converted through floats. Bounded native identity strings use the existing process-identity domains and refuse unavailable required fields. Time observations never authorize expiry or reuse of identities.

The following fixed column groups expand every binding named in the relation table. There are no discretionary evidence dictionaries or arbitrary strings whose interpretation grants authority.

| Column group | Native fields and domains |
| --- | --- |
| Process identity | `host_id`, `boot_id`, `pid_namespace`: nonempty printable ASCII, at most 256 bytes each; `pid`: integer 1–2³¹−1; `start_time`: nonnegative signed-64. These are the existing `ProcessIdentity.identity_key()` fields, all required here. `leads_group` is not an identity field or evidence of closure. |
| File anchor | `device`, `inode`: unsigned eight-byte native identifiers; `canonical_path`: exact native path bytes, 1–4096 bytes, no NUL. Anchors cover the directory, its parent, each of the four fixed lock files and journal main file. Path equality does not replace opened-handle identity checks. |
| Physical profile | `qualification_digest`: 32-byte identity of the exact retained installation-method/input report. The verifier must match actual current native inputs and qualifying results; the digest itself grants no admission. The same principle applies to the original transaction's saved `settings_digest`, a 32-byte identity of its bounded observed native settings. |
| Provider binding | The canonical existing `StorageIdentity` with its one `store_id` field, plus the selected local root's file anchor. The provider continues to verify its private manifest/epoch itself. Core does not decode a private provider database or invent an epoch accessor. |
| Metadata binding | `metadata_id`: fresh nonzero `id128` created only in provisioning; `backend`: `sqlite` or `postgresql`; qualified profile. SQLite has its main-file anchor. PostgreSQL has unsigned-eight-byte `system_identifier`, positive unsigned-32 `database_oid`, and 32-byte `connection_authority_digest` over the credential-free configured authenticated authority. Inapplicable backend columns are NULL. |
| PostgreSQL native transaction | Original full unsigned-eight-byte `xid8`; `backend_pid` in the PID domain; `backend_start` as native UTC microseconds in signed-64; `server_start` in the same domain. These identify the captured server/backend, not a timeout-based termination proof. |

The metadata singleton also stores the immutable `metadata_id`; all journal and metadata bindings must agree. File identity may change during an authorized complete-image install only while `restoring` holds exclusive ownership; the original source and target anchors must be retained by that procedure until its binding update is durably complete. Ordinary open cannot silently adopt a changed inode.

| Relation and key | Complete logical fields and constraints |
| --- | --- |
| `authority(singleton=1)` | Version 2; `journal_id`; immutable host, journal and provider binding, including the `journal_order_device`, `journal_order_inode` and `journal_order_path` file-anchor triple; metadata binding; `mode` (`provisioning`, `active`, `fenced`, `restoring`); `generation`; `allocated_commit`; `allocated_issuer`; `confirmed_generation`; `confirmed_commit`; `confirmed_token`; optional `recovery_priority_incarnation`. The initial confirmed triple is `(0,0,zero-id128)` only during provisioning. All other triples have positive counters and nonzero token. Allocators never decrease, including on abort. |
| `pending_commit(singleton=1)` | Version; journal/generation; allocated commit sequence and fresh token; exact previous confirmed triple; original issuer sequence and kind (`ordinary`, `recovery`, `provisioning`); native transaction binding; `phase` (`prepared`, `dispatching`, `committed`, `aborted`). One row maximum. Its sequence is greater than the confirmed sequence and no greater than `allocated_commit`; previous triple equals `authority` until settlement. `committed` and `aborted` require the original completion producer below, never a supplied status. |
| `participant(slot)` | Version; slot 0–63; journal/generation; globally allocated issuer sequence; immutable complete native process identity; `gate` (`open`, `closing`, `closed`); `allocated_receiver`; `allocated_invocation`; optional current receiver sequence and state (`active`, `closing`); `closure_revision`. All current-receiver fields are absent together or present together. `closed` requires no current receiver and completed native exclusion/resource closure; it does not erase unresolved domain effects. Slot reuse requires complete prior issuer closure, all unresolved referenced operations settled and no remaining foreign-key obligation. Surviving settled history retains its immutable provenance; moving unresolved work to a typed row does not free a slot. |
| `recovery(singleton=1)` | Version; globally allocated incarnation; current complete native coordinator identity; gate; receiver/invocation allocators and optional receiver as above; optional one active invocation consisting of typed owner kind, exact owner key, semantic slot, original operation identity, issuer/receiver/invocation binding and phase (`registered`, `entered`, `closing`). All invocation fields are present or absent together. Typed owner keys use their existing domains; no arbitrary SQL, path or provider request lives here. A previous unresolved invocation survives coordinator replacement until actual native closure. |
| `image_transition(singleton=1)` | Version; non-reused transition sequence from `allocated_commit`; original recovery incarnation; metadata binding; source and private destination anchors; expected confirmed triple; optional exact pending triple; `phase` (`copying`, `complete`, `installed`); optional 32-byte complete-image manifest digest. Digest is NULL in copying and required afterward. One row only while mode is restoring. The native producer owns the manifest's complete file inventory outside the journal; it is streamed and independently size-admitted, not loaded into this row. |
| `provisioning(singleton=1)` | Version; original recovery incarnation and complete process identity; metadata binding; exact target Alembic revision as printable ASCII of 1–128 bytes; phase (`schema_running`, `schema_complete`, `frontier_running`); optional original dedicated migration connection binding. The connection binding is persisted before the first migration dispatch and then immutable; its absence proves only that no migration dispatch was authorized. PostgreSQL uses cluster/database/backend PID/start/server identity, SQLite its original anchored connection sequence. One row only in provisioning mode; schema_complete requires the actual whole migration owner's successful completion and resource release. No per-migration outcome ledger accumulates. |

The native transaction binding is a discriminated shape. SQLite stores the original issuer, local native connection sequence and transaction sequence, anchored metadata database identity and original qualified settings identity. Connection/transaction sequences use `counter`, allocated before exposure under their original issuer; they cannot repeat within that issuer. PostgreSQL additionally stores cluster/database binding, full `xid8`, backend PID and backend-start identity captured on that writer. These are observation inputs, not standalone proofs. One journal transaction allocates a sequence and installs its row; an interrupted allocation cannot reuse an exposed identity. A pending row's original native binding never changes on recovery. A participant's `closure_revision` is NULL until closed, then the positive exact metadata outcome revision that established its domain closure. Fresh receiver/invocation allocators start at zero, advance before exposure and remain consumed on failure.

The metadata database has one logged `custody_frontier(singleton=1)` relation: version, immutable nonzero `metadata_id` in the `id128` domain, journal identity, authority generation, commit sequence, token, previous generation/sequence/token. It has exactly one row after provisioning. The original transaction updates it atomically with all its domain writes, from the exact previous triple. Its logged persistence and declared constraints are established by the owned migration and its tests; native durability qualification does not introduce runtime schema introspection. No public route can write it. A mismatched binding or absent singleton after provisioning fences admission. Journal confirmation advances to that exact triple, not to a maximum observed counter.

`participant` is the independently retained lifetime registry. Metadata `content_issuer` retains the typed domain-facing projection and operation references from execution content; it is not a second authority. Registration persists the journal slot first, then its metadata projection through the ordinary handshake, and only then opens useful dispatch. Partial registration consumes the slot until resolved. Closure first seals native admission, closes actual resources, writes the corresponding domain closure through the handshake, and finally advances the journal slot. An unknown projection commit keeps the slot. There is no atomicity assumption across the two databases.

Ordinary current invocation bindings and immutable operation provenance remain in the original typed operation rows, such as `upload_operation`, with their existing finite semantic slots. The journal adds no append-only operation, receiver or invocation history. A slot contains at most one current receiver. The recovery row contains at most one active control invocation. Typed historical outcome retention is distinct from disposable journal state.

Journal statements use primary-key lookups or the fixed 64-slot scan. Set `max_page_count=4096` at the fixed page size: the main database cannot grow beyond 16 MiB; allocation failure fences new work. Disable automatic vacuum and explicit VACUUM in active operation, use no temporary sorting, and keep only one bounded journal connection/native job per admitted owner. Before registration, at most one registrar owns a temporary journal control handle/job after acquiring commit admission; it closes that handle/job before releasing `commit.lock`. This is a bounded registration resource, not a 65th ordinary participant. Contenders allocate no task/connection; metadata checkout and receiver construction remain forbidden until durable slot admission. The main-page cap is not a claim about total filesystem bytes or RSS: rollback-journal high water, native cache and temporary files need measured qualification under the bounded transactions. No unbounded WAL is created by this selected journal mode. Error output is bounded and content-free. Journal-full, corruption and synchronization failure retain original pending custody, not an empty replacement database.

## 3. Original metadata COMMIT protocol

All metadata writes participate, including writes unrelated to storage. The [priority contract](execution-custody-recovery-priority.md#one-ordered-recovery-request) governs native admission and dispatch before any writable checkout, connection initialization or domain lock. The real source paths and bypass obligations are enumerated in the dated inventory. A positively checked transaction owns its checkout, cancellation shield and completion result through the following phases.

| Phase | Ordered operation and durable result | Failure/cancellation behavior |
| --- | --- | --- |
| Admission | Acquire native commit admission; verify anchored journal, issuer, generation, confirmed metadata frontier and no pending row. Acquire the actual writer, validate native durability and begin. Capture its native transaction identity. | Refuse before lending on mismatch. Original owner rolls back and closes an entered transaction; no detached cleanup owner inherits it. |
| Preparation | Perform domain work under existing locks. Allocate the journal commit sequence/token and durably insert `prepared`, then set the metadata singleton to its exact next triple in the same domain transaction. | Failed journal persistence prevents COMMIT. If persistence itself is uncertain, retain admission and inspect its exact original row after the journal's native owner settles. |
| Dispatch | Recheck native settings on the exact metadata writer. Durably change `prepared` to `dispatching`; only its completed persistence permits issuing the one native COMMIT. | `prepared` after affirmative issuer/native exclusion proves no COMMIT dispatch. `dispatching` does not prove that COMMIT ran. Cancellation between these actions remains unknown unless the original owner establishes rollback/no-dispatch. |
| Native completion | Retain a write-once in-memory result from the original native task: committed, affirmative rollback before any successful COMMIT, or unknown. Shield native completion through requesting-coroutine cancellation. | A later rollback, pool reset, connection close or cancellation exception cannot overwrite committed/unknown with aborted. Deadline expiry closes useful work but leaves the original resources owned. |
| Settlement | Release actual metadata cursor, transaction and checkout; durably record the affirmative `committed` or `aborted` result in the pending journal row. For committed, atomically advance the confirmed triple and remove pending. For aborted, remove pending without advancing; the allocated sequence remains consumed. | An uncertain journal update is resolved by its exact token. No new writer starts while pending remains. A crash before result persistence may require native recovery even when the caller observed success. |
| Reliance | After journal confirmation, return the saved domain outcome or admit an exact provider invocation. Positive custody read and all DB resources finish before provider entry. | A lost response repeats only the original domain receipt. It does not allocate a new mutation or infer absence. |

An original native task that observes success but loses its journal write keeps ownership until journal settlement or real process loss. `Database.close()` returning after its deadline is not that closure: current code may retain units and dispose later. Future custody shutdown must distinguish a refusal/unfinished shutdown from actual release. Native rollback failure also preserves the unresolved pending owner.

Pending `committed`/`aborted` is a durable outcome only because the native owner produced it under the qualified profile; callers cannot construct those facts. Recovery may finish journal compaction from either state after checking exact bindings and coherent metadata. No subsequent write is admitted until it does. The `prepared` no-dispatch branch additionally excludes the original native owner and any copied/inherited dispatch capability before clearing the pending row.

Plain read paths must be demonstrably read-only on both databases. The ordinary reader implementation under [#1600](https://github.com/realkarych/kora/issues/1600) establishes PostgreSQL native READ ONLY before caller access while preserving READ COMMITTED and the shared pool; snapshots retain their separate setup, and SQLite retains query-only readers. This supplies only the plain-read access mode. Qualification of checkpoint-capable connections, journal continuity and the remaining custody producers is still pending. Exposed SQLAlchemy engines must not provide an unmanaged writable checkout when custody is active. The [qualified pool contract](execution-custody-recovery-priority.md#postgresql-admission-and-release) governs checkout entry and release, including authentication error classification. Trusted administrative writes, direct SQL and external maintenance cannot bypass the profile. SQLAlchemy pre-COMMIT events alone cannot implement post-COMMIT outcome ownership.

PostgreSQL Alembic autocommit/concurrent-index work is not wrapped by this ordinary handshake. Active custody refuses migration entry before a connection or session advisory lock. Initial migrations run only inside fenced provisioning before effect admission. Later migration requires an explicitly qualified whole-image transition while useful work and old issuers are closed; this first native design does not supply arbitrary upgrade transitions. The preexisting ordinary-mode migration command remains available for installations without active custody. No active-profile upgrade may pretend that an empty autocommit block is a read-only operation.

## 4. Recovery, provisioning and coherent images

### 4.1. Provisioning and ordinary startup

Provisioning first establishes that metadata is a new empty installation and the selected provider is a new empty domain through their actual native producers. It anchors the v2 installation and durably initializes the latch to `ARMED` before publishing the authority binding in `provisioning`, with zero confirmed frontier and the single provisioning row in schema_running. No ordinary writer, public result, receiver or provider effect is admitted. The reserved recovery owner holds exact exclusive `R`, `L` and `C` as defined by the [priority contract](execution-custody-recovery-priority.md#one-ordered-recovery-request). Under durable `ARMED`, the [qualified PostgreSQL pool owner](execution-custody-recovery-priority.md#postgresql-admission-and-release) admits that owner's original migration lease and first frontier writer only after verifying their existing fenced provisioning entry and exact original provisioning binding. Both use the installed pool's capacity and actual release rules.

That original owner opens one dedicated migration lease and durably records its native connection binding before Alembic dispatch. It owns every actual setup, per-migration transaction, autocommit statement and cleanup call identified in the writer inventory, with no implicit reconnect/replacement. It retains their original completion through cancellation. Only successful completion of the entire schema installation, the expected Alembic revision and actual release of the native migration lease allow a durable transition to schema_complete. The owned schema installation creates the empty frontier relation in its selected target migration; it inserts no fabricated confirmed row. Layout/constraint correctness is covered by migration tests, not runtime introspection.

If initial migration completion or its journal persistence is unknown, retain schema_running and the original connection binding. A still-owned original native task may finish and persist its actual aggregate result. After loss of that owner, reading the expected Alembic head, finding no backend, or observing partial tables cannot manufacture successful aggregate completion. This first profile refuses continuation in that state; it supplies no automatic migration replay, destructive reset, fresh journal or caller-provided completion override. That conservative availability limit is explicit. Absence of a persisted connection binding permits resuming before first dispatch only after affirmative original owner exclusion.

From schema_complete, persist frontier_running and execute the first pending handshake. This one admission branch requires provisioning mode, the exact original binding, zero confirmed frontier, completed schema owner and no ordinary participant; it does not require an existing frontier row. Preparation inserts the singleton with the exact allocated next triple and zero previous triple. All subsequent transactions require and compare the existing singleton. A crash in this first transaction follows the same prepared/dispatching/committed/aborted rules; unknown original outcome cannot authorize another initialization. After positive confirmation of the first COMMIT and actual release of its original native resources, the reserved owner durably selects `active` and removes the provisioning row in one journal transaction while ordinary admission remains closed. The first `OPEN` requires completed bootstrap and the [priority withdrawal closure order](execution-custody-recovery-priority.md#one-ordered-recovery-request). The same owner retains exact `R` through the first `OPEN` write and publishes it only after verified release of the original metadata resources, durable reconciliation of the journal outcome and hint state, and actual closure of SQLite, `J` and then `C`. The reserved owner never supplies a second ordinary participant slot. An existing domain with a missing journal never qualifies as new.

At startup, the exact exclusive recovery coordinator checks the supported persisted versions, native anchors, latch and exact bindings under the [priority reconciliation rules](execution-custody-recovery-priority.md#native-failure-cancellation-and-fork). Under the required native exclusion, that coordinator settles any pending COMMIT, closes or retains old participants and establishes current native durability. For startup reconciliation, a joining ordinary issuer is limited to the installation, generation, lifetime and latch checks under the [native admission rules](execution-custody-recovery-priority.md#scope-and-compatibility) before useful dispatch. Both paths trust the migration-owned schema. A live old participant may continue only in its captured unchanged authority with its original ownership intact; startup of another process cannot rotate around it. Rotation seals admission, excludes all old issuers and native operations, takes exclusive lifetime ownership and advances the journal generation. The metadata frontier change uses the same handshake while admission remains closed. Failure leaves the new journal generation fenced; it never rolls back to reuse an old generation. Existing typed operations retain original provenance through rotation and authorize only their contract's recovery calls.

Ordinary restart of the same native files relies on the qualified crash-recovery producer and actual preservation of their anchored lineage. An operator who replaced/restored files must use the offline procedure instead. Root identity and singleton equality cannot detect a trusted operator's in-place partial rewrite; this is outside ordinary restart's assumptions, not a newly permitted restore method.

### 4.2. Resolving the original pending transaction

For SQLite, keep the original native completion task until it returns whenever its process still exists. After actual process/native exclusion, native hot-journal/WAL recovery of the unchanged metadata installation may establish a coherent image. An exact pending token in that image, with qualified durability and no intervening writer, permits confirmation of that transaction. An old token or absent row alone never proves rollback. `prepared` plus proven no-dispatch, or the durably saved original `aborted` result, can establish abort; otherwise retain pending. No file copy or current-object observation substitutes for this producer.

For PostgreSQL, assign and save the full transaction ID on the original writer using `pg_current_xact_id()` before dispatch. On the same pinned cluster/database authority, the reserved recovery observer checks `pg_xact_status` for that original ID. `in progress`, NULL, errors or changed lineage retain pending. `aborted` can confirm rollback only with coherent unchanged/recovered authority and the previous frontier. `committed` must agree with the exact pending token; it is not by itself proof that the required WAL/replica persistence completed. PID reuse and disappearance do not settle the transaction, and a new transaction ID cannot replace it.

Where the original synchronous COMMIT completion is unavailable, this design allows a separate trusted offline recovery operator to complete a native CHECKPOINT after observing the original transaction committed and before confirming its token. The observer binds the same cluster/database, current server incarnation and completed checkpoint to the original pending token; a lost checkpoint response retains unknown and may repeat the physical checkpoint only after its original native owner closes. The checkpoint is a physical persistence barrier, not a domain mutation or substitute token. It cannot excuse a prior settings downgrade or establish a stronger remote-replica acknowledgment. With a stronger replication policy, confirmation still requires its original completion or separately qualified replica evidence; otherwise it stays pending.

That recovery operation requires PostgreSQL's checkpoint privilege. It belongs to the separately authorized operator procedure, never ordinary API, scheduler or worker credentials. The owner accepted that bounded recovery privilege/procedure in #1586; #1575 alone did not. Missing privilege leaves recovery pending rather than silently granting it or using a weaker assertion. No prepared transactions, logical decoding, replication failover or external consensus dependency is introduced.

### 4.3. Offline image procedure

The producer owns an entire image operation, not a caller-supplied `restore_verified` flag. Seal useful admission; hold the reserved recovery owner, exclude original native writes/effects and all ordinary participants, and acquire exclusive lifetime and commit ownership. Resolve pending COMMIT first or preserve it as an explicit unresolved original transaction. Persist `restoring` and its single `image_transition` with original source/target anchors before touching metadata files. Native copy completion and complete streamed manifest verification advance copying to complete; installation and persistence advance complete to installed. Never include the independent journal in the metadata image replacement.

For SQLite, use the native backup API on the complete original database after fencing, with its real source/destination handles, native completion and error handling. Keep the destination private until completion, close native handles, persist its files and parent directory under the qualified filesystem method, and install only that complete image under exclusive ownership. Do not copy just a main file while ignoring WAL, mix pages from different images, or selectively copy custody/allocator relations. The source frontier is captured while writes are excluded; the destination's supported migration/record versions, complete-image provenance and exact frontier must agree with the retained journal. This does not re-verify its migration-created schema. An older coherent image still fails continuity if its frontier predates the last relied-on commit.

For PostgreSQL, use a complete physical base backup plus its required WAL and timeline history, restore it offline with complete native recovery, and verify the original cluster/database binding and exact custody frontier. The operator owns the actual backup/replay process and its resource completion; a manifest checksum or logical table dump alone does not establish this source. This design permits no failover to an independently writable clone or arbitrary timeline selection. A target missing the exact confirmed or unresolved pending transaction cannot be repaired by copying the singleton from another target.

After image validation, original issuer/effect closure and pending settlement, advance authority through the normal rotation handshake and atomically persist `active` while clearing the image row. Interrupted backup/install/replay remains `restoring`. A successor first closes/excludes the original copy/replay process, then matches the exact retained source/target anchors, phase, manifest and frontier before resuming that same transition. Missing or ambiguous completion permits only preservation or disposal of a proven uninstalled private copy; it never permits adopting a target or deleting the only original image. The producer owns its native handles, subprocesses and temporary disk reservation until actual close and safe removal. Neither temporary-file cleanup nor a successful new connection opens admission. If complete provenance cannot be established, refuse activation and keep witnesses/charges. Journal loss, damage, substitution, known rollback or simultaneous rollback with metadata/provider still requires a separately accepted independent continuity source. This design cannot reconstruct it.

## 5. Invocation and upload-retirement boundary

Before any positive issuance check, reserve an existing bounded dispatch slot and capture the actual receiver, issuer and next non-reused invocation sequence. Register that owner durably in the original typed operation through the COMMIT handshake. Positive custody checking then verifies the exact still-open operation, current authority, original request and current receiver. All database resources close before the dispatch owner calls the provider. Registration covers the interval before provider entry: a paused callable is already an outstanding owner, even if the provider has no receipt yet.

Closing issuance atomically prevents new registration and positive admission, then joins every previously registered original owner, including queued/pre-entry work, native futures, readers, parsers and finalizers. An owner paused after its positive check still has to finish or be natively excluded; a metadata state change does not retract that permission retroactively. Durable closure records must identify the exact operation and completed resource set. Only then may the typed stage's actual retirement/release acknowledgment contribute to its storage closure. Process death, timeout, absent receipt, an error from a stale receiver and a reconstructed receiver each fail to prove that closure alone.

The [upload-retirement contract](upload-retirement.md), published in [#1583](https://github.com/realkarych/kora/pull/1583) under the [approved #1581 plan](https://github.com/realkarych/kora/issues/1581#issuecomment-6893519377), retains protection for the complete declared/source/retained address union while native storage closure is pending. Its `retained_admission_generation`, `cleanup_generation_floor` and `storage_closure` fields belong to that separate specification and remain unimplemented. This journal supplies original commit continuity and issuer/native closure evidence to that producer; it never supplies an unchecked boolean. A deletion performed before a delayed original promotion can still create bytes cannot release the upload's final charge. Unknown COMMIT or acknowledgment keeps protection and full charge. No alternative delete intent, settlement or acknowledgment DTO is added.

The first useful integration remains an actual refused-upload lifecycle: admitted owned stage, real promotion attribution, irreversible original closure, then eligible other-owner release or exact admitted deletion, original observation/settlement, provider acknowledgment and exactly-once core reservation release. No production source currently composes this path. A conformance call, unused journal service, proof-object constructor or flag keeping every effect unavailable is not its implementation. Worker sealing/reports and scheduler settlement remain downstream until their real producers exist.

## 6. Qualification method and activation evidence

The method specifies future acceptance, not experiments run by this design PR. An implementing issue must name its actual test/qualification entry point and an owned disposable installation before execution. Never power-cycle a developer workstation or shared database. The [priority contract](execution-custody-recovery-priority.md#acceptance-and-owning-seams) adds the v2 latch coherence and persistence prerequisites and the checkout handoff cases. Existing Linux/macOS and both-database obligations remain; no process-kill fixture is relabelled as a system-crash result, and no new recurring CI campaign is created.

Record the exact kora revision, SQLite library/build/VFS, PostgreSQL server build, drivers, OS/kernel, filesystem/mount options, device/controller/firmware, volatile caches and power-loss protection, journal and metadata placement, sync behavior, server settings, replica policy and cut-controller identity. Changing a relevant input invalidates that profile's physical conclusion. A qualified profile is a concrete installation configuration, not just “Linux”, “macOS”, “SQLite” or “PostgreSQL”. No profile has yet passed this method.

Use a separate observer outside every power/reset domain being cut. It durably records the exact acknowledged journal/metadata commit and immutable operation/outcome identities before the cut controller proceeds. The controller's barrier pauses the real workload after acknowledgment and before any unrelated explicit flush/checkpoint; it does not call a graceful database or OS shutdown. Trace the actual synchronization and checkpoint path needed to show which boundary was exercised. If an incidental checkpoint/flush wins the race, that run has not exercised the intended window and is inconclusive, not a passing sample. Guest-process kill tests only process failure; guest reset cannot establish host cache/device power-loss behavior. The declared cut must remove the failure domain whose guarantee is claimed, with actual power interruption where the storage guarantee requires it.

| --- | --- |
| Journal `prepared` durable, before dispatch permit | No effect response occurred; after original native exclusion, no-dispatch can abort without reusing its sequence. |

Exercise SQLite metadata and the independent journal separately and together; for remote PostgreSQL cut the core host, database host/storage and their combined relevant failure domains. Native resource barriers and real processes/storage enforce ordering; no mocks or patched transports may stand in for native completion.

Blocking assertions are exact original outcome/authority, complete restore, actual resource closure, capacity admission and no lost acknowledged custody. Latencies, sync/checkpoint waits, throughput, journal physical high water and RSS are reported separately; deterministic page/slot/owned-buffer limits remain blocking. The real consumer must also satisfy applicable NFR-3 requirements without turning this document into an unapproved numerical method. Qualification reports name every unexercised failure domain and provide no broader claim than the tested method permits.
