## 1. Native ownership and installation binding

The journal lives in one private directory outside the metadata backup/restore set and outside the provider's private control database. Its fixed children are `authority.sqlite3`, `lifetime.lock`, `commit.lock` and `recovery.lock`; SQLite may create its own rollback journal beside the database. The journal uses rollback-journal DELETE mode, synchronous EXTRA, a 4096-byte page size, no attached database, no extension loading and no journal-mode changes after provisioning. EXTRA includes the FULL requirement and adds directory synchronization for rollback-journal removal. On macOS every journal connection also requests and verifies `fullfsync`. Actual native synchronization, including directory operations and fallback refusal, still requires qualification; returned pragma values are not physical evidence.

Provisioning opens the canonical private parent and child directory by native directory handles. It refuses symlinks, unexpected owners/permissions, hard-linked files, an existing nonempty target, and files whose device/inode differs between open and verification. Directory mode is 0700 and regular files are 0600 for the trusted service account. Direct file opens are relative to the anchored directory; SQLite uses its stable canonical private path, as the local provider does. Recheck named entries against retained handles before acquisition and before dispatch. Detected substitution refuses, but this is no race-safe SQLite-open guarantee against a trusted operator replacing files concurrently; live replacement is unsupported. Lock files are never unlinked, truncated or replaced. No path from an API request selects them. Directory and file creation, initial contents and parent-directory entry persistence must complete before provisioning can publish a binding.

The installation binds the journal's random 128-bit identity, the actual host identity, native root/lock/database anchors, one metadata installation, and the provider's complete resolved `StorageIdentity`. Native anchors include filesystem/device identity and inode/file identity, not only a canonical pathname. Copying those values is not an authority transfer. PostgreSQL binding includes the cluster system identifier and database OID obtained from the configured server, plus the pinned connection authority; it is not merely a URL or backend PID. A physical clone may retain a system identifier, so the qualified operator procedure and independent journal remain necessary. Credentials and provider payloads never enter the journal.

Locks use nonblocking native `flock` advisory file locks on the supported local filesystem. Every ordinary issuer holds shared `lifetime.lock` ownership from before registration until actual closure; generation rotation and offline image replacement require its exclusive form. `commit.lock` has one exclusive owner across metadata checkout, journal preparation, native completion, resource release and journal settlement. `recovery.lock` has one exclusive coordinator; ordinary participants cannot borrow its reserved slot. The recovery coordinator may coexist with ordinary shared lifetime holders while settling their original records; it obtains exclusive lifetime ownership only for rotation/offline replacement. It never treats shared ownership as proof that an ordinary issuer stopped.

Order is recovery coordinator ownership when applicable, lifetime ownership, commit admission, short journal transactions, then metadata checkout and the existing ordered domain locks. No operation upgrades a held shared lifetime lock in place. A coordinator closes its own shared admission before trying exclusive ownership; failure preserves closed useful admission. No journal transaction spans a metadata native await or provider call. Reads of journal state also acquire `commit.lock` briefly and release it before provider entry; the captured live issuer and registered invocation cover the later interval. Ordinary contention refuses before checkout or task allocation. Recovery records one bounded priority request; after the current owner releases, ordinary writers defer until that coordinator takes or withdraws the request. Its crashed coordinator is excluded through `recovery.lock` before the request is cleared. There is no growing waiter queue.

The priority request is the only journal administrative update allowed without `commit.lock`: under the exclusive recovery lease, one short journal transaction sets only `recovery_priority_incarnation` to its actual coordinator incarnation. It neither changes a frontier nor admits metadata work. Every ordinary writer checks it after acquiring `commit.lock` and before checkout; the existing writer may finish, but the next opportunity belongs to ready recovery bookkeeping. Journal SQL updates preserve unrelated columns. Clear the request before a provider call or after that bookkeeping finishes. A native journal transaction already in progress can delay this update only while its original bounded native owner remains unresolved; no second priority job or waiter is allocated. A dead coordinator's stale request is cleared only by its natively exclusive successor.

Descriptors are noninheritable. Forked children close inherited custody descriptors in the native child hook without issuing `LOCK_UN`, which would also unlock the parent's shared open-file description. They cannot use copied issuers: every admission verifies the captured PID and native host/boot/process-start identity, and composition does not fork an active receiver into a serving child. Exec closes descriptors. Neither hook success nor PID disappearance alone proves provider/native work closed. A paused process retaining its shared lock prevents rotation; a dead process frees a lock but may leave a PostgreSQL transaction or provider effect unresolved. These are cooperative controls for trusted core code, not protection against a hostile process with the service account's credentials.

## 2. Version-one native records

Records are native scalar columns with closed versioned data shapes, not an extensible JSON proof envelope. Each row has `format_version=1`; unsupported stored versions, enum values or invalid data refuse activation. Strict record decoders reject coercions and enforce the declared domains. Kora trusts the layouts its own migrations create under [data-model principle 7](data-model.md#1-principles): runtime code does not inspect relation layouts, extra columns, indexes, triggers or foreign-key actions. Migration tests establish the declared native constraints. Version/data validation, actual native durability inputs, binding and coherent-image provenance remain separate requirements. A complete encoded row is at most 16 KiB with depth at most 16; native width admission precedes driver materialization. Indexed keys and states are never decoded from documents. Nested values below expand into fixed columns, except the existing canonical bounded `StorageIdentity` encoding.

Common domains: `counter` is a positive signed-64 integer, never wrapped or reused; allocator exhaustion closes new admission. `zero_counter` also permits zero only for the initial frontier or an unused allocator. `id128` is exactly 16 bytes. Digests are exactly 32 bytes. Enums are exact ASCII values. Native integer identifiers that can exceed signed-64, including a PostgreSQL `xid8`, use fixed-width unsigned eight-byte big-endian values, compared bytewise and never converted through floats. Bounded native identity strings use the existing process-identity domains and refuse unavailable required fields. Time observations never authorize expiry or reuse of identities.

The following fixed column groups expand every binding named in the relation table. There are no discretionary evidence dictionaries or arbitrary strings whose interpretation grants authority.

| Column group | Native fields and domains |
| --- | --- |
| Process identity | `host_id`, `boot_id`, `pid_namespace`: nonempty printable ASCII, at most 256 bytes each; `pid`: integer 1–2³¹−1; `start_time`: nonnegative signed-64. These are the existing `ProcessIdentity.identity_key()` fields, all required here. `leads_group` is not an identity field or evidence of closure. |
| File anchor | `device`, `inode`: unsigned eight-byte native identifiers; `canonical_path`: exact native path bytes, 1–4096 bytes, no NUL. Anchors cover the directory, its parent, each of the three fixed lock files and journal main file. Path equality does not replace opened-handle identity checks. |
| Physical profile | `qualification_digest`: 32-byte identity of the exact retained installation-method/input report. The verifier must match actual current native inputs and qualifying results; the digest itself grants no admission. The same principle applies to the original transaction's saved `settings_digest`, a 32-byte identity of its bounded observed native settings. |
| Provider binding | The canonical existing `StorageIdentity` with its one `store_id` field, plus the selected local root's file anchor. The provider continues to verify its private manifest/epoch itself. Core does not decode a private provider database or invent an epoch accessor. |
| Metadata binding | `metadata_id`: fresh nonzero `id128` created only in provisioning; `backend`: `sqlite` or `postgresql`; qualified profile. SQLite has its main-file anchor. PostgreSQL has unsigned-eight-byte `system_identifier`, positive unsigned-32 `database_oid`, and 32-byte `connection_authority_digest` over the credential-free configured authenticated authority. Inapplicable backend columns are NULL. |
| PostgreSQL native transaction | Original full unsigned-eight-byte `xid8`; `backend_pid` in the PID domain; `backend_start` as native UTC microseconds in signed-64; `server_start` in the same domain. These identify the captured server/backend, not a timeout-based termination proof. |

The metadata singleton also stores the immutable `metadata_id`; all journal and metadata bindings must agree. File identity may change during an authorized complete-image install only while `restoring` holds exclusive ownership; the original source and target anchors must be retained by that procedure until its binding update is durably complete. Ordinary open cannot silently adopt a changed inode.

The connection binding is persisted before the first migration dispatch and then immutable; its absence proves only that no migration dispatch was authorized. One row only in provisioning mode; schema_complete requires the actual whole migration owner's successful completion and resource release. No per-migration outcome ledger accumulates. |

The native transaction binding is a discriminated shape. SQLite stores the original issuer, local native connection sequence and transaction sequence, anchored metadata database identity and original qualified settings identity. Connection/transaction sequences use `counter`, allocated before exposure under their original issuer; they cannot repeat within that issuer. PostgreSQL additionally stores cluster/database binding, full `xid8`, backend PID and backend-start identity captured on that writer. These are observation inputs, not standalone proofs. One journal transaction allocates a sequence and installs its row; an interrupted allocation cannot reuse an exposed identity. A pending row's original native binding never changes on recovery. A participant's `closure_revision` is NULL until closed, then the positive exact metadata outcome revision that established its domain closure. Fresh receiver/invocation allocators start at zero, advance before exposure and remain consumed on failure.

The metadata database has one logged `custody_frontier(singleton=1)` relation: version, immutable nonzero `metadata_id` in the `id128` domain, journal identity, authority generation, commit sequence, token, previous generation/sequence/token. It has exactly one row after provisioning. The original transaction updates it atomically with all its domain writes, from the exact previous triple. Its logged persistence and declared constraints are established by the owned migration and its tests; native durability qualification does not introduce runtime schema introspection. No public route can write it. A mismatched binding or absent singleton after provisioning fences admission. Journal confirmation advances to that exact triple, not to a maximum observed counter.

`participant` is the independently retained lifetime registry. Metadata `content_issuer` retains the typed domain-facing projection and operation references from execution content; it is not a second authority. Registration persists the journal slot first, then its metadata projection through the ordinary handshake, and only then opens useful dispatch. Partial registration consumes the slot until resolved. Closure first seals native admission, closes actual resources, writes the corresponding domain closure through the handshake, and finally advances the journal slot. An unknown projection commit keeps the slot. There is no atomicity assumption across the two databases.

Ordinary current invocation bindings and immutable operation provenance remain in the original typed operation rows, such as `upload_operation`, with their existing finite semantic slots. The journal adds no append-only operation, receiver or invocation history. A slot contains at most one current receiver. The recovery row contains at most one active control invocation. Typed historical outcome retention is distinct from disposable journal state.

Journal statements use primary-key lookups or the fixed 64-slot scan. Set `max_page_count=4096` at the fixed page size: the main database cannot grow beyond 16 MiB; allocation failure fences new work. Disable automatic vacuum and explicit VACUUM in active operation, use no temporary sorting, and keep only one bounded journal connection/native job per admitted owner. Before registration, at most one registrar owns a temporary journal control handle/job after acquiring commit admission; it closes that handle/job before releasing `commit.lock`. This is a bounded registration resource, not a 65th ordinary participant. Contenders allocate no task/connection; metadata checkout and receiver construction remain forbidden until durable slot admission. The main-page cap is not a claim about total filesystem bytes or RSS: rollback-journal high water, native cache and temporary files need measured qualification under the bounded transactions. No unbounded WAL is created by this selected journal mode. Error output is bounded and content-free. Journal-full, corruption and synchronization failure retain original pending custody, not an empty replacement database.

## 3. Original metadata COMMIT protocol

All metadata writes participate, including writes unrelated to storage. Admission happens before any writable checkout, connection initialization or domain lock. The real source paths and bypass obligations are enumerated in the dated inventory. A positively checked transaction owns its checkout, cancellation shield and completion result through the following phases.

| Phase | Ordered operation and durable result | Failure/cancellation behavior |
| --- | --- | --- |
| Admission | Acquire native commit admission; verify anchored journal, issuer, generation, confirmed metadata frontier and no pending row. Acquire the actual writer, validate native durability and begin. Capture its native transaction identity. | Refuse before lending on mismatch. The original owner retains the checkout and guard through actual closure under [section 3.4](#34-native-release-outcome-and-recovery). |
| Preparation | Perform domain work under existing locks. Revoke the writer loan and join its native work. Check current native identity and settings, allocate the journal commit sequence/token and durably insert `prepared`. Prove original continuity at the metadata frontier compare-and-set from the exact previous triple, within the same domain transaction. | Failed journal persistence or continuity check prevents COMMIT. If persistence is uncertain, retain admission and resolve the original journal operation. Only confirmed absence of `prepared` and affirmative no-dispatch allow the pre-preparation closure path in section 3.4. |
| Dispatch | Recheck qualified settings and continuity on the exact metadata writer. Durably change `prepared` to `dispatching`. The original owner may issue its one native COMMIT only after persistence, the successful frontier compare-and-set (or first-frontier insert) and the final native continuity check. | `prepared` after affirmative issuer/native exclusion proves no COMMIT dispatch. `dispatching` does not prove that COMMIT ran. Cancellation between these actions remains unknown unless the original owner establishes rollback/no-dispatch. |
| Native completion | Retain a write-once in-memory result from the original native task: committed, affirmative rollback before any successful COMMIT, or unknown. Shield native completion through requesting-coroutine cancellation. | A later rollback, pool reset, connection close or cancellation exception cannot overwrite committed/unknown with aborted. Deadline expiry closes useful work but leaves the original resources owned. |
| Settlement | Release actual metadata cursor, transaction and checkout; durably record the affirmative `committed` or `aborted` result in the pending journal row. For committed, atomically advance the confirmed triple and remove pending. For aborted, remove pending without advancing; the allocated sequence remains consumed. | An uncertain journal update is resolved by its exact token. No new writer starts while pending remains. A crash before result persistence may require native recovery even when the caller observed success. |
| Reliance | After journal confirmation, return the saved domain outcome or admit an exact provider invocation. Positive custody read and all DB resources finish before provider entry. | A lost response repeats only the original domain receipt. It does not allocate a new mutation or infer absence. |

An original native task that observes success but loses its journal write keeps ownership until journal settlement or real process loss. `Database.close()` returning after its deadline is not that closure: current code may retain units and dispose later. Future custody shutdown must distinguish a refusal/unfinished shutdown from actual release. Native rollback failure also preserves the unresolved pending owner.

Pending `committed`/`aborted` is a durable outcome only because the native owner produced it under the qualified profile; callers cannot construct those facts. Recovery may finish journal compaction from either state after checking exact bindings and coherent metadata. No subsequent write is admitted until it does. The `prepared` no-dispatch branch additionally excludes the original native owner and any copied/inherited dispatch capability before clearing the pending row.

Plain read paths must be demonstrably read-only on both databases. The ordinary reader implementation under [#1600](https://github.com/realkarych/kora/issues/1600) establishes PostgreSQL native READ ONLY before caller access while preserving READ COMMITTED and the shared pool; snapshots retain their separate setup, and SQLite retains query-only readers. This supplies only the plain-read access mode. Qualification of checkpoint-capable connections, journal continuity and the remaining custody producers is still pending. Exposed SQLAlchemy engines must not provide an unmanaged writable checkout when custody is active. A driver-error classification accessor replaces the current harmless dialect-only consumer. Trusted administrative writes, direct SQL and external maintenance cannot bypass the profile. SQLAlchemy pre-COMMIT events alone cannot implement post-COMMIT outcome ownership.

A qualified application read must stay natively read-only from handoff through every admitted operation and actual native work closure. The borrower cannot end or replace the read transaction, change its access mode, or retain a writable-capable checkout, cursor, driver or pool capability. Cancellation revokes further borrower entry and leaves queued operations, cursors, transaction and checkout with their original owner. Only that owner closes or retires the read transaction and resets or returns the checkout after actual work closure. Pool reuse cannot expose a writable interval to the reader or its retained work. The #1640 all-writers integration must prove this for plain and snapshot reads, including PostgreSQL's shared pool and SQLite's qualified checkpoint paths. This is an activation condition. The implementation plan owns the exact read interface and resource accounting. Ordinary-mode getters, read scopes, snapshot deadlines and migrations retain their existing contracts.

PostgreSQL Alembic autocommit/concurrent-index work is not wrapped by this ordinary handshake. Active custody refuses migration entry before a connection or session advisory lock. Initial migrations run only inside fenced provisioning before effect admission. Later migration requires an explicitly qualified whole-image transition while useful work and old issuers are closed; this first native design does not supply arbitrary upgrade transitions. The preexisting ordinary-mode migration command remains available for installations without active custody. No active-profile upgrade may pretend that an empty autocommit block is a read-only operation.

### 3.1. Exclusive managed writer and loan

The trusted database composition selects the qualified owner before any writable engine checkout or initialization. After verifying lifetime and commit admission, that owner controls the actual pool checkout and native connection, the original transaction and its one completion cell. The cell is private, write-once and tied to this owner, the original native binding and the exact pending token. Creating a journal transaction or holding a domain lock grants no terminal or settlement capability.

| Entry | Owner and permitted work |
| --- | --- |
| Untimed `Database.transaction` and `Database.run` | Enter the qualified owner before the existing lease/checkout boundary, preserve one managed unit and its existing ordered run/scope/address locks, and lend domain operations only after native admission. `run` retains its original result under requester cancellation; any confirmed public result still waits for custody settlement. |
| Timed `Database.transaction(admission_deadline=…)` | Use the same owner. Keep the original absolute admission deadline through local admission, checkout, native entry, durability checks and handoff. Preserve typed refusal before handoff and the existing busy/lock wait and restore behavior. Admission expiry closes entry and joins the original native entry and cleanup. A successful handoff ends the entry timer. |
| Fenced provisioning | The reserved owner runs the dedicated, version-bound migration lease of [section 4.1](#41-provisioning-and-ordinary-startup), with its own whole-workflow result and actual cleanup. It uses the exclusive original writer for the first frontier only after that lease closes. No domain loan exists during schema installation. |
| Maintenance, replacement and shutdown | Only the owner may perform qualified connection setup, safe per-connection maintenance and cleanup, including native reset or verified retirement. Any checkpoint-capable SQLite path participates in the qualified profile. Active-schema changes and image replacement follow section 4. Ordinary shutdown closes admission before joining actual owners and may return an unfinished status under its existing finite deadline. |
| Ordinary database and plain reads | Outside the qualified profile, retain the existing engine getters, transaction/timeout behavior and dedicated migration path. In a qualified profile neither engine getter, including a reader getter sharing a PostgreSQL writable pool, can grant a writable checkout. Application read entry points retain their native read-only modes. A dialect/driver error classification accessor returns classification only. |

The loan gives one designated managed task a revocable database operation interface. It exposes a closed backend discriminator, the existing current-writer and one-lock-context checks, and execution of registered, typed domain operations. An operation selects repository-owned statements from typed bound inputs, checks its existing read/write and row/byte scope, and returns detached typed values. This includes scalar and bounded row results, generated identities and affected-row counts where the caller needs them. Registration belongs to the database owner and is unavailable to the loan. Dynamic values bind as data. Native same-writer mode or layout observations needed by domain code are bounded typed owner operations. Existing constant lock and inspection statements remain eligible through their specific operations, with their original semantics and deadlines.

The loan exposes no connection, engine, dialect object, mutable connection information, transaction handle, driver, cursor/result context, arbitrary executable or connection callback. It has no transaction-control, savepoint, session-configuration, pool or cleanup operation. Both the writer lock context and results must preserve this boundary. The owner consumes and closes native results within the registered operation, including when conversion or cancellation fails. No checkout-backed value survives return. Only supported existing qualified operations may enter this interface. An unadapted writer prevents that composition from activating.

Each operation rechecks the exact loan and task before entering the delegate. The owner reserves the single operation slot before native scheduling. Concurrent, cross-task or revoked entries refuse before allocation. The transition out of the loan closes new admission synchronously before any terminal await, then joins the admitted operation and closes its real cursor/native work. Capture terminal disposition only after this join. Cancellation, callback failure, entry refusal or shutdown cannot transfer a checkout, terminal job or journal ownership to a second task. A late callback or retained loan cannot use a later owner, including on a reused pooled physical connection.

Cancellation before handoff closes entry. Cancellation or failure delivered inside the domain unit revokes the loan and selects original rollback if COMMIT has not been authorized. Requester cancellation outside a protected unit such as `Database.run` waits for that unit's actual disposition. Once native COMMIT can run, cancellation or a shutdown deadline cannot select rollback or alter its recorded result. Shutdown closes useful admission and joins the retained owners. Any return while those owners still hold resources or pending evidence reports unfinished shutdown.

Only the exclusive owner may attempt the frontier change. Its conditional write checks the original metadata and journal binding and exact previous frontier, and must affect exactly the singleton within the original native transaction. The first-frontier provisioning branch requires the original empty frontier and exact initial binding and must insert that singleton once. The same owner verifies the exact result before permitting terminal COMMIT. A failed comparison, insert or unknown update gives no dispatch permission.

### 3.2. SQLite continuity witnesses

Select the private SQLite connection factory only in the qualified writer composition. The standard [SQLite connection factory](https://docs.python.org/3.14/library/sqlite3.html#sqlite3.connect) provides the actual native connection used by the existing aiosqlite worker. Bind its original file anchor, connection and transaction sequences, and the qualified WAL/FULL settings, including macOS full-sync checks. Establish the actual native `BEGIN IMMEDIATE` and verify that the root is open before installing either witness. A SQLAlchemy root or DBAPI transaction-active flag alone provides insufficient continuity evidence.

On that native worker create two private, owner-generated [nested savepoints](https://www.sqlite.org/lang_savepoint.html), outer then inner, within the already open root. Their names are fresh and inaccessible through the loan. Neither savepoint owns the outer transaction. There is no durable marker row or reusable name across roots. Existing ordinary transactions and the separately owned provisioning migration keep their own nesting behavior. A qualified domain loan begins at the original root and cannot open, receive or retain a nested transaction.

Before dispatch of each domain mutation, the serial native owner checks the same physical connection and original root binding, the live native transaction state and its armed, unpoisoned witness gate. The check and dispatch run in the same native work turn. A registered operation with multiple statements or batch entries checks each native mutation individually. It cannot delegate a batch that conceals those dispatch boundaries. The owner excludes transaction control from domain operations and checks for loss of the original native root on statement completion, including when SQLite automatically rolls it back. Loss or uncertainty poisons and revokes the loan before any further domain statement can run. The owner refuses further mutation without permitting autocommit, automatic transaction restart, witness re-arming or a replacement owner. The native active flag is useful here only within this exclusive, non-restarting ownership. The two private witness releases still prove exact continuity at the frontier and terminal boundaries below.

After revocation, native delegate closure and durable `prepared`, the owner releases the inner witness. The exact frontier change runs only with that witness release and a same-turn check of the still-open original root on the exact native connection. The outer witness remains across frontier work and the durable `dispatching` update. For the terminal operation, one turn of the real native worker checks the connection, open native root and terminal durability settings, releases the outer witness, rechecks that the native root is still open and calls the original SQLite COMMIT without yielding or enqueuing a second operation. The owner records successful native completion before allowing wrapper teardown. Both releases require their original nested witness and an already open root. No second COMMIT is issued.

Missing witness, changed connection or anchor, inactive root, failed frontier comparison, rejected settings, or unclosed delegate work denies positive dispatch. A live pre-COMMIT abort may record `aborted` only when the original owner positively observes original rollback or established no-dispatch with actual native exclusion. Otherwise it retains the exact pending row, if allocated. An error at the terminal operation is never upgraded to success by later wrapper behavior. Cleanup retires the original witness state with the actual connection/transaction; reuse of a physical connection starts with unarmed state. The savepoints prove continuity and not physical crash persistence.

### 3.3. PostgreSQL native completion and timeout admission

Select the [public asyncpg `connection_class` extension](https://magicstack.github.io/asyncpg/current/api/index.html#connection) through the locked SQLAlchemy asyncpg dialect and trusted qualified composition. The observer is part of the actual asyncpg connection used by that checkout. It forwards the existing native terminal command once and observes its public command tag. Ordinary connections, unarmed traffic, arguments, server errors, close and pool reset retain their existing behavior. The owner must verify this forwarding and observation on the actual locked dependency versions using public interfaces. A known unsupported adapter, version or configuration refuses before writable checkout. After checkout and before lending or allocating a pending row, verify that the actual driver object supports the qualified observer and matches the trusted composition. Refuse a mismatch, retire that checkout and dispatch no domain work.

Qualified composition requires the effective asyncpg independent `command_timeout` to be unset and submits no per-command client deadline on the owned terminal path. Reject incompatible options before constructing the qualified writer pool and verify the actual connection was created by that exact composition on each checkout. This does not change the connection establishment timeout, existing pool/admission deadlines, server-side statement or lock controls, or timeout behavior outside custody. A disconnect, server cancellation or shutdown can still leave an unresolved original outcome. Closing the requester does not end server work.

Before the loan, verify the actual native mode and authenticated cluster/database, server and backend incarnation, then assign and capture the full original `xid8` inside the live writable READ COMMITTED root. Verify exact native connection, mode and original XID before the frontier change and again before terminal dispatch. A recheck uses [`pg_current_xact_id_if_assigned()`](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-PG-SNAPSHOT) and cannot create a replacement XID. A logical SQLAlchemy root, autocommit statement or native transaction-active flag alone cannot supply either recheck. Original settings and applicable durability, role and replica checks still apply. There is no borrower or unrelated native command between the terminal recheck and dispatch.

The original owner arms one observation for its exact physical driver object, terminal operation and task after the frontier and durable dispatch conditions hold. The exact COMMIT tag from that forwarded command is the positive live result. A different tag, absent tag, ambiguous error or disconnected transport leaves it unknown. An affirmative live rollback requires the same original identity established before sending the one owned rollback and its exact native rollback completion. A failed transaction that cannot prove its original XID stays unknown. Later rollback, pool reset, wrapper close, invalidation and a new connection never supply original-abort evidence. A failed tag observation cannot be retried by issuing another COMMIT. Disarm the one-shot observation on every exit before reuse or retirement.

### 3.4. Native release, outcome and recovery

Only the exact original owner can mint an in-memory terminal fact and pass it to its bounded journal settlement operation. That operation rechecks the lease, original native binding, phase, sequence/token and exact previous/next frontier. Neither ordinary journal callbacks nor domain code can allocate a dispatch permit, record a terminal result or compact pending. The completion cell remains empty while the native command can still return a result. A confirmed COMMIT or abort stays latched even when the waiter is cancelled or the settlement write fails. Before writing a durable terminal journal result, the live original owner joins its actual native work, positively verifies original transaction and lock release, and observes actual cursor and checkout release or retirement. A healthy PostgreSQL backend may remain in the pool after that proof. The owner retains commit admission through durable recording and compaction or until actual process loss. The reserved recovery owner may compact a durable original result or establish affirmative recovery evidence only through [section 4.2](#42-resolving-the-original-pending-transaction).

**Failure before durable preparation.** The original owner closes any loan and proves under its held admission that preparation never started or that the original journal operation settled without a `prepared` row. It also proves that the original terminal permission was never armed or issued. Together these facts prove no dispatch. A missing response, unverified journal or absent row on a newly opened authority supplies insufficient proof. If the original journal operation installed `prepared`, use that exact pending row. There is no fabricated pending token or terminal classification for the pre-preparation failure.

With proven no-dispatch, the owner still holds admission and accounts for the original native job, checkout, transaction and locks until their actual closure. Before reopening admission, verify either that no native writer was acquired or that the original native transaction ended, its server-side writer and locks can no longer act, the actual checkout was released or permanently retired, and the existing authority and confirmed frontier still agree. A confirmed original PostgreSQL rollback on an orderly live connection may prove transaction and lock release. An uncertain transport requires actual local retirement and affirmative native evidence of closure on the pinned PostgreSQL authority. Wrapper close, process death on the core host, or passage of time cannot certify remote closure. While closure is unproven, keep useful admission fenced and the original resources charged. No recovery borrower or detached replacement writer can take them over.

The existing format may contain no durable backend or XID binding for this pre-preparation phase after process loss. In that case, any qualified profile must prove original backend and lock exclusion through its existing accepted native ownership or recovery guarantees before any writer can reuse admission, including a previously registered peer. If those guarantees cannot establish exclusion, the implementation plan must identify the exact missing proof for an owner decision. Until then that profile remains fenced. This design supplies no new durable state or operator procedure to bridge that gap.

**Unresolved durable pending.** Keep an unresolved original native job and its checkout owned while live. After native work actually ceases, an uncertain transport must be permanently retired with actual local cleanup before its checkout charge can be released. Local retirement does not establish remote backend exclusion or make shutdown complete. The durable pending row preserves the exact saved binding and fences new writers. After the original owner relinquishes its local resources and exclusive lease or after its native process exclusion, only the reserved observer can resolve that binding under section 4.2. It never borrows the original writer or replaces the pending binding. Cancellation while an affirmative result is still locally recoverable through its original owner cannot transfer it to that observer.

The existing commit admission, one ordinary or reserved issuer slot, and existing pool/checkpoint admission fund this ownership. At most one physical checkout, one running native metadata operation (including terminal or cleanup), one loan, two SQLite witnesses or one PostgreSQL observer and one in-memory result belong to the active qualified writer. Journal work uses the existing short transaction and job bound. Keep the ordinary slot unavailable through its actual closure and any unresolved record. No extra pool overflow, waiting queue, result history, task replacement or timeout-driven rollover is admitted. A rejected contender allocates no writer task or checkout. Reserved recovery remains available with the ordinary registry full, subject to the original pending and recovery-lock rules.

## 4. Recovery, provisioning and coherent images

### 4.1. Provisioning and ordinary startup

Provisioning first establishes that metadata is a new empty installation and the selected provider is a new empty domain through their actual native producers. It anchors and persists the journal in `provisioning`, with zero confirmed frontier and the single provisioning row in schema_running. No ordinary writer, public result, receiver or provider effect is admitted. The reserved recovery owner holds exclusive lifetime and commit ownership; schema installation is a fenced bootstrap procedure, not an ordinary custody transaction.

That original owner opens one dedicated migration lease and durably records its native connection binding before Alembic dispatch. It owns every actual setup, per-migration transaction, autocommit statement and cleanup call identified in the writer inventory, with no implicit reconnect/replacement. It retains their original completion through cancellation. Only successful completion of the entire schema installation, the expected Alembic revision and actual release of the native migration lease allow a durable transition to schema_complete. The owned schema installation creates the empty frontier relation in its selected target migration; it inserts no fabricated confirmed row. Layout/constraint correctness is covered by migration tests, not runtime introspection.

If initial migration completion or its journal persistence is unknown, retain schema_running and the original connection binding. A still-owned original native task may finish and persist its actual aggregate result. After loss of that owner, reading the expected Alembic head, finding no backend, or observing partial tables cannot manufacture successful aggregate completion. This first profile refuses continuation in that state; it supplies no automatic migration replay, destructive reset, fresh journal or caller-provided completion override. That conservative availability limit is explicit. Absence of a persisted connection binding permits resuming before first dispatch only after affirmative original owner exclusion.

From schema_complete, persist frontier_running and execute the first pending handshake. This one admission branch requires provisioning mode, the exact original binding, zero confirmed frontier, completed schema owner and no ordinary participant; it does not require an existing frontier row. Preparation inserts the singleton with the exact allocated next triple and zero previous triple. All subsequent transactions require and compare the existing singleton. A crash in this first transaction follows the same prepared/dispatching/committed/aborted rules; unknown original outcome cannot authorize another initialization. After confirmation and native release, atomically select active and remove the provisioning row. The reserved owner never supplies a second ordinary participant slot. An existing domain with a missing journal never qualifies as new.

On startup, the one recovery coordinator checks supported persisted versions, native anchors and every persisted binding before registering ordinary work. It trusts the migration-owned schema. It settles any pending COMMIT, closes or retains old participants and establishes current native durability. A live old participant may continue only in its captured unchanged authority with its original ownership intact; startup of another process cannot rotate around it. Rotation seals admission, excludes all old issuers and native operations, takes exclusive lifetime ownership and advances the journal generation. The metadata frontier change uses the same handshake while admission remains closed. Failure leaves the new journal generation fenced; it never rolls back to reuse an old generation. Existing typed operations retain original provenance through rotation and authorize only their contract's recovery calls.

Ordinary restart of the same native files relies on the qualified crash-recovery producer and actual preservation of their anchored lineage. An operator who replaced/restored files must use the offline procedure instead. Root identity and singleton equality cannot detect a trusted operator's in-place partial rewrite; this is outside ordinary restart's assumptions, not a newly permitted restore method.

### 4.2. Resolving the original pending transaction

For SQLite, keep the original native completion task until it returns whenever its process still exists. After actual process/native exclusion, native hot-journal/WAL recovery of the unchanged metadata installation may establish a coherent image. An exact pending token in that image, with qualified durability and no intervening writer, permits confirmation of that transaction. An old token or absent row alone never proves rollback. `prepared` plus proven no-dispatch, or the durably saved original `aborted` result, can establish abort; otherwise retain pending. No file copy or current-object observation substitutes for this producer.

For PostgreSQL, assign and save the full transaction ID on the original writer using `pg_current_xact_id()` before dispatch. On the same pinned cluster/database authority, the reserved recovery observer checks `pg_xact_status` for that original ID. `in progress`, NULL, errors or changed lineage retain pending. The `aborted` outcome requires coherent unchanged or recovered authority and the previous frontier. The `committed` outcome requires the exact pending token and the required WAL and replica persistence. A new transaction ID cannot replace the saved ID.

The reserved observer may settle, compact and reopen admission only with the exact original outcome (or `prepared` with affirmative no-dispatch under section 3) and affirmative closure of the original native work, transaction and locks. Bind closure to the saved original server and backend incarnations and transaction on the pinned authority, and to actual original local resource retirement or native process exclusion. Status alone, a wrapper close, a bare PID observation or inspection of a replacement session cannot establish that closure. A healthy backend may remain alive after the original work, transaction and locks are affirmatively closed. An already durable original terminal result carries the original owner's closure proof from section 3.4, subject to rechecking the saved binding and coherent frontier before compaction. Otherwise the reserved observer needs a positive native closure producer supported by the qualified installation. The implementing plan must identify and test that producer. If there is no applicable approved source of closure proof, the owner must decide the prerequisite before the branch can activate. Until both proofs are available, retain the original pending row, associated charges and refusal of new writes.

An unknown outcome with a durable row retains the exact existing `prepared` or `dispatching` row. Unknown requires no additional persisted state. Recovery runs only with the existing coordinator, scope and native admission. It verifies the original binding and prior/pending frontier before using the native observations above. It has no replacement writable checkout for that operation or access to the original writer's terminal path. Reserved recovery can resolve an unproven original rollback when the full saved XID, original native closure, previous frontier and coherent authority all agree. A [pre-preparation failure](#34-native-release-outcome-and-recovery) without such a row follows original writer and backend exclusion, with no saved XID presumed.

Where the original synchronous COMMIT completion is unavailable, this design allows a separate trusted offline recovery operator to complete a native CHECKPOINT after observing the original transaction committed and before confirming its token. The observer binds the same cluster/database, current server incarnation and completed checkpoint to the original pending token; a lost checkpoint response retains unknown and may repeat the physical checkpoint only after its original native owner closes. The checkpoint is a physical persistence barrier, not a domain mutation or substitute token. It cannot excuse a prior settings downgrade or establish a stronger remote-replica acknowledgment. With a stronger replication policy, confirmation still requires its original completion or separately qualified replica evidence; otherwise it stays pending.

That recovery operation requires PostgreSQL's checkpoint privilege. It belongs to the separately authorized operator procedure, never ordinary API, scheduler or worker credentials. The owner accepted that bounded recovery privilege/procedure in #1586; #1575 alone did not. Missing privilege leaves recovery pending rather than silently granting it or using a weaker assertion. No prepared transactions, logical decoding, replication failover or external consensus dependency is introduced.

### 4.3. Offline image procedure

The producer owns an entire image operation, not a caller-supplied `restore_verified` flag. Seal useful admission; hold the reserved recovery owner, exclude original native writes/effects and all ordinary participants, and acquire exclusive lifetime and commit ownership. Resolve pending COMMIT first or preserve it as an explicit unresolved original transaction. Persist `restoring` and its single `image_transition` with original source/target anchors before touching metadata files. Native copy completion and complete streamed manifest verification advance copying to complete; installation and persistence advance complete to installed. Never include the independent journal in the metadata image replacement.

For SQLite, use the native backup API on the complete original database after fencing, with its real source/destination handles, native completion and error handling. Keep the destination private until completion, close native handles, persist its files and parent directory under the qualified filesystem method, and install only that complete image under exclusive ownership. Do not copy just a main file while ignoring WAL, mix pages from different images, or selectively copy custody/allocator relations. The source frontier is captured while writes are excluded; the destination's supported migration/record versions, complete-image provenance and exact frontier must agree with the retained journal. This does not re-verify its migration-created schema. An older coherent image still fails continuity if its frontier predates the last relied-on commit.

For PostgreSQL, use a complete physical base backup plus its required WAL and timeline history, restore it offline with complete native recovery, and verify the original cluster/database binding and exact custody frontier. The operator owns the actual backup/replay process and its resource completion; a manifest checksum or logical table dump alone does not establish this source. This design permits no failover to an independently writable clone or arbitrary timeline selection. A target missing the exact confirmed or unresolved pending transaction cannot be repaired by copying the singleton from another target.

After image validation, original issuer/effect closure and pending settlement, advance authority through the normal rotation handshake and atomically persist `active` while clearing the image row. Interrupted backup/install/replay remains `restoring`. A successor first closes/excludes the original copy/replay process, then matches the exact retained source/target anchors, phase, manifest and frontier before resuming that same transition. Missing or ambiguous completion permits only preservation or disposal of a proven uninstalled private copy; it never permits adopting a target or deleting the only original image. The producer owns its native handles, subprocesses and temporary disk reservation until actual close and safe removal. Neither temporary-file cleanup nor a successful new connection opens admission. If complete provenance cannot be established, refuse activation and keep witnesses/charges. Journal loss, damage, substitution, known rollback or simultaneous rollback with metadata/provider still requires a separately accepted independent continuity source. This design cannot reconstruct it.

## 5. Invocation and upload-retirement boundary

Before any positive issuance check, reserve an existing bounded dispatch slot and capture the actual receiver, issuer and next non-reused invocation sequence. Register that owner durably in the original typed operation through the COMMIT handshake. Positive custody checking then verifies the exact still-open operation, current authority, original request and current receiver. All database resources close before the dispatch owner calls the provider. Registration covers the interval before provider entry: a paused callable is already an outstanding owner, even if the provider has no receipt yet.

Closing issuance atomically prevents new registration and positive admission, then joins every previously registered original owner, including queued/pre-entry work, native futures, readers, parsers and finalizers. An owner paused after its positive check still has to finish or be natively excluded; a metadata state change does not retract that permission retroactively. Durable closure records must identify the exact operation and completed resource set. Only then may the typed stage's actual retirement/release acknowledgment contribute to its storage closure. Process death, timeout, absent receipt, an error from a stale receiver and a reconstructed receiver each fail to prove that closure alone.

The [upload-retirement contract](upload-retirement.md), published in [#1583](https://github.com/realkarych/kora/pull/1583) under the [approved #1581 plan](https://github.com/realkarych/kora/issues/1581#issuecomment-6893519377), retains protection for the complete declared/source/retained address union while native storage closure is pending. Its `retained_admission_generation`, `cleanup_generation_floor` and `storage_closure` fields belong to that separate specification and remain unimplemented. This journal supplies original commit continuity and issuer/native closure evidence to that producer; it never supplies an unchecked boolean. A deletion performed before a delayed original promotion can still create bytes cannot release the upload's final charge. Unknown COMMIT or acknowledgment keeps protection and full charge. No alternative delete intent, settlement or acknowledgment DTO is added.

The first useful integration remains an actual refused-upload lifecycle: admitted owned stage, real promotion attribution, irreversible original closure, then eligible other-owner release or exact admitted deletion, original observation/settlement, provider acknowledgment and exactly-once core reservation release. No production source currently composes this path. A conformance call, unused journal service, proof-object constructor or flag keeping every effect unavailable is not its implementation. Worker sealing/reports and scheduler settlement remain downstream until their real producers exist.

### 6.2. Physical qualification

Record the exact kora revision, SQLite library/build/VFS, PostgreSQL server build, drivers, OS/kernel, filesystem/mount options, device/controller/firmware, volatile caches and power-loss protection, journal and metadata placement, sync behavior, server settings, replica policy and cut-controller identity. Changing a relevant input invalidates that profile's physical conclusion. A qualified profile is a concrete installation configuration, not just “Linux”, “macOS”, “SQLite” or “PostgreSQL”. No profile has yet passed this method.

Record the actual qualified writer adapter and effective driver timeout mode with those inputs. Original-transaction evidence is a prerequisite to relying on a native completion. It does not satisfy the storage, operating-system or remote-replica cut cases.

Use a separate observer outside every power/reset domain being cut. It durably records the exact acknowledged journal/metadata commit and immutable operation/outcome identities before the cut controller proceeds. The controller's barrier pauses the real workload after acknowledgment and before any unrelated explicit flush/checkpoint; it does not call a graceful database or OS shutdown. Trace the actual synchronization and checkpoint path needed to show which boundary was exercised. If an incidental checkpoint/flush wins the race, that run has not exercised the intended window and is inconclusive, not a passing sample. Guest-process kill tests only process failure; guest reset cannot establish host cache/device power-loss behavior. The declared cut must remove the failure domain whose guarantee is claimed, with actual power interruption where the storage guarantee requires it.

| Deterministic cut or adversarial case | Required recovery assertion |
| --- | --- |
| Journal `prepared` durable, before dispatch permit | No effect response occurred; after original native exclusion, no-dispatch can abort without reusing its sequence. |
| `dispatching` durable, COMMIT sent, response withheld | Retain exact original pending owner until affirmative native settlement; no replacement mutation. Cover PostgreSQL server continuing after client-host loss. |
| Metadata COMMIT acknowledged, journal confirmation not complete | Resolve the same token from original completion or qualified coherent recovery; no response/effect may have relied early. |
| Confirmed journal and external success acknowledged, before unrelated flush/checkpoint | After the actual system/storage cut, exact journal frontier and complete metadata owner/intent/generation/allocator state survive; provider witness and charge remain sufficient for the original operation. Any lost acknowledged relied-on fact fails qualification. |
| Provider effect completed, response/acknowledgment withheld | Exact original observation and release resume without duplicate semantic effect, early compaction or repeated charge release. Include pre-entry paused invocation and stale receiver reconstruction. |
| Restore old image; equal allocator with missing custody; copied singleton; wrong journal/provider root | Every incomplete or mismatched image refuses effects. A verified complete image matching the independent frontier can resume only after original closure and rotation. |
| All 64 ordinary slots retained; coordinator repeatedly crashes | Reserved recovery still observes/settles eligible original work, with one active control invocation, no append-only coordinator history and no ordinary admission until capacity truly frees. |
| Cancellation/shutdown with blocked commit, reader, native provider job or finalizer | No premature lock/slot/checkout release; deadline reports unfinished closure. Once native completion is released, all actually releasable resources close. |

Exercise SQLite metadata and the independent journal separately and together; for remote PostgreSQL cut the core host, database host/storage and their combined relevant failure domains. Include a negative control with deliberately insufficient persistence in an isolated fixture; it must be rejected as ineligible or expose the lost guarantee, never qualify an ordinary-mode installation. Inspect recovered state through complete typed owners and exact original provider observations, not only a frontier counter. Native resource barriers and real processes/storage enforce ordering; no mocks or patched transports may stand in for native completion.

Blocking assertions are exact original outcome/authority, complete restore, actual resource closure, capacity admission and no lost acknowledged custody. Latencies, sync/checkpoint waits, throughput, journal physical high water and RSS are reported separately; deterministic page/slot/owned-buffer limits remain blocking. The real consumer must also satisfy applicable NFR-3 requirements without turning this document into an unapproved numerical method. Repeated workloads verify stable disposable rows/files and exact released resources; retained domain history is reported separately. Qualification reports name every unexercised failure domain and provide no broader claim than the tested method permits.

Diagnostics follow [observability](observability.md): INFO for bounded lifecycle transition, WARNING for busy/unresolved original work, ERROR for persistence/identity refusal, with catalogued safe reason/state/count fields. No journal path, credential, commit token, payload digest, native exception text or retained request enters diagnostics. Output failure cannot block closure or authorize it. The implementing #216 issue owns event registration and success/failure/cancellation/shutdown evidence before activation.

## 7. Implementation ownership and remaining decisions

Proposed `db` modules own journal native rows/locks, scalar process and storage binding interfaces, writer participation, original completion and native metadata recovery. They import only existing allowed `ir` and `observability` packages. Composition roots adapt the existing native process-identity reader and actual selected provider into those bounded interfaces; data fields alone cannot fabricate their owned lifetime. `engine` owns domain custody transitions and invocation/retirement orchestration over `db` and `protocols`; the storage provider continues to own its private epoch and physical effect closure. No `db` import of `runner`, `protocols`, `engine` or `plugins.storage`, new dependency or widened layer row is selected.

The exact rows and procedures above refine accepted #1575. Owner acceptance in #1586 explicitly covers the rollback-journal profile, native formats, read-only/bypass enforcement, active-profile migration refusal, checkpoint recovery privilege and coherent-image/system-crash method. The [revised sizing](../research/execution-custody-native-plan-2026-11-15.md#complete-delivery-and-size) counts their missing implementation and the real consumer. It establishes no independently mergeable first implementation within 1,000 production changed lines and proves no indivisibility lower bound. No code may start on an assumed exception. The next implementation plan must either demonstrate a useful complete bounded cut or obtain a prior explicit bounded owner exception; native qualification and required tests remain part of that delivery.

The #1738 refinement uses existing `db` and trusted composition ownership. It selects no public operation, new durable format, database privilege, supported platform or dependency. The implementing plan must reconcile the actual writer inventory, registered domain operations and checkout accounting under [#1640](https://github.com/realkarych/kora/issues/1640). The owner authorization for this design does not expand #1640's implementation approval or authorize qualification or activation.
