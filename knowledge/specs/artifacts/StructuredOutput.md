# StructuredOutput revision 1

Status: owner-approved contract publication under [issue #246](https://github.com/realkarych/kora/issues/246), dated 2026-10-23. Models, providers and consumer execution remain pending the activation owners below. Governing decisions: [ADR-0008](../../../docs/decisions/0008-content-bound-approvals.md), [ADR-0018](../../../docs/decisions/0018-immutable-attempt-history.md) and [ADR-0026](../../../docs/decisions/0026-package-layers.md). The schema, descriptor and behavior identities are immutable; an incompatible revision needs a new identity. Deployment resolves only its saved closure, never current aliases. [Numerical sources and fixture provenance](../../research/structured-output-contract-2026-10-23.md) are evidence, not mutable authority.

## 1. Payload, limits and immutable identity

`StructuredOutput` revision `1` has no parent. Its draft-2020-12 schema has `$id: urn:kora:artifact:StructuredOutput` and admits object, array, string, number, boolean and null. `number` includes JSON integers. The payload is the value itself; neither `schema` nor `data` is a reserved payload member. A root null is a produced value, distinct from no selected output, an absent artifact, an expired payload or unavailable summary. `OutputCandidate(value=None)` is distinct from an absent candidate. Schema annotations never insert defaults or coerce values.

Validation behavior: `kora.structured-output-validation.v1`; whole-payload selection and identity summary: `kora.json-payload.v1`, with selection `[""]`. The per-type descriptor includes the exact schema-byte SHA-256, every limit below and numerical/canonicalization identity `kora.structured-json.v1`. That identity names the rules below rather than mutable Python defaults. VcsRef bytes, descriptor, schema, hashes, limits and URL grammar remain unchanged.

The closed [revision descriptor](StructuredOutput.revision-1.json) has `name`, `builtin_revision`, `schema`, `parent`, `behavior`, `validation`, `canonicalization`, `compatibility`, `digest_selection` and `schema_sha256`. `validation` contains exactly `max_raw_json_bytes: 1048576`, `max_canonical_json_bytes: 1048576`, `max_json_depth: 16` and `max_integer_bits: 14000`; `canonicalization` is `kora.structured-json.v1`. `compatibility` contains exactly `execution_semantics: kora.execution.v1` and `checker_view: kora.structured-output-view.v1`. Name/revision/URN/parent/behavior/root selection are as specified above. The schema hash covers the committed two-space-indented UTF-8 [schema](StructuredOutput.schema.json) bytes with their final newline; the publication test pins those exact bytes.

The raw and canonical payload limits are each **1,048,576 bytes**, nesting at most **16** object/array containers (root container depth 1, scalar depth 0), integer absolute magnitude at most **14,000 bits**. These are new explicit StructuredOutput revision parameters, not changes to ordinary IR embedded data or database JSON. No new global integer setting or restriction on existing large-integer IR tests is permitted. Smaller transport/form/producer limits remain independently applicable; this contract does not raise them or guarantee that every harness supports every root kind.

A custom type whose saved parent chain reaches StructuredOutput inherits this frozen parent's admission domain, limits and canonical numerical rules in addition to its own saved behavior and every parent schema. A child behavior cannot waive a parent refusal. `List[T]` remains a distinct derived contract: its items use the saved T contract, while list-container admission/aggregate limits remain independently defined by the saved list semantics; element ancestry alone does not impose StructuredOutput's 1 MiB whole-artifact ceiling on an entire list. No new list-wide numeric/size contract is silently introduced by this publication.

The raw-byte ceiling applies when the admitted wire envelope is that typed value. An already decoded embedded list item has no independent raw encoding: apply its inherited canonical-size, numerical, Unicode and root-relative depth domain without inventing raw bytes or serializing it before budget checks. The enclosing list's wire/aggregate policy remains independently applicable. The conformance vectors declare inherited custom-child and derived-list item refusals.

Raw admission checks the cumulative byte ceiling before decoding and container depth lexically outside escaped strings. Strict UTF-8 JSON refuses BOM, malformed input, duplicate decoded member names, lone surrogates, nonfinite numbers and parser-limit errors. Unicode scalar values include U+0000 in strings/keys: escaped NUL is admitted and canonicalized as the six ASCII bytes U+005C followed by `u0000`; raw unescaped control bytes remain invalid JSON. Only JSON whitespace may surround a candidate text value; accepted producer values are canonicalized before upload. Exact built-in in-process scalars, lists and string-keyed dictionaries are admitted without coercion or user callbacks; cycles and non-JSON types refuse. Count/check container cardinality and remaining byte/depth budget before copying, sorting, formatting an oversized integer or materializing another full container. Do not reuse the current generic object parser's eager copies as the untrusted admission algorithm. VcsRef retains its own unchanged NUL refusal.

Successful native admission creates an owned detached value snapshot under those bounds. Caller mutation cannot change the accepted value or its canonical/digest identity. Public mutable exports and identity summaries are fresh detached views; canonicalization, hashing and summaries revalidate any unchecked/model-constructed value before use. The model follow-up chooses the concrete immutable representation without changing this guarantee or adding a framework here.

Validation order is raw bytes, lexical/decode/numerical validity, bounded canonical-domain validation, then the saved effective schemas. There is at most one fixed safe shared `ContractViolation`; unknown property names, payload values and native decoder/schema exceptions do not enter messages, paths or chaining. Paths use only fixed approved field/vocabulary names and array indexes, otherwise their safe ancestor; names authored inside a custom schema are not automatically safe diagnostic names. No content-bearing error is logged. The implementing issue will pin exact codes and deterministic traversal before code; the general diagnostics list ceiling remains an outer bound.

## 2. Numerical values and canonical bytes

An integer token has no decimal point or exponent and is parsed exactly. Check decimal token length before constructing an integer, then its bit length; 4,215 decimal digits are the largest possible admitted magnitude. Signed integer zero canonicalizes to `0`. A token containing a decimal point or exponent is correctly rounded to finite IEEE-754 binary64, nearest with ties to even. Overflow refuses; ordinary underflow to signed zero is accepted. Structured-channel integers stay exact; exact native binary64 floats stay floats. Boolean is never an integer. Decimal/arbitrary precision objects require an explicit producer conversion and are not silently admitted.

Integers render in exact decimal without plus, leading zeros or decimal/exponent suffix. Floats use the shortest decimal significand that round-trips to the same binary64 value; among equally short candidates choose the closest exact decimal, with ties to an even final digit. Use fixed notation when the decimal exponent is -4 through 15 and scientific otherwise; scientific notation uses lowercase `e`, an explicit exponent sign and at least two exponent digits. Fixed notation includes `.0` for an integral float. Positive/negative floating zero are `0.0`/`-0.0`. This preserves integer versus float payload identity and signed floating zero. It is not RFC 8785/JCS: all admitted integers stay exact and keys use Unicode code-point order rather than UTF-16 order.

Other canonical rules match VcsRef: UTF-8 without BOM/newline, compact separators, Unicode code-point key sorting, recorded array order, fixed JSON short/control escapes, literal other Unicode scalars, no normalization/defaults. SHA-256 covers exactly the complete canonical bytes. Canonical-wire uploads compare staged bytes to these bytes and refuse a different representation before promotion; they never rewrite addressed content.

The immutable [vectors](StructuredOutput.vectors.json) include `1 -> 1`, `1.0/1e0 -> 1.0`, `-0 -> 0`, `-0.0/-0e0 -> -0.0`, `1e-4 -> 0.0001`, `1e-5 -> 1e-05`, `1e15 -> 1000000000000000.0`, `1e16 -> 1e+16`, `9007199254740993 -> 9007199254740993`, `9007199254740993.0 -> 9007199254740992.0`, `1e-324 -> 0.0`, `-1e-324 -> -0.0`, and `5e-324 -> 5e-324`; refuse `1e400`, NaN and infinities. They also cover all six roots, Unicode ordering including supplementary characters, escaping, root-null versus missing, array order, byte/depth/integer boundaries and invalid raw strings. Raw input and canonical text are strings or explicit concatenation/repetition segments; the fixture document's decoder cannot erase token distinctions. Tests pin exact vector file bytes/hash and per-case canonical UTF-8 hashes. Repetition segments reconstruct literal bytes only; they are not a parser or canonicalizer.

JSON Schema `integer` accepts a finite float with an integral mathematical value, but does not rewrite its payload identity. CEL conversion follows the saved checker type separately: integer-schema conversion requires an exact integral signed-64-bit value; number/dyn conversion uses the existing finite-double rules. For example `9223372036854775807` remains an exact payload and can project to CEL int; `9223372036854775807.0` rounds to 2^63 and cannot project to int. Under the compatibility binding below, the standalone artifact boundary admits a large integer when no incompatible CEL projection is required; [IR section 7.5](../ir.md#75-projections-and-typed-conversion) distinguishes that artifact boundary from independently narrower producer admission. Required conversion failure is explicit, never truncation or infinity; unrelated contracts retain their existing entry interpretation. Direct and polled approvals retain their existing signed-64-bit/data-bound entry restrictions, even for unused fields; the [API approvals contract](../api-and-agent-surface.md) and [scheduler section 16.3](../scheduler.md#163-error-and-recovery-policy) retain those restrictions. The vectors declare both direct and polled approval refusals independently of artifact admission.

For the new StructuredOutput validation behavior, schema arithmetic/equality interprets each admitted payload or saved-schema number as the exact rational value of its frozen canonical decimal spelling. This covers `type: integer`, inclusive/exclusive minima/maxima, `multipleOf`, and recursive numerical equality in `const`, `enum` and `uniqueItems`; booleans remain distinct. Do not use binary64 division, tolerances or Python's rounded int/float equality for these decisions. Thus `0.3` with `multipleOf: 0.1` accepts, a 401-digit integer with `multipleOf: 0.5` accepts, canonical float `1e+23` and exact integer `100000000000000000000000` are schema-equal, and `[1,1.0]` fails `uniqueItems: true` even though its two payload elements have distinct canonical spellings. The vectors record these schema/value/outcome cases. The ordinary structural fixture validator does not prove this runtime arithmetic; the provider implementation must configure/extend an existing engine and pass exact numerical conformance. This does not rebind generic behavior for unrelated artifact types. StructuredOutput's payload limit does not cap arbitrary embedded IR schema integers or total schema-evaluation complexity; existing schema-consumer admission/complexity obligations remain independently required.

## 3. Saved effective schemas and CEL view

Save the resolved type/parent/reference closure, applicable inline schema and its source, behavior identities, selected checker schema and all parameters in the effective output contract. Closed local/URN reference resolution remains in-memory; no network lookup or automatic import is allowed. Every applicable schema validates the same direct value. Do not manufacture a multi-member `allOf` and pass it to the existing checker: that would erase record fields to `dyn`.

`kora.execution.v1` supports this previously unbound StructuredOutput revision-1 contract through the immutable compatibility binding `kora.structured-output-view.v1`. Deployment saves the binding, selected checker schema and validation constraints in each affected effective output contract. It applies only to StructuredOutput revision 1, custom types whose saved ancestry reaches that revision, and the corresponding derived list contracts. Every previously supported unrelated interpretation, parser limit, cost and projection/conversion rule remains unchanged. Installations must explicitly support the exact binding before checking/executing affected contracts. Historical records lacking it are not upgraded or inferred from current defaults: new effects refuse explicitly before allocation/execution, while historical reads retain saved results. [IR sections 2.1/7](../ir.md#21-authoritative-type-contracts-adr-0018) and [data-model section 11](../data-model.md#11-immutable-contracts-and-execution-records-adr-0018) save this binding; a digest alone is not interpretation authority.

For an exact built-in StructuredOutput output, an applicable inline schema supplies the CEL checker schema; absent an inline schema, the any-JSON root maps to `dyn`. For a custom named type whose ancestry reaches that revision, or a corresponding derived `List[T]`, its saved declared schema/derived list schema supplies the checker view; an inline schema is an additional validation constraint and does not change declared CEL field types, requiredness or introduce new dot-access fields. Authors who need a different static view declare a named type. Within this mapping, pure-null schemas (`type: null`, `const: null`, `enum: [null]`) map to the existing CEL `NULL`/`null_type`; the checker vectors declare these cases. This conservative view preserves the number/integer distinction and parent assignability without a new general schema-merging engine. The execution-contract identity includes both the validation constraints and checker view, so neither can change on replay.

For the one agent-produced structured output, `config.output_schema` is the producer inline schema. If `outputs.<name>.schema` is also present, it must be structurally equal as JSON (object order ignored); otherwise `IR003`. When no structured output is declared, the existing harness-only `output_schema` configuration and ReviewBundle narrative handling remain as currently specified; this change grants them no artifact authority. Human-input responses keep section 4.2's exact effective-form equality rule; wait-event `outputs.event.schema` supplies its inline schema. Command `output_file` validates the declared output's effective contract. `List[T]` remains a separate derived type and preserves item contracts. Existing scalar parameter bindings and List[Hypothesis] examples keep their meaning. The schema belongs to the saved contract, not a payload wrapper ([IR section 3](../ir.md#3-nodes)).

The preservation guarantee starts at the selected typed producer value admitted into its owned snapshot. Generic upstream `inbound_event.payload`, `wait.observation` and `approval_request.response` retain their existing source semantics before that boundary; this contract does not newly promise to preserve earlier wire-number tokens or a signed zero already normalized there. A delayed scheduler producer admits the value from its retained source, then freezes the typed artifact once; it never invents original bytes or recomputes an accepted artifact through a current provider. Both-database source-to-output conformance must distinguish this boundary from full ingress preservation. Earlier source persistence semantics remain unchanged; narrower producer domains remain visible rather than being advertised as support for every admitted artifact value.

Harness-specific absence/capability semantics also remain: an adapter must not turn an absent/null sentinel into a produced JSON null. Existing allowed strict-text selection may produce null when the text is the JSON value `null`; unsupported root capabilities refuse explicitly under the existing harness rules. `test_structured_output_harness_absence_is_not_null` is a pending activation gate. The existing outer optional `SessionResult.output` and inner `OutputCandidate.value` already distinguish an absent candidate from a selected null without a new DTO.

## 4. Upload, storage, summaries and lifetime

Generic upload framing/progress/metadata/replay remains #224; the staged-storage and mutation-closure contract under #229 is published in #245 and supplies the storage authority. This contract neither copies VcsRef's absent `meta.part` rule nor changes generic part/cumulative caps. The new 1 MiB type cap applies to the cumulative logical JSON value, before the larger generic caps. Do not rescan the growing prefix after every application part; validate and compare the complete canonical value once, outside run locks, before promotion. Final locked acceptance still rechecks namespace/worker/grant/attempt authority. Cleanup, quota reservations, full-digest physical fences, independently eligible retained owners and unresolved deletion remain under the accepted #208/#229/data-model contracts.

Persist full canonical-byte storage/replay digest and exact effective contract separately from any approval-selected role. Revision 1 selects the full root for approval too, but roles remain distinct. Persist the identity summary as content-bearing data with explicit availability; root null is an available four-byte payload, never an unavailable sentinel. Summaries and core CEL projections have their existing content retention/access; expiration does not call today's provider, revive bytes, change metadata or recompute historical results. This contract supplies no publication, authorization, upload or rendering evidence.

For the affected StructuredOutput contracts, canonical UTF-8 bytes remain authoritative behind the existing content descriptor/storage reference at every size. The type-scoped exception to [data-model section 3](../data-model.md#3-identifiers-and-keys)'s <=64 KiB inline rule is: decoded inline JSON may be a non-authoritative view/cache, never the source for replay/hash or identity-summary reconstruction. Generic PostgreSQL JSONB/SQLite JSON storage is not presumed to retain signed zero, numeric kind or available root null. Reuse existing storage descriptors and owner fences rather than adding a column/codec in this specification PR. The identity summary may reference the same physical bytes through its separate derived-payload owner; retention/access and availability remain owner scoped. `inline = SQL NULL` can mean no decoded cache while canonical `b'null'`, size 4 and present payload state establish an available null.

Frozen CEL projections separately require a lossless representation of their converted numerical kind, binary64 signed zero and NUL-bearing strings/keys on both databases. A canonical source blob does not fix a lossy inline projection; work items 4/8/10 extend `test_cel_projection_number_kinds_round_trip` and `test_cel_projection_matches_full_binding` with these cases and require an approved concrete representation before activation. Preserve projection bounds and scheduler re-cutting without storage I/O inside its transaction. No JSONB round-trip evidence is established by this publication. Arbitrary payload strings/keys and identity summaries remain untrusted content, rendered inertly; #227 read-projection/response-construction bounds remain prerequisites independent of the payload byte ceiling. Public metadata/client descriptor shapes remain unchanged; their future payload-loading paths must preserve canonical machine-delivery bytes rather than decode/re-encode through an unsuitable numerical representation.

## 5. Verification and activation

The two publication tests run through the existing ordinary pytest command:

```sh
uv run --no-sync pytest -q tests/ir/test_structured_output_contract.py
```

They check schema/descriptor identity, all six direct-root examples, fixture-byte reconstruction/hashes and the declared structural cases using the existing Draft202012Validator with an explicit in-memory registry. They do not run the pending raw/typed validator, numerical canonicalizer, exact schema arithmetic, checker, producer or storage implementation.
