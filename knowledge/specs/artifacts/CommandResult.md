The project owner approved the complete plan, contract and exact human-facing documentation wording. Models, providers and real consumers remain pending the activation owners below. Governing decisions are [ADR-0008](../../../docs/decisions/0008-content-bound-approvals.md), [ADR-0009](../../../docs/decisions/0009-target-repository-trust-boundary.md) and [ADR-0018](../../../docs/decisions/0018-immutable-attempt-history.md). ## 1. Payload and immutable identity

The built-in has no parent and uses JSON Schema draft 2020-12, `$id: urn:kora:artifact:CommandResult`, revision `1`, validation `kora.command-result-validation.v1`, canonicalization `kora.command-result-json.v1`, and whole-payload selection and identity summary `kora.json-payload.v1`. The saved selection is `[""]`. The accompanying closed descriptor pins the exact schema-byte SHA-256 and every admission parameter. Deployment expands this immutable binding into the effective output contract; unsupported bindings fail before affected effects. Historical reads use saved results, not today's behavior implementation.

The payload is one closed JSON object. Every field below is required; null is allowed only where stated. There are no arbitrary extension members or parsed-JSON member. Optional JSON from `output_file` is the separately declared StructuredOutput or custom artifact under its saved effective contract. Its approval coverage comes from explicitly binding that output when its contents matter; the implicit result does not silently bind another artifact's payload.

| Field | Meaning |
|---|---|
| `exit_code` | Observed command-leader status, strict integer −255 through 255. Nonnegative values are ordinary exit codes. Negative values are minus the observed POSIX signal. It is never null or a fabricated sentinel. |
| `signal` | Null for a nonnegative exit code; otherwise strict integer 1–255 equal to `-exit_code`. This repeats a fixed fact explicitly, with equality checked by validation. |
| `termination` | `none`, `interrupted`, `killed` or `killed_after_grace`, using the matching existing runner outcome meanings. `none` records no runner-started stop; it does not assert that descendants or the runtime domain have closed. The harness-only `teardown_after_result` is not admitted. |
| `stop_reason` | `completed`, `deadline`, `cancel` or `journal_unavailable`. This is the trusted supervisor's selected command stop cause, using the corresponding existing cause. `completed` means no runner-started stop won, not command or node success, and requires `termination: none`. A deadline/cancel/journal stop may have a zero leader exit code without becoming a successful gate. |
| `duration_ms` | Strict nonnegative integer through 2^63−1. Floor of monotonic elapsed milliseconds from acknowledged execution of the actual command through observed leader exit. Excludes preparation, capture upload and cleanup. Sub-millisecond duration is zero. A restart never replaces the saved start/elapsed observations with adoption time. |
| `repo`, `commit`, `base_commit` | Trusted checkout identity from the existing WorkspaceRef/checkpoint, not command text or a candidate-provided claim. Repository text is nonempty and at most 4,096 UTF-8 bytes. Native commit and base revision use the unchanged VcsRef revision domain: nonempty, at most 255 characters, no U+0000–U+001F or U+007F, no normalization or Git-only hex rule. Existing narrower provider/transport admission remains independently applicable. |
| `protected_paths` | Exact resolved runtime-plus-node list in force, retaining order and any authored repetition. No sorting, case folding or Unicode normalization rewrites saved values. Existing protected-path syntax and call-wide limits apply. |
| `protection` | `unprotected` exactly when the list is empty; otherwise `verified`, only after the existing trusted changed-path/base check succeeded before launch. A failed check produces `protected_path_modified` before a CommandResult exists. `verified` describes these paths and this base/candidate identity, not evaluator independence or hostile-code isolation. |
| `resources` | Complete verified command-resource manifest, 0–64 closed records `{name, sha256, size, executable}`, sorted in the existing UTF-8 name order. Names are unique, already NFC, relative, no empty/dot/traversal segments, controls or backslash; at most 4,096 UTF-8 bytes total and 255 per component. Each size is a strict integer 0–262,144. The file digests are those verified immediately before actual execution. |
| `resource_set_digest` | Null exactly for an empty manifest. Otherwise SHA-256 of the unchanged IR/JCS manifest bytes, including names, size, executable flags and per-file digests. The existing quoted/non-ASCII-name vector remains unchanged. |
| `resource_protection` | `none` for no resources. For a nonempty manifest, `protected` only on a runtime actually providing the declared read-only resource boundary; otherwise `none`, including local. This is separate from protected repository paths and from the testing composition's `evidence: fake` stamp. |
| `stdout`, `stderr` | Independent immutable descriptors of sanitized retained capture bytes, defined below. |

All other integer members are also strict nonnegative signed-64-bit integers except their narrower named bounds. JSON booleans, strings and floats are not integers. A JSON token containing a decimal point or exponent is refused for integer fields, even if mathematically integral. This is a supplemental behavior predicate; ordinary JSON Schema `integer` alone does not prove it.

Derived `List[CommandResult]` retains the generic saved list/item semantics and has no separate registry alias. The per-result root cap does not impose a whole-list 1 MiB cap or establish an aggregate materialization bound. Structural validity and separately admitted items do not activate recursively derived lists or scheduler collect/export paths. **Pending activation:** work items 3/9/10 own admission and aggregate construction, coordinated with API 11 and artifact/storage/read owner 12. Before activation, their owner-approved plan must establish concrete bounded aggregate materialization, canonicalization/digest/summary, persistence and delivery under the saved generic semantics, including recursively nested lists and scheduler-produced values that bypass upload. Enforce the applicable aggregate admission before full materialization; retain existing transaction/storage-I/O boundaries and owner-scoped retention. Per-result limits, generic upload limits and CEL projection budgets do not establish that obligation. This publication selects no new numerical aggregate default, compatibility reinterpretation or measurement campaign. Applicable existing collection/export, upload/read/retention and resource checks activate with those consumers.

## 2. Captures and bounded tails

Each stream is the closed object `{storage_ref, payload_digest, size, observed_bytes, eof, truncated, tail_base64}`.

- `storage_ref` is the existing configured logical read reference, represented as 1–256 printable non-space ASCII characters. It is not an arbitrary URL to fetch, a filesystem path to open, a physical storage identity or an access credential. Acceptance requires its trusted binding to the named captured bytes and attempt/output owner.
- `payload_digest` is `sha256:` plus 64 lowercase hexadecimal digits, covering every retained sanitized byte. `size` is the retained byte count, at most 67,108,864 (64 MiB) per stream. These are independent of the artifact root's canonical JSON digest.
- `observed_bytes` is the count of sanitized stream bytes actually drained before sealing, at least `size` and at most 2^63−1. It is a lower bound when EOF was not observed. An unreceived or undrained suffix has no invented size or digest. Counter overflow makes a result unrepresentable; it must not wrap or saturate into a valid artifact.
- `eof` is true only after trusted capture observed EOF, not merely command-leader exit or a stop request. `truncated` is exactly `(observed_bytes > size) or (not eof)`. Thus complete observation and complete retention are separate facts.
- Retain the first at most 64 MiB of sanitized bytes and continue draining/counting beyond the cap without blocking stop escalation. Do not append a marker to binary command capture bytes. The existing opaque-transcript marker and server-side truncation rule do not apply to these captures or to the JSON root.
- `tail_base64` is canonical padded RFC 4648 base64 of exactly the last `min(size,4096)` retained bytes, at most 5,464 ASCII characters. Empty capture has an empty string and the SHA-256 of empty bytes. The tail refers to the retained prefix, not to a deliberately omitted later suffix. After the existing sanitation pipeline, no further UTF-8 replacement, normalization or line-boundary adjustment changes retained-byte or tail identity. Semantic validation checks canonical base64, exact decoded length and byte agreement with the trusted retained suffix.

Capture uses the existing StreamMasker pipeline: incrementally decode raw command bytes as UTF-8 with `errors="replace"`, apply the registered literal masks to decoded text, and encode emitted text as UTF-8. Complete the existing decoder/masker flush when the captured source is closed. Capture counts, prefix selection, full retained digest and tail selection all occur after that decode/mask/re-encode sequence. Invalid raw UTF-8 is therefore replaced before capture identity; a complete untruncated sanitized stream is UTF-8, while an exact byte suffix may start inside a code point and remains base64. This preserves the existing literal-redaction guarantee and its limits; it makes no digest or byte-preservation claim about the pre-sanitization stream. Human views can decode and present a labelled text view safely; sanitized retained bytes remain available through authorized existing content delivery once their owner binding is implemented. Presentation never changes saved bytes or digests. Captures, tails and decoded display text are untrusted content, not operational diagnostics or execution authority.

The 64 MiB per-stream ceiling is an owner-approved revision-1 artifact parameter, consistent with the proposed local stdout/stderr limit in protocols section 2. This contract makes that ceiling binding for CommandResult capture; it does not approve the other local journal/log proposals or increase existing stop, transfer, request or cleanup deadlines. The 4 KiB tail is a new explicit parameter, not a previously measured guarantee.

## 3. Result existence, success and recovery

A CommandResult can be frozen only after actual command execution was acknowledged, trusted command-leader exit was observed, both retained captures were durably sealed and all required identity/protection/resource facts are known. Nonzero exits, external signals and completed deadline/cancellation stops can have retained historical CommandResult evidence. A nonnegative zero code alone grants no success authority. `success_exit_codes` belongs to the already saved node contract; ordinary completion, result authority, closure and publication gates still determine current successful outputs.

No CommandResult is fabricated for preparation refusal, changed protected paths, resource mismatch before launch, launch refusal/failure before command execution acknowledgement, unknown leader exit or unavailable/unsealable capture identity. Those attempts retain their existing inputs, request, structured failure, events and recovery evidence. The fixed implicit output declaration does not invent a payload for an output-less failed attempt. Null or guessed exit codes, zero duration placeholders and empty captures substituted for unavailable bytes are invalid.

A result describes command observations, not quiescence or dispatcher closure. Existing runtime normal-completion/termination receipts, earlier-grant closure, current authority, inherited deadlines and target-result acceptance remain mandatory. Capture persistence and reporting do not postpone interruption/kill escalation. Losing the result response never authorizes another command launch. Recover a durably frozen result by its existing attempt checkpoint/transfer path; if it was not saved and cannot be recovered exactly, preserve uncertainty or an explicit failure instead of rebuilding facts from current files, current aliases or a new execution.

## 4. Canonical bytes, selected digest and replay

Raw and canonical root JSON each have a 1,048,576-byte ceiling and maximum 16 nested object/array containers. Root container depth is one. Check bytes and lexical depth before eager decoding. Refuse BOM, malformed UTF-8/JSON, duplicate decoded member names, lone surrogates, non-finite constants and decoder-limit failures. Native admission accepts only exact JSON scalar/container types under the closed schema; no coercion, defaults, callbacks, shared mutable aliases or cycles. Bound cardinality and byte work before copying, sorting or materializing oversized values. Successful admission owns a detached immutable logical snapshot; caller mutation cannot change it.

`kora.command-result-json.v1` renders only the admitted domain: exact decimal integers without leading plus/zeros, lowercase null/booleans, compact separators, Unicode code-point object-key order, recorded array order, fixed JSON short/control escapes, other Unicode scalars as UTF-8, and no BOM, insignificant whitespace or trailing newline. No Unicode normalization or default insertion occurs. Every string admits only its named schema/behavior domain. This is a new CommandResult identity; it neither changes nor rebinds VcsRef/StructuredOutput canonicalization. The resource-set digest still uses its independently fixed IR/JCS manifest algorithm.

SHA-256 of the complete canonical JSON is both the full root payload digest and the selected approval digest for revision 1, but these roles remain separate. The whole root covers exit/termination/cause/duration, exact checkout and protection evidence, the complete resource manifest and resource protection, both capture references/digests/counts/EOF/truncation flags and exact tails. No gate fact in this root is omitted. Approval provenance also retains the existing exact artifact version, attempt and trusted worker/image attribution; copying candidate claims into a well-formed root cannot establish that provenance.

A separate declared parsed output retains its independent complete identity and contract. An approval that relies on it must include its digest; binding only `result` cannot cover an unbound metric artifact. No automatic new bundle or gate binding is added.

Whole-output `(attempt_id, output_name)` acceptance compares complete canonical root identity and exact saved effective contract, never only a selected digest or capture digest. Equal replay returns the original descriptor read-only under current authorization. A changed root, changed capture binding or changed contract conflicts even if a consumer would display the same abbreviated summary. Object member reordering has identical canonical identity; array reordering does not. Replay cannot change settled outcome, replace accepted evidence, renew retention, restore an expired owner or authorize an effect.

Generic output upload keeps its existing meta/data/recover variants and framing. The root uses canonical wire bytes and the independent 1 MiB logical cap; validate and compare once outside run locks before promotion. A noncanonical source is refused rather than rewriting addressed bytes. This does not inherit VcsRef's absent `meta.part` rule. The generic 16 MiB non-final width means this root can occupy only one final public data part. Existing storage reservations, mutation outcomes, authority rechecks and shared-address fences remain mandatory.

## 5. Storage, retention and the pending capture wire binding

The root's `storage_ref` and `payload_digest` belong to the CommandResult JSON, not either child capture. Root JSON, both command-output captures, tails, identity summary and CEL projection follow `artifact_payloads` retention, default 30 days after the run finishes. The root is not a reference-only forever-retained artifact merely because it contains references. Permanent artifact identity, selected/full digests, contract identity, lineage and content-free outcome remain under the existing data model. The identity summary is content-bearing and independently owner-scoped even if it shares root bytes. No new permanent projection exception is added.

Capture availability is current owner state outside the immutable JSON; do not insert a mutable `payload_state` into the payload. A saved reference or surviving/recreated shared blob cannot authorize an expired capture owner or keep another owner alive. Namespace and applicable transcript-derived access follow the existing API. Command captures do not silently acquire an AgentSession metadata lifetime or bypass original content rights. Expiry never recomputes a tail/summary through a current provider. Shared-address deletion must consider every eligible capture/root/derived owner and active/recovery hold under the accepted physical-storage/full-digest fence.

There is an explicit implementation prerequisite: the current worker upload kinds are `output`, `execution_request` and `transcript`, and output identity is the declared `(attempt_id, output_name)`. The current closed envelope has no selector for separate command stdout and stderr captures. This publication defines their logical immutable descriptors and retention obligations but grants no new upload selector, undeclared output name, table, child-resource route or direct worker-to-storage authority.

Work item 12 (artifact upload/storage/retention) owns an approved concrete mapping for the two captured byte streams, coordinated with API 11, worker 17, command executor 13, runtime 14 and retention #216. Before real CommandResult activation, its implementation plan must define how existing routes stage/complete each capture, how trusted attempt/output/stream identity is bound, how exact replay and shared ownership persist, how partial acceptance is reclaimed and how reads/recovery authorize the same owner. Any changed public envelope, persisted format or owner semantics requires explicit owner approval. All applicable both-database failure/cancellation/restart/replay/delete-race and actual resource-release checks must pass. Until then, models/publication do not establish an executable capture-upload path; no runtime consumer may bypass the prerequisite.

A concrete existing-route envelope and persisted capture-owner mapping remain outside this publication. They require another owner-approved plan for the API/metadata/worker/read/retention contracts and exact documentation before implementation. The approved publication-only scope leaves this consumer-owned mapping pending explicitly.

## 6. Publication checks and separate activation

Two ordinary pytest publication checks are defined in `tests/ir/test_command_result_contract.py`: `test_command_result_contract_files_are_consistent` and `test_command_result_contract_vectors_are_immutable`. They use the existing Draft202012Validator with an explicit offline registry to check schema validity and structural fixtures, and pin schema/descriptor/vector bytes, fixture canonical bytes and SHA-256 declarations. They introduce no dependency or validation framework.

Raw decoding, canonicalization, strict integer semantics, relational predicates, captured-byte integrity/provenance, real replay and lifecycle cases in the vectors are declarations for their implementing owners. Pinning them is not executing them. The publication checks cover schema/descriptor/vector identity and structural fixture consistency only.
