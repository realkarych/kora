### Python boundary implementation

[Issue #209](https://github.com/realkarych/kora/issues/209) implements the frozen `VcsRef` and `PrincipalRef` values in `kora.ir.vcs_ref` and exports them from `kora.ir`. `parse_vcs_ref(object)` admits exact built-in JSON objects and exact model instances, revalidating unchecked constructed/copied values. Direct constructors and `model_validate` enforce the same ordered checks. Principals are immutable snapshots; `PrincipalRef.identity()` compares only provider instance and stable ID. Model equality includes the complete recorded snapshot.

`parse_vcs_ref_json(bytes)` is the designated untrusted raw boundary. `VcsRef.model_validate_json` routes through that bounded preflight, including when callers request relaxed native flags. Inherited `PrincipalRef.model_validate_json` and generic `TypeAdapter.validate_json` are not supported untrusted raw ingress: their native decoders run before the artifact preflight and may already have discarded duplicate-member evidence. Admit a principal through its strict object boundary or extract it from a validated VcsRef.

`canonical_vcs_ref`, `vcs_ref_digest` and `summarize_vcs_ref` revalidate their model input. They return canonical bytes, the complete-payload SHA-256 and a fresh identity projection respectively. Ordinary Pydantic serialization preserves values and omission but is not the canonical-byte API. Optional fields use absence rather than null; absent fields stay omitted regardless of unset/default/none serialization flags. Both actual schema modes match the published structural schema after removing nonsemantic titles.

`require_vcs_ref_revision(object)` checks the complete closed published manifest, including schema hash, every behavior parameter, parent and digest selection. It is a fixed revision-1 compatibility boundary, performs no network lookup and supplies no deployment-closure authentication or generic artifact registry.

Every payload refusal raises `VcsRefValidationError` carrying one shared `ContractViolation`. Codes `VCS001`–`VCS007` identify raw size, JSON decoding, closed shape, aggregate path bytes, semantic URL, canonical size and unsupported revision respectively. Messages are fixed; paths contain only known field names and array indexes. Submitted content, unknown keys and native decoder exceptions are excluded from the public error and its chaining. These values return to consumers without starting a logger or emitting payload diagnostics.

## 2. VcsRef publication facts

The closed object has required fields `repo`, `branch`, `commit`, `base_commit`, `changed_paths`, `diff_stat` and `pushed_by`. It has no extension map or mutable status field.

| Field | Meaning |
|---|---|
| `repo` | Logical repository resolved through the saved trusted deployment binding; never a candidate URL or transport authority |
| `branch` | Published branch at that trusted destination |
| `commit`, `base_commit` | Exact immutable native revision identifiers, nonempty and at most 255 Unicode scalar values; core imposes no Git hash syntax |
| `changed_paths` | Unique relative POSIX paths from the trusted inspection's union across newly published history, including deletions, reverted intermediate changes and changes against every merge parent; not merely the final-tree diff |
| `diff_stat` | Trusted inspection's display text; not independent verification evidence |
| `pushed_by` | Recorded authenticated publishing principal, including the binding-defined principal for explicit trusted credential-free local publication |

Repository, branch, revision and principal identifiers contain no U+0000–U+001F or U+007F. Paths contain neither those controls nor backslashes, absolute roots, empty segments, `.` or `..` segments. There are at most 10,000 paths and their combined UTF-8 length, without separators or JSON escaping, is at most 524,288 bytes. Providers preserve the complete inspected set; they never truncate it to fit. A real nonempty change is established by trusted inspection, not by accepting nonempty display strings or a claimed path list. Checkout recomputes the provider's protected-path evidence against the recorded base under [protocols section 4](../protocols.md#4-vcs-fr-52).

`PrincipalRef` is an embedded closed record with required `provider_instance`, `stable_id`, `kind` and `display_name`. The three free-text fields are nonempty and at most 255 Unicode scalar values, matching the persisted automation-principal columns. `kind` is `app`, `bot_user`, `service_user`, `user` or `local_service`. The last identifies the explicit trusted credential-free local service under #140; kind alone grants no credential-free authority. Identity comparison uses `(provider_instance, stable_id)`, never display name or kind; recorded display values remain immutable snapshots. The public model belongs in `kora.ir` and protocol consumers reuse it, preserving [ADR-0026](../../../docs/decisions/0026-package-layers.md).

Optional fields are `url` (change request), `commit_url`, `compare_url` and `opened_by` (`PrincipalRef`). `url` and `opened_by` occur together. Commit and comparison URLs may occur independently. Their immutable URL syntax is defined below. No URL is dereferenced during validation. URLs are untrusted display/link values, not repository identity, checkout instructions, authorization or observations of current status. Omission means no recorded fact; explicit null is invalid. A local push-only result omits code-host fields. The [#140 publication scope](https://github.com/realkarych/kora/issues/140#issuecomment-6319392587) retains authorization, principal recording and every late matching/closure check.

### URL syntax

Every URL matches the entire `IRI` production in [RFC 3987 section 2.2](https://www.rfc-editor.org/rfc/rfc3987.html#section-2.2), using its literal character ranges, restricted to the authority form and the following predicates:

- The prefix is exactly lowercase `http://` or `https://`. Authority ends at the first literal `/`, `?` or `#`; its host is nonempty and userinfo is forbidden.
- Host follows `ihost`: registered name, IPv4, bracketed IPv6 or IPvFuture, with [RFC 3986 section 3.2.2's first-match-wins rule](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.2.2). An IPv4-looking name that fails IPv4 may still be a registered name. IPvFuture permits `v` or `V`. A bracketed host consumes the entire IP-literal before an optional port; unmatched brackets, other bracket suffixes, unbracketed IPv6 and zone identifiers are refused.
- Port is absent, empty, or ASCII decimal digits with a value from 0 through 65535. Empty ports and leading zeros are preserved. Validate the value after ignoring leading zeros for comparison, without constructing an unbounded integer; a long all-zero port remains valid within the payload cap.
- Each `%` begins a two-ASCII-hex-digit triplet: `%000` is `%00` followed by `0`. Escaped registered names are allowed without decoding delimiters; escape case is preserved. This syntax does not assert valid decoded UTF-8.
- Raw backslash and U+0000–0020, U+007F–009F, U+00A0, U+1680, U+2000–200A, U+2028–2029, U+202F, U+205F, U+3000 and U+FEFF are forbidden. Do not use an evolving library whitespace category. The RFC's distinct `ucschar` and `iprivate` ranges still apply: private-use characters may occur in a query, not a host, path or fragment.

Do not trim, normalize, map IDNA, case-fold, remove dot segments/default ports, decode escapes or perform DNS/network access. The original string enters canonical JSON unchanged. Acceptance establishes this grammar, not browser interoperability, remote existence or publication authority; display links remain untrusted and cannot authorize server-side fetching. The structural schema approximates these predicates; the [semantic vectors](VcsRef.url-vectors.json) activate with #209's full validator.

## 3. Validation descriptor

`kora.vcs-ref-validation.v1` composes the generic `kora.json-schema-2020-12.v1` structural validator with these fixed boundary rules:

1. Raw JSON is at most 1,048,576 bytes. Enforce the cumulative bound before decoding, including across HTTP transport chunks; oversized declared totals are refused before receiving payload bytes.
2. A bounded lexical preflight counts object/array nesting outside strings, respecting escapes. Root container depth is 1; refuse depth above 16 before invoking a general decoder. Decode strict UTF-8 JSON, refusing duplicate object names, malformed JSON, lone surrogates, non-JSON/nonfinite values and parser-limit failures. Every string is a sequence of Unicode scalar values without NUL.
3. Validate the closed schema without coercion, default insertion, field dropping or normalization. JSON Schema establishes cardinality, uniqueness, field shape and character limits; it does not establish the following byte predicates or provenance.
4. Check the aggregate path bound as `sum(len(path.encode("utf-8"))) <= 524288`, with no normalization, and the semantic URL predicate. Canonical payload bytes defined below are at most 1,048,576 bytes.

The full behavior differs from structural schema acceptance: a schema-valid value can still fail a byte, Unicode or URL predicate. Constants and this exact semantics are part of the saved behavior binding, not mutable installation defaults. In-process typed validation enforces the same payload domain; only a raw-byte boundary can detect duplicate JSON members. Validation returns at most one content-free shared `ContractViolation`, using the representation owned by #135/#207. It fails fast in this order: raw size, lexical/decode validity, closed shape, then aggregate path bytes, URLs and canonical-byte predicates. Within a phase it uses the saved-schema field order and ascending array index; an unknown member is reported at the root or a known safe ancestor, never by copying its name. Stop before constructing or retaining further diagnostics; collecting all native schema/Pydantic errors and slicing afterward does not conform. The shared collection ceiling remains an outer bound; the full graph validator still collects its independent errors. Payloads, URLs, unknown key text and raw decoder/Pydantic exception messages never become diagnostics. The API uses its existing structured `API003` upload-refusal semantics. Validation, hashing, canonical comparison and summary work occur outside run locks.

Shape validity, a matching digest and a saved summary authenticate no publication fact. Trusted consumers separately match repository, branch, revisions and principals to the prepared operation, authorization, verified result and original execution domain. A forged model cannot become publication evidence merely by passing this validator.

## 4. Canonical bytes and digests

Digest selection is `kora.json-payload.v1`: the complete validated payload, including every optional field actually present. The stored field selection is `[""]`, whose empty string is the root JSON Pointer. No field is omitted because it looks informational. Reordering object members changes neither selection nor digest; array order is retained and changing it changes the content identity.

VcsRef contains only strings, objects and arrays. Canonicalization for this type is:

- UTF-8, without BOM or final newline;
- object keys sorted by Unicode code point, arrays in their recorded order;
- comma and colon separators with no whitespace;
- JSON short escapes for quote, backslash, backspace, form feed, newline, carriage return and tab; lowercase `\u00xx` escapes for other U+0000–U+001F characters; all other permitted Unicode scalar values encoded literally;
- no Unicode normalization or injected null/default fields.

SHA-256 covers exactly these bytes. The [fixed vector](VcsRef.digest-vector.json) contains the value, exact canonical text and hash `e978ea1463001e37edfb3970b0e3352cc929fde73efe5958958aedd9c9b5c955`; [vcs-ref.json](examples/vcs-ref.json) is its exact wire representation. This string-only rule agrees with the existing canonical serializer; it does not choose numerical canonicalization for other artifact types or require `kora.ir` to import the database package.

The selected approval digest and complete-payload storage digest remain separate roles even though both select the same canonical bytes for this revision. Storage deduplication and replay always use `payload_digest` and the saved contract identity, never a selected-field digest that another artifact type might narrow.

## 5. Upload, replay and result ownership

VcsRef revision 1 uses one application-level multipart request: exactly one `meta` part followed by one complete `payload` part. `meta.part` must be absent, including refusing explicit null. Resolve this restriction from the attempt's saved output contract, never caller-supplied `type_name`; refuse a chunk descriptor with `API003` before staging reservation or payload consumption/storage. Verify the multipart envelope ends before promotion and refuse duplicate or additional parts. HTTP streaming and transport chunking remain permitted; the 1 MiB payload fits the generic 16 MiB part cap. The general application-chunk progress/replay/metadata contract is separately tracked in #224 before generic upload routes ship.

VcsRef upload producers send the canonical bytes above. API validation compares the received bytes with their canonical form and refuses a noncanonical representation before promotion or acceptance; it never rewrites staged content. Equivalent whitespace, member order, Unicode escapes, BOM or trailing-newline alternatives are refused even when their declared wire size and digest are correct. This preserves the existing whole-received-byte hash, single-part digest and size declarations, and staging reservations. The VcsRef-specific 1 MiB ceiling applies before the larger generic artifact caps in [API section 8](../api-and-agent-surface.md#8-rate-and-size-limits).

A structural, semantic or canonical-validation refusal creates no accepted artifact or promoted address. An otherwise valid upload can still lose authority at the final locked recheck after promotion; its addressed object retains the existing `expiring` staging owner until reclamation. Existing staging ownership/reclaim applies on refusal, cancellation, disconnect and crash under the [API completion conditions](../api-and-agent-surface.md#worker-route-bodies-issue-139). After confirmed staging-key cleanup, an upload-created address keeps its row/reservation until required physical deletion completes, or an independently eligible durable owner retains the same bytes under the shared fence with no unresolved deletion generation/effect. Unknown promotion ownership remains charged; staging rows, transient holds and observed existence alone cannot justify release. The retained-owner alternative deletes no accepted bytes and restores no expired owner or access. Namespace/worker/grant checks still precede storage; locked acceptance still rechecks authority. Exact full-payload/contract replay returns the original descriptor read-only under the existing replay rules, without renewing retention, restoring expired owners or authorizing another effect.

The worker passes the complete issued or trusted-binding `PrincipalRef` in `PublicationAuthorization.principal`; there is no separate unresolved principal ID. Persist that nonsecret snapshot with the operation, prepared and destination identities before dispatch. Keep one current or unresolved dispatch snapshot; replace it only after authoritative absence and closure of every prior dispatch, preserving the existing control-plane issuance audit. Validate the complete push-only VcsRef with the actual authorized principal before effect dispatch; a prepared-content section fitting its bound does not prove room for the principal. Credentials remain ephemeral.

`Runtime.finalize` freezes its complete push-only VcsRef with the completed `PublicationOutcome` before returning. Repeat `finalize` only while the runtime state permits it. Once completion, retirement or release fences that operation, `RecoveryEvidence.publication_outcome.ref` returns the exact saved outcome, including original principal display values, without reopening dispatch or rebuilding values from current credentials/host responses. [Runtime result retention and transport](../protocols.md#publication-result-retention-and-transport) retain the bounded immutable result after cleanup and carry publication/adoption/recovery content in bounded chunks without raising the frame ceiling.

The authenticated supervisor publication summary freezes `runtime_result_fields`, `runtime_result_digest` and the saved VcsRef contract identity together. `runtime_result_fields` is the closed bounded set of top-level fields actually present in the validated runtime result: every required field is present, no unknown name is allowed, and the set is never inferred from an incoming artifact. Persist and relay this trusted tuple before artifact acceptance. Terminal closure evidence must match the complete canonical runtime result and contract, not only commit and branch. Validation and hashing happen outside the run lock; the locked transaction compares against the independent saved summary. The report itself cannot create the expected digest. Keep it distinct from the complete enriched artifact's storage/replay digest.

Code-host enrichment preserves every recorded field and value of the runtime VcsRef, including optional fields, nested principal values and array order; canonicalization ignores object-member order. It adds only absent `url`, `opened_by`, `commit_url` and `compare_url`, with the URL/opener pairing intact, from trusted code-host result provenance bound to the same operation, repository and revisions. An upload's own claims cannot establish this provenance. Artifact acceptance requires every authenticated `runtime_result_fields` field, canonicalizes that exact projection outside the run lock and compares its digest, saved contract and the same field set under the authority lock. Altered or removed runtime facts, a candidate-selected field set and unverified additions are refused. A valid terminal report does not substitute for this artifact check; the full enriched payload separately passes VcsRef validation and retains its own complete storage/replay identity.

Before actual change-request create dispatch, durably record attempt/output identity, runtime result identity, trusted destination/head/base and the complete acquired API principal in attempt-owned recovery state accessible to an adopting worker. Lookup and credential acquisition may precede this checkpoint; credentials are never persisted. The checkpoint is not proof of an effect and does not replace subsequent gate, lease, deadline or closure checks. For a confirmed creation by this operation, verify the remote opener's stable identity against the saved API principal and retain that snapshot. A pre-existing request uses its independently verified actual opener, never the lookup credential. Current credentials never replace a recorded creating principal. If evidence cannot establish the operation/outcome, retain uncertainty instead of fabricating attribution or starting another effect.

Record every learned remote object and settled creation outcome even if its host fields fail VcsRef validation or the payload cap; artifact refusal cannot forget an effect or authorize another create. Unknown effects retain recovery barriers; known settled effects with invalid artifacts can follow ordinary failure and closure. Durably freeze the validated enriched candidate and canonical identity before its first upload. Restart and response-loss replay use those exact bytes. A crash before outcome persistence requires reconciliation, not an assumption that an unrecorded response is recoverable. Concrete storage and DTO placement belong to code-host work item 17; no new service, outbox or table is required. Enrichment never mutates the runtime result. After `(attempt_id, output_name)` is accepted, no enrichment replaces it or creates a second payload under that identity. Later observations remain separate; a different producing attempt follows ordinary artifact production. Late authorization, dispatcher closure, retirement and deadline rules are unchanged.

## 6. Current observations and approvals

`ChangeRequestStatus` and `head_sha` return current observations; VcsRef stores no mutable status. An approval binds its exact recorded commit and artifact/version identity, never a URL or current registry alias. [ADR-0008](../../../docs/decisions/0008-content-bound-approvals.md) and [ADR-0021](../../../docs/decisions/0021-external-observations-outside-transactions.md) retain current-wait fencing, push invalidation and the mandatory fresh post-approval head check.

The supported revision domain also applies to head results, authenticated push revisions and approval-response observations. Out-of-domain values never count as matching/fresh heads, and are never truncated, hashed or coerced into the 255-character observed-head column. Record a content-free invalid-observation result without a valid observed SHA. Invalid provider results follow [scheduler section 16](../scheduler.md#16-external-observation-dispatch-adr-0021): fail the current waiting operation with `config_error`, close its wait and preserve any already-approved audit row. Invalid direct API input receives structured validation refusal.

A relevant authenticated push still conservatively invalidates a pending request even when its revision is invalid. For an approved gate awaiting verification, fence the outstanding read and require a newly claimed valid head observation. Stale results cannot affect replacement owners, extend expiry, satisfy a gate or resurrect a failed node. These bounds preserve both-database behavior without widening persistence or imposing Git-only identifiers.

## 7. Summary and availability

Summary is `kora.json-payload.v1`, the identity value. Store its applied contract identity, outcome, actual selection, selected projection/digest and summary at production/upload. Historical reads never execute today's plugin to reinterpret them.

This saved content result does not require eager loading or inlining in metadata, list, aggregate or history responses. The owner-scoped descriptor/reference remains distinct from a route's declared response projection. Concrete route projections, variable-length previews, page/byte budgets and client loading behavior are a prerequisite in #227 before the affected API and client consumers ship; the payload cap and storage-inlining threshold do not establish response-construction bounds.

The reference-only source VcsRef payload remains forever under [data-model section 10](../data-model.md#10-retention-dd-4). Its content-bearing identity summary has a separate `derived_payload` owner with `artifact_payloads` retention under [section 11.3](../data-model.md#113-results-observations-and-availability). Shared bytes do not keep an expired summary owner present and do not permit recomputation. CEL projections separately follow the source artifact's retention class. All namespace and applicable transcript-derived access checks remain. Summaries are untrusted display content, never operational diagnostics or authority.

Trusted inspection, schema validity and matching digests do not make artifact text safe to render. Every human-facing view renders VcsRef text, including `diff_stat` and its summary, as inert untrusted text. Terminal views visibly escape payload-derived U+0000–U+001F and U+007F–U+009F; line breaks, tabs and terminal styling used for layout belong to the renderer. Web and markup views display those controls visibly and use destination-appropriate inert text or literal encoding, so payload text cannot create markup, actions or surrounding structure. A view constructs links only through its own link policy, never by interpreting artifact text as markup. Presentation escaping applies only to the displayed copy: it never changes accepted payload values, canonical bytes, digests or saved summaries. API responses, CLI `--json` and MCP results retain the original values under their existing serialization contracts. This is a consumer requirement under TM-07, outside the immutable validation and canonicalization behavior.
