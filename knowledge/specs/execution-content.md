# Durable execution content

Status: design for owner review under [#1557](https://github.com/realkarych/kora/issues/1557), 2026-11-14. The owner approved preparation of this contract and the implementation split. The proposed records, transport extensions and installation capacities below require review of this PR; none is implemented or activated by publication. The local storage provider and address-lock foundations exist. Their existence does not establish a durable request producer, accepted result producer or safe core cleanup.

This is the execution-content part of [#216](https://github.com/realkarych/kora/issues/216). [Data-model retention](data-model.md#10-retention-dd-4), [ArtifactStorage](protocols.md#7-artifact-storage-fr-44), [worker authorization and upload](api-and-agent-surface.md#worker-route-bodies-issue-139) and the individual artifact contracts govern unchanged behavior. Governing decisions are [ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md), [ADR-0005](../../docs/decisions/0005-eleven-protocols-with-conformance-suites.md), [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md), [ADR-0018](../../docs/decisions/0018-immutable-attempt-history.md), [ADR-0019](../../docs/decisions/0019-immutable-run-target-identity.md) and [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md). No exception to their authority, durability, closure or retention requirements is selected.

## 1. Delivered boundary

The server owns exact content and the metadata that says which attempt or result retains it. Storage owns immutable bytes, mutation attribution and physical resource closure. Workers use the existing HTTP route; they never obtain database or provider credentials. A storage address, digest, successful validation or ready upload alone grants neither execution authority nor current-output authority.

| Content | Producer and immutable identity | Retention and acceptance |
|---|---|---|
| Execution request | Worker constructs the nonsecret request; Worker API validates the pinned graph/input/price and current execution policy. The canonical request digest excludes grant and credentials. | Combined content uses the shorter saved transcript/artifact period. Ready content remains charged until the one sealing transaction. |
| Explicit StructuredOutput | Harness/command candidate, validated against the complete saved effective contract by the effective-validation producer. Full canonical payload digest and contract identify replay. | Artifact-payload retention; a separate identity-summary owner can share canonical bytes. Produced JSON null is four available bytes, not absence. |
| Implicit command `result` | Trusted command observation plus exact captures; the CommandResult provider checks the native logical contract. Full canonical root and saved contract identify replay. | Root, captures, tails, summary and CEL content use artifact-payload retention. Root acceptance adopts both captures atomically. |
| Implicit agent `session` | Trusted finalization snapshot, API-derived cost and captured/unavailable transcript facts. Complete logical digest and saved contract identify replay. | Transcript is the primary payload; fixed metadata survives, denial sample expires separately. Logical JSON is a transfer/validation value, not a permanent full copy. |

The [walking skeleton](first-slice.md#walking-skeleton-and-narrowed-depth) has no target-derived run key, VcsRef publication or command-input materialization. This design does not activate them, recursively derived artifact lists, historical read APIs, S3 or full periodic retention. Ordinary output insertion keeps its existing current/historical decision. Only a target source outside this slice stages its whole output set until scheduler acceptance. Scheduler [#1472](https://github.com/realkarych/kora/issues/1472) retains terminal settlement, completeness/authority/deadline/closure rechecks and physical-capacity release; content acceptance releases only its upload charge.

## 2. Persisted records

### 2.1. Shared domains and physical encoding

New records use `format_version = 1`; there is no default backfill for historical rows. IDs use existing ULID domains, counts are strict nonnegative signed-64 integers, and timestamps use the existing UTC domain. All namespace-bearing foreign keys must agree with the attempt and run. Every write starts from an authorized internal selection, not namespace or store identity supplied by the client.

An address is the existing exact `(store_id, payload_digest)` pair: trusted physical storage identity plus full SHA-256, across aliases and namespaces. It is not a selected approval digest. Live custody also saves the positive native `fence_incarnation`; expiry history retains address identity without a foreign key that would prevent safe fence compaction. The existing `storage_address_fence` allocator and deletion-generation rules are unchanged.

Closed provider DTOs are saved as their bounded canonical text in native text columns, not implicitly decoded JSON. Their existing 16 KiB/depth-16 and finite semantic-slot limits apply. Scalar identities and indexed state remain native columns. Content-bearing logical values stay in owned byte storage or separately admitted escaped text; PostgreSQL JSONB is not the authority for numeric kind, signed zero or NUL-bearing values. Decoding, canonicalization and validation happen only after database resources are released. Native reads admit the whole selected representation and simultaneous copies before driver acquisition.

### 2.2. Upload custody

These relations specialize the already specified `upload_staging` owner; they are not a generic registry of durable content authority.

The [upload-retirement contract](upload-retirement.md#2-native-staging-facts) under #1581 adds native `retained_admission_generation`, `cleanup_generation_floor` and evidence-derived `storage_closure` to every applicable typed staging owner. The generation pair belongs to its admitted actual retained address; unknown closure stays pending. Those fields are specified, not implemented, and confer no provider or execution authority.

| Relation / key | Required native fields and constraints |
|---|---|
| `upload_staging(upload_ref)` | Namespace, run, attempt, original worker/dispatcher/epoch, `format_version`, payload kind, applicable output/stream, saved contract digest, original source size/digest, `stored_at`, fixed `expires_at`, `reserved_size`, `state` (`staged`, `accepted`, `expiring`), `phase` (`receiving`, `finalizing`, `ready`, `closing`), `next_index`, `bytes_received`, issuance state (`open`, `closed`), immutable StageRef/StageSpec, source address/incarnation, optional prepared address/incarnation, promoted ContentRef, truthful promotion attribution, accepted owner ID and finalizer ID. Absent observations are SQL NULL, never fabricated false/zero. |
| `upload_part(upload_ref, index)` | Index 0–15, exact part size/digest/final, immutable original prefix acknowledgment and PartRef. Unique index, contiguous accepted prefix. No receipt for an unreceived truncated part. At most 16 rows per owner. |
| `upload_operation(upload_ref, slot)` | Original StorageOperationRef, bounded exact request, immutable original issuer/receiver provenance, at most one current invocation binding, dispatch state (`intent`, `issued`, `settled`), exact saved outcome and its revision. Slots: begin; each part 0–15; one prefix capture; seal; prepare; promote; retire; release. One immutable operation per semantic slot; replay cannot replace its identity. |
| `upload_finalizer(upload_ref)` | Unique owner, issuer identity, original admission time/deadline, reserved installation slot and state (`active`, `closing`). Deadline expiry is not permission to replace it. Delete only after actual parser/reader/provider work closes. |
| `content_issuer(issuer_id)` | Non-reused process/authority incarnation, physical domain, non-reused receiver and invocation sequence allocators, optional current receiver binding/state, issuer state (`open`, `closing`, `closed`) and exact closure evidence. The issuer identity is immutable; its current receiver may change only through the qualified replacement transition. Foreign keys from unsettled operations prevent forgetting their issuer. A worker grant is not a core issuer identity. |

The source-to-prepared address union is admitted before promotion, in exact address order. A transformation must reserve its maximum simultaneous source/candidate bytes before construction; its destination address is added only after the actual candidate digest is known. A transaction that discovers another required address rolls back and reacquires the complete union, never takes an earlier lock later. No old admission witness bypasses a pending deletion.

The separation of original provenance from the current invocation binding above was accepted in [#1575](https://github.com/realkarych/kora/pull/1575#issuecomment-6886916062): the existing public provider protocol exposes no epoch accessor. Core binds the actual receiver it owns; the provider independently captures and checks its private epoch. The [custody authority design](execution-custody-authority.md#2-independent-identities-and-evidence) keeps those identities separate. Its [proposed native refinement](execution-custody-native.md#5-invocation-and-upload-retirement-boundary) under #1580 specifies original COMMIT and pre-entry closure producers; neither design supplies their implementation.

An unissued intent may be dispatched only by its still-open original issuer after capturing the actual receiver and positively checking current owner admission for a fresh bounded invocation. Reconstruction never refreshes an old invocation. If closure of an old issuer cannot be established, recovery keeps its operations charged and cannot dispatch a replacement mutation. These records describe the evidence to retain; implementation of actual issuer closure and crash-durable authority is a separate prerequisite in section 7.

### 2.3. Accepted owners

| Relation / key | Immutable binding and mutable availability |
|---|---|
| `execution_request_content(attempt_id)` | Namespace/run, format version, original upload reference/declaration, canonical size/digest, complete ContentRef, physical address, accepted fence incarnation, retention class, saved policy revision and acceptance time. `payload_state` is `present`, `expiring`, `expired` or `missing`; separate exact active/recovery holds govern deletion. Unique attempt; the existing ClaimRequestDescriptor is the public projection, not another descriptor format. |
| `artifact_acceptance(artifact_version_id)` | Unique `(attempt_id, output_name)` for physical outputs, namespace/run/node, original upload/source binding, saved output contract identity, full replay digest, selected digest, actual selection and content-free validation result, producer/evidence binding and acceptance time. AgentSession additionally saves its logical digest and original transcript declaration. Artifact status remains on `artifact_version`. |
| `artifact_payload_owner(artifact_version_id)` | Primary physical address/ContentRef/size and owner availability. AgentSession records `capture = captured` with all three present, or `capture = unavailable` with all three NULL and no physical owner. This immutable distinction supplies `not_recorded` to readers without adding that value to `payload_state`. |
| `artifact_derived_owner(artifact_version_id, kind)` | `kind` is `summary`, `cel` or `denial_sample`. Exact saved semantics/path-set identity, retained bytes or admitted escaped text, full content identity, retention/access class and independent availability. Sharing primary bytes does not merge owner lifetimes. AgentSession's fixed summary/CEL view is permanent metadata; its sample is not. |
| `command_capture_owner(artifact_version_id, stream)` | Exactly `stdout` and `stderr`, original child upload binding, logical read reference, physical ContentRef/address, size/full digest, observed-byte count, EOF/truncation facts, tail identity and current availability. Unique stream per result. Root identity binds both immutable capture descriptors. |
| `agent_session_snapshot(artifact_version_id)` | Exact accepted metadata snapshot, price identity, observation identities and immutable capture/source facts; logical digest; denial-sample digest/count/completeness. The sample bytes live only under the derived owner. No full logical JSON or transcript copy remains in this permanent row. |

The acceptance writer inserts the artifact and these companion rows atomically. A native unique constraint on the physical output key is required; the existing nonunique node/output index does not implement write-once acceptance. A concurrent loser returns the recorded descriptor only after complete identity equality; it never replaces the first result. Historical rows missing the new admission/evidence cannot become eligible owners by an invented backfill.

`artifact_acceptance.producer/evidence` binds the existing trusted source tuple: original execution domain, attempt, registered dispatcher/process, request digest, saved output contract, observation sequence/result identity and relevant frozen runtime fields. The authenticated worker relay obtains those fields from supervisor-owned checkpoints/phase records, never candidate JSON. API integration validates the tuple and preserves the source facts before accepting output. The worker-report producer owns this validation; storage cannot mint it from a hash, `validated=true`, caller type name or a terminal-report fingerprint. This producer is a named prerequisite of the result deliveries, including authentic command observation and session finalization/usage mapping.

Existing `artifact_version` identity, status, validation, selection and descriptor columns remain their projections. A versioned writer defines the exact projection in the same transaction; readers refuse absent admission rather than mix old and new authority. Content-bearing validation messages are derived content, never permanent validation metadata. Frozen CEL value persistence and its original numeric provenance still require the separate lossless representation producer; an available primary blob does not satisfy it.

### 2.4. Eligibility and indexes

Every physical owner relation records native `content_eligible` (accepted and present), `retention_clock` (`run_open`, `until`, `forever`), nullable `retained_until` and the exact saved run-retention source identity. `retained_until` is non-NULL exactly for `until`; it is an absolute UTC deadline, not a cached Boolean comparison with the current time. `forever` is allowed only by the owning content contract. The eligibility check uses one current clock observation and requires `retained_until > now`; equality is expired even when the expiry sweep has not marked the owner. A present-state flag alone never proves that an owner is unexpired.

Each typed relation has a partial index over `(store_id, payload_digest, retained_until, owner_key)` for content-eligible `until` rows, and separate address-leading partial indexes for content-eligible `forever` and `run_open` rows. The finite-owner `EXISTS` constrains the deadline as an index range, so increasing due-but-unprocessed history is not scanned then filtered. Permanent-owner lookup is a separate exact-address existence check. A `run_open` candidate additionally requires fresh bounded native confirmation that its saved run's retention clock has not started; NULL in a stale projection is not forever. If that confirmation observes a completed run or an unavailable/mismatched clock source, return unresolved before looking for more candidates or releasing any charge. Resolve its header under the same address lock with the exact saved finish time/retention period, through a bounded keyset catch-up owner in #216. A missing or stale clock projection blocks an absence proof until reconciled; a stalled catch-up cannot make cleanup unsafe. The implementation must establish finite catch-up admission and progress before this lookup path activates.

An atomic owner transition updates native state/deadline admission under the same address lock as deletion. An explicit address-leading hold relation names its retaining request/artifact/capture owner, holder and reason (`execution`, `recovery`, `read`), with a unique live identity and actual release condition. Holds have a separate live index and prevent deletion; transient holds never qualify as independently accepted owners for refused-created-object charge release. Run-clock publication and catch-up are content-retention responsibilities coordinated with the run-finish writer, not a new scheduler scan.

Checks probe every applicable typed relation through these paths; they never interpret a bounded candidate limit as proof that other eligible owners are absent. Legacy/unindexed potential ownership blocks deletion for the affected domain until migration/activation supplies complete coverage. Participating kinds include existing graph resources, session segments and sealed request-input owners even when this slice creates none. Domain configuration cannot exclude another namespace or storage alias.

Sealed `execution_request_content`, accepted artifact primary/derived content and accepted command captures are retaining durable owners. This explicitly extends the concrete retained-owner lookup inventory to the request and capture representations; a descriptor without its eligible owner is insufficient. Unknown, expired, expiring and missing owners do not qualify. An unavailable AgentSession has no primary-address eligibility. A current artifact status does not by itself prove present bytes; historical accepted content can still be retained.

Discovery uses `(state, expires_at, upload_ref)` for abandoned uploads, `(issuer_id, dispatch_state, upload_ref, slot)` for unresolved operations, and typed owner-state/expiry indexes for cleanup. Fixed keyset batches have finite row/byte admission. No permanent per-request retry ledger is introduced. Settled ownerless fences, receipts, slots and issuers are compacted only after the existing acknowledgment and closure requirements hold.

Deletion additionally checks [native staging protection](upload-retirement.md#31-protection-before-deletion-admission) at every admitted declared/source and retained address. Separate partial indexes contain `state = staged OR storage_closure = pending`; accepted or expiring rows remain protective until actual original creation closure is durable. A separate [generation-floor range](upload-retirement.md#32-original-settlement-consumers) identifies expiring owners still dependent on a settled delete. Zero-byte and unknown-attribution rows participate in both checks; neither lookup scans closed or consumed history.

## 3. State, transaction and crash boundaries

The existing scope order governs. When an operation needs a run lock, acquire it first; then any existing ordered scopes; then the complete ordered address set; then upload rows by upload ID, accepted-owner rows by their typed primary key and worker-accounting rows by worker ID. Initial staging uses the specified no-run-lock admission. Never later acquire a run lock in that transaction. Recheck current authority in the separate accepting transaction. Storage calls, full JSON work and slow response delivery hold no transaction, connection, cursor or scope lock.

| Boundary | Durable action before effect/response | Recovery after lost response or crash |
|---|---|---|
| Admission | Validate meta/auth and finite capacities; allocate immutable owner, address admission, charge and begin intent together. | Resolve the original COMMIT before dispatch; uncertain commit creates no replacement owner or effect. |
| Part | Persist the exact mutation intent before write. Persist verified PartRef and progress before acknowledgment. | Observe/reconcile the original operation. Equal replay returns its original prefix acknowledgment; conflict preserves the winning owner/prefix. |
| Finalization | One durable finalizer and all copy/validation/reader capacity are admitted before reread/parse. | Cancellation stops useful issuance and retains ownership until the actual synchronous work and readers close; timeout permits no takeover. |
| Preparation/promotion | Persist actual prepared identity, ordered source/destination address admission and exact promotion intent. | Observe original promotion; unknown creation attribution stays charged. Existence is not attribution. |
| Ready request or child content | Persist immutable promoted descriptor and retain staging/grant/expiry/charge. | Current original-grant recovery returns ready. It creates no accepted owner or effect authority. |
| Seal request | Atomically insert request owner, existing attempt descriptor/policy, Claim read admission/source revision and source completion binding; release its upload charge once. | Current-authorized equal seal returns original policy/descriptor before live-policy checks. Different complete request conflicts. |
| Accept output | Recheck authority and exact prepared/evidence identities; insert artifact/typed owners/lineage/projections and completion bindings; release all consumed upload charges once. | Saved complete identity supplies read-only recovery, even after expiry/supersession; never revalidate or promote on terminal replay. |
| Whole-owner refusal | Mark expiring and permanently close useful issuance before retire. | Preserve original stage/outcomes/reservation; request-local layout/conflict refusal alone does not expire a valid owner. |
| Stage retirement | Persist actual effect/reader closure and exact outcome revision/mutation set before release acknowledgment. | Retry the same acknowledgment; never reconstruct a state-creating retire after release authorization. |
| Created-object refusal | Under the address fence, prove an independently eligible accepted owner or persist the exact deletion generation/intent. | Without a qualifying owner, retain charge through actual deletion and all older issuer/effect closure. Unknown promotion is never false attribution. |
| Deletion acknowledgment | Persist exact deletion outcome and closed issuance before `release_delete`; compact only after durable acknowledgment on both sides. | Reconcile original operation; a stale delete can never execute against recreated bytes. |

Accepted uploads release their core charge at acceptance, but their provider-private state remains separately charged until retirement/release actually completes. Refused uploads release only after stage closure plus authoritative no-create attribution, independently retained accepted ownership, or completed safe deletion. A missing file, cancelled task or elapsed deadline satisfies none of these conditions.

The [retirement transitions](upload-retirement.md#4-transitions-and-original-recovery) keep all protective admissions after refusal until pre-provider-entry invocations, finalizers, readers, native work and original stage release actually close. Only that qualified transition permits deletion admission. Original created-object cleanup consumes an exact later settlement once; authoritative no-effect consumption advances its floor without releasing its charge. Upload closure, consumption and removal require the complete ordered source/retained address union; the one-address deletion units do not narrow that owner lock set.

## 4. Execution request handoff

Both an inline seal body and `payload_kind = execution_request` pass through the same custody lifecycle. Inline is a transport convenience, not permission to commit a descriptor before bytes are durable. The request semantic schema, rendering, capability checks and policy selection remain with [#1453](https://github.com/realkarych/kora/issues/1453); storage receives the exact validated nonsecret bytes and identity.

Ready upload recovery requires its original grant. First seal additionally requires current execute/result authority, the saved input/graph/price identities, current policy revision/capabilities and the inherited deadline. Under the run lock, an existing seal is checked after current namespace/service/lease authorization and before current-policy or new-effect checks. Equal replay returns the original descriptor and policy; a different digest conflicts without acquiring new storage authority.

The sealing transaction uses the existing atomic attempt/Claim source writer. It writes `execution_request`, `execution_policy`, `attempt_claim_read_admission` and increments `source_revision` together with `execution_request_content` and completion binding. The existing complete descriptor cap is 16 KiB, including ContentRef and wrappers. A failure rolls back all metadata effects and leaves the original upload cleanup-owned. No runtime allocation, workspace preparation, secret resolution or submit precedes durable bytes and the successful seal.

An active/recovery hold names the exact request owner. Recovery loads the recorded body and policy; it never renders current configuration or substitutes current inputs. Content expiry retains the digest, compact policy/bindings and descriptor with explicit availability. Prompt/feedback and equivalent derived content require the existing transcripts capability. No permanent canonical-body copy is hidden in admission, replay or diagnostics records.

## 5. Result transfer and acceptance proposals

### 5.1. Common wire rules

The following extensions are proposed for the existing `POST /attempts/{att}/artifacts` route. They are not admitted by current closed models. Implementing PRs must update the shared client, worker transport, OpenAPI and applicable CLI/MCP parity in the same delivery; no direct storage route is introduced. Existing meta-first 16 KiB, 16 MiB part, 256 MiB source and fixed progress/recovery rules remain. Native type limits apply before the generic maximum. All added selectors participate in immutable upload binding, replay and recovery.

| Kind | Extra closed selectors | Final result |
|---|---|---|
| Existing `output` | Existing output/type selectors; for command `result`, `capture_uploads: {stdout, stderr}`; for agent `session`, `transcript_upload_ref` or explicit null. These fields are absent for other outputs. | Complete accepted artifact descriptor, after atomic adoption of named children. |
| New `command_capture` | `output_name: result`, `stream: stdout` or `stderr`; `type_name` absent. Source size is at most 64 MiB. | Ready child descriptor, still reserved; no artifact version. |
| Existing `transcript`, when bound to implicit `session` | `output_name: session`; `type_name` absent. This is an explicit new bound variant, not reinterpretation of an existing unbound upload. | Ready child descriptor until session acceptance; server truncation retains original source identity and returns its actual retained descriptor. |

The output-specific child selectors occur in both data and recover metadata, unchanged across parts. A ready child response is the closed `{kind: ready, upload_ref, expires_at, content: {storage_ref, payload_digest, size}, truncated}`. `storage_ref` is a server-derived owner-scoped logical token, 1–256 printable non-space ASCII characters, not a provider DTO or URL. For a command capture it is exactly `capture:<attempt_id>:<stream>`, using the canonical stored attempt ID and `stdout` or `stderr`; for the bound session transcript it is `transcript:<attempt_id>:session`. The token identifies a logical owner slot, never a grant, upload, stage, physical address or storage alias. It confers no read capability. Before parent acceptance no readable accepted owner exists at that slot; parent construction also requires its exact current-grant ready upload and verified source identity. `truncated` is true only for server-truncated transcripts. Existing ready request responses are unchanged and have no content member. A child terminal recover returns its saved owner descriptor and current availability once adopted.

At most one live child per `(attempt, original grant, parent output, stream/kind)` is admitted. A refused/expired child cannot be replaced under the same identity while its effects remain unresolved; a fresh upload gets fresh admission and retains old cleanup charges. The unchanged open-upload ceiling of declared outputs plus two still applies: seal the request before uploading results; command result needs two captures plus its root, and session needs its root plus one transcript. Exceeding this ceiling refuses rather than borrowing another worker's allowance. These ordering conditions are worker obligations, not a new request timeout.

Child completion identity survives staging cleanup in its typed accepted owner. After current authorization, a saved parent is resolved by the existing complete canonical/logical digest and contract before checking live child rows or new-result eligibility. Exact terminal replay needs no live child or original grant, writes nothing and returns current saved availability/status. Saved child source completion bindings support recovery; they do not add transport upload IDs to the parent's immutable digest key. An alternative child reference is not permission to change an accepted parent.

Expired unaccepted children remain unavailable. A different grant cannot adopt the previous grant's unaccepted children. When current authority permits retransmission from the original immutable runtime checkpoint, it obtains fresh upload references, independently admits and verifies the same bytes and receives the same logical slot tokens. It can then submit the already frozen identical root bytes with its fresh child selectors. Old staging effects, fences and charges remain independently cleanup-owned; no grant or physical content authority transfers through the token. An unavailable checkpoint, changed capture facts or unresolved address admission prevents this recovery instead of regenerating a result or bypassing the old effects.

### 5.2. Command result

The worker retrieves both immutable sanitized captures and the trusted command observation from the original runtime checkpoint. It uploads captures, saves their returned logical-token mapping in its recovery state, then constructs and freezes the canonical CommandResult root with those tokens. Only the storage-reference mapping changes; exit, duration, checkout/protection/resources, capture digests/counts/EOF/truncation and tails must equal the trusted observation. Neither candidate files nor a command-provided JSON object can supply that provenance.

The API obtains the authenticated runtime-observation binding through the worker evidence producer, checks every root fact against it, and fully verifies actual retained capture bytes and tails outside database resources. The native provider alone proves neither this binding nor capture integrity. Empty captured streams have real empty-byte digest/size/tail and still have owners. Missing/unsealable captures or unknown leader exit cannot be replaced with empty bytes or a fabricated result.

One final transaction adopts both ready child owners, inserts the root and derived owners and records all three source completion bindings. Partial acceptance is forbidden. If parent validation or authority fails, the children remain charged under their original cleanup lifecycle. If a response is lost after commit, parent/child recovery returns the same accepted owner; no second command or new capture is generated. Acceptance does not attest runtime quiescence or release physical attempt capacity.

### 5.3. AgentSession

The worker uploads the opaque transcript through the bound variant above, or records genuinely unavailable capture. It then sends the complete session logical value as the `output` payload for `session`, within its independent 4 MiB/depth-16 bound; it never puts that value into the 16 KiB meta part. The canonical logical transfer is a staging source only. Its full digest is distinct from the primary transcript's physical digest.

The transfer contains the finalization observations from the trusted snapshot. Its claimed derived USD fields are comparison inputs, not accounting authority: the API derives them from the same immutable submitted usage observations and the attempt's pinned price revision, verifies equality and validates the accepted view. It does not substitute the later live ledger. The producer must prove exact source-to-accepted-view agreement and preserve the snapshot observation identities. A mismatch refuses the entire result; the server does not silently rewrite the addressed logical source. Broader unavailable effective contracts remain refused.

Acceptance atomically adopts the captured transcript owner, or records unavailable capture with NULL physical descriptor fields, and saves complete logical identity, fixed metadata, separate expiring denial sample, safe summary and frozen CEL view. The transient full logical source is not promoted as another permanent payload. Its private stage is retired after acceptance; sample-bearing copies follow sample lifetime. Source declaration and truncation facts remain immutable comparison evidence even after source cleanup.

Equal transcript bytes alone never establish replay. The logical digest binds metadata, usage snapshot, denial sample/completeness, capture state and source declaration. Captured-empty, unavailable, truncated, missing and expired remain distinct. Current namespace/transcripts access governs transcript/sample reads; the fixed summary/CEL view cannot expose them. Later usage corrections do not rewrite accepted session identity or projections.

### 5.4. StructuredOutput and projections

Canonical raw and retained bytes use the existing 1 MiB type limit and canonical-wire refusal; summary has an independent owner even when it shares root bytes. The actual producer must return the complete effective-validation result under the saved closure, then selection/summary/projection under that same identity. [ADR-0027](../../docs/decisions/0027-bounded-effective-schema-validation.md) and [common composition](artifacts/StructuredOutput.md#34-common-composition-and-resources) remain explicit unavailable prerequisites where unimplemented. Exact built-in model success does not activate inline/parent/custom schema support or an undeclared narrower exception.

CEL delivery requires the lossless frozen projection and original numeric provenance described by the existing contract, with admission before full acquisition and no storage I/O in scheduler transactions. This design does not choose a substitute codec. Until its actual producer exists, dependent admission [#1446](https://github.com/realkarych/kora/issues/1446) cannot consume a guessed projection merely because primary content was accepted.

## 6. Finite resources and diagnostics

The proposed initial core composition shares one local receiver per physical domain per API process, with a durable domain-wide admission pool across replicas. Reconstruction follows the existing maximum of three within the original finite deadline and closes actual old resources first. No receiver is created per upload request. Existing provider limits and worker staged-byte caps remain independent.

For owner review, initial installation capacities are four core finalizers, eight content readers and four synchronous validation operations per physical domain, with no waiting queue: saturation returns existing bounded busy/pending refusal before acquiring bytes or parsing. Each finalizer owns at most one validation operation. Cleanup has two reserved control admissions independent of useful work. These are admission counts, not process-memory or throughput guarantees; the implementation plan must qualify the configured composition on both databases/platforms before activation.

Before work, each admitted operation reserves all simultaneous raw/canonical/prepared buffers and semantic records. The proposed aggregate encoded-buffer budget is 512 MiB per domain; values may not borrow unaccounted heap via decoding or copied trees. Typed validator allocation accounting, native acquisition budgets and provider private bytes remain additional. A 256 MiB request can require the whole encoded allowance for source plus canonical copy; saturation reduces concurrency rather than the public payload ceiling. Python object overhead, driver buffers, RSS and elapsed time remain separately measured diagnostics unless an existing approved method makes them blocking. The request decoder's complete native allocation proof is a prerequisite, not established by this byte sum.

Persisted active capacity slots have unique owners, charged state and exact actual release conditions. Recovery preserves them through unknown effects. Finite active slots do not permit unbounded idle queues, pending tasks, receivers or prepared-contract caches. Disposable stage/intent/receipt/fence state must settle across repeated distinct uploads; accepted immutable history is deliberately excluded from that disposable-state count.

API owns content-free admission, validation refusal and replay diagnostics; metadata/retention owns reservations, fences and acknowledgment; workers own spool/relay closure; storage owns byte-effect diagnostics. Preserve the existing [observability contract](observability.md#7-component-coverage-and-activation). No payload, source/retained hash, private reference, observation value or parser exception enters diagnostics, including DEBUG. Broken/blocked sinks cannot delay heartbeat, stop escalation, response or cleanup. Logging creates no execution or deletion authority.

## 7. Activation and complete implementation deliveries

Publication delivers a specification, not executable evidence. Address-fenced effects remain disabled unless the actual metadata profile proves crash durability of every writer/checkpoint path, coherent allocator/owner/stage/intent/generation restore, provider lineage continuity, and closure of every earlier metadata authority/issuer. SQLite WAL/FULL/macOS full-sync and PostgreSQL settings checks are necessary observations, not that proof. No walking-skeleton exception extends to this boundary. If the supported deployment cannot meet it, present a separate explicit contract decision rather than silently downgrading guarantees.

The [qualified custody authority proposal](execution-custody-authority.md) under #1572 names an independent core journal, commit handshake, issuer ownership, conservative unresolved states and missing native producers. Its additional persistent owner, initial co-located-core/local-store profile and write serialization require owner acceptance. It supplies no implemented durability proof or size exception. Multi-host core and S3 still need a concrete qualification mechanism; publication cannot activate them by analogy.

The narrow cleanup prerequisite includes refused-created-object deletion, issuer/effect closure and acknowledgment. It breaks the dependency on deferred full periodic retention; disabling every deletion or retaining every refused object forever does not. [#1320](https://github.com/realkarych/kora/issues/1320) supplies shared delete custody, and [#1581](upload-retirement.md) specifies its indexed staging handoff. [#867](https://github.com/realkarych/kora/issues/867) remains graph-resource staging. Neither graph staging nor full periodic retention is silently resumed wholesale.

These are planning estimates against the 1,000-line complete-diff ceiling, not exceptions. Before each implementation, create or select its issue, inventory actual reusable code, post the exact plan and size, and split over-limit work by complete outcome. Tests, migrations with behavior and API/client/CLI/MCP parity cannot be discarded to fit. Any new package needs its approved layer row. No implementation may publish a partial API merely to fit a slice.

The request delivery supplies the content prerequisite for #1453. Result deliveries supply actual accepted owners and trusted summaries for [#1454](https://github.com/realkarych/kora/issues/1454). #1472 consumes them while retaining its closure and terminal-state decision; #1446 then selects accepted inputs with real frozen projections. Producer construction precedes report consumption, so a report fingerprint cannot be used to bootstrap missing provenance. Full agent completion needs both StructuredOutput and implicit AgentSession; request storage alone does not unblock it.

## 8. Verification ownership

The design PR runs repository Markdown/link checks, the current-architecture size check and one complete final-head CI, with independent correctness, security and performance review of these contracts. It introduces no new test framework, numerical campaign, CI lane, timeout or merge gate. The following are future implementation cases, not passing results of this publication.
