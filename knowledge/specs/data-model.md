# kora MVP design — control-plane data model

Status: design draft for owner review (2026-10-15, revised after the design review, see [review-2026-10-15.md](../reviews/review-2026-10-15.md)). Scope: the metadata-database entities, their state machines and the invariants the scheduler relies on (FR-4, FR-6, FR-7, FR-9, FR-12.4–12.5, NFR-1.2, NFR-2, NFR-4.3, NFR-5.5). Companion documents: [ir.md](ir.md) (what a graph version contains), [scheduler.md](scheduler.md) (who writes these rows and when), [api-and-agent-surface.md](api-and-agent-surface.md) (how they are exposed). Owner decisions on design choices are referenced as **DD-n** ("design decision n") and recorded in [design-decisions.md](../reviews/design-decisions-2026-10-15.md).

## 1. Principles

1. **Run state is interpretable data** (NFR-5.5, decision 12). Every row below is plain JSON-compatible data; no pickled objects, no callables (NFR-4.3, FR-7.5). The scheduler is a pure function from rows to actions, so a Temporal-backed execution backend could later own the `run`/`node_instance`/`attempt`/`wait` rows' transitions while `artifact_version`, `approval_request`, `usage_record` and the registry stay in kora's DB unchanged.
2. **Multi-tenant from the first table.** Every entity carries `namespace_id`; every query is scoped by it; ids are globally unique (ULIDs), so no composite tenant keys are needed in URLs.
3. **Durable before side effects** (NFR-2.1). An attempt row is committed before `runtime.submit`, and the submission is keyed by the attempt id; an approval request row is committed before `channel.request`; a start is acknowledged only after its canonical pending run or durable overlap-skip outcome commits (ADR-0020).
4. **Append, do not overwrite.** Superseded results stay as rows with a status; the timeline is an append-only `event` table.
5. **Same schema on SQLite and Postgres.** Only the statements in the dialect table of [scheduler.md section 10](scheduler.md#10-standalone-sqlite-versus-postgres) differ; no feature exists only in standalone mode (NFR-0.1).
6. **One writer path for workers.** Workers never touch these tables directly; they read and write through the HTTP API with a service principal, fenced by a lease epoch (section 3). Standalone mode runs the same client over an in-process ASGI transport.

| `event_evaluation` | `event_id`, `wait_id` (unique together, indexed by wait), `evaluated_at` | one narrow row per inbound event and wait whose `match` has been evaluated, whatever the result, inserted in the evaluating transaction, so each pair is evaluated at most once regardless of commit order and evaluation never rewrites the event row; any transaction that closes the wait only marks it closed, and a background task deletes a closed wait's rows in fixed-size batches, which is safe because a closed wait is never evaluated ([ir.md section 7.7](ir.md#77-evaluation-errors)) |
| `notification_subscription` | `id`, `namespace_id`, `revision` (advanced on every change), `kinds` (JSON list from the allowed set of actionable event kinds), `destination` (JSON: `json` with a `url` and `signing_key` secret reference; `slack` with a webhook-URL secret reference or a bot-token reference and channel; `telegram` with a bot-token reference and chat id), `enabled`, `state` (`ok`, `failing`), `last_error`, `created_at`, `updated_at` | ADR-0025; writes require the `platform` flag; no secret value is stored |
| `notification_delivery` | `id`, `subscription_id`, `event_id` (unique with `subscription_id`), `state` (`pending`, `delivered`, `suspended`, `dropped`), `attempts`, `next_attempt_at`, `claim_token`, `claim_until`, `subscription_revision_used`, `last_error` (redacted) | inserted in the same transaction as the event it delivers, one per enabled subscription selecting the event's kind, under the namespace notification lock (scheduler.md section 19), so commit order cannot skip an event; claimed and acknowledged by the delivery task (scheduler.md section 19) |

The [cancellation-cause storage foundation](https://github.com/realkarych/kora/issues/572) adds only nullable `attempt.cancel_cause` and its exact five-value domain through forward migration `0004`. Existing rows and old inserts that omit the field remain SQL NULL, meaning that no cause was recorded; NULL proves neither that no stop occurred nor that execution may resume. There is no default or backfill. Cross-update first-write ordering remains the future shared engine transition's responsibility, not a storage constraint. Original terminal-report outcome and complete immutable deadline persistence remain separate prerequisites under [#545](https://github.com/realkarych/kora/issues/545); this field activates no cancellation, timeout, completion or runtime authority. The [migration evidence and limits](../research/attempt-cancel-cause-storage-2026-11-01.md) distinguish schema qualification from those pending consumers.

### 2.1 Durable run scheduling marker

`run.needs_scheduling` is a non-null boolean initialized true on canonical run creation. Index the true-run discovery predicate. Existing-run graph-relevant writes hold the run lock and set it true in the same transaction as the state change. No separate notification or follow-up touch is sufficient. This marker requests reevaluation; it supplies neither effect authority nor a replacement generation (ADR-0003). Worker reports classify as scheduler.md section 12 states: a state transition writes its event and the marker; a usage upload marks the run without an event; a counter update marks the run only when `usd` or a token count changes and a budget scope applies (a run or subgraph `budget_usd`, or the namespace `daily_budget_usd`), and otherwise only updates `attempt.counters` ([issue #139](https://github.com/realkarych/kora/issues/139)); a lease-only renewal writes neither.

| Transition family | Marking obligation |
|---|---|
| Run creation, promotion, retry/clear, cancellation and lifecycle changes | Include the marker in the accepted transition, also when a settled failed run returns to running |
| Current attempt/state/result acceptance, output promotion, recovery changes and reservation release | Mark when local readiness, completion or admission can change; historical-only late output never gains result authority |
| Counter/usage updates and relevant effective-limit changes | Mark affected runs so aggregate budget/admission checks cannot miss new information: every usage upload, and a counter update that changes `usd` or a token count while a budget scope applies; unrelated diagnostics and other counter fields alone need not mark. No namespace policy or limit write, and no graph deploy or retire that changes a cap source, marks runs, because none holds a run lock: the independent admission-recheck predicate of scheduler.md section 8 finds the affected runs and takes each run's lock, and a raised limit takes effect at each held instance's admission `wake_at` |
| Wait/event/approval resolution, current observation application and deadline expiry | Mark atomically with their accepted state/artifact changes; future due work still has its independent discovery predicate |
| Body materialisation, branch decision/target state, wrapper export and collection | Mark atomically, including child-only recollection and every affected downstream clear |
| Any other transition enabling a local scheduler pass | Mark in its transaction; the list above is not an exemption for an unlisted enabling transition |

The scheduler clears the marker only under the same run lock after a fresh fixed-point check, in the same transaction as acknowledgement. At the ten-round cap it remains true if local work remains. Waiting for a future due time or external result can be a local fixed point because independent durable scans remain active ([scheduler section 8](scheduler.md#8-restart-and-multi-scheduler-safety)). `updated_at` is not a work-discovery watermark. A crash before acknowledgement leaves a candidate; after acknowledgement any later enabling change sets it again. No new generation or outbox is needed.

Future conformance uses real PostgreSQL and SQLite, injected clocks and explicit transaction barriers rather than sleeps:

| Test | Required result |
|---|---|
| `test_readiness_discovers_commit_behind_scan_without_notification` | PostgreSQL hides an uncommitted enabling write while a scan completes; its later commit is still discovered despite its earlier timestamp. SQLite exercises the serialized equivalent and the same eventual outcome |
| `test_settled_failed_retry_reenters_discovery` | Retrying a settled failed run with no active attempt/wait/deadline marks it and progresses without another write or notification |
| `test_readiness_continues_after_round_cap` | A graph requiring more than ten local rounds retains continuation and completes over later ticks |
| `test_readiness_restart_discovers_unfinished_work` | Restart before/after acknowledgement and while independent waits/observations are outstanding loses no work or duplicate-effect protection |
| `test_readiness_scan_revisits_work_behind_page_cursor` | Persistent marked rows and continuous arrivals cannot starve a finite sweep's tail; a row newly marked behind the cursor is revisited after wrap |
| `test_scheduling_ack_does_not_erase_concurrent_change` | An enabling writer before/after the locked final check is processed or leaves the marker true; a stale check cannot erase it |
| `test_scheduling_marker_preserves_incrementality_and_latency` | Notification-disabled MVP load meets NFR-3.1 including discovery/claim delay, while a 1,000-node graph meets NFR-3.3 without whole-graph rescans |

The [VcsRef revision-1 contract](artifacts/README.md) defines the immutable publication payload and shared principal record. These values do not replace the existing trusted operation/result authority.

### Retained grant prefixes (issue #226)

Every immutable attempt_dispatcher binding has a `prefix_count` and `prefix_digest` under the [shared history contract](protocols.md#resumable-retained-dispatcher-history-issue-226). Grant insertion under the run lock atomically saves those fields, advances the attempt's compact `{upper_epoch, count, digest}` tip and clears its current-grant-scoped verified-history acknowledgement. The digest includes the complete saved GrantBinding, including null process and leads_group, and excludes mutable closure state and recovery_version. Epoch gaps do not change count semantics. Grants are never dropped, capped or renumbered to fit a transfer.

The attempt retains the compact current tip, current-grant acknowledgement `{dispatcher_id, lease_epoch, snapshot}` when present, and bounded migration checkpoint/activation state when needed. A captured snapshot reads this committed tip in constant space. Index `(attempt_id, lease_epoch)` supports bounded keyset reads; an index covering open grants supports predecessor/all-grant closure without visiting retained closed rows. Submitted closure evidence is validated in one bounded batched lookup of only its dispatcher/epoch tuples. Current-tip acknowledgement, evidence validation and permitted-action changes share the existing transaction, so a failure commits neither half. Identical replay changes no row, event or recovery_version.

The runtime's accepted/refused evidence-delivery dispositions are delivery bookkeeping, not metadata closure authority. Refused evidence never closes attempt_dispatcher, removes a recovery hold, releases reservations or permits replacement. Only the existing authenticated authoritative closure transition does so. New grants invalidate verified-history acknowledgement; completed delivery of an older prefix cannot authorize effects against a later tip.

The initial schema creates fields/indexes before grants exist. Populated upgrades follow the shared contract's bounded atomic backfill and locked activation comparison: preserve null process identities, persist each verified checkpoint, release resources between batches, catch up without scanning under the authority lock, and wait for compatible writers and worker/runtime peers with affirmative legacy-authority drain. Previous request/readers/gates remain available during compatible rollout. No stale or unbackfilled tip is presented as complete. Both-database interruption, concurrent append, activation and unrelated-progress cases are pending work items 9–11; their implementing issues must exist before activation.

## 3. Identifiers and keys

- All primary keys are ULIDs with a type prefix in the API (`run_01J…`, `att_01J…`, `art_01J…`), sortable by creation time.
- `run.idempotency_key`: supplied by the caller (`Idempotency-Key` header, CLI `--idempotency-key`) or derived: cron → `cron:<graph_version>:<fire time>`, webhook → the delivery id, graph trigger → `<parent run id>:<event>`. Unique per `graph_id`; a duplicate returns the existing run (NFR-2.2).
- `run.target_key` (FR-6.11, [ADR-0014](../../docs/decisions/0014-target-identity.md), [ADR-0019](../../docs/decisions/0019-immutable-run-target-identity.md)): the optional namespace-scoped business identity, indexed on `(namespace_id, target_key)`, matching `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,255}$`. Equality is exact and case-sensitive; it is never a template variable. A valid present parameter binds at run creation; an absent optional parameter leaves the run unbound and an invalid present one is validation failure. An output source binds at successful atomic acceptance of its complete result (section 12). Once non-null, the key never changes or clears. The first `run.target_bound` event records its parameter name or exact artifact version and selector; same-key rediscovery writes no second binding event. `run.target_held_since` is separate: admission acquires it under the bound key, ordinary settled release clears only the hold, and retry must reacquire the same key. Terminal runs retain unresolved holds under ADR-0017. Delivery (`idempotency_key`), target and attempt remain distinct.
- Submission is keyed by the **attempt id**: runtimes dedupe on it and `lookup(attempt_id)` recovers a handle after a crash (FR-6.1a); there is no separate key column (current contract [scheduler](scheduler.md)).
- `approval_request.channel_request_id`: the primary external review/comment/page id, learned after durable dispatch authorization and external delivery. Read-only marker lookup recovers lost responses, including additional duplicate ids in `delivery`. Only a current pending request may authorize create/retry; terminal lookup never creates. A late learned id is saved on its original row regardless of current delivery revision (section 14).
- `attempt.lease_epoch`: incremented on every claim or reclaim and returned to the worker; every heartbeat, segment upload, artifact upload and state transition carries it, and the API rejects a stale epoch with `API008`, so a worker that lost its lease cannot write (fencing). The epoch fences a *previous lease holder*; it does not change on cancellation, so it cannot fence the attempt's own late writes.
- **Result authority** ([ADR-0007](../../docs/decisions/0007-attempt-model-and-retries.md)): an attempt may change current state only while `attempt.desired_state = run` and `node_instance.current_attempt_id = attempt.id`. The API checks both, together with the epoch, on an artifact upload and on a `succeeded` or `failed` terminal report, except `failed {timeout}` after the attempt's own deadline; when either fails, an uploaded artifact is stored with `status = superseded` and cannot bind or fail the current target source, and the report is answered with `desired_state = cancel` instead of being applied. A `cancelled` or `lost` report is a closure report outside result authority and never creates current outputs (section 4). Cancellation and clear-downstream (section 6) set `desired_state = cancel` and clear `current_attempt_id` in one transaction, so from that commit on the old attempt's writes are historical. The attempt-scope deadline expiry also revokes result authority through cancel intent (`desired_state = cancel`, `cancel_cause = timeout`), but keeps `current_attempt_id`, so the attempt stays its instance's current attempt until completion applies `failed {timeout}` and node retry policy (scheduler.md sections 2 and 17, [issue #139](https://github.com/realkarych/kora/issues/139)). Usage records, session segments and events are accepted under a valid epoch regardless of result authority, so the cost of a cancelled attempt is never lost. Late approval responses are recorded and ignored because the request is no longer `pending` (section 4). No generation counters are needed.
- `idempotency_record`: `(token_id, key)` unique; a replay with a different `request_digest` is `API004`. A manual trigger or a rerun without a key gets a fresh ULID; `params` are validated against the graph version's `params` schema (DD-36).
- **Artifact payloads** (DD-36): uploaded through the API as multipart; `payload_digest` is the SHA-256 of the complete canonical JSON (or of the bytes for files) and identifies the immutable stored payload. The separate `digest` covers the fields selected by the saved artifact-type contract for approval binding; it must never be used to deduplicate different complete payloads. Payloads ≤ 64 KiB are stored `inline`, larger ones under `artifacts/sha256/ab/cd/<hex>` with `StorageRef = local://sha256/<hex>` in the local implementation.

[AgentSession revision 1](artifacts/AgentSession.md) preserves `payload_digest` as actual retained-transcript byte identity for physical storage fences. Its complete replay identity additionally requires the saved effective contract and permanent `logical_output_digest` over the canonical metadata/denial/transcript validation value. The revision deliberately selects that full logical value for approval; equality of approval/logical digests does not turn either into a storage address. Operational availability and provider aliases do not change logical identity. No complete logical JSON copy containing expired denial content becomes permanent metadata.

For derived AgentSession lists and scheduler collections/exports, the [aggregate activation prerequisite](artifacts/AgentSession.md#derived-list-aggregate-activation) keeps full materialization, persistence and command/public-read delivery unavailable until work items 3/9/10 coordinated with 11/12 approve and save finite canonical-byte/depth/item-count/admission semantics and prove admission before full allocation. Exact child transcript/sample owners, eligibility and availability propagate under existing generic list/lineage semantics, with worker 17 and #216 owning actual resource integration. An aggregate row, copied digest or surviving metadata alone cannot renew content, bypass transcripts rights or hold shared bytes forever. Per-result/upload/CEL bounds supply no aggregate bound; no numerical aggregate default is selected.

The inline rule has a type-scoped exception for [StructuredOutput revision 1](artifacts/StructuredOutput.md#4-upload-storage-summaries-and-lifetime), its saved descendants and corresponding derived item contracts: exact canonical UTF-8 bytes behind the existing content descriptor/storage reference are authoritative at every size. Decoded `inline` JSON is an optional view/cache, never a replay/hash or identity-summary reconstruction source. PostgreSQL JSONB/SQLite JSON alone is not presumed to preserve numeric kind, signed zero, NUL or available root null. This changes no descriptor shape and adds no database column/codec. A derived list's aggregate wire/storage semantics remain separately saved; item ancestry alone cannot install a new whole-list codec or cap.

VcsRef revision 1 uses the [exact canonical wire representation](artifacts/README.md#4-canonical-bytes-and-digests); its entire payload enters both digest roles, which remain distinct. Its native revision/principal bounds match the existing approval and automation-principal columns. The reference payload remains forever, while its saved identity summary has a separate artifact-payload-retention owner under section 11.3, even when they share bytes.

**Publication recovery state** ([ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md)): the runtime checkpoint, outside candidate authority on protected runtimes, owns the immutable sealed bytes, prepared native revision and phase journal. The attempt summary mirrors its non-secret identity and phase for observability; it cannot reconstruct missing private state or authorize a different revision. Candidate events cannot mint `WorkspaceRef`, `PreparedPublication` or platform VCS facts. Local follows the same data path in a trusted environment without OS-enforced journal integrity. This publication checkpoint is distinct from the post-release harness checkpoint and from the complete attempt-input manifest tracked in issue #53.

## 4. State machines

Terminal states are in bold. Every transition writes an `event` row in the same transaction.

The internal pending-run cancellation branch under [#598](https://github.com/realkarych/kora/issues/598) accepts only a pending run with no node history, start time, deadline latch, finish time or target hold. Under caller-held run/global/namespace/graph locks on the same writer connection, it checks current user namespace authority and fresh run/graph/version relationships, then commits `cancelled`, the finish/update time, `needs_scheduling = true` and one `run.cancelled` event together. It preserves pinned interpretation, parameters, trigger, retention, target identity and accepted-start receipts. Retired versions and unavailable execution providers do not prevent this cancellation. The existing outstanding predicate releases one contribution; the branch owns no physical execution or hold release.

The owner accepted the first production cancellation event representation on 2026-11-01: payload `{trigger, graph_version, rerun_of}` copies the saved trigger, exact `run.graph_version_id` identifier and nullable `run.rerun_of_run_id`. The user actor is `{kind: "user", owner, token_id}` from the authenticated principal, without credential values or a permission snapshot. Attribution is historical data, never current authority. This defines no other authority kind's actor representation.

A repeated call for an already cancelled, unstarted and unmaterialized run with a finish time and the same deadline/hold exclusions returns unchanged after current authority checks. It neither reads nor repairs event history, consumes time/IDs, rewrites the original actor/time, nor claims to reconstruct an API idempotency receipt. The internal result exposes whether an application changed the scheduling marker from false to true. Caller integration still owns current credential authentication, transactional PostgreSQL notification, postcommit SQLite wake-up and committed INFO diagnostics. Public cancellation and active-run stopping remain pending under #593 and the API/scheduler work items; this library branch does not activate them.

**run**: `pending` → `running` → **`succeeded`** | `failed` | **`cancelled`**. `failed` is not terminal: `retry node` (FR-6.8) moves it back to `running`; `cancel` moves it to `cancelled`, which discards nothing and accepts recovery-only reconciliation/cleanup but no resumed execution (Archon's failed-resumable vs cancelled-discarded split). `pending` exists between canonical acceptance and promotion, including an overlap queue. Promotion is graph-serialized; queue chooses the oldest pending run when no run is running (section 13). `running` includes "all remaining nodes are waiting" and does not imply execution occupancy. A `running` run **finishes** in two ways. In pass 8 (scheduler.md section 2), under the run lock, once every top-level instance is finished for the run, it becomes `failed` when at least one top-level instance is `failed`, `upstream_failed` or `cancelled`, and `succeeded` otherwise. At run-scope deadline expiry it becomes `failed` with `timeout`, whatever its pending instances (scheduler.md section 17, ADR-0022). A top-level instance is the one instance of an entry of `graph.nodes`, whose `node_path` has no enclosing scope; `node_instance.top_level` marks it, indexed with `run_id`, because `subgraph_attempt = 1` alone also marks first-iteration body instances. The finish check is an indexed existence test for a top-level instance of the run that is not finished, so it never scans fan-out bodies. Finishing does not wait for attempt or recovery closure: reservations, outstanding usage and target holds follow section 13.1 until closure. `retry node` moves a `failed` run back to `running`, clears `finished_at` and sets the marker; a later finish writes a new outcome event and sets `finished_at` again, so retention never measures from an earlier finish while the run is live. Settled `failed` releases outstanding acceptance despite remaining resumable; retry reacquires it before effects.

**node_instance**: `pending` → `ready` (trigger rule satisfied, inputs resolved) → `queued` (attempt created, waiting for a worker) → `running` (from the attempt's `submitted` transition) → **`succeeded`** | `failed` | **`skipped`** | **`upstream_failed`** | **`cancelled`** | `waiting`. `waiting` is entered by human_input, wait_event, timer, admission back-pressure and retry back-off and returns to `running` or `ready` when the wait resolves. A full clear (section 6) returns every affected current instance to `pending`, including `skipped` and `upstream_failed` instances with no consumed versions; earlier artifact versions stay `superseded`. A wrapper reached only through a changed child result returns to `running` for recollection, preserving its current body. `skipped` is set by branch non-selection, trigger rules and `on_expiry: skip`. A node instance is **finished for the run** when it is `succeeded`, `skipped`, `upstream_failed`, `cancelled` or `failed`. A runtime node with an automatic retry left, including an infrastructure or provider retry, is `waiting` on its `retry_backoff` wait rather than `failed` (scheduler.md section 7), so for a runtime node `failed` means that no automatic retry is pending. When a `fan_out` or sub-graph counts as finished is part of the open container question below. A `failed` instance stays non-terminal for `retry node`; readiness evaluates upstream instances against "finished for the run" (scheduler.md section 2, pass 3). How a `fan_out` or sub-graph becomes finished while its body still has live work, how a container's outcome derives from its body, and what follows a cancelled node are open ([architecture reference](../architecture/detailed.md#open-implementation-questions)). A sub-graph instance is `running` while its current sub-graph attempt's body runs, `failed` with class `attempt_failed` when the body routes to `$fail_attempt`, and starts sub-graph attempt N+1 by re-materialising the body with `subgraph_attempt = N+1` if its retry policy allows. Ownership of finalisation (DD-36, amended by ADR-0019): the API validates uploaded artifacts against saved schemas, the worker moves the attempt to `finishing`, and completion verifies the complete output set and closure before moving the instance. Ordinary output versions are current; all outputs of the declared target source remain staged until the same transaction accepts its key and promotes its complete result (section 12). Wake-up and collection paths apply that acceptance rule to scheduler-only sources too.

**attempt**: `created` → `claimed` (a worker holds the lease) → `submitted` (handle persisted) → `running` (first heartbeat or status) → `finishing` (terminal report accepted; closure and outputs being settled) → **`succeeded`** | **`failed`** (with `error_class`) | **`cancelled`** | **`lost`**. `claimed → finishing` and `submitted → finishing` are edges too, for a report before the session ran. The worker's one write-once terminal report carries the outcome (`succeeded`, `failed`, `cancelled` or `lost`) and its closure evidence ([api-and-agent-surface.md](api-and-agent-surface.md#worker-route-bodies-issue-139), [issue #139](https://github.com/realkarych/kora/issues/139)); scheduler pass 8 applies the terminal status. `desired_state = cancel` is set by cancellation, by clear-downstream and by attempt-scope deadline expiry; the worker learns it from the next heartbeat response and performs the cancel, and from the moment it is set the attempt has no result authority (section 3): its uploads create no `current` version, a `finishing` report with `succeeded` or `failed` is refused, except `failed {timeout}` after the attempt's own deadline, and a `cancelled` report is accepted as a closure report and never creates current outputs. Only two attempts end without a report: a never-dispatched `created` attempt, cancelled from metadata, and an attempt whose closure an operator `confirm_stopped` completes, which pass 8 moves from `claimed`, `submitted` or `running` to `cancelled` or `lost`, or to `failed {timeout}` when its own deadline latched first; a `finishing` attempt closed by attestation completes with its recorded outcome after rules 0 to 2. `stalled` is an `error_class`, not a state: a stalled attempt is failed with class `stalled`, which the node's policy may retry. `lost` means affirmative original-domain retirement evidence and closure of every old dispatcher and unresolved platform publication establish that the original execution cannot continue, but its result cannot be recovered. A missing handle, lost registry, unreachable host or any lease duration is insufficient. It is classified `infrastructure` and does not consume agent attempts (NFR-2.4); retry policy applies only after this barrier clears. An ordered cancellation becomes `cancelled` after closure, never an infrastructure retry. An attempt is always a runtime submission; a sub-graph attempt is never an `attempt` row.

**Execution recovery** ([ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md)): `execution_state` is orthogonal to attempt status and runtime phase. `not_started` means no dispatch authority was ever granted; the first grant conservatively records `unknown` until an affirmative observation establishes `live` or stopped evidence establishes `stopped`. Lease expiry records `unknown` without making the attempt terminal or clearing its reservation, except for a `finishing` attempt whose runtime quiescence is recorded and whose reporting grant is closed, which keeps `stopped` and sets no `recovery_required` for that lease (scheduler.md section 3, [issue #139](https://github.com/realkarych/kora/issues/139)). `stopped` is affirmative runtime quiescence within the scope the receipt or record names (`TerminationReceipt.scope`, `NormalCompletionQuiescence.scope`, recorded in `attempt.recovery`; local scopes are cooperative, [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md)), not by itself proof that worker-host/code-host operations ended. Runtime observations never establish it ([protocols.md](protocols.md) section 2, issue #134): `RuntimeStatus` `queued`, `starting` and `running` support `live`; `exited`, `lost`, `Liveness.candidate_alive = false` and `Liveness.supervisor_alive = false` record `unknown`, or keep it, until stopped evidence arrives, and no runtime observation moves `stopped` back; only an original-domain `TerminationReceipt`, the runner's normal-completion runtime-quiescence record and operator `confirm_stopped` attestation establish `stopped`, each with its own provenance. `DispatcherQuiescence` affects only dispatcher closure and `replacement_blocked`; a grant closes on a `registry_acknowledgement`, on local `runtime_observed_process_exit` evidence whose observed identity equals the grant's `process`, or on operator `confirm_stopped` attestation ([protocols.md section 2](protocols.md#2-runtime-fr-81), "Local runtime"). `replacement_blocked` is derived from possible live execution, missing termination evidence, any unclosed dispatcher grant or unknown platform publication; reads list the exact reasons. A fresh observation can establish `live` and permit adoption of the same attempt, but new worker-dispatched effects wait for all earlier grants to close. The run-wide admission barrier applies to unresolved **recovery**, identified by `recovery_required`, rather than every healthy live attempt or its current grant. Set it on lease expiry, an uncertain effect outcome, cancellation/supersession awaiting closure or a failure awaiting termination evidence. An ordinary healthy first claim awaiting its initial observation does not by itself set it. Clear it when the same current non-retired attempt is affirmatively adopted live or recovered from an authoritative immutable prepared/completed checkpoint, with every earlier grant/operation closed, or when complete termination/dispatch/publication closure is established. Before the saved execution deadline, checkpoint recovery may finish only the original immutable operation (including change-request creation after a completed push), without restarting candidate execution; after expiry only read-only reconciliation/closure is allowed (ADR-0022); cancelled/superseded/stop-requested work remains recovery-only. A normal current executing grant is allowed during live/checkpoint adoption; it must close before the attempt becomes terminal. All new runtime admissions in the affected run wait while any `recovery_required` remains; healthy parallel attempts retain ordinary concurrency behavior. Direct replacement of an old attempt and linked rerun still require their full replacement conditions, even when ordinary live work is healthy. Normal terminal transitions also require execution and dispatch/publication closure; runtime phase completion or candidate exit alone is insufficient.

The API increments `recovery_version` on each recovery-relevant observation, authority grant, requested action or evidence change under the run lock. A request compares the expected version and original domain atomically. The original domain is persisted before any preparation/submission effect and is immutable on the attempt. Runtime receipt, worker acknowledgement, provider evidence and human attestation are recorded with distinct provenance, binding ids, observed time and evidence reference; operator evidence is never labelled automatically verified. Events `attempt.execution_unknown`, `attempt.execution_observed`, `attempt.retired`, `attempt.dispatcher_closed` and `attempt.reconciled` carry version, domain, reason, actor and non-secret evidence. A current recovery lease relays runtime-registry evidence through existing reporting routes, without giving stale API epochs a write exception. Ordinary retention never deletes dispatcher rows or retirement tombstones.

**wait**: `open` → **`satisfied`** | **`expired`** | **`cancelled`**. Timer wakes, retry/admission rechecks and approval/sensor timeouts use `wake_at` on a `wait` row (current contract [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md)); expiry applies the node's `on_expiry`. Execution deadlines instead use the persisted run, subgraph-instance and attempt clocks and guards in section 15 (ADR-0022); they are not wait rows. Cancellation happens on run cancel, on clear-downstream and when the owning attempt is failed by a timeout. At most one open wait owns a node's current activation; close the old wait before replacement. An approved VCS-bound request retains its original open wait until fresh head verification resolves its current gate; the request's historical status alone grants no authority (section 14).

**approval_request**: `pending` → **`approved`** | **`rejected`** | **`failed`** (a response passed every check but `approve_when` could not be evaluated; the response is kept and never counts as approval, [ir.md section 7.7](ir.md#77-evaluation-errors)) | **`expired`** (set by the wait's expiry) | **`invalidated`** | **`cancelled`**. A response whose `(commit_sha, digests)` differ from the bound values is refused with `API006` and the row stays `pending` (FR-7.2a); a response from a token without `approve` is `API005` (DD-32); a VCS response from the change-request author, from kora's bot identity, or from a login outside the namespace's `approver_allowlist` is refused and logged (DD-35). A head observation that differs from `bound_commit_sha` (the scheduler's `head_sha` poll or a push webhook, scheduler.md section 5) moves the row to `invalidated` with `observed_head_sha` recorded, commits channel-closure intent and fails the node with class `candidate_moved`; nothing re-requests on the same bundle, because the row covers one immutable revision (`bound_commit_sha`, `bound_digests`, `context_artifact_version_id`), and a new request exists only after the producing node was retried and the gates ran on the new commit ([ADR-0008](../../docs/decisions/0008-content-bound-approvals.md)). A response to a row that is no longer `pending` is recorded as an `approval.responded` event with `applied: false` and changes nothing (`API006` through the API); a pending-watch result cannot change a row that is no longer `pending`; an equal-head push changes no approval decision but fences outstanding read authority (section 14). Before an `approved` row's node completes, the scheduler checks the head once more and fails the node with `candidate_moved` when it moved; the row stays `approved`. `rejected` fails the node with class `approval_rejected`.

**artifact_version**: ordinary valid outputs start `current`, but are not bindable until scheduler pass 8 completes their attempt `succeeded`; under any other completion status they become `superseded`, or `invalid` when validation failed, so the completion transition is the result acceptance of ADR-0022 ([issue #139](https://github.com/realkarych/kora/issues/139)); every output of the declared target source starts `staged`, with complete-source acceptance atomically promoting it to `current` (section 12). Rejection/failure/clear makes valid staged companions `superseded` and invalid source data `invalid`. Current versions become `superseded` when replaced or cleared, or `invalid` on validation failure. A settled source production cannot return to staged/current through replay. Scheduling never deletes history. Payload availability and access are independent of this result state.

## 5. Attempts, sub-graph attempts and lineage

- An **attempt** is exactly one runtime submission and the unit of cost. A node instance stores mutable scheduling pointers in `consumed_versions` when it becomes `ready`. Creating each physical attempt copies its complete input bindings in the same transaction; the attempt's outputs derive `artifact_lineage` from that saved record. The attempt retains its bindings even if it fails before producing any output (ADR-0018, section 11).
- The **resolved configuration is saved on its attempt**, not recomputed from current node pointers, registry aliases or preset provenance. `execution_request` owns retained nonsecret rendered configuration/feedback; `resolved_config_digest` verifies its config portion, and the request descriptor binds the complete logical request. Payload expiry is explicit and a digest never reconstructs missing bytes. Different attempts can differ in policy, feedback, strategy and observed environment as well as input versions. A graph version pins its full execution/type contract (ADR-0018, section 11).
- A **sub-graph attempt** is an integer. The sub-graph's own node instance and every body instance carry `subgraph_attempt`; the body's `node_path` embeds it (`candidates[2]@3.review`). Sub-graph attempt N+1 materialises a fresh body with `subgraph_attempt = N+1`; nodes validly marked `attempt_invariant` are not materialised again (branches and their ordinary direct targets cannot use that flag in MVP, IR010), and their consumers get `artifact_lineage.relation = reused_invariant` rows pointing to the earlier version. The `PreviousAttempt` artifact is written by the scheduler as an `artifact_version` of the sub-graph instance (`output_name = previous_attempt`) so that lineage and the API treat it like any artifact. Nothing about a sub-graph attempt is a row in `attempt`.
- Limits spanning sub-graph attempts (sub-graph `timeout`, `budget_usd`, `max_attempts`) are evaluated against the sub-graph instance: its `started_at` and the sum of `usage_record.usd_estimate` over the attempts of all its body instances across sub-graph attempts.
- **Cost on an approval request** is the sum of the run's usage records at request time (DD-8, current contract [ADR-0010](../../docs/decisions/0010-cost-accounting-and-limits.md)); no lineage walk. Cost per accepted change (NFR-8.3) remains derivable offline from `artifact_lineage` and `usage_record`.

### 5.1 Current branch selection

A branch instance owns `branch_selection`: a nullable list of selected ordinary target node IDs in its graph/body scope. The owner instance ID, node path and its run's immutable graph version bind the decision to the concrete activation; no artifact payload or physical attempt is needed. `null` means no current decision, while `[]` is a valid selection of no ordinary targets. Publish the decision, `branch.selected` event and successful branch state atomically under the run lock. A successful branch must have a current decision. Reserved `$fail_attempt` retains its iteration-ending action and is not a node ID in this list.

Every direct target consults this state on readiness, even after target-only clearing. Owner clearing resets its decision to null in the same transaction as invalidation of its control dependents; historical events remain. A later body iteration materialises its own branch and direct targets: IR010 forbids `attempt_invariant` on both, so neither an old selection nor an already successful target is reused to bypass the current route. Target-only clearing retains the owner's decision. Compact selection survives artifact/request payload expiry and remains with the node's control record; inputs are needed to reevaluate a cleared owner, not to recheck an unchanged selection.

| Owner state | Direct target result before ordinary readiness |
|---|---|
| Non-terminal | Remain pending |
| `succeeded`, target selected | Evaluate terminal upstreams, trigger rule and required inputs |
| `succeeded`, target excluded, or `skipped` | `skipped` |
| `failed` or `upstream_failed` | `upstream_failed` |
| `cancelled` | Existing instance/run cancellation rules; never admission through routing |

This gate cannot be waived by `independent_of` or a permissive trigger rule. It governs direct targets only; untargeted joins and failure handlers evaluate ordinary dependencies.

Future conformance; runtime cases run on both metadata databases:

| Test | Required result |
|---|---|
| `test_branch_target_cannot_run_before_route` | A delayed route keeps even a data-independent target pending; selected/excluded outcomes are honored, including permissive triggers |
| `test_branch_unresolved_and_terminal_owners` | Nested skipped/failed owners propagate the direct-target outcomes above without recursively skipping an untargeted join |
| `test_branch_target_clear_retains_selection` | A separate upstream retry clears an excluded target while its owner remains successful; the retained exclusion still skips it, also after owner input payload expiry |
| `test_branch_retry_replaces_selection` | Clearing/retrying the owner revokes its decision and affected targets; only its new successful selection can enable them |
| `test_branch_ir_rejects_invariant_routing_nodes` | Shared compile/deploy semantic validation returns IR010 at the flag for an invariant branch (including fail-attempt-only branches) or any direct case/else target, in top-level and nested body scopes; omitted/false flags and ordinary invariant non-targets remain valid |
| `test_branch_new_iteration_uses_current_route` | Iteration 1 selects T and then fails elsewhere; iteration 2 materialises fresh route/target instances and excludes T, so T is skipped without executing or reusing its old success; an unrelated invariant result retains its existing reuse/lineage |
| `test_branch_ir_ownership_and_cycles` | DSL emits control edges; direct IR missing them or with two owners fails IR010; self/routing cycles fail IR001; an untargeted reconvergent join remains valid |

## 6. Clear downstream (FR-6.8a)

Downstream results are invalidated at exactly two moments: a **manual retry** of a node (FR-6.8) and the start of **sub-graph attempt** N+1. Both run one transaction under the run lock. Manual retry first checks persistent scope expiry (including a retried wrapper itself), then required retained inputs, and atomically reacquires outstanding acceptance if the failed run was settled; `run_backlog_full` refuses before any closure/artifact/wait mutation (section 13). Automatic sub-graph retry remains within its existing outstanding run:

1. Compute invalidation from the pinned IR's declared data and control dependencies, resolved to concrete current runtime instances. Include an input edge even when its consumer has never bound an artifact or created an attempt. Resolve `$inputs` forwarding and body-result dependencies through subgraph exports and fan-out collection to outer consumers. Current `consumed_versions` and reuse bindings supplement this graph; obsolete historical bindings do not revive obsolete iterations. A current consumer may legitimately reuse an invariant version produced in an earlier iteration, and that dependency must remain reachable.
2. Apply `independent_of` per affected **input name**, using the pre-clear state: it preserves only an already `succeeded` consumer's outcome, including a scheduler-only success without artifacts. It never exempts an unexecuted, failed, skipped, upstream-failed, running or waiting consumer. Any affected non-exempt input or control edge still invalidates the consumer. Propagation stops along a preserved unchanged result, but another affected path may still reach the same consumer or its descendants. Control and branch-routing gates cannot be waived by input independence.
3. Fully clear the explicitly retried node and affected consumers: set `status = pending`, clear `consumed_versions` and `current_attempt_id`, reset a cleared branch's `branch_selection` to null, mark their `current` and `staged` versions `superseded`, cancel open waits, invalidate pending approval requests with durable channel-closure intent, and set non-terminal attempts' `desired_state = cancel` with reason `upstream_superseded`. Classify wrappers separately as specified below; compute the complete affected set before mutating the pre-clear state.
4. A child-result change invalidates its enclosing wrapper's exports/collector result and propagates through those results to outer consumers. Rearm this wrapper as `running` for recollection, preserving its current body instances, unaffected sibling results, current iteration, original input bindings, first start and deadline. Do not move it to `pending` and rematerialise its body. In contrast, explicitly retrying the wrapper or invalidating one of its own non-exempt inputs or control/routing dependencies fully clears its current body and resets/re-expands it under the existing subgraph/fan-out rules; a changed mapped `over` input is this full-clear case. A full clear takes precedence if both paths reach a wrapper. Existing `attempt_invariant` reuse across a new subgraph iteration remains subject to those rules; it is not a cache for arbitrarily changed inputs.
5. Preserve every old attempt's input bindings, saved request and policy, and all non-terminal old attempts, dispatcher grants and reservations, including after a run cancel; make recovery-only claims available. While any old execution/publication is unresolved, all new runtime admissions in the run wait with `execution_recovery`. No old attempt is rebound to the instance as current.
6. Set `run.needs_scheduling = true` and commit. Readiness reevaluates terminal upstreams, trigger rules, required inputs and branch gates; clear is not an instruction to execute regardless of those checks. Wrappers recollect/export only when their current body permits completion. The run's first target key and binding evidence survive; replacement source results must pass the same complete-result acceptance and equality check (section 12), never rebind the run. No inherited run or wrapper clock is reset.

| Invalidation mode | Current state after clear | Preserved state |
|---|---|---|
| Ordinary affected node, including `upstream_failed` with no bindings | `pending`, no current scheduling bindings or result authority | Immutable attempts, lineage, usage and inherited clocks |
| Wrapper reached only by a child-result dependency | `running`, exports/staged results superseded until recollection | Body identities, iteration, unaffected siblings and original inputs/clocks |
| Explicit wrapper retry or affected wrapper input/control dependency | `pending`, affected current body reset for materialisation | Historical bodies/results and write-once scope clocks |
| Successful consumer exempt on every affected input, with no affected control edge | Unchanged successful outcome | Current result and its downstream result path |

Future integration conformance on PostgreSQL and SQLite:

| Test | Required result |
|---|---|
| `test_retry_producer_reactivates_unconsumed_dependents` | A exhausts retries before producing; data-only B becomes `upstream_failed` without bindings. Eligible manual retry of A clears B, and B can complete after A succeeds |
| `test_retry_input_independence_requires_success` | Only a pre-existing successful outcome survives an exempt input change; resultless, failed, skipped, running and waiting consumers are reevaluated; an affected non-exempt input/control path wins over an exempt path |
| `test_retry_body_output_invalidates_collector_and_outer_consumers` | Retrying one mapped body result rearms each enclosing export/collector and its outer consumers, preserving sibling identities/results and immutable history without rematerialisation |
| `test_retry_wrapper_input_resets_body` | Changing a wrapper input, including `over`, or invalidating its control/routing dependency resets the affected current body; child recollection cannot override this full clear |
| `test_retry_tracks_current_invariant_reuse` | Current reuse of an earlier invariant version participates in invalidation; obsolete historical bindings alone never reactivate an old iteration |

Because the transaction is atomic and revokes result authority (section 3) in the same commit that orders the cancel, no generation counter or dirty set is needed: a write that arrives after the commit with a still-valid epoch is historical, never current. The integration test `test_cleared_attempt_cannot_publish_current` fixes this: attempt A is stopped right before its upload, its upstream is retried and replacement intent is recorded, then A uploads its output and sends a `succeeded` report before its next heartbeat; the report is refused with `desired_state: cancel` and A later reports `cancelled`; A's output is `superseded`, the instance is not completed, nothing downstream becomes ready, and A's usage records are kept; no replacement B is admitted until A's execution and all dispatch/publication authority are closed; on PostgreSQL and SQLite, with the upload and the clear in both transaction orders.

## 7. Usage records and completeness (FR-9.1)

The ownership and arithmetic contract was approved under [issue #142](https://github.com/realkarych/kora/issues/142#issuecomment-6353409349). [Issue #213](https://github.com/realkarych/kora/issues/213) implements the shared immutable values in `kora.ir.cost`, pure arithmetic in `kora.ir.pricing`, scoped typed reads in `kora.db.cost_reads` and forward migration `0002_pricing_foundation`. Engine installation/pinning/aggregation, runner and adapter adoption, approval transactions and public cost projections remain **forward contracts** with the owners below. Accepting a value establishes neither execution nor accounting-write authority. Migration preserves predecessor facts and explicitly missing historical snapshots; it never reconstructs them from current prices.

### 7.1. Immutable price ownership and handoff

The API process, including its initialization in standalone, imports shipped/default or trusted operator namespace configuration through `kora.engine` functions. The scheduler selects stored revisions; a worker, candidate or graph cannot import or edit prices. No public price-management operation or additional provider protocol is introduced. A `price_table` revision contains `id`, `namespace_id` (null for the default), `effective_from`, `version = 1`, `normalization_version = 1` and `prices`, a model-keyed map. Each model entry has the total USD rates per million tokens for `input`, `cached_input`, `cache_creation_5m`, `cache_creation_1h`, `output` and `reasoning`; a null rate explicitly means unavailable. Model keys match normalized observations exactly, without implicit aliases or fallback. Canonical decimal strings encode rates. An identical scope/effective-time/content import is idempotent; different content at the same scope/effective time is refused. Imported revisions are immutable accounting history.

The engine pins `attempt.price_table_id` atomically with attempt creation and input bindings, using the injected attempt-creation time, not `started_at` (first executing claim). It selects the newest namespace revision with `effective_from` at or before that time visible to the transaction, otherwise the newest default revision. A namespace revision replaces the **whole table**, including an empty map; a missing model never silently consults default prices. With no applicable configured revision, the attempt pins an immutable empty default revision. Only a new attempt can select newer or backdated prices.

The claim carries the selected id and complete immutable revision. The worker includes those exact values in the nonsecret saved request; sealing verifies equality with engine-owned metadata. The request digest and runtime checkpoint bind them. The runner prices live observations with this map without a database or price-service lookup. Adoption and historical usage uploads keep the original snapshot, including missing entries. Price versions remain available independently of request/transcript payload expiry. Unreferenced-version reclamation is separate future work; this contract retains imported versions rather than introducing a cleanup path.

Selection uses indexed scope/effective-time lookups with a latest-row limit and bounded query count, never a preload of historical versions or configuration import under an attempt lock. Usage acceptance reads the pinned table once. Decoded maps, cursors and transactions are disposable; any later cache needs an explicit bound and release owner.

### 7.2. Normalized usage and derivation

One `usage_record` represents each attributable `(attempt, model)`. Its integer token columns are observed nonnegative lower bounds; `known_token_fields` distinguishes a reported zero from a missing dimension. `cache_creation_by_ttl`, when known, carries the attributable 5-minute and 1-hour counts. The normalized `reported_usd` is a nullable harness observation, distinct from the engine-derived `usd_estimate`; opaque vendor `source` is bounded evidence, never an engine pricing interface. Rows preserve immutable observation identity/order and `observed_at`. The attempt-level `usage_coverage` records `completeness`, source `observed_at`, `attribution_gap`, `observation_gap` and its own attempt-scoped `observation_id`/`observation_sequence` independently of model rows. The identity is at most 256 printable characters and the sequence a strict integer from 0 through 9,007,199,254,740,991. Both are null only in the initial unavailable/no-observation state, with null source time and no asserted gaps. A real coverage or gap revision has identity/order even when no usable usage timestamp exists. Checkpoint, `SessionResult`, `Liveness` and the usage envelope preserve that same revision through relay and adoption. Identical revision/content is a no-op, the same sequence with different identity/content conflicts, and an older sequence never replaces newer evidence; the initial state cannot reset accepted coverage. Receipt or poll time never creates a new coverage sequence. Sequence exhaustion preserves an explicit observation gap instead of wrapping or renewing the source identity. No usable report yields no model rows and `unavailable`; unknown model attribution records a gap rather than a fictitious model. Empty or omitted rows never delete earlier evidence.

`complete` requires usable final evidence under the adapter's detailed mapping, not merely a result event. Known interrupted usage is `partial`; absence of usable usage is `unavailable`. Claude's streaming-abort and post-result exceptions remain partial. A killed Codex turn cannot acquire complete usage from its completion status. `complete > partial > unavailable` orders completeness; aggregate views carry the weakest participating state. Unresolved execution/recovery or healthy live execution caps a reported figure at `partial`, while an unavailable report stays unavailable. Last source-usage time survives replay and is not replaced by a fresh heartbeat or API receipt time.

For `strategy = resume`, the adapter reports deltas against the previous attempt's whole-session observations and sets `delta_of_session_totals`; no whole-session total is added again. A `strategy_fallback` starts a new session and reports its own whole figures with that flag false. Resume integration remains pending the runtime capability, independently of the first-slice no-new-attempt rule. Late usage under a fresh recovery lease can improve historical evidence without restoring result authority.

The canonical token convention is uncached `input_tokens = I`, separate cache reads `C` and cache writes `W`, and `output_tokens = O` **including** `reasoning_tokens = R`. With rates per million tokens, the formula is:

`(I * p_input + C * p_cached + W5 * p_write5 + W1 * p_write1 + (O - R) * p_output + R * p_reasoning) / 1_000_000`.

`W5 + W1 = W` and `0 <= R <= O`. Rate values are total prices, not surcharges. Equal output/reasoning rates permit pricing known `O` without a separately reported `R`; equal write rates permit pricing known `W` without its TTL split. Zero writes need no split. Otherwise a missing required dimension makes the estimate null. A query-wide cache split is never allocated among multiple models by guesswork. Default reasoning pricing equals output where the provider bills them alike; a declared gateway may set a distinct rate. Each adapter owns native inclusion rules, mapped in [protocols section 14](protocols.md#14-harness-mapping-tables-fr-33-dd-27); it never double-charges cache or reasoning.

At usage acceptance, the API calls the engine to derive and persist `usd_estimate` with the coherent observation under the run lock. A worker cannot supply that output field. `harness_list` and `harness_managed` use the validated normalized per-model `reported_usd`; `price_table` and `gateway` use the attempt's pinned map. Missing evidence never triggers an implicit basis change. The supported adapter mapping determines allowed basis and billing class. Subscription overrides a numeric harness amount: tokens remain, USD is null and labelled **not billable in USD**. A partial row can have a numeric estimate for its reported portion, labelled partial; missing prices or required dimensions are null, never zero.

A replacement cannot lower token counts or completeness recorded by another grant. It replaces a coherent row, never independent maxima. One supported transition from an interim table estimate to the same attempt/model's validated final harness observation may lower USD; it does not change billing class, erase observations or reopen historical budget-exhaustion outcomes. Reverse transitions, arbitrary basis cycling, conflicting replay and regressive same-basis observations are refused. This is the approved amendment to the monetary implication of `test_usage_replacement_never_lowers_cost` from #139; `test_usage_replacement_preserves_observed_usage` and `test_usage_final_basis_can_correct_estimate` replace it. Identical replay changes nothing. A permanent regression refusal leaves accepted evidence intact; the worker records a safe bounded diagnostic and continues heartbeat/closure handling rather than endlessly retrying that upload.

### 7.3. Live observations and bounds

Normalized money crosses kora's JSON, API, request and journal boundaries as canonical finite nonnegative fixed-point decimal strings, without exponent notation or binary-float conversion. Rates and stored/reported/aggregate USD use the existing `Numeric(24,10)` domain, up to `99999999999999.9999999999`. Parse length/digits/scale before Decimal construction; use enough intermediate precision for all bounded products and sums. Round once per cumulative model row to ten fractional digits, `ROUND_HALF_EVEN`. Live pricing likewise accumulates exact products before cumulative quantization; totals sum stored decimals, not display-rounded or per-call-rounded amounts. Overflow and invalid subsets are explicit, never clamped.

The implemented lexical form is `(?:0|[1-9][0-9]{0,13})(?:\.[0-9]{0,9}[1-9])?`, matched against the entire string, at most 25 characters. Zero is `"0"`; signs, whitespace, redundant leading zeros, a trailing decimal point, trailing fractional zeros, exponent notation and numeric inputs are refused. Accepted examples include `"0.0000000001"` and `"99999999999999.9999999999"`; `"0.0"`, `"01"` and `1.0` are invalid normalized money. Arithmetic and storage formatting use their own Decimal contexts, independent of the caller. Aware timestamps normalize to UTC and serialize with `Z`; numeric epoch strings and UTC overflow are refused. These strict boundaries apply equally to direct construction and raw JSON admission.

The native adapter ingress is the sole monetary conversion exception: a supported SDK can already expose a cumulative model estimate as an integer or binary float. Reject booleans, negative, non-finite and out-of-range values; convert the finite value's shortest decimal representation to Decimal and quantize once to the canonical `reported_usd` string. This preserves the SDK estimate, not unrecoverable original wire precision. No rate or normalized monetary field in an event, `UsageRow` or worker/API payload accepts a float; engine arithmetic is decimal-only. Bounded opaque `source` may retain the native representation as non-authoritative evidence, never as a pricing input. The adapter uses its supported SDK interface; it does not replace the transport with CLI JSONL parsing to recover precision. The engine consumes only normalized `reported_usd`, never opaque vendor `source`.

The canonical price revision is at most 64 KiB. Model identifiers retain the 256-printable-character bound, `source` the 8-KiB bound, and at most 64 distinct models accumulate per attempt across all reports. Stored per-model token counts retain the PostgreSQL signed-32 maximum, 2,147,483,647, enforced identically on SQLite. Model/count overflow preserves an explicit partial/unavailable gap rather than wrapping, saturating or claiming complete totals. Boolean, float and string token inputs and inconsistent presence/TTL data are rejected before changing counters, coverage, observation identity/time or checkpoints. These product bounds are not measured performance budgets.

The runner derives price coverage from validated observations; an adapter's `priced` assertion grants no authority. Live counters expose nullable `usd`, separately labelled `known_usd`, `pricing_status` and `usage_coverage`, retaining the source observation time. Mixed priced/unpriced observations cannot present their known subtotal as the whole amount. Dedupe/order state is bounded independently of `max_events`, since `usage` is not an event-count-limited kind: retain cumulative state for at most 64 models, the existing 1,024 open messages and bounded source high-water state, not every id or raw observation. Loss of exact deduplication produces a gap and prevents additions that could double-count; eviction never authorizes recounting. Finalization reads bounded current state.

Adoption after a worker restart can preserve a surviving runner's counters. Runner death never authorizes a replacement runner. EventSink updates counters before its lossy journal queue, so journal loss, caps or a crash can leave only recovered lower bounds and last observations; a termination receipt does not prove complete usage or zero spend. The missing interval remains partial/unavailable. Accounting and diagnostics cannot stall interrupt/kill escalation. Price maps, counters and replay state release with their owning runner, retaining only required durable recovery/history evidence.

Usage and approval cost remain required in slice 1 regardless of deferred cost-read operations. [Issue #140](https://github.com/realkarych/kora/issues/140) owns budget implementation/refusal and unknown-pricing behavior when enforcement activates. An unsupported configured budget is refused, never silently accepted with a disabled check. This contract activates no USD enforcement and introduces no hard USD kill rule; unpriced usage without an enforced USD budget remains collectable and visibly unknown.

### 7.4. Immutable approval cost

Creating an approval request calls an engine transition under the run lock. Fresh reads after obtaining that lock aggregate persisted usage from **every** attempt of the run, including failed, cancelled, superseded, retry and fan-out attempts, and save `run_cost` in the same transaction. No live-counter value, artifact-lineage walk, current price lookup or external I/O participates. A late report, a final-basis correction, price installation, payload expiry or delivery retry never changes an existing snapshot. A later approval gets a new snapshot.

Coverage includes potentially cost-producing agent attempts even without rows: every attempt ever granted execute authority unless affirmative evidence establishes that candidate execution never began. A missing handle, worker loss or subsequent closure alone does not establish that. Healthy live agents are partial/unavailable. Never-granted cancellations and ordinary command-only work do not invent model usage gaps. Only a genuinely empty cost-producing ledger can show known zero without observations. Missing reports, attribution gaps, unpriced rows and mixed subscription billing remain explicit.

The version-1 `run_cost` is read-only domain data, separate from the approval response form:

| Field | Meaning |
|---|---|
| `version`, `as_of` | `1`; snapshot creation time |
| `observed_at` | oldest latest source-usage time among covered attempts; null if any required observation is absent, or no cost-producing attempt exists |
| `completeness` | weakest covered state, including attempts without rows; known empty ledger is complete |
| `usd_estimate` | sum of recorded amounts only when all contributing cost has a USD estimate; null for missing/unpriced/subscription components; a numeric partial amount is labelled with partial completeness |
| `known_usd_estimate` | sum of priced observations, explicitly a subtotal; null when none exists, except known empty ledger is zero |
| `pricing_status` | `estimated` when all represented cost is priced, `partially_priced` for a known priced subtotal with unpriced/subscription/missing components, `not_billable` for exclusively known subscription usage, otherwise `unpriced`; empty ledger is estimated zero |
| `missing_report_attempts`, `attribution_gap_attempts`, `observation_gap_attempts` | counts of relevant attempts; categories can overlap and are not summed as an attempt total |
| `models` | model-sorted entries containing `model`, the five observed token sums, `unknown_token_fields`, `completeness`, nullable `usd_estimate` and `known_usd_estimate`, `pricing_status`, `billing_classes` and `bases`; sets are sorted and contain unique values |

Per-model unknown token dimensions remain marked even when a known lower bound can be summed. A USD subtotal does not make an incomplete token ledger complete. Subscription-only rows keep null USD even if the native harness reports a list-price amount. Mixed bases/billing classes for one model are retained as sets rather than relabelled to one basis. Attempts with no attributable model appear in coverage, not a synthetic model row. API approval list/detail, shared clients, CLI/MCP and `ApprovalRequestDto` preserve this exact snapshot. Every channel displays its cost state next to the form; CLI in slice 1 and VCS when implemented use the same value on delivery/retry.

Approval list pages preserve each complete snapshot within the row and response-byte bounds of [the API contract](api-and-agent-surface.md#2-resources-and-operations); pagination never truncates accounting fields. The list loads no detail-only context or form payload and releases database resources before handing the bounded response to a slow consumer.

Aggregation uses indexed run-scoped bounded batches/cursors, linear work in attempts plus usage rows, and exact application-side Decimal addition on both databases. No SQLite SQL `SUM`/numeric cast, N+1 query or raw-source/price-map preload substitutes for that. Count each coverage attempt once independently of its model count. Batching bounds memory, not total lock time. At most 1,024 model entries and 1 MiB canonical JSON fit a snapshot; aggregate tokens remain in the exact JSON integer domain, 0 through 9,007,199,254,740,991, and aggregate USD in `Numeric(24,10)`. Overflow atomically fails the approval node with `config_error`/`approval_cost_too_large`, creates no request and leaves the ledger intact. It never publishes a truncated sum or kills running agents. Snapshot bytes are durable accounting history; disposable buffers, cursors, locks and connections release on success, error, cancellation and shutdown.

## 9. Compatibility with a Temporal-backed backend (NFR-5.5)

The shared transition functions of [scheduler.md section 12](scheduler.md#12-execution-backend-boundary-nfr-55) own the transitions of `run`, `node_instance`, `attempt` and `wait`; the API calls them for the requests it receives and the scheduler for its passes. A Temporal backend would replace the callers, not the rows: it would keep those four as projections written by workflow code, so the API still reads kora's DB, and it would need a synchronous, validated Update for signals, because the API applies a signal durably before it responds. Meanwhile `artifact_version`, `artifact_lineage`, `approval_request`, `usage_record`, `session_segment`, `event` and the registry are written by activities through the same code as today; of these, `approval_request`, `artifact_version`, price revision imports and `usage_record` writes are `kora.engine` functions, like those of the four execution tables, and `kora.db` holds the table definitions, the migrations and read functions (scheduler.md section 12). The API's synchronous contract and the protocols stay the same whichever backend performs the transitions. Two rules keep the door open: no table stores backend-specific handles except `attempt.handle` and `attempt.lease_*`, and the scheduler never relies on in-memory state between passes (NFR-1.2). The boundary is described in prose (scheduler.md section 12), not as an interface with one implementation (DD-7, [ADR-0001](../../docs/decisions/0001-own-control-plane.md) and [scheduler section 12](scheduler.md#12-execution-backend-boundary-nfr-55)).

## 10. Retention (DD-4)

A resolved run-retention record has `retention_version = 1` and exactly the saved `transcripts` and `artifact_payloads` values. A NULL version denotes an unversioned historical record; it is never resolved from current graph or namespace settings. The snapshot-input/read foundation does not enforce production run creation or authorize cleanup. Those consumers must establish immutable writes, legacy activation and complete owner admission before the corresponding runtime gates activate.

Retention is required for the first slice under [#216](https://github.com/realkarych/kora/issues/216), integrating work items 5/8/10/12. Finite content defaults below remain active when the graph omits retention settings; immutable metadata and active/recovery-held resources retain their separate lifetimes. Version retirement is deferred, so active-version resource growth is intentional durable state, not eligible garbage.

Retention is a graph-level setting (`runtime.retention` in the IR) with a namespace default (`namespace.policy.retention`); the resolved values are copied onto each `run` at creation. Defaults:

| data | default | what the retention task does |
|---|---|---|
| run, node instance, attempt, event and usage records | forever | nothing |
| session transcripts (`AgentSession` payloads) and session segments | 30 days after the run finished | deletes the blobs; rows retain fixed AgentSession metadata, complete logical identity and explicit capture/availability facts; a separately owned denial sample follows the shorter resolved transcript/artifact-payload period |
| artifact payloads (files, structured outputs, command output captures and content-bearing summaries/projections, including CEL projections) | 30 days after the run finished | deletes the blob and inline content, including `cel_projection` (an `AgentSession` projection holds only session metadata and stays with the row); the `artifact_version` row stays with `payload_state = expired`, digest and lineage intact |
| original terminal-report error message/details | shorter saved transcript/artifact-payload period after the run finished | clears the inline outcome body and all content copies, retaining the immutable receipt, byte identity and replay fingerprint (section 16); current reads require `transcripts` |
| saved request prompt/feedback content | 30 days after the run finished, using `transcripts` retention | deletes payload bytes and inline copies, retaining descriptor/digest/availability and compact policy/bindings |
| other saved request content | 30 days after the run finished, using `artifact_payloads` retention | same; a combined request payload uses the shorter transcript/artifact period |
| reference-only artifacts (`VcsRef`, other types whose payload is a reference) | forever | nothing |
| command resources of a graph version | while the version is `active` or any run pinned to it can still start an attempt; then the artifact-payload period | deletes the blobs only when no other version references the same digest; the version keeps names and digests |

[The staged storage contract](protocols.md#7-artifact-storage-fr-44), selected under [#229](https://github.com/realkarych/kora/issues/229), assigns private bytes and authoritative mutation outcomes to the provider. Core persists their intent, address admission, reservations and acceptance. Generic chunked integration follows the [bounded progress/recovery contract](api-and-agent-surface.md#bounded-chunked-uploads-issue-224). The actual upload-staging, worker accounting and deletion-intent schema and API/retention consumers remain pending implementation; the generic database foundation does not supply them.

A separate low-priority task, not a scheduler pass, selects eligible owners in batches and marks them `expiring`. Shared-address deletion uses a durable fence keyed by physical storage identity and full `payload_digest`, covering provider aliases and namespaces that deduplicate to the same address. Physical identity comes from trusted storage configuration and resolution, never a caller's alias. Reserving a deletion generation and checking all owners occur in the same serialized boundary used to admit owners. Check artifact versions, session segments, graph-version resources, request/derived payload descriptors, active-execution/recovery holds and `staged` upload rows. If another unexpired owner or hold exists, expire only the eligible references, without deleting shared bytes.

While a deletion generation is unresolved, no new staging owner, graph resource, descriptor or hold may become eligible for that address, and no promotion or acceptance may rely on it. Contention returns a bounded retryable refusal or waits only within the operation's existing finite deadline. No namespace-local scan can authorize deletion of an address shared with another namespace. Expired owners never regain eligibility merely because the bytes later reappear.

Commit the fence and exact `DeleteRequest` intent before storage I/O and release every database transaction, connection and scope/run lock. Invoke `delete_content` only for that operation/generation. Complete the generation in a separate short transaction only after every issued deletion effect has settled or is authoritatively fenced against executing later. A database generation alone cannot fence a delayed unconditional storage delete. Failure, cancellation, process restart, elapsed time or an `exists` result cannot by themselves establish closure; bounded recovery retains the durable fence until closure is proved. Never transfer deletion authority on timeout alone or reopen admission because the object is currently absent. The typed request records authority; it does not relax the requirement that every older delete be unable to execute before admission reopens.

After completed deletion, a later upload must promote again from validated staging bytes before acceptance; an earlier existence check or put receipt is insufficient. Then expired owners keep their metadata and content-free `retention.expired` events, while staging rows/reservations follow the API cleanup rules. `expiring` rows and unresolved deletion generations are resumed after restart without reopening eligibility. `kora db verify-storage` cross-checks rows and blobs but does not clear a fence merely from absence. Approval requests keep `run_cost` and bound digests. #216 owns the concrete schema, recovery implementation and both-database race/lifecycle evidence.

Persist each stage mutation intent in a short transaction before provider dispatch, then save its exact result in another short transaction. An uncertain result retains its operation identity and reservation; do not dispatch a replacement operation to hide uncertainty. Source/retained addresses use the same owner-admission boundary. Derive and reserve any prepared candidate privately before admitting its actual full digest for promotion. The implementation plan fixes a consistent lock order across run/upload/worker/address records, including both source and retained addresses, and proves both-database contention behavior.

One durable finalizer admission per stage spans rereading, validation, preparation, promotion and result persistence across API instances, without a database resource spanning that work. Contenders cannot open another reader or parse. Its deadline, cancellation or process restart never permits takeover while an earlier finalizer may still act. Ready execution-request uploads retain their row, original grant, reservation and expiry until successful sealing creates the descriptor atomically; failed or expired unsealed uploads remain cleanup-owned.

The [generic chunked upload contract](api-and-agent-surface.md#bounded-chunked-uploads-issue-224) derives at most 16 public-part receipts from the 256 MiB source cap and fixed 16 MiB non-final width. One upload row stores common immutable attempt/grant/source/contract fields once, the contiguous `next_index`/`bytes_received`, and each accepted part's index, size, digest, final flag and original prefix acknowledgment. Provider references retain their own finite DTO and fixed semantic-slot bounds; transcript prefix/prepared-candidate records do not claim an unreceived full part. The implementation chooses a compact representation, not one permanent row or receipt per request. Persist the winning part and progress before acknowledgment; concurrent replicas, exact replay, conflicts and response loss cannot overwrite or append another winner. Request-local replay/conflict/order/layout refusals preserve the valid owner and committed prefix; only their own uncommitted resources settle, without releasing unknown effects. Whole-owner authority loss, expiry, cancellation or whole-upload validation failure retains the existing retirement path. `stored_at` and `expires_at` are fixed at initial admission, never renewed by later parts, replay, failures, recovery or restart.

Recovery creates no receipt or renewed reservation. A live staged/ready lookup must match its original grant-bound owner. A current-authorized terminal lookup returns the retained owner's current descriptor before new-result eligibility checks; expired or superseded owners remain so. Missing/expired unsealed staging is unavailable, and any permitted restart needs a fresh upload reference. Receipt compaction removes old part-replay capability without removing durable owner-level completion identity. No lookup opens a retired stage, restores an old grant or treats receipt absence as effect closure. Both-database progress/conflict/expiry/recovery/lifetime cases are owned by work items 11/12/17 and #216, with actual owner queries, writer waits and unrelated-work progress measured under the existing lifecycle minima.

Every identity-changing accepted preparation stores one compact immutable completion binding with the durable payload owner: original upload reference and complete source declaration to the retained descriptor. Keep that binding after private-stage cleanup and payload expiry. It supports current-authorized read-only terminal recovery without revalidation, publication, retention renewal or authority restoration; the current descriptor reports availability. Canonicalized and truncated identities remain separate from selected-field approval digests. This is bounded metadata per accepted owner, not a permanent part/request ledger.

Stage cleanup first durably closes useful issuance, then confirms `retire_stage` has closed all issued effects and readers. Core persists outcomes and their revision/mutation-set identity before `release_stage`; provider independently proves closure before compaction. The acknowledgment handshake remains charged/durable until its completion is known. Receipt/guard removal cannot permit a delayed begin/write/promotion to recreate data. The existing refused-created-address completion rule below remains an additional condition before releasing the core reservation.

Deletion similarly reserves finite provider deletion capacity before I/O, saves the exact outcome and closed-issuance evidence, then acknowledges through `release_delete`. Only actual effect closure and the durable acknowledgment permit provider receipts and the matching core intent/generation to compact. Stale operations become unavailable, never a new delete of recreated content. No unbounded per-generation history or timeout-based forgetting is allowed; any retained compact guard has explicit ownership and a finite bound. Unresolved state stays charged. Repeated delete/acknowledge/recreate cycles must demonstrate stable settled receipt/intent counts and preserve late-effect safety.

Bounded provider scans enumerate both stages and content with a physical-identity/kind-bound cursor and bounded actual work. Every candidate still requires a current complete ownership lookup; scan results neither authorize deletion nor close unknown effects. Measure lookup/query/scanned-row work with growing history, shared owners and sparse orphan candidates, plus locks, cursors, pool checkouts and unrelated-work progress. #216 owns these integration proofs, separately from provider conformance.

Refused or expired uploads finish their staging ownership under the same physical-storage/full-digest fence after confirmed stage retirement and outcome acknowledgment. If authoritative promotion evidence proves the upload did not create the addressed object, release its row/reservation exactly once. Unknown promotion ownership remains charged. A created-object upload completes only after required physical deletion is confirmed complete with all issued effects settled or authoritatively fenced, or when an independently eligible accepted artifact payload, retained derived payload or graph resource under the eligibility rules above retains the same address and no deletion generation/effect remains unresolved. Check current content eligibility and release the row/reservation atomically against owner expiry/removal and deletion admission. Expired, expiring or missing payload owners, surviving metadata alone, other staging rows, transient holds alone and existence/promotion observations cannot justify that retained-owner alternative. It issues no physical deletion and changes no remaining owner's retention or access; without it, sole-owner cleanup stays charged until deletion completes. Crash cleanup follows the same conditions and never releases twice. The [API refusal and reclaim contract](api-and-agent-surface.md#worker-route-bodies-issue-139) owns the complete sequence and `test_refused_upload_shared_address_releases_staging_reservation`, implemented by #216 with work items 8/12 using the #229 promotion-attribution and cleanup-effect contract.

### 11.1. Graph-version contract

Evaluation never recomputes them. Each effective output contract has its own digest over its resolved type closure and applicable inline schema; `artifact_version.contract_digest` refers to that digest, not merely the type name or a current alias. It also carries declared resolved skill/MCP/resource identities already available to deployment; later observed facts never overwrite it. Canonical `execution_contract_digest` identifies these saved values. `deployment_digest` hashes canonical `{ir, execution_contract}`; `ir_digest` continues to identify just the compiled document. A new resolved contract cannot silently deduplicate to an incompatible graph version. Current namespace type aliases are authoring conveniences, not execution dependencies.

Exact built-ins take the applicable inline checker schema or `dyn`; named descendants and derived lists retain their declared checker schema while inline schemas add validation only. Every applicable schema validates the same direct value. Neither checker view nor constraints can change on replay. This mapping does not reinterpret unrelated contracts. Unsupported or historically missing bindings refuse new effects before allocation/execution without inferring current defaults; historical reads keep saved results. A digest alone is not interpretation authority.

[ADR-0027](../../docs/decisions/0027-bounded-effective-schema-validation.md) additionally requires the exact `schema_validation.policy` and complete `parameters` map in each affected future effective contract, alongside original document/source identities, ordered applicable constraints, exact reference targets and required behavior/checker bindings. Reference closure supplies targets, not extra top-level assertions; equal original bytes do not collapse local document bases. The existing deployment/effective-contract writer owns their canonical saving and inclusion in the effective-contract, execution-contract and deployment identities. Prepared execution views and normalized resource accounting are not a second saved schema digest or database format. The initial `kora.structured-output-schema-policy.v1` identity remains reserved/unavailable pending a concrete owner-approved accounting/parameter/charging specification. Missing or unsupported interpretation refuses new effects without current defaults; saved historical results remain readable. Acceptance-affecting policy/charging/engine changes require a new immutable identity or explicitly supported immutable compatibility binding. Actual writer, replay and retention activation remain with existing consumers and #216.

Deployment resolves merges, installation capabilities and defaults once, preserving validated authored dormant fields. First-slice values explicitly contain `max_wait: "0s"` and `max_attempts: 1`. Both `execution_contract_digest` and `deployment_digest` include this map even when the compiled IR retains omission. Different resolved policies cannot share a deployment identity. Equivalent maps serialize identically, while deployment identity still includes the complete compiled IR and the rest of the execution contract.

### 11.2. Attempt inputs and write-once request

`input_bindings` is written with attempt creation under the run lock. Each declared input records its source (artifact version, immutable run parameter or subgraph binding), declared path/selector, selected list indices or fan-out element and order, relation (`consumed`, `reused_invariant`, `previous_attempt`) and explicit `absent` for an unresolved optional input. Bindings to parameter values reference the immutable run/parameter path; inline derived values belong to retained payloads. Nested bindings terminate at exact source artifact versions or run parameters. Saving these IDs does not claim that their bytes remain available forever. No scheduler action overwrites them, and output lineage uses them rather than the current instance cache.

`execution_request` is null before sealing, otherwise `{version, digest, storage_ref, payload_state, retention_class}`. The body is canonical JSON containing attempt/graph-contract identities, exact bindings, nonsecret resolved config and rendered text, feedback, intended retry strategy and source session/artifact, logical workspace/checkout/publication intent, limits, the engine-selected price revision id and values (section 7.1), selected runtime/harness/provider behavior identities, declared resource references/digests and secret aliases/references. The complete effective execution policy is also bound into the request digest and copied into durable `execution_policy = {namespace_revision, values, semantics}`. Its values contain execution requirements and composed tool policy, never the entire namespace policy with live authorization/quota settings. `resolved_config_digest` hashes the saved nonsecret config portion. No raw credential, resolved secret value or secret-derived hash is included.

Sealing is a one-time conditional write through the existing worker reporting path, under a current execute grant and unchanged result authority. The API checks current namespace policy revision and required execution capabilities before accepting it; a stale revision is `API002` `policy_revision_changed` with the refreshed policy values and revision, and the worker rebuilds the as-yet-unsealed request and reseals; a capability mismatch is `API003` `capability_unsupported`, which the worker reports as `config_error`. A successful seal returns the recorded descriptor and the policy revision it was sealed under ([issue #139](https://github.com/realkarych/kora/issues/139)). After current namespace/service/lease authorization, check an existing sealed record before checking the current policy revision: the same digest returns its recorded descriptor read-only, including after policy change or cancellation; different content is `API002` (`execution_request_conflict`). Only an absent record can be sealed, requiring current execute/result authority and policy/capability checks. A read-only replay grants no effect rights. Durable request bytes, metadata and policy precede any workspace allocation/preparation or execution effect; an upload staged before the transaction is reclaimed through its `upload_staging` row on failure and grants no effect rights. There is no extra attempt state. An attempt that stops earlier keeps its inputs and `execution_request = null` (`not_recorded`).

Runtime-specific allocated paths and exact preparation plans are derived from the saved logical request, then bound in the existing trusted runtime checkpoint before their effects. They do not trigger request re-rendering. The semantic-request digest covers the logical request body only, not dispatcher/epoch or credential injection. Runtime verification checks the body digest and immutable logical fields; it stores and compares derived plan/workspace digests separately so a duplicate cannot replace previously accepted preparation. Unknown actual checkout/fallback/version remains a later observation. The private sealed publication input in ADR-0016 is a different object and retains its own digest and authority rules.

### 11.3. Results, observations and availability

[CommandResult revision 1](artifacts/CommandResult.md) identifies its canonical JSON root independently from its two captured byte streams. Root JSON, command captures, bounded tails, identity summary and CEL projection use artifact-payload retention, not reference-only lifetime. Capture availability belongs to its current owner outside the immutable JSON. A surviving or recreated shared address cannot restore an expired owner. Work item 12 with API 11, worker 17 and #216 must approve the concrete capture owner/completion representation and its write-once, full-replay and shared-deletion mapping before activation; publication defines no new row or column. Recursive List[CommandResult] and scheduler collect/export aggregate materialization, persistence and read delivery remain pending work items 3/9/10/11/12 under generic saved semantics; per-result/upload/CEL bounds do not establish an aggregate bound, and no new numerical aggregate default or campaign is selected.

Artifact upload records the producing contract identity and the validation outcome, actual digest field selection and summary/projection produced under that binding. AgentSession validates its complete logical value, saves its immutable finalization/price snapshot and logical digest once, and derives its fixed metadata view before CEL path cutting. Later ordered usage acceptance can improve the independent ledger without rewriting this artifact, its projections or existing approval cost. Its denial-sample copy expires under the artifact contract; only content-free hashes and the fixed metadata view remain permanently. Existing promoted denial audit rows retain their independent event ownership and lifetime. Validation diagnostics and projection/summary values that contain user content are in `derived_payload` with artifact-payload retention; the CEL projection is cut at the same validation step, or in the producing transition for scheduler-produced versions, into `cel_projection`, with its artifact's retention class (artifact payloads; forever for reference-only types; for `AgentSession`, whose projection holds only session metadata, the lifetime of the row); only content-free outcome, field selection and digests are permanent metadata. The generic identity summary can share the artifact payload reference. Historical reads use these results without calling a changed implementation; expiry affects their availability rather than silently recomputing them. Scheduler-produced artifacts use the same graph contract and write their result bindings when produced.

Existing trusted phase events/checkpoints and attempt provenance fields report actual checkout commit, image, harness, selected fallback and verified resources with observation time/source and request digest. Re-delivering a journal event with the same attempt/sequence is idempotent; conflicting content is rejected. Facts not yet observed are `unknown`; records not captured are `not_recorded`. Neither state proves no execution. No copy of an observed value retroactively becomes a deployment pin or an authorization.

Payload descriptors distinguish `present`, `expiring`, `expired` and `missing`; `not_recorded` and `unknown` describe absent records/observations, not stored bytes. Immutable body content and identity never change, although retention may delete its bytes and update availability. An expired owner never becomes present merely because another upload recreates the same content-addressed blob; availability and access belong to the saved owner, not global hash existence. Inspect/diff expose IDs and availability after expiry; content requires namespace `transcripts` access for prompt/feedback and equivalent derived projections. All namespace checks still apply. A storage check reports physically absent referenced bytes as `missing`, not as a successfully completed retention action.

An admitted StructuredOutput root null is available content: canonical `b'null'`, size 4 and `payload_state = present`. `inline = SQL NULL` may instead mean no decoded cache; it cannot identify an absent candidate, unavailable summary or expired payload. Persist the identity summary with its own `derived_payload` owner and availability, even when it references the same physical canonical bytes. Source and summary retention/access remain owner scoped; expiry never recomputes through today's provider or revives an expired owner. Frozen CEL projections separately require lossless converted numeric kind, binary64 signed zero and NUL strings/keys on both databases; work items 4/8/10 must supply the approved representation and extended projection tests before activation. No existing JSONB round-trip result is implied.

An active attempt explicitly holds request/input bytes it needs, and unresolved recovery holds only checkpoint/request references required to adopt or finish its original stored operation. A terminal run's potential future retry is not a hold. Retention marks/deletes inline values and shared blob content only after all unexpired owners and active holds permit it, with the same crash-safe `expiring` protocol. Manual retry preflight checks the input/feedback sources required by the selected new attempt and returns `API002` (`execution_inputs_unavailable`, with IDs and states) when unavailable; internal execution fails `config_error` before new effects. It does not require irrelevant historical request text merely to retry a fresh node. New attempts may bind new available upstream inputs; old history remains unchanged. A rerun remains a separate run under its existing rules.

## 12. Immutable run target identity (ADR-0019)

### 12.1 Binding, origin and authority

`run.target_key` has one write boundary: valid parameter binding in the creation transaction, or the first successful complete result of the declared top-level output source. A key never changes or clears afterwards. An absent optional parameter is not an invalid/null/empty present parameter: the latter is `API003` before manual run creation, subject also to the parameter schema. A skipped or unsuccessful first source creates no binding. Binding, including the first `run.target_bound` event with exact parameter or artifact/selector evidence, is atomic; equal-key rediscovery creates no second initial-binding event. The compact origin and key are permanent metadata, independent of source payload expiry.

All API and scheduler source mutations take the run lock before authority/state reads. Namespace/service/epoch checks precede replay lookup. A matching saved source output returns its current descriptor read-only before current-result eligibility is tested, never promoting it or restoring authority/retention. A new result requires the current physical attempt and desired state, a permitted lifecycle state, or the exact current scheduler-owned production. A terminal production cannot accept new current/staged output merely because an old pointer remains set. Valid-epoch late results without authority are historical, cannot bind and cannot fail the replacement source; stale epochs retain `API008`.

### 12.2 Staged source artifacts and replay

Only the node named by `graph.target.key.from` stages its whole output set, including implicit `AgentSession`/`CommandResult`. All automatic input/template/branch/collection/approval resolution selects accepted `current` artifacts; no fallback to staged, rejected or expired content. Explicit artifact/node/attempt inspection may show staged history under existing namespace/content permissions. Logs, segments and usage continue through their ordinary paths.

Physical source output identity `(attempt_id, output_name)` is write-once. Persist `payload_digest` over the complete immutable payload (canonical JSON for inline values), separate from the artifact type's selected-field digest, plus the contract identity. A changed replay is `API002` with reason `source_output_conflict`; it cannot overwrite the first payload or change settled success/failure. The descriptor survives the request-idempotency cache and content retention. Matching replay never renews retention or resurrects an expired owner. Partial multipart bytes may leave an orphan blob but no artifact row/binding; receive/hash/store bytes outside locks, then recheck current authority inside the metadata transaction.

StructuredOutput source replay compares the complete authoritative canonical bytes and exact saved effective contract under section 3's all-size exception, independently of any decoded inline cache or selected approval role. Revision 1 selects the full root for approval too, but that does not merge identity/owner roles or grant acceptance authority. Scheduler-produced event/observation/approval outputs freeze their admitted typed value from the retained source once; preceding source normalization retains its existing semantics ([IR section 7.5](ir.md#75-projections-and-typed-conversion)).

Staged content follows the run's existing retention, active/recovery holds and transcript access; it is not an indefinite hold. Full payload identity, result disposition and binding origin remain compact metadata after expiry. Live segments are separate from the final write-once session artifact.

### 12.3 Complete source acceptance

One transaction under the run lock checks current authority and, for a physical attempt, normal successful completion with ADR-0017 execution/dispatcher/publication closure. It requires every declared output to be present, validated and owned by that same current production. It extracts exactly one string at the declared path and validates the key grammar, with exact case-sensitive equality and no normalization. It then binds an unbound run or compares its existing key, promotes the entire output set and completes the source together. A crash commits all of these or none. The first source upload does not bind on its own.

Failed execution cannot partially succeed or bind and retains its original failure class. Missing/malformed key data or missing/invalid companions use ordinary `artifact_invalid` handling. A complete valid proposal differing from the bound key fails the source with `config_error`, internal code/reason `target_identity_conflict`, `retryable: false`, bound/proposed keys, source node/output/path, artifact-version ID, physical attempt ID when present and recovery hint. The conflicting artifact becomes invalid and valid staged companions become superseded. The comparison is at final acceptance, not an upload-time stop state. Source retry policy cannot hide the conflict, including a source wrapper's retry or `skip_failures`; no new attempt state or early termination assumption is introduced. The asynchronous failure is not a synchronous retry-request refusal.

Scheduler-only sources use the same all-or-nothing decision without an attempt row. A wrapper/collector owns distinct logical exported artifact-version rows with lineage to exact child versions; immutable bytes may be shared. Rejection never changes the underlying child's disposition. Recheck the owning current wait/request, subgraph iteration, consumed bindings and child versions before accepting results prepared outside the transaction. The source resolves to one top-level graph node; its internal body can already have produced its own ordinary results. The acceptance barrier covers exported results, not retroactive body execution.

### 12.4 Holds, history and recovery

Binding does not acquire a hold or need a shared target lock. Admission still acquires under ordered limit locks; release still requires ordinary run release plus ADR-0017 closure. PostgreSQL count/state reads occur after the relevant locks using READ COMMITTED or explicitly retried serializable transactions; SQLite keeps its single writer. Never acquire another run's lock under a target lock. Do not use a global unique-holder index because incoming `allow` runs can coexist.

Clear/cancel preserves key/origin and all immutable attempt history. Settled failed-run retry reacquires that same key behind an intervening holder; unresolved holds remain retained. First binding associates prior unbound run history once; later rejected proposals, independent old evidence and late costs remain attributed to the original run/key. An expired payload never causes reconstruction or retargeting.

Explicit retry may return the original key; it does not change params or generically force discovery. A linked rerun is an independent run with its own first binding, no old artifact inputs or transferred hold, subject to every existing replacement blocker. It does not inherit the rejected proposed key or guarantee selection: the graph must expose and deterministically enforce a selector if required. Pre-binding parallel work, internal body work and already produced external effects are not rolled back. Scheduler-only approvals need not acquire a runtime hold; capacity and eligible-ordering policy is defined separately in section 13 (ADR-0020). Failure-compatible control handlers may run without consuming rejected source data.

## 13. Run acceptance and execution capacity (ADR-0020)

[ADR-0020](../../docs/decisions/0020-execution-capacity-and-bounded-run-acceptance.md) separates lifecycle, outstanding work, physical execution and target holds. These are derived from existing rows, not a new admitted-run state or reservation table.

### 13.1 Exact occupancy predicates

`has_physical_attempt(run)` means any of its attempts has status in `created`, `claimed`, `submitted`, `running`, `finishing`, including historical/superseded attempts and attempts of a cancelled or failed run. Do not filter by current-attempt pointers, leases, instance status, wait reasons or target binding. ADR-0017 requires execution and every dispatcher/publication closure before terminalization; unknown execution still counts.

- **Execution-run usage:** distinct run IDs satisfying `has_physical_attempt`, across all versions of the graph. The first attempt insert adds one; terminalizing the last subtracts one. Another attempt in an already counted run adds zero to this count, while adding ordinary physical attempt/node/runtime reservations. Fan-out max_parallel counts logical body instances separately, as below. Repeated terminal reports subtract nothing twice.
- **Namespace outstanding usage:** each run satisfying `status in {pending, running} OR has_physical_attempt(run) OR target_held_since is not null`, counted once. `max_pending_runs` applies to this predicate, not to the literal pending status. Its default is 1000; null, unlimited, zero and negative values are invalid namespace policy.
- **Target ownership:** the existing `target_held_since` predicate, independent of both counts. Binding acquires nothing; runtime admission acquires the hold; ordinary run release plus recovery closure clears it. Incoming allow permits several holders. An unheld defer candidate checks every other holder of the same namespace/key, not a globally unique row.

A run that finishes (section 4) releases at its outcome transition only what the predicates above no longer hold. With no physical attempt and no unresolved hold left, that is everything: the outstanding count and the target hold drop with the `running` status, as the table shows for a settled run. An unresolved physical attempt or hold keeps its contribution until recovery closure, and execution-run usage ends when the last physical attempt terminalizes. The completion transition of scheduler pass 8 releases an attempt's contributions exactly once: its execution-run usage, and the outstanding count and target hold of an already finished run ([issue #139](https://github.com/realkarych/kora/issues/139)).

| run situation | outstanding contribution | execution-run contribution | physical attempt/node/runtime reservations | acquired target hold |
|---|---|---|---|---|
| accepted pending, including overlap queue | 1 | 0 | none | none before first eligible keyed admission |
| ready or admission/target/budget wait with no physical attempt | 1 | 0 | none | retain if already acquired; waiting invents none |
| approval, sensor, timer or retry-backoff wait with no physical attempt | 1 | 0 | none | retain through review/soak |
| non-terminal physical attempt, including another branch alongside a wait | 1 | 1 per run | one per attempt in each applicable physical scope | ordinary acquisition/retention |
| failed/succeeded/cancelled lifecycle retaining unresolved attempts or a hold | 1 | 1 iff a physical attempt remains | retained until closure | retained until ordinary release plus closure |
| settled failed/succeeded/cancelled | 0 | 0 | none | released; immutable key remains |
| manual retry of settled failed | acquire 1 before clear effects | 0 until first attempt | ordinary admission | reacquire same key behind current holders |
| retry while already outstanding | existing 1 | determined by all old/new attempts | old reservations remain; no replacement through recovery barrier | unresolved hold remains |

Fan-out max_parallel preserves its existing body-instance unit. A logically started body consumes one unit until it ends and every non-terminal historical descendant attempt settles; no-attempt approval/timer/backoff waits retain that body unit. Parallel runtime nodes within the same body consume their individual physical reservations but no additional body unit. Body activation, including scheduler-only bodies, and release are atomic under the applicable ordered scopes; no new admitted-run state is needed. This logical cap is separate from runtime execution-run occupancy.

A wrapper's `running` label is not physical work: its non-terminal body attempts determine the count. Discovery before target binding consumes normal execution capacity. Completing one branch or entering a wait cannot release a run slot while any other physical attempt remains. Scheduler-only paths retain ADR-0019's no-universal-hold limitation. Approval success opens readiness, not an execution reservation.

### 13.2 Canonical start and durable replay

All start sources call the shared start-run transition. Existing `inbound_event` rows also carry compact durable start receipts, keyed by the graph's start-receipt name and run idempotency key under their existing namespace/name/key uniqueness. Receipt names are internal and separate from signal routing; wake matching excludes rows with `start_outcome`. A receipt contains the original canonical request digest and either the accepted run ID or a no-run overlap-skip outcome. Hash the caller's semantic request, including its version selector rather than today's resolved version; authentication material is not semantic input. These content-free identity/outcome descriptors outlive the 24-hour response cache and payload expiry, without renewing payload retention.

Authenticate and validate the envelope first. An existing accepted receipt with matching request digest returns its saved outcome before current graph-version/schema/target validation or quota checks; mismatch follows existing `API004` rules. For a new start, select and validate the graph version and params, then under the shared locks recheck receipt uniqueness, the selected version/validation, overlap and outstanding capacity. Commit the pinned pending run, resolved overlap, receipt and event together, or only the deduplicated skip receipt/event. A trigger-directed webhook is acknowledged only after this commit; there is no acknowledged unconverted trigger event to accumulate outside quota. Concurrent duplicate starts create one outcome. Wait-directed events retain ordinary matching semantics.

`allow` accepts subject to outstanding capacity. `skip` records no run when any accepted pending/running run of that graph exists. `queue` accepts a bounded pending run; promotion under the graph scope lock chooses the oldest pending run by ID when none is running. All pending-to-running promotions use that lock. Every tick revisits oldest-pending candidates independently of `needs_scheduling`, so a previously blocked queue progresses after another run ends without mutating the queued row to wake it. Explicit allow and existing same-run manual retry keep their semantics. Each accepted run saves the resolved overlap in `trigger`; later graph deployment does not reinterpret its queue role.

A new start at full outstanding quota returns HTTP 409 / `API002`, `retryable: true`, `details.reason: run_backlog_full`, scope, configured limit and used count. Persist no run, unprocessed trigger event or accepted receipt; the key remains retryable when room returns. Do not cache this transient refusal as an accepted or permanently replayed outcome. Accepted duplicates and skips consume no additional quota even when it is full or lowered. Settled-failed manual retry performs the same positive-contribution check before any clear effects; already outstanding retry adds no credit. Saturation never disables read, cancel or recovery.

For cron, start-sensor and graph-triggered occurrences, saturation records `trigger.rejected` once per occurrence, advances `last_fired_key`/the relevant occurrence cursor and creates no hidden retry queue. No catch-up is added. Skip records `trigger.skipped`. These namespace events have null run/node/attempt references and contain graph/binding/occurrence identity, reason and quota snapshot, never submitted input content. Existing trigger reads derive the last occurrence outcome/reason/time from them; rejected-start metrics expose the aggregate. Client-driven refused webhook/manual starts may be retried; rejected internal occurrences are explicitly consumed.

### 13.3 Live policy, locking and visible state

Graph concurrency counts aggregate every version of `graph_id`. The highest-numbered active graph version supplies live `runtime.concurrency`; if none is active, the highest-numbered deployed version remains the source. An absent graph cap adds no graph restriction. Expose the cap-source version and effective counts/limits; these operational limits override pinned IR concurrency values for admission only, without reinterpreting pinned execution inputs, target declarations or topology. Deploy/retire and admission serialize on the same graph scope. Namespace policy updates and every occupancy-changing insert, terminal transition and hold release use compatible ordered scope locks. Reads use fresh PostgreSQL snapshots after the locks, or explicit serializable retries; SQLite uses its existing writer discipline.

A lower limit below current usage cancels nothing; positive additions wait/refuse until space exists. An existing execution-reserving run may add another branch without an additional run slot, still obeying every attempt limit. Unknown/historical work retains all physical capacity. Do not acquire another run lock under shared target locks. Candidate ordering and reason priority are specified in scheduler section 6; no head-of-line stop at a blocked target, strict multi-scheduler FIFO, starvation guarantee or weighted fairness is implied.

Public state distinguishes `outstanding` and `execution_reserved` from lifecycle status and acquired target hold. Scope/limit/used, cap source, observation/recheck times, target holder IDs and recovery attempt IDs come from the authoritative rows. A full shared outstanding quota can still refuse a new independent target; only the target wait itself is guaranteed not to consume an execution slot or stop the eligible scan. Counters bound outstanding runs, not history, total approval rows or artifact bytes.

## 14. External observation and delivery ownership (ADR-0021)

[ADR-0021](../../docs/decisions/0021-external-observations-outside-transactions.md) separates short database claims/applications from bounded external calls. The following are plain typed JSON records on existing owners, not a general job table. Snapshot payload descriptors follow section 10 retention and section 11 saved-contract rules; events retain compact identity/outcome only. No secret values or executable objects are stored.

### 14.1 Observation record and current authority

`wait.observation` and sensor `trigger_binding.observation` contain:

| field | meaning |
|---|---|
| `due` | per-purpose next observation times, independent of `wait.wake_at`; purposes are `sensor`, `approval_poll`, `pending_head`, `approved_head`, `start_sensor` as applicable |
| `current` | nullable `{token, purpose, claimed_at, deadline, snapshot}`; token is fresh and never reused; snapshot binds exact owner/inputs/contract/resource revisions and contains references to retained payloads |
| `last_success_at`, `last_error`, `failure_count`, `next_retry_at` | bounded, redacted integration diagnostics/backoff; no unavailable result is represented as negative evidence |

A CEL `match` or `until` evaluation error is not an integration failure. It is stored in the owner's `evaluation_error` (the error record of ir.md section 7.7: kind, field, nullable offset, event identifier or observation time, recording time). An `until` error is written only from the current claim; a `match` error, which has no claim, is written in the pass-6 transaction that verified the exact open wait under the run lock. Neither changes the integration fields above ([ir.md section 7.7](ir.md#77-evaluation-errors)).

One wait has one current read slot, shared by approval polling, pending head watching and approved head verification. A new claim atomically replaces expired logical authority. A completed, failed or negative current read consumes its token and schedules the relevant next due purpose. A state-changing current application sets the owning `run.needs_scheduling = true` atomically with its transitions/artifacts so incremental downstream scheduling observes it, including after restart. A duplicate completion cannot consume it again. Obsolete successes and errors are discarded. Physical task credits are separate scheduler bookkeeping and remain occupied until that task settles, even when its token expires or is revoked.

All wait-affecting apply/clear/cancel/expiry/replacement decisions use the existing run lock and verify the exact open wait of the node's current activation. Closing/replacing a wait revokes its token in that transaction. The original VCS-bound approval wait remains open after `pending -> approved`; only a fresh `approved_head` claim issued after that transition can finish it. An approval without a VCS binding completes through saved-contract/current-wait validation without a head read. Success satisfies the wait; failure cancels it or expiry applies its existing policy. Historical approved requests left after clear cannot authorize another wait, including one with identical inputs.

| read purpose | snapshot identity and apply conditions |
|---|---|
| `sensor` | namespace/run/graph-version/contract; node id and subgraph iteration; exact open wait, subscription/poll config and consumed artifact versions; sensor implementation and configured dependency-resource revisions; token, current activation, relevant policy/authority and remaining lifetime |
| `approval_poll` | exact current wait and pending request; channel binding and primary external id; context artifact version, bound SHA/digests and saved form/approval contract; current approver rules; shared approval-response transition |
| `pending_head` | exact pending request/current wait, trusted repository/ref/resource identity and immutable bound SHA; token and relevant current bindings |
| `approved_head` | exact approved request that still owns the open wait and pinned content; newly issued post-approval purpose/token; equal observed head required for gate success |
| `start_sensor` | binding id/revision, enabled state, occurrence cursor, poll config/resource revisions, selected graph version/contract; same token/cursor; canonical start outcome and cursor commit together |

Relevant configuration/authorization changes revoke or reject old authority and schedule fresh work. Use exact relevant revisions, not whole-run `updated_at` or unrelated policy edits. Dispatch checks current HTTP/secret access; application checks current transition/approval authorization. These point-in-time checks do not promise retroactive revocation of a remote request. No mutable branch/input/type alias is resolved again to reinterpret a saved result. Scheduler target sources still accept their whole output set and target key atomically under section 12.

An approval response and a relevant authenticated push fence older reads under the existing run lock, including a new equal-head push that changes no logical state. Deduplicated replay adds no second fence/event/notification. Ingress processing durably fixes locally selected wait/request recipients before asynchronous handling; it never rematches a queued push to replacement waits. Generic unordered ref pushes use ADR-0021's conservative policy: a remotely old event first delivered during a newer request may fail that locally selected pending request. Neither a delivery id nor arbitrary timestamps prove remote order. Valid provider request binding/ordered cursors may narrow recipients. Equal-head pushes never complete a gate, and local tokens cannot fence later remote movement.

### 14.2 Start binding ownership and discovery

A binding edit, pause/resume or applicable deployment change advances `binding_revision` or replaces the binding with a new id. Applying a start observation preallocates the prospective run id and takes its run lock, then global/namespace/graph scopes, then the binding row/CAS. Recheck enabled state, revision, token and occurrence cursor after these locks. Canonical start acceptance commits accepted/skip/saturation-rejection outcome and cursor atomically (section 13), consuming observation authority once. Stale results create no run and advance no cursor. Binding mutation/deployment follows compatible scope-before-binding order. A claim-only binding transaction takes no later scope/run locks.

Index direct due/expired-claim queries on observation purpose/time and delivery due time; do not depend on `needs_scheduling`. Empty memory state after restart loses no due owner. Claims are repeatable reads rather than runtime leases or execution-recovery barriers. HA must explicitly budget aggregate dispatcher resources; the MVP installation has one scheduler.

### 14.3 Approval delivery intent and uncertain effects

`approval_request.delivery` records `desired_state` (`open` or `closed`), `revision`, the original configured resource identity/revision and marker (`approval_request.id`), learned external ids, durable dispatch authorizations/outcomes, reconciliation cursor, next due time, last error and closure evidence when available. A new delivery authorization binds operation, original approval id, desired revision and resource before external work. A token/revision prevents stale local acknowledgements from claiming the new intent complete; every learned external id is retained even from an obsolete authorization. Lookup results are accumulated as bounded pages, never assumed to contain every duplicate in one response.

Only a current pending request desires `open`. Every nonpending or superseded owner desires `closed`, including approved requests awaiting head verification and approved requests whose gate later fails. Approved/rejected/failed requests use `notify(resolved)` and transport `cancel`; invalidated/expired/cancelled use their existing notification and transport closure. `cancel` closes channel interaction without rewriting audit decisions. Request audit state, current gate state and channel delivery state are distinct projections. A native code host may still accept reviews; kora ignores responses to closed/nonpending owners.

Closure intent commits with the local transition and prevents new create authorizations/retries. A preterminal authorized call is potentially in flight even before it sends: it can pause after claim, send after cancellation, then finish. Suppress unsent work when terminal intent is observed, but do not claim an atomic remote fence. A late create result saves its id on the old request and schedules closure; it cannot restore state authority. No fresh terminal create is authorized to discover an id.

Recover uncertain creates through read-only marker lookup on the original resource, enumerating all matching ids and closing each. Search-before-create is not atomic exactly-once publication. Retry transport with the same logical intent; notification order or duplication never grants approval authority. Lookup absence alone does not close an uncertain authorization. Continue finite calls/backoff and keep uncertainty visible unless affirmative provider closure establishes no outstanding create can act; MVP has no abandonment action. This holds no attempt reservation/target hold and creates no ADR-0017 recovery barrier.

After open/create is forbidden, release its form/context/ReviewBundle delivery payload hold. Retain only content-free marker/resource/credential references, learned ids and compact progress/error/evidence; unresolved metadata can outlive payload retention indefinitely. Current authorization applies to the original resource; an alias edit cannot retarget cleanup. A currently forbidden resource stays visibly blocked without external calls. This is not a promise to stop remote work or retain full payloads forever.

## 15. Inherited execution deadlines (ADR-0022)

[ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) is authoritative. Execution deadlines use scope/attempt fields; the existing `wait.wake_at` remains the one mechanism for timer, approval, sensor and retry/admission waits. No deadline task table or per-wait worker is added.

### 15.1. Write-once scope clocks and binding

| Owner | Clock and deadline | Lifetime |
|---|---|---|
| `run` | `started_at` on promotion; add pinned run timeout when configured | Accepted backlog excluded; never reset by same-run retry/clear |
| Subgraph `node_instance` | Set `started_at` on first `ready` activation before first body materialization; add pinned wrapper timeout | All own iterations, backoff and waits share it; concrete nested/fan-out identities distinguish newly materialized wrappers |
| `attempt` | Set `started_at` in first executing-claim transaction before any effects; add pinned node timeout | Prior unclaimed queue excluded; parent clocks continue. Recovery/adoption never reset it; a new physical attempt starts independently |

In that first claim transaction, under the existing run lock, compare all active parent deadlines/expiry latches before returning execute authority. If eligible, record a logically null deadline when no configured scope contributes a limit; otherwise record `{at, scope_kind, scope_id, clock_uncertainty_seconds, grace_seconds: 30}`. `at` is the earliest UTC sum. `scope_kind` is `run`, `subgraph` or `attempt`; `scope_id` identifies that concrete owner. Equal deadlines choose run first, then outermost wrapper, then attempt. For versioned records, section 16 distinguishes an unrecorded binding from an explicitly unlimited one. An unclaimed attempt has no start/binding; an older non-null start with a null scalar does not establish unlimited execution.

The deadline and timing assumption are immutable execution semantics, included in the ADR-0018 saved request. Recovery checks the original binding, not current aliases/configuration or a new lease start. The authenticated protocol context and existing runtime registry/checkpoint carry it before `workspace_target`/preparation; `Workload` repeats it rather than defining a later clock. No recovery path can weaken the saved clock assumption or issue a new grace. Each provider also supplies finite local operation/transfer/decoding bounds even when there is no overall deadline.

### 15.2. Sticky expiry and current-result authority

`deadline_expired_at` is a write-once observation latch, not another calculated deadline. It exists on the run, subgraph wrapper and physical attempt as applicable; unrelated node kinds leave it null. Record observed expiry in the existing shared timeout/cancel transition under the run lock and in the runtime's durable closed execution gate. Once observed, expiry never clears on retry/clear, adoption or a backward clock correction. A new physical attempt has its own latch, while existing persistent-scope latches remain. Runtime observations can be relayed under a fresh recovery lease; stale epochs retain no write exception.

At every new execute/publication authorization and every current-result promotion/success transition, compare `now < deadline.at` and all relevant unexpired scope latches in the same transaction as the existing authority checks. Scheduler-only wrapper/collection/wait completion checks the applicable run/wrapper scope deadlines even without a physical attempt. Equality is expired. On an expiry decision, commit existing timeout/cancel intent and set `run.needs_scheduling = true` atomically; do not wait for the next timeout pass. Late outputs can be retained only historically; they cannot satisfy gates or unblock downstream. Already accepted success is not retroactively undone. Authenticated exact read-only replay of a saved request/completed operation still returns its saved descriptor without effect rights.

Manual retry checks persistent run/ancestor deadlines, and a retried subgraph wrapper's own deadline, before quota acquisition or clear effects. Return `API002`, `retryable: false`, `details.reason: deadline_expired`, scope kind/id, deadline and rerun guidance. Do not use the previous physical attempt's deadline to reject an otherwise eligible new attempt. Expiry of a persistent scope cancels descendants and cannot be escaped through child retry policy. A newly materialized nested wrapper may start its own clock, but its enclosing wrapper/run cutoff remains. The existing rerun replacement barrier still applies.

### 15.3. Recovery and future acceptance contracts

The nominal force threshold is always `deadline.at + 30s`, never observation time plus grace. Earlier manual cancellation may shorten it. Elapsed time, a closed logical gate, runtime phase exit or an interrupted HTTP call provides no affirmative termination/publication/dispatcher evidence. Preserve every ADR-0017/ADR-0020 reservation and acquired hold until closure. After expiry, bounded historical collection and read-only reconciliation/retirement/closure may continue, but no new checkout, candidate, commit, push, change request or current result. Incomplete publication checkpoints do not create authority; remotely absent means absent evidence, not permission to push again.

These are future release checks for #57, not runtime tests executed by documentation CI. Use injected clocks/randomness, explicit phase/process barriers and configured conforming protocol fakes; no mocks, patched transports or synchronization sleeps. Every metadata case runs through the same PostgreSQL/SQLite parametrized fixture. Local process evidence runs on Linux/macOS, Docker evidence on Linux; neither fake-protocol success nor local trusted process cleanup proves protected domain containment.

## 16. Original outcome and full deadline persistence (#545)

The physical formats below implement the immutable history/content boundary of ADR-0018 and the timing contract of ADR-0022. Their durable design is accepted under [#545](https://github.com/realkarych/kora/issues/545#issuecomment-6550566787). Storage/codecs activate separately under [#575](https://github.com/realkarych/kora/issues/575) and [#576](https://github.com/realkarych/kora/issues/576); this specification does not establish their implementation or authorize a report/claim writer.

### 16.1. Original outcome receipt and content

`attempt.outcome` is a nullable version-1 compact immutable receipt. Its closed fields are `version: 1`, original `outcome`, `error_class`, `error_code`, `lost_reason`, `reporting_dispatcher_id`, `reporting_lease_epoch`, `replay_digest`, `response: {status, desired_state}` and `error_payload`. The original outcome/class/lost-reason shapes are the terminal-report shapes, independently of completion-applied `attempt.status`, `attempt.error_class` and `attempt.error`. The response is the original accepted `{status: finishing, desired_state}`; replay returns it without deriving today's state. A safe error code is present exactly for `failed`.

For a failed report, `error_payload` is `{format: attempt-error/1, sha256, size}`. The digest and exact UTF-8 byte size describe the separate `attempt.outcome_payload` TEXT value, a canonical JSON envelope `{format: attempt-error/1, value: AttemptError}`. `AttemptError` includes its original code, message and details, with its existing 16-KiB error limit and details depth. Wrapper overhead cannot reduce that admitted domain. The stored envelope is bounded by `MAX_ERROR_BYTES + 1024` bytes. For other outcomes the descriptor and body are null.

Canonical text uses UTF-8, `ensure_ascii=False`, sorted object keys, compact separators and finite JSON values. Only JSON-required escapes are added, so U+0000 in a string or key becomes a JSON escape rather than an actual SQL-string null character. Non-ASCII Unicode remains UTF-8; no Unicode normalization, lossy numeric conversion or truncation occurs. Invalid Unicode, duplicate JSON members, nonfinite numbers, malformed/unknown versions, incorrect digest/size and contradictory record/body shapes are explicit content-free incompatibilities. The existing `JsonDocument` contract is unchanged.

`attempt.outcome_payload_state` is separate from immutable receipt identity:

| Receipt/content | State | Body |
|---|---|---|
| No original outcome recorded | SQL NULL | SQL NULL |
| Recorded non-failed outcome | `not_applicable` | SQL NULL |
| Recorded error available for its owner | `available` | present |
| Recorded error deletion in progress | `expiring` | present until atomic expiry |
| Recorded error expired | `expired` | SQL NULL |
| Recorded error explicitly missing | `missing` | SQL NULL |

The typed codec validates the closed receipt and all body/descriptor relationships; database cross-column constraints also reject impossible receipt/state/body presence combinations. Unknown recorded values never become unrecorded values. Existing rows and omitted old-writer inserts remain unrecorded, with no default or backfill from status, error, scratch, logs or current configuration.

The message/details body requires the existing namespace `transcripts` capability and follows the shorter of the run's saved transcript and artifact-payload retention periods. The inline body has the same original attempt owner; it creates no independently readable owner. Retention clears the body while retaining the compact receipt, byte identity and replay digest. Copies in completion-applied errors cannot escape the same lifetime/access rule; diagnostics, events and recovery summaries contain no copy. Active and unresolved-recovery holds remain prerequisites of #216. Its deletion machinery and selected reads remain inactive until their actual integrations ship.

The selected `reported_outcome` value is exactly the original four-field core `{outcome, error_class, error, lost_reason}` while its content is available. Expired/missing content returns an explicit availability descriptor, never a reconstructed error from completion-applied fields. This selector does not promise the complete original `TerminalReport` or its `ClosureEvidence` envelope. Aggregate closure may have advanced since acceptance; it cannot recreate the original dispatcher subset/order or earlier publication state.

### 16.2. Exact report replay identity

`replay_digest` is SHA-256 of the canonical UTF-8 closed document `{format: attempt-report-replay/1, namespace_id, attempt_id, grant: GrantBinding, report: TerminalReport}`. It binds the original complete validated reporting grant, original domain and complete terminal report/evidence, including fields not exposed by the selected outcome core. The report includes its original error content; body expiry does not change the fingerprint. The original grant's retained dispatcher/epoch identity is also explicit in the receipt. Full original grant/process-snapshot persistence must exist before the authoritative consumer activates; the codec cannot construct missing provenance from a current worker.

Canonical equality ignores object-key order and equivalent JSON escaping. It preserves array order, integer versus floating representation, signed floating zero and every validated field. Thus `1` differs from `1.0`, and `-0.0` differs from `0.0`. `ProcessIdentity.leads_group` is included in full-record hashing; the existing process-exit identity equality, which excludes that field, and dispatcher-item identity/deduplication remain separate unchanged rules. The fingerprint is comparison-only, not a representation from which original evidence can be recovered.

Validate and detach bounded protocol inputs before canonical serialization/hash preparation outside the run lock. The complete temporary envelope bound derives from the existing VcsRef, dispatcher-envelope, error and fixed grant/wrapper limits. A smaller unrelated JSON-root budget must not reject a valid combined report. Only bounded immutable prepared bytes/metadata survive into the eventual transaction; no provider/network/storage call or secret resolution spans it.

Current authentication, namespace, reporting-grant/epoch, saved-semantics, deadline and evidence-binding checks remain authoritative in their specified order. A matching fingerprint supplies neither authentication nor closure and creates no stale-grant exception. After the required checks, an identical replay returns the saved response read-only; changed grant/report/evidence produces `API002 outcome_conflict`. Original payload expiry alone does not destroy comparison identity. The first authoritative engine transition saves receipt/body/availability, `finishing`, accepted monotonic evidence, scheduling marker and events atomically. Whole-request refusal or rollback accepts none of those effects except expiry effects already expressly required by the governing contract.

### 16.3. Complete deadline envelope and legacy projection

`attempt.deadline_binding` is nullable `JsonDocument` with a closed envelope:

| Stored value | Interpretation |
|---|---|
| SQL NULL | No complete binding was recorded |
| `{version: 1, value: null}` | An executing claim explicitly recorded no overall limit |
| `{version: 1, value: {at, scope_kind, scope_id, clock_uncertainty_us, grace_seconds: 30}}` | Complete immutable inherited deadline |

`at` is canonical UTC text `YYYY-MM-DDTHH:MM:SS.ffffffZ`. `scope_kind` is exactly `run`, `subgraph` or `attempt`; `scope_id` identifies the concrete determining owner under the existing bounded identifier rules. `clock_uncertainty_us` is an exact nonnegative decimal integer string, without a sign or leading zeros except `0`, at most the microsecond value of `timedelta.max`. A decimal string preserves the whole existing timedelta domain without float rounding or an additional 64-bit ceiling. Grace is exactly 30 seconds. No cross-host monotonic timestamp is stored.

The typed engine adapter distinguishes unrecorded, explicitly unlimited and recorded `ExecutionDeadline`. It never maps unrecorded data to `None`/unlimited. Malformed/unknown versions, non-UTC instants, invalid concrete identities, negative/oversized durations, changed grace and inconsistent known scalar projections refuse explicitly and without content. Preparation is detached and round-trips the existing protocol value; no runtime registry, Workload or ProtocolContext format is redefined.

The legacy `attempt.deadline` timestamp stays the N−1 scalar projection. A future first executing-claim transaction under the run lock writes `started_at`, the new envelope and the matching scalar once before request sealing/preparation/effects. Unlimited has a non-null envelope and null scalar; a known bound's `at` equals its scalar. Old rows/writers may have only a scalar or null and remain unrecorded. Migrations preserve every scalar, start and sticky latch, and infer no scope, clock uncertainty, grace or no-limit value from current settings/status. An authoritative consumer cannot grant new useful effects from unrecorded data. Adoption from a verified complete original request/registry requires its own approved compatibility procedure.

Existing clock starts, run/outermost-wrapper/attempt tie precedence, fresh persistent-ancestor checks, exact equality, sticky expiry, fixed `D + 30s` escalation and earlier cancellation are unchanged. The effective attempt binding never substitutes for fresh ancestor eligibility. Codec/storage tests do not establish first-claim atomicity, active deadline discovery, real process stopping or publication closure.

### 16.4. Implementation and verification ownership

Issue #575 owns the bounded outcome codec and inactive nullable receipt/body/state migration after `0004`; #576 owns the three-state deadline codec and the next nullable migration.
