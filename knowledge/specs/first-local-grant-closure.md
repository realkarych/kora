# First local execute-grant closure

This walking-skeleton design covers one original execute grant on `local`, after normal workload settlement. The owner approved the ordering and exact replay boundary under [#197](https://github.com/realkarych/kora/issues/197#issuecomment-7064394905). The retained format, exact intake and report evidence below are proposed under [#1743](https://github.com/realkarych/kora/issues/1743). Activation requires approval of this design and the actual producers in section 6.

[ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md) separates Worker and metadata authority. [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md), [ADR-0018](../../docs/decisions/0018-immutable-attempt-history.md) and [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) govern provenance, dispatcher closure, immutable execution and deadline authority. The ordinary cooperative local threat boundary stays in force. A runner exit does not establish that the Worker closed its gate or that publication settled.

## 1. Original grant intake

Before any local preparation, the first Claim commits the original grant for the scheduler-created attempt, binding its domain, dispatcher, stable worker, incarnation, epoch and registered process. The trusted Worker uses that authenticated `mode=execute` response and requests `GET /attempts/{att}/grants` under the same original lease, starting from the scoped empty prefix. This path accepts exactly one complete version-1 page. Require `count=1`, the saved upper epoch equal to the current grant epoch, the exact empty start and descriptor tip at the end. Compare the page record with the full Claim `current_grant` using the same canonical record bytes that advance the scoped history chain. Check the attempt, original domain and namespace against the trusted context and both snapshots. Additional grants, partial pages, a conflicting original row and legacy missing original process are outside this activation. No replacement Claim is needed for a retry. [Existing history contract](protocols.md#resumable-retained-dispatcher-history-issue-226)

The Worker calls `Runtime.accept_grant_history` before any runtime preparation or submit, using the existing `current_grant` and page arguments. Before a runner exists, the trusted LocalRuntime worker-side composition attests the original caller through its configured local process binding and existing native identity reader. The full retained process record must match the original Claim record exactly, including recorded group leadership. The native liveness recheck uses the existing local process rules. This does not add a verifier for extended platform identity. Once the runner starts, its existing authenticated control channel checks the attached original submitter. A dispatcher identifier or verifier digest does not authenticate the peer.

Install the verified grant and the supplied original deadline, null included, in the original attempt's `unsubmitted` head under the attempt lock. `grant_history_status` can return the scoped empty position under original local caller checks before the first page is committed. Never return empty progress from an unreadable head, a known missing referenced file, or a different or legacy bound attempt. On success and exact retry before release, progress is reconstructed from the checked retained record and returns that snapshot, its exact tip and `complete=true`. History intake and progress for a released attempt are refused with `attempt_retired`. The Worker supplies this exact descriptor in `grant_history_complete` and uses the current matching `grant_history_verified` echo and `permitted_actions` for subsequent API result reporting. Current bearer, lease, original timing and result authority remain independent. All first preparation effects still require the #1453 sealed request and permitted execution. History intake itself allocates no workspace and starts no runner. [Worker routes](api-and-agent-surface.md#worker-route-bodies-issue-139)

The implementing Worker and local runtime need an owner-approved, trusted selection of this singleton profile before accepting any request that can prepare or submit. That selection applies even before a registry head exists. A workload, caller-supplied field, or the presence or absence of a record does not select the profile. The current composition does not establish this selection. Treat its exact authority and exclusion of incompatible writers as activation prerequisites. The existing unbound path remains available only under its trusted legacy selection.

A runtime selected for this profile must refuse `workspace_target` and `submit` before any preparation, new registry state or launch effect unless it verifies the confirmed original head, first-grant record, complete singleton binding and live original caller. The required head and record must agree with the trusted attempt, namespace, domain, original deadline and process. Submission must also match its dispatcher. Once a submitter is persisted, check that identity before granting any further effect. An absent head or missing, unconfirmed or conflicting binding gives no legacy fallback. The verified grant stays outside the semantic execution-request and logical workload digest. No adopted or later grant can use this singleton intake for effects.

## 2. Retained local format

The proposed closed head has exactly `format: "local/2"`, `execution_domain_id`, `attempt_id`, the existing lifecycle `entry` and one required `first_grant` member. That member has exactly `grant` and `closure`. The grant reference is required and the closure reference is null until the original acknowledgement commits. Each present reference has exactly `size`, a positive integer up to the existing retained allowance, and `digest`, a lower-case hexadecimal SHA-256 value. They bind the complete canonical UTF-8 JSON record. Check the full attempt and domain in the head against the anchored registry key. Reject unknown versions, wrong shapes, missing records and mismatched identities or bytes as unavailable lineage.

| Registry location | Closed record |
| --- | --- |
| `registry/<name>.first-grant.v1.json` | `{format: "local-first-grant/1", snapshot: GrantHistorySnapshot, grant: GrantBinding}` |
| `registry/<name>.first-closure.v1.json` | `{format: "local-first-closure/1", closure: DispatcherClosure}` |

The file paths are derived from the original local registry key. No caller supplies a filename. The closure record contains exactly the existing `DispatcherClosure` with `provenance="registry_acknowledgement"`, `process=null` and the original `DispatcherQuiescence`. The quiescence tuple agrees with the head's attempt and with the retained grant's execution domain, dispatcher, incarnation and epoch. The retained grant supplies the stable worker identity and original process. The closure reference can be set once. Start, registration, completion, cancellation, deadline expiry, retirement and release must preserve the verified grant and the exact already-recorded closure reference, including null. The cancel, expiry and retirement paths do not fill an empty closure slot or establish normal completion. Activation requires demonstrating that every reachable local/2 lifecycle writer preserves this state or refuses before effects. A first closure is possible only on the normally settled running path in section 3.

Keep the existing 64 KiB head limit and the existing 16 KiB allowance for retained encoded binding, closure and index records per grant. Account for both closed records and their retained descriptors within that allowance and confirm the admitted maximum before activation. A call owns at most the original head and this pair of bounded records and no full history. Read each file through the original private directory anchor and existing file checks, validate bounded length and digest before using the record, and verify the exact identities. The qualified local/2 path uses only the existing attempt lock, exact head and the named retained records it references. An exact replay before or after release acquires the existing lock without creating it, reads only those bounded records, and neither runs a shared-directory sweep nor unlinks or writes any file. A missing or unreadable lock or referenced record refuses the operation. Prove this path and its actual resource closure before activation.

Under the original per-attempt lock, persist the canonical immutable file before publishing its reference in the durable head. The proposed qualified writer owns only one fixed private temporary name per destination, derived from the exact head or immutable record name under the attempt lock. No temporary name comes from a request or a directory enumeration. Bound each temporary by its destination limit and reserve the old and replacement representations until closure. Use private anchored creation and clean only a known inactive temporary belonging to that attempt under its lock. Preserve immutable file and directory synchronization and atomic head replacement. An unbounded registry sweep cannot supply the proof for this path. The bounded writer and exact temporary handling require owner approval and qualification.

A lost reply after a confirmed durable commit permits exact read-only replay. A failed synchronization with unknown outcome does not. For a definite failure before head publication the operation remains unacknowledged; a left-over leaf is no proof of commit. For an uncertain commit retain the original scope and frozen bytes and issue no acknowledgement based on a visible file or head alone. The original owner or its approved local reconciler must join the original native operation, compare the exact anchored head, full grant and attempted record against the original intent under the same lock, and establish durability of the same file and head and their directory entries before returning success. If durability needs re-synchronization, that is a separate admitted reconciliation of the original write, outside the read-only replay path. A conflicting record, missing identity, failed proof or unresolved work remains unavailable. No first write or repair may occur as part of a post-release replay.

Read `local/1` under its existing rules. It confers no verified first-grant progress or first-grant closure and cannot be promoted using a guessed process, epoch, past quiescence or request. Compatible runtime and Worker are required before selecting this path. Drain incompatible live writers before activation. Restore, missing lineage and the full multi-grant runtime migration remain governed by their existing owners.

## 3. Close and complete

After the workload settles and the result, usage and publication work required by the existing report sequence has settled, the Worker atomically closes local effect admission for the original grant. The Worker serializes the final fresh lease, desired-state and deadline check with each effect dispatch under that same gate. Closing stops every new effect under the grant and keeps already-admitted work owned until actual completion or affirmative provider fencing. A cancelled waiter, transport disconnect, closed socket or expired lease cannot settle an unresolved native or remote operation. Keep the gate closed on refusal, cancellation, shutdown and reply loss. A new process cannot reopen it through reuse of an identifier.

After settlement the original Worker freezes one `DispatcherQuiescence`, including its original `closed_at` and `evidence_ref`, and reuses it across all attempts to deliver this acknowledgement. While the runner lives, `Runtime.record_dispatcher_quiescence` dispatches through the authenticated attached channel. The proposed local request is `{op: "record_dispatcher_quiescence", request_id, grant, acknowledgement}`, with the existing closed grant and acknowledgement types. The reply is `{request_id, result: "dispatcher_quiescence_recorded", value: {}}` and the Runtime operation returns `None`. Match the same original sender and full grant under the lock before writing. Reuse existing bounded control-frame, admission and native-operation ownership. Qualify the largest complete encoded request against the existing attached frame bound. Check that the normal workload session has settled before this path writes its first acknowledgement. The Worker remains the authority for closure of its independent work.

Before normal workload settlement the live runner returns retryable `workload_busy` for the first write. An observational peer receives `execution_unauthorized` and a failed current-submitter recheck receives `submitter_superseded`. An otherwise admitted changed binding or acknowledgement for the existing slot returns non-retryable `workload_conflict`. Reuse the existing malformed-control and unavailable-registry refusals. A closed journal while running prevents a new acknowledgement under the existing full-disk fence. An equal replay of the committed record does not create or reopen any authority. Once the closure reference is durable, refuse future runtime effects for that grant. This fence is independent of the existing deadline latch and does not change its saved time or refusal. Existing permitted observation, stop and quiescence operations do not become effect operations.

Call `quiescence` after the acknowledgement. For this verified bound path, require the durable acknowledgement before recording `Completed`. The runtime separately checks workload, managed-domain and publisher settlement and persists its own `NormalCompletionQuiescence` through the existing normal-completion path. Status, a journal line without a committed head, and physical process exit do not substitute for either record. The existing `Completed` transition starts ordinary supervisor exit. The broader `local/1` normal-completion and later-grant paths retain their respective contracts.

## 4. Report, release and replay

After earlier dispatcher and publication checks prescribed by the API, the Worker includes the original committed `DispatcherClosure` and separate `NormalCompletionQuiescence` in the real terminal report. The same current service bearer must still authorize the namespace, stable worker, attempt, dispatcher and epoch. The API compares the tuple with its saved grant row, including the row-derived stable worker, before it accepts any evidence. Keep #1454's authorized exact outcome replay and conflicting-report refusal. In this skeleton, `publication=not_applicable` requires a sealed `publish=null` and an output contract without `VcsRef`. Missing storage, output or publication proof remains unresolved. [Terminal report contract](api-and-agent-surface.md#worker-route-bodies-issue-139)

Proposed #1454 release evidence is the authenticated accepted response or exact saved receipt replay for the original terminal report after normal runtime completion. This can include an accepted `failed` report after natural exit when the original result classification and evidence satisfy the existing report rules. The #1454 acceptance transaction must verify and bind the exact already-durable accepted outputs required for the reported outcome, the settled publication facts and the matching original runtime and sole dispatcher closure facts, including any already recorded. Commit the original report and its receipt atomically with any newly accepted closure evidence. The [accepted-output producer](execution-content.md#23-accepted-owners) owns validation and durable acceptance of those outputs. Any other owner-approved release evidence must verify and bind the same facts to the exact committed report and receipt. An HTTP success status, a generic `finishing` observation or a lost response alone does not prove acceptance. The receipt-free cancellation refusal commits no result report and cannot authorize release. Under the existing winning own-attempt timeout rule, an accepted `failed {timeout}` report may also return `desired_state: cancel` and requires the same proof of acceptance for release. Keep bulky state until the required API fact is available and the existing local release checks confirm actual supervisor exit. On a lost report response, attempt exact replay only while the original bearer and grant are still authorized by #1454. Expired or superseded authority, or a report whose acceptance cannot be recovered under the original authority, leaves bulky state pending authorized recovery. The local acknowledgement remains replayable within its local scope and confers no API authority or release permission. Do not add a new HTTP response or service read in this design. If the implementing #1454 contract cannot establish report acceptance with its existing response, choose another approved settlement authority before enabling Worker release. #1472 separately owns the scheduler's terminal transition and reservation release. [Existing report receipt](data-model.md#16-original-outcome-and-full-deadline-persistence-545)

The checked head and immutable records remain outside bulky workspace and runtime cleanup. The original Worker may replay the already committed acknowledgement with the exact saved grant and acknowledged value. After release this exception requires a checked `completed` head with `released_at` and its saved `NormalCompletionQuiescence` for the same attempt and original domain. A released `retired` head returns `attempt_retired` even if it retains the same acknowledgement and normal-completion record. While the runner serves, recheck the attached original peer. Without a live runner, use the original trusted worker-side local composition and recheck the live originating Worker identity, retained grant and stored bytes under the existing attempt lock. Post-release replay opens that lock without creating a missing file, and issues no file or directory synchronization. This scoped exception to the normal released-attempt refusal returns the existing success without writing files, replacing evidence, renewing an API lease or reopening any effect. An absent or different acknowledgement, a different Worker process or a different grant after release is refused. A different Worker may not use this exception to recover, report or start the attempt. Release and retained evidence consumption for retired attempts remain with the existing #197 recovery contract.

## 5. Resource ownership and diagnostics

Use the existing bounded attempt transition and attached runner native executors and lock deadlines. A caller holds admitted frame data only through its actual operation and cleanup. LocalRuntime joins the original native transition on cancellation and retains any unresolved ownership until confirmed. An exact replay owns a bounded read under the normal operation allowance and takes no new durable ownership slot. API history and heartbeat release their database work before response connection I/O. No callback, metadata transaction or filesystem lock encloses an HTTP call or wait for Worker effect settlement. A failed diagnostic output cannot delay native closure or constitute evidence.

The Worker owns gate-close and unresolved-operation outcomes. LocalRuntime owns history intake, original registry closure and replay diagnostics. The API retains its existing single owner for durable `attempt.dispatcher_closed` and final report acceptance. Use fixed outcome and refusal codes with bounded counts and durations. Do not log full grants, process identities, bearer values, values of `evidence_ref`, history digests, runtime payloads or file paths. [Observability ownership](observability.md)

## 6. Activation and verification

The local runtime owner under #197 first supplies singleton intake and durable original normal closure. Work item 17 owns the real Worker gate, original acknowledgement retention, exact authenticated history transfer and report relay. #1453 supplies the immutable sealed request. The accepted-output producer supplies the durable outputs that #1454 consumes for its real terminal transition and proposed release confirmation. #1454 also owns the submitted and running transitions. #1472 owns final scheduler settlement and reservation release, and verifies that final application releases the original reservation only once and only after the required evidence. Admission selection before a head exists, bounded duplicate reads, exact durability reconciliation, and local/2 preservation through cancel, expiry and retirement are prerequisites for activating the trusted singleton profile. Later histories, adoption, process-exit evidence and full recovery remain under their existing owners. No test using only constructed closure DTOs qualifies this integration.
