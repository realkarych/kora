# Durable positions for live run history

This design specifies how a reader can follow the saved timeline of one authorized run and resume after an interruption. It specifies storage, cutover, and delivery checks for [#1988](https://github.com/realkarych/kora/issues/1988). The [finite event page](api-and-agent-surface.md#early-finite-run-timeline-issue-1848) is the active operation. Follow requires its own implementation and qualification. The [single-host demo](live-demo-execution-profile.md) records and opens a known run through the finite console.

The [append-only event and retention contract](data-model.md#2-entities), [shared writer and lock order](scheduler.md#12-execution-backend-boundary-nfr-55), [bounded reads](bounded-read-projections.md#2-continuations-and-observation-semantics) and [API stream contract](api-and-agent-surface.md#follow-stream-authorization-and-failure-framing) govern this design. The HTTP API owns the operation and its current-authority decision under [ADR-0002](../../docs/decisions/0002-ai-first-api-and-thin-clients.md).

## Position and writer

Positions belong to one immutable run within its original namespace. The storage owner maintains a checked positive integer position for each committed run event and a run-local committed high-water mark `H`. In a ready run the committed positions are exactly 1 through `H`. Zero means the run has no positioned events. An indexed protected relation binds each position to exactly one saved event by its original identity. The storage checks enforce the position and event uniqueness and the exact run and namespace binding. A missing, duplicate or conflicting position in a ready run is a fixed integrity failure. The numeric representation must have the same exact ordering and checked range on SQLite and PostgreSQL. Exhaustion refuses publication and rolls back the original effects with a bounded error. Readers seek strictly greater than their last verified position without computing a successor past the maximum.

The writer takes the original run lock before allocation and keeps the existing scope and row lock order. PostgreSQL uses the transaction-scoped run advisory lock. SQLite uses its managed writer and `BEGIN IMMEDIATE`. With those original resources held, the writer appends the event, binds the next position and advances the counter in the same transaction as the original transition. Multiple events take consecutive positions in insertion order within that transaction. A reader observes the event, position and counter only after commit. Rollback leaves the next position available for a later transition, confirmed replay reuses the original result without allocating again, and restart reads the persisted counter. The event ID, saved actor, attachment, timestamp, kind and body keep their original identity, lifetime and access rules.

Any future run-local insertion must demonstrate that its commit participates in the position order before it can coexist with follow. In particular, the deferred `vcs.credential_issued` path has a [lock-free second transaction](scheduler.md#12-execution-backend-boundary-nfr-55). Preserve unconditional audit publication, the current-attempt check and withholding of any unusable credential while qualifying a compatible ordering decision. Adding a run lock to that transaction requires a separate owner decision. [Retention deletion](data-model.md#retention-delete-custody) holds the original address and participating rows and cannot acquire an earlier run lock. If it emits a run-local record, qualify a compatible order before the two features can coexist. Namespace-only audit and graph-only retention records have no run position. Attribution or attachment cannot be invented to assign one.

### Commit order examples

| Scenario | Required observation |
| --- | --- |
| Lower ID commits late | The reader observes position 7 ending in event `event_Z` (abbreviated ID). The writer later commits the lower `event_A` at position 8. A position query after 7 reaches 8. The finite traversal still uses its existing ID ceiling and order. |
| Two contending writers | Writer A allocates 8 and is paused before commit. Writer B cannot allocate under the run lock yet. A committed read sees 7. After A commits, B allocates 9. While B is paused before commit, a read at cutoff 8 sees the event at 8. After B commits, a query after 8 sees 9. A sequence allocated outside this ordering would allow 9 to commit first and a reader after 9 to miss a later commit of 8. |
| Rollback and multiple events | A allocates 8 and 9, then rolls back. Both event inserts and positions disappear and the cutoff remains 7. After the writer settles, a different transaction can commit two events at 8 and 9 in append order. |
| Restart or lost acknowledgment | Reopening observes the durable committed cutoff and exact event keys. Replaying saved transition authority, including the first Claim receipt, does not append a second event. An unsettled outcome requires the original recovery path before any retry. |

The late lower ID occurs in the [finite regression](../../tests/api/test_run_events.py#L762). Allocation/commit separation and run-lock serialization were also compared in isolated PostgreSQL 16.15 transactions during design planning. The future implementation must reproduce the relevant cases with original writers and real snapshots on both databases.

## Legacy prefix and activation

The legacy prefix is the complete inventory of events for the exact run that precede the position handoff. It receives positions from 1 in ascending canonical event ID byte order, identical on SQLite and PostgreSQL. This baseline provides deterministic reconstruction of existing history. Historical commit order is unavailable from retained IDs and timestamps. The first position allocated by the ordered writer follows the full verified prefix; a later commit gets the next position even if its ID sorts inside that prefix. The original `event` rows are preserved.

The [ordinary migration contract](scheduler.md#14-migrations-nfr-72) governs other revision pairs. [ADR-0031](../../docs/decisions/0031-run-event-position-maintenance.md) allows one controlled maintenance window for an existing ordinary installation moving from genuine `run_event_metadata_0034` to the proposed `run_event_position_0035`. The [current Claim gate](../../src/kora/db/first_claim_basis.py#L256) admits exact revisions and native schemas. The [installed SQLite checker](../../src/kora/api/serving.py#L696) requires its binary's own Alembic head and exact finite event-page schema. An additive successor alone cannot keep either old admission check working. The approved window holds ingress and writers across the switch, with no old and new production overlap. Qualified custody requires its separately qualified whole-image transition.

### Maintenance transition

| Phase and owner | Required evidence before advancing |

Install the successor artifact separately and keep production ingress, startup and issuance closed. Quiescent traffic and version inspection give no settlement proof. |
| SQLite authority, deployment owner | Establish closure of the original database and journal/WAL/shared-memory users, including idle handles, workers and any other process with the old authority. Prevent those owners reopening the actual database and its sidecars. Verify the original identity and final transaction dispositions before handing that installation to the protected migration owner. A lock on a path by itself cannot prove external lifetimes have closed. |
| PostgreSQL authority, deployment owner | Confirm the writable primary and intended metadata catalog. Close the original service and pool sessions, prevent reconnection and remove or fence their ability to write. Observe commit or rollback of every original transaction, including the disposition of any prepared work. Admit maintenance through a distinct authorized owner on that same primary. Recheck primary and authority on resume. A migration advisory lock alone does not exclude writers that never take it. |
| Restore point, backup owner | After the last original transaction settles and before any DDL, capture a compatible image of the saved metadata and corresponding artifact state. Verify the image with the exact prior artifact in an isolated environment without production writer or provider authority. Preserve the state and associations needed for finite history, Claim/replay and retained artifacts. A late original commit belongs to the restore image as well as the frozen membership for the successor. |
| Guarded change and preparation, migration owner | The successor verifies the live fence, exact provenance, stamp and native layout before any DDL. Resume the same transition only after rechecking the exact identity, fence and durable checkpoint. ### Fresh provisioning and the release boundary

The first runtime delivery contains the guarded migration, exact native schema and first Claim checks, restartable backfill, startup readiness and atomic positioned writers in one releasable artifact. Before that delivery qualifies, the migration target remains at the current revision. The runtime plan selects the explicit installed maintenance entry point and trusted producer for the required operator proof. Its underlying migration path enforces the same checks at the point where effects can begin.

For an existing installation, bare `kora db upgrade` facing the initial position transition refuses before advancing the revision. Genuine `0032` and `0033` fixture histories reach the genuine predecessor through the supported earlier migrations and their existing checks. Only `run_event_metadata_0034` is the predecessor of this maintenance exception. A private `0034` stamp or a plausible stamp over the wrong native schema cannot enter the transition.

On SQLite and PostgreSQL, bare `kora db upgrade` provisions a genuinely empty intended metadata catalog using the ordinary command. The migration owner establishes emptiness and exact identity before applying any earlier revision. It retains that provenance through the chain to the verified successor. The previous revision encountered inside that proven chain has different provenance from the same stamp on an existing installation. An unstamped native catalog with contents or indeterminate emptiness supplies no provisioning authority. Bare upgrade is a no-op after verified completion at the successor. An incomplete successor follows the checked maintenance resume or restore path for an existing installation.

### Frozen membership, checkpoints and readiness

With the original cohort excluded, use the original metadata writer and its run guard to prepare exact frozen membership. Advance in finite indexed batches across the frozen inventory of runs and in ascending canonical ID byte order within an exact namespace and run. Include original commits that settled before the fence, even when the new ID sorts before an earlier visible ID. Preserve the event ID, attribution, attachments, timestamp and original data. Qualify the native seek order for both databases, including under the configured PostgreSQL collation.

Commit each batch of protected positions and its corresponding checkpoint in the same original transaction and release the native resources between batches. A checkpoint names the guarded transition, frozen run and namespace, last verified canonical ID and verified next position or completion. Resume proves the exact binding and the settled batch outcome before it advances. Inconsistent, missing or foreign progress causes a refusal. Failed or interrupted work cannot publish a partial prefix as ready.

Under the original run guard, indexed exhaustion and the verified high-water mark establish readiness with a fixed number of indexed probes and bounded rows, independent of the size of the history. Incremental durable evidence also accounts for the exact completed frozen run inventory. Startup uses that evidence and the exact native schema to check overall completion with fixed work, without reranking or rescanning histories. After readiness, the original writer appends each event, its position and the counter in the same transaction. Qualification accounts for native releases on both databases. The separately deliverable positioned reader uses the same stored data without another schema change or maintenance window.

## Initial history and continuation

The reader resolves the current credential, namespace and exact run scope before interpreting a history or resume selector. The existing method, schemas, CLI, MCP and browser profile continue under their finite contracts until separately activated.

| Case | Rule and owner |
| --- | --- |
| Start without a resume selector | With one short committed observation of the ready run, the storage reader captures the high-water mark `H`. For `H > 0`, the initial window is the inclusive range from `max(1, H - 19)` through `H`, emitted oldest first within the window. An empty run has `H = 0` and starts with no history. The committed positions in that range are dense and immutable, so indexed reads within the original range maintain membership after the observation transaction closes. A later append cannot join this window. The API reads and checks each protected record for delivery without staging the full window in a queue. |
| A commit after the initial observation | After the initial interval, the API seeks strictly after `H` in ascending position order. A commit during initial delivery remains in that suffix and cannot be skipped because its ID sorts earlier. Without a resume selector, positions older than the chosen window stay outside this view and remain inspectable through existing finite history. |
| Resume after complete delivery | Each normal record supplies a bounded opaque anchor. The follow-only parameter `after` accepts the anchor for the last complete event the consumer accepted. The anchor binds a version, operation, namespace, run, exact position and saved event identity and carries no authority. The HTTP activation specifies its exact encoding and byte bound. After scope checks, the storage reader verifies the original scoped binding by indexed lookup. The API then seeks strictly after that position. This catches up all later positions, including any undelivered portion of the previous initial window, even if the anchor is now outside a fresh latest window. The resume path does not apply a new latest-window trim. |
| Invalid or unauthorized selector | A missing or foreign run and missing current rights keep their existing scope refusals before selector processing. Within the authorized run, malformed, out-of-range and wrong-scope anchors or an event key that does not match its saved position get the same fixed API003 selector refusal. An absent expected position within the authorized committed range indicates storage integrity failure and receives its own content-free refusal. Neither refusal supplies any other run's state. The finite `cursor` remains in its own domain. Requests that combine selectors from the two modes are refused. |
| Interruption | A consumer advances its local anchor only after complete framing, schema validation and successful output or application. It discards a partial tail. A reconnect is a new authorized request with the last retained complete anchor. Without one, including interruption before the first event or while an empty run is idle, a new request makes a fresh initial observation. It has no continuity promise about the earlier unobserved window. |
| Terminal status and EOF | Keep following even after a terminal run status. For example, a later retirement event may still be published. The first activation has no normal server EOF. Explicit client stop cancels locally. The API can end in one valid terminal failure record or abort if it cannot deliver that record. A clean HTTP body end and a truncated tail both indicate an interruption and preserve already accepted records. Any future normal completion rule needs proof of closure across all run-local producers and documented observable framing. |

For example, with `H = 26`, the fresh window starts at 7 and ends at 26. Positions 27 and 28 commit during its delivery. A consumer that accepted 12 and lost the remainder resumes at 13 and reaches 28 in order under fresh authority. A new request without an anchor observes a new latest window. Existing finite pages still use a descending ID keyset and provide separate historical navigation.

## Delivery boundaries and activation owners

- **Storage projection and writer cutover.** The original metadata writer owns atomic publication. The storage reader admits only finite indexed work on the exact scoped run and transfers only the [saved metadata fields](api-and-agent-surface.md#early-finite-run-timeline-issue-1848), with original actor and attachments. Use bounded keyset seeks and the existing finite native deadlines and settlement rules. A coherent counter and position observation distinguishes an exhausted committed suffix from integrity failure when an expected position is missing. The initial observation and each later read release native snapshots, statements and checkouts before network wait, retry or idle pause. Read no event payload or transcript. Qualify growing same-run and unrelated histories, invalid anchors, append contention, crash/replay, cancellation, handoff and true native release on both databases.
- **HTTP and CLI.** The API authenticates before headers, checks current credential and namespace/run scope for each protected record and each idle one-second recheck, and preserves the existing NDJSON bounds and terminal semantics. The listener owns the post-send drain boundary in plaintext and TLS and signals drain start to the application before it waits for active requests. Prove one protected record outstanding with no queued protected successor across the ASGI writer and the lower transport queues. The [planning probe](https://github.com/realkarych/kora/issues/1988#issuecomment-7226397911) observed about 3.9 MB still queued beneath HTTP and TLS after a 4 MiB send returned, even when the upper TLS queue was empty. The request stayed active during serving drain until disconnect. Qualify the real listener with a stalled reader, actual revocation and each disconnect, cancellation, shutdown and deadline path. Verify release of the original socket, tasks, timers, subscription and database work. Bound and document any deployment intermediary buffers under the general stream contract.
- **Shared client, CLI and parity.** The HTTP/CLI change owns exact schema, resource and framing checks, structured terminal failure records, local partial-output behavior and the approved resume selector. It preserves existing finite MCP behavior and the installed finite page selectors, the OpenAPI and generated-client contracts, and verifies reachable parity of the affected operation. A server error record, an incomplete or invalid record and a transport completion without the documented normal signal have their distinct client outcomes. Client cancellation closes the owned reader even during output backpressure. No content, selector or credential enters operational diagnostics. Ownership and safe correlation follow the [observability contract](observability.md).
- **Installed browser.** A separate activation composes the same operation with the current HTTPS session and exact run scope, without passing a Bearer to the browser. Fresh checks and bounded record decoding precede rendering. Retained and rendered rows and bytes remain bounded over the whole session, regardless of stream length. Navigating to another run, signing out, revocation and replacing a request cancel old work and prevent late delivery into current UI state. Prove current rights, reconnection, bounded long-lived presentation, slow-reader bounds, real TLS cancellation and actual packaged Chromium behavior in addition to finite pagination recovery.

Name the implementing issue for each delivery before its code changes. The design verification preserves the finite late-ID and native release tests, installed schema regeneration and parity, and the genuine run-event migration/Claim regression. The future blocking acceptance cases above remain pending with their corresponding owners. CLI and browser activation do not follow from the storage design or migration alone.
