# Canonical execution requests

Proposed format and verification contract under [#1736](https://github.com/realkarych/kora/issues/1736). The owner approved the design scope. The format, outstanding resource and compatibility decisions, and production implementation require their own approval. Runtime activation belongs to the implementing issues.

[Attempt inputs and the write-once request](data-model.md#112-attempt-inputs-and-write-once-request), [execution-content custody](execution-content.md), [Worker authorization and uploads](api-and-agent-surface.md#worker-route-bodies-issue-139) and [inherited deadlines](data-model.md#15-inherited-execution-deadlines-adr-0022) govern the lifecycle. The design below selects the proposed body and handoff for [#1640](https://github.com/realkarych/kora/issues/1640) and [#1453](https://github.com/realkarych/kora/issues/1453). The [walking-skeleton feature rules](first-slice.md#walking-skeleton-and-narrowed-depth) govern what an installation can execute. Accepted coverage, physical custody qualification and activation requirements remain with their owning issues.

## 1. Version-one request

The body is a closed JSON object. All top-level members below are required. Optional members are allowed only where the selected nested type defines them. A property explicitly set to null must have a nullable type. An absent optional property remains absent. An empty map or array is a value. Retain list order, numeric kind and exact decoded strings. An integer identifier, version or count must arrive as an integer token, even if a surrounding API elsewhere accepts an integral real. Runtime effect facts and live grant authority belong to their existing separate records.

| Members | Type and server source |
| --- | --- |
| `version` | Integer `1`. Selects this complete grammar and normalization. Unknown or missing versions cannot create a new ready or sealed request. |
| `attempt_id`, `run_id`, `node_path`, `kind` | The selected physical attempt ID and its run ID, exact Claim node path, and `agent` or `command`. IDs use the existing attempt/run ULID domain. The grant authorized by the API must select this exact attempt. |
| `graph` | Exactly `version_id`, `contract_digest`, `semantics`. Use the saved graph version ULID and Claim's exact execution-contract digest and semantics. The digest has 64 lower-case hexadecimal characters. Version one selects `kora.execution.v1`. |
| `deadline` | Claim's exact checked [complete deadline envelope](data-model.md#163-complete-deadline-envelope-and-legacy-projection) from the original executing claim. Require `{version: 1, value: null}` for a recorded unlimited request. A finite `value` contains exactly `at` (UTC `YYYY-MM-DDTHH:MM:SS.ffffffZ`), `scope_kind` (`run`, `subgraph` or `attempt`), `scope_id` (the concrete determining owner's bounded identifier), `clock_uncertainty_us` (the canonical nonnegative decimal string up to the existing `timedelta.max` microsecond value) and integer `grace_seconds: 30`. Missing or unrecorded evidence, a bare null and a legacy scalar alone cannot name an unlimited request. |
| `input_bindings` | The logical entries of the [version-one sequential input envelope](data-model.md#version-1-sequential-input-bindings-issues-1446-and-1492) as an array in pinned declaration order. Each entry is exactly `name`, `source`, `path`, `relation`, with that section's tagged artifact/absent source, nullable path and literal relation. The entries bind the saved input selections. The proposed command coverage below requires an empty inventory. |
| `render_profile` | Exactly `kora.jinja2.v1`. Names the proposed installed renderer and semantic profile. Its package pin, normalized environment and evidence are approval prerequisites under section 3. |
| `config`, `rendered` | The selected by-kind config and exact rendered instructions defined below. The saved config contains template sources and logical workspace/checkout intent. Worker-selected paths, actual checkout results and runtime plans stay in their own records. |
| `limits`, `protected_paths` | `limits` requires Claim's exact `stall_after_us` as a canonical unsigned decimal JSON string, either `"0"` or a nonzero digit followed by zero or more digits. Claim derives it in order from the authored node limit, graph runtime limit or configured runtime default and admits its width in the existing immutable partition. Preserve authored zero and the exact admitted width, including values above the signed-64 integer range. Other members are only present operational `timeout`, `max_events` and `budget_usd` from the typed limits, subject to installation refusal rules. `protected_paths` is the ordered checked array from Claim's execution context. |
| `retry_policy`, `retry_source`, `feedback` | `retry_policy` is the checked closed node-policy shape from [saved disabled retry policies](data-model.md#saved-disabled-retry-policies), plus its required `interpretation`. `retry_source` and `feedback` must be null in version one. It supports the first physical attempt with no earlier session, artifact or feedback. Enabled retry and separately derived requests require an approved supported profile before activation. |
| `providers` | Exactly `runtime`, `vcs`, `harness`. Runtime and VCS are required selected-provider records. Harness is a selected-provider record for an agent and null for a command. The record is defined below. |
| `publication`, `resources`, `secret_aliases` | `publication` must be null in version one. `resources` contains exactly the checked [command resource manifests](data-model.md#saved-command-resource-manifests) entries for the node, in saved order. The skeleton requires an empty array, including for an agent. `secret_aliases` is the exact checked declared alias-to-reference map from the saved graph. Version one and its fixtures retain declared references only. Feature-bearing secret settings remain subject to the [existing refusal rules](first-slice.md#shared-refusal-rules) and the skeleton start guard. |
| `price_table`, `execution_policy` | Complete existing `PriceRevision` and composed execution-policy encoding defined below. These values bind the request, even when prices or particular policy requirements are absent. |

### Config and rendering members

`config` is the exact approved operational subset of the saved `AgentConfig` or `CommandConfig` as selected by Claim. It has the existing IR field types and preserves optional-field presence. Informational extension members of structural IR records stay in the graph. Schema bodies and other explicitly typed by-value JSON data preserve their saved content without removing keys by prefix. Installation feature checks still govern authored settings, including fields that must be rejected before a request can be derived.

| Kind | Required config fields | Optional config fields | Exact rendered object |
| --- | --- | --- | --- |
| `agent` | `harness`, `prompt`, `workspace` | `model`, `system_prompt_append`, `skills`, `subagents`, `hooks`, `mcp_servers`, `tool_policy`, `permission_mode`, `sandbox`, `trust_repo_config`, `network_policy`, `output_schema`, `env`, `secret_env`, `runtime`, `vcs` | Exactly `prompt`, `system_prompt_append` and `workspace_revision`. `prompt` is the rendered string. `system_prompt_append` is the rendered string if authored and null otherwise. An authored empty append stays empty. |
| `command` | `cmd`, `workspace` | `output_file`, `resources`, `resource_set_digest`, `env`, `secret_env`, `network_policy`, `success_exit_codes`, `runtime`, `vcs` | Exactly `cmd` and `workspace_revision`. `cmd` is the nonempty ordered array of rendered strings. Each declared element produces exactly one element, without word splitting, shebang insertion or shell evaluation. |

`config.workspace` admits exactly `repo`, optional `rev` and optional `from_ref`, with their existing IR types. It preserves the authored values and omission. Command-resource entries, environment-name maps, tool policies and network policies use their existing field domains. The only admitted `skills`, `subagents`, `hooks` and `mcp_servers` values are the existing first-slice no-ops. A rejected setting cannot be converted to a no-op by this projection. No credential or secret resolution occurs during projection, rendering or comparison.

`rendered.workspace_revision` is required for both kinds. Its value is exactly one of the following, in [the existing workspace precedence](ir.md#41-agent-node-config-resolved-fr-31).

| Selected source | Stored value |
| --- | --- |
| `from_ref` selects a present verified `VcsRef` through the pinned input | A closed object `{"source":"from_ref","value":COMMIT}` with the exact recorded commit string from that artifact. The original input identity stays bound in `input_bindings`. |
| The `from_ref` selection is omitted or proves the existing allowed absence, and `config.workspace.rev` is authored | A closed object `{"source":"rev","value":REV}` with the exact string produced by the approved Jinja sandbox over the pinned inputs. Apply the existing template and webhook provenance rules. Preserve an empty rendered string as a string and apply selected-runtime revision validation separately. |
| The `from_ref` selection is omitted or proves the existing allowed absence, and `config.workspace.rev` is omitted | JSON null, preserving the omitted-revision case for the owning preparation rules. |

If the pinned selection is present but unavailable, unverified or invalid, refuse instead of using the fallback. The v1 request check derives this whole value before ready or inline first seal and compares it to the submitted member. An authored fallback used in an attempt retains its exact original template and the result it produced. Runtime allocation, provider resolution of a symbolic revision and checkout run under the existing post-seal authority, with actual checkout commit and other native observations in the original preparation record. Recovery uses the saved logical revision and any original prepared checkout evidence without re-rendering or resolving an already pinned checkout again. Installation feature support still determines which selection paths can execute.

The proposed v1 command coverage is limited to the walking skeleton's fixed check with no declared or materialized inputs. Check the pinned declaration as well as the request. Refuse a command with any declared input, including an optional input recorded absent, a nonempty command `input_bindings` array, or a materialized input member. Dropping declarations or converting them to an empty array cannot satisfy the comparison. The later compatible profile for [#106 command input preparation](data-model.md#command-input-preparation-issue-106) must bind the whole declared-order materialization result, with `absent` or the exact `{sha256, size}` of each entry. Its first seal compares the whole result with the same attempt, grant and generation and hands all corresponding ready-promoted input owners to their sealed request-input owners in the same transaction.

### Provider, pricing and policy members

A selected-provider record proposes exactly `name`, `implementation_version`, `selection_id` and `selection_revision`. The first two use the registered provider name and version domains for that protocol. `selection_id` is a configured selection ULID. `selection_revision` is a positive signed-64 integer from the trusted installation selection owner. A selection revision identifies the complete nonsecret behavior selection, including any applicable harness binary identity. Changing behavior must select a new revision before new effects. The first seal separately checks current installed compatibility. The installation owner must approve and produce the exact revision mapping and durable compatibility mechanism before this branch activates. Derive the identity from the original configured selection and its approved nonsecret facts. Provider registration metadata and [same-call validation facts](validation-facts.md#4-separation-from-execution-authority) serve their separate purposes.

`PriceRevision` has exactly the existing `id`, nullable `namespace_id`, `effective_from`, `version`, `normalization_version` and `prices`. The existing model selects canonical UTC timestamps and decimal strings for USD rates. A null rate is unpriced and an empty table identifies an existing revision with zero entries. Use the complete revision already pinned to the original attempt. Do not select today's price table when building, checking or replaying the request.

`execution_policy` is exactly `namespace_revision`, `semantics` and `values`. Require the supported Claim policy semantics `kora.execution.v1` and the existing revision domain. `values` has exactly `namespace` and `node`. `namespace` admits only the existing Claim execution requirements (`require_protected_execution`, `require_protected_resources`, `require_network_enforcement`, `allow_unenforced_agent_secrets`, `allow_trust_repo_config`) and `tool_policy`. `node` has exactly `tool_policy`. Require the existing boolean and bounded typed tool-pattern values. The actual projection preserves its checked optional field presence and array order. Current authorization, live quotas and other namespace policy stay with their current owners. Credentials stay with the trusted runtime boundary. Ending up with the same policy behavior does not make two different saved request bodies equal.

## 2. Canonical bytes and refusal

Frame either transport as exactly one UTF-8 JSON object for the logical body. Reject a BOM, invalid UTF-8, trailing non-whitespace, duplicate decoded keys (including differently escaped spellings), unknown schema members and nonfinite numbers. Apply bounds before allocating the value they protect. The inline HTTP envelope must detect duplicate names before materializing a merged object and preserve number kind into the same check. Normalize only a fully validated logical body.

The version-one canonical encoder emits compact UTF-8 JSON, without a BOM or trailing LF. Sort each object's decoded member names by Unicode scalar value and retain array order. Emit Unicode without normalization or optional escaping. Escape quote and backslash. Use the short JSON escapes for backspace, form feed, LF, CR and tab, and lower-case four-digit escapes for the other U+0000 through U+001F scalars. Reject unpaired surrogates. Field-specific exclusions on control characters still apply. Escaped NUL is retained as data only where the selected field contract permits it. This refusal applies to the proposed request format, even where the graph or prior input binding can store an escaped surrogate. Check that compatibility choice explicitly before using v1 for such a source. Never rewrite the saved source into a reachable value.

After field validation, integer leaves render in base ten, with integer zero as `0`. Finite fractional or exponent tokens preserve the real kind, using the binary64 spelling shared with the current local runtime digest. Use shortest round-trip digits, preserve negative real zero as `-0.0`, and use an explicit decimal or exponent spelling for every real. At magnitudes with a nonzero scientific exponent below −4 or at least 16, use lower-case `e`, explicit exponent sign and at least two exponent digits. Otherwise use fixed decimal notation, including `.0` for an integral real. The representation of a supported subnormal remains round-trippable. Refuse overflow, and propose refusing nonzero input that rounds to zero rather than interpreting it as signed zero. Price money strings retain their separately validated spelling. [Exact vectors](examples/execution-request-v1.md) bind the interpretation.

The request digest is `sha256:` followed by the lower-case SHA-256 of the complete canonical bytes, including `version` and `attempt_id`. `resolved_config_digest` hashes the canonical `config` object by the same recipe. The content address uses the whole canonical body, while the source declaration uses the actual received upload bytes. Both identities survive transformations in the original owner/receipt. The closed field inventory defines the full digest input. Use the same canonical recipe in the worker, API and runtime. It agrees with the current local object-digest encoding for their common admitted values. Apply the request-specific schema and limits to that shared encoding.

A noncanonical but valid uploaded source uses [canonical preparation](api-and-agent-surface.md#worker-route-bodies-issue-139) in the original custody owner, with separate source and canonical size/digest. The raw source stays immutable. Promote the fully checked canonical candidate under its original stage. Inline uses the same codec and comparison. A first inline seal makes the canonical bytes durable through the same custody lifecycle. An equal inline replay compares the request under request-local admission and returns its saved outcome with no durable stage or upload reservation. Equivalent inline and upload inputs compare the same canonical digest. Each upload reference retains its own staging authority.

Use existing Worker authorization and replay precedence. Malformed or secret-bearing values and unsupported/missing body versions are `API003`. Current epoch and wrong-stage/original-grant checks use the existing `API008` or upload-scope refusal as applicable. Changed saved pinned facts and different complete sealed content use `execution_request_conflict` in the existing seal boundary. First-seal policy drift and capability refusal use `policy_revision_changed` and `capability_unsupported`. Pending finalization and expired unsealed owners use `upload_pending` and `upload_unavailable`. The exact public classification of exhausted parser/renderer admission, missing trusted derivation and policy drift before the ready write is an owner decision. Keep those states distinct from a completed invalid body. Never invent a successful validation or disclose content in a refusal. Existing saved descriptors and authorized recovery use their original interpretation and availability. No default v1 reader, re-render, backfill, or conversion of an unversioned body authorizes new effects.

## 3. Trusted derivation and finite admission

Render with the full Jinja2 `SandboxedEnvironment` selected by [ADR-0006](../../docs/decisions/0006-graph-definition-dsl-and-yaml-representation.md) and [ADR-0013](../../docs/decisions/0013-implementation-stack.md). Only the [IR template variables and sandbox rules](ir.md#710-prompt-templates) apply. The verified source is the exact saved template with its admitted logical input context. Use no filesystem loader, import, include, provider hook, repository config, network, arbitrary Python object or ignored template error. The selected `render_profile` must pin the renderer package, deterministic environment and options, and bound data rules. The immutable context includes the original admitted run parameters and exact saved inputs with their applicable access and availability. It uses no mutable provider output or implicit current value. Missing required data refuses instead of substituting an empty value. Command and workspace provenance restrictions still apply. The Worker owns the proposal render under that same profile and the original Claim. The API independently derives the expected rendering once for its admitted finalization and compares the entire result before returning ready, or before accepting a first inline seal. The first seal of a ready upload uses the checked identity. Seal replay and recovery use the recorded bytes.

Finite rendering work needs admission and actual stop controls in addition to the sandbox. Each compiling and evaluating job must enforce its own working-allocation bound separately from admitted template, context and output bytes and from CPU, work and deadline bounds. It covers the compiler's parsed, translated and generated code state, the evaluator's intermediate structures and native allocations, including work done before yielding any output. A full source budget, a write counter or a passed timing diagnostic cannot supply that proof. The same profile applies to the actual Worker producer and the API verifier. Each owner admits its aggregate concurrent jobs and work allocation before invoking the engine, charges all simultaneously retained input, result and transport copies, and keeps its job and reservations through actual stop and join. On refusal, disconnect, cancellation or shutdown, close owned readers and discard result, compiled state and temporary copies when the work settles. Transfer a result or spool to the next admitted owner only by explicit handoff. Deadline expiry cannot release a job or authorize a replacement.

The implementing plan must select and obtain approval for the exact raw/canonical parser work and allocation profile (depth, members, tokens, numeric width, key and string storage), renderer input/output and compile/evaluate limits, enforcement and stop mechanism, maximum concurrent jobs, and reader/chunk/copy allowances. Admit source, decoded structure, sort/key bookkeeping and concurrently retained encoded representations before allocating them. Canonicalization, comparison and staging use bounded windows when complete simultaneous copies would exceed the allowance. The detached comparison result lives within its admitted finalizer and supplies comparison evidence only.

Retain the existing 16 MiB part, 256 MiB whole-upload, 512 MiB aggregate encoded-buffer and 16 KiB complete descriptor limits. Keep the existing per-domain reader, finalizer, validator and cleanup admissions and the provider's separate private limits. The reused Claim acquisition and policy/price subobjects keep their own source allowances. The whole upload retains its separate envelope limit.

### Inline HTTP admission

The HTTP ingress owner admits every seal body, including both first inline seal and equal inline replay, before retaining any payload bytes or invoking framework buffering or decoding. A route with several body variants makes that decision before reading the discriminator. Maintain finite active ingress and aggregate reservations for complete HTTP request bytes, transport and parsing copies, decoded/native allocations and any canonical comparison buffer. Use the existing [complete ordinary HTTP envelope limit](api-and-agent-surface.md#8-rate-and-size-limits), including the transition wrapper. Count actual received bytes under the reservation, including for unknown or incorrect declared lengths. A later durable finalizer slot cannot retroactively admit an earlier buffer. Finite admission refusal must leave independent Worker control traffic able to progress.

Ingress owns the stream, buffers and parser/normalizer work until actual release, including when the client disconnects mid-body or while work is admitted. Stop further intake on refusal, disconnect or shutdown and settle the original work before returning the affected reservations. Use a bounded explicit transfer if admitted first-seal preparation takes over retained content. A read-only replay uses no durable stage or finalizer. Its request-local owner still keeps its reservations until the read, comparison and cleanup actually settle. Exact aggregate allowances and the approved enforcement mechanism belong to #1453's implementation plan.

### LocalRuntime request compatibility

LocalRuntime currently hashes the complete `Workload.execution_request` into the verified request digest. Its agent admission and runner then decode that same field as closed `AgentExecution`, requiring top-level `runtime_attempt`, `policy_layers` and `output_format` with its own shape. This request leaves those runtime fields to the selected consumer and includes members that closed `AgentExecution` refuses. Passing the proposed body unchanged fails current agent admission. Substituting just an `AgentExecution` object in that field would replace the bytes checked against the sealed digest. #1453 and the runtime owner must obtain approval for a compatible consumer mapping and verify it before allowing first seal for local execution. The chosen boundary must digest and verify the entire admitted v1 body and derive or authenticate the runtime fields from that same verified request and its exact saved sources. Independently supplied or unhashed runtime projections cannot stand in for it. Use the same parsed inherited binding in `Workload.deadline` and the trusted protocol context, as required by the [runtime submit contract](protocols.md#2-runtime-fr-81).

Verification also applies to the selected consumer's actual `Workload.execution_request` value and control-path bounds, including the representability of the exact saved stall duration and selected workspace revision. A ready result supplies storage evidence. The first seal checks runtime representability and mapping. The request retains the Claim value even when a selected consumer must refuse it under its approved compatibility rules. An expanded runtime transport or smaller request body limit requires its own decision.

Existing owner fields supply facts they already bind. Additional compact native fields and indexed access belong to the implementing plans. No second body copy or opaque validation boolean supplies this evidence.

## 4. Original handoff and recovery

For an unsealed request, upload recovery returns ready only for the same live original grant and immutable source binding. The read leaves the owner, expiry and charge intact. A new grant requires fresh admission for a new source. If source, current grant, policy or configured selection changes before the ready commit, or the recorded deadline mismatches or is now expired, the old comparison cannot mark the stage ready. Settle the original owned work and apply the existing conflict/refusal and cleanup rules. Do not substitute another ready stage for a missing original reference.

At `seal_request`, check current namespace/service/lease authorization before disclosing a stored outcome. An existing seal compares complete canonical request identity for inline, or resolves the exact checked `upload_ref`/original completion binding for upload form. Matching content returns the original descriptor and policy before today's policy comparison or a new-effect check. An exact previously consumed reference can use its durable terminal binding after the stage is retired. A reference to a different live stage still needs its own authorization and exact ready binding. Equal replay writes nothing, never re-renders, and neither reopens an expired stage nor renews authority. Different complete content cannot replace the seal. The retained descriptor records actual availability and can identify bytes no longer retained.

Only a missing seal proceeds to the first-seal capability, policy, inherited deadline and current execute/result checks. Complete detached inputs and storage observations outside locks. Then serialize the original run and all participating scope/address/owner rows in established order. Recheck current attempt, original live grant, any sticky expiry or prior stop, runtime/installation compatibility, and exact ready stage/source, retained bytes, compared saved facts and current fence. The full submitted or previously checked `deadline` must equal the original saved binding, including explicit unlimited state. Separately apply fresh persistent-ancestor and attempt expiry checks under the existing [current authority rules](data-model.md#152-sticky-expiry-and-current-result-authority). The body cannot start a later clock or add grace, including on recovery. The body policy revision and `expected_policy_revision` must agree with the trusted current policy revision and the checked policy projection must still apply. No checks use a worker-supplied digest or policy as affirmative evidence. Perform one conditional transaction inserting the durable `execution_request_content` owner and completion binding, accepting the owned staging reference and releasing its charge once, recording the exact descriptor and policy, and updating the Claim read admission and incrementing its source revision together. Until that authoritative original transaction has committed with durable bytes, do not allocate a workspace, prepare runtime state, resolve secrets or submit.

Cancellation, timeout and response loss retain the actual original work/effects and original commit identity under [native custody](execution-custody-native.md#3-original-metadata-commit-protocol). A known refusal cannot report ready or sealed, and failure before acceptance leaves the stage under its original cleanup obligations. Unknown outcomes retain their guards and charges until the original owner resolves them. Recover ready/terminal results read-only using their own published rules. After a seal, execution and recovery read the exact retained canonical request and original policy with a qualified hold. An unavailable request never becomes current configuration, a freshly rendered prompt, or evidence of termination.
