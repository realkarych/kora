# GitHub pull request publication for the second slice

[Issue #1832](https://github.com/realkarych/kora/issues/1832) defines the provider contract and delivery order. The GitHub adapter first proves creation and read-only recovery against a controlled fixture. Activation in a graph follows the milestone order in [ADR-0001](../../docs/decisions/0001-own-control-plane.md#milestone-order-amendment-of-2026-11-11). Creation and recovery follow [ADR-0007](../../docs/decisions/0007-attempt-model-and-retries.md), [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md) and the [VcsRef enrichment contract](artifacts/README.md#5-upload-replay-and-result-ownership). The provider checkpoint is implemented under [#1835](https://github.com/realkarych/kora/issues/1835). Graph activation remains pending.

## 1. Publication identity

The initial profile supports a GitHub pull request whose source and target refs are in the same repository. Use the saved, trusted binding identity, revision and credential mode to select the GitHub host, immutable repository ID and target branch. Resolve the source branch and exact head SHA from the authenticated result of the original push. The expected base SHA is the result's saved comparison base. The target branch is separately configured and must resolve to that SHA for this profile. An advanced target branch fails preflight for the saved SHA. Accepting a different base requires its own eligible publication and evidence. A candidate URL, branch suggestion, commit message or PR text supplies no destination or revision authority.

A request matches only when the provider has checked the repository ID on both sides, both full branch names and both exact Git SHAs. The base SHA returned in a PR describes that observation and can differ from the current tip of its named branch. Check both current refs through the bound host before a first create, and check the actual PR facts returned after dispatch. The PR number scoped to the bound repository and host identifies the remote object. Host URLs serve as display values after validation. Neither a URL nor a branch name identifies a repository or an operation on its own.

The [GitHub REST create operation](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request) takes branch names and offers no expected-SHA condition. Preflight and readback can detect many changes and establish facts at those observations. A ref can still move during dispatch or move away and back. An observed mismatch refuses enrichment and retains learned effects. The controlled fixture holds the refs fixed for its successful cases and deliberately moves them for refusal cases. A live activation plan must identify the writers that can move or reuse these refs and establish the protections for its promised guarantee. Observation alone cannot prove that an off-target side effect was prevented.

## 2. Credential and caller boundaries

[ADR-0023](../../docs/decisions/0023-code-host-identity-and-purpose-scoped-credentials.md) places the GitHub App signing key with the control plane. The trusted caller obtains a fresh, ephemeral `api` credential for each code-host call under the original saved binding and the applicable namespace and attempt authority. The issuer narrows the installation token to the immutable repository and required native permission for the call. Read-only reconciliation uses read permissions. Create requires pull request write permission. The caller verifies the binding, purpose, effective repository scope, rights, expiry and stable principal before use. Bind the secret transfer to the original namespace, attempt and applicable dispatcher grant. Register it under the original transfer scope and release it on every exit. The implementation plan specifies the typed transfer and the evidence for the actual repository and permissions. The adapter receives only the role and context needed for the call. Checkout and late publication credentials keep their separate purposes.

The trusted binding selects the HTTPS API origin and its TLS policy. The isolated fixture supplies its own trusted endpoint and trust root. Resolve only allowlisted API operations under that origin with certificate chain and bound hostname verification before any credential is sent. The repository path used for dispatch must resolve to the bound immutable repository ID, and the installation token must exclude other repositories. Host-returned links, untrusted configuration and ambient proxies cannot redirect the credential or select a different resource. The initial provider limits a list lookup to one page of at most 100 entries under its byte budget. A continuation leaves the lookup unresolved and only safely identified scoped PR numbers may be returned. The adapter never sends a request to the continuation. A redirect is a refusal with no forwarded credential. The caller supplies title and body under the original approved presentation and bounded input policy.

GitHub's App, installation and author account identifiers have distinct roles. The issuer and provider must agree on a trusted mapping to the stable host account that can appear as the PR opener. Compare the stable scoped identity through that mapping. A login, display name or number in a different identity namespace grants no match. A newly confirmed creation by this operation uses its original saved API-principal snapshot after matching the remote opener. A pre-existing request uses its independently verified actual opener. A credential acquired during recovery supplies no evidence of who opened the PR.

The worker owns persistence and effectful dispatch. Before dispatch it saves the original attempt, output, runtime result, destination, revisions and acquired API principal in the attempt-owned recovery state. After credential acquisition, the worker requires fresh authenticated authority to dispatch the exact effect under the original binding, in execute mode, with the current lease, desired state and deadline. It serializes the effect against local dispatch closure. Every earlier dispatcher and unresolved platform action retains its existing closure obligations. Provider lookup, provider construction and credential issuance confer no create authority. The implementation must expose distinct read-only and caller-authorized effect paths so a recovery call cannot send a POST.

## 3. Create, lookup and recovery

The caller searches the bound repository before first create. Use the provider's ref filters where useful, and verify each matching object's exact identity and revisions independently. Include open, closed and merged requests in the precreate and recovery searches. Reuse one exact request with verified provenance. A later change of status supplies no create authority. Precreate discovery follows the inherited execution deadline. The authorized historical recovery path remains available after that deadline under [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md), with its own finite reconciliation timeout and no current-result promotion. Both paths bound request count, total response bytes and response parsing. A complete bounded search establishes what was visible to the authenticated caller within that search. Pagination exhaustion, invalid responses, missing permissions or conflicting observations do not establish absence. An already known PR number permits a direct bound read.

Before the first POST, the caller must establish absence through a complete bounded search performed under the profile's writer protections for the natural key consisting of the bound host, repository, refs and revisions. Hold that protection from the search through dispatch settlement, including across distinct intents for the key. Discard and repeat a negative search obtained before acquiring the protection or during a prior holder's tenure. The dispatch owner retains exclusion while the outcome is unresolved. Concurrent callers for the same key observe or reconcile the original effect. The provider sends one POST for each authorization and never silently retries a mutation. An acknowledgment can settle a known create. Accepting one exact PR also requires evidence of a unique matching result under the profile's writer assumptions and bounded observations. A lost response, interrupted transport, incomplete search, inaccessible resource or generic validation error supplies no proof of absence or closure. While the earlier action remains unresolved, recovery is read-only. Any later create requires affirmative proof of the earlier action's closure and absence of its effect, plus fresh external authority for the same intent.

| Evidence | Provider outcome and caller action |
| --- | --- |
| One existing exact request, with verified opener and no ambiguous equivalent objects | Return the scoped identity and verified fields. Use the actual opener and keep any observed open, closed or merged state separate from the immutable result. A known request needs no new creation. |
| Valid acknowledgment of this create with unique exact PR facts and verified opener | Return the scoped identity and facts of the created request. The caller preserves the original principal snapshot and may freeze the enriched candidate. |
| Known created request whose revision, opener or artifact fields fail the required checks | Record the learned effect and its attribution confidence under the original intent. Refuse enrichment. Settle the external action only where evidence identifies its outcome independently of artifact acceptance. |
| Lost create response followed by exact readback attributable to the original action | Recover the scoped identity and verified facts. Attribution and closure require affirmative evidence that the original dispatch produced the object and can cause no additional effect. A confirmed original effect identity or independent evidence of the exclusive writer and its settled action can establish this relationship. The fixture holds the refs fixed and records the single dispatch committing before it drops the response. |
| Exact readback after a lost response, with attribution or closure unresolved | Preserve the observation. A shared bot account and an exact branch/SHA match alone cannot tie a request to a specific POST. Retain the original dispatch and its recovery obligations. |
| Movement, competing matches, malformed data, incomplete search, or no visible match after uncertain dispatch | Return conflict or unresolved evidence as appropriate. Preserve known observations without starting a new effect. |
| Previously completed, validated and frozen enrichment | Replay the caller's saved canonical bytes and exact outcome. Current refs, response display values and credentials cannot rebuild or replace them. |

On a verified effect, the worker preserves the bounded repository and PR identity with the fixed attribution and closure facts even if the artifact is refused. The effect record never copies host payloads or arbitrary host text. The provider validates returned links against the trusted host and verified PR or revision identity. While the secret registration is active, it refuses enrichment with registered secret spellings in any returned field, including otherwise valid links or opener display values. Refusal keeps sanitized effect evidence. Validate and freeze the enrichment before first upload. The original push result stays immutable. The provider may supply verified additions allowed by the [VcsRef revision-1 contract](artifacts/README.md#5-upload-replay-and-result-ownership). The worker retains an unknown dispatch and its owner holds until authoritative settlement or fencing. A local HTTP client finishing cancellation or closing its socket supplies no proof that GitHub stopped processing a request.

Use the normal [structured diagnostics](observability.md#7-component-coverage-and-activation) path. The provider records bounded operation names and outcome classes with caller correlation. Request and response bodies, headers, credentials, raw URLs, upstream exception detail and repository content stay out of diagnostics. The caller retains recovery facts in the existing durable owner. Log delivery cannot change the operation's result or recovery state.

## 4. First provider evidence and activation

The installed `vcs.git` provider exposes separate `lookup_change_request` and `create_change_request` calls when its trusted configuration includes `change_requests`. The configuration pins the immutable repository ID, owner and repository path, base branch, binding and stable App bot-account identity. Its code-host binding is separate from its local Git bindings. The regular origin is GitHub's HTTPS API. A controlled loopback origin requires an explicitly configured CA. The local Git path keeps its credential-free rules and refuses API acquisition.

The operation receives a trusted caller's registered API grant. Precreate lookup checks the bound repository and uses pull-request and contents read rights. Historical lookup uses pull-request read rights. Create uses pull-request write rights. Inside the caller's admitted dispatch it verifies the repository ID with the write-scoped grant before sending a single POST. Binding and path verification carry no authority of their own. Each grant also carries GitHub's metadata read permission. The installation reuses the saved principal namespace and maps GitHub accounts to stable IDs in that namespace. A read observation supplies no evidence of original dispatch settlement. A create response can acknowledge a mutation even if no usable PR identity or enrichment can be extracted. A body timeout after HTTP 201 preserves the acknowledgment and leaves the PR identity unresolved.

Exercise the installed production adapter through the [provider conformance path](protocols.md#13-conformance-suites-nfr-102). Use actual Git revisions in a local bare repository and a controlled stateful code-host fixture reached through the adapter's real HTTP transport. The fixture uses the host's branch-name create semantics. In the lost-response case it commits the PR to its state and drops the response. A fresh caller then reads the same PR number and exact revisions, with one PR and one authorized POST in the fixture. Existing local Git and directory-backed VCS cases keep their applicability and coverage.

| Check | Required evidence and owner |
| --- | --- |
| Provider exact create and lookup | The installed provider proves one same-repository PR for the saved head and base. A repeat or a pre-existing exact PR returns the same identity and the verified actual opener. Closed or merged objects remain discoverable without a reopen. |
| Provider response loss and ambiguous outcomes | The installed provider reads the same PR after a committed POST loses its response. Further tests hold a POST in flight while a different operation using the same App creates a matching request, return a generic validation error, move either ref after preflight, exercise movement away and back, and supply wrong identity, multiple matches, malformed and incomplete responses. Exercise competing intents for the same natural key and show that a preexisting closed match or an unresolved dispatch blocks a second create. A malformed or capped precreate lookup grants no first POST. None of these observations grants a second POST. A known off-target or invalid result preserves a bounded effect observation. |
| Provider credentials and actual resource release | Conformance checks purpose separation, wrong-repository or insufficient grants, wrong-host and untrusted-chain TLS refusal, and redirect refusal, bounded pagination and response sizes, and registered credential spellings echoed in otherwise valid response fields. Verify secret-free results, retained effect records and diagnostics, and actual local client and fixture closure on success, failure, cancellation and shutdown. Admission and its resource bound remain in force until local cleanup completes. The GitHub App issuer supplies actual scope, expiry and principal evidence under its own implementation. The code-host identity cases in [protocols](protocols.md#code-host-identity-contracts-adr-0023) retain their respective backend and database obligations. |
| Caller idempotence and original dispatch closure | Work item 17 proves concurrent same-operation requests have one authorized wire effect and the same result, and owns the integrated `test_publish_and_open_change_request_are_idempotent` and `test_publish_reconciles_after_response_loss` change-request legs. It exercises loss, adoption, deadline and lease changes, and closure using the original durable intent. Hold a contender after an empty read, let the eligible writer create and close its request, then release the contender. The contender must discard its stale absence, find the same PR and send no POST. A POST that loses its response before expiry can be reconciled after expiry without another POST or current-result promotion. |
| Immutable enrichment and replay | Work item 17 owns `test_vcs_ref_enrichment_replay_is_immutable`, including replay of frozen bytes, changed principal display data, preservation of settled effects on artifact refusal and all required metadata cases on SQLite and PostgreSQL. |

The provider checkpoint is tracked by [issue #1835](https://github.com/realkarych/kora/issues/1835) and may land before first-slice acceptance. It uses a trusted caller and a controlled fixture and establishes evidence only for the exercised provider boundary. The control-plane issuer and worker issuance route, credential-bearing Git transport, durable Worker integration and live deployment each supply the evidence required at their boundaries before product activation. Automated repository tests use the controlled fixture. Any separate live publication uses an authorized controlled repository.

## 5. Integration ownership

| Input or effect | Owner |
| --- | --- |
| Exact push and the original `VcsRef` | Runtime and the common executor own inspection and the immutable result. The Worker and API retain late publication authorization and dispatcher fencing under ADR-0016 and ADR-0017. |
| GitHub App identity, credential issue and dispatch | The control plane owns credential issuance and audit. The Worker owns current authorization, the saved create intent and principal, external effect settlement and the frozen enrichment. The GitHub adapter owns bounded host I/O and verified observations. |
| Command gate results and diff evidence | The gate producer owns the accepted `CommandResult`, exact input revision and protected-path evidence. The integration consumes accepted gate and publication facts through the [review facts contract](../../docs/decisions/0008-content-bound-approvals.md). Provider input may carry an approved presentation of those facts. A PR body supplies no test result or proof of the change. |
| Cost of all attempts | The accounting owner supplies the pinned, whole-run cost evidence, including missing or unpriced entries. The integration establishes the accepted cost cut and passes its presentation to the adapter. |
| Delivering the second-slice evidence on the PR | The graph-integration owner binds the verified PR identity to the diff, accepted gate result and exact whole-run cost cut. It proves that those facts are visible on that PR whether creation or reuse produced the identity. When a reused PR lacks those facts, the integration must specify and authorize any additional delivery under the external-effect rules. |
| Content-bound CLI approval | The scheduler and approval API own the original approval request, exact SHA and gate-digest binding, current-head observation, invalidation on push and the fresh post-approval check. The GitHub adapter can provide a verified observation and recorded PR identity. A PR URL, state or opener supplies no approval. |

The graph-activation work composes these owners with the retried agent and command-gate subgraph for both harnesses under ADR-0001. It supplies the accepted gate and cost presentation and exercises SHA-bound approval and invalidation. The first provider evidence carries no authority to activate any of those graph effects.

Before live activation, the implementing change records the authorized repository, the host-side ref and writer assumptions, how it settles uncertain dispatch, and any accepted residual external effects in the applicable threat-model entries. GitHub may act on a created PR before kora can validate it. The planned activation requires owner approval of those limits and the integration evidence.

## 6. GitHub App credential issuance

[Issue #1844](https://github.com/realkarych/kora/issues/1844) supplies an optional issuer for the trusted control-plane composition. An immutable binding pins the destination profile, App ID, client ID, installation ID, namespace, and the provisioned stable account identity of the App bot. The binding also names a dedicated control-plane key resolver namespace and reference. Provision the key outside every namespace resolver and prefix available to graphs. The issuer calls that dedicated resolver with its own registered scope. It keeps both the parent key and the signed App assertion within issuer-owned lifetime.

The initial issuer serves the PR adapter's three API roles. Before resolver or host calls it matches the original binding, revision, credential-required mode, repository, namespace, attempt and typed caller scope. The trusted caller carries the dispatcher identity and selects its admitted role. The Worker route will check the actual current grant and original sealed request. This provider boundary has no route or graph activation.

| Role | Requested and verified native permissions |
| --- | --- |
| Historical lookup | `metadata:read` and `pull_requests:read` |
| Precreate lookup | `metadata:read`, `pull_requests:read` and `contents:read` |
| Create | `metadata:read` and `pull_requests:write` |

The App assertion is RS256, with a five-minute future expiry and a one-minute backdated issued-at from the trusted clock. Successful authenticated App and installation reads must match their pinned identities. The installation must be an active user or organization installation. The issuer requests one immutable repository ID and the exact role permissions. It rejects excess or missing returned permissions. A returned repository list must contain exactly the selected repository. If the host omits that list, use the new installation token for one bounded read of `/installation/repositories` and require a complete singleton result with the pinned ID. Explicitly broader scope refuses issuance.

Treat the returned token as an opaque, bounded bearer value. Register it in a private verification scope before any read with that token. Its reported expiry must be in the future and within one hour plus one minute of clock allowance. Recheck expiry again before handoff. The transferable grant retains the exact host expiry, verified repository and role permissions, and original App principal snapshot. It reports `reissue` and `native` as the provider's replacement and revocation capabilities. The caller owns the registered returned value until it releases its scope. After handoff the issuer releases its own registrations, including the verification copy. Local release supplies no remote revocation evidence. Response loss can leave a token minted. Each separately authorized acquisition makes a fresh exchange.

One finite deadline covers resolver and host work. Precreate and create also respect the original useful deadline, and historical lookup can acquire a read token under a separate finite budget after execution expiry. The issuer uses the pinned HTTPS origin and TLS policy of the destination profile. Secure refusal and closure evidence cover unsuccessful exchanges and independent cancellation. Diagnostic output includes a fixed outcome and caller context through the bounded logging contract. The Worker storage and audit integration retain their separate responsibilities.

The optional `kora[github-app]` profile carries the pinned signing libraries. The base provider imports no signing dependency. Controlled HTTPS exercises the real signing exchange, verified scope, and handoff to the installed PR adapter. Any live qualification depends on the independently authorized repository and App installation.
