# Renderer release provenance

The project owner approved revision 1 and the first Linux dm-verity evidence source on 2026-11-23.
[The exact reviewed design](https://github.com/realkarych/kora/issues/1640#issuecomment-7086460830) has SHA-256 `f0a09fddf748590c9a63384ddb5db195248c79ca3c73900bf89ed85ce90d9946`.
[The recorded approval](https://github.com/realkarych/kora/issues/1640#issuecomment-7086773303) and [#1811](https://github.com/realkarych/kora/issues/1811) cover this specification.
The [Canonical base and owner-manifest decision](https://github.com/realkarych/kora/issues/1640#issuecomment-7086368842) and the [optional Doctor and independent verifier decision](https://github.com/realkarych/kora/issues/1640#issuecomment-7083316762) also apply.

This specification governs static preparation of the first Linux renderer installation.
It binds an independently supplied expected deployment document to two actual frozen installation roots under the cooperative local trust boundary in [ADR-0016](../../docs/decisions/0016-trusted-execution-and-publication.md).
Implementation and activation belong to [#1640](https://github.com/realkarych/kora/issues/1640).
Live launch, guarded rendering and renderer qualification have their own acceptance.

## Preparation and release authority

The trusted release preparer may register and compare an explicitly pinned draft in the preparation-only registry.
A passing static comparison supplies evidence for the owner’s review.
Only a project owner may approve the exact final OS and installed identities out of band and make that manifest available in the independently provisioned runtime registry.
The draft has no approval field and cannot grant release authority.
Candidate files, metadata, launcher arguments and RECORD cannot supply the expectation or the registry anchor.

## Closed revision 1

Use the following required keys with no optional keys, nulls, extensions or aliases. Digests and salts are exactly 64 lower-case hex digits. Integer leaves are JSON integers of exact kind, excluding booleans, and within signed 64-bit range. Refuse unsupported revisions.

The first is the referenced inventory digest. `entry` names the verifier launcher in the verifier root and the future guarded bootstrap in the candidate root. `interpreter` and `elf_loader` name the intended executable and ELF interpreter file. The inventory also covers native dependencies and package files in that root. These declared paths provide inputs to later live resolver verification. |
| `verity` | `data_blocks` positive and at most `floor((2^63-1)/4096)`, `root_hash`, `salt`. The revision fixes ext4 without a journal, dm-verity target format 1, SHA-256, 4,096-byte data and hash blocks, a detached hash device with start block 0, no on-disk verity superblock and zero optional target flags. |

Include every regular file beneath the held root once, ordered by ascending UTF-8 path bytes. The directory set is the implied parent directories and mount root. Refuse aliases, symbolic links, hardlinks, extra directories or members, special files, and nested or overlapping mounts. A prepared package can materialize regular files in the approved layout before sealing its volume. |

Relative paths are slash-separated nonempty components from the ASCII alphabet `[A-Za-z0-9._+-]+`, neither `.` nor `..`, with no leading or trailing slash and at most 1,024 UTF-8 bytes total. Retain the planned verification byte, memory, traversal and time envelope from [the renderer design](https://github.com/realkarych/kora/issues/1640#issuecomment-7083447929), including the 4 MiB encoded input budget across all three documents, 4,096 examined entries and 256 MiB verified file bytes. Account for copies and actual settlement in the same owner. There is no new budget or fallback to a partially checked inventory.

For all three documents use the [v1 canonical JSON encoder](execution-request.md#2-canonical-bytes-and-refusal). Require exact canonical bytes on disk. Sort decoded object keys by scalar value, preserve prescribed array order, use UTF-8 with no BOM, whitespace or trailing LF, standard canonical string escaping and minimal base-ten integers. Reject duplicate decoded keys, invalid encoding, noncanonical forms and any extra token. Lookup the deployment document as `<selector>.json` inside the trusted registry's fixed deployment directory. Its selector is the lower-case SHA-256 of the complete canonical bytes with no prefix. No field embeds its own digest or any approval marker. Resolve each inventory as `<inventory_sha256>.json` inside the fixed inventory directory of the same trusted registry. Hash a full deployment-root inventory as SHA-256 of `UTF8("kora.renderer-root-inventory/1") || 0x00 || canonical_inventory_bytes`. This domain belongs to the complete root-relative tree, including files outside any one behavior package. Open both kinds of document by descriptor below the known anchor, without links.

The deployment selector selects a complete preparer/owner document. It is not stored in `0033` or used as the installed renderer behavior identity. [Installed selection](installed-execution-selection.md#canonical-nonsecret-fingerprint) already defines which package-relative inventories and effective options feed `kora.installed-selection/1`. Those remain separate package-relative projections under their existing `kora.installed-artifacts/1` domain and meaning. The deployment inventory reuses the canonical encoding and file-row structure. Its digest cannot stand in for an installed behavior-package digest. A new boot, mount or verifier distribution can affect deployment admission without changing renderer behavior. Keep machine-local anchors, mount IDs, credentials, workload and rendered bytes out of the canonical documents. Bind the actual mounts by live preparation evidence.

## Golden vector

For both inventory arrays use one-byte files `bin/python` containing ASCII `p`, `lib/ld.so` containing `l` and `std/x.py` containing `s`. Add `entry.py` containing `v` for the verifier and `c` for the candidate. Each inventory is 448 canonical bytes. The verifier and candidate domain-separated inventory digests are respectively `8d09374f70f88d52b4e32c8bcbd1928e49ed73f539940e8746d4ba6349ce9960` and `8b5cad86a06e8e08b7aad62ecd8306e0c4f36ce0189e1dfa8564b2b9053a0c4d`.

For the document use the fixed base and input values above, kernel release `6.8.0-147-generic`, and 64 copies each of `1` for initrd and `2` for the kernel. Set both roots to their inventory digest and paths `entry.py`, `bin/python`, `lib/ld.so`, and `std`. Set each `data_blocks` to 2048. Use 64 copies of each indicated digit, `3`/ `4` for the verifier root hash/salt and `5`/ `6` for the candidate root hash/salt. The 1,349 canonical bytes have selector `e6868b5c2a9acac05d0b8064833261f8428d43a64564405e754dfad635f68e2d`. The one-byte files and repeated digits only exercise encoding and binding. They do not supply executable, boot or media proof.

## First Linux immutable root evidence

Use two separate ext4 images under dm-verity in the exact amd64 Canonical preparation guest.
The [Canonical Noble 20261017 image](https://cloud-images.ubuntu.com/releases/noble/release-20261017/) passed independent verification of the public signature and actual image bytes under the approved acquisition plan.
Its signed amd64 package manifest matched SHA-256 `78d7da6ab1556daa6c0f685bf4e0e3da36395f170e8fad411d7ba032f14d08c2` and lists `cryptsetup-bin` `2:2.7.0-1ubuntu4.2`, `dmsetup` `2:1.02.185-3ubuntu3.2`, `e2fsprogs` `1.47.0-2.4~exp1ubuntu4.1` and the `6.8.0-147-generic` kernel image and modules.
Those are build inputs. The guest, prepared media and live observations remain pending.
[veritysetup](https://manpages.ubuntu.com/manpages/noble/man8/veritysetup.8.html) · [Kernel dm-verity](https://docs.kernel.org/admin-guide/device-mapper/verity.html)

1. The already trusted release preparer, working under the project owner's preparation authority, builds both expected inventories from independently verified source, the pinned archives and the declared build outputs. This is on the trusted build side before the comparison. Using the base image's `mke2fs` and `veritysetup format`, the preparer stages separate ext4 roots with 4,096-byte blocks and `^has_journal`. Remove any mkfs-created empty directory outside the implied parent tree before sealing. Format each completed volume with a separate hash file, `--no-superblock`, format 1, SHA-256, both 4,096-byte block sizes, exact `data_blocks`, hash offset 0 and the recorded 32-byte salt. Pin the reported root hash. Treat the resulting image and hash tree as build outputs. The preparer provisions the initial trusted comparison launcher, expected deployment and inventory bytes, and their digest through its dedicated trust anchor outside both mounts. The static checker runs from this pretrusted preparation installation. It does not bootstrap trust in itself by comparing the verifier root that will be issued later. Candidate bytes, metadata, launcher arguments and RECORD may not establish that expectation or that anchor.
2. On the trusted exact boot, the preparer exclusively owns mount and DM operations in a private mount namespace with no external mount propagation. It retains each role’s separate data and hash devices, instantiates two read-only mappings with distinct per-job DM UUIDs from the expected roots and salts, mounts each whole ext4 root read-only with journal loading disabled, and opens each actual mountpoint root under the held anchor. It retains these original directory descriptors, the namespace and the mappings until full settlement. Before spawn it checks each descriptor’s `mnt_id`, `st_dev` and `st_ino` against the root it opened and its mount record. Require filesystem root `/`, read-only ext4, and no subordinate mounts. Bind each role’s device number and DM UUID to the active, read-only mapping with no suspended or internally suspended state, inactive table or pending removal. Require exactly one target at sector 0 with length `data_blocks * 8` in 512-byte sectors, referring to that role’s distinct held data and hash devices. Compare the expected type, version, geometry, hash start, algorithm, digest and salt. Require zero optional flags and status `V` on the pinned Linux 6.8 kernel.
3. The preparer starts one direct unprivileged comparator child in the same held mount namespace. Give it only the two original read-only root descriptors for filesystem authority and private inherited framed request/result pipes for this job. Keep the independent registry outside both mounts. The bounded starting frame carries a per-job correlation value, the independently pinned deployment selector and expected canonical documents, the namespace identity and the two role-tagged observations. Each observation carries the actual mountpoint root’s `mnt_id`, device and inode, plus the matched live DM device number, UUID, table parameters and status. The child checks the selector and document bytes, its own mount namespace identity, the two actual descriptor identities from `fdinfo` and `fstat`, and their mount records. Use those held descriptors for all walking. A subdirectory on the right mount has the wrong root inode. Use no candidate-provided values to establish an expected root or a live observation. Device-mapper control ioctls require privilege. Only the preparer makes those calls, with neither the control descriptor nor that privilege passed to the child.
4. The child returns a tentative result scoped to the same job and selector. The preparer takes the final matching mountpoint, namespace, active table and status observation after the complete result and EOF, known successful exit and reap of the original child, and closure of the child’s resources. It still owns both original mappings and mount anchors at that observation, and never swaps or tears either down during the comparison. Only the preparer publishes a static match, after releasing its owned pipes, descriptors, mounts and mappings and observing actual settlement. Cancellation, lost owner/channel, changed namespace, root or mapping, stale observation, or missing final check refuses without a positive result. Hold the existing admission charge through actual cleanup, including parent-owned pipes, anchors and tasks. No privileged child or publicly connectable endpoint is required. [Linux 6.8 DM control code](https://github.com/torvalds/linux/blob/v6.8/drivers/md/dm-ioctl.c#L1917-L1930) · [Kernel mount and fdinfo evidence](https://docs.kernel.org/filesystems/proc.html#proc-pid-fdinfo-fd-information-about-opened-file) · [dmsetup](https://manpages.ubuntu.com/manpages/noble/man8/dmsetup.8.html)
5. Refuse before candidate import on missing trusted selector or boot proof, malformed/mismatching canonical document, absent/mutable/aliased root, wrong live device or verity parameters, an unreadable block, a file or inventory mismatch, unexpected discoverable entries, or unresolved work/closure. Open files relative to the held root without links, compare byte count and SHA-256 on actual bytes and recheck identities. Return only deterministic static match plus the deployment selector on success, or a fixed refusal without content or a renderer fingerprint. The preparation invocation does not execute or import candidate code even on success. Later Doctor additionally needs actual verified launch resolution, crash policy, the guarded renderer and qualified limits.

## Implementation acceptance

The static comparison must reproduce the exact golden bytes and refuse malformed, duplicate or noncanonical documents.
Exercise a real match through both verified mounts on the pinned Linux base.
Require pre-import refusal on a wrong digest, a different mount or device, ordinary read-only ext4 without verity, swapped root descriptors, a subdirectory descriptor on the correct mount, a stale snapshot from a different job, and loss of the owner or its final recheck.
In each refusal case no positive comparison leaves the preparer.
Check real traversal, file and digest divergence, cancellation and actual closure as described in the [implementation plan](https://github.com/realkarych/kora/issues/1640#issuecomment-7086368842).
Exercise integrity error propagation on a disposable owned test volume with changed backing data and the original digest. The comparison must retain the I/O refusal without reporting success.

This static result leaves actual verified launch resolution, crash policy, guarded rendering, framed Doctor settlement and compile and evaluation caps to their implementing changes.
The remaining Linux tuple, macOS, and real Worker and API qualification preserve their existing acceptance.
