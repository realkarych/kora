# kora MVP design — HTTP API and the four thin clients

Status: design draft for owner review (2026-10-15, revised after the design review, see [review-2026-10-15.md](../reviews/review-2026-10-15.md)). Scope: FR-0 (AI-first parity), FR-7.2–7.3, FR-11.1, FR-11.5, FR-12.2, NFR-0.3, NFR-4.4, NFR-11.3, NFR-13.1. The HTTP API is the only implementation of every operation; the CLI, the MCP server, the harness skills and the web console are derived clients. Owner decisions on design choices are referenced as **DD-n** ("design decision n") and recorded in [design-decisions.md](../reviews/design-decisions-2026-10-15.md).

The MCP server and the skills exist for the **user's own coding-agent session**, so that an agent replaces the manual actions a human would take in the CLI or the page: author, compile, deploy, trigger, inspect, approve, retry, cancel. Agent **nodes** running inside a kora graph have no access to kora's MCP server or API (DD-5, DD-16); the IR gives them only the MCP servers their resolved config lists.

## 1. Conventions

- Base path `/api/v1`; JSON bodies; ids are prefixed ULIDs (`run_…`, `node_…`, `att_…`, `art_…`, `apr_…`, `gv_…`).
- **Authentication** (NFR-4.4, DD-32): `Authorization: Bearer <token>`. **Personal user tokens** are bound to a person and a namespace list and carry exactly two flags: `approve` (may respond to approvals) and `platform` (may publish presets, namespace policies and tool policies); reading transcripts, session segments, saved prompt/feedback and equivalent content-bearing config/diff projections needs the `transcripts` capability on the namespace entry (ADR-0018) (current contract [protocols](protocols.md)). No roles or groups. **Service tokens** belong to workers, are bound to a namespace list enforced at claim (current contract [ADR-0011](../../docs/decisions/0011-namespaces-and-personal-tokens.md)) and may register, claim, heartbeat, upload, transition and perform bounded worker-only reads for attempts whose current grant they hold. Each retained-history page rechecks the worker, incarnation, original domain, dispatcher and lease epoch; a position grants no authority. Every by-id route joins on `namespace_id` against the token's list. The MCP servers and `kora web` present their configured personal credential and have exactly that credential's permissions. Standalone issues separate CLI and MCP personal tokens for the same owner/default namespace: both have `transcripts`, and only the CLI default has `approve` and `platform` (ADR-0011). The authentication protocol in [protocols.md](protocols.md) replaces the token check without changing routes.
- **Namespace scoping**: every resource path starts with `/namespaces/{ns}`; a token's scope lists the namespaces it may read and write.
- **Idempotency**: every `POST` that creates or mutates accepts `Idempotency-Key`; the server stores `(token, key, request digest) → response` in the `idempotency_record` table for 24 h and replays it from any replica. Canonical starts additionally keep durable graph-scoped accepted/skip receipts beyond this cache; a transient run_backlog_full refusal creates no accepted outcome and is not cached as an unrecoverable refusal (ADR-0020). A lock-wait refusal of a signal route rolls back and is never cached either ([signal routes](#signal-routes-schedulermd-section-12)). Heartbeat, segments, usage and every body of `POST /attempts/{att}/transition` are naturally idempotent, take no `Idempotency-Key` and ignore one that is sent; they and the other worker routes replay as [worker route bodies](#worker-route-bodies-issue-139) states ([issue #139](https://github.com/realkarych/kora/issues/139)). Credential issuance (`POST /attempts/{att}/credentials`) is the one exception that never returns a stored response: its response is never stored in `idempotency_record` or any cache, and a repeated request with the same key is treated as a fresh request that re-runs the current lease, epoch, binding identity/revision/mode, purpose, repository and digest checks and acquires a new credential, so no replay returns a stored or expired secret (ADR-0023). Triggers without a key get a derived one, a manual trigger a fresh ULID (data-model.md section 3); `params` are validated against the graph version's `params` schema (DD-36). `PUT`/`DELETE` are idempotent by definition.
- **Lease fencing**: every worker write carries `lease_epoch` and the opaque `dispatcher_id` of its grant; a stale epoch is refused with `API008` (scheduler.md section 3), and a write from another worker or grant is refused ([worker route bodies](#worker-route-bodies-issue-139)).
- **Pagination**: `?limit=&cursor=`; responses carry `next_cursor`.
- **Long-running reads**: logs and events stream as newline-delimited JSON over `GET …?follow=true` (chunked); no WebSocket in MVP. Waiting for a run is the bounded `wait` option of the run read, at most `45s` per request (section 2, [bounded run-read wait](#bounded-run-read-wait-adr-0002)). The shared Python client bounds a waiting read by one total deadline of its own, on an injected clock, which the CLI and the stdio MCP process take from their test configuration: the requested `wait_timeout` capped at `45s`, or `45s` when the value is absent or does not parse, plus a fixed margin of at most 10s that covers everything outside the API's own wait (pool acquisition, connect, send, authentication, a re-check still in flight at the deadline, the final read and its transfer, and the call's follow-up reads), so that the cap plus the margin stays below the default tool-call timeout of the supported coding-agent clients ([MCP Tasks probe record, section 3](../research/mcp-tasks-probe-2026-10-19.md#3-client-support-claude-code-and-codex)). The deadline covers the whole waiting call, including the follow-up reads of the same `kora_runs` call; the client enforces it with its own cancellation scope on every transport and issues the waiting request with no shorter per-phase timeout. The client never retries a waiting read automatically and reports expiry of the deadline as a client transport failure, never as a wait outcome; the CLI or MCP boundary reports such a failure once, with no fabricated request ID. The client, the CLI and the MCP tools forward `wait` and `wait_timeout` unchecked as plain strings, so every surface that accepts the options returns the API's own refusal. Each waiting read opens its own HTTP/1.1 connection outside any bounded pool that ordinary calls draw from and closes it when the read ends, so open waiting connections are bounded by the concurrent waiting calls, each held at most until its deadline, and outstanding waits never delay or fail another call through the same client. Cancelling the caller (MCP `notifications/cancelled`, the end of the MCP session, stdio input or response stream, a CLI interrupt, or closing the client) or expiry of the deadline cancels the request. Closing the client ends its outstanding waits on both transports. A load balancer or proxy in front of the API keeps its idle and read timeouts above the cap plus the client margin, for the run read and for the `/mcp/*` endpoints, because neither needs to send bytes while it waits; a read cut there reaches the client as a transport failure, and the API wait still ends at its own deadline.
- **Versioning** (NFR-11.3): additive changes within `v1`; the OpenAPI document is published at `/api/v1/openapi.json`; the web TypeScript client is generated from it, the Python client is hand-written over the same Pydantic models and contract-tested against it, and the parity coverage test (section 7) reads it.

### Structured errors (FR-0.4)

Apply [request correlation](observability.md#4-context-and-request-correlation): each API-handled exchange returns a fresh server-generated `X-Request-ID`, ignoring caller IDs as canonical identity. New error envelopes use that same ID. Idempotency replay preserves the saved body and its original error ID exactly; the current header/log ID remains fresh and links the saved error ID as `replayed_request_id`. Shared Python and generated TypeScript clients retain both identities in safe diagnostics without changing response bodies. Success replay does not rerun the mutation; stream setup carries the current header ID. Correlation grants no authorization.

```json
{ "error": { "code": "API001", "message": "Object not found.", "location": null,
             "retryable": false, "details": {}, "request_id": "req_01J…" } }
```

Code families: `IRnnn` (IR validation), `DSLnnn` (compile), `APInnn` (request errors: `API001` not found, `API002` conflict, `API003` validation, `API004` idempotency replay mismatch, `API005` forbidden (namespace outside the token's list, missing `approve` or `platform` flag, missing `transcripts` capability), `API006` approval stale (the only code for a bound-content mismatch or a request that is no longer `pending`, current contract [api-and-agent-surface](api-and-agent-surface.md)), `API007` webhook authentication failed (bad signature, bad bearer, or a Standard Webhooks timestamp outside the tolerance window), `API008` stale lease epoch), `RTnnn` (runtime and protocol errors surfaced on attempts), `POLnnn` (policy denials recorded on attempts). The HTTP status is derived from the code; clients branch on `code`, never on prose. Compile, validate and provider findings use the [shared `Diagnostic`](diagnostics.md), separate from this outer error envelope. Its `path` is a nullable array of document segments, its `location` is an optional source file/line pair, and its `offset` is a zero-based count of Unicode code points in the decoded expression/path field ([ir.md section 7.2](ir.md#72-parser-limits-and-canonical-rendering)), never a YAML/source column or UTF-16 index. An offset is null when the exact field cannot be safely identified. Shared collection ordering, bounds and omission counts follow that contract. HTTP status, retryability and request correlation stay outside individual findings; the [error and validation sections](#error-codes-and-statuses) define the complete envelopes and code-to-status table. `kora compile` and `/validate` report the same code, path and offset for faults kora's own parser, checker and cost estimate find; a fault only the server-side binding compile finds is `IR011` at server-side validation alone (`/validate`, `/plan`, deployment, and `kora_compile`, which validates through `/validate`).

### Error codes and statuses

Every API error uses the existing structured envelope. For the API codes in this revision, outer `location` is always null; individual validation locations belong to the shared diagnostics in `details`. `request_id` follows the existing response/replay correlation contract. The table is exhaustive for this revision; reasons never change the status.

| Code | HTTP status | Meaning | Retryability |
|---|---|---|---|
| `API001` | 404 | Object absent from the authorized namespace | false |
| `API002` | 409 | Conflicting state or refused precondition | operation-specific; false unless the existing contract explicitly permits retry |
| `API003` | 422 | Invalid request, document or result evidence | false |
| `API004` | 409 | Idempotency key reused for a different semantic request | false |
| `API005` | 403 | Authenticated principal lacks required authority | false |
| `API006` | 409 | Approval content changed or request no longer pending | false; read the current request before another action |
| `API007` | 401 | Trigger authentication failed | false |
| `API008` | 409 | Stale lease epoch or dispatcher grant | false; acquire/observe current authority through its existing protocol |
| `API009` | 401 | Missing or invalid ordinary API credential | false |
| `API010` | 500 | Internal failure or bounded validation that could not complete | false, except the existing credential-issuance audit-commit failure described below |
| `API011` | 503 | Recognized transient dependency failure | true only for a read, a known pre-effect refusal or an explicit operation-specific safe retry contract |

API009 covers missing, malformed, unknown, expired and revoked bearer values and cookie-only requests to bearer-only routes. Its body is identical across these categories except the exchange's request ID: message `Authentication is required.`, location null, retryable false, details {}. Its `WWW-Authenticate` header is exactly `Bearer`, without validity or token-specific detail. API005 remains the sole forbidden code. Expected invalid-credential refusals cannot be converted into API010; unavailable authentication dependencies cannot be disguised as a bad credential or produce an anonymous principal. Webhook authentication retains API007 and its trigger-bound protocol.

API010 uses the fixed message `Internal operation failure.` and empty details; raw exception text is never a response. The credential-issuance audit-event commit failure is its sole retryability exception: API010/500 with retryable true, including an unclassified or nontransient insert failure. The issued value is withheld and discarded; a retry rechecks current authority and reacquires rather than replaying a secret. Late-holder staleness remains API008. This preserves the existing operation contract without activating a remote issuer in the first slice. API011 uses `Required service is unavailable.` and a closed, operation-defined safe reason when needed. A dependency exception alone does not prove that a mutation had no effect. Unknown commit or external-effect outcome has retryable false unless the existing operation contract supplies a safe recovery/replay path. Credential issuance retains its explicit current-authorization/reacquisition behavior and never replays a cached secret. API010/API011 failure responses do not finalize or overwrite an idempotency result. A proven pre-effect transient refusal leaves no accepted outcome or cached failure, and the caller retries with the same key under current authorization. After an uncertain commit, the route first recovers any durable accepted receipt or idempotency result and preserves its exact saved body/request ID; a failure cannot delete or replace it or authorize duplicate effects. Reads have no mutation idempotency record. The credential route remains outside response caching altogether. Existing definitive operation refusals retain their specified caching rules.

A lock acquisition timeout rolls back the complete unit and returns API002, retryable true, reason `lock_timeout`; the refusal is not stored as an idempotent response. Existing API002 reasons, including `run_backlog_full`, retain their documented retryability and never become HTTP 429. Worker result/evidence refusal codes remain as specified by their operation contracts.

### Validation envelopes

For an authenticated, syntactically valid request, `POST /namespaces/{ns}/validate` returns HTTP 200 and `{valid, errors, warnings, errors_omitted, warnings_omitted}`. Each finding is the shared Diagnostic; all collection bounds, ordering, omission counts, safe fields and exact-code-point offsets come from diagnostics.md. `valid` is true exactly when `len(errors) + errors_omitted == 0`. Warnings do not invalidate a document. The validator collects independent faults; an invalid prerequisite prevents only checks that depend on it. Accepted document findings are preserved: an unavailable harness remains IR018, an unsupported/inconsistent saved type or behavior binding remains IR022, and installation-feature refusal retains the accepted code precedence (including IR028 when #140 applies). These return the normal invalid collection, not a service failure. Only a recognized transient failure of an otherwise applicable validation dependency maps to API011; an unexpected provider fault maps to API010. Neither yields a partial collection claiming validity.

| Validation outcome | Validate/deploy result | Offline compiler result |
|---|---|---|
| Established schema/semantic/installation finding | HTTP200 collection / API003 collection | Shared diagnostics, preserving existing IR/DSL codes |
| Conforming provider returns findings | Collect and safely rebase findings | Same shared findings |
| Applicable dependency temporarily unavailable | API011/503, safe failure, no version | CLT005 with reason dependency_unavailable |
| Provider diagnostics_limit or aggregate DiagnosticCollectionError/count_overflow at a count above 2^53−1 | API010/500, fixed message, retryable false, empty details; discard partial collection, no version | CLT005 with reason diagnostics_limit or diagnostic_count_limit |
| Unexpected provider fault | API010/500, fixed message, retryable false, empty details; no normal collection/version | CLT005 with reason provider_failure |

Within an API-handled exchange, malformed JSON/encoding or an exceeded request/document byte limit returns API003 using the API envelope, including framework validation failures. This does not claim that a server can return an application envelope before it has parsed a valid HTTP exchange. Document schema/semantic faults inside a valid validate request instead use the HTTP-200 finding collection. A refused deployment returns API003 with `details: {errors, warnings, errors_omitted, warnings_omitted}` using the same collection; it creates no graph version. Operation-specific non-document refusals preserve their existing error code/details. Compiler findings and retained RT/POL attempt failures are not alternate HTTP status codes.

### Authorization precedence

On a bearer API route, authenticate before choosing a principal kind or exposing scoped state. Reject a valid principal kind that the operation does not accept with API005. Check an explicitly named namespace against the token before looking it up: outside the list is API005 whether or not it exists. All object lookup and projection is scoped to authorized namespaces. An absent object there, including an identifier that exists elsewhere, is API001 without revealing foreign scope. Then check the operation's flags/capabilities before effect-specific grant/precondition work. This does not weaken existing pre-body/pre-upload authorization, authorization rechecks under locks, current wait/stream authorization, approval freshness or late credential-delivery checks.

Wrong worker ownership is API005; stale epoch or dispatcher is API008 after ordinary authentication and namespace/object checks. Service rights are never inferred from user flags. A mixed inspection/history/diff response without transcripts retains permitted metadata with `content_access: forbidden` and omits protected content; a transcript-only route returns API005. The approval-list foreign/absent run filter remains an empty list under its existing contract. No client or MCP wrapper duplicates the API's permission decisions.

### Client and local-validation failures

A local transport failure is distinguishable from a completed API response and has no invented HTTP status or server request ID. The shared Python client constructs transport errors CLT001–CLT004; the CLI/MCP boundary renders a typed offline validation failure as CLT005 and a local artifact-download failure as CLT006. These use `{error: {origin: "client", code, message, location: null, retryable: false, details: {reason, outcome, recovery_hint}, request_id: null}}`. An admitted artifact-download local failure additionally carries the bounded cleanup state defined below. Only the following code/reason combinations are emitted; messages are fixed. The generated TypeScript client's adapter preserves the same server/client distinction without changing API bodies. The compiler/validator library never imports a client or transport model to construct this boundary record.

| Code | Fixed message | Allowed reasons |
|---|---|---|
| `CLT001` | `The API connection could not be established.` | `connection`, `tls`, `pool`, `destination_policy`, `proxy_policy` |
| `CLT002` | `The API request deadline expired.` | `deadline` |
| `CLT003` | `The API response was invalid.` | `status_envelope`, `json`, `schema`, `response_limit` |
| `CLT004` | `The API response stream ended unexpectedly.` | `stream` |
| `CLT005` | `Local validation could not complete.` | `diagnostics_limit`, `diagnostic_count_limit`, `provider_failure`, `dependency_unavailable` |
| `CLT006` | `The local artifact download could not complete.` | `download_destination_rejected`, `download_capacity_exhausted`, `filesystem`, `integrity`, `cleanup` |

`recovery_hint` is fixed advisory text, never execution authority or proof of absent effect. It contains no request-derived values. For any `outcome: unknown`, it is `Inspect authoritative state and any remaining local output before retrying explicitly.` For proven `not_sent`, CLT001 uses `Check connection settings without weakening credential transport policy.`, CLT005 uses `Repair validation or its dependency before compiling again.`, CLT006 uses `Check download settings and local cleanup state before trying again.`, and other codes use `Check the request and client/API contract before trying again explicitly.` Clients branch on code/reason/outcome and existing operation authority, never on this prose. No hint authorizes automatic mutation/wait retry, a new logical action or relaxed TLS/proxy/destination checks. The local-error conformance cases assert these exact safe values and every applicable code/reason/outcome, including the download deadline and retained-cleanup paths.

CLT005 reports failure of offline compile/validation before its API validation phase, with outcome not_sent and request_id null. That outcome describes API request delivery only; importing graph code remains execution in the author's own environment and is not promised to be side-effect-free. Established DSL import/construction diagnostics retain their current meanings. Other codes use outcome not_sent only when the transport proves that no authenticated request could have reached the API, otherwise unknown. In particular, disconnect or deadline after sending is not proof that a mutation failed. No URL, bearer, raw body, arbitrary header or exception text enters this local record. A valid server request ID observed before a transfer failure is retained only as separate safe diagnostic correlation metadata, never placed in this client error's `request_id` or invented when absent. A completed valid API error is forwarded unchanged. A future additive API code that still satisfies the envelope contract remains a server error; an older client does not turn it into a transport failure solely because the code is new.

The shared client performs no automatic mutation or waiting-read retry. Explicit retry follows the operation's idempotency/current-authority contract. Deadline, invalid response, refusal and cancellation release the response, connection and owned tasks before returning; closing the client ends outstanding calls. Caller cancellation follows the existing CLI/MCP cancellation contract rather than fabricating an API timeout. CLI `--json` prints one local error object and exits nonzero; an interrupt of a waiting read still exits 130 with nothing on stdout. MCP emits one `isError` result carrying the local record, with diagnostics on stderr for stdio and no result after cancellation. A local NDJSON parsing/transport failure emits one client terminal record if output remains writable, closes the stream and exits nonzero; earlier complete validated records remain valid. A validated server terminal is instead forwarded exactly once unchanged and never recast as or followed by a client failure. Output failure follows the existing stdout-failure contract and never recursively prints an error to the failed output.

The #141 credential/destination policy remains the shared client's authority. Missing MCP configuration is the content-free startup error under that contract, before any tool/API request; it is not fabricated as an API009 response. Artifact downloads retain #140's exclusive destination, admission, integrity and partial-file cleanup contract. CLT006 classifies locally rejected destinations, exhausted download slots, filesystem failure, size/digest mismatch and failed cleanup. Transport/deadline/response failures retain CLT001–CLT004. Local download failures carry `details.download_cleanup: {temporary: "none" | "removed" | "retained" | "unknown", destination: "not_created" | "published" | "unknown"}`. Before admission both are none/not_created. States report only proven facts, including an uncertain publication; no path, filename or unrestricted exception text is added. The API-delivery outcome covers every API request in that call: not_sent requires proof that none could have reached the API; otherwise unknown. It says nothing about local file effects. A download receipt is returned only after verified local completion. Unsettled cleanup remains charged to #140's process-wide admission limit; it cannot be reported as released or free a slot while owned resources remain. This specific retained-cleanup rule qualifies ordinary release-before-return wording. Completed API refusals stay verbatim; a concurrent cleanup failure reports its bounded state separately through safe boundary diagnostics without changing that API error. Cancellation/EOF/shutdown likewise emits no cancelled tool result and exposes cleanup state only through safe diagnostics. The implementing download issue registers these fields and proves destination races, full/failed filesystems, integrity errors, refused requests, cancellation and cleanup-failure accounting before activation.

### Follow-stream authorization and failure framing

A follow stream authenticates before headers. A submission unit is one bounded JSON record, or one opaque raw byte chunk for raw follow. For this check the API sets the trusted internal RequestInfo.requires_current_authority flag, bypassing stale cached authority or requiring proven invalidation; inability to validate fresh fails closed as API011. The successful current-credential/namespace/content-capability check is the authorization decision point for the next submission unit handed to the transport. A JSON record is at most 4 MiB of compact UTF-8 JSON including its newline; this protocol bound covers the accepted 4 MB request payload plus bounded event metadata and is not a measured performance budget. The application has at most one such submission unit submitted but not drained and does not queue further protected records behind it. It releases the check's database resources before network delivery. During backpressure it waits for that one submitted unit rather than authorizing or queuing another; an already authorized in-flight unit may arrive after a later revocation, up to this stated byte bound. Bytes already handed to the transport cannot be retracted. Before another submission unit is submitted, a new successful check is required; a rejected check discards unsent protected content and permits only the content-free structured terminal or aborts raw transfer. While idle with no unit in flight, authority is checked at the same one-second interval as the bounded run-read wait. A dependency failure stops further content rather than continuing with stale authority. A stored record that cannot fit the protocol bound causes a safe API010 terminal, never silent truncation or a fabricated normal record. Deployment/server proxy buffering must be finite and its additional in-flight bytes measured/documented before implementation readiness; the application bound is not a claim that external intermediaries can retract bytes. Disconnect, cancellation and shutdown release timers, subscriptions, buffers and checkouts; no recheck emits INFO diagnostics.

Before stream headers, ordinary refusal uses the code-to-status table. After a successful NDJSON stream has begun, failure is a terminal `{stream_error: {code, message, location, retryable, details, request_id}}` record followed by closure. Its API code has the same meaning as an ordinary API error, but the record is embedded stream content, not a new HTTP response or a changed status for the already-sent headers. The request ID is the established stream exchange ID. The NDJSON union has normal endpoint records, a server terminal with only stream_error, or a client terminal using the already-defined error object with origin client. Terminal discriminants are reserved by the endpoint's discriminated record schemas. A server terminal is at most 1 MiB plus 4096 bytes, covering the shared diagnostic-data cap plus its bounded envelope; it is emitted once, forwarded unchanged and completes the failure without an added/recast CLT record after stream closure. Only a local parsing/framing/transport failure emits a client terminal. Clients publish complete schema-validated records only and discard an incomplete input tail. Untrusted nested content or raw message strings are never parsed as control frames. If required terminal delivery fails, abort the transfer; do not mark normal completion. Earlier complete records remain valid. Clients terminate successfully only at the endpoint's normal completion and surface a server terminal as failure while preserving its code and exchange ID.

Within API v1, readers validate required known fields/types, record byte limits and control discriminants while tolerating permitted additive fields and documented extension variants. A new optional normal-record field alone never becomes CLT003. Unknown fields remain bounded opaque data, are preserved when forwarding a completed API response, and are never rendered as trusted markup, interpreted as control or used for authority. Terminal containers keep their one reserved top-level discriminator (`stream_error` for server, `error` for local); producers never add a reserved control key to a normal record, and readers reject conflicting/mixed control discriminants. Additive fields inside a server terminal envelope follow ordinary API-envelope compatibility, including unknown API codes; they do not turn it into a normal record or a local error. The implementing client contract tests run an older reader against permitted new optional fields/extension variants, reject malformed known fields and reserved-control collisions, and prove safe UI handling of unknown data.

An opaque raw-transcript transfer has no in-band JSON error frame. For raw follow, each opaque chunk is at most 4 MiB of raw bytes with no framing added. The same trusted current-authority check, single submitted-unit backpressure bound, no queued protected successor, idle recheck and finite intermediary-buffer requirements apply to each chunk. Rejected or unavailable fresh authority discards unsent bytes and aborts the transfer; it never emits a JSON terminal into raw output. After headers, the server aborts the transfer on failure and emits its one safe diagnostic; the shared client reports an incomplete transfer as CLT004. It never appends JSON or diagnostic prose to raw bytes. Human/raw CLI output preserves already-written bytes, emits a safe stderr failure and exits nonzero. Raw and `--json` modes are mutually exclusive and rejected as a CLI usage error before a request; structured log/event `--json` streaming uses the NDJSON framing above. A successful HTTP raw transfer requires its declared Content-Length to be satisfied or its explicit chunked/HTTP-stream completion framing; connection-close-delimited success is not permitted. A server failure aborts before that successful completion, so the client detects truncation. The in-process ASGI transport likewise distinguishes normal body completion from an aborted body. Transfer completion describes delivery of the available retained bytes, not proof that the original execution transcript is complete; its saved truncation/availability facts remain authoritative.

Future test `test_follow_stream_revalidates_authority` covers revoked/expired credentials, removed namespace/transcript rights, idle rechecks, JSON-record and raw-chunk capture/check/submit barriers, authority loss under raw backpressure, dependency failure, real disconnect/cancellation/shutdown and bounded resource release on both databases. `test_client_distinguishes_transport_and_api_failures` additionally covers normal versus aborted raw completion, NDJSON terminal errors, untrusted content resembling control frames, older-reader/additive-field compatibility and reserved-control collisions, missing or valid safe header correlation, unknown mutation outcome and partial-output preservation. API11 with retained-content12 owns follow enforcement; shared client/CLI11 and console activation own consumer cases. All are pending implementation.

The metadata API authenticates first and enforces namespace membership and object scoping. The deferred cookie-to-bearer bridge remains undecided and cannot add an implicit proxy or credential source.

### Probes and installation metrics

GET /healthz is anonymous, read-only and returns HTTP 200 with {"status":"ok"} while its serving process can answer. GET /readyz is anonymous and returns HTTP 200 with {"status":"ready"} when the metadata database is reachable and recovery is complete, otherwise HTTP 503 with {"status":"not_ready"}. Optional or malformed credentials do not change these fixed probe outcomes. Their fixed response shapes are explicit infrastructure exceptions to the ordinary API error envelope. No dependency names, DSNs, exception text, configuration, namespaces or object IDs are returned. Probes never repair state. Diagnostic sink or external integration degradation alone does not fail core readiness. Bounded DB checks and cleanup are required. The availability bit and anonymous dependency-check load remain explicit residuals.

#### Metrics authority

GET /metrics requires an ordinary personal Bearer credential with platform=true and grants covering every currently existing namespace. Missing/malformed/unknown/expired/revoked credentials produce API009; valid service credentials, missing platform or incomplete namespace coverage produce API005 without naming or counting missing namespaces. Cookies do not authenticate this bearer-only route. Neither approve nor transcripts is required for the content-free catalog. A valid platform credential also qualifies when the installation has no namespaces; the empty set is an explicit grant case.

This is a NEW installation-wide observation grant and therefore amends ADR-0011, the API/authentication contracts and the threat model. It includes the reviewed operational metric catalog's global process/worker/runtime aggregates and retained historical aggregates irrespective of the contributing namespace's lifetime. It grants no additional mutation, transcript, diagnostic-log or session-content authority. Fixed finite metric names/label dimensions remain mandatory; no credential or untrusted content labels become permissible.

A dedicated scraper personal token should omit approve and transcripts. It still possesses ordinary namespace operations and platform mutation powers: this proposal does not create a read-only credential. Do not silently reuse the standalone CLI token. Scraper grant updates and explicit token rotation belong to the operator/credential implementation owner; no automatic wildcard or future-namespace grant follows from this rule. New namespaces outside its grants stop the entire scrape until grant updates; success/refusal exposes the one-bit complete-coverage predicate. These authority, availability and disclosure tradeoffs accompany the installation-observer grant.

#### Freshness and complete projection

Authenticate current credential state and authorize at a defined linearization point after bounded payload capture and before emitting metric bytes. Revocation, expiry, platform removal and namespace-grant removal committed before that point invalidate the request; there is no promise to retract bytes after delivery begins. A cached previous principal or successful response cannot authorize a later request.

The captured payload and all collectors/caches, including independent workers/processes and retained cumulative series, must belong to the same installation/namespace generation used by the final authorization check, or an explicitly equivalent fail-closed invariant. A database snapshot alone is insufficient. A namespace created and removed while metrics retain a contribution must not bypass this check through set equality. Historical contributions are within the explicit installation-observer authority above, but every current producer/cached payload still participates in the generation/freshness contract. If consistency cannot be established, return a safe API011 failure before any metric bytes; never a successful partial scrape. Do not hold a DB transaction across network transfer. The implementation plan chooses concrete bounded capture, generation coordination, invalidation and release mechanics and proves them on both databases before code.

The final credential check sets the trusted internal `RequestInfo.requires_current_authority=True`; providers must bypass stale authority, prove relevant invalidation or refuse with `authentication_unavailable` before metric bytes.

**Bearer destination policy** (#141). The shared client accepts plain HTTP only when the URL host is literal `127.0.0.1`, using a direct connection that bypasses ambient proxies independently of `NO_PROXY`; an explicit proxy is refused if direct delivery cannot be preserved. Every other destination requires HTTPS with certificate-chain and requested-hostname verification before an authenticated HTTP request is sent. Verification cannot be disabled; a failed handshake never causes a cleartext or unverified retry. The client never forwards a bearer across origins on redirect, where an origin includes scheme, host and effective port. This does not alter in-process ASGI authentication. Standalone listener and first-token issuance follow [scheduler section 10](scheduler.md#10-standalone-sqlite-versus-postgres).

### Bounded metadata and selected content (issue #227)

The normative [bounded read projections](bounded-read-projections.md) catalogue defines affected route fields, exact client selectors, 100-item/1-MiB ordinary metadata responses, the approval-list exception, explicit owner-pinned content representations, finite query/comparison budgets and implementation activation. Metadata contains descriptors and bounded identities, never implicit saved payload/summary bodies or unbounded history arrays. Full originals retain their existing access and availability. Pagination, counts, live membership and refusal are explicit. The API owns aggregates and advisory mutation previews; every client forwards the same operations. Worker report/upload routes and worker-only retained grant transfer keep their separate contracts.

### Signal routes ([scheduler.md section 12](scheduler.md#12-execution-backend-boundary-nfr-55))

A route that receives a start, a direct approval response, a cancellation, a manual retry, a reconciliation request, a worker report or a namespace policy write validates it and applies its transition through the shared transition functions before it responds. It returns that transition's result or refusal; a refusal changes no requested state, though it may commit what the specification defines for it, such as `approval.responded {applied: false}`, a cached refusal response or an expiry the request observed. No route runs a scheduler pass. Authentication, through its own short read, body consumption, storage writes and validation hooks finish before the transaction's connection is checked out. The transaction unit is shielded from request cancellation and client disconnect and always ends in commit or rollback, releasing the connection, the locks and, on SQLite, the writer. On PostgreSQL the wake-up `NOTIFY` is issued inside the transaction and delivered at commit; in standalone the in-process event is sent after commit. On PostgreSQL `lock_timeout` bounds each lock acquisition; on expiry the unit rolls back and the route returns a retryable structured error, never cached as an idempotent response, whose code the error-model work item of [#127](https://github.com/realkarych/kora/issues/127) assigns. Credential issuance checks lease, purpose and digests in a short locked transaction, calls the issuer with no transaction held, then inserts `vcs.credential_issued` in a second transaction that takes no lock, with outcome `withheld` and `API008` when a lock-free read finds the holder went stale during the call, and returns the value only after that commit with outcome `issued`; the whole sequence is shielded from cancellation and disconnect. An inbound event is authenticated, deduplicated and persisted; matching it to waits is the scheduler's.

### Admission state and bounded starts (ADR-0020)

The authoritative predicates and state-by-limit table are [data-model section 13](data-model.md#13-run-acceptance-and-execution-capacity-adr-0020); ordering and locks are scheduler section 6. Existing namespace/graph/run/node/target reads expose applicable `admission` fields: run `outstanding` and `execution_reserved` booleans; limit observations `{scope, limit_name, limit, used, source_graph_version_id?, observed_at}`; target hold and blockers; `recheck_at` and `next_action`. Scope identifies kind and resource ID. Shared graph counts cover all versions, while `source_graph_version_id` names the live cap source, distinct from the run's execution version. An omitted graph cap is explicit as no additional cap, not fabricated zero capacity.

An admission wait's bounded reason retains its kind (`execution_recovery`, `target_held`, `concurrency_limit`, `daily_budget`) and names exact recovery/target blocker counts and at most 20 sampled IDs with the matching paginated read reference, or the limiting scope/name/limit/usage. Among recovery/target/concurrency reasons, priority is recovery, target, then concurrency scopes; budget-check ordering remains scheduler section 4's separate contract; it does not alter lock order or acquire a reservation before all checks pass. Large blocker sets use `{count, ids, truncated, read_ref}` with a bounded sample and an existing paginated read/filter reference; a sample is never presented as complete. `recheck_at` is the current wait's next recheck, not a promised start time. Next action distinguishes automatic recheck/wait for capacity or holder, retrying a refused start, and operator recovery with existing permissions. No queue-position, priority or starvation guarantee is implied.

Authenticate and check the envelope, then find a durable accepted start receipt and compare its original semantic request digest before selecting today's graph version or validating current params/target/quota. Matching replay returns the saved accepted run or no-run overlap-skip, including after response loss, deployment, quota lowering or 24-hour cache expiry. A changed request is `API004`. The shared `StartOutcome` is `{outcome: accepted, run_id, graph_version_id, status: pending}` or `{outcome: skipped, reason: overlap, run_id: null}`. It is the saved acceptance snapshot, not a live run-status read; matching replay returns it unchanged. A new start validates the chosen version/params and atomically commits its pending run and receipt, or a durable skip outcome. `skipped` is an operation outcome, never a new run status. A webhook start is not acknowledged as an unconverted event. Existing wait-event delivery remains unchanged.

Full outstanding quota returns HTTP 409 with `code: API002`, `retryable: true`, `details: {reason: run_backlog_full, scope: {kind: namespace, id: <ns>}, limit_name: max_pending_runs, limit, used, next_action: retry_start}`. It accepts no run/pending trigger event and consumes no accepted delivery key or permanent cached response. Retry may succeed after space returns. Settled-failed retry performs this check before clearing nodes, artifacts, waits or approvals; an already outstanding run contributes no second credit. Rerun retains all original recovery refusals before new acceptance. Cancellation, observation and recovery remain available when full.

Internal cron/start-sensor/graph-triggered saturation records `trigger.rejected`, advances its occurrence cursor and creates no hidden retry queue or catch-up. Existing trigger-binding reads show the last outcome/reason/time/quota snapshot; metrics count rejected starts. Accepted/skipped replay remains stable after an old run ends. Namespace policy lowering retains existing accepted work and physical/target reservations; it blocks positive additions until room exists. Incoming allow can create several target holders; an unheld defer candidate remains blocked until every other holder releases; an already acquired hold is not reacquired.

CLI JSON and existing MCP reference/inspection/trigger/admin responses forward these same API fields and errors through existing operations. kora_reference maps GET namespace policy/admission and GET graph triggers under ordinary namespace read authorization, so non-platform callers can inspect rejected occurrences and quota usage. Human-readable views distinguish accepted work, physical capacity and target ownership. The console displays the observations and saturation refusal read-only around its existing trigger/retry actions; no endpoint, command, tool or fifth console mutation is added. Approval success only opens readiness, never guarantees immediate downstream execution.

### Bounded run-read wait (ADR-0002)

Tools and commands that start work return its outcome at once; waiting for a run is an option of the existing run read, not a new operation and not a blocking start (ADR-0002, amended 2026-10-19; evidence in the [MCP Tasks probe record](../research/mcp-tasks-probe-2026-10-19.md)). `GET /namespaces/{ns}/runs/{run}?wait=finished|needs_person[&wait_timeout=<duration>]` takes `wait_timeout` as a duration string in the grammar of every other kora duration (the [NodeLimits.timeout property of the IR schema](ir.schema.json#/$defs/NodeLimits/properties/timeout)), positive and at most `45s`; the API applies `45s` when `wait` is given, and the OpenAPI document declares no schema default. The cap is a constant of this contract that an installation cannot raise. `wait_timeout` without `wait`, an unknown condition, a malformed duration or one above `45s`, and either option on the list operation `GET /runs` are refused with the API's own `API003` envelope, never a framework default response. A read without `wait` is unchanged, returns `wait: null` and never blocks.

The conditions are fixed. `finished` holds when the run status is `succeeded`, `failed` or `cancelled`; it tests status only, so unresolved execution recovery, retained target holds and outstanding capacity remain reported by the `recovery_required` and `admission` fields of the same view (data-model section 13 calls a run *settled* only when they are released). `needs_person` holds when the run is `pending` or `running` and has at least one approval request with status `pending`. Unlike the console's run-level "waiting for you", which requires all live work in the run to wait for a person, it holds as soon as any request is pending; operator recovery is not `needs_person`. The wait ends at the first of: the condition holds (`ended_by: condition`); for `needs_person`, the run finishes (`run_finished`); the deadline passes (`timeout`); the API process begins shutdown (`shutdown`). A condition that already holds, and a `needs_person` wait on a run that has already finished, answer at once with `waited_ms` 0. A wait requested after shutdown has begun answers at once with `ended_by: shutdown`; the process accepts no new connections by then, and every `shutdown` ending closes its connection (`Connection: close`), so the caller's next request reaches another process or fails as a transport failure. `ended_by` records the re-check that ended the wait and `satisfied` the final snapshot, so the two can disagree when the run changes between them. When the read at the deadline finds the condition, or for `needs_person` a finished run, the ending is `condition` or `run_finished`, not `timeout`. The condition is sampled at re-checks, so a transient state between two re-checks can be missed; the run timeline is the complete history.

Every ending with a `wait` result is HTTP 200 with the ordinary run view plus `wait: {condition, satisfied, ended_by, waited_ms, pending_approvals?}`. The condition and the view are read in one read snapshot. `satisfied` states whether the named condition holds in that view; `waited_ms` runs from the start of the wait to the final read on the injected clock. For `needs_person`, `pending_approvals` is the run's pending requests in the large-set shape `{count, ids, truncated, read_ref}` of section 2's admission projection, with `GET /namespaces/{ns}/approvals?status=pending&run=<run>` as the read reference; a sample is never presented as complete. A reached cap is a result, not an error: a caller that wants to keep waiting reads again.

Authentication and authorization are those of the plain read and complete before the wait begins. A request the plain read would refuse, unauthenticated or for a namespace outside the token's list, is refused at once, before any condition is evaluated, with latency independent of the addressed run's state; a run id of another namespace is `API001`, the same as a run that does not exist. Every re-check revalidates the credential through the configured authentication protocol ([protocols section 10](protocols.md#10-authentication-fr-124-nfr-44)) and reads through the same namespace-scoped query: for the built-in token check this is part of the same short read, and a provider whose validation is not a bounded local read runs it outside that read and caches its result per credential, shared by every wait of that credential, for at most one interval. A token revoked or expired, or a namespace removed from the token's list, ends the wait within one interval for the built-in check, and within two for such a caching provider, with the error the plain read would return at that moment, never with the view or the `wait` object. The final view is composed under the token's current capabilities exactly as a plain read issued at that moment, so a change to `transcripts` affects only the content-bearing projections that the plain read already gates.

The API fixes the deadline from an injected monotonic clock when the wait starts. Re-checks run at a fixed 1 s interval with at most one in flight per wait; at the deadline no new re-check starts, a re-check still in flight finishes, and the final read follows. Each re-check evaluates only the credential and the condition, the run status and whether a `pending` approval request of the run exists, as one short index-backed read: the existence check joins approval requests to the run's node instances, and the implementing change declares that index. A re-check never composes the run view, takes the run or a scope lock or opens a write transaction, and no database connection is held between re-checks; on SQLite it holds the single-connection lock only for that read ([scheduler section 10](scheduler.md#10-standalone-sqlite-versus-postgres)). An implementation may serve all waits of a process with one batched re-check per interval, or wake a wait early from an in-process notification of a change to that run's status or approval requests, coalesced to at most one extra re-check per wait per interval; the interval remains the latency guarantee. The run view is composed once, after the wait ends, and the response is sent no later than the deadline plus one re-check and one ordinary read. Caller departure, a closed connection observed at the next re-check or cancellation of the calling task on the in-process transport, ends the wait without the final read and releases its timer and any database checkout. When the process begins shutdown, every outstanding wait ends within one interval with `ended_by: shutdown`, independently of the application lifespan, so held waits never delay process exit beyond that interval plus the final read. A database error during a re-check is the ordinary structured error, with no silent retry and no stale view. There is no limit on concurrent waits (DD-6, section 8): a wait holds one request task, its connection, one timer and its registrations (the early-wake subscription, membership of a batched re-check and the shutdown registry), all released when it ends, and no database resources between re-checks.

Re-checks emit no INFO diagnostics ([observability section 3](observability.md#3-levels-and-emission-ownership)); each wait ends with one DEBUG completion diagnostic carrying `condition`, `ending`, `waited_ms` and, when a final read happened, `satisfied` as typed fields, never the query string. `ending` is the `ended_by` value, or for a wait that ends without a `wait` result `departed` (caller departure) or `error` (authorization loss or a database error); these two are not `ended_by` values. `/metrics` exposes a gauge of outstanding waits and a counter of endings labelled by condition and `ending`. The accepted retry transaction moves a `failed` run back to `running` before it responds (data-model section 4), so a wait that follows `kora_retry` cannot observe the pre-retry status. A replayed `StartOutcome` remains the saved acceptance snapshot; the wait reads live state.

`kora run <run> [--wait finished|needs_person] [--wait-timeout <duration>]` makes one bounded call with no repeat loop (section 3), and MCP `kora_runs` forwards the same options (section 4); `kora approvals --run` and `kora_approvals` forward the `run=` filter of the approvals list. Operation coverage in section 7 is unchanged because no operation is added; schema coverage includes the `wait` field and the `run` filter, the skill reference carries the examples of section 7 item 3, and the named contracts below prove that the clients forward the options.

Performance and resource-lifetime obligations are pending implementation. They are owned by the issue that first implements this read, the shared client's waiting read, `kora run --wait` and the `kora_runs` wait, under the first-slice implementation plan ([issue #127](https://github.com/realkarych/kora/issues/127)), and activate with the first implementation of `GET /namespaces/{ns}/runs/{run}?wait=`. They are:

### Historical execution records (ADR-0018)

Existing graph-version reads expose the saved execution-contract identity, exact declared/resolved definitions and `execution_contract.retry_policies`; they never fill omissions from current defaults. Existing node/attempt metadata exposes `record_version`, the immutable input-manifest descriptor, request digest/availability, recorded execution-policy identity and namespace revision, and actual observed checkout/image/harness/resource/strategy facts with their source/time. Unobserved values are `unknown`, an attempt that never sealed a request is `not_recorded`, and missing or expired bytes are explicit. A schema/behavior descriptor names required semantics, not an archived runnable environment.

`kora node`, `kora diff`, MCP `kora_inspect` and the existing console attempts/diff views use these API projections. Add no curated tool and keep the four console mutations. Diff compares saved request/config/feedback and produced artifacts, not current `consumed_versions`, today's registry/plugin results or a newly rendered prompt. `resolved_config_digest` covers config; the request digest also binds policy, exact inputs and logical execution intent. Different availability is reported per side and field; missing content is never an empty/equal value or an invented JSON Patch. A missing actual identity is not inferred from its declared expectation.

All by-id and derived reads check namespace access. Full request text/feedback and any equivalent config/summary/diff projection require namespace `transcripts`; without it return permitted IDs, policy/contract metadata, digest and availability with `content_access = forbidden`, omitting content and content-derived differences. Content authorization is checked before loading either side. A forbidden view is distinct from expired or not-recorded data. Other artifact payloads retain their existing namespace access rules; copying protected request text into a response does not change its required capability. Internal worker reads remain governed by their runtime/namespace/current-lease reporting permissions. Content-addressed deduplication never grants cross-namespace/attempt access by a known digest.

Use existing attempt reporting to save the request, not a new user mutation. `POST /attempts/{att}/transition` accepts a record-only `seal_request` payload `{body_or_upload_ref, expected_policy_revision}` without changing attempt status. Large request bodies use the existing multipart upload path with `payload_kind = execution_request`; the uploaded reference is bound to the same namespace/attempt and is not a node output. The API parses the nonsecret projection, checks exact input/contract and equality of the node's retry policies with the saved graph-version map, the engine-selected `price_table_id` and complete revision, and current execute/result authority, checks current policy revision/capabilities, computes the canonical request/config digests and commits its descriptor/policy once. Policy revision mismatch is `API002` (`policy_revision_changed`) with the current revision; changed content after sealing is `API002` (`execution_request_conflict`); malformed/secret-bearing fields are `API003`; stale epoch is `API008`. After current namespace/service/lease authorization, an already sealed matching request returns its recorded descriptor read-only before any comparison with today's policy revision, even if policy or desired state changed after response loss; different content conflicts. Only first sealing requires current execute/result authority and policy/capability checks. A read-only replay grants no renewed effect rights. Request body and stored policy must be identical to the composed values the API validates; caller-supplied policy or price values are not authority. The price revision was pinned at attempt creation; claim, seal replay and recovery never select current prices. Request digests bind its id, normalization version and exact values, including missing prices. Durable bytes and this commit precede workspace allocation/preparation. A storage upload alone grants no execution permission.

Manual retry first checks persistent run/ancestor deadlines and the target wrapper's own deadline, without treating the previous physical attempt's expired node clock as a prohibition. An expired persistent scope returns `API002`, `retryable: false`, `details.reason: deadline_expired`, scope kind/id, deadline and rerun guidance before quota/clear mutations (ADR-0022). It then checks the sources required by the selected new attempt; `API002` with `{reason: execution_inputs_unavailable, inputs: [{id, state}]}` identifies missing/expired required bytes before new effects. A fresh retry need not have its predecessor's entire historical prompt if it consumes none of it. An accepted new attempt can bind new upstream versions; it never changes the old history. Existing recovery barriers and rerun rules still apply. Internal failure to obtain a required saved input or compatible execution/type behavior is structured `config_error`, not a placeholder or current-value fallback. The future acceptance matrix is in [data-model section 11.4](data-model.md#114-future-acceptance-contracts).

Bodies are closed models in `kora.models`; the outcome and evidence types are in `kora.protocols` ([protocols.md section 2](protocols.md#2-runtime-fr-81)). Unknown fields are `API003`. The authorization rows of these routes and their codes land with [issue #135](https://github.com/realkarych/kora/issues/135).

**The terminal report.** `POST /attempts/{att}/transition` with `to: finishing` carries the attempt's one write-once `TerminalReport`:

| outcome | from | authority | runtime evidence |
|---|---|---|---|
| `succeeded` | `running` | result authority (`desired_state = run`, current attempt, `mode = execute`), the deadline and sticky-expiry guard of [data-model.md section 15.2](data-model.md#152-sticky-expiry-and-current-result-authority), and every earlier grant closed | the runner's normal-completion quiescence record or a `TerminationReceipt` |
| `failed {error_class, error}`, `error` a closed model `{code, message?, details?}` of at most 16 KiB | `claimed`, `submitted`, `running` | the same as `succeeded`; `failed {timeout}` needs no result authority once the attempt's own deadline has passed | the quiescence record when the runner's lifecycle ended; otherwise a `TerminationReceipt` |
| `cancelled` | `claimed`, `submitted`, `running` | a current grant of either mode, under `desired_state = cancel`, a stop request, supersession or any expired deadline latch | a `TerminationReceipt` |
| `lost` | `claimed`, `submitted`, `running` | any current grant of either mode on an attempt with `desired_state = run`, no stop request and no supersession, once it holds a `TerminationReceipt`; refused under cancel intent, which reports `cancelled` | a `TerminationReceipt` and a `lost_reason`: `execution_gone`, `checkpoint_missing` or `result_unrecoverable` |

- **Refusals.** An outcome sent from a status outside its `from` column is `API003`. A `succeeded` or `failed` report while an earlier grant is open is `API002` `earlier_dispatch_open`. A result report under cancel intent keeps the existing response, `desired_state: cancel`. A `succeeded` or `failed` report must carry a settled publication outcome (`completed`, `failed`, `not_dispatched` or `not_applicable`); with `unknown` it is `API002` `publication_unsettled`, and the worker keeps its execute grant and reconciles. A `cancelled` or `lost` report may carry `unknown`, which read-only reconciliation under a recovery grant then settles.
- **Write-once.** The recorded report (`attempt.outcome`: the outcome, `error_class`, `error` and `lost_reason`) never changes, and completion records the status and class it applies separately. An identical replay (same attempt, grant, report and evidence equal to what is recorded) returns the recorded `{status, desired_state}` and writes nothing; any other report is `API002` `outcome_conflict`.
- **Shape.** `error_class` and `error` are present exactly when the outcome is `failed`, and `lost_reason` exactly when it is `lost`; `cancelled` and `lost` carry a `TerminationReceipt` and never a `NormalCompletionQuiescence`; every terminal report carries a `publication` outcome. A report that breaks one of these is `API003`.
- **Who may report what.** The worker may report `harness_error`, `command_failed`, `timeout`, `events_exhausted`, `budget_exhausted`, `artifact_invalid`, `stalled`, `protected_path_modified`, `secret_leak`, `provider_limited`, `integrity_error`, `infrastructure` and `config_error`. `attempt_failed`, `approval_rejected`, `approval_expired`, `candidate_moved`, `wait_expired` and `cancelled`, which is an outcome and never a class, are reserved to the control plane: reporting one is `API003`. A command exit outside `success_exit_codes` is `failed {command_failed}` ([ir.md section 3](ir.md#3-nodes)). Runner stop causes map to classes through the `RunnerOutcome` cause table ([protocols.md section 3](protocols.md#3-harness-adapter-fr-21-fr-33-fr-66-fr-91-dd-27)). From `claimed`, a result outcome is `failed` with `config_error` (a refused `seal_request` or `execution_inputs_unavailable`, data-model.md section 11.3) or `integrity_error` (a resource digest mismatch before handoff); a deadline that passes before submit follows the timeout rule of scheduler pass 8.
- **Binding the evidence.** Every item is checked under the run lock, with one bounded batched lookup of only the submitted dispatcher/epoch tuples; no whole-history grant query or per-item lookup is allowed. Any failure refuses the whole request with `API003` `evidence_unbound`, the item's request index and dispatcher/epoch tuple, and records nothing. The runtime record names this attempt and its immutable original domain. Each dispatcher item matches an `attempt_dispatcher` row on its full tuple: `attempt_id`; `execution_domain_id`, equal to both the row's and the original domain; `dispatcher_id`; `worker_incarnation_id` against `incarnation_id` and `lease_generation` against `lease_epoch`; `worker_id` comes from the matched row. Items are unique per `(dispatcher_id, lease_epoch)`, the list is no longer than the compact retained-grant count and is bounded by 128 items and 256 KiB when encoded as the dispatchers sub-envelope `{dispatchers: [...]}`, and a terminal report includes the reporting grant's own closure. Process-exit evidence carries the observed `ProcessIdentity`, which must equal the grant's bound `process` under the equality rule of [protocols.md section 2](protocols.md#2-runtime-fr-81) (`ProcessIdentity`). It is also `evidence_unbound` when the grant's `process` is null, when the bound identity lacks `leads_group: true`, when the item's `process` is null, and when the item names the grant of the incarnation that is reporting it; a `registry_acknowledgement` item carries a null `process`. The publication outcome binds to the attempt's recorded publication summary in `attempt.scratch`: the same `operation_id`, a `state` that agrees with the recorded outcome, and for `completed` a `ref` whose complete canonical bytes match the saved `runtime_result_digest` and VcsRef contract identity, in addition to the inspected revision/destination binding. The digest and contract come from the authenticated supervisor publication summary, never from this report itself; compute/validate canonical bytes outside the run lock and compare the saved identities under it. An unchanged commit/branch with altered repo, base, paths or principal is `evidence_unbound`; `not_dispatched` is refused once any publication operation is recorded, and `not_applicable` is accepted only when the sealed request's `publish` is `None` and the saved output contract has no `VcsRef` output.
- **Recording.** Closure is monotonic. A re-relayed identical item writes nothing: no row, no event and no `recovery_version` increment. A different item for a closed row is `API002` `evidence_conflict`, with the item's request index and dispatcher/epoch tuple. Whole-request refusal accepts no other item. These fixed item identities permit the exact accepted/refused delivery dispositions of issue #226; a refusal never closes a grant. Each new item writes, in one transaction, an increment of `recovery_version`, the event `attempt.retired` or `attempt.dispatcher_closed`, the run marker and a recompute of `recovery_required` and `replacement_blocked`, and keeps its provenance, distinct from operator attestation.

**Worker identity.** Every attempt write carries `lease_epoch` and the opaque `dispatcher_id`. The API refuses the write unless the token's worker is `attempt.worker_id`, `dispatcher_id` is the current grant and the epoch is current; a stale epoch is `API008`. `POST /workers/{id}/claims` requires that the token owns `{id}`. Registering a worker `id` bound to another token is refused, a `process` whose identity is already recorded for another retained incarnation is `API002`, and `host_id` belongs to the worker's execution domain. Registration records the process in `worker_incarnation` ([data-model.md section 2](data-model.md#2-entities)); `process.leads_group` is stored with it and is outside the identity-equality rule, and an identity without `leads_group: true` supports no process-exit evidence. The execution domain of a non-portable runtime belongs to the worker `id` that first registers it, and a registration of another worker `id` into it is `API002`. Registering an incarnation while an earlier incarnation of the same worker `id` with a different `boot_id` is live is refused with `API002`, `retryable: true`, `details: {reason: incarnation_boot_live, lease_until}` until that incarnation's lease lapses; the worker retries registration after `lease_until` and does not exit.

**Publication authorization heartbeat.** `PublicationExpectation` is a closed model with required `binding`, `binding_revision`, `credential_mode`, `operation_id`, `prepared_digest` and `destination_digest`, using the corresponding protocol bounds. The API compares it with the sealed execution request, authenticated prepared-publication summary and current authorized binding state, together with current epoch/dispatcher, `desired_state=run`, execute permission, live lease/deadline and predecessor closure. These caller-supplied expectations are never configuration authority. Only a successful check of a supplied expectation returns an exact `publication` echo; an ordinary heartbeat omits it. Malformed expectations are `API003`, a changed, removed or mismatched binding is `API002` with `details.reason: publication_binding_changed`, and a stale grant is `API008`. Unavailable validation permits no dispatch.

Both credential modes require this fresh authenticated heartbeat after acquisition finishes, including issuer I/O, and before each effectful `finalize` or retry. The worker requires the exact echo and serializes response validation and dispatch with its local gate; closure while awaiting the response prevents dispatch. An ordinary heartbeat, issuer response, missing/mismatched echo or earlier check cannot substitute. Credential-free mode does not call the control-plane credential-issuer route and emits authenticated phase provenance, never `vcs.credential_issued`. Real issuance remains audited even if the final check refuses publication. This check grants no durable capability and is not an atomic fence against a configuration change or external push after it completes; uncertain already-dispatched effects retain recovery obligations ([protocols.md](protocols.md#credential-free-local-publication)).

**Credentials.** The request carries the expected immutable binding identity/revision/mode; the API checks them against the saved trusted execution request and current binding authorization before secret resolution or issuer work, never treating them as caller-selected configuration. The returned `IssuedCredential` carries the same required tuple, which the worker verifies before constructing `PublicationAuthorization`; mismatch is a content-free `config_error`. The response model of `POST /attempts/{att}/credentials` declares `IssuedCredential.value` as the encoded transfer field of the `kora.protocols` codec, never `SecretValue` or a plain string, and sets `hide_input_in_errors` ([protocols.md section 6](protocols.md#6-secrets-fr-101)).

**`Claim`.** It carries the identifiers (`attempt_id`, `run_id`, `namespace_id`, `node_path`, `execution_domain_id`, `dispatcher_id`); the lease (`mode`, `lease_epoch`, `lease_until`, `deadline`); the bound `process`; the inputs to the request (the run parameters, `resolved_config`, `input_bindings` as descriptors with inline values up to the 64 KiB rule of [data-model.md section 3](data-model.md#3-identifiers-and-keys), the output contract, `limits`, the secret aliases, `price_table_id` and the complete pinned `price_table` revision); `execution_policy {values, namespace_revision, semantics}`, so the worker can build the request it seals; the command `resources` as descriptors `{name, sha256, size, executable}`, fetched through the resources route; `permitted_actions`; `current_grant: GrantBinding` separately from `grant_history: GrantHistorySnapshot` on every claim, including the initial one-grant claim; and, for recovery/adoption, the saved request descriptor, recorded `handle` and acknowledged segment offset. The worker fetches and transfers every retained grant through [bounded history reads](#retained-dispatcher-history-issue-226), never by repeating claim with a new claim_id. Heartbeats keep supplying the latest compact snapshot until verified, even when earlier grants are already closed; no response embeds the whole grant list.

**Heartbeat.** `observation` carries the `RuntimeStatus` fields and `counters` the `Liveness` counters of [protocols.md section 2](protocols.md#2-runtime-fr-81). A successful response means every evidence item in it is recorded, so the worker stops resending them; after an `evidence_unbound` or `evidence_conflict` refusal the worker resends the heartbeat at once without the refused item and logs it at WARNING, so bad evidence never lets the lease expire. A terminal report refused for its evidence is resent with the evidence corrected; the worker keeps heartbeating until a report is accepted. Only a change of `state`, `phase` or `execution_state` increments `recovery_version` or writes an event; a refreshed `observed_at` updates the last observation time only. Coverage identity/sequence orders heartbeat and empty-row usage updates under data-model section 7.2: identical revision/content is a no-op, a conflicting revision is `API002` with `usage_conflict`, and an older sequence is non-retryable `API002` with `usage_regression`. The null initial revision cannot reset accepted evidence. The `Liveness.usage_coverage.observed_at` timestamp remains the source usage observation time, separately from a fresh liveness poll or receipt; a repeated observation does not make old usage fresh. Nullable money and its known subtotal keep their pricing/completeness state. A counter update marks the run only under the rule of [data-model.md section 2.1](data-model.md#21-durable-run-scheduling-marker). `worker.last_seen_at` is written at most once per 15 s per worker. `permitted_actions` includes `report_result` only when every earlier grant is closed and the attempt holds result authority or its own deadline has passed; `cancelled` and `lost` reports do not wait for it ([scheduler.md section 3](scheduler.md#3-submission-execution-uncertainty-and-recovery)).

**Segments and usage.** A segment chunk is accepted when its `offset` equals the acknowledged stream offset; an exact `(offset, count, digest)` replay writes nothing, and any other offset or overlap is `API002`. Promoted event rows per chunk are bounded by the chunk's event count. Usage acceptance follows [data-model section 7.2](data-model.md#72-normalized-usage-and-derivation): the API validates the closed envelope and current worker grant, then calls the engine under the run lock to preserve coherent cumulative rows, source identity/order/time and coverage, and derive USD from normalized evidence and the pinned map. It sets `worker_id` and `image_digest`; callers cannot provide `usd_estimate`. Empty/omitted rows never erase earlier evidence, and attempt-level coverage records no-report and attribution/observation gaps independently. Cross-grant token/completeness regression is refused; one validated interim-table to final-harness basis correction may lower monetary estimates without rewriting earlier approvals. Identical replay is read-only, including coverage-only batches; conflicting coverage revisions are `API002` with `usage_conflict`. Malformed, coercible or oversized fields are `API003`; incompatible/regressive observations are `API002` with `usage_regression`, non-retryable. Validation and replacement are atomic, including the accumulated model cap. A permanent refusal preserves accepted evidence and does not block worker heartbeat, result or closure reporting.

**Replay of the other worker routes.** A repeated claims request with the same `claim_id` from the same worker and incarnation (a worker is bound to one token) returns the grant it created (attempt, `dispatcher_id`, epoch, original mode and permitted actions) and writes nothing, so no grant is left that its worker never learned; a new `claim_id` claims new work up to `worker.capacity`, a replay after that grant is no longer current is `API008`, and the same `claim_id` with a different body is `API002`. Registration replays on the same `incarnation_id`. `submitted` with the same handle replays, and a different handle is `API002`. `running` replays. `seal_request` follows data-model.md section 11.2. Artifacts replay on an equal complete `payload_digest` and saved contract identity, never on a selected approval digest. `POST /attempts/{att}/credentials` carries `lease_epoch` and `dispatcher_id` in its body, and `GET /attempts/{att}/resources/{sha256}` as query parameters.

**Uploads.** The staged provider operations and outcome/closure records are [ArtifactStorage section 7](protocols.md#7-artifact-storage-fr-44), selected under [#229](https://github.com/realkarych/kora/issues/229). Work items 8/12 and #216 implement this contract together with the [bounded chunked progress/recovery rules](#bounded-chunked-uploads-issue-224). These remain required first-slice gates. The caps are in section 8. Every multipart body starts with its `meta` part, at most 16 KiB; a body whose first part is not `meta` is `API003`, refused before any further part is read. Before any byte is stored, an unlocked pre-check refuses the upload unless the token's namespaces include the attempt's, the token's worker is `attempt.worker_id`, and `dispatcher_id` and the epoch are current as read; the locked recheck stays. Each live `upload_ref`, including `seal_request.body_or_upload_ref`, is bound to `(attempt_id, dispatcher_id, payload_kind)` by its `upload_staging` row. Foreign attempt/grant use is `API003`; within an authorized generic chunked binding, changed source/part declarations follow the conflict rules below. Terminal recovery uses the retained owner under current authorization, without reviving the original grant.

- **Staging rows.** Each upload first gets one `upload_staging` row ([data-model section 2](data-model.md#2-entities)) in a short transaction without the run lock: a single-part body, a segment chunk or a whole chunked upload keeps that row through its parts and any preparation. Core persists a unique `StageRef`, immutable `StageSpec`, full-address admission generation and reservation before `begin_stage`, and saves each mutation's exact `StorageOperationRef` before dispatch. The transaction first admits the declared full-payload address through the shared owner-admission/deletion fence, then reserves declared size against the worker's `staged_bytes`: `meta.size` for a segment (at most 8 MiB), `total_size` for a complete chunked upload, or the bounded retained-source/preparation maximum for an over-cap opaque transcript under the rule below. All parts repeat the original total size/digest. Exceeding staged bytes or open-upload capacity refuses before allocation with the existing bounded retryable refusal. Provider-private capacity is separately reserved and remains charged after core acceptance until actual cleanup.
- **Private immutable bytes.** The API streams to `write_part`, never a content address or an in-memory part buffer. Both API and provider check the declared part size/digest; mismatch or excess is `API003`. Persist an immutable `PartRef` and progress before acknowledgment. Conflicting index/bytes cannot replace a part. `seal_stage` fixes the ordered bytes, and complete sources must match the original full raw size/digest before transformation. Core fully rereads that immutable source outside all database resources, applies the saved contract, and uses either the unchanged complete `SealedStage` or one `PreparedContentRef`. Every prepared candidate is also completely reread/checked before publication. `promote` is create-only and binds its destination to the exact selected publishable reference, not the raw digest when preparation changed bytes. Persist its truthful `PromotionResult`, including created-object attribution. Response loss reconciles the saved operation; unknown never becomes `created_object=false`. Promotion requires current stage ownership and current admission for the actual retained address, with no unresolved deletion generation. After completed deletion, a new promotion from validated private bytes is required; an old receipt or `exists` observation cannot establish availability.
- **Acceptance.** One core finalizer per stage, across API instances, owns rereading, validation/preparation, promotion and outcome persistence. Its short durable admission transaction releases all database resources before I/O; competitors return bounded busy/pending before reading or parsing. Timeout cannot replace a still-live finalizer. Cancellation/restart require actual reader/work/effect closure before takeover. The accepting transaction checks current authority, the present `staged` row, exact prepared identity, current promotion and full-address admission, then references the address, releases core `reserved_size` and marks `accepted` atomically. An execution-request upload remains ready in `staged`, grant-bound and reserved until successful `seal_request` performs its policy/capability/authority checks and conditional descriptor write; ready grants no execution authority. A missing/expiring unsealed generic chunked owner is non-retryable `API002` `upload_unavailable`; explicit recovery first checks for a saved terminal owner, and a permitted new upload requires a fresh reference. Other upload envelopes retain their existing retryable missing-row refusal. A deletion-fenced address is `API002`, `retryable: true`, `details.reason: payload_deletion_pending`; any wait uses the existing finite request deadline without database resources. More than one `payload` part is `API003`. Non-transcript content over its cap is `API003`; opaque transcript truncation follows the bounded preparation rule below. Cleanup uses `retire_stage`, acknowledgment through `release_stage` and then row removal; accepted private bytes remain provider-accounted until actual closure.
- **Refusal and reclaim.** A whole-owner refusal (grant loss at the locked recheck, cancellation, expiry or whole-upload validation failure) marks the row `expiring`, and the API closes issuance and calls `retire_stage` only after that commits. Confirm private-byte, reader and issued-effect closure under the provider contract before completing the row; observed absence alone does not settle a delayed write or deletion. If authoritative promotion evidence establishes that the upload did not create the addressed object, a following transaction deletes the row and releases its reservation exactly once. Unknown promotion ownership remains unresolved with the row and reservation charged; it must never be interpreted as `created_object = false`.
- **Created-address completion.** An upload that created its addressed object retains its `expiring` row and reservation until either required physical deletion is confirmed complete and every issued deletion effect has settled or is authoritatively fenced, or a different independently eligible durable non-staging owner retains the same address and no deletion generation or effect remains unresolved. Both alternatives require confirmed stage retirement and release first. The retained owner must be an accepted `artifact_version` payload or retained `derived_payload` descriptor with current content eligibility, or a graph-version resource whose version is active or whose pinned run can still start an attempt, under [data-model section 10](data-model.md#10-retention-dd-4). Surviving metadata alone, an expired, expiring or missing payload owner, another staging row, a transient hold alone, observed object existence or an earlier promotion receipt does not qualify. Under the same durable physical-storage/full-`payload_digest` fence, check eligibility and delete the staging row/release its reservation atomically against owner expiry/removal and deletion admission. Release exactly once. The retained-owner alternative issues no physical deletion, renews no retention, restores no expired owner and grants no access; do not disclose a foreign owner's identity to the uploader. Without a qualifying owner, retain the created-object row and reservation until required physical deletion completes. Timeout, cancellation, restart and observed absence never clear unresolved deletion authority.
- **Interrupted cleanup.** A timed-out or disconnected upload leaves its row in `staged`; after `expires_at`, the stored time plus the longest upload duration plus the lock-wait bound (1 hour), retention marks it `expiring` in its own transaction and closes issuance and retires the stage only after that commits. Retention also finishes every row left in `accepted` or `expiring` by a crash. An accepted row's reservation was already released at acceptance; delete its row after confirmed stage retirement and release. An `expiring` row follows the same authoritative promotion and created-address completion conditions above, including idempotent reservation release. `kora db verify-storage` uses bounded `scan(stages, ...)` inventory to report private stages that no row names. Retention retires them only after authoritative issuer/effect closure; a missing row or scan observation alone is insufficient. A `staged` row acquires ownership of its declared `payload_digest` atomically against deletion admission, so a prior owner scan cannot race a newly eligible upload into referencing deleted bytes ([data-model section 10](data-model.md#10-retention-dd-4)). `kora db verify-storage` reports staging rows and private stages; its content inventory uses `scan(content, ...)` with the same current ownership/fence checks.
- **Canonical preparation.** Provider code never interprets artifact types or JSON. If the saved contract requires canonicalization, core streams the canonical bytes through `prepare_content` in the same upload owner, without rewriting sealed raw input. Reserve the candidate's maximum additional bytes against the same worker budget and the actual simultaneous provider-private peak before allocation. Raw declarations/receipts and actual prepared size/digest remain distinct. Admit any newly derived address through the shared physical-store/full-digest fence after its digest is known and before promotion; a fenced candidate stays private and charged. VcsRef keeps its separately approved exact canonical-wire rule, 1 MiB cap and single application upload. [StructuredOutput revision 1](artifacts/StructuredOutput.md#4-upload-storage-summaries-and-lifetime) separately requires canonical wire bytes and its own 1 MiB logical raw/canonical cap: compare the complete staged value once before promotion, without repeated prefix rescans or rewriting addressed bytes. It does not inherit VcsRef's absent `meta.part` restriction. Other types acquire no new canonical-wire refusal.
- **Opaque transcript preparation.** An over-cap transcript retains at most 268435432 source bytes plus the 24 ASCII bytes `\n[transcript truncated]\n` (LF at both ends), within the existing 256 MiB cap. Record the larger original declaration but reserve/allocate only the bounded captured source and candidate maxima. Validated complete parts remain immutable; `capture_prefix` records the actual bounded bytes/digest of the overflowing next part with `source_complete=false`, never a receipt falsely verifying its full declared size/digest. Seal that captured sequence and prepare prefix-plus-marker as one immutable candidate. Core verifies the retained full size/digest, admits its actual address and promotes that candidate; an incomplete source seal cannot publish directly. The accepted owner has `truncated=true`. Further source parts are `API003`; the worker stops transmission and closes its producer/request resources. No integrity claim covers the deliberately unreceived tail.
- **Completion identity.** Acceptance of every identity-changing preparation, canonicalization as well as truncation, atomically saves one compact binding from the immutable original upload reference/source declaration to the retained owner/descriptor. It stays with owner metadata after stage cleanup, not in a permanent part ledger. After current authorization, terminal recovery returns that owner's current saved descriptor, including expired/superseded state, without parsing, promotion, renewal or effect authority; full source/retained identities never become approval-selected digests. Execution-request completion is recorded only by successful sealing. A missing terminal owner or expired unsealed upload is unavailable, never reopened; The [generic chunked contract](#bounded-chunked-uploads-issue-224) supplies its explicit recovery envelope. Whole-upload VcsRef replay remains its existing contract.
- **VcsRef provenance.** Before first artifact acceptance, persist/relay the authenticated supervisor's frozen `runtime_result_fields`, complete digest and saved contract tuple. The field set comes from the validated runtime result, is bounded to its closed top-level schema and contains every required field; candidate input cannot choose or replace it. Require every recorded field/value, canonicalize that exact projection outside the run lock, then compare its digest, contract and the same saved field set under the authority lock. Added fields may only be absent `url`, `opened_by`, `commit_url` or `compare_url` with trusted code-host provenance bound to the same operation/repository/revisions; the upload's claims cannot establish it. Preserve URL/opener pairing. A matching terminal report cannot authorize a divergent artifact. The complete enriched payload is separately validated, durably frozen before first upload and stored/replayed by its full digest under the [enrichment recovery contract](artifacts/README.md#5-upload-replay-and-result-ownership).
- **Work outside the lock.** Validation, projection cutting, digest selection, NDJSON parsing and the per-event check run before the locked transaction, over the immutable graph-version contract; the transaction only checks identity, epoch and authority, binds evidence and inserts rows.

### Bounded chunked uploads (issue #224)

This contract applies to generic chunked output, execution-request and opaque transcript uploads on `POST /attempts/{att}/artifacts`. [VcsRef revision 1](artifacts/README.md#5-upload-replay-and-result-ownership) keeps its one complete canonical payload, exactly `meta` then `payload`, with `meta.part` absent; it does not acquire these modes. Segment chunks keep their separate offset/count/digest and 1,000-event/8 MiB rules. The [staged storage contract](protocols.md#7-artifact-storage-fr-44) owns provider effects; the API owns current authorization, progress, acceptance and the response union below. No new endpoint or per-token rate limit is introduced.

#### Requests and immutable binding

Generic chunked metadata has a required closed discriminator `mode: data | recover`. Every request starts with exactly one `meta` part of at most 16 KiB. Unknown fields, wrong variants or an invalid multipart shape are `API003`. Authenticate and authorize the attempt/current grant before reading payload bytes or disclosing any upload state; current authority is checked again at acceptance. Snapshot/position/history verification never supplies upload authority or storage closure.

| Mode | Closed metadata and envelope |
|---|---|
| `data` | `{mode, lease_epoch, dispatcher_id, payload_kind, output_name?, type_name?, digest, size, part: {upload_ref, index, final, total_size, payload_digest}}`; exactly one following `payload` part. Existing output/type fields retain their saved-contract meaning; the caller cannot select a different contract. |
| `recover` | `{mode, lease_epoch, dispatcher_id, payload_kind, output_name?, upload_ref, total_size, payload_digest}`; exactly the `meta` part and no payload. `part`, `digest`, `size` and `type_name` are absent. The saved contract and immutable source binding determine the result. |

`payload_kind` is `output`, `execution_request` or `transcript`; `output_name` is present exactly for an output. Identifiers, full payload digests, strict integers/booleans and timestamps use the existing API/protocol definitions. `digest` and `size` describe this source part; `payload_digest` and `total_size` describe the complete original source. Every data request repeats those immutable source declarations. The upload binding additionally fixes attempt, original dispatcher/grant, kind, applicable output and saved contract. A new field value cannot rebind an existing upload.

#### Fixed progress and replay

Let `P = 16777216` bytes (16 MiB), the existing payload-part cap, and `T = total_size`. The accepted cumulative source cap remains 268435456 bytes (256 MiB), except the already specified server-owned over-cap transcript truncation. Indexes start at zero and are contiguous. Every non-final part has exactly P bytes and leaves at least one source byte outstanding. The final part contains exactly the remaining source bytes, at most P. A zero-byte final part is legal only for the whole empty upload at index zero, with T=0 and the digest of empty bytes. A positive exact multiple of P ends with its last full data part marked final, never an additional empty final request.

| Input / current state | Result |
|---|---|
| First valid part, index zero | Admit one owner and its reservation/intents before effects; persist verified part/progress before acknowledgment. |
| Next index, non-final size P with source remaining | Append exactly once and advance the contiguous prefix. |
| Next index, final exact remainder (or the one empty-upload final part) | Verify the whole immutable raw source, then follow finalization and acceptance; saving the part alone is not successful completion. |
| Zero/tiny non-final part, oversize part, premature/late final marker or inconsistent declared remainder | `API003`; no prefix advancement or expiry renewal. |
| Index above the next index or any gap | `API002`, non-retryable, `details.reason: upload_part_order`; no append. |
| Earlier index with its live receipt and exact immutable request tuple plus verified bytes/digest/size | Return its original acknowledgment without appending, changing the saved prefix or renewing expiry. An original prefix acknowledgment is not a fresh current-progress observation. |
| Reused index/upload binding with changed declarations, fields or bytes | `API002`, non-retryable, `details.reason: upload_part_conflict`; never replace the winning bytes or receipt. |
| Concurrent first writers for the same next index | One semantic provider mutation/metadata progress commit wins. An identical loser reconciles that receipt; a conflicting loser conflicts. A still-uncertain winner remains pending, not a second write. |
| Finalization unresolved | `API002`, retryable, `details.reason: upload_pending`; bounded refusal under the existing request deadline, with no new finalizer, reread or preparation. |
| Missing/expired unsealed owner or no retained receipt for a data replay | `API002`, non-retryable, `details.reason: upload_unavailable`; the worker uses explicit recovery to distinguish completion from unavailable staging. |
| Any further data request after terminal transcript truncation | `API003`; explicit recovery may still return its retained descriptor. |

An existing receipt is compared before classifying a reused index as a new malformed layout; a changed replay is a conflict. A received body whose actual bytes exceed its stated size or fail its stated digest is `API003` unless it is a conflicting replay of an existing receipt. Authorization refusals retain their existing precedence and codes. A request-local replay/conflict/order/layout refusal, including a losing concurrent request, does not expire or retire an otherwise valid shared owner or its committed prefix. Close only that request's streams/readers and uncommitted effects under the existing bounded provider admission and settlement rules. Unknown effects remain charged and block dependent progress until settled; after request-local cleanup, the valid next index remains usable. Grant loss, cancellation, expiry and whole-upload validation failure retain whole-owner retirement. No refusal discards an uncertain mutation, reader or reservation.

For a complete source within the cap, the number of parts is `max(1, ceil(T / P))`, at most 16. A larger declared opaque transcript terminates at the existing captured prefix plus 24-byte marker; the incomplete overflowing part is not a verified full public-part receipt. The fixed prefix/candidate slots are additional provider metadata, not further public progress. Truncation is the sole terminal exception to receiving the complete declared source.

#### Closed responses and result recovery

| Kind | Closed response / meaning |
|---|---|
| `progress` | `{kind, upload_ref, next_index, bytes_received, expires_at, receipt?}`. Data acknowledgments include `receipt: {index, size, digest, final, next_index, bytes_received}`, whose prefix values are immutable. A recovery response omits `receipt` and reports the currently committed contiguous prefix without accepting bytes. |
| `ready` | `{kind, upload_ref, expires_at}`. A completely validated execution-request upload remains grant-bound, staged and reserved, with immutable bytes available to the separate `seal_request`. This result creates no execution-request descriptor or effect rights. |
| `completed` | `{kind, descriptor, truncated}`. The existing owner-specific output/transcript or sealed-request descriptor, under its saved schema and current availability/status. `truncated` is a strict boolean, true only for server-truncated transcripts. No provider-private reference is returned. |

A data response for a non-final part is progress. Final output/transcript success requires durable core acceptance and returns completed, not merely a promotion receipt. Final execution-request upload returns ready; successful sealing alone creates its terminal descriptor. Pending finalization never fabricates either success. Exact final replay while still ready may return the saved ready acknowledgment; once terminal acceptance/sealing closes part replay, the worker obtains the current descriptor through recover, even if physical receipt cleanup is still pending.

Live staged/ready recovery must match the original grant-bound row and source declaration. It never changes stored_at/expires_at or resumes a retired stage. Terminal recovery uses current authorized access to the retained owner, matching the source binding, attempt, kind/output and saved contract. It does not revive the original grant. Perform the read-only saved-owner lookup before deciding eligibility to create a current result; expired or superseded owners return their current descriptor rather than becoming new results. Current-tip history verification remains required wherever the existing contract requires effect authority; a permitted saved-result read requires no effect authority.

Terminal recovery after stage/receipt removal is not part replay. For an unchanged source, resolve the existing owner by attempt/output and complete identity; every identity-changing transformation uses the compact durable source-to-retained binding established by #229. Return no invented part acknowledgment. Do not parse, canonicalize, promote, renew retention, recreate expired bytes, restore a superseded result or reopen a stage. A missing terminal owner, including an expired unsealed request upload, is API002 upload_unavailable; the worker must begin any permitted new upload with a fresh upload_ref. Source/retained full digests remain distinct from approval-selected digests. VcsRef's separate complete-upload replay is unchanged.

Response loss or an API-process restart preserving the same live worker grant permits prefix/ready recovery; the worker compares the saved original source binding and sends only the next needed immutable part. A worker restart that obtains a new incarnation/grant cannot resume the old live stage. It first uses current-authorized terminal recovery; if no matching terminal owner exists and the reference belongs to the older grant, the response is `API003` for foreign-grant staging use. Any permitted new upload then requires a fresh reference and current admission/effect authority; the old stage remains cleanup-owned and charged until its existing settlement conditions hold. No recovery transfers staging ownership or restores the old grant. It distinguishes progress, ready and completed. Completed stops source transmission and closes producer/request resources, including after truncation. Ready permits only the separate sealing path. No response renews a lease, grant or upload expiry.

One upload row owns at most 16 public-part receipts and their bounded immutable fields; common source/grant/contract/expiry fields are stored once. Provider PartRef/control records retain the 16 KiB/depth-16 DTO limits and finite semantic-slot rules of #229, so the public part-reference slots total at most 256 KiB before the fixed stage/preparation/outcome slots. Retries, malformed requests and recovery calls create no permanent receipt per request. All partial bytes and uncertain operations remain under existing finite admission and actual cleanup bounds. Stored_at and expires_at are fixed at first admission. Next parts, exact replay, conflicts, errors, recovery and restart cannot renew them. Receipt absence or elapsed time cannot settle prior effects. Byte quotas and the 16-part bound do not bound arbitrary request repetitions, aggregate RSS or worker spool size; DD-6 remains unchanged.

It records the human actor, time and `provenance=operator_attestation`; it is not automatically verified provider evidence, a force-retry switch or a substitute for actually establishing closure. The runtime/provider evidence paths retain their own provenance. Both terminal and active runs can reconcile old attempts without restoring their result authority.

Under the run lock compare version/domain and apply the action once, advance `recovery_version`, record an audit event and return `{attempt_id, execution_domain_id, recovery_version, execution_state, requested_action, replacement_blocked, retained_scopes, permitted_actions, evidence}`. The idempotency record is checked before version comparison so an identical replay returns the original response even after the version advanced; a changed replay is `API004`. A stale version/domain or conflicting recovery action is `API002` with current projection and recovery hint; malformed/incomplete evidence is `API003`; missing permission is `API005`. Conflicting actions are `API002` except for explicit, versioned escalation: `stop` may supersede pending `observe`, and evidenced `confirm_stopped` may supersede either pending action. Each escalation records both request identities and an audit event atomically; a delayed old observation cannot overwrite newer stop intent/evidence. A worker completes an `observe` request by persisting its observation or structured inconclusive error, leaving unresolved recovery visible. `stop` persists stop intent and revokes execution/publication permission; its current/next claim is recovery-only. A pending unreachable `observe` or `stop` does not block a versioned `confirm_stopped` with complete operator evidence: that action closes the pending request atomically. A mere request never certifies closure. The terminal transition and release happen only after the scheduler applies the complete evidence under existing locks; attestation never directly starts another attempt.

Existing run/node/attempt, target and worker reads expose `execution_state`, original domain, `recovery_version`, `recovery_required`, reason, last observation/time, dispatcher counts/paged grant references and selected closure evidence, publication uncertainty, evidence provenance, retained reservation/target scopes, `replacement_blocked` and permitted reconciliation actions. Include historical/superseded attempts and terminal runs with retained holds in those projections; `GET /runs?recovery_required=true` and `GET /workers` expose the recovery backlog without filtering it to active leases. Events carry the same identities/version. Cost is last-known with `observed_at` and at most `partial` while recovery is unresolved. Worker registration includes a fresh incarnation and runtime domain; claims persist each dispatcher grant before returning its id, original domain, `execute`/`recover` mode and permitted effects. A current desired-run attempt may use `mode=execute` during recovery with observation-only permitted actions until affirmative live adoption or recovery of the original immutable prepared/completed checkpoint and closure of every earlier grant/operation; checkpoint effects remain limited to the original operation on a non-retired current attempt; a normal current executing grant does not itself create a run-wide recovery barrier. A recovery-only claim for a cancelled/superseded or stop-requested attempt is allowed after terminal run status, with no new submission, publication or current-result authority.

Every mutating operation records an `event` row with `actor` taken from the token.

Compiling Python sources is not an API operation: it runs in the author's own process (`kora compile`, or the stdio authoring server's `kora_compile`, sections 3 and 4), and the API accepts only compiled documents, so no control-plane process ever imports graph authors' code (ADR-0002, amended 2026-10-16; [dsl.md](dsl.md) section 2). Running a graph's scenarios is not an API operation either (`kora test`, `kora_test`; ADR-0002, amended 2026-10-19; [dsl.md](dsl.md) section 4).

Body shapes (DD-36; unsupported first-slice operations are excluded by the matrix below): deploy `{graph, ir, resources: [{node_path, name, content_base64}]}` → `{graph_version_id, number, warnings[]}`, with at most 64 resource files and 1 MiB of resource content per version and 256 KiB per file; run `{params, graph_version?}` and rerun `{graph_version?, params?}` → `StartOutcome`; transition bodies follow [worker route bodies](#worker-route-bodies-issue-139) → `{status, desired_state}`. A run view is `{run, rerun_of, reruns_ref, nodes_ref, attempts_ref, artifacts_ref, events_ref, state_summary, admission, totals, wait}` with metadata descriptors for selected saved fields; `wait` is null unless requested. A node view is `{instance, current_attempt, attempt_count, attempts_ref, artifacts_ref, wait, recovery, selected_content}` with bounded scalar/count/sample data. A collection is `{items,next_cursor,observed_at}`. Detailed projection/selector fields and selected-content envelopes are normative in [bounded read projections](bounded-read-projections.md); histories and bodies are not embedded arrays.

### Target-source result acceptance (ADR-0019)

Artifact reporting returns the stored version ID, result `status` and payload availability. For the declared top-level target source, every output is `staged` until its complete result is accepted atomically with key binding/comparison and source success. Automatic input/branch/collection/approval consumers select only current results of completed attempts ([data-model.md section 4](data-model.md#4-state-machines)); node/attempt inspection exposes tentative and rejected history explicitly. Namespace/transcript access, expiry and recovery holds remain unchanged. Live logs/segments/usage do not wait for source acceptance.

Source output `(attempt_id, output_name)` is write-once, with a permanent full `payload_digest` and saved contract identity. After current namespace/service/epoch checks, exact replay returns the saved descriptor read-only before testing current-result eligibility. Compare full canonical inline/blob identity, not selected-field digests. Changed replay is `API002` with `reason: source_output_conflict`; it cannot replace the first payload, change settled success/failure, renew retention or restore expired content. New late reports after terminal/clear/cancel cannot become staged/current. Multipart bytes are received/stored outside the run lock; the commit rechecks current authority. Storage success alone grants no result rights.

The first binding origin identifies the parameter name or accepted source node/output/path and artifact-version ID. A different valid proposed key fails the source asynchronously with existing `config_error` and internal error `{code: target_identity_conflict, retryable: false, details: {reason: target_identity_conflict, bound_target_key, proposed_target_key, source: {node_path, output_name, path, artifact_version_id}, attempt_id?, recovery_hint}}`; normal message/location fields remain present. Physical sources store it on their attempt and node.failed event; scheduler-only sources use the durable node.failed event for the same node/run error projection, without an invented attempt. Missing/malformed/incomplete source data is artifact_invalid. No output of the rejected production becomes current.

`POST .../retry` accepts ordinary clear/cancel intent and cannot synchronously refuse a value not yet discovered. A later `kora_runs` or `kora_inspect` read exposes the source failure. Only an actual synchronous request refusal is an API-family HTTP error. Existing `kora node`, `kora_inspect` and `kora_retry` expose the same classification/details; existing CLI/MCP error behavior applies. The console keeps its failed-node state, shows bound/proposed keys and a fully bound existing rerun command, and adds no mutation.

Explicit retry must produce the original key. Existing rerun creates an independent run, consuming no old artifact or hold and honoring every replacement blocker; it does not automatically carry the rejected key or guarantee rediscovery. Deterministic selection is graph-owned through declared inputs/validation or a suitable version. Target/history/approval/cost reads retain original run attribution, including failed proposals and late usage after payload expiry. The future acceptance matrix is [data-model section 12.5](data-model.md#125-future-acceptance-contracts).

### External observation and delivery diagnostics (ADR-0021)

Existing node/approval/trigger reads expose an `integration_observation` projection: `purpose`, configured `integration_id`/resource and relevant binding revision, `state` (`due`, `in_flight`, `deferred`, `backoff`, `blocked`, `degraded`), last successful observation/time, active claim deadline, next poll/retry/cooldown, and bounded structured error/recovery hint. Secret values and credential-bearing URLs are never returned. Large external-id or error/history sets use bounded samples with explicit counts/completeness and existing paginated read references. Retained content stays subject to transcript/namespace authorization and payload availability; an observation gap is never a fabricated negative value.

The same node reads (the current wait) and sensor trigger-binding reads also expose `evaluation_error`, the last CEL `match` or `until` evaluation error record, and approval reads expose `evaluation_error`, the `approve_when` error record of a `failed` request. A node failed by an evaluation error carries reason `cel_evaluation_error` with the same record in its failure details. The record holds only the error kind, field, nullable offset, event identifier or observation time and recording time, never expression text, values or binding messages, and it is separate from `integration_observation` ([ir.md section 7.7](ir.md#77-evaluation-errors)). `kora node`, `kora approvals`, `kora schedules`, `kora_inspect`, `kora_approvals` and `kora_reference` forward it through existing operations.

Approval detail/list additionally expose `delivery` desired open/closed state, revision, last delivery error/time, next reconcile time, unknown authorization and learned-id/closure progress. Keep terminal requests with pending/unknown delivery discoverable through the existing approvals list (including status selection); include approved/rejected/failed records and terminal runs. Approval audit decision, current node/gate outcome and channel delivery are separate. A recorded approval awaiting head verification is not shown as a completed gate, and a failed-after-approval gate does not rewrite that audit entry.

The existing `GET /namespaces/{ns}` also returns `integration_health`: namespace-visible configured-resource degradation and observation/delivery counts/oldest ages, linking existing paginated approval/node/trigger reads for detail. Shared-resource state never reveals other namespaces' owners or credentials. `kora namespaces` and `kora_reference` already map this read. These are existing namespace-authorized reads. `kora node`, `kora approvals`, `kora schedules`, MCP `kora_inspect`, `kora_approvals` and `kora_reference` forward the same API projections. Namespace integration/policy administration retains `platform` permission; human decisions retain `approve`; observer dispatch gains no worker service-token rights. No public operation, curated tool or console mutation is added. Existing contract/parity tests must cover added fields when implemented.

Retryable observation errors are diagnostics plus scheduler-owned backoff, not new runtime attempts or synchronous HTTP failures of an unrelated cancel/retry. Permanent current-operation failure uses existing node `config_error` with a specific structured integration code and recovery hint; trigger bindings report blocked/degraded without consuming the occurrence. Credential/access repair is detected by bounded authorized probes even under the same secret reference; existing binding repair/pause-resume also schedules a recheck. Failed nodes use ordinary manual retry after repair. A policy denial permits no external probe; local policy recheck remains possible. No new generic recovery action is required. API errors keep section 1's structured envelope; async failures remain durable node/event/read diagnostics.

Existing node/Review/Approvals/System views display integration gaps, last success, deadline/backoff and delivery uncertainty. An external outage alone does not fail core database readiness. [Scheduler section 16](scheduler.md#16-external-observation-dispatch-adr-0021) defines the fault model, defaults and metrics; [data-model section 14.4](data-model.md#144-future-acceptance-contracts) defines future tests, not documentation-CI results.

## 4. MCP servers (FR-0.1, DD-28)

kora ships **two curated MCP servers** with task-shaped tools, not one generated tool per API operation: `kora-authoring` for writing and deploying graphs and `kora-operating` for running and inspecting them. Both run as the stdio process `kora mcp --server authoring|operating --url …` for a local coding-agent session and are mounted on the API at `/mcp/authoring` and `/mcp/operating` (DD-18). The HTTP-mounted authoring server omits `kora_compile` and `kora_test`, which would run authors' code inside the API process; a session that uses it compiles with `kora compile`, runs scenarios with `kora test` and passes the document to `kora_plan` and `kora_deploy`. Every other tool calls the API with its configured personal token through the shared client; the servers mounted on the API reach it through the shared client's in-process ASGI transport, the same one the standalone worker uses ([ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md)). Every MCP HTTP request, including session initialization, listing, the stream and session deletion, is authenticated before any session state is created or touched, and a session records the authenticated principal, never the bearer value. Each mounted tool call presents the Bearer credential of the HTTP request that carried it, and the API authenticates and authorizes it for that call as for any external request; a mounted server holds no process-level token (`KORA_MCP_TOKEN` configures only the stdio server), never uses the in-process worker's service token, binds no credential to an MCP session or to inherited context, and refuses a request on a session established by another credential. An application failure on the in-process path reaches the tool as the API's structured response, the API boundary owns its single failure diagnostic, and no rule relies on listener-level controls or on the client address. The servers add no domain state or API permission model of their own (DD-5, DD-16); the stdio launch-time download root below bounds only local file-creation authority. **Tools that start work return at once** (ADR-0002, amended 2026-10-19): `kora_trigger` and `kora_retry` return the API's start or retry outcome, and `kora_plan` returns the plan; `kora_compile` and `kora_test` are client-side operations that return their result like any other call. `kora_test` waits for its in-process scenario runs and has no duration cap of its own: a suite whose real commands can outlast a client's tool-call timeout runs with `kora test` instead, and cancelling the call (`notifications/cancelled`, the end of stdio input, or SIGTERM, SIGINT or SIGHUP to the stdio server process) ends its scenario runs and releases what they acquired (runtime resources, and the temporary standalone's data directory, workspaces, database connection and scheduler and worker tasks), as the command watchdog does for a hanging command, with no result after it; after `notifications/cancelled` the server keeps serving the session. How the scenario runner closes further launches, which runtime resources it releases, its termination grace and its budget against the MCP clients' shutdown escalation are an [open implementation question](../architecture/detailed.md#open-implementation-questions). A server killed with SIGKILL, and descendants that leave their process group, cannot be released; these are remaining limits. The resource-lifetime obligations of `kora_test` are pending implementation, owned by the issue that first implements `kora_test` and `kora test` under the first-slice implementation plan ([issue #127](https://github.com/realkarych/kora/issues/127)) and activated with it: at least 1,000 `notifications/cancelled` cycles in one long-lived stdio server with process groups, descriptors, tasks, database connections, temporary directories and memory back at baseline and the following call succeeding, and actual process exit after the end of stdio input and after each signal. Waiting for a run is the bounded `wait` option of `kora_runs`, which forwards the [run-read wait](#bounded-run-read-wait-adr-0002); apart from `kora_test`, no tool otherwise waits on run, node or approval progress, and none uses a `?follow=true` stream. The cap of `45s` sits below the default tool-call timeout of the supported coding-agent clients, which progress notifications do not extend ([MCP Tasks probe record, section 3](../research/mcp-tasks-probe-2026-10-19.md#3-client-support-claude-code-and-codex), checked 2026-10-19). MCP Tasks are not used: they are an optional protocol extension that the official Python SDK does not implement and that the supported clients do not declare. They are revisited when the SDK implements the `io.modelcontextprotocol/tasks` extension and Claude Code or Codex declares it; a task would then serve declaring clients only, as a projection of the run.

**Full artifact downloads on stdio.** [#135](https://github.com/realkarych/kora/issues/135) must define the shared local client-error envelope (including stable code/reason, retryability and recovery hint) before work items 11/12 implement this path or claim its gates; it remains distinct from the API error envelope. Full downloads require the trusted launch option `kora mcp --download-root <absolute-existing-directory>`; without it they are disabled. Validate and pin this directory at startup. A tool call, current working directory, repository configuration, artifact or HTTP header cannot select, widen or replace the root. `kora_inspect` accepts `artifact_id` with `download_to`, an explicit absolute destination componentwise beneath that root. Reject traversal, the root itself, outside paths and sibling-prefix matches before creating anything. The path is never inferred from artifact content or names. Require an existing parent directory, create no directories and refuse every existing destination, including dangling symlinks. Use descriptor-relative traversal from the pinned root without following symlinks, retain directory handles, reject parent/root identity replacement, create a private temporary file exclusively in the selected directory, and publish without replacing a destination. Path races cannot redirect writes or overwrite unrelated files. This root authorizes file creation within an operator-selected area; the absence of an existing file elsewhere is not permission to create one.

Each stdio process admits at most four artifact downloads across all callers and identities, with no waiting queue and no tool override. Acquire a slot before the metadata request or any per-call filesystem handle, temporary file or transfer buffer. When saturated, refuse immediately through the safe local client-error contract with the fixed content-free reason `download_capacity_exhausted`; do not fabricate an API error or request ID. A slot remains owned through cleanup and releases exactly once only after all owned requests, handles and temporary files have settled. Unresolved cleanup remains charged against the limit and reports bounded evidence; it cannot release admission while accumulating abandoned resources. The startup root handle is a single server-owned resource. Saturated or blocked downloads do not delay ordinary tools or other admitted downloads.

The trusted launch option `--download-timeout <duration>` sets the positive finite transfer budget, default `45s`; tool arguments cannot change it. It covers metadata, payload, hashing, file completion and publication together. Reserve at most another `10s` for the response and bounded cleanup, and configure the consuming client's wall-clock tool timeout to at least the transfer budget plus that allowance. Defaults fit a `60s` caller budget; a longer transfer requires an explicitly longer compatible client timeout as well as this server setting. The server cannot infer or extend a caller timeout from progress notifications. Required operator examples pair both settings. A deadline, cancellation or path too slow for the selected budget remains a transport failure with no partial success; no throughput-independent completion or resumption is promised.

Use the existing authorized artifact metadata GET to obtain immutable full `payload_digest` and `size`, then stream the payload GET through the shared client under the same identity and one finite deadline covering both requests and local completion. `payload_digest` is SHA-256 of the exact stored canonical JSON or raw file bytes, not the artifact type's selected-field approval `digest`. Missing/malformed metadata fails closed. Transfer exact bytes in bounded chunks without full-payload buffering, parsing/reformatting, direct storage access or presigned redirects; compute SHA-256 and byte count incrementally. Enforce the existing artifact-size ceiling even without Content-Length and compare both final values with metadata before publishing the file. Truncation, size or digest mismatch fails closed and removes the temporary file. A valid hash does not make artifact content trusted or executable.

The call owns its requests, connections, file/directory handles and buffers through cleanup; no background download, retained session or MCP Task is created. Return `{artifact_id, download_to, bytes_written, payload_digest}` only after complete receipt, successful integrity checks, file close and no-replace publication. This bounded verified-transfer receipt is a local transport result, not an API response or diagnostic. The startup root handle belongs to the server and closes at shutdown; per-call handles close independently.

API refusals preserve their error envelope. Transport, filesystem, integrity and deadline failures use the safe client-error representation, with no fabricated API request ID or unrestricted exception text. Failure, cancellation, stdio EOF and shutdown cancel requests, release owned resources and remove only temporary/partial files created by that call; a cleanup failure reports remaining owned output honestly. Concurrent downloads are independent. Namespace/transcript authorization and retention availability stay with the API, and payload bytes never enter diagnostics or MCP stdout outside a deliberately bounded inline result. A future HTTP-mounted MCP server must not interpret `download_to` on its own filesystem; its activation requires a complete payload representation and parity evidence of its own.

The request, its connection and the timer end when the result is sent or the call is cancelled: by `notifications/cancelled` on stdio or on the session that carried the call (2025-11-25 and the earlier session-based revisions), by the end of stdio input, by the end of such an MCP session, by a closed response stream, or by shutdown of a stdio server process. A cancellation affects only a call of the same session and credential; one that does not reach the process holding the call, for example on another replica, leaves the call to end at the client deadline. No result and no notification follow a cancellation. A shared-client transport failure, including deadline expiry, is an `isError` result carrying a fixed content-free client error, never a `wait` outcome; its shape is the [client-origin failure record](#client-and-local-validation-failures), and the MCP boundary reports it once. What the skills teach, in order: (1) the DSL in [dsl.md](dsl.md) by example, including presets and artifact types; (2) the authoring loop: write Python, `kora_compile`, fix `DSLnnn`/`IRnnn` findings using their segmented `path`, code-point `offset` and optional source `location`, preserving unknown locations as null, write scenarios, `kora_test` until every scenario passes (a call cut off by the client's tool-call timeout, or scenarios that keep returning `error`, are reported, and a long suite runs with `kora test --json`), `kora_compile` again after any source edit so that the document planned and deployed is compiled from the tested sources, `kora_plan`, `kora_deploy`; (3) the operating loop: `kora_trigger`, which returns at once, then follow the run with `kora_runs`, `kora_inspect` and `kora_cost`, answering approvals only when the user asks for it and only with a token that carries `approve`. The loop branches on the start outcome: an accepted run is followed; a skip (`run_id: null`) or a refusal is reported, and `run_backlog_full` is retried with the same key and params only when the user asks. An accepted run is followed with `kora_runs` and `wait: needs_person`, which also ends when the run finishes, passing `wait_timeout` only to stay within the remaining waiting budget. When a person is needed it reports the exact pending count and bounded sample from `pending_approvals`, labels an incomplete sample and gives its scoped continuation command. It does not automatically enumerate all requests/details. Explicit inspection of one selected approval uses the cumulative eight-read/4-MiB-JSON/256-KiB-content budget, context-fit and complete-binding rules of [bounded operating references](bounded-read-projections.md#8-client-parity-and-local-effects); unavailable or incomplete values cannot authorize a response; `API005` on a response means the token lacks `approve`, so it points the user to `kora approve` or the console, and `API006` means the request changed, so it reads it again and reports. Future product-reference generation and error-hint coverage includes user-requested safe API011 retry, unknown API010/API011 outcome, same-key receipt recovery, changed authority, and refusal of automatic retry. The skill text is derived from the same reference material as `kora_reference`, so both stay in sync; skills are files in each harness's own format and nothing else (current contract [api-and-agent-surface](api-and-agent-surface.md)). They are installed in the user's own session, never into the sessions kora runs as nodes.

## 6. Web console (FR-7.3, FR-11.5, NFR-13.1)

`kora web` is the React console served by `kora api` ([stack reference](../architecture/detailed.md#stack-per-component)). In MVP it is a full console (requirements decision 21) held to the user-experience bar of NFR-13.1, and its design is decided before it is built: [docs/console.md](../../docs/console.md) records the design, [ADR-0015](../../docs/decisions/0015-web-console-design.md) the decisions that change the API, [knowledge/design/console/](../design/console/pages.md) the elements of every page with the route behind each, the state-to-colour mapping and the two pilot scenarios. Editing graphs in the console stays post-MVP (FR-1.5); graphs are authored in Python and deployed through the CLI or MCP. Every view is a composition of public API routes from section 2, called through the generated TypeScript client; no view needs a route of its own.

Detailed console contracts have one owner each: [pages](../design/console/pages.md) defines page composition, navigation, route-to-element mapping and interaction recovery; [states](../design/console/states.md) defines state words, colours, glyphs and attention reasons; [tokens](../design/console/tokens.md) defines exact styling and geometry; [pilot scenarios](../design/console/pilot-scenarios.md) define the cross-page acceptance journeys. Those files apply the owner decisions above. This section owns the API/client boundary, login, permitted mutations and runtime projections; it does not repeat the page inventory.

Live views read the newline-delimited JSON streams of `?follow=true` through `fetch` streaming; there is no WebSocket in MVP (section 1). The console's mutations in the MVP are four ([ADR-0015](../../docs/decisions/0015-web-console-design.md)): the approval response; `POST /namespaces/{ns}/graphs/{graph}/runs` from a form rendered from the graph's `params` schema, on the latest active version, with a fresh idempotency key; `POST …/nodes/{node_path}/retry` through an advisory API preview of strategy, exact observed affected counts and paged reset/recollection members; `POST …/runs/{run}/cancel` and `…/nodes/{node_path}/cancel` with a paged advisory preview and confirmation. Preview failure does not disable an otherwise authorized mutation; submission recomputes current effects. Each is the same API operation the CLI and MCP tools call, with the same permission checks; a rerun, graph deployment and every `platform` operation stay in the CLI and MCP.

Login (DD-19, amended 2026-10-16 by ADR-0011): `kora open` requests a one-time login link and opens it in the browser, and `GET /auth/session/{code}` exchanges the single-use code for a session; pasting the API token into the login form (`POST /auth/session`) is the fallback; either way the result is an **opaque server-side session cookie** (`SameSite=Strict`, `Secure`, HTTP-only); the approver recorded on the request is the token's owner (DD-32). Cookie-authenticated mutations carry CSRF protection (an `Origin` check plus a double-submit token), the SPA ships a Content Security Policy, and cookies are never accepted on Bearer-only API paths (current contract [ADR-0011](../../docs/decisions/0011-namespaces-and-personal-tokens.md)). A stale response shows the `API006` message and reloads the request. Every call the console makes is a public API call through the generated TypeScript client. The route/credential bridge between the cookie-authenticated browser and those Bearer-only operations is not yet specified; it is an [open implementation question](../architecture/detailed.md#open-implementation-questions), not permission to accept cookies on public Bearer paths or expose a token to browser JavaScript.

The [bounded console read contract](bounded-read-projections.md#7-target-cost-and-console-behavior) governs complete pinned scope painting, fair coalesced refresh, total deadlines and settlement, paged history retention, explicit owner-pinned content, structured-render limits and stale identity/navigation rejection. Target cost is API-owned and must name the displayed approval.

**Execution recovery in the console** (ADR-0017): show unknown execution and publication as a recovery reason, with last observation, retained scopes, domain/version, earlier dispatcher closure and evidence source. System and Targets include terminal runs that still hold capacity/targets. Offer the fully bound `kora reconcile` command for an operator; no fifth console mutation is introduced. A retry dialog explains deferred admission, and a refused rerun names blocking attempts. A missing heartbeat is never shown as a successful stop or automatic retry.

**Publication progress** (ADR-0016): on authenticated worker segment/report upload, reserved supervisor phase records become `runtime.phase` timeline rows and update the non-secret `attempt.scratch` summary atomically. Candidate/harness payloads cannot generate this reserved record kind. Existing attempt detail, events, logs and CLI/MCP projections expose supervisor-reported `phase`, `operation_id`, input/prepared/inspection/destination digests, inspected commit, trusted branch, outcome, `binding`, `binding_revision`, `credential_mode` the complete `principal: PrincipalRef`, `runtime_result_fields`, `runtime_result_digest` and saved VcsRef contract identity when available. Fields not yet observed remain absent; acquisition adds the principal without inventing one for earlier phases. Attempt/history projections read the same saved values under current read permissions, never today's aliases, and retain them after checkpoint release or payload expiry. The completed field set, digest and contract are frozen together only from the validated authenticated supervisor result, and are independent of the terminal report and of any later worker-enriched artifact digest. `awaiting_authorization` and `publication` are runtime phases, not new attempt states or user actions. The worker continues heartbeats before `finishing`; only authenticated supervisor results become platform publication facts. Structured runtime errors retain `code`, attempt location and the existing error class: `execution_protection_unsupported`, `workload_conflict` and `publication_authorization_mismatch` → `config_error`; `publication_input_unavailable` → `infrastructure`; `publication_conflict` → `artifact_invalid`. Recovery hints name the unavailable protected runtime, lost private input, mismatched binding or unexpected remote revision. Before fresh platform writes, all earlier dispatcher grants and operations must be closed; an API heartbeat alone is insufficient (ADR-0017). `Runtime.finalize` is an internal protocol operation, not a new HTTP/CLI/MCP mutation.

## 7. Parity checklist (FR-0.3, release gate)

Every added bounded read, filter and selected representation is covered by [the exact selector catalogue](bounded-read-projections.md#9-exact-client-read-selectors), including the generated TypeScript client. Query options do not create extra curated tools. Activation follows the named real consumer; no unimplemented parity case is passed.

The checklist is executed by a CI job on every release; a failing line blocks the release.

1. **Coverage**: every operation in the OpenAPI document is reachable through at least one CLI command and at least one MCP tool; the test derives the mapping from the shared client's call sites and fails on an uncovered operation (DD-28). Exclusions identify operations by method and purpose: worker registration and claim, service-only attempt heartbeat/report/upload and resource and retained-grant reads (`GET /attempts/{att}/resources/{sha256}`, `GET /attempts/{att}/grants`), the infrastructure probes `GET /healthz`, `GET /readyz` and `GET /metrics` (parity only, with no authentication exemption), and frontend-only sign-in operations: `POST /auth/login-links`, `GET /auth/session/{code}`, `POST /auth/session` and `DELETE /auth/session` (ADR-0011). Do not exclude path families: `GET /workers`, user attempt reads and versioned/evidenced attempt reconciliation remain user/operator operations covered by CLI and MCP (operator operations through `kora_admin`). `kora open` remains a convenience over the excluded sign-in operations, not an additional MCP parity obligation (current contract [api-and-agent-surface](api-and-agent-surface.md)). A **client-side operation** is one that is reachable through the CLI and an MCP tool and has no API operation by design, because the control plane must not perform it; its members in MVP are compiling Python sources (`kora compile`, `kora_compile`) and running a graph's behavioural scenarios (`kora test`, `kora_test`; issue #46), both of which import graph modules. `test_parity_client_side_operations` checks pair presence when compile/test are implemented; its unconditional check is that the OpenAPI document contains no operation that compiles sources or runs scenarios, so such a route cannot return silently (ADR-0002, amended 2026-10-16 and 2026-10-19).
2. **Schema coverage**: every API request and response model used by the CLI, MCP tools and worker client is a model the API exports; local failure records remain explicitly client-owned; the TypeScript client is regenerated and diffed.
3. With product harness skills/reference delivery, every operation appears in the skill reference (`kora_reference` topic index) with at least one example; the run read has one example per `wait` condition, including a wait that ends at `timeout` with `satisfied: false`, a `needs_person` wait that ends `run_finished` and the approvals list filtered by run.
4. The web console performs every action through the public API (verified by the generated client being its only HTTP dependency).
5. Every error code in the registry has a documented recovery hint. With product harness skills, every code and every `details.reason` value the skills branch on appears in the skill's error table; `IR027`'s hint is to simplify the expression or declare a smaller `maxItems` or `maxLength`.
6. No operation requires interactive input: CLI prompts are disabled under `--json`; `kora approve` fails with a structured error when required form fields are missing instead of asking.

## 8. Rate and size limits

[Bounded read projections](bounded-read-projections.md#1-response-budgets-and-completeness) owns metadata, selected bytes, comparison, finite query-work and client-retention bounds. Preserve the approval-list 100-row/2-MiB full-cost snapshot exception. The storage-inline threshold, worker upload caps and follow-stream record limits are distinct; none substitutes for an operation's response budget.

[VcsRef revision 1](artifacts/README.md#3-validation-descriptor) has a tighter 1 MiB cumulative raw/canonical payload cap and depth-16 predecode bound, applied before the generic artifact limits below. Exact-wire validation and all failure/cancellation staging cleanup remain outside run locks and preserve section 2 ownership.

[StructuredOutput revision 1](artifacts/StructuredOutput.md#1-payload-limits-and-immutable-identity) independently limits each cumulative logical typed JSON value to 1 MiB raw/canonical bytes, depth 16 and exact integers of at most 14,000 bits. This is not a new whole-list cap or a change to generic part/cumulative transport limits. Validation, canonical comparison and expensive schema/digest/summary work stay outside run locks and database resources; final acceptance rechecks current namespace/worker/grant/attempt authority. Storage promotion, unresolved mutation/deletion and cleanup reservations retain the published #229 fence and independently eligible owner rules. Generic framing/recovery remains #224. Direct and polled approval admission keeps its existing narrower signed-64-bit and data-bound checks, even for unused fields ([IR section 7.5](ir.md#75-projections-and-typed-conversion), scheduler section 16.3); a broader artifact domain does not raise those producer limits or undo earlier retained-source normalization.

Request bodies up to 4 MB (an IR with 1,000 nodes fits), except chunked segment, transcript and artifact uploads from workers; oversized tool results inside a segment are cut with a truncation marker; artifact inlining and storage references follow [data-model section 3](data-model.md#3-identifiers-and-keys); payload downloads use the authorized API route, which proxies storage access with no presigned-store redirect (DD-37, [artifact storage](protocols.md#7-artifact-storage-fr-44)); log streams page at 1,000 events. There are no per-token rate limits in MVP (DD-6), and no limit on concurrent held reads: bounded run-read waits, at most `45s` each (section 2), and `?follow=true` streams.

Worker uploads have their own caps ([worker route bodies](#worker-route-bodies-issue-139), issue #139):

| part | cap |
|---|---|
| `meta` part | 16 KiB |
| segment chunk | 1,000 events and 8 MiB, each event within the 64 KiB record cap of [protocols.md section 3](protocols.md#3-harness-adapter-fr-21-fr-33-fr-66-fr-91-dd-27) |
| artifact, execution-request or transcript `payload` part | 16 MiB; generic chunked non-final parts are exactly this width, final parts are the exact remainder |
| one artifact, execution request or transcript, over chunked parts (`upload_ref`, `index`, `final`) | 256 MiB; at most 16 public parts; over-cap opaque transcripts use the bounded terminal prefix/marker exception |
| open chunked uploads per attempt | the number of declared outputs plus 2 |
| staged bytes outstanding per worker | 1 GiB |
