# Qualified execution custody authority

Status: mechanism and design accepted on 2026-11-15 in [#1575](https://github.com/realkarych/kora/pull/1575#issuecomment-6886916062), closing [#1572](https://github.com/realkarych/kora/issues/1572). No authority journal, custody admission service, schema or placement profile is implemented or activated by this document. The [native companion](execution-custody-native.md) under #1580 specifies the concrete persistence and recovery refinement [accepted in #1586](https://github.com/realkarych/kora/pull/1586#issuecomment-6894239462). The [recovery-priority amendment](execution-custody-recovery-priority.md) specifies the v2 installation and handoff in the qualified PostgreSQL pool. The [source inventory](../research/execution-custody-authority-2026-11-15.md) identifies existing and missing producers.

This accepted design specializes [execution content](execution-content.md#7-activation-and-complete-implementation-deliveries) and the [metadata durability and continuity requirements](data-model.md#durable-storage-address-coordination). [ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md), [ADR-0005](../../docs/decisions/0005-eleven-protocols-with-conformance-suites.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md), [ADR-0018](../../docs/decisions/0018-immutable-attempt-history.md) and [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) remain governing. Unknown evidence preserves witnesses, fences and charges. A walking-skeleton deployment receives no durability exception.

## 1. Decision and scope

The accepted mechanism is a core-owned durable authority journal outside the metadata database's restore set, coupled to each participating metadata commit and to actual issuer lifetime ownership. It supplies an independent last-relied-on frontier. A row inside the database being restored cannot supply that independence; the local provider's private epoch does not represent metadata history.

The first accepted qualification profile places every participating API, scheduler, recovery and migration process on one host with the same local authority journal and one local physical storage domain. Aliases of that domain share its identity. Processes remain separate as in ADR-0003; standalone may combine them. PostgreSQL may be on another host, but remote server-side transaction settlement remains a separate required producer. This is an accepted qualification boundary, not a change to kora's accepted deployment shapes or S3 choice. Multi-host core, several independent physical domains, authority relocation and S3 admission need their own concrete ownership/continuity design before activation. Local locks cannot qualify them.

The owner accepted this additional persistent owner and first-profile placement restriction in #1575. Neither an operator boolean nor a settings check can authorize continuation after authority continuity becomes uncertain. Supporting every accepted deployment shape still requires a broader mechanism before those placements activate. No ADR, supported platform or guarantee is amended here. Native format/method approval and a compliant implementation plan remain separate from this mechanism's acceptance.

The journal is additional recovery state, not payload storage, an execution registry or a replacement for typed owners. #216 remains the integration owner, #867 owns graph staging, and #1320 owns the shared deletion-intent and acknowledgment representation. This design defines prerequisites for that handshake without introducing another delete format. Workers retain HTTP-only access and receive no journal, database or provider credentials.

## 2. Independent identities and evidence

| Identity or fact | Producer and immutable binding | Verifier and authority limit |
| --- | --- | --- |
| Installation journal identity | New provisioning producer creates one random identity in a private, natively anchored directory and pins the one metadata installation and resolved `StorageIdentity`. | Core composition verifies the actual canonical journal, native anchors and physical provider identity. Copying identifiers into another directory or database is not provisioning. |
| Metadata authority generation | New journal producer advances a positive signed-64 generation under exclusive lifetime ownership; never wraps or reuses it. | Every process captures it once before registering any work. A later mismatch permanently closes that process's useful gate. |
| Custody frontier | New journal record and metadata singleton share the exact original commit token, previous frontier and next sequence. | Native commit/recovery producer verifies the same authority, exact transaction outcome and coherent image. A greater allocator value or equal sequence alone is insufficient. |
| Core issuer | New durable registration binds journal identity, authority generation, non-reused issuer sequence and native host/boot/process-start identity. | A lifetime owner and bounded registry account for ordinary participants, including migration; the separate fixed recovery owner below accounts for cleanup/bootstrap without consuming an ordinary slot. Worker lease/dispatcher identity is separate. |
| Concrete receiver instance | Core assigns a non-reused sequence within its issuer and binds it to the actual constructed receiver and physical domain. | Each invocation gate checks its exact captured instance; immutable semantic-operation provenance does not authorize another invocation. The provider checks its own private immutable epoch. No public provider-epoch accessor currently exists. |
| Original byte operation | Existing `StorageOperationRef`, exact arguments, stage/address incarnation and original core issuer/receiver binding, saved before dispatch. | Core admission checks original custody; the provider independently validates reference/request binding and returns its own exact receipt. |
| Original persisted outcome | Typed metadata outcome and revision in the qualified commit; the journal confirms its frontier before it can release another witness. | Recovery reads the original saved outcome. Current object existence, current content generation and diagnostic logs are not replay authority. |
| Issuance closure | New irreversible per-issuer gate closure plus enumeration and actual settlement of all its dispatch owners; native process exclusion where it cannot cooperate. | Core acknowledges only the exact closed operation set. Provider retirement and exclusive effect/reader ownership still prove provider closure independently. |

All journal records are closed, versioned, content-free records. The accepted fixed bounds are a 16 KiB/depth-16 record envelope, one confirmed frontier and one pending transaction, 64 ordinary participant slots, and one separately reserved recovery-owner slot for the installation; saturation refuses before allocating tasks, connections or receiver resources. Slot reuse requires complete prior issuer closure and a new monotonic issuer sequence. Exhausted authority, frontier, issuer, receiver or invocation counters close new admission without wraparound. These are accepted deterministic bounds, not measured memory or throughput guarantees.

`upload_operation` and `content_issuer` need the actual core receiver-instance binding, not an invented provider epoch field. The provider-private epoch remains immutable inside the receiver and enforces the existing [local lifecycle](protocols.md#74-local-provider-implementation-contract-issue-255). Reconstructing a receiver is an explicit, bounded core transition after actual old-resource closure; it cannot change the issuer or refresh an old invocation's authority.

## 3. Journal ownership and commit protocol

The journal's selected native implementation is a separate private local SQLite database with an anchored, non-replaceable lifetime-lock file. Its native transactions use a separately qualified FULL-synchronization profile, including macOS full-sync, actual journal/directory persistence and supported filesystem/device behavior. This is a new core producer, not access to the provider's private database. A successful SQL call or `fsync` request alone is not its physical qualification. The [native companion](execution-custody-native.md#2-native-records-and-versions) specifies the accepted exact schema and filesystem/commit procedure; their implementation and migration count as production code.

One native commit owner serializes all participating metadata writes, including ordinary writers, maintenance and recovery. Ordinary commit admission remains nonwaiting and refuses before allocating a task or database checkout on contention. The [priority contract](execution-custody-recovery-priority.md#one-ordered-recovery-request) governs the pre-allocation checks and the reserved coordinator's native wait. The [qualified PostgreSQL pool owner](execution-custody-recovery-priority.md#postgresql-admission-and-release) arbitrates the actual checkout for both readers and writers with their original deadline bounds. Closed-admission schema provisioning uses its separately owned migration lease. Reducing serialization requires a separately reviewed independence proof and owner-approved contract change.

One native commit owner holds admission through pending-record persistence, metadata completion and frontier settlement. It acquires that admission before any metadata checkout or run/scope/address lock. Existing metadata lock order remains unchanged within the transaction. Journal transactions are short and close between phases. No provider call, payload validation or response delivery occurs while a metadata transaction, connection, cursor or scope lock is held. Cancellation never transfers the native commit owner's resources to a second writer.

1. Before opening a metadata write, verify journal/lifetime ownership, the exact authority generation, last confirmed frontier and absence of an unresolved pending transaction. After acquiring the actual native transaction, capture its original identity and check all applicable durability settings on that writer, including replacement connections.
2. Persist one journal pending record containing the original commit token, previous and next frontier, authority/issuer identity and the exact native completion owner. Do this before dispatching COMMIT. The metadata transaction writes that token/frontier into its singleton atomically with all domain changes. A failed pending persistence prevents COMMIT and leaves rollback under the original native owner.
3. Recheck native durability at the actual metadata commit boundary. Settle the original COMMIT or rollback, release its database resources, then durably confirm or abort the pending journal record. Confirm only from the exact successful native outcome or the qualified recovery path below. Aborting requires affirmative rollback/no-dispatch evidence, not a missing row after an uncertain restart.
4. Only after journal confirmation may a successful response or provider permit rely on that metadata result. Before provider entry or last-witness release, a short guarded read validates the current authority, confirmed frontier and exact saved custody/outcome. It releases database resources before calling the provider. The issuer's lifetime and operation ownership remain held across the call; an authority rotation cannot race through them. The persisted per-operation issuance gate and registered dispatch ownership also prevent a concurrent acknowledgment from declaring that operation closed.

A later metadata commit cannot erase the evidence needed to resolve an earlier pending one: there is only one such transaction and further writes are refused until it settles. Compaction replaces the previous confirmed frontier only after both the native metadata outcome and the journal advancement are durable. Original operation outcomes continue to live in their typed owners for as long as replay/retention requires; the frontier is not an ever-growing operation ledger.

Every writer route must participate before composition activates. SQLite connection, checkpoint, autocommit/migration and maintenance paths need actual coverage; PostgreSQL includes logged custody/allocator tables, pooled and dedicated migration backends, session/transaction overrides and server durability. A nontransactional migration cannot silently bypass the handshake: fence useful effects, close participating issuers, and retain the old authority until a qualified whole-image transition and new generation are established. If that migration path has no such producer, it is unsupported while custody is active. External database administrators and replacement/restore tools remain trusted operators and must use the qualified offline procedure; arbitrary live writes are not a supported profile.

## 4. Startup, restore and original COMMIT settlement

Fresh provisioning is allowed only for a demonstrably new empty metadata installation and new empty physical storage domain. It persists the initial deny latch and the journal binding in the [v2 provisioning order](execution-custody-native.md#41-provisioning-and-ordinary-startup) before permitting the first participating metadata commit. A missing journal beside an existing domain is a recovery failure, never permission to initialize another authority. Partial provisioning keeps effect admission closed until its original identity and outcome are resolved.

The exclusive recovery coordinator verifies and reconciles the v2 latch and journal under [native priority startup and successor rules](execution-custody-recovery-priority.md#native-failure-cancellation-and-fork). Restart verifies unchanged native journal/provider anchors and the coherent metadata image, reconciles the pending record, and establishes closure of prior issuers before advancing the authority generation. It does not infer closure from a PID alone, a timer, a receiver exception or an expired lease. A joining process in a still-live generation registers under that generation's lifetime protection and verifies current latch permission before dispatch. A previously registered process never adopts a later generation in place.

Restore requires a new supported offline producer which excludes all previous writers/issuers and binds the complete native image to its source authority and the journal frontier. SQLite recovery includes the correct WAL state and allocator, not a copied main file alone. PostgreSQL recovery includes the complete consistent database/WAL state, allocator and original commit settlement; backup-manifest validity alone is insufficient. Selective table restore, marker copying, allocator repair and unqualified standby promotion cannot qualify the image. These producers are missing today.

| Observed state | Required transition and retained evidence |
| --- | --- |
| Confirmed journal frontier equals a qualified coherent metadata image; no pending record | May complete restart only after the original issuer/effect closure and current durability qualification. Equality alone does not establish image provenance. |
| Lost COMMIT response; exact pending token is present in the original qualified authority | Resolve actual native completion and durable persistence, then confirm that exact journal transition. Do not allocate another token or repeat the domain mutation. |
| Pending token is absent after crash or restore | Keep pending and refuse dependent writes/effects. The old frontier may mean rollback, or a successful COMMIT followed by restoration of an older image. Only affirmative original rollback/no-dispatch evidence can clear it. |
| Allocator rewound | Refuse address admission and authority continuation; keep original operations, fences and charges. A new allocator seed does not repair history. |
| Equal allocator high water but missing owner, stage, intent or generation state | Reject the image even if its settings pass. The qualified whole-image producer and external confirmed frontier are both required. |
| Earlier core process or database COMMIT can still act | Keep lifetime/commit ownership unresolved; do not rotate authority, issue replacement effects or release the last witness. |
| Provider root/manifest lineage differs or cannot be established | Refuse the profile. Copying `StorageIdentity`, opening a fresh receiver or observing equal payload bytes cannot transfer authority. |
| Settings downgrade or actual connection/profile mismatch | Fence useful admission immediately; settle or retain each original native operation under its owner. Stronger later settings do not retroactively qualify an earlier commit. |
| Journal missing, damaged, substituted or known rolled back | Refuse continuation. Do not recreate it from the metadata singleton. Recovery needs a separately accepted external source of continuity. |
| Cancellation or deadline during a commit, provider call or cleanup | Close useful dispatch; retain admission, native work and evidence until actual settlement. Timeout is neither rollback nor effect closure. |
| Shutdown | Seal admission, close gates, settle native commits, readers and provider jobs, persist eligible outcomes/closure, then release lifetime ownership. Unresolved work prevents a false completed shutdown acknowledgment. |

For SQLite, the native completion owner must distinguish successful COMMIT from confirmed rollback before releasing its writer. For remote PostgreSQL, client disappearance is insufficient: qualification must bind backend start identity and original transaction to server-side completion, including a COMMIT already accepted by the server. Terminating a client connection, checking that its PID disappeared or reading a new session's settings does not supply this evidence. If the exact original outcome cannot be resolved, the single pending record remains and custody admission stays closed. This conservative state is permitted; availability is not fabricated by retrying an ambiguous mutation.

The journal is outside the metadata backup/restore set by deployment rule, not physically impossible to roll back. A simultaneous undetected rollback of journal, metadata and provider cannot be detected by comparing those copies. This profile excludes that continuation path and requires actual preservation of the independent journal; it does not promise resistance to a trusted operator forging or rolling back every source. Supporting joint restore would require a further independent source and a new owner decision. The profile's physical qualification must still establish crash durability of the journal itself; exclusion of operator rollback is not an exemption from crash safety.

## 5. Issuers, receiver closure and acknowledgment

Each participating process retains a noninheritable lifetime ownership descriptor from registration through actual closure, with a fixed native host/boot/process-start binding. Authority rotation needs exclusive ownership; a paused old process holding a descriptor therefore prevents rotation. Registration and rotation serialize under the same native ownership mechanism. Process spawning must not leak descriptors or an initialized issuer/receiver into children. A killed process can release its local descriptors, but pending remote database work and provider evidence still need their own settlement.

Within an authority, the process issuer gate and each bounded semantic operation gate can only move from open to closing to closed. Dispatch requires both gates open and registers its actual owner before entry. Closing a stage or deletion permanently closes all its operation gates and settles every registered issuer for that exact operation set; it does not require stopping unrelated work in an otherwise open process. Process shutdown or authority loss closes the whole issuer gate. No closed operation gate can reopen through a different receiver. Closing the whole issuer prevents all new useful calls and receiver reconstruction for useful work. Control operations have their own original identities and remain accounted until settlement. A bounded dispatcher set accounts for background native futures and readers even after the requesting coroutine returns or is cancelled. Actual `aclose` completion, not merely calling it, releases a receiver's resources. The durable issuer row remains while any unresolved operation references it.

The issuer record owns a monotonic receiver-sequence allocator and at most one current receiver slot in state active or closing. Its process/authority identity never changes. Each original operation retains its immutable origin provenance; each actual invocation captures its own `(issuer_id, receiver_sequence, invocation_sequence)` and registered dispatch owner before the positive issuance check. The invocation sequence is non-reused within its issuer; the reserved recovery owner has its own non-reused sequence. The original operation identity/request/outcome and an already captured invocation binding never change. Replacing the current receiver pointer cannot refresh either of them. Replacement first seals admission on the old receiver, closes its actual jobs/readers/executors, and durably records the closure fact for every retained operation that referenced it. Only then may one qualified transaction clear the old current slot and register a fresh sequence for the newly constructed receiver. Failure or uncertain persistence leaves replacement unadmitted. No historical receiver-row ledger is required: retained original operations hold their own origin/closure facts, and disposable current-slot state is bounded to one per ordinary issuer. Unknown operation outcomes remain unknown even when receiver resources are closed. Recovery may observe their exact original receipts through a permitted new receiver. Where the owning contract permits retry while issuance remains open, the same semantic operation may receive a new invocation after capture-before-positive-check; this is not reuse of an old invocation binding. The bounded dispatch slot retains that invocation until its actual resources close, with no append-only invocation ledger. An unknown provider effect stays in the original charged intent and must satisfy provider closure before final acknowledgment. Closed issuance permits no new effect-producing invocation. New independently admitted semantic operations may also bind the new receiver, including later parts of an existing open stage.

Stage retirement and delete acknowledgment retain the existing provider contract. Core first confirms the original outcome and irreversible issuance closure in a qualified commit, then invokes the exact acknowledgment without database resources held. The provider separately proves all issued effects/readers closed and compacts under its private epoch rules. Core finally persists the acknowledgment before removing its own last guard or charge. Lost acknowledgment response keeps the original guard and retries only the exact authorized acknowledgment; it cannot authorize a new retirement or deletion. #1320 specifies the common deletion representation and durable handshake details.

The accepted 64 ordinary participant slots bound live and unresolved issuers together, not just currently connected processes. Each receiver and operation also consumes the already specified domain-wide execution-content and provider capacities. One process owns at most one current local receiver for the domain; replacement closes actual old resources first and preserves the existing limit of three reconstructions within the original finite deadline. No new count increases any existing data/control/reader allowance. Full registries refuse new participants instead of evicting unresolved history.

The single reserved recovery owner has an exclusive native coordinator lease and its own non-reused incarnation sequence. It can bootstrap with all 64 ordinary records occupied: it reads retained custody, resolves original native outcomes, persists verified recovery/closure facts and performs only authorized observation, retirement, exact acknowledgment and a fresh invocation of an already admitted exact deletion. That deletion must use the unchanged saved request, operation, incarnation and generation: capture the actual receiver first, then positively check that the exact intent is present, settlement absent, the fence still points to that incarnation/pending generation, and current authority/durability proofs hold. Release database resources before dispatch. Missing/settled custody, unknown COMMIT or closed issuance refuses it. This supplies no authority to admit a new deletion or change #1320's immutable intent/write-once settlement format. It grants no new upload, promotion or ordinary writer admission. It uses the same metadata commit handshake and the existing reserved provider control capacities, rather than bypassing an unresolved COMMIT or borrowing useful capacity. The [native and pool priority contract](execution-custody-recovery-priority.md#one-ordered-recovery-request) gives ready recovery the next eligible checkout opportunity. An unresolved native COMMIT remains blocking. Ordinary admission resumes only after verified withdrawal and applicable capacity and authority checks.

The recovery slot retains at most one active control-invocation binding and one current native coordinator identity; the semantic operation remains in its original typed custody. A new coordinator must first exclude the old native coordinator under the exclusive lease. It preserves any original pending transaction/invocation binding and may only observe or settle that invocation until its actual dispatch resources close; it cannot replace the semantic operation or start a second live invocation. Once native closure is established, a fresh invocation of that same admitted deletion is allowed only through the positive check above. A returned pending/unavailable observation does not prove the domain effect closed: the original intent keeps that effect and its charge, while the completed observation invocation releases its control slot so the recovery walk can move to another intent. An unknown remote COMMIT still blocks writes. A native observer for that original outcome is owned by this one recovery slot, so observation does not require an ordinary participant slot. No list of failed coordinator incarnations accumulates: the original operation retains its original identity, and a previous coordinator identity is discarded only after affirmative native exclusion/closure of its dispatch resources. If that cannot be established, recovery remains unresolved for that actual safety reason, not merely because the ordinary registry is full. Repeated coordinator crashes must preserve this fixed bound and every original operation. Original operation provenance and outcomes stay in their existing typed records; current invocation ownership does not rewrite them.

Journal and metadata ownership do not supply host containment. Installed core/provider code and operators remain trusted under [the threat model](../../docs/threat-model.md), especially TM-09, TM-10, TM-11 and TM-12 and its storage boundaries. Candidate content, workers and API callers cannot choose or refresh these identities. Logs contain only bounded safe state/reason/count fields under [observability](observability.md); journal paths, tokens, payload digests, stored requests and backend exceptions are not diagnostic fields. Log failure cannot delay core progress or manufacture closure.

## 6. Qualification and delivery limits

The following are future acceptance cases, not test results. Each implementing issue owns real source producers, its exact activation condition and executable evidence. Existing SQLite/PostgreSQL and Linux/macOS obligations remain. Existing scheduled/manual provider studies keep their scope and schedule; this document adds no new CI campaign or merge gate.

| Required case | Producer and checkable decision |
| --- | --- |
| `test_custody_journal_covers_all_writers` | Real writer, migration, recovery, maintenance and replacement paths cannot commit a relied-on change outside the handshake. Verify both databases and exact resource release. |
| `test_custody_ack_survives_system_crash` | Installation qualification crashes after acknowledged commit before an unrelated flush/checkpoint and recovers the original journal, metadata and provider state. Process termination alone cannot pass it. Record build, VFS/filesystem/device, synchronization and server/replica inputs. |
| `test_custody_lost_commit_never_creates_replacement` | Real native barriers lose the response before/after COMMIT, resolve the exact original outcome or retain pending. Cover remote PostgreSQL backend survival and cancellation/shutdown ownership. |
| `test_custody_rejects_incomplete_restore` | Real native consistent-image producers exercise old frontier, rewound allocator and equal-high-water images missing custody. Copied marker/selective restore cannot pass as a qualified image. |
| `test_custody_old_issuer_cannot_refresh_authority` | Keep a real prior process paused with queued work; demonstrate rotation refusal and no useful fresh receiver under a newer generation. Verify no inherited ownership descriptor can counterfeit closure. |
| `test_custody_provider_release_requires_both_closures` | Real local storage, delayed effect/reader and saved outcome; neither core gate closure nor provider epoch alone releases the last witness. Exercise lost acknowledgment and exact replay. |
| `test_custody_journal_loss_refuses_existing_domain` | Missing/substituted journal, partial provisioning and provider lineage mismatch cannot create a replacement authority. Joint rollback remains outside the claimed profile. |
| `test_custody_capacity_releases_only_settled_owners` | Fill all 64 ordinary slots with unresolved issuers, terminate their processes, and restart the reserved recovery owner. Include a deletion committed before first dispatch and a deletion whose receiver becomes stale after another release. The reserved owner invokes the same saved request after fresh capture-before-check, preserves original identity, and makes cleanup progress while new useful admission stays refused. A returned pending observation permits cursor progress with the old effect still charged; repeated coordinator crashes preserve the single active invocation and original custody. Also cancel/shut down with blocked native work and refuse before extra allocation. Repeated settled operations stabilize disposable journal/issuer/receipt state; accepted history is distinct. |
| `test_custody_receiver_replacement_preserves_original_bindings` | Release a stage/delete so the provider epoch advances; close the old receiver, register a new sequence under the same issuer, and continue independently authorized work. Original operation provenance and old invocation bindings remain unchanged; only a fresh positive check may authorize another invocation while issuance is open. Closed issuance cannot regain useful dispatch. Per-operation closure leaves unrelated open operations usable. |

Deterministic capacity, exact ownership, integrity and recovery assertions are blocking when their implementation activates. RSS, native sync/checkpoint waits and transaction throughput are diagnostics unless an existing approved requirement supplies the method. Serialization must also satisfy applicable NFR-3 admission/query requirements at the real consumer; this design does not waive them or claim that they pass. Measure ordinary traffic alongside custody traffic, with cold startup reported separately.

The [updated native inventory and sizing](../research/execution-custody-native-plan-2026-11-15.md#complete-delivery-and-size) does not establish a sub-1,000-line implementation. No helper-only proof object, journal without a consumer, caller-provided durability flag or fake-only integration is a complete delivered result. The mechanism/placement is accepted; before production work, each complete implementation issue still needs an approved plan within the repository limit, or an explicit bounded indivisibility exception. Design approval alone supplies neither exception nor native qualification.
