# Qualified execution custody authority

Status: proposed design for owner review under [#1572](https://github.com/realkarych/kora/issues/1572), 2026-11-15. Approval of the preparation plan is not acceptance of the mechanism below. No authority journal, custody admission service, schema or placement profile is implemented or activated by this document. The [source inventory](../research/execution-custody-authority-2026-11-15.md) identifies the existing producers and the missing ones.

This proposal specializes [execution content](execution-content.md#7-activation-and-complete-implementation-deliveries) and the [metadata durability and continuity requirements](data-model.md#durable-storage-address-coordination). [ADR-0003](../../docs/decisions/0003-scheduler-and-workers-over-http.md), [ADR-0005](../../docs/decisions/0005-eleven-protocols-with-conformance-suites.md), [ADR-0017](../../docs/decisions/0017-execution-uncertainty-and-safe-replacement.md), [ADR-0018](../../docs/decisions/0018-immutable-attempt-history.md) and [ADR-0022](../../docs/decisions/0022-inherited-execution-deadlines.md) remain governing. Unknown evidence preserves witnesses, fences and charges. A walking-skeleton deployment receives no durability exception.

## 1. Decision and scope

The proposed mechanism is a core-owned durable authority journal outside the metadata database's restore set, coupled to each participating metadata commit and to actual issuer lifetime ownership. It supplies an independent last-relied-on frontier. A row inside the database being restored cannot supply that independence; the local provider's private epoch does not represent metadata history.

The first proposed qualification profile places every participating API, scheduler, recovery and migration process on one host with the same local authority journal and one local physical storage domain. Aliases of that domain share its identity. Processes remain separate as in ADR-0003; standalone may combine them. PostgreSQL may be on another host, but remote server-side transaction settlement remains a separate required producer. This is a proposed qualification boundary, not a change to kora's accepted deployment shapes or S3 choice. Multi-host core, several independent physical domains, authority relocation and S3 admission need their own concrete ownership/continuity design before activation. Local locks cannot qualify them.

Owner acceptance must explicitly decide whether this additional persistent owner and placement restriction are acceptable. The alternative is to leave address-fenced effects unavailable after authority continuity becomes uncertain; neither an operator boolean nor a settings check can authorize continuation. If the owner requires the first implementation to support every accepted deployment shape, this proposal is insufficient and implementation remains blocked pending a broader mechanism. No ADR, supported platform or guarantee is amended here.

The journal is additional recovery state, not payload storage, an execution registry or a replacement for typed owners. #216 remains the integration owner, #867 owns graph staging, and #1320 owns the shared deletion-intent and acknowledgment representation. This design defines prerequisites for that handshake without introducing another delete format. Workers retain HTTP-only access and receive no journal, database or provider credentials.

## 2. Independent identities and evidence

| Identity or fact | Producer and immutable binding | Verifier and authority limit |
| --- | --- | --- |
| Installation journal identity | New provisioning producer creates one random identity in a private, natively anchored directory and pins the one metadata installation and resolved `StorageIdentity`. | Core composition verifies the actual canonical journal, native anchors and physical provider identity. Copying identifiers into another directory or database is not provisioning. |
| Metadata authority generation | New journal producer advances a positive signed-64 generation under exclusive lifetime ownership; never wraps or reuses it. | Every process captures it once before registering any work. A later mismatch permanently closes that process's useful gate. |
| Custody frontier | New journal record and metadata singleton share the exact original commit token, previous frontier and next sequence. | Native commit/recovery producer verifies the same authority, exact transaction outcome and coherent image. A greater allocator value or equal sequence alone is insufficient. |
| Core issuer | New durable registration binds journal identity, authority generation, non-reused issuer sequence and native host/boot/process-start identity. | A lifetime owner and bounded registry account for every participant, including cleanup and migration. Worker lease/dispatcher identity is separate. |
| Concrete receiver instance | Core assigns a non-reused sequence within its issuer and binds it to the actual constructed receiver and physical domain. | The core gate checks the exact instance; the provider checks its own private immutable epoch. No public provider-epoch accessor currently exists. |
| Original byte operation | Existing `StorageOperationRef`, exact arguments, stage/address incarnation and original core issuer/receiver binding, saved before dispatch. | Core admission checks original custody; the provider independently validates reference/request binding and returns its own exact receipt. |
| Original persisted outcome | Typed metadata outcome and revision in the qualified commit; the journal confirms its frontier before it can release another witness. | Recovery reads the original saved outcome. Current object existence, current content generation and diagnostic logs are not replay authority. |
| Issuance closure | New irreversible per-issuer gate closure plus enumeration and actual settlement of all its dispatch owners; native process exclusion where it cannot cooperate. | Core acknowledges only the exact closed operation set. Provider retirement and exclusive effect/reader ownership still prove provider closure independently. |

All journal records are closed, versioned, content-free records. Proposed fixed bounds are a 16 KiB/depth-16 record envelope, one confirmed frontier and one pending transaction, and 64 participant slots for the installation; saturation refuses before allocating tasks, connections or receiver resources. Slot reuse requires complete prior issuer closure and a new monotonic issuer sequence. Exhausted authority, frontier, issuer or receiver counters close new admission without wraparound. These are proposed deterministic bounds requiring owner acceptance, not measured memory or throughput guarantees.

`upload_operation` and `content_issuer` need the actual core receiver-instance binding, not an invented provider epoch field. The provider-private epoch remains immutable inside the receiver and enforces the existing [local lifecycle](protocols.md#74-local-provider-implementation-contract-issue-255). Reconstructing a receiver is an explicit, bounded core transition after actual old-resource closure; it cannot change the issuer or refresh an old invocation's authority.

## 3. Journal ownership and commit protocol

The journal's proposed native implementation is a separate private local SQLite database with an anchored, non-replaceable lifetime-lock file. Its native transactions use a separately qualified FULL-synchronization profile, including macOS full-sync, actual journal/directory persistence and supported filesystem/device behavior. This is a new core producer, not access to the provider's private database. A successful SQL call or `fsync` request alone is not its physical qualification. The exact schema, filesystem operations and migration are owned by the implementing plan and count as production code.

The first profile serializes all metadata writes under one nonwaiting commit admission, including ordinary writers, maintenance, recovery and migrations. This deliberately avoids an unproven classification of which writes can affect custody. There is no admitted waiting queue; contention returns the caller's existing bounded busy/pending outcome before a database checkout. Read snapshots retain their existing limits. Reducing serialization later requires a separately reviewed independence proof and owner-approved contract change.

One native commit owner holds admission through pending-record persistence, metadata completion and frontier settlement. It acquires that admission before any metadata checkout or run/scope/address lock. Existing metadata lock order remains unchanged within the transaction. Journal transactions are short and close between phases. No provider call, payload validation or response delivery occurs while a metadata transaction, connection, cursor or scope lock is held. Cancellation never transfers the native commit owner's resources to a second writer.

1. Before opening a metadata write, verify journal/lifetime ownership, the exact authority generation, last confirmed frontier and absence of an unresolved pending transaction. Capture the original native transaction identity. Check all applicable durability settings on the actual writer, including replacement connections.
2. Persist one journal pending record containing the original commit token, previous and next frontier, authority/issuer identity and the exact native completion owner. Do this before dispatching COMMIT. The metadata transaction writes that token/frontier into its singleton atomically with all domain changes. A failed pending persistence prevents COMMIT and leaves rollback under the original native owner.
3. Recheck native durability at the actual metadata commit boundary. Settle the original COMMIT or rollback, release its database resources, then durably confirm or abort the pending journal record. Confirm only from the exact successful native outcome or the qualified recovery path below. Aborting requires affirmative rollback/no-dispatch evidence, not a missing row after an uncertain restart.
4. Only after journal confirmation may a successful response or provider permit rely on that metadata result. Before provider entry or last-witness release, a short guarded read validates the current authority, confirmed frontier and exact saved custody/outcome. It releases database resources before calling the provider. The issuer's lifetime and operation ownership remain held across the call; an authority rotation cannot race through them.

A later metadata commit cannot erase the evidence needed to resolve an earlier pending one: there is only one such transaction and further writes are refused until it settles. Compaction replaces the previous confirmed frontier only after both the native metadata outcome and the journal advancement are durable. Original operation outcomes continue to live in their typed owners for as long as replay/retention requires; the frontier is not an ever-growing operation ledger.

Every writer route must participate before composition activates. SQLite connection, checkpoint, autocommit/migration and maintenance paths need actual coverage; PostgreSQL includes logged custody/allocator tables, pooled and dedicated migration backends, session/transaction overrides and server durability. A nontransactional migration cannot silently bypass the handshake: fence useful effects, close participating issuers, and retain the old authority until a qualified whole-image transition and new generation are established. If that migration path has no such producer, it is unsupported while custody is active. External database administrators and replacement/restore tools remain trusted operators and must use the qualified offline procedure; arbitrary live writes are not a supported profile.

## 4. Startup, restore and original COMMIT settlement

Fresh provisioning is allowed only for a demonstrably new empty metadata installation and new empty physical storage domain. It persists the journal binding before permitting the first participating metadata commit. A missing journal beside an existing domain is a recovery failure, never permission to initialize another authority. Partial provisioning keeps effect admission closed until its original identity and outcome are resolved.

Ordinary restart acquires lifetime ownership for recovery, verifies unchanged native journal/provider anchors and the coherent metadata image, reconciles the pending record, and establishes closure of prior issuers before advancing the authority generation. It does not infer closure from a PID alone, a timer, a receiver exception or an expired lease. A joining process in a still-live generation registers under that generation's lifetime protection; a previously registered process never adopts a later generation in place.

Restore requires a new supported offline producer which excludes all previous writers/issuers and binds the complete native image to its source authority and the journal frontier. SQLite recovery includes the correct WAL state and allocator, not a copied main file alone. PostgreSQL recovery includes the complete consistent database/WAL state, allocator and original commit settlement; backup-manifest validity alone is insufficient. Selective table restore, marker copying, allocator repair and unqualified standby promotion cannot qualify the image. These producers are missing today.

| Observed state | Required transition and retained evidence |
| --- | --- |
| Confirmed journal frontier equals a qualified coherent metadata image; no pending record | May complete restart only after the original issuer/effect closure and current durability qualification. Equality alone does not establish image provenance. |
| Lost COMMIT response; exact pending token is present in the original qualified authority | Resolve actual native completion and durable persistence, then confirm that exact journal transition. Do not allocate another token or repeat the domain mutation. |
| Pending token is absent after crash or restore | Keep pending and refuse dependent writes/effects. The old frontier may mean rollback, or a successful COMMIT followed by restoration of an older image. Only affirmative original rollback/no-dispatch evidence can clear it. |
| Allocator rewound | Refuse address admission and authority continuation; keep original operations, fences and charges. A new allocator seed does not repair history. |
| Equal allocator high water but missing owner, stage, intent or generation state | Reject the image even if its settings pass. The qualified whole-image producer and external confirmed frontier are both required. |
| Earlier core process or database COMMIT can still act | Keep lifetime/commit ownership unresolved; do not rotate authority, issue replacement effects or release the last witness. |
| Provider root/manifest lineage differs or cannot be established | Refuse the profile. Copying `StorageIdentity`, opening a fresh receiver or observing equal payload bytes cannot transfer authority. |
| Settings downgrade or actual connection/profile mismatch | Fence useful admission immediately; settle or retain each original native operation under its owner. Stronger later settings do not retroactively qualify an earlier commit. |
| Journal missing, damaged, substituted or known rolled back | Refuse continuation. Do not recreate it from the metadata singleton. Recovery needs a separately accepted external source of continuity. |
| Cancellation or deadline during a commit, provider call or cleanup | Close useful dispatch; retain admission, native work and evidence until actual settlement. Timeout is neither rollback nor effect closure. |
| Shutdown | Seal admission, close gates, settle native commits, readers and provider jobs, persist eligible outcomes/closure, then release lifetime ownership. Unresolved work prevents a false completed shutdown acknowledgment. |

For SQLite, the native completion owner must distinguish successful COMMIT from confirmed rollback before releasing its writer. For remote PostgreSQL, client disappearance is insufficient: qualification must bind backend start identity and original transaction to server-side completion, including a COMMIT already accepted by the server. Terminating a client connection, checking that its PID disappeared or reading a new session's settings does not supply this evidence. If the exact original outcome cannot be resolved, the single pending record remains and custody admission stays closed. This conservative state is permitted; availability is not fabricated by retrying an ambiguous mutation.

The journal is outside the metadata backup/restore set by deployment rule, not physically impossible to roll back. A simultaneous undetected rollback of journal, metadata and provider cannot be detected by comparing those copies. This profile excludes that continuation path and requires actual preservation of the independent journal; it does not promise resistance to a trusted operator forging or rolling back every source. Supporting joint restore would require a further independent source and a new owner decision. The profile's physical qualification must still establish crash durability of the journal itself; exclusion of operator rollback is not an exemption from crash safety.

## 5. Issuers, receiver closure and acknowledgment

Each participating process retains a noninheritable lifetime ownership descriptor from registration through actual closure, with a fixed native host/boot/process-start binding. Authority rotation needs exclusive ownership; a paused old process holding a descriptor therefore prevents rotation. Registration and rotation serialize under the same native ownership mechanism. Process spawning must not leak descriptors or an initialized issuer/receiver into children. A killed process can release its local descriptors, but pending remote database work and provider evidence still need their own settlement.

Within an authority, the issuer gate registers every operation owner before dispatch and can only move from open to closing to closed. Closing prevents all new useful calls and receiver reconstruction for useful work. Control operations have their own original identities and remain accounted until settlement. A bounded dispatcher set accounts for background native futures and readers even after the requesting coroutine returns or is cancelled. Actual `aclose` completion, not merely calling it, releases a receiver's resources. The durable issuer row remains while any unresolved operation references it.

Stage retirement and delete acknowledgment retain the existing provider contract. Core first confirms the original outcome and irreversible issuance closure in a qualified commit, then invokes the exact acknowledgment without database resources held. The provider separately proves all issued effects/readers closed and compacts under its private epoch rules. Core finally persists the acknowledgment before removing its own last guard or charge. Lost acknowledgment response keeps the original guard and retries only the exact authorized acknowledgment; it cannot authorize a new retirement or deletion. #1320 specifies the common deletion representation and durable handshake details.

The proposed 64 participant slots bound live and unresolved issuers together, not just currently connected processes. Each receiver and operation also consumes the already specified domain-wide execution-content and provider capacities. One process owns at most one current local receiver for the domain; replacement closes actual old resources first and preserves the existing limit of three reconstructions within the original finite deadline. No new count increases any existing data/control/reader allowance. Full registries refuse new participants instead of evicting unresolved history.

Journal and metadata ownership do not supply host containment. Installed core/provider code and operators remain trusted under [the threat model](../../docs/threat-model.md), especially TM-09, TM-10 and TM-12 and its storage boundaries. Candidate content, workers and API callers cannot choose or refresh these identities. Logs contain only bounded safe state/reason/count fields under [observability](observability.md); journal paths, tokens, payload digests, stored requests and backend exceptions are not diagnostic fields. Log failure cannot delay core progress or manufacture closure.

## 6. Qualification and delivery limits

The following are future acceptance cases, not test results. Each implementing issue owns real source producers, its exact activation condition and executable evidence. Existing SQLite/PostgreSQL and Linux/macOS obligations remain. Existing scheduled/manual provider studies keep their scope and schedule; this document adds no new CI campaign or merge gate.

| Required case | Producer and checkable decision |
| --- | --- |
| `test_custody_journal_covers_all_writers` | Real writer, migration, recovery, maintenance and replacement paths cannot commit a relied-on change outside the handshake. Verify both databases and exact resource release. |
| `test_custody_ack_survives_system_crash` | Installation qualification crashes after acknowledged commit before an unrelated flush/checkpoint and recovers the original journal, metadata and provider state. Process termination alone cannot pass it. Record build, VFS/filesystem/device, synchronization and server/replica inputs. |
| `test_custody_lost_commit_never_creates_replacement` | Real native barriers lose the response before/after COMMIT, resolve the exact original outcome or retain pending. Cover remote PostgreSQL backend survival and cancellation/shutdown ownership. |
| `test_custody_rejects_incomplete_restore` | Real native consistent-image producers exercise old frontier, rewound allocator and equal-high-water images missing custody. Copied marker/selective restore cannot pass as a qualified image. |
| `test_custody_old_issuer_cannot_refresh_authority` | Keep a real prior process paused with queued work; demonstrate rotation refusal and no useful fresh receiver under a newer generation. Verify no inherited ownership descriptor can counterfeit closure. |
| `test_custody_provider_release_requires_both_closures` | Real local storage, delayed effect/reader and saved outcome; neither core gate closure nor provider epoch alone releases the last witness. Exercise lost acknowledgment and exact replay. |
| `test_custody_journal_loss_refuses_existing_domain` | Missing/substituted journal, partial provisioning and provider lineage mismatch cannot create a replacement authority. Joint rollback remains outside the claimed profile. |
| `test_custody_capacity_releases_only_settled_owners` | Fill participant/commit/domain allowances, cancel and shut down with blocked native work, and show refusal before extra allocation. Repeated settled operations stabilize disposable journal/issuer/receipt state; accepted history is distinct. |

Deterministic capacity, exact ownership, integrity and recovery assertions are blocking when their implementation activates. RSS, native sync/checkpoint waits and transaction throughput are diagnostics unless an existing approved requirement supplies the method. Serialization must also satisfy applicable NFR-3 admission/query requirements at the real consumer; this proposal does not waive them or claim that they pass. Measure ordinary traffic alongside custody traffic, with cold startup reported separately.

The [implementation inventory and sizing](../research/execution-custody-authority-2026-11-15.md#implementation-and-verification-status) does not establish a sub-1,000-line implementation. No helper-only proof object, journal without a consumer, caller-provided durability flag or fake-only integration is a complete delivered result. Before production work, the owner must accept the mechanism/placement and each complete implementation issue must have an approved plan within the repository limit, or an explicit bounded indivisibility exception. Design approval alone supplies neither exception nor native qualification.
