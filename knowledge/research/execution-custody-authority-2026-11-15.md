## Why the identities cannot be collapsed

The metadata authority, address-fence incarnation, original core issuer, concrete receiver instance, provider-private epoch and deletion generation describe different owners. The provider epoch changes during ordinary compaction and records no metadata transaction frontier. A core issuer can still possess queued work or construct a new receiver after its earlier receiver becomes stale. Replaying a settled provider receipt is also different from granting a new useful effect.

The accepted [address-continuity contract](../specs/data-model.md#durable-storage-address-coordination) requires coherent owner, stage, intent and generation state as well as the allocator. Two snapshots can have the same allocator high water while differing in later admissions, acknowledgments or releases. A current settings sample and a row placed only in the database being restored cannot independently distinguish those snapshots.

An independent continuity mechanism must therefore name its own persistence and rollback assumptions. Merely moving a boolean into another file, signing a digest, checking a backup manifest or comparing the provider's current epoch does not establish which metadata outcome was last relied on. Loss or rollback of the independent evidence must itself prevent new authority; it cannot authorize creating a replacement record for an existing physical domain.

## Native evidence limits

The following primary documentation was checked on 2026-11-15 to distinguish native mechanisms from installation qualification. It is not evidence that the current kora host or CI storage device meets a crash guarantee.

- [SQLite synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous) distinguishes WAL/FULL from WAL/NORMAL durability across operating-system failure or power loss. Its [full-sync and checkpoint settings](https://www.sqlite.org/pragma.html#pragma_fullfsync) describe requested synchronization behavior, not independent proof of a device's persistence.
- [SQLite WAL](https://www.sqlite.org/wal.html) describes checkpoint and WAL ownership. A kora qualification must include its actual participating handles and checkpoint paths, rather than infer coverage from one writer setting.
- [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html) states hardware assumptions and describes failure modes of locking and disk flushing. Its main algorithm discussion is for rollback-journal mode and is not evidence for kora's WAL path.
- [PostgreSQL 16 reliability](https://www.postgresql.org/docs/16/wal-reliability.html) describes the cache and storage layers below a commit. Verifying backend parameters does not independently verify those layers or a standby's retained commits.
- [PostgreSQL 16 backup verification](https://www.postgresql.org/docs/16/app-pgverifybackup.html) checks a base backup against its manifest. That can contribute backup-integrity evidence; it does not establish that the backup contains the latest custody relied on by core or that an earlier issuer can no longer act.

Future execution must distinguish four observations: requested database settings; actual synchronization/native settlement; coherent restored state relative to independently retained custody; and actual exclusion/closure of old issuers and provider effects. Each has a separate producer. Passing one cannot discharge the others.

## Implementation and verification status

No source, schema migration, dependency, API operation or runtime activation is part of #1572. The [proposed mechanism](../specs/execution-custody-authority.md) uses a new independent core journal, original-commit handshake and real issuer lifetime ownership. Its first qualification profile co-locates core writers on one host with one physical local storage domain; remote PostgreSQL still needs exact server-side settlement. It preserves separate API/scheduler processes and HTTP-only workers. It is not a qualification of multi-host core or S3 and does not amend their accepted product designs. The existing #1320 deletion-intent format and #216 ownership remain governing dependencies.

The alternative considered was continuation using only a metadata generation, provider epoch and operator confirmation. It cannot distinguish an incomplete restored image or exclude an old core which constructs a fresh receiver, so it cannot authorize effects. Refusal while evidence is unknown is safe but supplies no new usable admission service. A remote consensus/authority service might support more placements but would introduce another dependency and trust/operations boundary; this work does not select one.

The journal proposal adds persistent state, serializes metadata writes, requires preserving the journal independently of database restore and bounds the first qualification placement. Those are explicit owner decisions before implementation. It also corrects the earlier execution-content reference to a captured provider epoch: no public producer exists for that field. Core instead binds its concrete receiver instance and leaves provider epoch verification inside the existing provider. No storage protocol change is implied.

### Complete outcomes and size assessment

The following ranges are conservative planning estimates from the named missing responsibilities, not measured diffs or promises that individual rows are mergeable PRs. They include handwritten migrations and composition wiring. Tests and documentation are excluded only from the production-line count, never from delivery. Existing connection, locking and provider machinery is reused; none currently produces the missing global frontier or issuer closure.

| Required responsibility | Reusable source and new work | Estimated added plus deleted production lines |
| --- | --- | --- |
| Native journal, provisioning and bounded lifetime registry | Reuse existing native identity patterns; new closed journal schema/migration, anchored local persistence, registration/rotation, shutdown and composition ownership. Provider-private tables cannot be borrowed. | 550–900 |
| Complete metadata commit participation | Existing `db/connection.py`, transaction/maintenance and migration owners; new singleton migration, original-token handshake, all-writer admission and exact native settlement integration for both databases. | 500–850 |
| Real guarded stage lifecycle | Existing graph promotion custody/address sets and local storage; new core issuer/receiver ownership, durable dispatch/closure producer and actual outcome/acknowledgment integration. No public execution upload activation. | 450–800 |
| Coherent startup/restore and qualification integration | Existing native connection/provider identity inputs; new offline whole-image provenance, original pending-outcome resolution, configuration/diagnostics and actual startup consumer. | 400–750 |

The complete qualified admission/recovery outcome is therefore approximately 1,900–3,300 production lines before any newly discovered native boundary. The rows describe coupled responsibilities, not permission to merge four disconnected foundations. A journal-only PR, proof DTO, test-fixture consumer or temporary flag which bypasses missing qualification does not deliver this outcome. The earlier 650–950-per-component estimate in execution content did not account for these missing producers and cannot justify starting implementation.

No independently mergeable sub-1,000-line split for this complete first outcome is established by this inventory. Before code, either identify a smaller useful complete consumer with exact files and a credible complete-diff count, or present a bounded demonstrated indivisibility case for an explicit owner exception. This design requests no exception and does not claim indivisibility is proved. Native physical qualification also needs a declared executable method/environment; ordinary process-kill fixtures cannot replace a system-crash assertion. If either obligation cannot be met, the implementing issue stays unready.

After that prerequisite, refused-created-object cleanup remains a separate useful result using #1320's representation and actual finite reclaim. Durable request/sealing, accepted StructuredOutput, CommandResult captures and AgentSession ownership remain the separate complete deliveries in execution content. They do not become ready merely because this proposal is published; shared cleanup, validator/projection and runtime provenance dependencies still apply.
