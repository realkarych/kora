# Threat-model document structure and kora evidence

Checked on **2026-10-18** for [issue #90](https://github.com/realkarych/kora/issues/90). This is agent-produced research supporting [the threat model](../../docs/threat-model.md), not a product decision or a security certification.

## Method and source selection

The comparison read primary documentation from five established projects relevant to orchestration, secrets and hostile-code execution. It is a purposeful sample, not a survey of all large repositories or a popularity ranking. File dates below describe visible source history, not the date of a complete audit. An immutable source link makes the observation reproducible; it does not establish that every statement remains current.

| Project and source | Observed structure | Useful adaptation for kora |
|---|---|---|
| [Tekton](https://github.com/tektoncd/pipeline/blob/42b45a0b37c930d5c460b5630809bf7036a17e84/docs/security/threat-model.md), introduced by [PR #10313](https://github.com/tektoncd/pipeline/pull/10313), 2026-07-09 | `docs/security/threat-model.md` describes its relationship to the underlying cluster, trust boundaries, in-scope/out-of-scope reports and recommendations. It relates permission to create a pipeline run to permission to create a pod, and separates operator duties such as isolation and egress. It contains no threat-to-test register or boundary diagram. | State which authority kora grants and which enforcement belongs to runtime, operator and external service. |
| [OpenBao](https://github.com/openbao/openbao/blob/bf725ab89f288525375561ef5cec585fa406be8d/website/content/docs/internals/security.mdx), out-of-scope clarification [2026-07-28](https://github.com/openbao/openbao/commit/f413479e044ad697dedc4f236050919432065072) | `website/content/docs/internals/security.mdx` covers goals, threat model, exclusions, external threats and internal threats. It follows client/server/storage interactions and states what an authenticated attacker can already do. There is no numerical risk register. | Name initial attacker capabilities and explicit limits rather than implying that authentication or installation makes content safe. |
| [Kata Containers](https://github.com/kata-containers/kata-containers/blob/d06dadd8ef579210373521957e082def99e27f43/docs/threat-model/threat-model.md), file change 2026-03-19 | A dedicated document starts from protection objectives and attacker/assets, then addresses interfaces and devices. Its linked diagram shows actual nested execution boundaries. Its structure follows the runtime architecture rather than an exhaustive generic threat taxonomy. | Use an authority-oriented diagram and make runtime-dependent protection conditions visible. |
| [Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/e6f007968525f0ede4c9c9587c3ff1bed710a929/docs/design.md#threat-containment), 2026-09-16; [host setup](https://github.com/firecracker-microvm/firecracker/blob/fe9f12adc012691287e38bebf177da3441f66cbc/docs/prod-host-setup.md), 2026-05-06 | Threat containment lives inside the design document, with guest code treated as malicious and a real nested-boundary diagram. Host setup carries separate operational requirements. [Formal-verification notes](https://github.com/firecracker-microvm/firecracker/blob/73fe828ed624eefb16f4ac908b350d030f68eb76/docs/formal-verification.md), 2024-12-11, bound claims to individual harnesses and assumptions. | Keep deployment conditions separate from proof, and never extrapolate one tested property to the entire system. |
| [gVisor](https://github.com/google/gvisor/blob/ffb3b11dcf4038d75258363461bb4e84bf80b4a8/g3doc/architecture_guide/security.md), file change 2024-09-22 | `g3doc/architecture_guide/security.md` is an architecture chapter about threats, goals, defense in depth and limitations. Workload-accessible files and network remain accessible. Its image labelled as a threat model is an illustrative bug in a cube, not a data-flow or trust-boundary diagram. | Explain what the sandbox does not remove from an intentionally authorized workload. |

The sample supports explicit assumptions, attacker capabilities, boundaries and non-goals. It does not establish a mandatory filename, STRIDE checklist, risk score or review cadence. The per-threat contract/evidence mapping is an adaptation to kora's existing verification policy. A disclosure policy such as `SECURITY.md` has a different purpose; duplicating response timelines or contact instructions in the model would add maintenance without clarifying architecture.

## Repository baseline and evidence

The inspected accepted baseline is [`0c1ee5bdc7f390509a42bf75191dde706924d15a`](https://github.com/realkarych/kora/commit/0c1ee5bdc7f390509a42bf75191dde706924d15a), the scaffold merge on 2026-10-18. [Development instructions](../../docs/development.md) and [CI](../../.github/workflows/ci.yml) define the actual current commands. The earlier [AI setup record](../reviews/ai-development-setup.md) describes the documentation-only stage at its creation; its activation rules remain applicable as implementation arrives.

| Area at the inspected baseline | Observable state | What it establishes |
|---|---|---|
| Python package and frontend shell | Typed package, React/Vite shell and committed dependency locks exist | Source/build/packaging checks apply now. Their presence alone is not a passing run. |
| CI | Three scaffold lanes plus Markdown, links, Mermaid, IR examples and GitHub templates | The workflow describes required checks; a run must identify the actual revision and results. |
| Product API, scheduler, worker, runtime and providers | Contracts and future conformance cases exist; implementations are absent | Product threat controls and real API/process isolation tests remain `pending implementation`. |
| Contributor security review | Existing security profile and native GitHub reviewer mode exist | Procedural review obligations, not deterministic invocation or an OS sandbox. |
| Automated SAST, dependency and secret scans; browser/performance jobs | No dedicated jobs in the inspected workflow | No clean scan or runtime measurement can be inferred. The existing security profile's source/lockfile activation condition has been reached; tool selection/registration evidence is not supplied by this research. |

For this documentation/profile change, independent correctness/security review and the current scaffold/documentation CI apply. It changes no frontend/backend behavior or interaction, so browser/performance execution is not newly triggered by its diff. Product activation gaps remain separate work; any mandatory gate applicable to the actual change still blocks readiness if absent. Do not weaken the base policy to fit the document's five-file scope.

The threat model distinguishes document approval, accepted architectural direction and implemented protection with evidence. Deployment assumptions are another axis. The applicable security/lifecycle [ADRs](../../docs/decisions/README.md) sometimes record accepted direction while their precise wording remains pending owner review; a synthesis must preserve that status.

## Unresolved contract and evidence questions

- Evaluation resource limits: [IR section 7](../specs/ir.md#7-expressions-and-templates) and [ADR-0006](../../docs/decisions/0006-graph-definition-dsl-and-yaml-representation.md) restrict CEL functions and sandbox full Jinja2, but do not specify CPU/time, memory, evaluation-step or rendered-output limits. The verification profiles require assessment of expression/template bounds; that review obligation is not an accepted product limit. Before claiming protection against expensive expressions or oversized rendered output, resolve the limit and enforcement contract and verify it with real evaluator boundary cases. This research selects no limit or implementation. Update of 2026-10-19: the CEL half now has a contract in [IR section 7](../specs/ir.md#7-expressions-and-templates) (issue #126), whose budget and cost weights the first implementation fixes from measurements; its evaluator boundary cases are `pending implementation`, and bounds for rendered Jinja2 output remain open.
- Artifact downloads: [API section 8](../specs/api-and-agent-surface.md#8-rate-and-size-limits) describes large-artifact `storage_ref` redirects, while [protocol section 7](../specs/protocols.md#7-artifact-storage-fr-44) says the API always proxies downloads and that presigned URLs were dropped. This research records the discrepancy and does not select a transport. The model can cover authorization, immutable identity, retention and untrusted payloads without inventing a transport guarantee.
- At the check date, PRs [#80](https://github.com/realkarych/kora/pull/80), [#81](https://github.com/realkarych/kora/pull/81), [#82](https://github.com/realkarych/kora/pull/82), [#83](https://github.com/realkarych/kora/pull/83), [#84](https://github.com/realkarych/kora/pull/84) and [#85](https://github.com/realkarych/kora/pull/85) remained open and unmerged. Proposed credential identity, session-secret restrictions, resource delivery, graph scenarios, provider quotas and notifications are not accepted controls at this baseline. Recheck their disposition before a later model update.
- Current contracts do not establish a universal model-service retention policy, a general containment guarantee against a compromised trusted host/provider, or a guarantee that intentionally supplied credentials cannot be abused. These cannot be inferred from hermetic configuration or known-value redaction.
- Conformance fakes establish protocol behavior. Real harness interception and runtime containment need the evidence required by [protocol sections 12–15](../specs/protocols.md#12-policy-dd-29), not a documentation review or successful packaging test.

These observations do not change the product contract. Resolving a contract conflict or adding a protection follows the ordinary issue, owner decision, specification and implementation process.
