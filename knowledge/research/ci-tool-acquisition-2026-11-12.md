# CI tool acquisition through a digest-keyed cache, 2026-11-12

Checked on **2026-11-12** for [issue #1350](https://github.com/realkarych/kora/issues/1350), part of [issue #1347](https://github.com/realkarych/kora/issues/1347). Between 2026-11-06 and 2026-11-11, 2.6% of analysed `CI` attempts failed while downloading a pinned tool. On 2026-11-11, hosted Ubuntu runners could not resolve the Ubuntu package mirrors; `apt-get` failed in two jobs and ran until the job deadline in both Linux local-runtime lanes. The project owner decided that every pinned tool is restored from a GitHub Actions cache keyed by its exact pinned identity, and on a miss downloaded with bounded attempts inside the job deadline. Size and digest verification stays strict, and acquisitions end with a clear error instead of reaching the deadline.

## Helper and bounds

[`scripts/ci/acquire.py`](../../scripts/ci/acquire.py) uses only the Python standard library and curl, and runs under the runner's system `python3`, 3.9 or newer, because macOS jobs call it before setup-uv.

| Constant | Value |
|---|---|
| Attempts | 3 |
| Spacing between attempts | 5 s |
| Connection limit per request | 15 s |
| Time limit per attempt of a pinned download (both requests share it) | 30–45 s, per artifact below, plus a 5 s stop reserve |
| Time limit per attempt of a bounded command | 1–120 s, given by the caller, plus a 10 s stop reserve |
| Stop of a timed-out command | SIGTERM to its process group, SIGKILL to the group 5 s later |
| Acquisition budget per job, shared by every invocation | 240 s |
| Longest accepted redirect target | 8,192 bytes |

`fetch STORE NAME` verifies a file already in the store, such as one restored from the cache, before printing its path. It must be a regular file reached without symbolic links, with the exact size and SHA-256. A mismatch exits 1 with no download. A missing file is downloaded by curl with `--disable`, a private home and temporary directory, `--proto =https`, a byte ceiling equal to the pinned size, and the URL on standard input. Transport failures and non-200 statuses are retried. A size or digest mismatch, a body above the ceiling, a second redirect, or a redirect that is not HTTPS on exactly the admitted host is refused after that attempt. No credential is sent: the inherited environment, curl configuration files and netrc are not used.

`run SECONDS -- COMMAND` runs an idempotent acquisition command with the same attempts and spacing. A command that needs root runs the helper as root, so the helper can stop the command's whole process group.

Every invocation in a job reads and updates one ledger, `$RUNNER_TEMP/kora-acquisition-budget`, outside the cached store. Each attempt is shortened so that the attempt and its stop reserve fit in what remains of the 240 s budget, and no pause starts unless an attempt can follow it. An exhausted or invalid budget ends the invocation with `The job acquisition budget of 240 s is exhausted; <subject> was not acquired.` The time between acquisitions is not charged. Commands run with `sudo` keep `RUNNER_TEMP` through `--preserve-env`, and the helper refuses to run without it. An architecture test sums the worst case of every acquisition step of each job, three times its limit and reserve plus the two pauses, caps the sum at the budget, adds 5 s per invocation for process start and verification, and requires the result to stay 120 s inside the job's `timeout-minutes`.

## Cache design and scope

Each job has one `actions/cache` step, pinned to [v5.1.0](https://github.com/actions/cache/releases/tag/v5.1.0) at commit `caa296126883cff596d87d8935842f9db880ef25` (2026-06-26). It restores `${{ runner.temp }}/kora-acquisitions` under the exact key `kora-acquisitions-<runner.os>-<runner.arch>-<content label>-<hashFiles('scripts/ci/acquire.py')>`. The file digest covers every pinned source, size and SHA-256, so any pin change selects a new entry. The content label names the archives the job stores, such as `node-uv-python-3.11.17`, so every job that shares a key stores the same set. There are no `restore-keys`. An architecture test refuses any other cache path, key shape or option.

Ref scoping is the defence against cache poisoning. GitHub keeps a cache entry in the scope of the ref that created it. A pull-request run writes only into its own merge-ref scope and can read the base branch's entries; a master push run reads only master entries, and an existing key cannot be overwritten. A pull request therefore cannot place an entry that master restores. Any code that runs in a master job, including a merged change or a compromised action or dependency used there, can write master-scope entries, so master entries are only as trustworthy as master jobs.

The pinned digests are the defence against corrupted bytes. `actions/cache` unpacks an entry, which is not confined to the store, before any verification runs; the helper then checks every archive it uses against its pin, refuses symbolic links, and fails the job on a mismatch without a download or retry. Files in the store that no pin names are never read. The cache saves after a successful job only.

When the runner already has the exact Node or uv tool-cache entry, the preparation uses it without fetching that archive, so that path needs no network. A job on such a runner can then save its entry without that archive; a later runner that lacks the tool downloads it within the bounded attempts each time until the key changes.

The Gitleaks workflow's scanner download, the CodeQL bundle, the OSV scanner and setup-uv in the daily, storage, mutation and conformance-lifetime workflows are outside the `CI` workflow and the analysed failures; they can adopt the helper later.

Without the budget, one acquisition could take three times its limit and stop reserve plus 10 s of pauses: 160 s for Node and 400 s for Playwright. The sum over a job reached about 560 s for the console browser checks and 745 s for a Linux local-runtime lane, close to or beyond the ten-minute deadline. The shared budget caps the sum at 240 s plus process start, leaving at least five minutes of the deadline. A resolution failure or an HTTP error ends an attempt within seconds, so an outage like the one on 2026-11-11 now ends with an acquisition error in well under a minute. No job deadline changes.

## Local observations

On macOS arm64 with the system Python 3.9.6 and curl 8.7.1:

- The helper downloaded the uv, CPython 3.11.17 and Lychee archives into an empty store. The unauthenticated Lychee asset request answered HTTP 403 on the first attempt; the second attempt, 5 s later, returned the pinned archive. A repeated `fetch` used the stored archive in 0.07 s without a request.
- `setup_uv_cache.sh 3.11.17`, run against a copied store and an empty tool cache, wrote `uv/0.13.1/aarch64` with its completion marker and the mirror variable. A second run reused the entry without reading the uv archive. The seeded uv 0.13.1 installed CPython 3.11.17 from the file mirror. After one byte was appended to the stored uv archive, a run with an empty tool cache refused it before any extraction and left the tool cache empty; a run with the entry present does not read that archive. The budget ledger recorded 0.039 s for these invocations.
- The uv 0.13.1 file mirror expects the decoded file name, `cpython-3.11.17+20261013-…`, below the build directory. An archive altered by one byte was refused by uv's own SHA-256 check.

The Linux runner paths, the hosted cache save and restore, and the workflow changes are first exercised by the pull request's own CI run.

## Linux Scaffold pnpm acquisition, 2026-11-24

[Issue #1813](https://github.com/realkarych/kora/issues/1813) records the slow GitHub Action repository download and the [approved Linux-only acquisition plan](https://github.com/realkarych/kora/issues/1813#issuecomment-7116480108). The verified [immutable release archive](https://github.com/pnpm/pnpm/releases/tag/v12.14.0) contains the same 56,326,440-byte Linux x64 executable as the npm native package used by the previous setup. Its SHA-256 is `5e9119e6f4f18dace3795169e9b3672231ab3662505862dc3026571303a8ef32`. The entire checked archive is extracted unprivileged in the job's private temporary directory. This preserves the executable's adjacent `dist` tree, including the POSIX node-gyp launcher and the internal hardlinks. The executable and its version are checked before its path is published. The existing job budget covers the download and has the same deadline and retry limits.

The workflow selects the pinned Node and then the verified pnpm before the cache-only invocation of pinned `actions/setup-node`. The package store cache key uses the operating system, architecture and frontend lockfile. The acquisition archive has its own manifest-keyed cache. `PNPM_CONFIG_STORE_DIR` gives cache discovery, the frozen install and the Hatch offline build the same absolute job-owned base outside the checkout and the tool staging directory. The pinned pnpm resolves the store-format directory under that base. The pinned uv frontend retains this setting and the tool path in the PEP 517 child from the extracted build root. The sdist excludes `web/node_modules`. [pnpm configuration](https://github.com/pnpm/pnpm/blob/fe4a0c232384289de82be3d502896ca7e070050c/pnpm/crates/config/src/env_overlay.rs#L180-L190) · [uv build environment](https://github.com/astral-sh/uv/blob/62faed3351cfee2121b3c28b937b1f4b93233a93/crates/uv-build-frontend/src/lib.rs#L1309-L1328)

Before project commands use the store, a reported hit must match the primary key exactly. A reported miss must have a valid primary key, no matched key and a still-empty store. When the cache action succeeds with all cache outputs absent, the job can continue with a still-empty store. This is recorded as cache unavailable and supplies no cache hit or miss/save evidence. GitHub ref scoping and trusted in-scope writers still govern cache trust. The pinned cache action can extract an entry before the workflow receives its matched key. The workflow refuses use of a nonexact or ambiguous restore. The existing archive verification still detects corruption of consumed tool archives after the acquisition cache is extracted.

## Browser system package attempt ownership, 2026-11-26

The [browser dependency failure in #1887](https://github.com/realkarych/kora/issues/1887) reached package configuration and timed out before the following attempt found the `dpkg` database locked. The job log could not establish which attempt owned the reported lock holder. A process group and the return of its timeout command do not establish that package work and its locks have settled.

The Ubuntu browser job uses one transient system service for each system package attempt. The launched helper supplies its invocation through the fresh launch's private output. The controller matches that invocation to the manager and retains its native cgroup before admitting the fixed package command through a private input pipe. The helper independently bounds its pipe read by the monotonic admission cutoff and verifies its invocation and cgroup. It closes the intake and acknowledges acceptance before recovering `dpkg` and running the locked Playwright dependency installer. The installer uses the prepared Node tool-cache entry and the pinned pnpm action's selected executable. The manager bounds running jobs, service runtime and cgroup stop. The [systemd v255 transient setter](https://github.com/systemd/systemd/blob/v255/src/core/dbus-unit.c#L2195-L2206) rejects `JobTimeoutSec`, so the manager may retain a queued job past the cutoff. Even if that job later starts, its helper cannot begin package work. The controller requires acknowledged admission, the terminal result and settlement of the original cgroup before a retry. It resets an exact failed service only after that cgroup is empty. If the kill deadline expires while a process remains, the controller fails the acquisition. No later installation in that job can take over uncertain work.

The existing acquisition ledger includes launch, command time, stop, ownership proof and retry pauses. The procedure keeps the three attempts, five-second spacing, 120-second per-attempt maximum and 240-second shared job budget. The browser download, source checks, browser tests and verification artifacts keep their existing workflow. An offline fixture in the same Ubuntu job uses an isolated `dpkg` administrative directory and a real lock holder in a separate session. It observes contention and release before retry. It also verifies that a helper launched after its cutoff refuses before work, that the manager settles an admitted service after its controller dies and that a same-name collision preserves the incumbent's invocation, process and lock.


## Console Ubuntu package sources, 2026-11-27

[Issue #1978](https://github.com/realkarych/kora/issues/1978) records a Console failure after all three service attempts encountered HTTP 403 on the unrelated Microsoft Noble index. Chromium and the installed browser exercise did not run. The [approved plan](https://github.com/realkarych/kora/issues/1978#issuecomment-7226425131) preserves the original systemd controller and changes the APT inputs in that service.

The attempt admits the runner's fixed Ubuntu source and Canonical archive key through no-follow descriptors before recovering dpkg. The source directory chain stays protected. The runner's writable installed signer path supplies bytes only, and the root-owned stage receives those bytes only after verifying the exact pin. [Hosted permission evidence](https://github.com/realkarych/kora/issues/1962#issuecomment-7220388030). The admitted key is the 3,607-byte Noble keyring from `ubuntu-keyring 2023.11.28.1` with SHA-256 `80a36b0a6de2f69f49d2df75ef473ccde121e9e190b9ea01d20a4f63778d5c31`. The protected source copy preserves the Noble suites and components. Its mirror reference selects `https://archive.ubuntu.com/ubuntu` using a stage-owned mirror file, and its signing reference points to the checked copy. The workflow leaves the runner's mirror file untouched.

The service checks the effective native apt-get configuration before recovering dpkg and at all three APT calls. The locked Playwright dependency process receives a PATH containing only its stage directory with the fixed shell and guarded APT adapter. The native calls use the standard system PATH, the real dpkg database and the runner's existing hooks. Each update must obtain the admitted indexes and pass native verification. Each attempt uses private cold lists and archives and disables inherited binary cache inputs. This excludes a same-size ambient archive that [Noble APT may otherwise reuse](https://git.launchpad.net/ubuntu/+source/apt/tree/apt-pkg/acquire-item.cc?h=applied/2.8.4ubuntu0.1#n3494). Only a protected receipt written after native APT returns its ordinary error status permits retry when Playwright normalizes the child status. A refusal or an unproven outcome ends the acquisition.

The [hosted ownership witness on `3879f37`](https://github.com/realkarych/kora/actions/runs/46079187115/job/140774216780) observed an ambient apt-get update after the guarded directory was prepended to the system PATH. Confining the dependency process to the stage directory removes command-search fallback while the guarded native APT process retains the original system environment. The hosted witness covers both an explicit adapter refusal and an unexecutable adapter through the locked Playwright command and requires a terminal outcome and settled stage for both.

The stage records the original invocation and native cgroup identity. The controller proves the original service and native cgroup have settled before admitting a separate bounded cleanup service for the exact stage. It proves release of the cleanup service within the original return reserve. Uncertain original or cleanup ownership blocks another package attempt. The hosted witness opens the staged signer while the original process holds an isolated dpkg lock. It exercises actual release on interruption, timeout and controller loss, and preserves the incumbent's stage during a same-name collision. Its isolated loopback archive uses native APT and signed synthetic metadata to check required-source failures, ignored unrelated sources, unchanged ambient caches and actual hooks. The Console job also executes the real Playwright package commands, downloads the pinned browser and runs the installed HTTPS fixture.
