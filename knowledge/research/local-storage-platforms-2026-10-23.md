# Local storage platform evidence, 2026-10-23

This record supports the selected mechanics of [#255](https://github.com/realkarych/kora/issues/255), not executable readiness. Checked on 2026-10-23; platform CI and measurements remain required.

## Lock and filesystem inspection

The Linux [flock manual](https://man7.org/linux/man-pages/man2/flock.2.html) associates locks with open file descriptions: duplicate descriptors share ownership, while separate opens can contend within one process. The implementation therefore uses separate noninheritable descriptions for owned units and never replaces permanent lock inodes.

Linux [fstatfs](https://man7.org/linux/man-pages/man2/statfs.2.html) exposes filesystem type and filesystem identity on the actual descriptor. The ext-family magic alone does not distinguish ext4; the local implementation additionally checks the descriptor device against the kernel mount inventory. Apple publishes the [statfs layout](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/mount.h), including filesystem name and identity. Supported names remain the owner-selected ext4, APFS and HFS+ set; this does not validate network filesystems.

## Native ACL inspection

Apple's [ACL header](https://github.com/apple-oss-distributions/Libc/blob/main/include/sys/acl.h), [descriptor retrieval](https://github.com/apple-oss-distributions/Libc/blob/main/posix1e/acl_file.c) and [entry iteration](https://github.com/apple-oss-distributions/Libc/blob/main/posix1e/acl_entry.c) define the native extended ACL type, allow/deny tags and indexed access. Descriptor retrieval obtains FILESEC_ACL from fstatx state; absent ACL properties return no ACL. Local macOS inspection observed ENOENT for existing root/private/var descriptors with no ACL. That specific absence is accepted after fstat confirms the descriptor remains valid; other retrieval failures refuse. A retrieved allow entry refuses regardless of principal. Real ACL tests must establish acceptance/refusal on the supported filesystems.

## SQLite durability and bounded private state

SQLite's [PRAGMA documentation](https://www.sqlite.org/pragma.html) distinguishes FULL from EXTRA in DELETE journaling: FULL does not independently promise durability of the journal-directory deletion. The selected implementation keeps the approved FULL mode, enables the native full-sync facility and explicitly synchronizes the anchored control directory after commit, before acknowledging an outcome or dispatching an effect dependent on that intent. This additional flush is part of implementing the plan's durable-intent/acknowledgment ordering. Failure remains unresolved and cannot authorize compaction.

FULL auto-vacuum must be selected before tables are created. It can truncate free tail pages at commit but does not repack partially occupied pages. Therefore row counts cannot establish stable physical allocation: database, journal, freelist and file/block measurements remain mandatory. The 256 KiB cache setting limits the requested page cache, not total native memory. Zero busy timeout and nonblocking external ownership avoid hidden contention retries; they do not prove latency bounds for arbitrary filesystem syscalls.

## Native synchronization and fixture ownership, checked 2026-10-24

Apple's [fcntl definitions](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/fcntl.h) identify F_FULLFSYNC as the operation that also requests a drive-cache flush. The implementation synchronizes affected directories and then the permanent manifest file with that native operation on macOS. This also covers recovery that observes an already present link/directory or an already absent private leaf/stage directory; absence or presence does not substitute for flushing the earlier namespace effect. Control reads flush before returning retained outcomes, including after an earlier commit whose synchronization failed. This is a selected supported-filesystem implementation ordering, not a claim about arbitrary filesystem power-loss behavior.

The [mke2fs reference](https://www.man7.org/linux/man-pages/man8/mke2fs.8.html) provides root_owner, allowing an unprivileged formatter to prepare the test filesystem for its actual workload owner without a later privileged ownership change. The [1.47.0 implementation](https://raw.githubusercontent.com/tytso/e2fsprogs/v1.47.0/misc/mke2fs.c) supports root_owner but lacks the newer root_perms option; the fixture uses the former and accepts a non-writable ordinary volume root beneath its private acquisition directory. The [util-linux loop-device implementation](https://kernel.googlesource.com/pub/scm/utils/util-linux/util-linux/+/refs/tags/v2.43-devel/sys-utils/losetup.c) exposes backing-file inode and device identity in explicit JSON columns. The pressure fixture must check those together with its private image identity before cleanup.

Apple [documents machine-readable hdiutil output](https://developer.apple.com/forums/thread/721232) for disk-image relationships. Native process identity comes from the [published process-information definitions](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/proc_info.h) and [libproc wrapper](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.c). The unique-process query is a private native flavor; the fixture must fail explicitly if unavailable. Recovered orphan processes are observed until their exact identity closes rather than signaled using a possibly reused bare PID.

The installed hdiutil help was checked alongside its local manual. Its current create interface no longer lists or accepts the manual's uid/gid/mode arguments. The fixture therefore supplies an empty private source directory and supported source-owner preservation, retaining the approved HFS+ UDRW format and finite image size. These tool arguments need real local and macOS CI evidence; the older manual alone is insufficient.

The first hosted Linux pressure run could read a loop backing path but refused its unavailable backing inode/device fields. The [util-linux implementation](https://github.com/util-linux/util-linux/blob/v2.39.3/sys-utils/losetup.c#L121-L136), checked on 2026-10-24, identifies missing loop-status ioctl permission for an unprivileged caller. The fixture therefore performs its fixed read-only loop inventory under sudo as well as its fixed attachment operations. It still requires the exact backing inode/device and verified mount identity before cleanup; path equality alone is insufficient. Linux execution of that correction remains unverified until the next committed qualification run.
