# Archon vs kora: sourced comparison

Checked on 2026-10-15: Archon at tag `v0.11.1`, with the state of its `dev` branch on 2026-10-15 noted where it differs; kora as designed, with no code. The retry and loop rows were re-verified on 2026-10-16 at the same tag against `packages/workflows/src/schemas/node-execution.ts`, `schemas/node-artifact.ts`, `node-execution.ts`, `node-record-serialization.ts`, `artifacts-index.ts` and `dag-executor.ts` (issue #22). The human-reviewed summary of this comparison is [docs/archon-comparison.md](../../../docs/archon-comparison.md); this file holds the sources behind every row.

**Archon.** The tag checked is `v0.11.1` (latest release, 2026-09-25, commit `aa09544`) of the repository github.com/coleam00/Archon. The `dev` branch is 2,359 commits ahead (HEAD `54ec4fb`, 2026-10-15). Where `dev` differs materially, this is marked **[dev]**: such changes are not yet in a release.

Metadata from the GitHub API: MIT, TypeScript, 23,690 stars, 3,508 forks, 186 open issues, default branch `dev`.

The code was read in an isolated clone and not executed. Abbreviations in references:

- `D/` = `packages/docs-web/src/content/docs/`;
- `DN` = `packages/workflows/src/schemas/dag-node.ts`;
- `AW` = `D/guides/authoring-workflows.md`.

**kora.** There is no code; everything below describes the project as designed. References point to FR/NFR in [docs/requirements/](../../../docs/requirements/), to ADRs in [docs/decisions/](../../../docs/decisions/README.md) and to specifications in [knowledge/specs/](../../specs/). Almost everything is marked **[MVP]**; exceptions are marked **[post-MVP]**.

The "Difference that matters" column is filled only where a difference actually exists. "≈ same" means there is no substantive difference.

## (a) Product

| Aspect | Archon v0.11.1 | kora (design) | Difference that matters |
|---|---|---|---|
| Self-description | "The first open-source harness builder for AI coding", "a workflow engine for AI coding agents", "Think n8n, but for software development" (README.md:8,23,25). In the maintainer documents: "governed agentic automation engine", with coding named the most mature area (AGENTS.md:3, `.archon/direction.md:11`). | "Open-source platform for running graphs of coding-agent sessions at organisation scale"; analogy "Airflow for agentic pipelines" (`docs/positioning.md`). | Archon is a workflow engine for a repository (by its own account, expanding into business automation too). kora is a control plane for an organisation. |
| Target user | The documents contradict each other. "Single-developer tool", "no multi-tenant isolation" (`D/reference/security.md:28`, `D/reference/api.md:35`). At the same time "single-tenant per install", with several users per install supported (`direction.md:12`); the GitHub App is recommended "for teams sharing one instance" (`D/adapters/github-app-setup.md:11`). | A platform team (installs, implements protocols, publishes presets) plus engineers of product and data teams who write graphs. A single developer is not the centre of the design (`positioning.md` "Who it is for"; NFR-0.1). | Archon: one operator or a small team per install. kora: many teams on one instance. |
| Scope | SDLC workflows: issue → plan → implement → review → PR. Plus a chat with the project through Slack, Telegram and web (README; `D/adapters/index.md`). | Only the deterministic outer loop around sessions. Not an agent framework, not a task runner, not a data orchestrator, not a sandbox (`positioning.md` "Non-goals"). | Archon has a conversational chat interface to the agent. kora does not have one and none is planned. |
| Deployment model | Binary (curl, PowerShell, Homebrew) and `archon serve` on :3090. One Docker container on SQLite; compose profiles `with-db` (Postgres 17), `cloud` (Caddy HTTPS), `auth` (sidecar) (`docker-compose.yml:71,96,121`; `D/deployment/docker.md`). SaaS is explicitly not a goal (`direction.md:25-26`). Windows partially, WSL2 recommended (`D/deployment/windows.md:12-15`). **[dev]** Providers and the server are no longer bundled in the binary: `archon provider add`, the server is downloaded on `serve`. | `kora standalone` (one process, SQLite, for development) and `docker-compose` (Postgres + scheduler + API + workers) (FR-12.3, NFR-7.1). Helm and K8s **[post-MVP]**. Linux and macOS only (AGENTS.md "Platforms"). | Archon is a product ready to install. kora does not have a single line of code yet. In form, both are self-hosted with SQLite and Postgres. |
| Maturity | 11 releases since April 2026. The CHANGELOG has `### Breaking` sections in 0.8.0, 0.9.0, 0.10.0 (about 12 items), 0.10.1 and 0.11.0. | Documents only: "There is no code" (`docs/roadmap.md`). | The largest factual difference. |
| Licence | MIT (LICENSE:1-3). A move to fair-code with a CLA is recorded as an open question (`direction.md:117`). | Apache-2.0; all protocols in the open-source core, no enterprise-only parts (NFR-12.1). | A small difference: Archon's licence may change, kora has the Apache patent clause. |

## (b) Features

| Aspect | Archon v0.11.1 | kora (design) | Difference that matters |
|---|---|---|---|
| Graph definition | YAML in `.archon/workflows/`: flat files or packs `<pack>/<workflow>/`. Zod schemas, validation through `archon validate workflows` (`D/reference/cli.md:1046`); unknown keys produce only a warning. No JSON Schema for editors. There is an experimental visual builder that can only create (`D/adapters/web.md`). No code-first definition. | A Python DSL (`@graph`, `>>`, keyword-only inputs) compiles to a versioned YAML IR with `ir_version`. The IR is validated against the published `ir.schema.json` and semantic rules; compilation is deterministic (FR-1.1–1.4, NFR-6.1–6.2, ADR-0006). UI editor **[post-MVP]** (FR-1.5). | Hand-written YAML versus code compiled to a validated IR. Archon's format breaks often (see "Maturity"). |
| Node kinds | One mode key per node: `command`, `prompt` (AI), `bash`, `script` (bun or uv), `loop`, `loop_group`, `approval`, `wait` (duration, until, event, attention), `cancel`, `include`, `include`+`fan_out`, `workflow` (child sub-run) (DN:1120-1240). | `agent`, `command` (argv, no shell), `human_input`, `wait_event`, `timer`, `branch` (CEL), `fan_out`, `subgraph` (ADR-0012; `ir.md` §4). There is no `transform` node. | Archon has a dedicated loop node and a `cancel` node. kora has a sensor and a branch node with CEL. Overall the sets are comparable. |
| Dependencies and conditions | `depends_on`. Four trigger rules: `all_success`, `one_success`, `none_failed_min_one_success`, `all_done` (DN:49). `when:` is its own mini-grammar: comparisons on `$node.output.field`, `&&`/`\|\|`, no parentheses (`condition-evaluator.ts`). Nodes of one layer run in parallel. | Seven trigger rules, including `none_failed_min_one_success`, borrowed from Archon (FR-1.6, ADR-0006). Expressions are CEL everywhere, with static type checking (FR-2.5). | ≈ same in meaning. kora's expressions are typed and checked; Archon's is a simplified grammar. |
| Fan-out and sub-graphs | `fan_out` over a JSON array known only at run time; `max_parallel` defaults to 5; `join` = `all_done` or `all_success`. `include:` up to 3 levels, `workflow:` up to 5 levels, the cost of child runs is rolled up into the parent (`executor.ts:1169`). | `fan_out` over a typed `List[T]`, the body is always a sub-graph; `max_parallel` and `skip_failures` exist (FR-2.6). `subgraph` with its own retry policy, timeout and budget (FR-2.7). | ≈ same in capability. The difference is in sub-graph retry (next row). |
| Retry | `retry` on a node: `max_attempts` 1–5 (counting retries, i.e. up to 6 runs), `delay_ms` doubles, `on_error: transient\|all` (`schemas/retry.ts:8-11`). Error classes FATAL, TRANSIENT, UNKNOWN are determined by a substring of the message; FATAL is never retried (`executor-shared.ts:38-120`). On rate limit, up to 5 retries with a 45 s delay. Retry is forbidden on `loop`, `loop_group` and `workflow:`. Every attempt is recorded as a node execution with its own `attempt.id`, `invocation.id`, usage and output (`schemas/node-execution.ts:74-85,185-190`; `node-execution.ts:43,96-98`; `node-record-serialization.ts:22,47-57`), but the retry loop re-runs the node with the same inputs and returns only the last output; the next attempt has no reference to an earlier one (`dag-executor.ts:1075-1139`). **[dev]** Typed provider error classes. | `retry` on a node and on a sub-graph: `max_attempts`, backoff, `retry_on` and `non_retryable` by error class, plus a CEL predicate on the artifact (FR-6.3). Three strategies: `fresh`, `resume`, `fresh_with_feedback` (FR-6.4, ADR-0007). An attempt is an object in the database; the artifacts of all attempts are stored with lineage (FR-4.5). | A real difference: kora retries a whole sub-graph and has attempt objects and lineage. Archon records every attempt but retries only at node level, and an earlier attempt is not addressable as an input. |
| Loops and iterations | `loop` and `loop_group` (a body of several nodes), mandatory `max_iterations`, `fresh_context`. Loop exit: `until` (agent signal, marked deprecated), `until_bash` (exit code 0), `until_field` (boolean in `output_format`). `$LOOP_PREV` gives access to the previous iteration. `approval.on_reject {prompt, max_attempts}` repeats the step with the rejection reason (`executor-shared.ts:897`; `D/guides/loop-nodes.md`). Body outputs are stored per iteration (`loopGroupPath` frames, `schemas/node-artifact.ts:4-25`; `artifacts-index.ts:45-53`); `$LOOP_PREV` reaches the previous iteration only, and `$groupId.output` seen by the outer DAG is the final iteration's output (`dag-executor.ts:4514-4518`). | There is no loop as such: the graph is acyclic, and iteration is expressed as a sub-graph retry. The next attempt receives `previous_attempt` (reason and artifacts), nodes with `attempt_invariant` are not rerun, and `fail_attempt` ends an attempt explicitly (FR-2.7a, ADR-0007). | Both systems can iterate with feedback. In Archon the exit decision can also be deterministic (`until_bash`). The difference is in the model: in Archon it is a loop node, in kora a sub-graph retry with attempts addressable as inputs and artifact lineage. |
| Approvals | `approval:` (`message`, `capture_response`, `on_reject`); a rejection without `on_reject` cancels the run. `wait: attention` is free text, continued through resume. Channels: CLI, chat slash commands, web, a Slack button, REST `/approve` and `/reject`. The next node reads `$gate.output`. No timeouts and no default value. The approval is not bound to a SHA or digest. **[dev]** Attention forms (`message`, `approval`, `select`, `multi_select`); `approval:` is declared deprecated; an answer can be bound to `expectedGate {nodeId, pauseId}` (`D/reference/api.md:422-430` in dev). | A `human_input` node: a typed form (JSON Schema), timeout, `on_expiry` (`fail`, `skip`, `default_value`), approver identity (FR-2.2). The approval is bound to the commit SHA and to the digest of the `ReviewBundle` facts; a new push invalidates it (FR-7.2a, ADR-0008). Channels are a protocol: CLI/API and VCS change request (FR-7.1–7.2). Chats **[post-MVP]** (FR-7.4). | A real difference: binding to content and a timeout with a default value exist only in kora. Archon has more notification channels. |
| Artifacts | `output_format` (JSON Schema; Claude, Codex and OpenCode validate it in the SDK, Pi and Copilot best effort), `returns:` and `outcome_field`. `$id.output.field` and `with:` bindings. Files in `$ARTIFACTS_DIR`, `output_type` writes typed sidecar files. `GET /api/runs/{id}/artifacts` (`D/reference/api.md:269`). `inputs:` are untyped. | Every edge carries a typed artifact with a version, a producer (run, node, attempt) and lineage (FR-4.1). Built-in types: `StructuredOutput`, `VcsRef`, `AgentSession`, `CommandResult`, `ReviewBundle` (kora writes the facts, the agent the narrative). User-defined types. Storage is a protocol (FR-4.2–4.5). | A real difference: domain types, versions and lineage, plus `ReviewBundle`. Archon validates JSON output against a schema, but without versions or lineage. |
| Deterministic gates | `bash:` and `script:` (default timeout 120 s), `until_bash`. `mutates_checkout: false` checks that the git tree has not changed. `evidence_policy` only requires that `evidence.json` exists. | `command` (argv) with `CommandResult`. `protected_paths`: the agent may not edit them, and digests are compared before the gate (FR-2.8, ADR-0009). | ≈ same in idea. kora additionally protects gate scripts from being edited by the agent. |
| Cost | USD and tokens per node and per run, including failed attempts and child runs. The source is the provider's report; there is no price table; Codex and Copilot do not report cost. The only limit is `maxBudgetUsd` per node and only for Claude (`providers/src/claude/provider.ts:724`). `concurrency.providers.<id>` is a concurrency limit per provider. **[dev]** `budget: {max_work_units, max_spend_usd}` per workflow. | Tokens per model for every attempt, with a completeness flag (`complete`, `partial`, `unavailable`). A pluggable price table, billing class. A soft USD budget per node, sub-graph and run; a daily limit per namespace. Cost is shown next to the approval form (FR-9.1–9.5, FR-6.9, ADR-0010). Reconciliation with vendor billing **[post-MVP]**. | A real difference: kora has a price table (cost is computed for Codex too), budgets and the cost of all attempts. Archon has only the provider's report. |
| Isolation | By default a git worktree per run, `--no-worktree` turns it off (`D/getting-started/concepts.md:90-101`). But `direction.md:109` says "worktree only on explicit `isolation: worktree`": the documents disagree. Only a `workflow:` sub-run can get its own worktree. The authors themselves write that a worktree "is not an execution or security sandbox" (AGENTS.md:25). `--container` works only for folders without git and only with Claude (`D/guides/container-isolation.md`). | Every agent node gets a fresh checkout (FR-5.1). Runtime is a protocol: local and Docker in the MVP, a separate container per attempt (FR-8.2). Cloud sandbox and K8s **[post-MVP]** (FR-8.3). Network policy (FR-8.6). | A real difference: kora isolates per node, has a container for a git repository and a runtime behind a protocol. Archon has a worktree per run, without a sandbox. |
| VCS and forges | Git only. Forges: GitHub (webhook, @mention, GitHub App with bot attribution and token rotation); GitLab and Gitea as community adapters (webhook and comments; the adapter does not create MRs: `packages/adapters/src/community/forge/gitlab/adapter.ts`). `archon forge` (`pr.create`, `comment.upsert` and so on) through an executable plugin; only the GitHub plugin is supported (`D/reference/forge.md`). The built-in workflows call `gh` by default. | VCS is a protocol (`checkout`, `publish`, `open_change_request`, `change_request_status`, `diff_paths`). In the MVP, git with the GitHub and GitLab APIs (FR-5.2, ADR-0005). A non-git VCS is implemented by the adopter; this is part of MVP acceptance. | A real difference: VCS behind a protocol versus "git only". Archon's GitHub integration is deeper (App, bot). |
| Runtime | Host process: the server or the CLI runs the SDK in its own process. A container only for folders without git and only with Claude. `vm` and `remote` are declared in the types but not implemented (`packages/isolation/src/types.ts:24`, `factory.ts:5`). | A runtime protocol (`submit` keyed by attempt id, `lookup`, `adopt`, `cancel`, capability flags); local and Docker in the MVP; a conformance suite for the adopter's runtime (FR-8.1–8.7, ADR-0005). | A real difference: remote or corporate execution exists only in kora's design. |
| Triggers and schedule | Manual: CLI, web, chat, REST. GitHub webhook bindings (issue, PR, label, check_run), with signature, deduplication and `capacity` + `skip`/`queue` (`D/guides/workflow-triggers.md`). No cron engine: `archon trigger schedule install` writes a macOS launchd entry with a fixed `StartInterval` (`packages/cli/src/triggers/native-schedule.ts:103`); on Linux an external cron calling `trigger fire` is needed. No sensors; `wait: event` waits for a push to `/signal`. **[dev]** A generic webhook source with HMAC (Standard Webhooks). | Manual, cron with time zone, webhook (HMAC or bearer with nonce), "on completion of another graph", sensor (poll with a CEL predicate); overlap policy `allow`/`skip`/`queue` (FR-6.2; `ir.md` §8). `wait_event` and `timer` nodes (FR-2.3–2.4). | A real difference: kora has built-in cron and sensors. The webhook difference will disappear once Archon's `dev` is released. |
| Observability | Pino logs, a JSONL transcript per run, SSE (`/api/stream/...`), `/health`, `/health/db`, `/health/concurrency`, anonymous PostHog telemetry (opt-out). Prometheus and OTel not found (`D/reference/security.md:57`, README.md:322-360). | An append-only event table, session event stream segments, `kora logs --follow` (FR-11.1–11.2). An OTel exporter with GenAI semconv as a protocol (FR-11.3). Prometheus metrics (NFR-7.3). Audit log (FR-11.4). | A real difference: OTel and Prometheus only in kora. |
| Operability for agents (MCP, skills, CLI) | No outward MCP server (an internal SDK MCP only for `manage_run` in chat: `providers/src/claude/native-tools.ts:53-64`). An `archon-cli` skill for Claude Code and Codex (`archon skill install`): launching, managing runs, configuration, writing workflows (`.claude/skills/archon-cli/SKILL.md`). A large CLI. REST with OpenAPI 3.0 (`/api/openapi.json`). No CLI/API/UI parity rule: trigger, forge and container resume exist only in the CLI. | Two curated MCP servers (13 tools) plus skills for Claude Code and Codex. The rule: the API is the single implementation; CLI, MCP, skills and web are thin clients; parity is checked by a test in CI (FR-0.1–0.4, ADR-0002). | A real difference: an MCP server and parity as a rule exist only in kora. Both have a skill; Archon's also covers writing workflows. |
| UI | Web console: list of runs, a run page with the event log, artifacts, DAG, approve/reject/resume/cancel/abandon buttons and cost; chat with the project; settings; experimental builder (`D/adapters/web.md:52-114`). No separate approval queue (**[dev]** an attention queue appears). | In the MVP only the approvals screen: list, `ReviewBundle`, form (FR-7.3; `api-and-agent-surface.md` §6). Runs, graphs, attempts and cost **[post-MVP]** (FR-11.5). | In the MVP design, kora's UI is noticeably poorer than Archon's today. |
| Chat interfaces | Slack, Telegram, Web, CLI, GitHub (core); Discord, GitLab, Gitea (community) (`D/adapters/index.md:14-32`). | None; chat approval channels **[post-MVP]** (FR-7.4). | Archon's advantage. |

## (c) Technology and architecture

| Aspect | Archon v0.11.1 | kora (design) | Difference that matters |
|---|---|---|---|
| Language and stack | TypeScript on Bun 1.4.2; Hono (`@hono/zod-openapi`) on `Bun.serve`; React 19 + Vite 6 + xyflow; SQL without an ORM over `bun:sqlite` and `pg`. One idempotent schema `migrations/000_combined.sql`, additive changes only, no migration journal (AGENTS.md:120). | Python 3.11+ asyncio; FastAPI + Pydantic v2; SQLAlchemy 2 + Alembic; CEL; sandboxed Jinja2; React + Vite + TanStack Query (ADR-0013). | Versioned migrations and upgrade without downtime (NFR-7.2) versus a "CREATE IF NOT EXISTS" schema. |
| Process model | One process: server = adapters + orchestrator + `InProcessWorkflowEngine` (`core/src/orchestrator/orchestrator.ts:536`). The CLI executes a workflow itself in its own process, against the same database (`cli/src/commands/workflow.ts:3126`); `--detach` moves the run into a background child process. | Three processes: `kora api`, `kora scheduler` (stateless, passes over the database) and `kora worker` (one per runtime, outbound HTTPS only). Inside the runtime, `kora-runner` enforces limits. `standalone` combines everything into one process (ADR-0003, [pre-consolidation architecture overview](https://github.com/realkarych/kora/blob/1baf9891af1d8dc69e4e33dd7bc2af22237072c5/docs/architecture.md)). | A real difference: distributed workers versus one process. |
| State storage | Postgres: 25 tables (21 on SQLite, 29 in dev). The documents state 14, 16 and 18 tables (README.md:300, `D/reference/architecture.md:57`, `D/reference/database.md:74`). Transcripts, artifacts and state live in the file system under `~/.archon/workspaces/...`. | All run state only in the database (run, node_instance, attempt, wait, artifact_version, lineage, usage_record, event...). Payload is stored by digest in the artifact storage protocol (`data-model.md` §2, FR-6.1). | In Archon part of the state is in the local file system, so a run is tied to its host. |
| Crash recovery | Explicit resume only (skips completed nodes). "Archon does not auto-fail running rows on server startup"; the operator cancels stuck runs manually (`AW:815-836`). Paused runs survive a restart. `loop_group` has no iteration cursor. There is an option to continue automatically after a quota reset. | Adoption of sessions by attempt id after a restart; at-most-once submission; leases with epoch fencing; stall detection (FR-6.1, FR-6.1a, NFR-2.1–2.3, ADR-0003). | A real difference: automatic recovery exists only in kora's design. |
| Scheduler | No separate scheduler: the DAG executor runs inside a request or process, nodes of one layer are started through `Promise.allSettled`. Long waits are stored in the database. | A separate stateless scheduler: readiness, admission, waits, timeouts, retries and clear-downstream passes under a run lock; waits are stored as rows (`scheduler.md`, ADR-0001). | A real difference. |
| Connection to workers and runtime | No workers; the SDK is called in process. In container mode, `docker exec` through the SDK hook `spawnClaudeCodeProcess` (`D/guides/container-isolation.md:31`). | A worker claims tasks over the HTTP API with a lease and heartbeat; the worker has no database access (ADR-0003). | A real difference: kora can execute inside the adopter's closed network. |
| Extension model | Two kinds of plugins: `forge` (an executable, JSON over stdio) and `workflow-pack`. Installed from GitHub pinned to a commit (`packages/plugin-manifest/src/index.ts:44-86`). Providers, adapters and isolation are built into the code. A marketplace of 15 SHA-pinned workflows. **[dev]** `provider` and `chat` plugins, marketplace removed. | 11 protocols (runtime, harness, VCS, approval, secrets, artifact storage, artifact type, observability, authentication, sensor, policy). Plugged in through `kora.provider` entry points, each with a conformance suite (NFR-5.1–5.2, ADR-0005). Presets in a registry (ADR-0006). | A real difference: kora plugs in infrastructure (runtime, VCS, secrets). Archon distributes ready-made workflows (packs); kora has no such mechanism. |
| Harness integration | SDK imports: Claude Agent SDK (launches the Claude Code binary), Codex SDK, Pi (in process), OpenCode SDK, Copilot SDK. Hooks, `maxBudgetUsd`, sandbox, `settingSources` and container exist only for Claude (`D/reference/provider-capabilities.md`). No ACP. **[dev]** Providers are separate executables; Codex through `app-server`; OpenCode and Copilot declared deprecated. | Adapters over the Claude Agent SDK and the Codex SDK (app-server) plus one ACP adapter for OpenCode, Pi, Gemini CLI. `kora-runner` itself enforces `max_events`, the budget and stall detection, independently of the harness. Harness versions are pinned per installation (FR-2.1, FR-3.3, ADR-0004). | ≈ same in approach (SDK). kora has ACP and uniform limits; Archon has more providers already working. |
| Security and trust boundaries | Claude in `bypassPermissions` mode (`D/reference/security.md:14`); `allowed_tools`/`denied_tools` on a node (not for Codex). The agent gets only the declared skills and MCP (for Codex in 0.11.1 they are added to the environment). For Claude, `settingSources` defaults to `['project','user']`. Secrets in `.env`; user keys and tokens are stored encrypted (AES-256-GCM). The API has no authentication by default, CORS `*` (`D/reference/api.md:35`, `security.md:155`). Webhook signatures: HMAC for GitHub and Gitea, a plain token for GitLab. | Hermetic mode by default: repository configuration is not loaded without `trust_repo_config` (FR-3.4, ADR-0009). A tool policy protocol through a pre-tool hook, argv-level checks, `protected_paths` (FR-8b.1). Secrets are references only, responses are redacted, a leak scan runs before publish (FR-10, FR-5.2). Personal tokens are mandatory, workers use service principals (ADR-0011, NFR-4.4). | A real difference: "hermetic by default" and mandatory authentication versus "bypassPermissions and an open API by default". |
| Multi-tenancy | Explicitly not: "one install per client", client isolation is at the deployment level (`direction.md:12,25`). Users exist; in 0.11.1 all are `admin` (`D/reference/database.md:128`); **[dev]** member/admin roles for run actions. | Namespaces are the only partitioning; limits, policies, secrets and budgets per namespace; tokens are bound to a list of namespaces (FR-12.4, ADR-0011). RBAC and OIDC **[post-MVP]**. | A real difference. |
| Scale | No target numbers. `MAX_CONCURRENT_CONVERSATIONS` = 10; per-provider limits without defaults; one active run per `working_path`; `fan_out.max_parallel` = 5 (`D/reference/configuration.md:143-151,795-842`). Several processes can share one Postgres as trigger hosts, while execution remains local. | Target: hundreds of concurrent agent nodes, tens of thousands of runs per month; the MVP is verified at tens (NFR-1.1). Waiting nodes hold no resources (NFR-1.3). Limits: global, namespace, graph, runtime, fan-out (FR-6.10). The numbers are unverified, there is no load test yet (`roadmap.md`). | Scale is a design goal of kora, not a proven fact. |

## 1. Claims about Archon in `docs/positioning.md`: false, outdated or inaccurate

These findings were applied to [docs/positioning.md](../../../docs/positioning.md) in the same change.

| # | Claim in positioning.md | Verdict | Evidence |
|---|---|---|---|
| 1 | "forge plugins that open PRs on GitHub/GitLab/Gitea" (section "The problem", item 3) | **False for GitLab and Gitea** | The forge plugin protocol (`pr.create` and others) is supported only for GitHub (`plugins/forge-github`; `D/reference/forge.md`). GitLab and Gitea are community adapters: they accept webhooks and comments but do not create PRs/MRs (`packages/adapters/src/community/forge/gitlab/adapter.ts`: notes and event parsing only). ## 2. What Archon has that kora's design lacks

1. **A working product**: releases, binaries, Homebrew, a Docker image, about 23.7k stars. kora has no code.
2. **Chat interfaces and a conversational mode** (Slack, Telegram, Discord, GitHub @mention, chat with the project in web). In kora, chat approval channels are **[post-MVP]**, and there is no conversational mode at all (a non-goal).
3. **Per-user credentials**: users' own API keys and provider OAuth subscriptions, their own GitHub tokens (AES-256-GCM), a GitHub App mode with bot attribution. In kora, harness keys are environment variables at adapter level (ADR-0004), without per-user separation.
4. **Ready-made pipelines out of the box**: an SDLC pack (issue → plan → implement → review → PR) and distribution of workflows as packs from GitHub pinned to a commit. kora has only a registry of node presets and one canonical example; there is no mechanism for distributing ready-made graphs.
5. **A full web console today**: runs, DAG, event log, artifacts, cost, control buttons, builder. kora has only the approvals screen in the MVP.
6. **Resilience to provider limits**: rate-limit-aware retry (5 retries at 45 s), automatic continuation after a quota reset (`workflows.autoResumeOnQuotaReset`), `fallbackModel`, model tiers and aliases. kora has no "quota exhausted, wait until reset" error class and no fallback model.
7. **A per-provider concurrency limit** (`concurrency.providers.<id>`) shared across all processes. kora has limits per runtime, namespace, graph and fan-out, but not per provider or model.
8. **An explicit loop node** (`loop`, `loop_group` with `until_bash`/`until_field`) and `on_reject` on an approval. In kora the same is expressed through a sub-graph retry, which is a less direct way to write it.
9. **A dry-run mode with pauses at gates and fixture tests for workflows** (`--pause-at-gates`, `archon workflow test`). kora has `kora plan` and `kora trigger --dry-run` on the fake runtime; file fixtures per graph are not planned.
10. **Projects without VCS**: work in a plain folder, in place or in a container with an overlay and an approvable write-back. In kora every node requires a VCS checkout through the protocol.
11. **Deep GitHub integration** at the event level: bindings on label, check_run and status with `capacity` and a queue. kora has a generic webhook trigger and CI and change request sensors, without ready-made GitHub events.
12. **Pausing and answering from chat and with a Slack button**, `abandon` for a run. In kora this is **[post-MVP]** (chat) or absent (`abandon`).

There is no reverse list (what Archon lacks) here: it is fully visible in the "Difference that matters" column.
