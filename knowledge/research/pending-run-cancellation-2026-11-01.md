# Pending-run cancellation implementation

[Issue #598](https://github.com/realkarych/kora/issues/598), part of #593, implements only cancellation of an accepted run before node materialization. The project owner accepted the event payload and user actor representation on 2026-11-01. The normative branch and representation are in [data-model section 4](../specs/data-model.md#4-state-machines); this record supplies implementation scope and evidence limits.

## Transaction and authority

`kora.engine.cancellation.cancel_pending_run` requires an explicit authenticated user principal, namespace/graph/run identifiers, caller-owned writer connection and matching `TransitionLocks`. The connection assertion rejects using one live connection's locks for another connection. Run/global/namespace/graph scopes are asserted, never acquired by the transition. Fresh joins verify the run's graph and namespace and its pinned version's graph. An indexed node-existence predicate excludes every materialized lifecycle, including terminal node history; no node means no attempt, wait or approval owner can be changed.

One Core update and event insert share the caller transaction. Error, cancellation or refused commit cannot leave only the state or only the audit event. Caller cancellation through `Database.run` retains the database's shielded unit and release semantics. The branch changes no physical reservation, target hold, saved execution contract, retention policy, deployment status or accepted receipt. Current provider configuration is not needed to cancel existing work.

`UNCHANGED` reports only that the authorized row is already cancelled in the supported shape. It reads scalar state rather than scanning event history, produces no new event and consumes neither time nor identifier. It is not a saved HTTP response or proof that an existing event was previously verified. Event construction on first application copies the required saved trigger; work is proportional to that content, not a fixed-memory or aggregate throughput guarantee. Unrelated parameters and graph documents are not loaded. The namespace outstanding query is a test oracle, not an additional production recount.

## Verification and limits

The parametrized real-database regressions in `tests/engine/test_pending_cancellation.py` exercise atomic state/event/marker/history, duplicate and concurrent calls, promotion before a waiting cancellation, fresh authority and scoped relationships, unsupported lifecycle states, exact connection ownership, event insertion failure, rollback, request/body cancellation and database shutdown. The PostgreSQL connection-mismatch leg uses two simultaneously active writer connections; SQLite uses its writer and a distinct reader. Focused SQLite checks and strict static checks run locally; PostgreSQL, Linux/macOS and the complete final revision remain required CI evidence recorded in the PR.

The [observability activation row](../specs/observability.md#7-component-coverage-and-activation) records the safe precommit DEBUG event and filtering/sink-failure regressions. The result carries the false-to-true marker change for future caller composition. PostgreSQL NOTIFY belongs inside the caller transaction; SQLite wake-up and committed INFO belong after commit. Neither notification delivery nor the public API is implemented here.

Independent correctness, security and performance design review selected the narrow branch and removed an event-history lookup that the existing index could not bound. Final source results and exact commands/revisions/native artifacts belong in the implementing PR. The daily master mutation audit's pricing/CEL scope supplies no engine evidence and adds no campaign. CI's ten-minute feedback target remains diagnostic; transaction deadlines, exact resource release and all safety checks remain blocking.

Security applicability is TM-01, TM-08/TM-11, TM-09, TM-10, TM-06/TM-07 and TM-12. Existing threat-model actors and controls remain accurate; no human-validated threat-model change is needed. Internal object/authority checks do not establish current credential authentication/revocation, HTTP authorization, active stopping, scheduler progress or physical closure. Those consumers and the remaining #549 validation/saved-execution prerequisites retain their existing owners. No migration, dependency, package-layer widening, public operation or verification-policy change is introduced.
