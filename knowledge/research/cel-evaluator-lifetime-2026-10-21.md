# CEL evaluator lifetime baseline

Checked on 2026-10-21 for [issue #166](https://github.com/realkarych/kora/issues/166). This record covers evaluator infrastructure, not the author-expression cost and crash calibration of [issue #167](https://github.com/realkarych/kora/issues/167). The approved parent plan is [issue #160](https://github.com/realkarych/kora/issues/160).

## Ownership and workload

One daemon worker owns native programs and its LRU cache for the process lifetime. Handles own queued and in-flight jobs; the process admission ledger retains each delivered result until the caller loop receives it or closes. Closed handles release all disposable state. A stopped open loop retains charged state. Terminal failure closes admission and releases native programs; bounded failure notifications then belong to caller loops.

Defaults are 32 outstanding evaluations, 32 compiles, 16 evaluations per batch, 8 MiB outstanding charge, 128 handles and at most 256 pending lifecycle reports, 128 cache entries and 131,072 rendering characters. The charge covers detached values, renderings, metadata and result growth; it is not an exact Python/native heap measurement. Cache occupancy and outstanding counts are separate. The worker uses a restored 1 MiB stack setting; a handle close has a one-second deadline and never interrupts native work.

`tests/measurements/test_cel_evaluator_lifetime.py` runs three independent processes for each workload, each with 20 warm-up and 200 use/release cycles; resource samples follow every ten measured cycles. Native workloads include bool success/false, missing fields, wrong overloads, index/arithmetic failures, maximal list/string inputs, cache turnover beyond 128 entries and validation without cache insertion. Protocol-fake workloads alternate queued/in-flight cancellation, instance isolation and repeated close, overflow both cache bounds, repeat every mapped fault through the injected protocol, then terminate once through an unmapped fault. A separate repeated loop workload cancels completed deliveries, resumes stopped loops and closes loops before delivery. The control-exception regression verifies native cache release without catching process-exit or cancellation exceptions. Idle and eight concurrent 16-expression batch hop samples run separately from tracing. Real diagnostic pipes cover draining, blocked and broken sinks at CRITICAL (lifecycle disabled), INFO and DEBUG, with three independent processes per combination and warmed resource samples throughout 200 handle cycles. A counting reader discards bytes. Full pipes use blocking descriptors and remain open through interpreter exit. Separate exit cases hold an evaluator job in a protocol fake; they establish daemon exit with controlled in-flight work, not interruption of a native call holding the GIL. Shutdown and parent-observed exit times are retained separately.

Samples retain current/peak Python allocations, retaining paths, current Linux RSS, process peak RSS from getrusage, Linux image peak RSS from `/proc/self/status` `VmHWM`, and Linux OS task count, Python threads, descriptors, asyncio tasks, handles, outstanding jobs/charge and cache bounds. macOS RSS/OS-task counters are unavailable through these Linux interfaces and are recorded as null. Filled pipe bytes are recorded separately because process RSS excludes kernel pipe buffers. Quiescence uses owned completion and condition barriers, never sleeps or stable-count guesses. Closed/stopped-loop and fatal conjunctions also have deterministic subprocess contract tests alongside these repeated measurements.

## Pilot and gates

The initial local pilot used macOS arm64 and CPython 3.11.17 with common-expression-language 0.10.0. The native 20+200-cycle workload took 29.52 seconds with tracing, finished with one persistent worker, zero disposable jobs/handles/charge, seven descriptors and two Python threads. Cache occupancy reached its configured 128 entries. Post-cycle traced heap rose from 16,790 to 61,038 bytes as the cache filled; its final traced peak was 308,214 bytes. The largest retained difference between cycle 100 and cycle 200 came from the bounded cache and the measurement's own sample list. The fake lifecycle pilot took 0.26 seconds, ended with zero jobs/handles/charge, and its terminal fault left zero evaluator workers. These are development samples before the final revision, not final readiness evidence.

Exact gates require restored stack configuration, one persistent evaluator worker before failure and none after, zero disposable state after quiescence, unchanged descriptor/thread/task counts across measured cycles, no execution of queued-cancelled jobs, validation without cache insertion, bounded cache count/length and successful child exit. There was no evaluator implementation on the base revision, so no zero-memory or zero-latency base is fabricated. Existing binding-only and frontend controls remain comparable to base.

The expanded pilot at revision `93b9b3b` ([CI run](https://github.com/realkarych/kora/actions/runs/39631282584)) exceeded the unchanged 60-second child deadline in its first native process; its 36 diagnostic-sink and in-flight exit cases passed. No evaluator timing or memory result is inferred from that incomplete process. The replacement workload supplies each expression with its relevant input instead of converting the same combined maximal payload in five input-referencing cases. It retains all nine exact outcomes, 1,000-element lists for both index failure and size success, a 16 KiB string for size success, and all repetitions. The timeout's precise cause was not established. Loop samples measure and assert the actual pending-task count before each loop closes.

The successful reference pilot at `09e0fd8422f5fea7e9cf1e6d774ef040bfc72b0f` ([CI run](https://github.com/realkarych/kora/actions/runs/39632577712)) used Ubuntu 24.04, CPython 3.11.17 and common-expression-language 0.10.0. All 37 tests and 30 exact gates passed; the artifact retains 1,971 samples. Main workloads took 99.016 seconds and the whole suite 118.140 seconds. The following per-process budgets were frozen before the final verification run. Full spans are maximum minus minimum over cycles 10–200; late spans use cycles 100–200.

|---|---|---|---|
| Full retained heap | 46,974 B / 72 KiB | 14,414 B / 24 KiB | 9,372 B / 16 KiB |
| Late retained heap | 11,459 B / 20 KiB | 6,518 B / 12 KiB | 5,030 B / 8 KiB |

| Late RSS | 184,320 B / 320 KiB | 118,784 B / 192 KiB | 12,288 B / 24 KiB |

These ceilings round approximately 50% headroom upward, with extra page-scale margin for small RSS spans. Native retained growth is mainly bounded cache resizing and measurement samples; loop growth is mainly samples and allocation-tracing bookkeeping. Lifecycle snapshots include about 2 KiB in asyncio callback allocation sites. Exact owned-state gates accompany memory ceilings and prevent an apparently flat RSS from hiding retained jobs.

Per-process hop p95 gates are 175 microseconds idle and 1.6 milliseconds for eight concurrent batches of 16 expressions; observed maxima were 110.237 microseconds and 1.007194 milliseconds. The main-step gate is 150 seconds and whole-suite gate 180 seconds. The shared child deadline remains 60 seconds. Whole-image peak RSS is capped at 128 MiB. The pilot's getrusage value was the same 95,244,288-byte high-water mark in every child; resource accounting survives exec, so this is a conservative upper bound containing the launcher floor, not isolated native allocation calibration. The final run records and gates Linux `VmHWM` instead, with getrusage retained for comparison.

Diagnostic sink gates are one second for the complete workload and actual process exit, one second for controlled in-flight exit, 50 milliseconds for diagnostic shutdown, 192 KiB peak traced heap, 32 KiB full retained-heap span, 16 KiB late retained-heap span, 512 KiB full RSS span and 256 KiB late RSS span. Across the two expanded Linux pilots the largest complete sink exit was 0.693052 seconds, in-flight exit 0.286513 seconds, shutdown 0.010358 seconds, traced peak 114,132 bytes, full retained growth 24,371 bytes and full RSS growth 167,936 bytes. The blocked enabled writer must still be alive, undrained, with a nonempty filled pipe at actual interpreter exit; other sink cases must finish the writer. In-flight cases retain these shutdown statistics too.

Timestamp-site retained allocations were investigated in 18 separate CPython 3.11.17 processes. After 1,000 warm-up calls, isolated `datetime.isoformat()` reproduced 58-byte allocations while timezone conversion and string replacement controls did not. Three processes ran 20,000 calls and retained 45, 71 and 45 such blocks; the documented interpreter type-cache clear plus collection released every block at that site. The lookup [creates a method name](https://github.com/python/cpython/blob/v3.11.17/Objects/object.c#L743-L754), and the [type lookup cache retains names](https://github.com/python/cpython/blob/v3.11.17/Objects/typeobject.c#L3552-L3603) in a [4,096-entry table](https://github.com/python/cpython/blob/v3.11.17/Include/internal/pycore_typeobject.h#L19-L30). This attributes the growth to a bounded interpreter cache. The production code and CI measurement never clear that cache; their budgets include its measured variance.

The dedicated `CEL evaluator lifetime` CI job installs locked wheels with read-only repository permissions and pinned actions; its artifact is `cel-evaluator-lifetime-measurement`. The artifact records the PR head and checked-out revision separately. All existing checks remain active. The owner must add this new status to required merge protection after it exists; this change does not claim that workflow creation activates that protection.

## Consumer activation

No API, scheduler, standalone or testing product consumer is activated. #167 calibration, schema-driven checking/projections and correction of minimum-int unary negation (including dynamically computed values) must precede the first author-expression consumer. Typed `additionalProperties` also belongs to checker/projection integration because the current `Record` type cannot express it. Persistence, transaction allowance, error deduplication and public-surface parity remain with their implementing work items.
