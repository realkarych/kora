# Separate raw-crash storage contract for #778

## Impact

Raw crash output may use an explicitly selected destination independently of execution state. This permits native filesystem fault verification without admitting user-space filesystems for state_root or treating diagnostic contents as execution authority. FSKit support remains conditional on platform and recovery qualification.

## Status and governing context

Date: 2026-11-06. This is a proposed design under [#778](https://github.com/realkarych/kora/issues/778), preserved by [#799](https://github.com/realkarych/kora/issues/799). It does not activate FSKit, change accepted storage admission or establish implementation readiness. The [issue contract and review](https://github.com/realkarych/kora/issues/778#issuecomment-6671108020) record its provenance.

The governing contracts remain [local runtime](../specs/protocols.md#local-runtime-issue-123), [observability](../specs/observability.md) and [verification](../../.claude/skills/kora-verify/SKILL.md). The collector design depends on the unmerged [#701](https://github.com/realkarych/kora/issues/701) implementation based on revision `15807431190bdf873a06f230a112d52d90e72772`; the repository target inspected for this record is `5251bafebb8f34cbee9402773adf9c17f6c10c8b`. Existing [native fixture release](native-fixture-release-2026-11-05.md) supplies only the explicitly reused release boundary.

All requirements below are proposed requirements, not claims of implemented behavior. The proposal changes only the placement and associated ownership of raw crash bytes for the opt-in route. It does not activate structured runner.log isolation, journal/checkpoint storage or a general user-space-filesystem runtime. No deadline, assertion, capacity or required platform is removed.

Feasibility update, 2026-11-06: [research PR #834](https://github.com/realkarych/kora/pull/834) records the subsequent investigation ([inspected research revision](https://github.com/klukashka/kora/blob/2157faaaa965213faed44316e5fcd62dda3410a2/knowledge/research/macos-native-io-fixture-feasibility-2026-11-06.md)). It supplies source-based findings, not native qualification. [FSKit provisioning #827](https://github.com/realkarych/kora/issues/827) remains blocked: no supported macOS-15 mechanism has been established that both proves settlement of all extension sessions and excludes new sessions, including queued launches, before owned bundle removal. Observed disabled state, known-process exit and registration inventory do not establish that complete boundary. The restart-based NFS alternative also lacks an established five-second borrower-settlement and ordinary-unmount mechanism after server loss. ## 1. Configuration and authority separation

Keep state_root and diagnostic_directory semantics unchanged: diagnostic_directory is the existing LOCAL collector coordination directory, not the output destination. Their open_local_directory and unsafe-filesystem refusal remain mandatory. Qualify the actual FSKit f_fstypename and add a narrow refusal for every admitted fixture filesystem type if the current denylist does not already reject it. A newly named FSKit type is not an exception; no FSKit admission can ship until the authority-root negative test passes. This may strengthen the guard, never remove or bypass it. Domain/registry/Starting, runner state, sockets, owner records, locks, journal/checkpoint, control and evidence stay on accepted local filesystems.

Add an optional provider configuration raw_crash_storage with exactly {kind, root}; kind is local or fskit, root is an absolute printable path of at most 1024 UTF-8 bytes. Null/omission preserves the existing state_root/attempts/<key>/runner.crash behavior. Explicit local requires the ordinary local-filesystem guard. Explicit fskit is a macOS-only capability and requires a qualified owned FSKit mount; Linux refuses this kind as unsupported, not silently local. No environment override, automatic detection, per-attempt producer path or fallback destination.

The opt-in root is a sibling/disjoint tree, not equal to, below, or an ancestor of state_root, coordination, sockets or the fixture control/backing/evidence directories. Reject aliases using retained ancestry identities, not string prefix checks alone. An FSKit mount hidden under state_root never authorizes this route. Local structural configuration errors are config_error; missing/unavailable/unqualified destination makes raw diagnostics unavailable under existing nonfatal diagnostic admission rules, without changing execution eligibility. No workload receives an FSKit descriptor or control capability.

Only raw runner.crash bytes use the opt-in root. All raw content remains potentially sensitive and never becomes public CI evidence, structured logs, recovery input, credentials, launch parameters or a source of registry state. An FSKit backend sees this content; enabling it explicitly trusts that reviewed extension and its backing owner with raw crash data. Mode/UID/inode values reported by a user-space FS do not authenticate that extension or establish isolation from a malicious same-user backend.

## 2. Destination binding and persisted authority

Bind the route to the existing local exclusive collector lease. Proposed owner format local-diagnostic-owner/3 and transport crash-inherited/2 carry a storage binding; older live collectors are not replaced. Unknown/old incompatible live formats yield diagnostic unavailability, not adoption or workload failure. Migration requires proved prior collector exit, acquisition of the SAME local lease and no unresolved storage claim. Do not raise the existing 4096-byte owner/activation or handshake limits: reject an encoded record/frame that does not fit.

Closed storage object in owner/3: storage_version is literal 1; kind is default/local/fskit; root is explicitly null for default and the validated exact absolute configuration string otherwise; route_id is lowercase 64-character hex SHA-256 of canonical UTF-8 JSON {storage_version,kind,root}; destination is explicitly null until first preparation and then DirectoryIdentity; mount_session is explicitly null for default/local and a required local-owner-issued Nonce for fskit. No unknown fields or implicit defaults. Reject dot/dot-dot path components rather than rewriting paths; do not realpath through FSKit to normalize them. Use the repository canonical JSON encoder. The existing outer collector generation is the sole generation field and binds this storage object; do not duplicate it.

Activation carries the complete owner/3 record. Every Prepare/Prepared/Offer/Activate/Activated transport/2 binding carries route_id and mount_session in addition to its existing domain/generation/attempt/nonce fields. Prepared is the prepared-kind offer and is explicitly checked before an endpoint can be handed to a runner. Compare the configuration route before connecting to an existing collector, compare every handshake response and reject mismatches before destination I/O. Native peer authentication and local Starting validation remain mandatory; a hash is consistency evidence, not authentication. Updating destination from null to its first verified identity happens under the held local lease before Prepared. That identity is immutable for the generation; later requests validate against it. The same existing 4096-byte frame bound applies to the full encoded message.

A path, route hash, inode or FSKit filesystem name alone is not mount authentication. The fixture owner must bind an authenticated extension control peer (kernel process identity plus verified code-signing/build requirement), owner-issued session nonce, extension volume identity, kernel mount identity, backing directory identity and destination ancestry. Expected build identity comes from the independently retained reviewed fixture bundle, never from destination metadata. This local attestation remains outside the mounted FS. Restarted extension processes require a new session; they cannot adopt an old claim. The exact macOS API/entitlement availability for this peer-to-mount binding is a qualification blocker, not permission to accept a self-reported receipt. No generic third-party FSKit adoption in this slice.

The collector's initial ready means only control/lease readiness, never destination readiness. It performs NO destination open/stat/mount query before an authenticated Prepare. It validates the current local Starting/submitter/nonce, durably reserves that attempt's opening claim, then opens and validates the destination inside its accounted native-I/O owner, pins/publishes its first identity and only then sends Prepared. Thus even a blocked first root-open has an existing counted durable owner. Never perform potentially blocking destination operations on the worker event loop. The existing launch/preparation cutoff applies; timing out leaves any started operation owned and prevents replacement.

Pin one destination identity/mount session per generation. Each registration retains its own opened root descriptor until its file and directories actually close; no unaccounted generation-long destination FD survives claim settlement. Open children relative to that descriptor, no-follow. Configuration changes, root replacement, remount or extension restart cannot redirect a live collector. New generations use distinct opaque namespaces: <generation>/<registry-key>/<Starting-nonce>/runner.crash for explicit routes. Preserve regular-file, same-user, 0600, single-link and directory-0700 checks. No symlink/hard-link traversal, truncation, cross-generation append or arbitrary name supplied by a producer.

All mutable execution authority stays local. Destination bytes/metadata cannot clear a local claim. The new ledger and cleanup receipts apply ONLY to explicit local/fskit routes; the default retains its existing cleanup/recovery algorithm. A local bounded claim ledger has format raw-crash-claims/1, a maximum of 16 entries and a maximum encoded size of 16 KiB; each entry contains generation, route_id, mount_session (nullable for local), attempt key, Starting nonce, collector identity and state opening/active/closing/unresolved. No raw payload or arbitrary exception text. Insert and durably commit the local claim BEFORE the first destination effect. Commit/rename obey the existing local atomic-write rules; failed or unknown persistence cannot authorize an effect. Claims charge the existing 16-registration capacity, not an additional pool of 16. If claim removal fails after physical closure, the credit remains charged and new generations remain blocked. These are new persisted formats requiring explicit approval. Format/handshake compatibility checks apply to both modes; preserving the default does not mean an incompatible live collector can be upgraded in place.

## 3. Resource ownership and loss

The collector owns native work, destination descriptors, buffered raw bytes and the local lease. The fixture storage owner independently owns the FSKit mount, extension session, backing directory, request barrier, control channel and teardown. It survives loss of the client/test worker; no parent-death handler running on a blocked filesystem thread is sufficient.

Opening, active, closing and unresolved registrations all consume capacity until actual native closure. Retain existing single native executor, 16-registration ceiling and 64 KiB payload chunk. No unbounded queue, replacement collector, replacement writer thread or automatic mount retry. Additional storage protocol metadata is bounded separately and never increases payload admission.

A claim becomes settled only after the collector's actual native operation/descriptor closure AND, for a faulted FSKit session, independent proof that the filesystem has no outstanding request/late completion for that binding. Removing a claim is the local owner's operation under the original lease; storage-supplied messages alone cannot clear it. Collector death, channel EOF, elapsed time, signal delivery, extension exit and path disappearance are individually insufficient. If a collector dies before closure, the persistent claim remains unresolved and blocks new generation admission; there is no automatic clearing on restart. No append replay or inference of written bytes from file size.

Successful crash data is retained until Runtime.release, as in the existing contract. Release must remove the exact bound opt-in crash file and its now-empty owned attempt directories before reporting successful release. Record the route/generation/file identity needed for that deletion in a bounded local per-attempt cleanup receipt before any output is admitted; receipt is at most 4096 bytes, format raw-crash-cleanup/1, contains the same route binding plus generation/key/nonce and nullable file identity until open completes. Keep it in the existing local attempt lifecycle, not in the FSKit mount. Only one receipt per attempt is allowed: a retained receipt for another generation/route refuses a new diagnostic preparation until its existing release completes, rather than accumulating another file or overwriting cleanup authority. This is a further explicit persisted-format change. The public LocalRuntime.release(handle, ctx) is specified but not implemented at the inspected master or preserved #701 checkout. Runtime close()/_release() and registry.release are not attempt cleanup. Implementing that public release path is a separate prerequisite. Deletion must use an accounted bounded native cleanup owner, preserve the specified deadline and return the specified retryable refusal on uncertain/blocked deletion; no successful tombstone precedes actual cleanup. Cancellation prohibits starting new deletions; late completion does not create a tombstone. No automatic replay or best-effort deletion of a substituted path. Fixture-owned synthetic data is likewise deleted only after full settlement. Background cross-attempt GC remains outside scope; release behavior is not waived.

On lost readiness, cancellation or extension failure, preserve the original failure and the local unresolved claim. A late write or reply may establish settlement but cannot revive the cancelled producer, create activation success, resurrect a retired attempt or produce a tombstone. If complete recovery cannot be proven, report nonzero/unavailable and retain ownership; this is not successful cleanup or acceptance evidence.

## 4. FSKit barrier, observation and recovery

One fixture mount/session, one armed target and at most one held native request per fixture. Closed control commands ARM, RELEASE, ABORT and STATUS contain only owner-issued session/operation identifiers; no path, PID, device, command, filename or raw data supplied as control authority. Control is private and bound to the directly owned participants. Explicit bounded control frames are at most 4096 bytes; no public listener.

State machine: IDLE -> ARMED -> HELD -> RELEASING -> SETTLED. ABORT/EOF in IDLE/ARMED permanently disarms that operation generation; a later request proceeds normally and cannot become held. RELEASE/ABORT/EOF in HELD completes the real backing write and replies exactly once. Repeated terminal commands cannot issue another write. A failure before any write can reply with the actual error; partial writes report the actual byte count, never success for unwritten bytes. The test remains failed when its required exact-byte outcome did not occur.

The extension retains only a bounded target request, correlated to its kernel request identity, file handle/identity, offset and count. Split requests are not automatically treated as a complete syscall: holding one request is acceptable only with proof that the originating collector call cannot complete; subsequent fragments remain subject to the unchanged capacity and byte limits. Do not copy an unbounded SDK-supplied request into an owned buffer. If the installed API cannot bound delivery or provide the required identity/correlation, qualification fails.

The release/watchdog path must be independently schedulable while the target request is held. It and every executable, stack/control/evidence/backing path remain outside the FSKit mount. No freeze/thaw ioctl is used. No force/lazy unmount, global daemon kill or automatic eject is a success witness.

Observation requires BOTH a kernel-delivered write for the exact collector/file/operation and proof that the collector's syscall remains outstanding. A callback before os.write, an extension receipt alone, a sleeping thread or elapsed time is insufficient. macOS-15 cache/completion behavior must be qualified; newer cache APIs are not assumed available. Positive control uses an ordinary real regular-file writer; negative controls cover unarmed writes, unrelated files and operations already completed through caching.

Normal release requires exact bytes and actual collector termination within the existing five-second post-release bound, followed by acquisition of the same local lease. Client/control-owner loss must release without help from the lost process. Extension death and late kernel completion require a separate real negative test: no false settlement; borrowed resources must settle within existing cleanup limits for the supported case to pass. The framework's behavior on extension loss is unverified; this design makes no promise that a watchdog can cancel arbitrary kernel I/O.

Normal cleanup order: permanently disarm -> settle held/native requests and registration descriptors -> collector durably clears the corresponding claims while still holding its original local lease -> collector closes/releases lease and actually exits -> settle all remaining borrowers -> ordinary unmount -> stop/release owned extension session and control resources -> release backing image using #751 where applicable -> remove fixture files. Successful output deletion by Runtime.release is separately accounted as above. If the collector dies first, a recovery owner acquires the same lease, verifies prior process identity/absence and ledger binding, and may clear a claim only after independently proving native/filesystem settlement; unknown completion has no automatic clearing path and forbids new generations. Ordinary recovery is not an extension-self-report shortcut. Unknown completion prohibits later destructive steps. Existing outer deadlines and #751 release's 30-second budget with five-second settlement reserve stay unchanged and are not restarted by a prior timeout.

## 5. Blocking acceptance and risks

Named acceptance cases, all real paths without mocks/skips:

- test_state_root_and_coordination_still_refuse_userspace_filesystems: real forbidden mounts fail unchanged admission even with raw_crash_storage configured.
- test_raw_crash_route_cannot_redirect_execution_authority: malformed/replaced root, mount session, producer path and tampered diagnostic metadata cannot affect registry/lease/Starting.
- test_raw_crash_storage_defaults_preserve_existing_path: omission preserves current behavior; explicit route writes only its destination; unavailable storage never falls back.
- test_raw_crash_binding_survives_configuration_change: same lease/generation rejects route change, remount and incompatible live collector; no duplicate writer.
- test_raw_crash_claim_precedes_destination_effect: real process loss at admission/settlement boundaries leaves correct local claims and prevents unsafe reuse.
- test_raw_crash_root_open_loss_is_accounted: loss during the FIRST destination open before Prepared retains its already durable attempt claim; initial control-ready never implies storage-ready.
- test_release_removes_bound_external_crash_before_tombstone: normal, blocked, cancelled, replaced-target and late deletion preserve existing release semantics and deadlines.
- test_fskit_write_is_native_and_outstanding: kernel request plus syscall evidence, cache-negative controls and exact bytes after release on macOS 15.
- test_fskit_abort_before_arrival_never_holds_late_request: real arrival/abort/EOF races, repeated release and split-request handling.
- test_fskit_owner_loss_preserves_release_and_capacity: loss of client/control owner/collector/extension, late completion and all opening/closing/unresolved slots retained until proved settlement.
- test_collector_keeps_lease_during_native_diagnostic_write: actual #701 scenario, independently pre-opened second runtime reaches handshake, same lease held through original L, original P refusal, actual exit after release within five seconds.
- test_fskit_cleanup_requires_settled_borrowers: no premature unmount/detach, all owned resources return to baseline under existing lifecycle method; RSS remains diagnostic.

Strict checks, affected pressure regressions and one complete final-head Linux/macOS CI remain mandatory. FSKit-specific capability is macOS-only; Linux still exercises route/authority/claims/collector behavior with a real accepted local destination and its native barrier. No platform omission is converted into skip/pass. FSKit qualification does not prove #616 journal/checkpoint durability or all storage failure modes.

Key risks: raw content disclosure to the extension; spoofable filesystem metadata; old/new owner-format compatibility; blocked destination admission; late effects after collector loss; unbounded framework requests; filesystem cache hiding syscall completion; extension install/enable/signing and macOS-15 CI availability; directory/rename/fsync semantics of the fixture. None is resolved by the written contract alone. Apple documents the [extension](https://developer.apple.com/documentation/fskit/building-a-passthrough-file-system) and [reply API](https://developer.apple.com/documentation/fskit/fsvolume/readwriteoperations), not this collector correlation or five-second recovery guarantee.

## 7. Review coverage and decision

Correctness: local binding/claims -> collector admission and loss -> fixture operation/recovery; boundary owner is the coordinator. Security: state-root isolation, diagnostic-content exposure, filesystem/mount identity and private control authority. Performance/resources: all counted native jobs/requests/FDs/processes/mounts, bounded buffers and lifecycle deadlines. Reuse prior #751 results only for unchanged post-settlement backing release; they do not qualify FSKit. Browser/API parity is not applicable: no new HTTP operation or visible console flow.

Implementation approval must explicitly cover the new diagnostic-only filesystem boundary, optional config, owner/protocol/claim formats and platform/toolchain requirements. Code, installation, privileged qualification, publication of code and CI runs require their own authorization. No storage guard, acceptance criterion or deadline changes through this proposal alone.
