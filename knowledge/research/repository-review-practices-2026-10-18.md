# Repository-owned review practices

**Kora should first validate and reuse its existing native GitHub Codex review and repository-owned local skill.** Native review supports scoped repository rules and focused requests; an observed kora result also identifies the reviewed commit. The outstanding questions are reliable mandatory enforcement, all-contributor eligibility, and proof of independent component coverage—not whether an AI review engine exists. Sentry provides the strongest external evidence linking specialist instructions, dispatch, and a finding naming that specialist. Warden and CLI/action runners remain alternatives if a demonstrated native gap requires them; no evidence yet justifies adding a second engine or API-key requirement. Reverse-transitive selection and executable resource checks remain useful mechanisms whichever engine runs the review. ([Native review documentation](https://learn.chatgpt.com/docs/third-party/github), [kora result](https://github.com/realkarych/kora/pull/88#issuecomment-6250640362), [Sentry specialist finding](https://github.com/getsentry/sentry/pull/127793#discussion_r4296908262))

This comparative survey did not run paid reviews, independently reproduce findings, compare provider quality, or audit external repositories' live branch protections. Sentry's useful separation is between routing, specialist knowledge, and reporting policy. Its backend skill follows callers, serializers, tasks, and ORM boundaries and requires concrete triggering conditions and consequences. That is semantic investigation, not exhaustive graph closure. Coverage must follow actual configuration: its frontend skill is absent from the inspected Warden profile list, while the DoS profile disables both reporting and failure. Likewise, Continue's React performance guidance sits outside the runner's discovered `agents/` directory. **Available instructions do not establish executed coverage.** ([Sentry skill](https://github.com/getsentry/sentry/blob/5218028463085ab2daa66a4675eef73ff6506282/.agents/skills/sentry-backend-bugs/SKILL.md), [configuration](https://github.com/getsentry/sentry/blob/5218028463085ab2daa66a4675eef73ff6506282/warden.toml), [Continue runner](https://github.com/continuedev/continue/blob/5522c6f44ca0ac3528b37244818fbfa39b5af470/.github/workflows/continue-agents.yml))

## Native Codex deserves validation before another engine

Official documentation supports automatic reviews, focused `@codex review` comments, and root/nested `AGENTS.md` guidance. Eligibility for every contributor has not been demonstrated in this survey. A referenced `code_review.md` can also guide local review, so repository-owned review knowledge can already be shared. These capabilities establish a practical starting point; they do not promise arbitrary child-agent fanout, per-component completion traces, or identical local/cloud execution. Kora's existing single-pass, no-children GitHub mode is **project policy**, not evidence of a service limitation. ([GitHub integration](https://learn.chatgpt.com/docs/third-party/github), [scoped review rules](https://developers.openai.com/blog/custom-code-review-rules-for-codex), [local guidance](https://learn.chatgpt.com/docs/learn/best-practices), [kora policy](https://github.com/realkarych/kora/blob/0c1ee5bdc7f390509a42bf75191dde706924d15a/.claude/skills/kora-verify/SKILL.md))

Independent fresh contexts for the applicable profiles are a required outcome, not an optional alternative to a single pass. The first bounded validation asks whether one native review can demonstrably delegate to fresh profile agents; whether automation covers external contributors and subsequent commits; and whether completion remains observable after edits or retries. The comparative survey itself ran no such experiment; the separate probe records its narrower result. An overall completed review does not prove that every expected component received a fresh independent reviewer.

**Warden is the closest packaged candidate**, inspected at `15f9ae6` (2026-10-16). Its local CLI and Action share execution machinery; configuration includes skills, triggers, models, turn limits, concurrency, and failure/report thresholds. Local review calls shared `runSkill`; Pi creates in-memory sessions and Claude disables session persistence. These are executable agent invocations, stronger evidence than a prompt requesting several perspectives. However, its main analysis work item is a **diff hunk with context**, and same-file hunks can run concurrently. Path-selected hunk agents do not establish one independent, whole-component review for every directly or transitively affected component. ([Local execution](https://github.com/getsentry/warden/blob/15f9ae6ff3ffc01ba34e8ba2f427a87847239794/packages/warden/src/sdk/local.ts#L56-L150), [analysis dispatch](https://github.com/getsentry/warden/blob/15f9ae6ff3ffc01ba34e8ba2f427a87847239794/packages/warden/src/sdk/analyze.ts#L410-L440), [architecture](https://github.com/getsentry/warden/blob/15f9ae6ff3ffc01ba34e8ba2f427a87847239794/packages/docs/src/content/docs/architecture.mdx#L48-L110))

Warden is **source-available under FSL-1.1-ALv2**, with a Competing Use restriction and an Apache-2.0 grant effective on each version's second anniversary. This warrants an explicit adoption decision; it is not an unqualified permissive dependency. Pi offers provider/model routing, while Claude is a separate backend. Aggregate cost limits, complete failure handling, immutable revision binding, and component-level coverage remain unverified. Sentry's observed use does not identify the exact Warden engine revision behind its finding. ([License](https://github.com/getsentry/warden/blob/15f9ae6ff3ffc01ba34e8ba2f427a87847239794/LICENSE), [runtime configuration](https://github.com/getsentry/warden/blob/15f9ae6ff3ffc01ba34e8ba2f427a87847239794/packages/docs/src/content/docs/config/models.mdx))

**Codex CLI/action** is a fallback execution primitive if native review cannot satisfy an approved requirement. Action `a8d8be6` (2026-10-09) launches one `codex exec`, accepts a pinned CLI, prompt and output schema, and rejects nonzero exit. Shared invocation supports local/CI parity without guaranteeing identical environments or judgments. The action supplies neither component selection nor verified task completeness; its merge-ref example also does not enforce reviewed-byte identity. These capabilities justify retaining the option, not adopting it before establishing the native gap. ([Action inputs](https://github.com/openai/codex-action/blob/a8d8be6ee028bea4525bc722d16f36687b408c81/action.yml#L1-L126), [execution](https://github.com/openai/codex-action/blob/a8d8be6ee028bea4525bc722d16f36687b408c81/src/runCodexExec.ts#L260-L396), [example](https://github.com/openai/codex-action/blob/a8d8be6ee028bea4525bc722d16f36687b408c81/README.md#L22-L96))

**Claude Action**, `f27be6b` (2026-10-16), provides SDK execution, structured-output validation, turn limits, and genuine native subagent capability. Its own five-category review command is not an affected-component selector; its current review workflow skips forks and triggers only on opening. Default settings loading also includes user/local configuration. Claude's proprietary runtime and action licensing are separate questions. ([Result handling](https://github.com/anthropics/claude-code-action/blob/f27be6b65a4652f08a2ba3cff79114829b588967/base-action/src/run-claude-sdk.ts#L189-L288), [workflow](https://github.com/anthropics/claude-code-action/blob/f27be6b65a4652f08a2ba3cff79114829b588967/.github/workflows/claude-review.yml), [settings mapping](https://github.com/anthropics/claude-code-action/blob/f27be6b65a4652f08a2ba3cff79114829b588967/base-action/src/parse-sdk-options.ts#L314-L348), [runtime license](https://github.com/anthropics/claude-code/blob/dd6bee38458cc3e6dc5f2b16eca1f0f364619ad8/LICENSE.md))

**PR-Agent**, `33d3e26` (2026-10-18), reuses its reviewer across local and hosted providers and supports multiple model providers. Its parallel work is diff-chunk completion calls, not autonomous component agents; partial chunks can survive failures, and CLI failure propagation is configurable. **gh-aw**, `a84462a` (2026-10-18), supplies a larger workflow compiler with constrained publication and several agent engines. Its normal run/trial commands dispatch GitHub execution rather than equivalent local review, and its inspected reviewer caps prefetched diff and permits fifteen minutes. Neither fits kora's entire contract without additional policy. ([PR-Agent local provider](https://github.com/The-PR-Agent/pr-agent/blob/33d3e267c910d196689b6770c3e36f3ece0bd00f/pr_agent/git_providers/local_git_provider.py#L42-L100), [partial results](https://github.com/The-PR-Agent/pr-agent/blob/33d3e267c910d196689b6770c3e36f3ece0bd00f/pr_agent/tools/pr_reviewer.py#L489-L529), [gh-aw execution](https://github.com/github/gh-aw/blob/a84462a7dc357328a53b8bb3f39aa06b6f18b16f/pkg/cli/run_workflow_execution.go#L80-L195), [review policy](https://github.com/github/gh-aw/blob/a84462a7dc357328a53b8bb3f39aa06b6f18b16f/.github/workflows/pr-code-quality-reviewer.md#L36-L90))

## Impact selection needs a graph outside the reviewer

Nx provides a concrete mechanism worth reusing conceptually. At `b58ec0d`, its own CI runs affected targets; implementation reverses the project graph and recursively visits dependents with a visited set. Declared shared inputs include configuration and workflows, while project deletion has a conservative all-project fallback. Unowned paths do not automatically select everything. These details matter more than the label “affected”: **ownership, dependency edges, and global inputs must be explicit**. Installing Nx is not necessary to reuse those semantics. ([Traversal](https://github.com/nrwl/nx/blob/b58ec0df554ac86f3f37e37ae25181fa67665c8e/packages/nx/src/project-graph/affected/affected-project-graph.ts#L40), [shared inputs](https://github.com/nrwl/nx/blob/b58ec0df554ac86f3f37e37ae25181fa67665c8e/nx.json#L8), [deletion fallback](https://github.com/nrwl/nx/blob/b58ec0df554ac86f3f37e37ae25181fa67665c8e/packages/nx/src/native/affected/projects/project_glob_changes.rs#L9))

For kora, the inference is that imports alone cannot express how API contracts affect backend, CLI, MCP, generated clients, and frontend. Specification and policy relationships need declared influence, with semantic investigation extending the deterministic selection. Unknown paths, missing history, renames, deletions, and policy changes need conservative behavior. A PR must not lower its own required coverage by editing the selector. A trusted base policy and conservative reconciliation with changed topology are proposed invariants, **not verified properties of Nx or the inspected AI engines**.

Independent review likewise needs a controller-owned expected task set. Separate fresh invocations give clearer task boundaries than asking one parent model to fan out correctly. Structured results can identify scope, examined contracts, evidence, findings, and revision; schema validity proves only shape. Completion requires comparing actual task records against the expected set and validating their revision identity. It cannot prove the model read everything or found every defect. This extends the observed runner primitives into a kora-specific contract, rather than claiming an existing engine already supplies it.

## Required checks must bind completion to the current head

Kora PR #88 provides concrete native evidence. A comment by `chatgpt-codex-connector[bot]` contains `codex-review-state:v1`: code review is `completed`, both finding flags are false, and `commit_sha` is `d6f8be0c76bdd6f6f03689be6670d8555eed24ac`; security-review fields are unset. A second receipt identifies that commit. Inspection found no Codex CheckRun at that SHA, only existing documentation jobs. **The marker is observed behavior, not a documented stable API.** ([State comment](https://github.com/realkarych/kora/pull/88#issuecomment-6250640362), [receipt](https://github.com/realkarych/kora/pull/88#issuecomment-6250719979), [check-runs endpoint](https://api.github.com/repos/realkarych/kora/commits/d6f8be0c76bdd6f6f03689be6670d8555eed24ac/check-runs))

This makes a small native-status gate a candidate worth validating. It would need authenticated bot/App identity, exact current-head matching, strict marker version/shape validation, and non-success for unknown or incomplete states. Its semantics would be “native review completed for this head,” with finding policy separately defined; it could not attest to unseen internal agents, component coverage, or runtime measurements. Depending on an undocumented marker also requires an explicit compatibility decision.

VS Code's executable precedent is an aggregate job with `needs`, `if: always()`, and an explicit success predicate. Failed, cancelled, or skipped dependencies do not accidentally satisfy it. CPython similarly aggregates results with explicitly declared exceptions. Their checked-in code proves aggregation; it does not independently prove the current repository ruleset requires those names. ([VS Code aggregate](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/.github/workflows/pr.yml#L336), [CPython aggregate](https://github.com/python/cpython/blob/cdf010b10c673e1ec4faaf3f8f9be39237986880/.github/workflows/build.yml#L606))

The corresponding kora requirement is a stable required result for **the exact reviewed PR head**, independent of contributor identity. Missing, duplicate, malformed, stale, timed-out, or incomplete required reviews cannot become success. GitHub can evaluate test-merge checks rather than head checks, so head binding must be deliberate; the Check Runs API accepts explicit `head_sha`. Source-restricted required checks and merge-queue handling also require repository administration. `always()` cannot guarantee execution after whole-workflow cancellation: the status must remain non-successful. ([Required-check semantics](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [Check Runs API](https://docs.github.com/en/rest/checks/runs#create-a-check-run))

All-contributor coverage still requires checking native eligibility and trust boundaries. A native-status adapter need not invoke a model or receive a model API key. If a separate runner becomes necessary, fork workflows normally lack model secrets; elevated `pull_request_target` must not execute untrusted PR code or configuration. The disabled Next.js publisher offers design evidence for trusted identity validation, current-head rechecking, bounded output, and late write authority. Any PR-code execution belongs outside the privileged controller, without model or publishing credentials. ([GitHub security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target), [Next.js publisher](https://github.com/vercel/next.js/blob/bb63c72077ad7b81b2319f74a7ef3b00c1751483/.github/scripts/automated_code_review.js))

## Performance evidence comes from executable lifecycle checks

Performance review also needs a comparison, not isolated timings. VS Code's executable benchmark drives an Electron application against a local scenario server and compares build metrics using thresholds and statistical tests; only selected metrics can fail the run, with explicit handling when statistical results are unavailable. Kora should transfer the requirement for representative workloads, controlled comparison conditions, and an explicit verdict rule, rather than copying thresholds. A generic prompt asking about complexity or memory cannot provide that evidence. ([Executable comparison](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/scripts/chat-simulation/test-chat-perf-regression.js#L1024))

VS Code connects agent guidance to concrete resource ownership. `ensureNoDisposablesAreLeakedInTestSuite()` tracks disposable objects and throws during teardown when ownership leaks remain; real suites invoke it. Its chat leak runner repeatedly exercises scenarios, returns to empty state, forces GC, excludes warm-up where possible, and fails on retained heap growth. This measures particular lifecycle scenarios, not every allocation or resource. ([Teardown checker](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/src/vs/base/test/common/utils.ts#L53), [real suite](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/src/vs/base/test/common/stream.test.ts#L617), [heap verdict](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/scripts/chat-simulation/test-chat-mem-leaks.js#L425))

**Instruction/code drift is observable:** at the same revision, skills describe per-message slope and a 2 MB/message threshold, while executable code uses clean-state residual. Its benchmark workflow runs and uploads evidence, but the latest observed runs failed for uninvestigated reasons. Therefore reports must name the actual command, revisions, workload, metric, threshold, output, and limitations. A skill description or successful AI job is insufficient measurement evidence. ([Stale description](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/.github/skills/chat-perf/SKILL.md#L206), [current calculation](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/scripts/chat-simulation/test-chat-mem-leaks.js#L352), [observed run](https://github.com/microsoft/vscode/actions/runs/39106215917))

CPython, at `cdf010b`, extends repeated lifecycle measurement to references, allocated blocks, and file descriptors after warm-up and cleanup. Availability of this machinery does not prove every PR invokes it; its ASan configuration even disables leak detection. For kora, the transferable method is repeated completion, cancellation, and failure returning to a known state, with accounting appropriate to tasks, processes, connections, streams, descriptors, retained buffers, or frontend listeners. Thresholds must be workload-specific. ([Resource loop](https://github.com/python/cpython/blob/cdf010b10c673e1ec4faaf3f8f9be39237986880/Lib/test/libregrtest/refleak.py#L103), [ASan configuration](https://github.com/python/cpython/blob/cdf010b10c673e1ec4faaf3f8f9be39237986880/.github/workflows/reusable-san.yml#L47))

Reuse the measurement mechanism rather than incompatible test code: the inspected VS Code scenario loops contain fixed waits and catch-and-continue paths. Kora requires injected protocol fakes, explicit completion conditions, and fail-fast behavior. Lightweight lifecycle assertions belong in deterministic product tests; live agent review can select and inspect their evidence without introducing model calls into those tests. ([Scenario loop](https://github.com/microsoft/vscode/blob/bd48654d9acb491371090b13841cff4dd1888fc8/scripts/chat-simulation/test-chat-mem-leaks.js#L290))

## Conclusion

At kora `0c1ee5b`, `kora-verify` already defines four review profiles; native GitHub review is observed, while repository CI does not orchestrate the profiles. **First validate native profile delegation and reuse the local repository skill.** A PR-wide status gate cannot satisfy the independent-context requirement by itself. Native review could cover repository-specific judgment and head-bound completion without another model integration. Strict fresh component agents and local/CI execution parity remain unproven; shared instructions and overall completion must not silently substitute for them. Only a demonstrated gap, followed by owner approval, warrants a pinned CLI/action layer or Warden evaluation. Warden's packaging remains attractive if its hunk granularity and FSL terms fit; neither alternative removes kora's scope and evidence responsibilities. ([Current skill](https://github.com/realkarych/kora/blob/0c1ee5bdc7f390509a42bf75191dde706924d15a/.claude/skills/kora-verify/SKILL.md), [current CI](https://github.com/realkarych/kora/blob/0c1ee5bdc7f390509a42bf75191dde706924d15a/.github/workflows/ci.yml), [native result](https://github.com/realkarych/kora/pull/88#issuecomment-6250640362))

Independent fresh profile contexts are required. Unresolved implementation decisions are native automation eligibility and result correlation, undocumented-marker dependency, measurement depth, outage/waiver policy, and check administration. Provider funding and Warden licensing become adoption questions if another runner is justified. Live model review remains separate from deterministic product tests. Integration must retain typed Python, no handwritten comments or mocks, uv/pnpm, Linux/macOS, and the whole-pipeline ten-minute limit. Missing measurements remain missing evidence. Policy changes require an issue and explicit owner-approved plan before repository edits. ([Kora contribution constraints](https://github.com/realkarych/kora/blob/0c1ee5bdc7f390509a42bf75191dde706924d15a/AGENTS.md))
