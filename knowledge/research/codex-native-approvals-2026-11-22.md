Reviewed on 2026-11-22 against kora base `2b35d9659aa06ea2a02bd1ad8067b13b888b1041` and official Codex 0.166.0 at `6ff1e1ca3b30fc8b914720681fcf5fe62e95f856`. The policy decision is recorded in [#1356](https://github.com/realkarych/kora/issues/1356), [#1360](https://github.com/realkarych/kora/issues/1360) and the [design plan](https://github.com/realkarych/kora/issues/1360#issuecomment-7082506496). This record uses pinned source and retained evidence. The production approval path and the deferred adapter implementation require their own evidence.

## Effective approval selection

The [pinned config loader](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/core/src/config/mod.rs#L3954-L3995) rejects an explicit untrusted value in public `approval_policy` configuration. An explicitly untrusted active project defaults to `UnlessTrusted` when the policy field and request overrides are absent. The [thread acknowledgement](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server/src/request_processors/thread_processor.rs#L1730-L1742) reports the effective policy, reviewer and workspace. The [managed requirements fields](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/config/src/config_requirements.rs#L1069-L1080) constrain allowed policy and reviewer. These inputs support the owner-selected untrusted-project route. The design omits the turn-level override.

The [native approval witness](https://github.com/realkarych/kora/issues/1004#issuecomment-6727629422) observed `approvalPolicy: untrusted` with the untrusted project and omitted config policy. Its 15 cases covered the three effect routes and native-rule controls. The [requirements and custody witness](https://github.com/realkarych/kora/issues/1004#issuecomment-6727829732) observed thread-start normalization, turn-start rejection, and the need to protect native rules separately from constraining the policy and reviewer. Those witnesses used the selected executor and a scripted local model in disposable Linux amd64 containers. The policy allow used a fixture permit and verified hook completion. The evidence does not qualify complete rule-source custody, an independent native-only adapter path, alternate producers, macOS or activation.

## Effect identity and timing

Its parsed actions are best-effort display data. The [patch approval path](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server/src/bespoke_event_handling.rs#L641-L668) keys the request to the call's item. The earlier witness used a matching pre-effect file item and a separately staged permit. The implementing slice must demonstrate which native evidence identifies the complete effect and all applicable Policy conditions before a reply. Ambiguity declines, and qualification must cover the admitted routes before complete coverage is claimed.

The pin [prompts for unmatched commands](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/core/src/exec_policy.rs#L805-L825) and [requests approval for nonempty patches](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/core/src/safety.rs#L67-L88) in this mode. The [app-server response path](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server/src/bespoke_event_handling.rs#L1983-L2021) waits for the response and maps unusable file replies to denial. [Turn abort](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/app-server/src/bespoke_event_handling.rs#L1243-L1247) aborts pending server requests. The owning runner supplies the deadline, fence, first cause and actual release. A successful wire decision alone cannot establish after-stop closure.

## Shell ownership decision pending

The [built-in executor shell evidence](codex-managed-shell-controls-probe-2026-11-04.md) establishes default non-login Bash and configured login refusal. The [pinned preparation](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/core/src/tools/handlers/unified_exec/preparation.rs#L216-L244) restricts model shell selection for the remote environment only. The [pinned shell selector](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/codex-rs/core/src/tools/handlers/unified_exec.rs#L151-L177) retains explicit shell selection in the built-in route. The [selected executor shell witness](codex-selected-executor-shell-probe-2026-11-04.md) and [verified Bash witness](codex-selected-bash-pin-2026-11-08.md) qualify the separate executor's shell selection and the bound runtime check for their fixed Linux cases.

An approval-gated built-in executor would move the before-start check of effective interpreter invocation to the adapter's native approval path. The proposed decision keeps physical Bash identity and its launch binding with the runtime and requires the adapter to decline any command whose effective interpreter, invocation, cwd and input it cannot establish from the approved native route. The owner must select that boundary before changing the shell or launch contract. Any later request to remove the executor must qualify both actual interpreter identity at process start and the retained credential, effect and stop guarantees for the resulting topology. The existing witnesses establish no such combined result.

A focused future discriminator for that decision would test a supported inert command on the approved built-in profile and assert the verified interpreter image, non-login invocation and expected output with one acceptance. A refusal case would assert zero process starts when the effective interpreter cannot be verified. A refusal-only result would leave positive shell binding unverified. The candidate is grounded in the retained evidence and launches no new probes.
