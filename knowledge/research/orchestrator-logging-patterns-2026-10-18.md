# Orchestrator logging patterns

Checked: 2026-10-18. Scope: primary documentation for Airflow, Dagster, Python logging and structlog, compared with kora's accepted contracts at `0c1ee5bdc7f390509a42bf75191dde706924d15a`. This is research for [issue #91](https://github.com/realkarych/kora/issues/91), not a runtime experiment or an architectural decision. The resulting contract is [structured component diagnostics](../specs/observability.md).

## Sources and transferable patterns

| Primary source | Observation | Application to kora |
|---|---|---|
| [Airflow logging architecture, pinned 3.1.7 documentation](https://airflow.apache.org/docs/apache-airflow/3.1.7/administration-and-deployment/logging-monitoring/logging-architecture.html) | Component operation and task execution have distinct logging concerns and collection paths. | Keep component diagnostics separate from session output and durable domain events; identify the logical component even in standalone mode. |
| [Airflow task logging, stable documentation](https://airflow.apache.org/docs/apache-airflow/stable/administration-and-deployment/logging-monitoring/logging-tasks.html) | Task context and task-attempt identity support finding the relevant execution output. Python logging integrates with the task logging path. | Join diagnostics with authorized run/node/attempt/session IDs; explicitly bind and reset context across request, task, thread and process boundaries. Do not copy the task-log storage/UI design into a first logging stage. |
| [Airflow sensitive-value masking](https://airflow.apache.org/docs/apache-airflow/stable/security/secrets/mask-sensitive-values.html) | Masking depends on which secret values are known and when registration occurs; capture paths outside the protected flow can escape it. | Register known secrets before output, test alternate handlers and startup errors, and separately prohibit nonsecret payload content. Masking is not proof that arbitrary transformed content is safe. |
| [Dagster logging](https://dagster.io/docs/guides/log-debug/logging) | Structured execution events and raw compute stdout/stderr serve different purposes. | Preserve separate diagnostics, authoritative events and session streams; raw candidate output cannot assert trusted component identity. |
| [Dagster custom logging](https://dagster.io/docs/guides/log-debug/logging/custom-logging) | Configurable loggers and standard log levels support application-specific output behavior. | Centralize entry-point configuration and use the existing decided Python logging stack; providers receive a bound logger. |
| [Dagster Python logging](https://dagster.io/docs/guides/log-debug/logging/python-logging) | Python logger capture is configurable. Excessive captured logging can burden event storage and the UI. | Allowlist third-party capture, bound volume and avoid inserting general diagnostics into kora's event table. |
| [structlog context variables](https://www.structlog.org/en/stable/contextvars.html) | Context isolation and propagation depend on concurrency boundaries; synchronous and asynchronous contexts can differ. | Explicitly test sync/async bridges, concurrent requests, recovery and child processes instead of assuming context variables propagate everywhere. |
| [Python 3.11 logging cookbook: blocking handlers](https://docs.python.org/3.11/howto/logging-cookbook.html#dealing-with-handlers-that-block) | Queue-based producer/consumer separation moves handler work away from the producer. | Use bounded nonblocking enqueue and a separate writer, with explicit byte limits, loss accounting and bounded actual process exit. A queue helper alone does not establish those guarantees. |
| [POSIX write semantics](https://pubs.opengroup.org/onlinepubs/9690949599/functions/write.html) and [Linux pipe semantics](https://man7.org/linux/man-pages/man7/pipe.7.html) | Partial writes and finite atomic-write limits matter for concurrent writers and stalled readers. | One writer per output stream; bounded framed subprocess merging and incomplete-tail handling. A 16 KiB record is not assumed atomic. |

The fetched Airflow stable pages identified version 3.3.2; the architecture source above is explicitly pinned to 3.1.7. Dagster's documentation identified 1.13.26 and structlog's stable documentation identified 26.1.0. These are dated documentation observations, not installed or benchmarked versions. Stable URLs may change after this check. kora's dependency choices remain those of [ADR-0013](../../docs/decisions/0013-implementation-stack.md).

## Design synthesis

The transferable pattern is explicit ownership: a component emits a small structured explanation, an execution stream retains user content under its existing permissions, and a durable transition remains authoritative independently of logging. Correlation uses validated IDs rather than copied payloads. Levels express operational significance; unchanged polling does not create INFO volume. The boundary handling an error owns its safe diagnostic.

kora adds requirements derived from its own execution and threat boundaries: candidate output cannot impersonate trusted supervisor logs; redaction state and incident keys remain finite; a stalled collector cannot hold a transaction or delay execution-stop escalation; loss remains visible independently of the failed sink. These are design inferences from kora's contracts, not claims that either researched orchestrator supplies identical guarantees.

The first stage deliberately requires no managed collector, log database, diagnostic search API, UI log viewer or new tracing dependency. Remote task-log storage and event-database log capture would add retention, authorization and delivery obligations beyond leveled component diagnostics. Existing domain-event export remains opt-in and separate. The specification's queue/record/drain defaults are product constraints, not measured performance results.

## Evidence limits and implementation obligations

No Airflow or Dagster deployment was installed, no comparative load benchmark was run, and no kora logging implementation exists in this change. Documentation establishes patterns, not conformance. The [planning review](../reviews/structured-logging-plan-review-2026-10-18.md) records independent assessment of the proposed contract. Each component's implementing PR must supply the named integration/conformance checks and measurements in the specification, using real output channels and protected runtimes where isolation is claimed. Existing CI and verification gates remain mandatory.
