# Engine transaction-lock foundation

Implementation owner: [#594](https://github.com/realkarych/kora/issues/594), the first prerequisite of the [first-slice engine work](https://github.com/realkarych/kora/issues/593). Baseline: `1b2375236db7da173063951d2f57b55c423fd565`. This record describes internal locking, not implemented run creation, admission, scheduling or execution authority.

## Contract and ownership

The implementation follows [scheduler sections 6, 10 and 12](../specs/scheduler.md), ADR-0020 and ADR-0026. `Database.transaction` installs one writer lease for its existing transaction body. The lease binds the exact asynchronous connection, root transaction and creating task. Body exit invalidates the lease and removes it from the connection's saved information dictionary, including after connection invalidation. Readers, unmanaged connections, different tasks, savepoints and ended or replaced root transactions cannot supply a current engine lock assertion. This is cooperative internal misuse detection, not isolation from malicious Python code.

`TransitionLocks` claims one context from that lease. A run is acquired before any scopes; repeated acquisition of the same run performs no second SQL call. A different run is refused. The complete scope set is acquired once in sorted key order, deduplicating actual keys. A context without a run can acquire scopes for future namespace-policy transactions. Assertions acquire nothing and name the exact requested run/scopes. An unsuccessful try-lock or interrupted/failed acquisition leaves the context unusable; the caller ends that candidate transaction before another candidate. The future caller must still obey the separate rule that no advisory lock follows a row lock.

PostgreSQL uses only transaction-scoped two-integer advisory locks. The fixed classes are run=1, global=2, namespace=3, graph=4, runtime=5, fan-out=6 and target=7. The second integer is the first four SHA-256 digest bytes of compact ASCII JSON encoding of the identity-component tuple, interpreted as signed big-endian. Runs use a one-component run-ID tuple; global uses the empty tuple. Scope identities contain one component for namespace/graph/runtime, three for fan-out, and two for namespace plus target. Composite component boundaries remain unambiguous. Distinct classes cannot alias each other; digest collisions within a class intentionally add serialization and grant no additional logical scope in assertions. Future notification locking has no implementation in this delivery.

The database PostgreSQL engine explicitly selects READ COMMITTED, so reads performed after waiting for an advisory lock receive a fresh statement snapshot. SQLite uses the existing writer lease and `BEGIN IMMEDIATE`; no second mutex is acquired. Lock acquisition creates no background task, pool, shared cache or retained registry. Caller-owned transaction commit/rollback releases actual advisory locks, and the existing database lifecycle owns connection return. Direct transaction cancellation rolls back; `Database.run` retains its existing shielded completion before cancellation returns. A database close deadline does not close an active connection underneath its unit.

## Verification and limits

The focused integration suite is `tests/engine/test_transition_locks.py`, parameterized by the repository's SQLite/PostgreSQL fixture. It exercises deterministic key/order identity, composite separation, scope-only transactions, stale/different-task/read/unmanaged/nested/replaced context refusal, blocking and try-lock contention, fresh reads after scope contention, success/rollback/cancellation, partial acquisition failure, shielded-unit cancellation and shutdown. PostgreSQL cases inspect actual advisory lock ownership; SQLite cases prove writer release. Passive SQLAlchemy events observe acquisition order without substituting behavior. Existing database transaction and architecture tests remain required.

`tests/observability/test_engine_lock_logging.py` covers the engine's DEBUG acquisition diagnostics, safe fields, disabled levels, stalled/broken sink independence and actual transaction release. Diagnostic fields are only the run-lock presence and count of distinct scope keys. Contention has a fixed DEBUG message; database rollback retains persistence-failure ownership. No run ID, namespace, target text, SQL parameter or payload is copied into these records. These checks activate only the internal engine-lock diagnostics; committed run/attempt/event diagnostics remain with their transition owners under #593.

Local macOS CPython 3.11.17 verification: `KORA_TEST_DATABASES=sqlite uv run --no-sync pytest tests/engine/test_transition_locks.py tests/observability/test_engine_lock_logging.py tests/db/test_transactions.py tests/architecture -q` passed 956 tests in 38.77 seconds. Whole-repository Pyright reported zero errors/warnings; Ruff lint and format checks passed. The earlier lock-only check passed 14 tests. The local Docker daemon was unavailable; local results do not establish PostgreSQL coverage. The implementation PR owns the final source revision, focused regression results, independent correctness/performance findings and complete Linux/macOS CI evidence. No process-wide heap, RSS, latency or starvation guarantee is inferred. Existing database lifetime checks and future signal lock deadlines and scheduler latency gates remain active with their respective consumers.
