# Native custody implementation evidence and delivery plan

Checked 2026-11-15 against `4d246192132cfbe56435841168b31f634f61d42a` for [#1580](https://github.com/realkarych/kora/issues/1580). This is source/design evidence, not executable custody or installation qualification. The owner [approved preparation](https://github.com/realkarych/kora/issues/1580#issuecomment-6893484560) of the [native companion](../specs/execution-custody-native.md). The independent authority mechanism was already [accepted in #1575](https://github.com/realkarych/kora/pull/1575#issuecomment-6886916062); its native refinements still require owner acceptance.

## Delivered design and boundaries

The companion fixes the journal's row shapes, ownership order, original COMMIT phases, read/migration bypass obligations, native recovery procedure, explicit multi-commit schema bootstrap before the first frontier, whole-image producer, invocation closure and concrete qualification method. It preserves #1575's placement, serialization and capacity decisions. No production code, schema migration, public operation, dependency, import allowance, supported-platform change or runtime activation is delivered.

The [previous inventory](execution-custody-authority-2026-11-15.md) remains a historical source snapshot. Its 1,900–3,300-line estimate did not identify native fields or every writer route and was not a proof of indivisibility. An [independent delivery-cut assessment](https://github.com/realkarych/kora/issues/1580#issuecomment-6893190586) found no established smaller useful first consumer; that planning result does not replace review of the actual new native design.

The concrete new decisions are rollback-journal DELETE/EXTRA for the independent journal, bounded native rows and page allocation, lifetime/commit/recovery lock ownership, original transaction status preservation, PostgreSQL read-only enforcement and active-profile migration refusal, separate operator checkpoint recovery, coherent image ownership and the system-crash method. They remain proposals, not retroactive claims about #1575's approval. Existing metadata SQLite WAL/FULL remains unchanged.

## Native sources checked on 2026-11-15

These sources establish native semantics, not that a particular installed host passes qualification.

- [SQLite synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous): EXTRA adds rollback-journal directory synchronization to FULL. The proposed journal selects DELETE/EXTRA; metadata keeps its existing WAL/FULL contract. Native full-sync fallback and actual device persistence still need observation.
- [SQLite backup API](https://www.sqlite.org/backup.html): a completed native backup produces a coherent snapshot. Native completion/error handling and a correctly owned destination are part of the proposed producer; freshness relative to the independent frontier is a separate kora assertion.
- [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html) and [Apple's flock manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html): locks are cooperative, nonblocking acquisition is available, and inherited/duplicated descriptors refer to shared lock ownership. The child must close its inherited descriptor without explicitly unlocking the parent's lock; noninheritability alone addresses exec, not fork.
- [PostgreSQL transaction information](https://www.postgresql.org/docs/16/functions-info.html): `pg_current_xact_id()` identifies the original top-level transaction; `pg_xact_status()` reports recent committed/aborted/in-progress state and may return NULL after status removal. The proposed design treats NULL as unknown. Cluster control identity is an input, not unique proof against physical cloning.
- [PostgreSQL CHECKPOINT](https://www.postgresql.org/docs/16/sql-checkpoint.html): the command forces a physical checkpoint and requires superuser or `pg_checkpoint` privileges. Its proposed recovery-only use does not prove a stronger replication policy and gives no privilege to ordinary core/worker credentials.
- [PostgreSQL physical backup and recovery](https://www.postgresql.org/docs/16/continuous-archiving.html): physical base state plus WAL supports native recovery; logical dumps do not supply that replay input. The proposal additionally requires the exact independently retained custody frontier and original issuer exclusion.

The earlier inventory's [native evidence limits](execution-custody-authority-2026-11-15.md#native-evidence-limits) retain their primary references for WAL, cache/device behavior and manifest verification. No source claims that setting a pragma, finding a PID absent, comparing a digest or reading a transaction status alone establishes the complete custody guarantee.

The combined planning range is **2,700–4,350 added plus deleted handwritten production lines**, including composition and migrations, excluding only tests, documentation and generated files. Rows are responsibility estimates, not independent PRs or measured diffs. The new inventory adds migration/read bypasses, native-outcome ownership, concrete restore and the absent upload producer to the earlier estimate. API transport needed by the first actual upload route must retain its CLI/MCP parity in that same deliverable; it is included as risk in the consumer range and needs an actual complete-diff estimate before code.

The dependency boundary is explicit: journal/native settlement must precede reliance; all writers must participate before any such reliance; exact original invocation/closure must precede acknowledgment; and coherent startup must precede renewed effects. A journal without a relying production consumer is unfinished infrastructure, while cleanup without an admitted upload producer has no real owner to retire. Splitting these four rows verbatim would leave those gaps. Sharing source modules or postponing qualification does not make them independently useful outcomes.

No independently mergeable sub-1,000-line first outcome is demonstrated. This is **not** a lower-bound proof and requests no exception. Before implementation, the owner must receive either a concrete smaller complete delivery with files, dependency/activation boundaries and credible full-diff count, or a bounded indivisibility proposal proving why independently useful intermediate behavior is unavailable. The present design does not authorize production edits while that question is unresolved. Native deployment qualification also needs an actual disposable environment and producer; a named future method is not passing evidence.

Subsequent durable request/sealing, accepted StructuredOutput, command captures and AgentSession retention remain separate complete deliveries in [execution content](../specs/execution-content.md#7-activation-and-complete-implementation-deliveries). Validator #1361, Worker #1453/#1454 and scheduler #1472 retain their own work. This design neither claims them implemented nor makes them dependent on arbitrary new helper-only PRs.
