# AI development verification

This development workflow was designed under [issue #87](https://github.com/realkarych/kora/issues/87). Its scope is contributor verification in Codex and Claude Code, not kora's product harness skill packages. [AGENTS.md](../../AGENTS.md) requires the checkpoints; [kora-verify](../../.claude/skills/kora-verify/SKILL.md) owns routing and evidence. Product behavior remains in the specifications and their cited decisions.

CEL numerical-calibration amendment dated 2026-10-23: the project owner approved lightweight validation and a 100 ms target under [issue #167](https://github.com/realkarych/kora/issues/167#issuecomment-6351849696); the corresponding human-facing documentation wording was reviewed line by line and approved by the project owner on 2026-10-23.

## Minimal inventory

There is one canonical skill in `.claude/skills/kora-verify`, exposed to Codex by the relative directory symlink `.agents/skills/kora-verify`. `CLAUDE.md` imports `AGENTS.md`. Five reference profiles define distinct reviews: correctness, code condensation, browser behavior/diagnostics, controlled performance measurement and security boundaries. The skill is the single review router across planning, implementation, shipping and local/native entry points. Complete component/profile coverage maps to independent single-profile assignments; related components may share a bounded assignment. Different profiles remain separate independent contexts. The parent reconciles coverage; only the development coordinator implements fixes.

Correctness spans the component contracts, so separate permanent architect, API, database, documentation and test-writing agents would duplicate ownership. Browser and performance remain separate reviews because performance needs an uncontended measurement environment and an explicit conclusion beyond successful interactions. Security owns threat-based reasoning beyond correctness and scanner output. References avoid duplicated host-specific agent definitions. No custom router, report validator, extra command skill or global plugin configuration is required.

[Condensation](../../.claude/skills/kora-verify/references/condensation.md) independently challenges unnecessary implementation growth, duplication, abstractions and low-value tests under [issue #185](https://github.com/realkarych/kora/issues/185). The skill selects it for relevant implementation designs and source/test/tooling/dependency changes, including deletions and renames, without adding a review to unrelated editorial changes. Findings identify a simpler alternative and preservation evidence; shared extraction respects semantic ownership and package layers, and test consolidation maps removed behavior to retained coverage. This adds a review responsibility without a size quota or authority to weaken existing checks.

Independent plan review checked minimality, invocation and component coverage. The accepted corrections made scope semantic as well as path-based, included renamed/deleted/untracked files, protected existing obligations against policy edits, separated design from executable evidence, and included installed-provider and product-skill coverage. The [dated host evidence](../research/ai-development-host-support-2026-10-18.md) records earlier observations, not current delegation policy. Native subagent support is an operating assumption; a new capability experiment or access to internal traces is not required.

## GitHub review entry point

Root `AGENTS.md` directs native Codex Review to the same skill's GitHub reviewer mode. The native coordinator identifies direct/transitive coverage, matches qualifying existing results to bounded single-profile assignments and dispatches fresh agents for missing work. Descendants subdivide uncovered scope with a recorded reason and parent ownership. All inherit the native read-only prohibition on PR code execution, installation, edits and independent publication. The development coordinator resolves findings and supplies executable evidence. No fixed reviewer quota may remove applicable coverage.

A PR comment containing `@codex review` requests native review without naming the skill. For automatic review across contributors, a maintainer must configure the repository's Automatic review setting for **All PRs** in [Codex review settings](https://chatgpt.com/settings/code-review), rather than rely on each author's personal preferences. Configure the review trigger to cover new PR revisions as well as initial review, and verify a result for the current head before merge. An unsupported or inaccessible trigger/settings control is an activation gap; manually requesting a missing head covers that review, but does not establish automatic coverage.

This is the AI review stage of the PR workflow alongside [executable CI](../../.github/workflows/ci.yml), using the existing native integration. Repository files define what it reviews; they cannot activate account/repository settings or merge protection. Record the actual setting/trigger coverage and missing activation work in the implementing issue/PR. Fork and bot-authored PRs require the same coverage; installation, eligibility or quota failures do not waive it. No extra bot, privileged comment Action, credential, executor or personal plugin is required by these rules.

A native aggregate verdict counts only for the results it exposes. Reuse actual revision-matched component/profile conclusions when available; obtain missing specialist results locally if the host cannot expose them. Do not turn unavailable internal traces into a prerequisite capability test, invent a finding for a status report, or infer runtime measurements from a clean review. Executable checks and required merge statuses remain separate obligations.

## Review assignments and reuse

[Issue #252](https://github.com/realkarych/kora/issues/252) changes assignment mechanics and duplicate review stages, not the component checklist, profile triggers or executable gates. The coverage matrix lists every affected component/profile obligation and integration owner. The assignment ledger lists each independent reviewer/result once, with the covered components, common contract and grouping reason. One result cannot satisfy several independent profiles. A generic workflow's checkpoint does not itself justify another reviewer.

Qualifying reuse requires actual independent results with matching scope, source/contract/evidence inputs, revision and execution restrictions. The coordinator verifies that provenance and requests missing work. A review request, implementation-authored report or aggregate clean verdict cannot fill an assignment. Native invocation and automatic-review activation remain distinct from result reuse.

At readiness and after changes, compare inputs and re-evaluate coverage. The existing independent reviewer may perform bounded reassessment, identifying supported and invalidated conclusions against the new inputs. Changed contracts, trust/resource boundaries, dependencies/configuration, trusted policy or evidence invalidate affected conclusions. Missing comparison or reassessment remains unverified. Implemented behavior still needs readiness review; a planning verdict proves neither runtime behavior nor final committed-revision checks.

The following methodology cases apply in local and native routing. They define review expectations, not automated dispatch enforcement or measured token savings.

| Routing case | Coverage and assignment outcome | Evidence that must remain distinct |
|---|---|---|
| Related components, two profiles | An API contract and its Python/TypeScript consumers may share one bounded correctness assignment and one separate security assignment; enumerate each component and both sides of each boundary. | Each profile's actual result covers the enumerated consumers and shared contract; missing consumers remain uncovered. |
| Unrelated trust or resource boundaries | Split independent authentication and subprocess-cleanup scopes when one bounded assignment cannot inspect both adequately; record the split reason and parent ownership. | Every applicable component/profile obligation remains mapped; no fixed reviewer cap overrides coverage. |
| One reviewer offered for several profiles | Keep correctness, condensation, browser, performance and security in separate contexts whenever selected. | A general step-review verdict does not establish several independent profile results. |
| Duplicate generic/local/native review | Map an actual qualifying result to the matching assignment once; dispatch missing work rather than automatically repeating fulfilled coverage. | Verify independent origin, exact scope/inputs, revision and restrictions; required native invocation is not waived. |
| Changed contract or evidence input | Reopen affected conclusions and obtain bounded reassessment from the existing independent reviewer, or a new assignment if unavailable or no longer independent. | Compare old/new inputs explicitly; a renamed report or old pass cannot qualify a new head, and final-head CI remains required. |
| Unavailable or implementation-authored evidence | Mark the missing independent result unverified or blocked and obtain it; retain supported portions separately. | Neither an implementation-authored report nor a generic clean native response proves missing reviewer work or executable evidence. |

## Component checklist

Use [the knowledge index](../README.md) for exact contracts and ADRs. This checklist identifies navigation families, not indivisible agent assignments or a second architecture specification. Split a family into actual affected components with distinct contracts, state/resource owners or failure boundaries. Every affected component receives correctness review; the skill selects other profiles from its effects. Follow the skill's transitive-impact procedure, assign each integration boundary an owner and map every component/profile obligation to a bounded single-profile assignment. Add new implementation areas when their first PR lands. The final column selects measurements under the performance profile's [common lifecycle method](../../.claude/skills/kora-verify/references/performance.md#resource-lifetime-measurements); runtime checks activate with implementation, not merely because this table names them.

| Component family | Check focus | Performance and resource-lifetime workload |
|---|---|---|
| DSL/compiler/presets | Determinism, precedence, source locations, client-side Python execution and IR/schema agreement | Compile increasing graph/preset sizes repeatedly; measure CPU, peak/retained memory, temporary structures and bounded caches. |
| IR/CEL/Jinja/graph validation | Types, cycles, references, bounded evaluation, fan-out/subgraphs and hostile input | Validate/evaluate increasing node/edge/expression sizes, including the NFR-3 workload; track native/Python allocations, compiled-expression/template caches and failure cleanup. |
| Metadata/state/lineage/retention/cost | Both databases, immutable history, result authority, usage completeness/deltas, retention and arithmetic | Exercise read/write/retention and retry cycles on both databases; count queries, pool checkouts, sessions/cursors and retained objects. Separate required durable history from disposable state. |
| Scheduler/admission/triggers/waits/retries | Idempotency, locks, capacity/target holds, stale observations, deadlines, recovery and provider-stall fairness | Measure admission/scheduling latency and incremental work; repeat waits, cancellation, stale-result and recovery cycles. Count tasks, timers, dispatcher slots and correctly retained/released reservations. |
| API/shared Python client/CLI/MCP/generated TypeScript | Operation/schema parity, structured errors, auth, idempotency, pagination, streaming and noninteractive use | Split the surfaces: API pagination/stream/disconnect load, Python client close/cancellation, CLI/MCP repeated invocation and shutdown, generated-client stream aborts. Track buffers, sockets, descriptors and tasks. |
| Product harness skills/shared references | Generation drift, every operation/example and error/recovery hint; installation in user sessions | Check generated reference/context size and repeated load/lookup work; runtime measurements apply to an implemented generator or consumer, not to Markdown itself. |
| Worker/supervisor | Epoch fencing, original-domain adoption, checkpoints, journal authority, descendant shutdown and disconnected operation | Split worker and supervisor lifecycles: submit/recover/cancel/finalize and shutdown; measure relay memory, tasks, pipes, descendants, journals and unresolved handles without premature release. |
| Runtime protocol/local/Docker | Shared conformance, lifecycle, deadlines, idempotency/recovery and actual protected-runtime evidence | Repeat local/Docker create/start/stop/release and recovery paths; confirm actual descendant/container termination, workspace/volume cleanup, descriptor counts and startup latency separately. |
| Harness adapter protocol/fake/Claude/Codex | Recorded SDK streams, normalization, usage/liveness, version compatibility, hermetic configuration and policy interception | Replay bounded SDK event workloads incrementally; reconnect/cancel/close and count retained messages, tasks, callbacks and harness/MCP processes. Recorded streams do not prove live compatibility. |
| VCS protocol/Git/other providers | Unchanged canonical graph, inspected revision/destination, history, response-loss reconciliation and no unintended overwrite | Use real local Git operations and disposable remotes; repeat checkout/seal/publish failure/reconciliation and track processes, pack/temporary storage and response buffers. |
| Approval-channel protocol | Bound content, invalidation, permissions, expiry, durable delivery and uncertain cleanup | Repeat delivery, expiry, invalidation and uncertain cleanup; measure response bounds, tasks, client connections and retained form payloads versus required compact delivery metadata. |
| Secrets protocol | Namespace rights, minimal environments, redaction, phase-limited credentials and no stored resolved values | Resolve/rotate/release credentials through configured providers; measure registrations, bounded caches, file handles and redaction matching cost without exposing secret values in evidence. |
| Artifact-storage protocol | Digests, integrity/size bounds, upload/download, retention/failures and local/S3-compatible behavior | Exercise bounded upload/download/cancel/failure and retention; measure streaming throughput/memory, open files/connections and partial-upload/temporary-storage cleanup. |

| Observability-exporter protocol | Correlation, bounded buffering, outage independence, drop metrics and redaction | Measure event/redaction cost, queue bytes and sustained slow/broken sinks; verify bounded loss and shutdown. Include process/pipe/merger memory and continued core progress. |
| Authentication protocol | Namespace/object access, user/service separation, approve/platform/transcripts, cookies/CSRF and tokens | Repeat login/validate/logout/expiry/denial; measure validation/query work and bounded token/session/cache retention with real API/provider integration. |
| Sensor protocol | Duplicate events, bounded polling, expiry/cancellation, stale ownership and outage isolation | Repeat polling, timeout, duplicate delivery, cancellation and stale-owner results; measure polling cost, pending tasks/connections and payload cleanup. |

| Provider registry/configuration/distribution | Installed local third-party fixture, `kora.provider` discovery/metadata/configuration, plugin listing and external conformance without core imports | Load/configure/close an installed third-party fixture repeatedly; measure discovery cost, module/provider caches and owned clients/threads/tasks. ## Activation and completion

### Component diagnostics

[Structured component diagnostics](../specs/observability.md) applies across every component row above, beyond the observability-exporter protocol. Its [activation matrix](../specs/observability.md#7-component-coverage-and-activation) names component and all eleven provider obligations; its [future evidence table](../specs/observability.md#8-future-executable-evidence) defines named integration/conformance scenarios. Issue #91 owns pending inventory until each implementation issue assumes its rows before code starts. The first real backend consumer ships shared logging infrastructure and tests; subsequent component PRs include their applicable diagnostics and evidence. The existing shell's functional browser and owned-resource release obligations remain active, with the numerical exclusion below.

Correctness reviews levels, event ownership, context and stream separation for each changed component. Security reviews content, identity and channel boundaries; performance reviews bounded work, noise, loss and sink independence. Changes to collection, redaction, propagation, buffers or sinks select all three profiles at planning and readiness, including contract-only changes. This extends the same component/profile routing in local and native review, without a separate observability profile or replacement for executable checks.

| Example scope | Observability selection and evidence |
|---|---|
| Scheduler behavior | Correctness checks events/levels/context; performance and any other matching profiles remain required; real integration covers volume, durable events and sink independence when implemented |
| Redactor or sink change | Correctness, security and performance before plan/readiness; content, lifetime/cost, saturation and shutdown evidence |
| CLI output | Correctness checks exact stdout and request IDs; existing client/backend semantics select other applicable profiles; changed collection/sinks select all three |
| Provider-only logging | Provider name/path is no exemption: bound-context/output changes select all three; conformance and real core integration provide evidence |
| Editorial documentation only | Record the concrete applicability reason; no invented runtime logging tests; every PR still receives correctness and security applicability assessment |
| Logging deletion or rename | Inspect removed behavior and semantic effects using stricter base obligations; required coverage cannot disappear with the filename |

### Browser benchmark exclusion

The owner-approved [issue #179 removal amendment](https://github.com/realkarych/kora/issues/179#issuecomment-6329273349) removes the experimental numerical browser loading/memory benchmark and its calibration workflow. The exception covers the current console shell's base/head loading statistics, Chromium and Node heap/retainer measurements, GC/snapshots, native RSS trends and calibrated regression budgets. These checks are removed, not passing or pending calibration; historical failures remain unresolved. The current shell has no numerical loading or memory-regression guarantee.

Functional production/development smoke, readiness and deadlines, six failure scenarios, ordinary/forced/report-collision cancellation, exact owned PID/descriptor/proxy/temporary cleanup, network restrictions and bounded safe artifacts remain mandatory through `test:browser`. The [browser protocol record](../research/console-browser-checks-2026-10-21.md#current-console-functional-v1-protocol) defines the retained command and evidence. Separate applicable resource-ownership and security review remains required. This exception does not reduce backend, CEL, database or other component performance/lifetime requirements, nor waive future console journeys; new numerical browser checks need a separately approved method and activation.

### CEL numerical calibration exclusion

The owner-approved [issue #167 amendment](https://github.com/realkarych/kora/issues/167#issuecomment-6351849696) replaces exhaustive CEL coefficient fitting, RSS-envelope and GIL calibration, native crash-threshold searches and the five-job collection with the [compact cost-regression protocol](../research/cel-cost-calibration-2026-10-22.md#current-compact-regression-protocol) and golden estimates. The removed checks are not passing or pending calibration gates. Historical failed-budget evidence stays failed, and the qualified conversion collection establishes only its stated smaller-bound selection. The unchanged provisional weights and regex tables, 100,000,000,000,000-unit logical steps budget and 16 MiB logical estimate establish no universal time, RSS or native crash-margin guarantee. The fixed-case observed target is 100 ms, not an interruption deadline.

The compact suite and ordinary golden/specification checks are required, together with existing functional boundary/conformance, static, logical-cost/refusal, resource-ownership and evaluator-lifetime checks. The existing dedicated evaluator measurement job and its required status remain; the compact report is a separate artifact with revision provenance. Browser, logging, database, provider, scanner and security obligations remain unchanged. The `cel` diagnostics activation row and future API/scheduler error ownership in [observability.md](../specs/observability.md#7-component-coverage-and-activation) remain active or pending with their existing owners. Schema-driven checking/projections, native minimum-int negation correction and real consumer integration remain prerequisites. Scheduler/API validation, transaction duration, fairness, NFR-3.1 and large-scale workloads activate in their implementing issues; the logical allowance and compact cases cannot satisfy those measurements. Pin changes repeat the retained checks; a newly exposed workload gap needs an explicitly approved measurement method.

### Existing activation rules

The repository now has a typed Python scaffold, runnable React shell and builds; the API, scheduler and execution engine remain subsequent implementation work. Use the actual revision and [development instructions](../../docs/development.md) to determine activation. The shell’s functional browser and owned-resource release obligations are already active under the explicit benchmark exclusion; absent commands for an existing capability are a coverage gap, not proof that the capability is unimplemented. Unimplemented capabilities are `pending implementation`; an existing capability that cannot be checked is `blocked`. The installed-wheel and archive-content tests were removed by owner decision under [issue #112](https://github.com/realkarych/kora/issues/112); packaging reviews cite that issue for the missing check instead of reporting it as a new coverage gap.

- The first executable backend component activates relevant integration/conformance and performance checks even without a UI. Preserve strict static checks, both databases, supported platforms and deterministic tests under `AGENTS.md`.
- A frontend package-only scaffold activates build/static checks. The first runnable shell activates Playwright boot/diagnostics/basic accessibility and exact owned-resource release checks. Every subsequent frontend/backend change runs common smoke plus affected journeys and separate applicable performance checks, subject to the explicit numerical browser benchmark exclusion above.
- Each view/action adds its journey and negative-case coverage. When implementation starts, record executable versus pending segments in the existing pilot-scenario document; both complete pilots are required before console/MVP completion.
- Each provider feature adds its conformance gate. Protection claims require real protection tests; supported harness versions additionally need documented manual live compatibility probes outside deterministic product CI.
- Each activation PR registers actual local commands and CI jobs, evidence, budgets where applicable, and required merge statuses. Include any owner/admin configuration gap. Missing tools are never silently installed or counted as passing; dependency adoption follows repository policy.

Each implementation issue owns its pending activations and concrete trigger, rather than a generic future TODO. Existing required checks cannot be downgraded because a feature was renamed or removed. Open architecture proposals and issues, including #41–#46 and #71, are not accepted contract overrides.

Prompt routing is procedural, not deterministic enforcement. Native delegation is an accepted operating assumption, not a measured capability claim. Reviewers inspect source and actual results; an implementation-authored report alone does not prove independent execution. Required CI statuses enforce executable checks, with all mandatory jobs passing on the final PR revision and the whole pipeline remaining below ten minutes. Long optional exploration can supplement, but not replace, required coverage.
