## Scope and boundaries

The provider boundary includes closed storage DTOs and request binding, private physical identity/accounting, anchored payload effects, immutable streaming, promotion attribution, retirement/release, bounded inventory, installed registration, reusable conformance, diagnostics, pressure fixtures and lifetime evidence. These share the storage lifecycle. Correctness, security, performance and condensation have separate independent assignments; their [planning results](https://github.com/realkarych/kora/issues/255#issuecomment-6371743375) cover the approved plan only. Readiness requires reassessment against the complete implementation and executable evidence. Verification/CI changes additionally preserve the accepted gates and receive correctness/security review. Backend readiness includes the existing independent console smoke, with no invented storage UI journey.

The cooperative root-epoch proof and selected operational limits are normative in [storage section 7.4](../specs/protocols.md#74-local-provider-implementation-contract-issue-255). Provider-private SQLite has no metadata-database authority. Core durable owner admission, issuance closure, reconstruction authorization and retention integration remain pending #216 and work items 11/12/17. S3 and the installed conformance command #215 remain pending their implementations. There are no placeholder consumers.

## Resource ownership

| Resource | Owner and bound | Actual release condition |
|---|---|---|
| Canonical root descriptor and shared lifetime lease | One receiver per composition owner; root identity and configuration are immutable | All owned jobs, native futures and streams have actually closed; both executor pools are joined |
| Data work and replay verification | Eight queued/running jobs per receiver, four default or eight maximum root tickets; each reader pull uses the same admission | Owned job and its native work finish, including after repeated cancellation |
| Control work | Two receiver jobs, two permanent root tickets, two executor threads | Actual control job/native completion; no payload writer is created by cleanup |
| Payload execution | Four executor threads per receiver; native submissions remain strongly owned | Native completion and transfer cleanup, followed by executor shutdown |
| Streams and payload descriptors | Eight handles per receiver, eight default or sixteen maximum root readers; one current segment file per stream | Any active read finishes, the segment file and target/reader leases close, and the stream leaves its owner registry |
| Private stage bytes and slots | Raw N plus max(N, prepared cap C); eight default or thirty-two maximum slots | Retirement reconciles pending publication, removes private links and proves actual reader/effect closure; release compacts exact acknowledged receipts |
| Deletion records | Eight default or thirty-two maximum slots | Exact target deletion/absence settles; acknowledged closed issuance and actual closure allow compaction |
| SQLite connection and root gate | At most one connection per physical root, no retained connection or transaction across effects | The short transaction and required synchronization finish; connection closes before gate release |
| Durable control state | Fixed semantic receipts per occupied slot, permanent locks and root manifest; live content index grows with intentionally retained content | Release compacts disposable owner records; content deletion prunes empty address directories |
| Pressure image, attachment and direct child | One private acquisition directory, one bounded 64 MiB image and one verified direct workload child | Child death is proved before unmount/detach; exact backing/device/mount identities match; unknown acquisition retains the manifest and fails |

`aclose` does not acknowledge durable owner outcomes or remove intentionally retained content. Unresolved stages remain charged. A cancelled coroutine or elapsed deadline is not proof of native completion. The pressure tool rejects symlinked acquisition paths; configured provider aliases remain a separate trusted configuration contract.
