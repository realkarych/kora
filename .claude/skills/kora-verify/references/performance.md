# Performance review

Act as an independent reviewer. Read `AGENTS.md`, affected specifications and NFR-3 in `docs/requirements/non-functional.md`. Apply only performance to the assignment's enumerated components and boundaries under the parent skill's grouping, result-matching and reassessment rules. Delegate narrower uncovered scope only with a recorded reason and inherited revision and permissions; own the combined conclusion and report descendant assignments. No source edits, commits or publication. Native GitHub mode inspects existing evidence without executing PR code. Return measurement evidence and limitations using the parent skill's format.

Before implementation, review complexity, bounded work, query/stream behavior and performance-sensitive architecture. After frontend/backend changes, measure the relevant executable components even if no console exists yet. Use registered local/CI commands. Missing tooling for an implemented capability is blocked; an unimplemented capability names its activation issue and trigger. Neither is a passing benchmark.

Declare datasets, workload, sample count, metrics and regression decisions before running. Compare base and head with the same production build configuration, browser/tool versions, runner resources and database state. Retain all samples and environment details. Run uncontended and serially; a noisy or invalid run needs a documented cause and complete replacement measurement, not reruns until green.

- Backend: compiler/IR scale, API latency and payload size, database query work, scheduler throughput/latency and incremental streams. Exercise the relevant SQLite and PostgreSQL paths. NFR-3 requires scheduling latency below five seconds at MVP scale, reports runtime startup separately, and requires nonpathological validation/scheduling of 1,000-node materialized IR.
- Browser: apply the [owner-approved numerical benchmark exclusion](../../../../knowledge/reviews/ai-development-setup.md#browser-benchmark-exclusion) to the current console shell. Its functional readiness/deadline, failure/cancellation and exact owned-resource release checks remain mandatory. Numerical loading, heap/snapshot and native RSS regression measurements and calibration are removed; future numerical checks require a separately approved method and activation. Record lab versus field meaning for any later approved measurements; TBT is not INP.
- Establish baselines from measured representative runs when a component first becomes executable. Record justified budgets in the implementing PR and durable configuration; do not invent a zero baseline or arbitrary threshold. Budget increases or reduced coverage need explicit owner approval.
- Diagnostics: apply [bounded output](../../../../knowledge/specs/observability.md#6-bounded-output-and-failure-behavior). Cover disabled levels, INFO/DEBUG, oversized records, redaction registration/rotation/matching, incident-key cardinality, total process/pipe/merger memory, sustained saturation and real blocked/broken sinks. Measure continuing core progress and actual process exit, including shutdown hooks; logging cannot delay execution-stop escalation. Verify poll frequency does not create INFO noise, loss is independently visible and diagnostic metrics preserve existing bounded operational dimensions. Product queue defaults are not measured performance budgets.

The first executable backend activates its measurements independently of console readiness. A frontend package alone has build/static checks; the current runnable shell activates functional browser and owned-resource release checks under the explicit numerical benchmark exclusion, then features add their applicable journeys and approved interaction/large-data workloads. Preserve the whole CI pipeline's ten-minute budget through parallelization and consolidation; do not silently drop required coverage or move it to optional schedules. Runtime performance remains unproved until those measurements exist.

## Resource lifetime measurements

Use the [component checklist](../../../../knowledge/reviews/ai-development-setup.md#component-checklist) to select the workload and resource counters for the assigned component. Scope these checks to the changed lifecycle and transitive consumers; a fast happy path does not establish leak freedom. The current console shell follows the explicit benchmark exclusion above: inspect and exercise retained resource ownership/release without reinstating deleted statistical loading or memory measurements. Backend, CEL, database and other component measurements remain required.

1. Inventory acquired resources, owner, maximum retained size and release condition. Include Python and native allocations, async tasks, threads, timers, subscriptions, connections, descriptors, processes, containers, temporary workspaces and registrations where applicable. Distinguish disposable state from required durable history, bounded caches and unresolved execution/recovery records; cleanup must not violate their contracts.
2. Declare warm-up, input sizes, concurrency, cycle/sample counts, measurement points and justified budgets before execution. Measure base/head under identical conditions. Repeat complete acquisition/use/release cycles for success, real error paths, cancellation, timeout, disconnect/reconnect, recovery and shutdown as applicable. Use real components and injected protocol fakes under repository testing rules, never runtime patches or live model calls.
3. Wait for explicit completion/cleanup conditions with deadlines before post-cycle samples; do not use sleeps to conceal unfinished cleanup. Inject time for expiry decisions and use real lifecycle evidence for process exit. Run repeated cycles in one long-lived process to expose accumulation, with independent process runs for variance; restarting after every cycle alone can hide a leak.
4. Record peak and post-quiescence memory plus resource counts throughout the run. Use allocation snapshots/retaining paths for Python objects and browser heap where supported, and process/native memory plus descriptor/task/process/container counts for resources those heaps omit. Record exact tools and counter meaning; Python heap alone misses native allocations, and flat RSS alone does not establish cleanup.
5. Compare growth per cycle, steady-state plateaus and release conditions against declared budgets and the accepted contract. Distinguish allocator high-water retention and intentional bounded caches from retained live resources. A shared leak in base and head still fails the cleanup contract. Attribute unexplained growth with allocations/retainers or owned-resource evidence; do not invent a zero-memory target or label a single snapshot leak-free.
6. Preserve all samples, workload/environment, commands, revision and failure/cleanup evidence in PR-linked CI artifacts or local evidence. Report unavailable counters and paths explicitly. Implemented but unmeasurable requirements are blocked/unverified; unimplemented components name their activation issue and trigger. Native reviewers inspect this evidence and request missing measurements through their result, without running PR commands.

The first implementation of each component registers its actual lifecycle/performance commands in local development instructions and CI with the owning integration/conformance suite. Extend those checks with each relevant lifecycle change. Measurements share the existing ten-minute CI budget; no optional schedule or reviewer narrative replaces required executable evidence.
